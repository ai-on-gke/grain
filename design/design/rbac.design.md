# Basic RBAC: admin, writer, and reader roles

**Owner:** @bwsalmon

**Specified by:** [`rbac.spec.md`](../spec/rbac/rbac.spec.md)

**Status:** Superseded by [`docs/design/access-rbac.md`](../../docs/design/access-rbac.md) (task 2969). Not implemented as written.

> **Superseded.** Grain implemented roles as API scope sets (`grain/viewer`, `grain/contributor`, `grain/operator`, or sets a deployment declares), checked by the same route scope table that checks agents. It did not implement the fixed `admin`/`writer`/`reader` roles proposed here. [`docs/design/access-rbac.md`](../../docs/design/access-rbac.md) describes what is built, and [`rbac.spec.md`](../spec/rbac/rbac.spec.md) maps each part of this proposal to what replaced it. This document is kept as the record of the proposal.

**The core rule:** Every admitted human or service principal resolves to one of three ordered roles (`admin > writer > reader`) from database-backed allowlist entries and an immutable deployment-owner floor, enforced at a single server-side check point (`ui.RequirePermission`) across HTTP, WebSocket/SSE, MCP, and CLI calls; agents acting on a person's behalf intersect their own `api:*` scopes with that person's current role and can never exceed it.

## Context

[`authentication.design.md`](authentication.design.md) verifies caller identity through `ui.IdentityVerifier` (IAP or a registered signed-header proxy) and admits allowlisted callers, while [`operator-attribution.design.md`](operator-attribution.design.md) records the acting `model.Principal` and `OnBehalfOf` on every mutation via `ui.RequestActor(ctx)`. Until now, every admitted principal had full operator powers. Shared team deployments and self-service registry instances ([`hub.design.md`](hub.design.md), [`simple-config.design.md`](simple-config.design.md)) need teammates who can file, review, and `Submit` tasks without changing connections or secrets (`writer`), and stakeholders who can read tasks, conversations, and CI logs without changing anything (`reader`).

## 1. Roles and role assignment

Grain defines three fixed, deployment-wide roles ordered `admin > writer > reader`:

- **`admin`:** full control over the deployment, including all configuration (settings, `config_mode`, git and model connections, repositories, capability servers and policy, scope sets, write-only secrets, hostds, users and roles, `grain/config`, upgrades, restarts, and `force-merge`).
- **`writer`:** creates and operates on tasks and their pull requests (file, edit, reorder, approve ordinary proposals, comment, chat with the director, run/cancel CI, `retry-merge`, `Submit`, run schedules and suites, approve/reject pending releases, acknowledge/clear notifications), with **no configuration access**.
- **`reader`:** views tasks, boards, conversations, transcripts, pull-request diffs, CI runs and job logs, schedules/templates/suites, the inbox, and deployment health/metrics, and **changes nothing**.

### Where roles live and how they resolve

- **Per-entry roles (`user:`, `group:`, `domain:`, `serviceAccount:`).** Each entry on the allowlist pairs a principal pattern (`authentication.design.md` §3) with a role (`admin`, `writer`, or `reader`). Startup/CLI flag syntax extends `-ui-allowed-principals` (`$GRAIN_ALLOWED_PRINCIPALS`) with an optional `=<role>` suffix (for example `user:alice@example.com=admin,group:eng@example.com=writer,domain:example.com=reader`).
- **Highest role wins.** When a verified caller matches multiple entries, the most permissive role (`admin > writer > reader`) wins, so a broad `domain:example.com=reader` rule never downgrades `group:eng@example.com=writer` or `user:alice@example.com=admin`. Direct entries (`user:`, `serviceAccount:`, `domain:`) are evaluated in memory before Cloud Identity `group:` lookups (`CloudIdentityGroupChecker` is skipped entirely when direct entries already grant `admin`, and only `group:` entries strictly higher than the best direct match are queried). Sandbox `gcp-key` pool service accounts remain unconditionally refused (`403`, `AU-8`).
- **Stored in SQL (`allowed_principal`), not `grain/config`.** Role bindings live in the database `allowed_principal` table (exposed at `/api/access/principals` and `/settings/users`), excluded from `staterepo.SettingsTables` and included in `staterepo.BackupOnlyTables` cold dumps ([`simple-config.design.md`](simple-config.design.md) §4.3). Storing roles in SQL rather than the Git config repository ensures a `grain/config` pull request or sync failure cannot escalate privileges or lock `admin`s out, allows immediate role updates even when `settings_locked` or `config_mode: simple` is active, and survives VM replacement via Cloud SQL on registry instances.
- **Default role when omitted: `reader` (recommended).** Going forward, adding an allowlist entry without an explicit role defaults to **`reader`**. Operators most often omit roles on broad `domain:` or `group:` entries added so colleagues can open task links; defaulting to `writer` would grant everyone in that domain model spend, director turns, and `Submit`. Promoting a `reader` to `writer` takes one click on `/settings/users`, whereas legacy pre-RBAC deployments seed existing entries as `admin` once on upgrade (§7).
- **Bootstrap `admin` (immutable floor).** `-deployment-owner=<email>` (`$GRAIN_DEPLOYMENT_OWNER`, set from `entries.owner` on registry VMs per [`hub.design.md`](hub.design.md), or falling back to `Config.Actor.ID` / `-as` when it is an email address) plus `Config.ProvisionedServiceAccounts` (`grain-daemon@…`) are merged in memory as an immutable `admin` floor. Mutations on `/api/access/principals` refuse (`422`) removing or demoting `user:<deploymentOwner>`, leaving zero human `admin` `user:` rows when no deployment owner is set, or removing/demoting the calling human `admin`'s own `admin` access unless `-deployment-owner` still covers them.
- **Break-glass.** Requests authenticated by the deployment access code (`local-api-token` / `grain_access`) or unproxied loopback (`kubectl exec … -- grain …` or SSH tunnel to `127.0.0.1:4242`) resolve to **`admin`** and record `operator (access code)` or `operator (local)` ([`operator-attribution.design.md`](operator-attribution.design.md)), never a person's name.

## 2. Permission summary and hard cases

[`rbac.spec.md`](../spec/rbac/rbac.spec.md) §3 classifies all 327 existing `Server.Routes()` patterns plus the new RBAC and `whoami` routes, WebSocket/SSE streams, and CLI verbs. By surface:

| Surface | `reader` | `writer` (adds to `reader`) | `admin` (adds to `writer`) |
|---|---|---|---|
| **Tasks & queue** | List/read tasks, prompts, transcripts, trees, attachments, pipeline changes | File, `from-template`, edit, reorder, defer, pause/resume, stop, close, reopen, retry, `run-now`, pipeline pause/resume | Recreate sandbox; approve/attach admin-only grants; `priorityDispatch`; `deployment/broadcast` |
| **PRs, CI & tests** | Read CI runs, job logs, artifacts, faults, merge batches, base gates, branch diffs | Open PR, `retry-merge`, `Submit` (non-`grain/config`), start/cancel CI runs, quarantine tests | `force-merge`; approve/submit `grain/config` changes |
| **Capabilities & tokens** | Read capability catalog, repo grants, policy, scope sets (`picker` reads) | Attach/detach ordinary task grants; manage **own** `writer`-bounded `gma_` tokens | Capability servers, policy, scope sets, repo grants, `hostds`, all `gma_` tokens & `revoke-all`, local-script approvals |
| **Sessions & staging** | Read console sessions, conversations, and console output | Chat with `director`/sessions, restart/cancel turns, live PTY input/resize, `/staging/*` proxy (HTTP/SSE/WS) | Create, edit, or delete standing console session definitions |
| **Processes & releases** | Read schedules, templates, suites, suite runs, boards, memory, releases, release notes | `POST /api/schedules/{id}/run`, `POST /api/suite-runs`, cut/promote candidates, approve/reject pending releases & qualification, edit release notes | Create/edit/delete schedules, templates, suites, boards, memory; edit release config, qualification plans, and release secrets |
| **Settings, secrets & host** | `GET /api/config` (public), `GET /api/whoami`, `GET /api/settings`, `GET /api/agent-models`, health, sandbox pool, metrics, `restart-watch` | — | All settings/connection/repo writes, `reachable-repos`, secret names/audit & write-only bindings, raw controller/host logs & `top`, state-repo, DB, upgrade/restart/reboot, `/settings/users` |

### Hard cases

1. **Proposal approval and admin-only grants.** Approving an ordinary proposed task (`POST /api/tasks/{id}/approve`) is **`writer`**. However, **admin-only grants** (`model.IsAdminOnlyGrant`: every `model.IsPersonOnlyGrant`—dangerous `api:*` scopes, `requires_person` scope sets, `priority-dispatch`, `durable`—plus any `api:*` grant resolving to an `admin`-classified route scope such as `repos:write`, `schedules:write`, `templates:write`, `suites:write`, `sessions:write`, or `caches:write`, and host-level `self-repair`) require **`admin`** both to grant (`POST /api/tasks/{id}/capabilities`) and to approve.
2. **`Submit`, `force-merge`, and `retry-merge`.** `Submit` (`POST /api/tasks/{id}/submit`, human-only) and `retry-merge` (`POST /api/tasks/{id}/retry-merge`) are **`writer`**, except tasks targeting the deployment's `grain/config` state repository (and `POST /api/tasks/{id}/config-change/approve`), which require **`admin`**. `force-merge` (`POST /api/tasks/{id}/force-merge`) bypasses merge gates and is **`admin` only**.
3. **Director and console sessions.** `reader`s may view `/director` and session transcripts read-only; `writer`s may message sessions (`POST /api/tasks/{id}/comments`) and restart/cancel stuck turns; only `admin`s may create, edit, or delete standing session definitions (`/api/console-sessions*`), because those configure standing capabilities and `TasksApproved`.
4. **Minting `gma_` vs. `hostd` tokens (recommended split).** `hostd` registration and token rotation (`/api/hostds*`) attach execution hosts and are **`admin` only**. For `gma_` external-agent tokens ([`external-cli.design.md`](external-cli.design.md)), when `externalAgentApi` is enabled by an `admin`, **`writer`s may list, mint, rotate, revoke, and delete their own tokens** (`owner == caller`) whose scopes stay within the `writer` role ceiling (such as `grain/external-dev`), so engineers can run `grain login --issue-token` without an admin bottleneck. Minting `admin`-scoped tokens, viewing/revoking other users' tokens, and `revoke-all` are **`admin` only**; `reader`s cannot mint tokens.
5. **Release approve/reject and schedules.** Running an existing schedule (`POST /api/schedules/{id}/run`) or suite (`POST /api/suite-runs`) and executing release checkpoints (`pending-releases/{version}/approve` or `reject`, candidate cut/promote, qualification approve) are **`writer`** operational actions; editing schedules, suites, release configuration (`PUT .../release`, `qualification-plan`), or `release-secrets` is **`admin`**.
6. **Repository import.** Onboarding or removing a deployment repository (`POST /api/repos`, `DELETE /api/repos/{owner}/{name}`, `reachable-repos`) is **`admin`**; importing GitHub issues as tasks into an already-configured repository (`POST /api/repos/{owner}/{name}/import-issues`) is **`writer`**.
7. **Secrets.** Reading plaintext secret values is **never permitted for any role** (`nobody`). Listing secret names/audit metadata (`secrets:read`) and writing or binding secrets (`PUT /api/secrets/*`, `PUT /api/tasks/{id}/secret`, `bind-secret`) are **`admin` only**.
8. **Deployment health and logs.** Queue/sandbox health, metrics, upgrade status, and `GET /api/restart-watch` are **`reader`** so every user sees why tasks wait; raw controller/host journals (`GET /api/logs*`, `persistent-sandboxes/{name}/logs`) and `GET /api/host/top` are **`admin`** because controller logs contain refused-principal emails, capability stderr, and RBAC denial records (whereas task transcripts and CI job logs are **`reader`**).
9. **Inbox and notifications.** Reading `/inbox` and `GET /api/notifications` is **`reader`**; raising, acknowledging, clearing, and `investigate` are **`writer`**, while inbox items whose action hits an `admin` route (`PUT /api/tasks/{id}/secret`, approving an admin-grant proposal) still require **`admin`**.

## 3. Agents and delegation

- **No elevation via agents (`OnBehalfOf` intersection).** When an agent acts on behalf of a verified person—a director/console session turn triggered by that person's message, a `gma_` token owned by that person, or a task carrying `OnBehalfOf` ([`operator-attribution.design.md`](operator-attribution.design.md))—`agentAPIGate` and `POST /mcp` intersect the agent's `api:*` grants with the **current RBAC role of `OnBehalfOf`** on every call. Demoting a `writer` to `reader` (or removing them from `allowed_principal`) immediately blocks writes from their `gma_` tokens and session turns.
- **Writer-filed tasks and hold-for-approval.** When a `writer` (or an agent acting for a `writer`) files or proposes a task requesting any `IsAdminOnlyGrant` capability, `EscalatedCapabilities` (`pkg/model/auto_submit.go`) treats that grant as unapproved escalation: filing with `approved: true` is refused (`403`, `requiredRole: "admin"`), while filing as a proposal holds the task in `proposed` with a `CapabilityEscalationNote` naming the admin-only grants until an **`admin`** approves it.
- **Autonomous runs with no human caller.** Tasks fired by a schedule or trigger carry no live HTTP caller; per [`attribution.design.md`](attribution.design.md), their effective delegator is the schedule's `owner` (or `grain_config.oncall` at firing time when `owner: oncall`). Because only `admin`s can create or edit schedules and `grain_config.oncall`, any admin-only grants attached to a schedule were already authorized by an `admin`; if a schedule's named `owner` is a `writer`, `OnBehalfOf` intersection bounds any dynamic `api:*` calls the run makes to `writer` unless the schedule's grants were explicitly pinned by an `admin` at configuration time. Unattributed `operator` fallbacks (`access-code`, `loopback`, `in-process`) carry `admin`.

## 4. Enforcement, read scoping, and audit

- **Single check point and totality test.** Every HTTP, WebSocket, and SSE handler is gated by `ui.RequirePermission(ctx, perm)` keyed off `ui.RequestActor(ctx)`, wired into `Server.route` from a declarative `routePermissions` table alongside `routeScopes`. `TestEveryRouteHasDeclaredPermission` (mirroring `TestEveryMutatingRouteIsAttributed` and `TestRouteScopesAreTotal`) fails CI if any registered route lacks a permission entry or declares an unknown level.
- **Refusal contract and UI.** API denials return `403 Forbidden` with `{"error": "…", "code": "insufficient_role", "requiredRole": "writer"|"admin", "actorRole": "reader"|"writer"}` so CLI and browser callers always name the role needed. The UI reads `whoami.role` to hide or disable unauthorized controls (while keeping `/settings/preferences` available to all roles for browser-local theme/timezone); the server remains authoritative.
- **Read scoping.** In basic RBAC, `reader`s see **all repositories and tasks** on the deployment. Grain deployments are already single-team or per-owner appliances, and cross-repo task trees/dependencies break if half a tree is hidden.
- **Audit.** Every insert, update, or delete on `allowed_principal` writes a `config_audit` row (`surface: "access:principals"`) recording `RequestActor(ctx)` and the before/after role diff, and logs to the daemon journal. Every `403 insufficient_role` denial is logged (bounded/deduplicated per `(actor, route, requiredRole)` like `AU-19`) and recorded in an in-memory/SQL denial counter for operator inspection.

## 5. Migration and UI

- **Zero-breakage upgrade.** On schema migration of an existing deployment (one with an existing `grain_config` row) when `allowed_principal` is empty, Grain seeds all configured `-ui-allowed-principals` entries into `allowed_principal` with `role = "admin"`. Every previously admitted user keeps full access after upgrade. An `admin` then visits **Settings → Users** (`/settings/users`), adds a broad `group:` or `domain:` rule as `reader` or `writer`, and narrows individual teammates from `admin` to `writer` or `reader`.
- **UI surfaces.** `GET /api/whoami` (`OA-5`) adds `role` (`"admin" | "writer" | "reader"`) and `deploymentOwner`. The header user badge (`PageHeader.jsx`) and phone drawer footer (`Sidebar.jsx`) display a compact role pill beside the signed-in email. **Settings → Users** (`/settings/users`, `admin` only, active in both `simple` and `full` config modes) lists principals, roles, matched source (`pinned owner`, `database`), add/role-change/remove controls, and lockout warnings.

## 6. Non-goals

- **Custom roles or per-scope user grants** (`api:*` scopes remain the agent/token narrowing vocabulary; humans hold `admin`, `writer`, or `reader`).
- **Per-repository roles or read-scoping** (hiding specific repos or tasks from `reader`s or limiting `writer`s to a subset of `targetRepos`, deferred to future multi-team work).
- **Per-task ACLs or private tasks/conversations.**

## 7. Open questions

1. **Default role when an allowlist entry omits `=<role>`:** `reader` vs. `writer`? **Recommendation:** **`reader`** for newly added entries (least privilege on `domain:`/`group:` rules), while seeding pre-RBAC `-ui-allowed-principals` entries as `admin` during existing-deployment migration so upgrades never break.
2. **Minting `gma_` external-agent tokens:** `admin` only vs. `writer` self-service within their own role? **Recommendation:** allow **`writer`s to mint/manage their own `writer`-bounded `gma_` tokens** when `externalAgentApi` is enabled (preserving `grain login --issue-token` in `external-cli.design.md`), keeping `admin`-scoped tokens, cross-user management, and `revoke-all` `admin`-only.
3. **Controller/host logs (`GET /api/logs*`, `GET /api/host/top`):** `reader` vs. `admin`? **Recommendation:** **`admin`** for controller/host logs and `top` (they log refused emails and internal errors), while task transcripts, CI logs, health, sandbox counts, and metrics are **`reader`**.
4. **Operational release checkpoints (`pending-releases/{version}/approve`, `candidates/promote`):** `writer` vs. `admin`? **Recommendation:** **`writer`** for running release checkpoints (matching `Submit` to trunk), keeping release configuration and `release-secrets` **`admin`**.
5. **Shared saved boards (`POST/PATCH/DELETE /api/boards*`):** `admin` vs. `writer`? **Recommendation:** **`admin`** while boards live in `grain/config`'s shared `board` table; revisit if personal boards are added.
