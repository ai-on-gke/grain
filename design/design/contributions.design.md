# Grain contribution processes

Note: attribution will be handled in a second design.

## The design folder

Each repo has a design folder with 5 classes of things in it:

1. **Design documents** - These are high level design documents written up about a specific topic. They are generally "1 pagers" of various topics. These are generated in interactive sessions between PMs, engineers and agents. These are all human reviewed. Note that they may reference docs in other repos from other designs in some cases.
2. **Specifications** - These are detailed specifications of the design documents, generally one (or one folder) per design document. These are generated by agents and reviewed by humans, with humans potentially providing edits. These might include screen mock ups, apis, etc.
3. **Tasks** - These are organized by design PR and contain high level task specifications, including permissions (as defined in the grainfile specification). These are agent generated and may be occasionally audited by humans. These are grainfiles or a moral equivalent. These are given specific extensions to differentiate them so grain can import them automatically.
4. **Playbook designs** - These are overall designs for background tasks like releases, nightly testing, etc.
5. **Playbooks** - These are detailed definitions of tasks, schedules, etc in a grain specific format. These are also grainfiles or moral equivalents.

Alternatively, all of the design material could live in a separate repo rather than in a folder in each repo; either layout could be supported.

## Process

Wherever an agent opens a PR against the design folder (specifications, tasks, clarifications, playbooks), it should listen to that PR and respond to review comments by making updates to the doc PR.

### Design

PM and engineers work together to write a new design or update an existing design. They work on a branch and eventually, when everyone approves, they commit it. This is not done with grain; it can be done with any interactive coding agent or by hand.

### Specification

Once a design document is approved, grain automatically files a task to generate the detailed specification (e.g., APIs, screen mockups, schemas) which it opens as a PR on a new branch. Humans review the specification, provide edits as needed, and approve and merge the PR when happy.

### Tasks

Once the specification is approved, an agent is run in grain to create a new PR tasks folder with high level tasks and initial permissions described (as grainfiles or a moral equivalent). This is again in a new PR on a new branch, which humans audit and check. When humans are satisfied, they approve and merge the PR.

### Implementation

Grain automatically imports the tasks into its backlog. A grain oncall watches the queue to ensure that tasks are completed in a timely manner. Agents decompose tasks into smaller tasks as desired, staying within their initial grants (per the grainfile specification). No human is in the loop during code implementation and landing; agents land code changes autonomously unless an escalation is needed. If agents have questions or require clarifications, this is handled entirely via pull requests: the agent raises a new PR against the design folder documentation, which humans review, edit, and approve. If agents encounter problems with execution or testing (test flakes, insufficient permissions, etc.), they send a message to a grain on-call chat session for the team. Once the feature is landed, the task in the design folder is marked as complete, with the URL of the task serving as the index into the grain db for more information as desired.

### Checking

Grain playbooks are run regularly and include prompts to check changes end-to-end beyond their initial commits. Playbooks include steps that involve humans; for example, a release may require a human to review change summaries.

### Loops

We track uncaught bugs, clarification questions, etc and attempt to drive code faster with fewer errors by modifying playbooks, processes, etc.

### Bugs

Bugs and issues come in as GitHub issues or proposed PRs. A human files or reviews the issue and tags it (or does so via a PR) to send it on into the grain pipeline.

### Playbooks

Playbooks are edited in a similar way in the design folder, with humans authoring overall principles and agents authoring specific "cron" jobs with potential human oversight.
