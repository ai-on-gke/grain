# Grain contribution processes

Note: attribution will be handled in a second design.

## Principles

At a high level, the design documents and specifications are the core definition and single source of truth for the repository. The codebase is generated from and governed by these designs and specs.

Key principles guiding this workflow:

- **Designs and specifications drive code:** The repository's code is derived from and governed by the design documents and specifications in the design folder.
- **Two contribution paths:**
  - *Spec-first / Agent-driven:* Contributors update designs and specs, and then request Grain to update the codebase to match.
  - *Full-stack / End-to-end:* Contributors author and push the complete change through design, specification, and code themselves.
- **Autonomous agent execution within boundaries:** In either flow, agents can modify and land code autonomously without asking humans, provided they stay within the configurations and boundaries established by the designs and specifications.
- **Avoid code-only updates:** Contributors should avoid making code-only changes that are not reflected in the designs and specs. Because the codebase is derived from and reconciled against the design folder, isolated code changes risk being undone or overwritten by future agent runs.

## The design folder

Each repo has a design folder containing 6 classes of items:

1. **Design documents**
   - **Description:** High-level design documents written about a specific topic, generally "1-pagers" generated in interactive sessions between PMs, engineers, and agents. They may reference documents in other repositories. Each design document must designate at least one "owner".
   - **Review guidelines:** Thoroughly human-reviewed and approved. PMs and engineers collaborate on a branch (by hand or using interactive agents) until consensus is reached. Any change to an existing design requires approval from at least one of its designated owners before merging.
2. **Specifications**
   - **Description:** Detailed technical specifications derived from design documents (generally one document or subfolder per design), defining APIs, schemas, screen mockups, and interface contracts.
   - **Review guidelines:** Generated by agents as a PR once a design is approved. Humans review the specification, providing comments or direct edits. The agent listens to the PR and responds to review feedback with revisions until humans approve and merge.
3. **Tasks**
   - **Description:** High-level task breakdowns and initial permission grants (authored as grainfiles or moral equivalent) organized by design PR. These use specific file extensions so Grain can automatically import them into its backlog.
   - **Review guidelines:** Agent-generated via PR; humans audit and check task scope and permission boundaries (as defined in the grainfile specification). Humans approve and merge the PR once satisfied with task definitions and permission limits.
4. **Playbook designs**
   - **Description:** High-level designs and operational principles for recurring background tasks such as releases, nightly testing, monitoring, and maintenance.
   - **Review guidelines:** Human-authored and human-reviewed to establish safe operational parameters, policies, and escalation paths.
5. **Playbooks**
   - **Description:** Concrete definitions of tasks, schedules, and triggers in a Grain-specific format (grainfiles or moral equivalent).
   - **Review guidelines:** Authored by agents from playbook designs (or authored/refined by humans); audited and reviewed by humans for schedule safety, resource limits, and execution permissions before activation.
6. **Implementation**
   - **Description:** Houses implementation status records, progress tracking, and completion logs for tasks and features executed by Grain agents. The structure of the implementation folder mirrors the structure of the tasks folder.
   - **Review guidelines:** Unlike the rest of the sub-folders in this repo, the implementation folder is updated directly and autonomously by Grain agents without any human review.

Alternatively, all of the design material could live in a separate repo rather than in a folder in each repo; either layout could be supported.

## Process

Wherever an agent opens a PR against the design folder (specifications, tasks, clarifications, playbooks), it should listen to that PR and respond to review comments by making updates to the doc PR.

### Design

PM and engineers work together to write a new design or update an existing design. Each design must designate at least one owner. They work on a branch and eventually, when everyone approves (including the required approval from at least one owner to change an existing design), they commit it. This is not done with grain; it can be done with any interactive coding agent or by hand.

### Specification

Once a design document is approved, grain automatically files a task to generate the detailed specification (e.g., APIs, screen mockups, schemas) which it opens as a PR on a new branch. Humans review the specification per the review guidelines above, provide edits as needed, and approve and merge the PR when happy.

### Tasks

Once the specification is approved, an agent is run in grain to create a new PR tasks folder with high level tasks and initial permissions described (as grainfiles or a moral equivalent). Humans audit and check permissions per the review guidelines, approving and merging when satisfied.

### Implementation

Grain automatically imports the tasks into its backlog. A grain oncall watches the queue to ensure that tasks are completed in a timely manner. Agents decompose tasks into smaller tasks as desired, staying within their initial grants (per the grainfile specification). No human is in the loop during code implementation and landing; agents land code changes autonomously unless an escalation is needed. If agents have questions or require clarifications, this is handled entirely via pull requests: the agent raises a new PR against the design folder documentation, which humans review, edit, and approve. If agents encounter problems with execution or testing (test flakes, insufficient permissions, etc.), they send a message to a grain on-call chat session for the team.

Agents record and maintain implementation status directly in the `implementation/` folder (matching the structure of the `tasks/` folder), updating status records autonomously without human review as tasks progress and features land. The URL of the task and implementation status record serve as the index into the grain db for more information as desired.

### Checking

Grain playbooks are run regularly and include prompts to check changes end-to-end beyond their initial commits. Playbooks include steps that involve humans; for example, a release may require a human to review change summaries.

### Loops

We track uncaught bugs, clarification questions, etc and attempt to drive code faster with fewer errors by modifying playbooks, processes, etc.

### Bugs

Bugs and issues come in as GitHub issues or proposed PRs. A human files or reviews the issue and tags it (or does so via a PR) to send it on into the grain pipeline.

### Playbooks

Playbooks are edited in a similar way in the design folder, with humans authoring overall principles and agents authoring specific "cron" jobs with potential human oversight.
