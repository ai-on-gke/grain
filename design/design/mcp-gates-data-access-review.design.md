# MCP gate data access: prefer complete declared inputs

**Owner:** @ai-on-gke/ai-factory-root-owners

**Status:** Task #56 review; recommendation and draft amendment **pending operator decision**. Documentation only. The agreed [MGS-11 transport](../spec/mcp-gates/mcp-gates.spec.md#MGS-11), wire protocol 2.0 and action profile 3.0 remain the normative baseline. This report neither supersedes them nor authorizes implementation, deployment, configuration changes or follow-up filing.

## Recommendation

Prefer **one evaluation call carrying all declared, bounded, typed inputs**, gathered by Grain before calling the pinned evaluator. Keep the observation-cut, evidence, authorization and acceptance guarantees; remove evaluator-selected pages and transient continuation. Share internal observation/authorization/schema machinery where useful, without introducing a new capability-wide data-access wire protocol now.

The strongest reason is specific to the agreed baseline: MGS-11.2 already requires Grain to materialize the entire bounded observation cut before round 0. `needs_data` saves provider working memory and allows incremental computation; it does not avoid collecting or retaining that cut. A bounded payload of roughly 8 MiB is a reasonable proposed starting point for ordinary service providers, subject to measurement before admission. Simpler does not mean unbounded: oversized inputs remain unknown, and collection still stops within explicit limits.

This is a replacement recommendation, **not an accepted replacement decision**. An operator can retain the baseline if bounded provider streaming is an initial requirement. Do not implement both transports speculatively. The current design's statement that no transport decision blocks implementation describes its existing resolved defaults; this review proposes reopening that one decision explicitly.

## Standard MCP facilities do not reverse access direction

Inspected the versioned **2025-06-18** standard, the revision requested by this client, on 2026-11-16:

| Facility | What it provides / what remains custom |
|---|---|
| [Resources](https://modelcontextprotocol.io/specification/2025-06-18/server/resources) and [pagination](https://modelcontextprotocol.io/specification/2025-06-18/server/utilities/pagination) | Servers expose resources to clients. Standard cursors paginate resource/tool/prompt **lists**; `resources/read` does not specify snapshot-record paging. As connected today, these would expose provider data to Grain. A Grain snapshot server requires a separate connection/role, authorization and snapshot semantics. A resource URI or tool-result resource link grants neither connectivity nor access. |
| [Tools](https://modelcontextprotocol.io/specification/2025-06-18/server/tools) | Ordinary `tools/call` carries either candidate contract. Schemas/structured results are reusable; `needs_data` and domain completeness are Grain extensions. There is no standard symmetric reverse `tools/call` that exposes arbitrary client tools. |
| [Roots](https://modelcontextprotocol.io/specification/2025-06-18/client/roots), [sampling](https://modelcontextprotocol.io/specification/2025-06-18/client/sampling), [elicitation](https://modelcontextprotocol.io/specification/2025-06-18/client/elicitation) | Respectively filesystem boundaries, model generation and user input. They are not authenticated typed observation reads. Using sampling/elicitation to fetch task facts would also violate pure evaluation. |
| [Transport](https://modelcontextprotocol.io/specification/2025-06-18/basic/transports) and [HTTP authorization](https://modelcontextprotocol.io/specification/2025-06-18/basic/authorization) | Streamable HTTP permits server requests over client-opened SSE and client POST responses. That can avoid a new inbound socket, but requires a supported request method, negotiated client capability and a real dispatcher; this client has none. HTTP credentials authenticating Grain to a provider do not authenticate that provider to Grain. Resource-server audience, scope and revocation still need design. |

A real callback alternative has two concrete forms. A separate provider → Grain HTTPS connection needs routable DNS/service/ingress across remote/host/container installations, TLS, provider workload identity or audience-bound short-lived tokens, rotation/revocation, per-evaluation scope/expiry, quotas and a snapshot service. Loopback at a remote provider is not Grain. A multiplexed callback on the existing channel avoids inbound routing but needs custom client request dispatch on stdio and HTTP, reentrancy/cancellation/deadlock handling, authenticated session-to-provider binding and scoped read authorization. Both add deployment/support cost or transport implementation cost; neither follows from “MCP is bidirectional.” Neither is recommended for this small interface.

## Workloads and large tasks

These are sizing examples, not measured production distributions. Bytes include bounded typed facts and coverage, not raw logs or complete report text. Current initial mappings come from the [gate design's migration table](mcp-gates.design.md#MGD-4).

| Gate | Complete declared input and predicate boundary | Large-case handling |
|---|---|---|
| Checks | Required suite/policy set, exact head, authoritative latest applicable check records, collection time and explicit coverage. Missing required suite is unknown; observed failure is unmet. | 1,000 check facts at about 1 KiB each fit eager input. Do not include all historical reruns/logs. A registered latest-per-suite projection must preserve the provider's selection semantics; an opaque provider-specific predicate can instead request bounded raw facts. |
| Reviews | Current head/path digest, assignments, roles, findings/dismissals, policy and scoped approval facts. A completed review with findings does not pass a merge prerequisite. | 2,000 bounded 2 KiB records are about 4 MiB, suitable for eager delivery. A contract requiring full 50 MiB diff/discussion history cannot use this budget; collect an approved bounded exact-scope fact projection, narrow the authorized contract, or remain unknown. Never infer a clean review from a summary. |
| Child outcomes | Explicit required links and predicate (success/integration/legacy terminal closure), child outcome revisions, relationship coverage. Advisory children do not block. | 5,000 facts at roughly 1 KiB plus coverage can fit 8 MiB/6,500 records; more required children may exceed the record bound. No recursive graph download. A registered coverage aggregate is possible only if it proves the exact required set and failures. Link edits or any relevant child revision invalidate it. |
| Report | Durable artifact/version/digest, bounded coverage claims and incoming/processed message watermarks; separate receipt acknowledgment if required. | A 100 MiB report is not automatically a 100 MiB evaluator input. Delivery/coverage gates usually need immutable metadata. A content-analysis predicate needing uncaptured text stays unknown; mutable artifact URLs are not a fetch escape hatch. |
| Integration | Exact PR merged head or all scoped CL submission outcomes, immutable identity mapping, authoritative receipts and freshness. | Thousands of CLs need bounded per-subject records or a registered all-scoped-outcomes coverage record. Closed-unmerged PRs and unreadable CLs cannot pass. Integration remains a completion outcome, never a prerequisite for that same merge. |

A demanding combined task might need 1 MiB checks + 4 MiB reviews + 5 MiB child facts. Those are usually **separate attachments**, each below 8 MiB, with one shared bundle snapshot/version vector and separately scoped views. They do not justify sending one provider the union. A single custom gate joining all 10 MiB exceeds the proposed budget (and the baseline's roughly 8.25 MiB materialization limit). Both require a narrower contract, an explicitly approved projection, or unknown.

Paging is materially better when a provider must process several MiB with a small per-call memory budget and a ≤16 KiB sufficient accumulator. It is not an unlimited large-task solution: one 5,000-record reference needs 50 pages at 100/page, while only one next page per reference per round is allowed. Even with round-0 prefetch, eight rounds cannot exhaust that reference. Sixty-four pages is an aggregate ceiling, not promised reachability. Splitting a natural collection solely to exploit parallel references adds machinery. Eager delivery removes that particular shape-dependent failure.

Provider-specific predicates still execute in the pinned provider. Grain gathers declared registered domains/selectors resolved against pinned args; it does not learn predicates from provider code. Namespaced bounded record schemas can carry provider-specific facts. A new input requirement needs a new declaration/schema/release pin and authorized scope/contract revision in **both** designs: current `needs_data` cannot discover undeclared inputs. Optional inputs have explicit availability; if a predicate needs one to prove success, its registered prerequisites must say so. A Grain-generated “all passed” projection is appropriate only when its exact semantics and evidence provenance are registered, not as a universal replacement for provider logic. No general query language is proposed.

## Proposed contract amendment — pending decision

This is a concrete delta to MGS-2/11 and AGB-3, **not a change to their current schemas**. Temporary labels `eager-draft-1` (completion), `eager-action-draft-1` (action), and snapshot `eager-draft-1` distinguish examples from valid v2/3 messages. Accepted versions must be assigned in a separate normative amendment; unsupported profiles are refused, never coerced into the baseline.

1. Retain the existing request fields, semantics and mode restrictions except remove `round`, `phase`, `previous_response_digest`, `continuation_state`, `deliveries`. Retain `request_digest` over the whole request except itself, fixed `now`, deadline, pins/args/scope digests, durable state revision and every authority fence. Remove `pin.continuation_version` only. Discovery retains inputs/required/kinds, record schemas and replay-safety; replace transport with `grain_complete_inputs`, remove continuation version and input prefetch preference. Hash the revised declaration and repin it.
2. Snapshot keeps ID, evidence revision/journal cursor, domain list, explicit unavailable markers, incoming/processed watermarks and created/expiry times. Remove `references`; put all bounded typed records in `records`, in stable domain/kind/ID order. Each kind belongs to exactly one declared domain in this profile; shared semantics use separately registered kinds. Metadata excluding records is ≤256 KiB. Preserve required-domain coverage/empty-set proof and registry prerequisites; absence is never empty scope. Partial prefixes are allowed only with explicit unavailability, which prevents met for dependent predicates.
3. Limits become: `elapsed_ms≤30000`, `metadata_bytes≤262144`, `snapshot_bytes≤8388608` (entire snapshot), `record_bytes≤131072`, `records≤6500`, `state_bytes≤16384`, `args_bytes≤16384`, `json_depth≤16`, `response_bytes≤262144`, `request_bytes≤10485760`, `transport_bytes≤25165824`, `retries_total≤1`, `retention_ms=60000`. Keep ≤32 domains/64 kinds, wire parser depth 32, fixed evidence-age budgets and current bounded restart/backoff policy. Lower positive limits may be negotiated before construction; retries may be zero. Snapshot total is slightly smaller than the baseline's separate 256 KiB manifest + 8 MiB pages. Raising per-call request size from 2 to 10 MiB is a deliberate tradeoff, not an existing client guarantee.
4. Collection stops before any byte/record/time bound, including oversized single records or unenumerated remainders. No unbounded preload or count. Redact before accounting. Provider response exceeds limits → error, no result/state acceptance. Admission must bound decoded memory and concurrent evaluations, not just wire size; a provider unable to accept this bounded request advertises lower limits and returns unknown/resource_limit when necessary. No streaming continuation fallback.
5. Response is only the current final-response shape, minus `round`, with the new profile literal. Keep `kind=final`, all context echoes, statuses/evidence/work/waits/buttons, and final-only state CAS. `needs_data` is invalid in this profile. Echoed request digest acknowledges every supplied record. Grain validates citations against that request and registered predicates. Missing/stale/incomplete required inputs independently prohibit met. Migration/recovery remain unknown-only as currently specified.
6. Persist a bounded canonical request, counters and lease before send; reserve worst-case request+response bytes before each attempt. A retry repeats identical bytes to the same pin within the original deadline/TTL; pure providers require no session/cache or external calls. At maximum sizes two attempts consume ≤20.5 MiB, within the 24 MiB budget. A crash keeps uncertain reservations. Lost snapshot/request, changed evidence/permissions/pin, conflicting response or expired deadline aborts, never refills from live data. Retain final receipt uniqueness, atomic result/state/subscription CAS, cited evidence copies and audit history; transient writes never dirty gates or trigger task creation.
7. Apply the same delta to action-profile requests/discovery/results, preserving `evaluation_purpose`, qualified binding identity, operation/resource/context and context digest, null task provenance where applicable, and all AGB authority semantics. Recompute enclosing declaration/request/context digests and binding pins; do not strip context to reuse a completion request. Action input is a separately scoped view of the same observation cut.

## End-to-end calls and responsibilities

**Existing baseline (unchanged):** [success-paged.json](../spec/mcp-gates/examples/success-paged.json) contains complete call/reply envelopes with real canonical digests. Wrap each `call.message` in `{"jsonrpc":"2.0","id":N,"method":"tools/call","params":{"name":"gate_checks","arguments":MESSAGE}}`; each `reply.message` is `result.structuredContent`. Grain creates `snap-19`, authorizes/materializes the catalog and sends round 0. Provider selects `checks:a1`/null cursor in non-final `needs_data`. Grain reauthorizes, checkpoints and sends page 1 plus unchanged continuation/context in round 1; provider selects the returned next cursor; round 2 delivers page 2 and gets final met. Grain validates delivered evidence and commits once. The [prefetch transcript](../spec/mcp-gates/examples/prefetch-single-round.json) demonstrates today's one-call path. [Action examples](../spec/mcp-gates/action-bindings.examples.json) show profile 3.0 and a distinct non-final review continuation.

**Proposed eager profile:** the complete [draft wire example](mcp-gates-data-access-eager.example.json) includes discovery declaration and actual JSON-RPC request/response wrappers. It uses the same bounded checks/context facts as the prefetch fixture, flattened into one snapshot; its digests are recomputed. It is intentionally invalid against current normative schemas. Pins/IDs are fixture identities, not deployed releases.

```mermaid
sequenceDiagram
  participant C as Grain collectors / observation store
  participant G as Grain controller
  participant P as Pinned evaluator
  C->>G: Committed authorized versioned facts (or unavailable)
  G->>G: One bounded observation cut; separately scoped views; persist exact request
  G->>P: tools/call gate_checks (all declared records, fixed deadline)
  P-->>G: final met/unmet/unknown/error, evidence, candidate state
  G->>G: Recheck pins/vector/auth/freshness; atomic result/state/subscriptions once
  G->>G: Action executor or closure independently rechecks current fences
```

Grain owns collection, boundedness, completeness, immutable provenance and authorization; provider owns its pinned pure predicate and proposed explanatory result. A missing required check yields final unknown with a blocker; Grain also refuses an erroneous met. H1→H2, dismissed review, new message/child outcome, dirty external hint or permission epoch change aborts the old bundle; an identical resend never refreshes evidence. A lost reply can cause one exact resend, with one eventual accepted receipt/state update. All-met action guards then enter AGB's separately authorized fenced executor; expected-head conditional execution/exclusion and authoritative reconciliation are still required. All-met completion enters MGS-7's separate close transaction with current message watermarks and settled/fenced operations.

**Shared read abstraction (evaluated, not proposed):** a concrete callback sequence would be `Grain→provider tools/call gate_review(snapshot S, scoped credential reference)`, `provider→Grain resources/read(uri for S/reviews/page1)`, Grain authenticates provider and returns scoped immutable records/next-page metadata, then provider returns final evidence against S. The page URI convention, metadata, token/session binding and completeness remain custom; the credential is delivered through a protected transport context, not args. Standard `resources/read` has no content cursor field. Over an existing SSE/stdio channel the read would instead be a newly negotiated custom server-to-client request. Controller must run a concurrent read dispatcher and reauthorize each access; provider must implement transport/expiry/retry handling. This is more work than eliminating continuations with complete inputs. A controller-driven generic chunk protocol avoids callbacks but reproduces paging/state with a broader name.

## Essential guarantees and shared boundaries

Keep immutable snapshot identity + version vector; source subject/freshness and dirty-observation fences; one consistent task/subtask/external-evidence bundle; permission-scoped views and revocation; declaration/record/predicate pins; pure read-only evaluation; finite collection/allocation/latency/retry budgets; missing-data fail-closed behavior; durable final-only CAS/idempotency; copied cited decision evidence; and separate action/closure authorization and transactions. Neither handles nor hashes are credentials. No callback exists without an implemented transport and authenticated scope.

Removable mechanics are page reference catalogs/indexes, cursor progression, per-read IDs/loop warnings, partial delivery batches, delivery acknowledgment ledger, prior-response digest chain, request-carried accumulator/version, prefetch tuning, round checkpoints and round-specific counters. Request digest, durable provider state, snapshot identity, observation cursor, owner lease, final receipt and permission fences remain; they solve different problems.

For tracked-resource Tasks #45/#48, reuse canonical resource identity/provider pins, authorization partitions, schema validation, immutable observation storage, freshness and bounded collection helpers under TDS. Resource providers still receive Grain→provider Resolve/Observe/Watch calls and report facts. They do not acquire reads of Grain task data or become outcome interpreters. Provider evidence handles must already be captured/verified before snapshot construction. Equality-only provider revision tokens, Grain accepted-observation sequence, journal cursors and snapshot IDs remain distinct.

For trigger Tasks #46/#49, reuse authenticated journal ingestion, bounded records, redaction, leases and independent consumer checkpoints where semantics match. Event occurrence identity/replay/coverage is not an observation snapshot. Watch hints are not review-request occurrences. Gate waits consume journal events under separate authority; read attempts, retries, provider state/summary churn and continuation activity never become source events. No trigger event methods, resource-provider envelopes, watch leases or unrelated interfaces are redefined here. Task #48's TDS-11/12 further specifies the existing installed connection's `credential_binding`, explicit bounded access restrictions, and pull-only Watch read/renew: no provider callback. Task #49's TTS-17 likewise selects Grain-initiated open/read/renew/close, with a separately provisioned GitHub gateway upstream of the provider; that webhook ingress is not provider-to-Grain reachability. Its TTS-18 material-observation outbox excludes dirty hints, freshness refresh and repeated gate evaluations from transitions. Preserve these constraints and the common installation registry rather than introducing another provider/credential catalogue. A future shared internal library can precede any decision on a shared public protocol; require an actual second immutable-snapshot consumer before standardizing that protocol.

## Decision and migration impact

**Operator decision requested:** accept the complete-input direction and the bounded-memory/request-size tradeoff for a subsequent normative amendment, or retain the currently specified rounds because initial providers need incremental bounded-memory evaluation. Recommended: accept the direction. Actual ≤8 MiB payload parsing, concurrency and collection latency still need qualification in later authorized implementation; this report supplies sizing reasoning, not benchmark evidence. No automatic follow-up is filed.

If accepted, revise MGS-2/11, MGD-2/6 and both profiles together before implementation. Replace the `wire.schema.json` request/response/discovery/snapshot/pin/limits definitions and obsolete page/delivery/continuation definitions. Update action-profile compositions in `action-bindings.schema.json`, binding declaration pins, action context/request hashes and action fixtures; keep the non-transport binding/action authority schema semantics. Recompute tools-list input schemas/declaration digests, examples and registry/schema references. Required-domain delivery acknowledgment becomes whole-request acknowledgment.

Replace success-paged/partial-batch/repeated-request/denied-read examples with eager success/partial-required-input/unauthorized-scope/oversize cases. Keep and adapt permission-revoked, stale-snapshot, timeout, provider/controller crash, cancellation and retention-expiry cases: loss of the retained canonical request still aborts. Prefetch disappears into ordinary complete input. Update MGS-10/11 acceptance tables and AGB-7/8 responsibility matrix so no page driver is accidentally required by one profile. Reconcile Task #48's TDS-14 gate-publication/close reference to unchanged MGS-11 paging and both siblings' gate-version references, while preserving their native collection/event envelopes and grant contracts. Old unsupported versions must hold, never silently fall back or reinterpret stored state. Since the gate runtime is not implemented, this is contract/fixture churn rather than a runtime data migration; any separately started implementations must be inventoried before claiming zero migration cost.

Phase 1 still builds evidence schemas, bounded observation cuts, scope/pins, final acceptance and audit storage; replace page store/ledger with bounded canonical request retention. Phase 2 shadow evaluation uses a one-call driver and exact retry/lease accounting instead of continuation checkpoints. Phases 3–5 retain explicit authority handoff, Go/SQL parity, central closure, durable waits/dispatch and UI/API work; AGB executor/credential boundary prerequisites remain independent. Readers/negotiation precede writers and no deployment is authorized here.

If the operator retains the baseline, use its existing prefetch path for initial gates, narrow declared domains and register only necessary fact projections. Implement one gate driver shared by completion/action profiles, plus common internal scope/schema/cut helpers. Keep exact-retry and fail-closed rules. Do not add callbacks, another read tool, generalized selectors or a provider session cache. These are the smallest useful implementation simplifications available without changing the agreed wire contract.
