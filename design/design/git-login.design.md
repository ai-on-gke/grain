# Delegated GitHub login and task attribution signatures (`grain git-login`)

**Owner:** @AntonTyb

**The core rule:** an engineer can delegate their personal GitHub HTTPS credential to a Grain deployment with a single CLI command (`grain git-login`), and every pull request description, issue/PR comment, and code review that Grain creates or updates with that credential carries an explicit human signature (`Signed by <Name> (via Grain)`) showing both who owns the credential and that the action went through Grain.

[`attribution.design.md`](attribution.design.md) defines task ownership and `Co-authored-by:` commit credit across multi-user workflows, and [`operator-attribution.design.md`](operator-attribution.design.md) defines how runtime API calls record their verified human principal. This design covers the complementary single-engineer / delegated-credential workflow: capturing a user's GitHub HTTPS token (interactively via browser OAuth Device Flow or locally via `gh auth token` / `stdin`), binding it as the deployment's git connection on that host, and signing every GitHub pull request and comment authored through that connection with the user's name.

## Problem

When an engineer runs Grain to execute tasks on their behalf using a delegated personal GitHub token (rather than a dedicated GitHub App bot installation), two gaps arise:

1. **Manual token plumbing.** Previously, delegating a GitHub HTTPS credential required manually minting or copying a Personal Access Token and calling `grain connections add git -value ghp_...` or pasting it into Settings. There was no `gh auth login`-style interactive browser flow or one-step delegation from an existing local `gh` CLI login, and re-authenticating required manually deleting the previous connection on that host first.
2. **Ambiguous GitHub authorship.** When Grain opens pull requests or posts comments using a user's delegated HTTPS token, GitHub displays the PR or comment under the user's own GitHub account. Without an explicit text signature in the body, reviewers cannot tell at a glance that the PR or comment was generated by Grain acting on the user's behalf, and when a shared or bot-backed credential is used with an explicit author name, the human delegator's name is not visible at the bottom of the PR or comment.

## Overview

`grain git-login` provides a `gh auth login`-style experience for delegating a GitHub HTTPS credential to a Grain deployment and enabling explicit signature attribution:

```
Engineer workstation                              Grain daemon
┌──────────────────────────────────────┐          ┌──────────────────────────────────────────┐
│ grain git-login [--web | --from-gh]  │          │ POST /api/deployment/git-connections     │
│   1. Acquire HTTPS token:            │          │   - Saves encrypted PAT in CredentialSet │
│      • --web: GitHub OAuth Device    │ ───────► │   - Resolves Author via GET /user when   │
│        Flow (/login/device/code)     │          │     SignAs=true and Author is unset      │
│      • --from-gh: `gh auth token`    │          │   - Records Author in <cred>.host.json   │
│      • --with-token: stdin           │          │   - Replaces prior connection on same    │
│   2. Send token + SignAs=true        │          │     (host, scope)                        │
└──────────────────────────────────────┘          └────────────────────┬─────────────────────┘
                                                                       │
                                                                       ▼
                                                  ┌──────────────────────────────────────────┐
                                                  │ GitHubClient + AuthorSignatureSource     │
                                                  │   - PR body:                             │
                                                  │     Signed by <Name> (via Grain)         │
                                                  │   - Comment / Review body:               │
                                                  │     *Signed by <Name> (via Grain)*       │
                                                  └──────────────────────────────────────────┘
```

## Requirements

### Interactive and non-interactive token delegation (`grain git-login`) {#GL-1}

The CLI provides `grain git-login` (not `grain login`, which signs the CLI in to a deployment -- see `host.spec.md` CLI-108) supporting three mutually exclusive token-capture modes:

- **Interactive browser OAuth Device Flow (`--web`, default when stdin is a terminal):**
  - Initiates an RFC 8628 OAuth 2.0 Device Authorization Grant against the target GitHub host (`POST https://<host>/login/device/code`) with scopes `repo`, `read:org`, and `workflow` (`github.DefaultOAuthScopes`).
  - Displays the one-time `user_code` and `verification_uri`, opens the browser when possible (unless `--no-browser` is passed), and polls `POST https://<host>/login/oauth/access_token` (`github.PollDeviceToken`), honoring `authorization_pending` and `slow_down` intervals until the user authorizes the session or the code expires.
  - Uses `--client-id` or `$GRAIN_GITHUB_CLIENT_ID`, falling back to `github.DefaultOAuthClientID` on `github.com`.
- **Local GitHub CLI delegation (`--from-gh`):**
  - Invokes `gh auth token --hostname <host>` with `GH_PROMPT_DISABLED=1` and an explicit environment to read the token already configured on the user's workstation.
- **Standard input (`--with-token`, or automatic when stdin is piped):**
  - Reads the token from `stdin` for headless and scripted environments.

### Deployment-wide connection registration and replacement {#GL-2}

`grain git-login` registers the captured token as the deployment-wide git connection on the target host (`--host`, defaulting to `github.com`, with optional `--scope` and `--base-url`) via `POST /api/deployment/git-connections`:

- The request sets `Type: "pat"`, `SignAs: true`, `Replace: true`, and optional `Author: <name>` (from `--author`).
- When `Replace: true` is set on `AddTeamGitConnectionRequest`, `AddTeamGitConnection` replaces any existing connection matching the normalized `(host, scope)` pair—including migrating and replacing the legacy `Config.GitCredential` when logging into the default host with an empty scope—and removes the superseded deployment-owned credential from `gitproxy.CredentialSet`.

### Credential author resolution and persistence {#GL-3}

Each credential's host metadata (`<name>.host.json`, `gitproxy.CredentialHost`) stores an optional `Author` field:

- When `AddTeamGitConnection` receives `SignAs: true` and an explicit `Author`, it records that trimmed `Author` directly on `CredentialHost`.
- When `SignAs: true` is set and `Author` is empty, the daemon queries the credential owner's GitHub identity (`CredentialOwnerIdentityWithin`, backed by `GET /user`) and records the user's GitHub display name (`id.Name`, falling back to `id.Login` when display name is unset, excluding `*[bot]` accounts) in `CredentialHost.Author`. This is deliberately not the commit identity (`CredentialGitIdentity`), which prefers the host account's `git config user.name`/`user.email` where ambient logins are available: the signature must name whoever owns the token, not whoever runs the daemon.
- `gitproxy.CredentialSet.AuthorOf(name)` returns the recorded author for a credential, and `credentialTokenSource.AuthorSignature(owner, repo)` resolves the active connection for `(host, owner, repo)` and returns its author to `github.GitHubClient`.

### Explicit pull request body signature {#GL-4}

When `GitHubClient` has an `AuthorSignatureSource` (`WithAuthorSignatureSource`) that returns a non-empty author `<Name>` for the target `owner/repo`:

- `CreatePullRequest` and `UpdatePullRequestBody` append a trailing signature block separated by a horizontal rule:
  ```markdown
  ---
  Signed by <Name> (via Grain)
  ```
- `SignPullRequestBody` is idempotent: if the body already ends with a `Signed by ... (via Grain)` block, it updates the line in place rather than stacking duplicate dividers or footers.

### Preserving `grainAuthored` and signatures across orchestrator refreshes {#GL-5}

Grain's orchestrator identifies pull requests it manages by checking whether the PR description starts with `"Automated changes by [grain]"` (`grainAuthored` in `pkg/orchestrator/description.go`) and periodically rewrites the description (`refreshPRDescription`) as commits and task provenance change:

- `SignPullRequestBody` appends the signature at the end of the description so the `"Automated changes by [grain]"` prefix remains intact.
- `refreshPRDescription` calls `github.PreservePullRequestSignature(composed, pr.Body)` so that if a pull request already carries a `Signed by ... (via Grain)` footer (even when refreshed through a client without an active `AuthorSignatureSource`), the existing signature is preserved across description updates.

### Explicit comment and review signatures {#GL-6}

When `GitHubClient` resolves a non-empty author `<Name>` for `owner/repo`:

- `CreateComment`, `UpdateComment`, and `ReplyToReviewComment` append an italicized signature footer to the comment body:
  ```markdown
  *Signed by <Name> (via Grain)*
  ```
- `CreateReview` and `SubmitReview` sign the top-level review summary body when non-empty (or default an empty review body to `*Signed by <Name> (via Grain)*` when inline review comments are present) and sign each inline `ReviewCommentInput.Body`.
- `SignCommentBody` is idempotent and updates any existing trailing `*Signed by ... (via Grain)*` line in place.

### Bot marker preservation {#GL-7}

Grain uses hidden HTML markers (such as `<!-- grain:progress:task-123 -->`, `<!-- grain:clarify:task-123 -->`, and `<!-- grain:ci:run-456 -->`) in comments to find and edit its status comments in place (`pkg/github/bot.go`):

- Because `SignCommentBody` appends the signature at the end of the comment body and replaces any existing signature in place on `UpdateComment`, all leading `<!-- grain:... -->` markers remain intact and in-place comment updates never duplicate the signature line.

### HTTP client and subprocess hygiene {#GL-8}

- `pkg/github/deviceflow.go` never falls back to `http.DefaultClient`; when a caller passes a `nil` `*http.Client`, it constructs a bounded `*http.Client` with a 30-second timeout and `CheckRedirect` returning `http.ErrUseLastResponse`.
- `pkg/cli/deployment.go` executes `gh auth token` with an explicit `cmd.Env = append(os.Environ(), "GH_PROMPT_DISABLED=1")` so subprocess execution is non-interactive and satisfies `tests/security/ratchet_test.go`.
