## TTS-17: Hosting, transport and subscription lifecycle {#TTS-17}

### Connectivity and ownership

V1 uses **Grain-initiated request/reply only** for provider traffic. MCP `initialize`, `tools/list`, then `tools/call` run through `servers.Registry.CallTool(ctx,capability_id,tool,arguments,timeout)` over an installed controller-owned capability transport (local supervised stdio, or an explicitly configured authenticated HTTPS MCP endpoint). No provider may initiate a Grain callback, SSE event stream, webhook or agent connection. MCP session/stdio lifetime is not subscription lifetime. An attempt-scoped mint/pass MUST NOT host a standing collector. Discovery MUST verify installed release and descriptor digests against the approved pin, not trust the server's self-reported digest. HTTPS endpoint resolution, TLS identity, service credential references and egress allowlist belong to installation configuration, never source/event args. Redirects to unapproved endpoints are refused. Stdio processes run under the installation's host identity and bounded supervisor; remote providers authenticate the controller service identity and its scope on every call. Transport authentication uses the configured installation principal/credential_binding for that whole connection, resolved only through existing secret-backed capability env/headers/config; no task-selected credential or new token service is assumed. Grain enforces consumer source/field grants and authorization epochs locally, and providers enforce the configured principal's upstream scope. Credentials remain in transport context, never JSON or attempt endpoints. Local grants and collector leases expire/renew independently of MCP connection secrets.

A single capability installation registry owns canonical capability identity, artifact/config pins and transport. Its event extension record adds descriptor digest, source types and the TTS-2 bridge to ResourceProviderIdentity. Do not introduce a second provider catalogue, credential store or action registry. Built-in `builtin:time` is an in-process implementation of the same adapter interface; its release identifies the installed calendar code, with separate pinned tzdb semantics.

| Boundary | Concrete v1 contract | Persistent state, failure and recovery |

Retry depends on GitHub/redelivery operator; **no guaranteed automatic source redelivery** |
| Gateway -> provider | Provider-initiated HTTPS GET `/v1/events?after=<opaque>&limit=N&wait=0`; configured gateway origin, existing signed relay request (`SignRelay`) plus TLS; no redirects | Proposed gateway v2 response adds oldest retained cursor, retention epoch, safe verification reference and coverage gap to current relay. Provider preserves upstream delivery identity and stores pull checkpoints/page receipts durably. Existing gateway v1 alone is insufficient |

The gateway extension is a required implementation responsibility, not a claim about today's receiver. Gateway v2 is selected by `Accept: application/vnd.grain.github-relay.v2+json` on the existing signed GET; a v1 reply is unsupported, never assumed gap-free. Its exact response is `$defs.relay_result`: api version, retention epoch, oldest retained sequence, latest sequence, normalized relay events and coverage. Sequences are scoped to the gateway installation/security partition; recipient filtering cannot hide a missing retained range. The provider translates relay sequences into opaque scoped tokens and stamps trusted normalized envelopes only after validating this response.

GitHub's raw-body HMAC does **not** cover the `X-GitHub-Delivery` header. Treating that header as a new occurrence merely because a body signature verifies would permit replay under a new ID. Gateway v2 stores `(installation,delivery_id,raw_body_digest)` and rejects conflicting same-ID bodies; repeated same digest under a different delivery ID is an ambiguous alias, held unless authenticated source history/redelivery evidence distinguishes a new request. Header/event type must also agree with the signed body's action/resource shape. Approved ingress restricts source traffic and rate/replay abuse; do not claim signatures prove occurrence time or that byte-identical re-requests are distinguishable without extra evidence. Quarantine safe digests, never signatures/raw secrets. A verified distinct genuine request is eligible; unresolved ambiguity is visible loss/hold, never a duplicate task. [server.go](../../../pkg/ghwebhook/server.go), [client.go](../../../pkg/ghwebhook/client.go), [store.go](../../../pkg/ghwebhook/store.go) and [event.go](../../../pkg/ghwebhook/event.go) demonstrate current append, relay and normalization. Today requested reviewer is a login, teams and request epochs are incomplete, and relay retention does not supply the required gap fence. A real GitHub binding MUST remain held until gateway v2 and installation setup are verified. Required setup evidence: gateway durable volume/retention policy, externally reachable approved TLS ingress, GitHub webhook event selection (`pull_request` including request/remove/synchronize), matching installation/repository IDs, secret handles/rotation, relay reachability and TLS, a signed test delivery pulled through the controller, and documented loss/redelivery behavior. Setup is separately authorized; `event_open` verifies it but MUST NOT install or reconfigure a GitHub webhook. If public ingress is unavailable, this occurrence adapter is unavailable. Current-state polling can support a different state schema, but cannot stand in for review-request occurrences.

### Exact lifecycle

`event_describe({protocol_version:"1.0"})` returns the descriptor schema. Only `structuredContent` is authoritative; an optional text mirror must equal it, and isError/JSON-RPC failure is never a page. Bound tools/list/descriptor to 1 MiB and 1000 tools before full allocation. Source/kind extension and payload schemas use the capability validator subset; each kind declares both local schemas and their canonical digests (including a closed title-only GitHub payload); the pin schema_digest hashes the full selected source descriptor including both schemas. Sources may not hide filterable/mapped paths in an untyped payload. protocol envelopes use JSON Schema 2020-12. No remote schema resolution. Descriptor `delivery` is `pull_cursor` for occurrences or `poll_state` for state reconciliation. V1 has no callback mode. Read and reconcile use the common request; open additionally requires `expires_at`; close requires it null. All fields are present, including nullable fields. Results are `tools/call.result.structuredContent`; JSON-RPC IDs are transport IDs, `request_id` is the durable operation identity. Provider errors use a schema-valid error result; MCP/HTTP/parse errors are unavailable and never cursor progress.

1. Grain persists registration intent, subscription ID (random 128-bit), generation, authority epoch, source/pin digest, desired expiry and operation request ID **before** open. IDs are never reused. Open returns an exclusive baseline cursor representing the source tail **at the first successful open**, not the tail at each retry. It does not emit tasks or consume events. For a first open, `after_cursor=null`; reopened subscriptions pass the last committed cursor. An exact request ID with changed arguments is `request_conflict`. Same request ID returns the same logical result, including baseline, until acknowledged by a later durable operation; retain the baseline for the generation's lifetime and operation receipts for at least 24 hours. A later uncertain operation beyond receipt retention holds/reconciles; never silently return a new baseline.
2. Registration expiry is 10 minutes by default, bounded to 60 minutes. Renew by `event_open` on the **same generation**, a new request ID and extended `expires_at`, at half the remaining lease. Each renewal rechecks Grain read/watch policy and provider service credentials. Same-generation renewal MUST preserve baseline/checkpoint. A new generation is required for pin/partition/source change, cancellation or expired registration; old-generation calls are fenced. Provider persistently rejects generations below its largest accepted generation. No clock-only generation reset after restart.
3. Read starts after the committed exclusive cursor. Empty successful pages may advance over nonmatching upstream records only if no eligible event is omitted and coverage is explicit. Cursor scope is `(installation,pin,authorization_partition,canonical_source,generation,retention_epoch)`; tokens are opaque, equality-only, never global or timestamps. The provider defines one ordered append sequence in that scope; event occurrence order need not equal append order. Parallel reads per subscription are forbidden. Grain CASes expected old cursor, generation and worker fence on commit; late replies cannot advance it. Maximum page 500 events/1 MiB; deadline at most 30 seconds; normal poll 60 seconds with permitted 30-second-to-one-hour bounds.
4. Reconcile uses the same cursor and returns verified history plus coverage. Complete/bounded occurrence history may overlap; stable IDs deduplicate. State-only reconciliation returns **no invented occurrences**, a gap and current-state data only via a separately pinned resource Observe call. `cursor_expired` returns no cursor progress. Grain persists the gap and pauses automatic matching before an authorized new baseline. Persist retry at 30 seconds doubling to 30 minutes with jitter, honor longer Retry-After, at most four concurrent calls/provider, 60 calls/minute burst 10 or stricter service limits. Three failures or 15 minutes unavailable produces one deduplicated owner blocker; ten consecutive failures open a persisted one-hour circuit, allowing one half-open probe and reopening for an hour on failure. Unauthorized/invalid/unsupported configuration holds until repair, never automatic probing. No task is automatically filed for escalation.
5. Close first increments local control/fencing epoch and persists cancel intent; it rejects further local reads/filings immediately. `event_close` is idempotent even after expiry. The remote generation is tombstoned; cleanup retries until closed or lease expiry. Shared collection closes only on removal of the last authorized consumer; removing one binding removes its consumer immediately. Expired credentials stop reads and discard no history. Remote cleanup failure cannot preserve local authorization.
6. Restart scans intents, leases, pending operations and due timers; reclaim with monotonically increasing worker fence, recheck authority, retry the exact uncertain request or renew before reading. A restarted provider must restore its journal, baseline and generation fences. Loss of those files yields `cursor_expired`/explicit loss, never a pretend empty queue. Source-generation handoff persists old last cursor/new baseline and an identity compatibility map; absent a provable gap-free overlap, hold with a gap. Subscriptions do not grant filing authority.

## TTS-18: Identity, versions and matching precision {#TTS-18}

Hash notation below means lowercase SHA-256 of RFC 8785 canonical JSON, with domain string as the first array element. This spec uses JSON arrays rather than ambiguous concatenation. Numbers in identities are integers within the interoperable JSON range. Identity strings and cursor logs are private scoped metadata.

| Identity | Exact content / immutability |
|---|---|
| Provider identity | Installation registry key plus bridge to `(capability_id,method)`; pin includes artifact, config, protocol/source version and descriptor/schema digests. Provider upgrades do not create new external occurrences |
| Source key `S` | `H(["trigger-source-v1", registry_identity, authorization_partition, source_type, canonical_source_args])`; envelope `source` is this registry key. GitHub canonical args are `{host,installation,repository_id,recipient}` with lowercased host, stable IDs and no display repository path/type discriminator. Calendar canonical args are `{source_uuid}` independent of recurrence/binding version. Other settings belong to the pinned subscription/config, not source identity |
| Event key `E` | `H(["trigger-event-v1", source_identity_lineage, event_id])`. Lineage preserves stable upstream identity across approved compatible provider upgrades. External provider alias equality must be verified before reuse |
| Match key `M` | `H(["trigger-match-v1",binding_id,binding_version,E])`. At most one per matching version; unmatched checkpoint is not a filing receipt |
| Logical firing key `F` | `H(["trigger-file-v1",binding_id,dedup_lineage,E,slot_id,replay_epoch])`; `slot_id="primary"`, `replay_epoch="live"` normally. Neither retry number, worker ID, current binding version nor current template digest is in F |
| Task identity | Existing Grain task ID allocated only for the transaction's chosen create disposition. Task ID is not event/firing ID. Multiple coalesced F keys may reference one task; one F has exactly one immutable final receipt |
| Repeat group | `H(["trigger-repeat-v1",binding_id,dedup_lineage,authorization_partition,typed_key_values])`. Compatible means exact template/content and constant security/composition pin, target, owner/service lineage and allowed run-boundary semantics; mapped inputs/event heads have separate immutable obligation digests and are excluded from the compatibility digest; head obligations remain per event |

Runtime extensibility uses `$defs.binding_common` (closed provider-independent envelope), then **mandatory** registry validation of `source` against the exact pinned descriptor source_schema, source.type=provider.source_type, declared event kind/version/semantics, admitted filter/mapping paths and repeat/freshness contract. Every registered source schema requires its literal type discriminator; unknown provider/kind/pin is held, never admitted merely because common validation succeeds. The shipped `$defs.binding` root adds the two concrete time/GitHub profiles for offline examples. Management/provider request schemas use the common envelope and a bounded source object plus that mandatory registry validation; new providers require reviewed registration, not a conflicting central source enum or executable custom validator.

The source identity lineage and binding dedup lineage are server-owned immutable UUIDs, persisted at creation. Every edit, including provider/template edits, keeps the binding dedup lineage. Only explicitly approved replay with `allow_new_firings` allocates a new replay epoch; no ordinary edit resets dedup. New versions normally start after their activation fence. If versions overlap by explicit catch-up, the first matching authorized F reservation wins; a later version records `already_filed` with the original receipt. A pending older match remains pinned to its old snapshot and authority, never retargeted by a newer version. A deleted binding ID and lineage remain tombstoned. Provider/source retargeting allocates a new source lineage; moving to an equivalent source requires verified identity mapping or held migration.

Time event ID is canonical JSON `[source_uuid,cadence_epoch,scheduled_at_utc]`. A collapsed catch-up uses oldest due scheduled instant as ID and immutable `covered_through`; later retries cannot extend that event. Later missed windows are new IDs. Calendar intervals anchor to persisted `next_due`, independent of worker time. Cadence changes preserve committed events and increment cadence epoch for subsequent instants only; config-only edits never increment it.

GitHub occurrence ID is canonical JSON `[host,installation_id,repository_id,delivery_id,"review_requested",recipient_kind,recipient_id]`; `request_epoch` is the stable delivery ID. GitHub source scope includes recipient, so one team request is one event. The authenticated raw body supplies the requested head, sender and stable recipient; do not substitute the head later returned by GET. GitHub request creation time is not necessarily authenticated: `occurred_at=null` unless a source history record supplies it. Gateway receipt time is retained separately but does not prove occurrence time. Provider `kind_version` pins GitHub normalization (v1); envelope `protocol_version` is independent. Reusing a delivery ID with changed source facts quarantines; change in receipt metadata alone is duplicate. If a different delivery aliases the same occurrence, only a demonstrable upstream alias mapping can merge it; otherwise disclose weaker dedup and hold exactly-once admission. A later genuine request uses a new delivery ID even for the same head. Current requested-reviewer state does not establish a missing request epoch.

Live enable commits both Grain receipt-sequence watermark and **upstream baseline cursor** before reads. Events after that fence with unknown occurrence time are eligible; events pulled before the fence are not. Read loss invalidates this proof, holds backlog and requires a new reviewed baseline/replay selection. Historical replay without authenticated occurrence timestamps requires a finite cursor range, never a guessed time range. Stale occurrence events remain in history with held/expired disposition. Out-of-order occurrence delivery can still match; it never changes the latest PR head. A state edge requires accepted authoritative observation sequence, with unknown/true initial baseline producing no event by default; `emit_current` uses a synthetic ID `[source,baseline_epoch,predicate_digest]` once, separately labeled, never a historical request. Registered state types are future extensions; the two v1 binding profiles are occurrence-only and reject state mode.

For an admitted state-edge adapter, false-to-true event identity is canonical JSON `[source_lineage,view_id,accepted_sequence,predicate_digest,"false_to_true"]`. Accepted sequence is Grain's transactional material observation sequence, not the provider equality token, so ABA can produce two distinct edges. Unknown after an outage breaks continuity: unknown-to-true is a baseline, not a proved edge. Initial emit-current is the separately authorized synthetic identity already described. Prior predicate/sequence and derived event/match checkpoint must commit atomically. A changed predicate starts a new baseline. Only committed material observation outbox records may enter this adapter; provider freshness refresh, summary changes, retries, dirty hints and repeated gate evaluations never count as transitions.

Filters evaluate only schema-allowlisted immutable fields with strict types; JSON Pointer escaping is RFC 6901, no array wildcards or dynamic keys. `in` is type-strict membership; string comparison is exact Unicode code point equality after provider-declared canonicalization (no locale folding). Missing is distinct from null. Evaluation order is array order, with deterministic trace; the 10 ms budget is a safety ceiling that holds rather than changes truth. Mappings serialize integers in base 10 and booleans as `true`/`false`; no other coercion, truncation or recursive expansion. Compose exactly once using the template's approved default substitution and parameter schema. Prompt data remains untrusted even if escaped; no payload may supply identity, repository, template, capabilities or approval. Templates capable of turning untrusted parameters into executable control syntax MUST be rejected at binding admission.

## TTS-19: Durable state and atomic filing {#TTS-19}

### Minimum relational contract

These are logical tables/constraints, not SQL migrations. Implement them in the existing model store for SQLite and Postgres. All keys below are NOT NULL. Nullable task references are explicitly marked. Runtime state is never reset by config reconciliation.

| Record | Required keys, fields and constraints |
|---|---|
| `trigger_binding_version` | PK `(binding_id,version)`; immutable full config, binding digest, dedup/source lineage, template content+schema/security snapshot, standing filing authority reference, owner/service, creation audit |
| `trigger_control` | PK binding; current version, control revision, enabled/tombstone, activation fences, policy epoch; CAS for all edits |
| `trigger_source` | PK subscription; unique partition/source/pin/generation; baseline, exclusive cursor, retention epoch, desired/actual expiry, intent/retry/error/gap, lease owner/until/fence |
| `trigger_event` | PK E, unique `(source_identity_lineage,event_id)`; canonical source digest, normalized envelope, Grain receipt sequence, verification reference; conflicts are quarantine records |
| `trigger_legacy_due` | PK legacy schedule ID; oldest due UTC, cadence/ownership epoch, compatibility hold/drop reason, nullable pending E. Before legacy eligibility clears this is a due candidate, not a pinned match; never loses held NextRunAt |
| `trigger_consumer` | PK `(binding_id,version,subscription)`; independent match checkpoint, baseline/dirty accepted observation sequence, lease/fence and activation range |
| `trigger_match` | PK M, unique `(binding_id,version,E)`; F/slot, snapshot digests, mapped values+digest, eligibility/freshness observation, status, lease/fence, retry deadline, trace; binding and event FKs |
| `trigger_filing` | PK F; unique `(binding_id,dedup_lineage,E,slot_id,replay_epoch)`; receipt ID UNIQUE, M, disposition, task ID nullable FK, immutable composition/authority digests, commit time, quota reservation, replay/causation; task required for created/coalesced/updated/ignored_active |
| `trigger_task_origin` | PK task ID FK, F UNIQUE FK for creation; immutable attribution. Deleting/archiving a task retains origin/firing tombstones; ordinary update must not change origin |
| `trigger_attachment` | PK F FK; task FK, event obligation, input digest, pending message ID UNIQUE; immutable coalescing provenance |
| `trigger_repeat` | PK group key; serial coordination revision, active task reservations keyed by task, compatible composition digest; task terminal/update paths lock this row too |
| `trigger_outbox` | PK `(receipt_id,effect)` FK; task, durable intent, retry time, lease/fence, delivered flag. Effects are `dispatch_wake` or `followup_wake`; payload contains IDs, no credentials |
| `trigger_authority_epoch` / quota / chain | Existing policy rows plus monotonically increasing revocation epochs; scoped reservation/bucket rows and chain counters updated under the same transaction as F |
| replay/gap/quarantine | Bounded jobs and coverage tombstones; actor/reason, finite range/budget/expiry and control CAS. Quarantine contains safe digest/size/code, no raw secret-bearing body |

No nullable-column uniqueness trick is acceptable: default slot/replay epoch have explicit string values. Hash collisions with unequal stored identity tuples are blocking integrity errors. Journal bodies may expire, but event identities and firing receipts remain through the authorized replay horizon; an expiry fence rejects older replay permanently. A dangling created task without a firing receipt or a created receipt without a task violates the contract.

### Transactions and fences

A collector lease lasts 60 seconds, renews at 20 seconds and increments fence on acquisition; each mutation checks `(owner,fence,lease_until>DB_now)`. Never hold a database transaction during network calls. SQLite uses existing immediate write transactions; Postgres uses existing serializable store writes with bounded serialization retry. `Store.write` retries the **whole closure** from fresh transactional reads; no side effects, random identity regeneration or external calls inside that closure. Persist operation IDs before calls. Allocate task IDs/order keys and branch composition via transaction-aware model helpers; gaps in DB sequence allocation on rollback are harmless, reuse for another task is forbidden. A preview allocates nothing.

`FileTrigger(F,match_id,expected_match_fence)` is a new **in-process typed store operation** returning the receipt schema. It MUST NOT call `POST /api/tasks`, `POST /api/tasks/from-template` or public `PutTask` and then separately store F. Current [PutTask](../../../pkg/model/store.go) wraps its own transaction; [putScheduleTask](../../../pkg/model/schedule_fire.go) allocates/inserts before cadence advancement. Neither is the required atomic operation. Extract/reuse a transaction-aware creation/composition/authorization helper. The API gate's typed task/template containment rules MUST be shared by the helper, rather than simulated with a fabricated HTTP principal or only checking JSON request flags.

The filing transaction proceeds in this fixed order (retries reread all state):

1. Look up F. If a final receipt exists, return it subject to caller read authorization, even if the binding is now disabled. This is receipt retrieval, never renewed authority. Verify M maps to that same identity; mark a newer match already filed if applicable.
2. Lock/control CAS binding, its pinned authority/policy epoch rows, repeat group, target task (if any), quota buckets and chain counters in deterministic sorted key order. Validate match lease/fence and enabled control, matching version not cancelled, immutable snapshot digests and expiry. A stale worker returns `stale_fence` without writes.
3. Recheck current owner/service and source read/watch grants, filing grant for **exact** repo/template/pin/action, target enabled/allowlisted/standing-work policy, current template existence and approved security ceiling, person-only/declaration acceptance, hosting/admission floor and automatic approval/merge/proposal policy separately. Admission resolves target repository to immutable deployment repository ID plus forge host/stable repository ID, archives `$defs.target_identity` in the authorization/match security snapshot and rechecks the display alias still resolves to that identity at filing. Rename/transfer/path reuse holds for an approved identity-preserving rebind; a new repository at an old path never inherits authority. Both proposed and standing tasks require the filing grant. Service authentication and webhook signature do not supply it. All policy mutation paths MUST bump/lock the same authority epochs. External authority that cannot participate needs a short-lived signed local grant plus local revocation epoch; absent that contract, hold. No stale cached approval.
4. Review freshness is read **before** this transaction under a controller read grant: latest accepted observation of PR open state, current head, recipient outstanding request. Default freshness lease is 30 seconds and bound to observation sequence and dirty generation. Transaction requires it unexpired and no newer dirty/accepted sequence. The concrete current-read projection is `$defs.review_freshness`: stable repo/PR/recipient, head, open/outstanding booleans, actual observed/valid-until times, accepted sequence, dirty generation and Grain verification reference. For GitHub, the installed provider uses its configured App credential on allowlisted HTTPS GET `/repos/{owner}/{repo}/pulls/{number}` (stable repository/installation ID checked, current requested_reviewers/requested_teams IDs); a separately pinned resource Observe projection may supply exactly the same fields. URLs never come from event payload. Reject source clock skew above 30 seconds and cap validity to 30 seconds from actual collection. The current requested set proves an outstanding recipient, **not** which historical epoch remains outstanding. A known removed/superseded epoch or ambiguous remove/re-request ordering holds pending authenticated history reconciliation; do not guess occurrence order from gateway append sequence. A changed head from event head holds `held_head_changed`; removal holds `held_request_removed`; unavailable read holds. A new request for the new head can proceed. An external change not yet observed can race commit: creation is not a guarantee of live GitHub truth. Dispatch rereads scope/head, and review submission/gates require current subject. This honest boundary MUST be shown in explain.
5. Resolve disposition using the locked repeat group and actual lifecycle state. Choose exact template/content revision **already pinned on match** (including compatible tracking resolved at match time), compose once, validate typed inputs and bounds. Reserve known cost (default one admission unit per new task with deployment run budget separate), task/concurrency/chain and rate capacity. Missing conservative cost policy holds. Coalesced/ignored receipts consume match/rate budget but no second task reservation; any extra execution cost reserves separately. Recheck F after acquiring the coordination locks; allocate a new task ID only for create. F is finalized by the unique receipt insert in step 6, not by a separately committed reservation. A losing unique-key race rolls back the whole transaction, including any inserted task, before returning the winner's stored receipt.
6. Within this same transaction use this foreign-key-safe write order: insert the new task (or CAS the compatible existing target), insert the final F receipt referencing that task, insert immutable origin/attachment referencing F, then write M disposition, per-event receipt links, accounting and outbox. Skipped receipts have null task and no origin. Use a composite `(F,task_id)` foreign key for origin/attachment to the corresponding unique receipt pair so they cannot attribute another task. Trigger-created tasks MUST be writable only through this helper; public PutTask/task-create paths cannot fabricate trigger origins or omit the receipt. No intermediate write is visible before commit. Task lifecycle operations serialize with repeat reservations. For coalescing, insertion of the task message/obligation and its pending-processing barrier is atomic with attachment; terminal-close path must check that barrier under the same task revision. Actual task closure first means create a new task; completion-without-closure holds pending ordinary closure (TTS-20). Attachment first means completion/closure refuses until consumed. No lost request at completion.
7. Commit. Return the immutable receipt. After uncertain commit, reacquire/read F; never allocate another key. A hold stores diagnostic/retry state but **no final F receipt** or consumed task budget, so resolving its blocker may retry the same identity. Final skip/ignore receipts are immutable; replay defaults to returning them. Outbox writes and consumed accounting roll back with task creation on every failure.

Pause/revocation races serialize: if the revoke commits first, filing holds; if filing commits first, its task/receipt exists and revoke applies to subsequent dispatch/current grants. Disable holds unfiled matches immediately; already committed tasks keep their independent task lifecycle, approvals and dispatch policy. The UI MUST state that pausing a binding alone does not pause/stop its existing tasks and link authorized task pause/stop controls. Revoking filing authority prevents new F commits, not historical receipt retrieval. Revoking the standing task-approval reference blocks unstarted tasks that inherit that approval until separately reapproved; revocation of execution capabilities/owner policy uses the normal task policy/stop path. None is undone by re-enabling the binding. Remove cancels unfiled matches permanently; existing tasks follow their current task policy. API/UI MUST state this distinction.

### Crash oracle

| Crash or race boundary | Durable result and restart requirement |
|---|---|
| Before registration intent / after intent before open | No collection, or pending intent retried with same identity |
| Remote open succeeds / local reply lost | Same persisted operation returns original fence/baseline, no moving activation |
| Page received / before journal commit | Cursor unchanged; retry page; no match permitted from volatile page |
| Journal commit / before reply acknowledgment or matcher wake | Events and cursor exist together; consumer scan/outbox resumes, duplicates reuse E |
| Matcher midway / before checkpoint commit | No partial checkpoint; replay inserts M once |
| Match commit / before lease or filing | Pending scan resumes M with new fence |
| After F reservation / task ID allocation / task insert / attribution / receipt / outbox, before COMMIT (each independently) | Entire filing rolls back, no visible task or receipt; retry same F; sequence gaps allowed |
| COMMIT accepted / client loses response | Task and F visible together; retry returns same receipt/task, even after task completion or config edit |
| Outbox delivered / ack lost | Repeat wake by `(receipt,effect)`; task and attachment not recreated; external notification may repeat if receiver lacks dedup |
| Lease expires during remote read or before filing commit | Late collector/matcher fence rejected; new worker safely retries same operation/F |
| Two workers or binding versions race F | Database uniqueness + locks permit one receipt; loser reads it, never creates second task |
| Completion vs coalescing vs disable/revoke | Shared task/group/policy revisions choose one serial result; no acknowledged request without receipt/processing barrier |
| DB restore while created tasks survived elsewhere | Dispatch remains fenced; reconcile surviving origins/receipts and external effects before replay. Incoherent restore cannot claim once-only |

## TTS-20: Repeat, updates and old authority {#TTS-20}

An implementation can start with built-in time plus local journal/FileTrigger, then add the explicit pull adapter. It need not wait on the resource Watch delivery transport or a gate evaluator. Reuse the same neutral interfaces when those ship. End-to-end GitHub enable still depends on its own gateway/pin/read grant and atomic task service. No runtime implementation proposal or task is filed here.
