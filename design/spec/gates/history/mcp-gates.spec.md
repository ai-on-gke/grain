# MCP gate evaluation and lifecycle specification

> **Deferred historical proposal.** Not normative for initial gates. Use [the canonical gate specification](../gates.spec.md). MCP hosting, paging and remote profiles below are not implementation prerequisites.

**Status:** proposed, normative for the protocol described here; not implemented. Documentation approval does not migrate any task or authorize implementation/deployment/follow-up filing.

**Specifies:** [Extensible MCP gates](../../../design/gates.design.md).

The words MUST, MUST NOT, SHOULD, SHOULD NOT and MAY have their BCP 14 meanings. Requirement IDs are stable. [wire.schema.json](wire.schema.json) is a JSON Schema 2020-12 document containing concrete request, response, attachment, action-event, waiver and reference-page, delivery, discovery and disjoint continuation/final schemas in `$defs`. Validate each message against its named definition, then apply the cross-field invariants below. These are documentation assets, not a new runtime validator or deployed endpoint. The normative [action gate bindings extension](../action-bindings.spec.md) and its [schema](action-bindings.schema.json) extend these requirements to protected operations, inherited resource policy and taskless callers. Snapshot transport remains in this wire schema; the separate action profile negotiates its authority context explicitly.

**Terminology:** Task goals such as `pr-merged`, `base-green` and `person-closes` retain their existing desired-outcome/standing-intent meaning and concrete APIs/configuration. Gates are this proposal's extensible evaluators/requirements for readiness and completion. All `gate_*` tool names and fields below belong only to the proposed extension; no legacy goal API or runtime behavior is renamed. The `MGS-*` requirement IDs remain stable from PR #1666.

## 1. Authority and attachment {#MGS-1}

1. Grain MUST own admission, lifecycle transitions, dispatch, operation arbitration, authorization and closure. An evaluator MUST NOT write these directly. Task completion authority MUST be exactly one of legacy or gates at a recorded authority epoch. Observation-only results MUST NOT affect legacy task decisions.
2. An extension MUST expose an MCP `tools/list` entry named `gate_<method>`, where method matches `^[a-z0-9][a-z0-9_-]{0,62}$`. Its `inputSchema` MUST describe the request envelope, with provider-specific capability-style `args`. Discovery MUST NOT attach a gate or authorize its reads/actions. `mint_*`, `release_*` and `configure` retain their capability meanings; `gate_*` MUST NOT be treated as a mint method.
3. An admitted contract MUST enumerate stable gate IDs, whether each is required, canonical provider identity and immutable release/artifact pin, tool name, gate version, argument schema digest, state version, validated canonical arguments and their digest. A schema digest MUST cover resolved local definitions; remote schema fetches MUST NOT occur during evaluation. Resolve capability-style defaults before hashing. Provider args MUST use the supported capability argument-schema subset; secret values and credentials MUST NOT be arguments.
4. Grain MUST separately authorize (a) contract attachment/editing, (b) evaluator access to the declared bounded read scope, (c) user/agent evidence reads and (d) every action. A required obligation with no read permission MUST remain required and unknown with a permission blocker. It MUST NOT implicitly mint access or waive itself.
5. Contract, policy and child-link edits MUST increment contract revision and invalidate affected results, waits, buttons and waivers. Removing/relaxing a requirement, changing success into closure, or replacing a provider MUST require an authorized person's reasoned approval unless that exact transformation was preauthorized in the contract. An agent MAY propose edits; it MUST NOT drop its own obligations to finish. Record before/after, actor, reason and authority epoch. Adding requirements MUST also respect caller authority and template constraints.
6. MCP annotations are hints, not authorization. Grain MUST enforce read-only execution independently of any `readOnlyHint`.

## 2. Requests, snapshots and state {#MGS-2}

1. Completion-profile `tools/call` arguments MUST validate against `$defs.request` for wire protocol 2.0; action-profile 3.0 envelopes use the separately negotiated AGB-3 schema over the same transport. [MGS-11](#MGS-11) defines the required Grain-driven transport for every mode and round. `mode` is `evaluate`, `migrate` or `recover`. The envelope includes protocol version, evaluation and attachment identity, deadline, exact pins/arguments, expected state revision, versioned state, contract revision, authority epoch, lifecycle policy revision and a versioned snapshot manifest. Grain MUST generate IDs and hashes; providers MUST NOT choose the authority context.
2. Snapshot `id` identifies immutable relevant evidence at `evidence_revision` and `cursor`. It MUST include contract, current head/change identities, authoritative observations, processed and incoming message watermarks, relevant children with relationship and outcomes, operation/action/waiver events, permissions metadata and available evidence references. Only Grain may advance the processed-message watermark, based on recorded delivery plus run disposition/response or an explicit authorized no-agent disposition; an evaluator summary/state MUST NOT mark a message processed. Full relevant state MUST be accessible within declared scope via bounded inline records and paginated snapshot-bound references. Necessary inaccessible facts MUST be marked unavailable with a reason, not silently omitted or read as false.
3. The complete inline snapshot manifest MUST be at most 256 KiB UTF-8 JSON. Snapshot data MUST be redacted, read-only and registry-schema validated. Each page is at most 128 KiB/100 records. One evaluation, **across all rounds and retries**, has a fixed 30-second deadline and at most 64 distinct pages/8 MiB of page envelopes, subject to MGS-11's unified bounds. The manifest MUST name all declared input domains and explicitly mark unavailable/incomplete domains. Larger necessary evidence requires a narrower authorized contract or unknown, never arbitrary truncation/met.
4. Pages MUST validate against `$defs.page` and come only from Grain's retained immutable materialization. The snapshot ID is an opaque scoped handle, not connectivity or credentials. Providers request catalog references/cursors in `$defs.needs_data`; Grain validates and delivers `$defs.delivery` in a subsequent call to the same pinned tool. There is no callback or provider fetch. MGS-11 supersedes the historical unspecified read-handle language and defines authorization rechecks, retention, cursor semantics and non-final continuation.
5. All gate results used in a lifecycle/action decision MUST refer to one snapshot ID, evidence revision and contract revision. Relevant changes during evaluation MUST make the result bundle stale even if UI status did not change. Grain MUST reject stale responses before state persistence or actions. It MAY reuse unaffected cached evaluation work only by explicitly revalidating it into a new consistent bundle; it MUST NOT concatenate results from differing snapshots as if current.
6. `gate_state` MUST be opaque JSON interpreted only by the pinned provider, bounded to 16 KiB encoded UTF-8, depth 16, with no credentials. Grain MUST validate its envelope and compare-and-swap expected revision for every accepted update. State revision MUST increase by exactly one for every accepted non-error final candidate, including identical values and null reset. It MUST be monotonic per attachment across explicit migrations/recovery and stored with provider/gate/state-version identity; revisions MUST NOT be reused under a new pin. Only a non-error final result can update state; needs_data and controller aborts MUST NOT. An accepted evaluation ID MUST be unique; retries MUST NOT apply state twice. Result, updated state, subscriptions and evaluation cursor MUST commit atomically, or none do. Provider state MUST NOT substitute for authoritative CI/review/approval evidence.
7. Version changes MUST use an explicit contract migration record with old/new pins and state version. `mode=migrate` supplies `previous_pin`, old state and current authoritative snapshot to the new pinned evaluator; it MUST return transformed state only, with status unknown, no actions/work/waits/buttons. Grain validates and CASes the migration, switches contract pins and schedules fresh evaluation atomically, invalidating prior results. A failed migration MUST preserve the old state/pin. No provider replacement may silently interpret old state.
8. `mode=recover` is allowed only when the pinned provider declares evidence replay safe. It receives null state and a reasoned recovery record; it MUST rebuild from authoritative evidence, return unknown and no work/actions/waits/buttons, and MUST NOT invent approvals. Otherwise recovery MUST hold for an authorized migration/repair. Preserve old state for audit. After recovery, evaluate afresh. Provider unavailability MUST NOT trigger automatic reset, downgrade or legacy fallback.
9. V2 defaults: the unified limits in MGS-11 cover materialization, all rounds and retries; response at most 256 KiB, at most 32 work items, 32 action requests, 64 waits, 16 buttons and 128 evidence references. Grain MAY lower bounds by recorded deployment policy and MUST advertise effective limits in the request; it MUST reject oversized/deep JSON before allocating unbounded memory. Deadline expiry is a timeout, never met.

## 3. Result semantics and compatibility {#MGS-3}

1. Completion-profile responses MUST validate against the disjoint `$defs.response` union (action-profile 3.0 uses the AGB-3 union with the same disjoint continuation/final semantics) and echo protocol, bundle/evaluation/round, request digest, gate, snapshot, contract, authority epoch, lifecycle policy, permission/scope, evidence and state revisions exactly. A response is either non-final `kind=needs_data` (MGS-11) or `kind=final`. MCP `structuredContent` carries this object, with the existing client’s single JSON text result fallback allowed; human-readable renderings are non-authoritative. Only final responses have statuses `met`, `unmet`, `pending`, `error`, `unknown`:

| Status | Meaning | Required handling |
|---|---|---|
| met | The declared predicate holds on the snapshot | Grain validates required evidence and scope; eligible for aggregation, not immediate self-close. |
| unmet | Predicate is known false | Show blockers; dispatch only explicit useful authorized work. |
| pending | An identified external operation/event is still unresolved | At least one viable wait or in-flight operation reference is required. Other independent work can run. |
| error | Evaluation failed | Error code and retry classification required; not unmet or met. |
| unknown | Evidence, permission, compatibility or interpretation is insufficient | Explain missing information and recovery/wait path; MUST NOT default to met. |

2. Every **final** response MUST carry a one-line summary (maximum 240 characters, no newline), evidence references, `gate_state` candidate, blockers, work, action requests, waits, buttons and optional separate `human_text` and `agent_text`. Evidence MUST reference records from the supplied authorized snapshot with immutable versions. Met MUST carry at least one reference, including a Grain-recorded no-work/report/person-action record where appropriate. Grain MUST verify evidence kind, subject, version, freshness and predicate-specific prerequisites using the registered contract; a fabricated ID or scope mismatch invalidates the whole response.
3. A blocker identifies kind (`answer`, `permission`, `acknowledgment`, `external`, `work`, `provider`, `policy`), a stable key, explanatory summary and optional related evidence. Text is untrusted presentation, never instructions with system authority. Grain MUST escape/sanitize display, redact known secrets in logs, avoid interpreting embedded links as action targets, and keep agent text labeled as provider output.
4. Work MUST identify stable key, target, summary, dependencies, evidence preconditions, and required registered tools/permissions. A provider MUST NOT make executable code or arbitrary URLs a structured operation. Agent work can include an ordinary task instruction such as investigate a cited failing test; it cannot confer a new grant. `action_requests` MUST name registered actions and validated JSON inputs, stable key, reason when required and expected evidence. Grain MUST reject unknown operation IDs rather than dynamically registering them.
5. For `met`, work/action requests and blockers MUST be empty; waits MAY request monitoring only under an explicit regression policy. For `error`, work/actions/buttons MUST be empty. A `pending` response with no viable wait/in-flight reference is `invalid_result`. Migration/recovery restrictions in MGS-2 override ordinary result semantics. A response MUST NOT request work whose dependency is its own unsatisfied output or otherwise form an action dependency cycle.
6. Wire v2 is exact: unknown envelope fields or unknown enum values MUST fail validation; extension payloads belong in registered `args`, record `data` or opaque `gate_state`, not ad hoc envelope keys. Compatible new optional protocol fields require negotiated minor support; required/semantic changes require a new protocol version. Grain MUST refuse unsupported pins/schema/protocol at attachment/admission or hold an already-admitted task unknown after an upgrade. No coercion of unknown status to false/success is permitted.
7. MCP transport failure, `isError:true`, malformed JSON, schema mismatch and deadline are protocol failures, not task verdicts. Grain MUST normalize failures to a synthetic error result without committing candidate state. Error codes are `timeout`, `unavailable`, `unauthorized`, `unsupported_version`, `invalid_request`, `invalid_result`, `state_conflict`, `stale_snapshot`, `reference_expired`, `resource_limit`, `provider_error`, `request_loop`, `canceled`. MGS-11 defines read-error deliveries and retry/restart classification; a diagnostic synthetic final is not an accepted result. Stale/conflict causes coalesced reevaluation, not agent dispatch. Invalid/persistent compatibility/authorization failures need operator recovery; transient timeout/unavailable/provider errors back off. Provider error text MUST NOT expose credentials.
8. Grain MUST retain accepted results, rejected-result diagnostic hashes/reasons, and closure/action receipts sufficient to explain decisions. Unknown/error in a required gate blocks success unless a separate valid waiver applies; advisory errors do not block success.

## 4. Actions, buttons and waivers {#MGS-4}

1. Initial evaluators MUST be pure bounded replayable read-only functions of arguments, the retained snapshot view/current deliveries, durable state, bounded request-carried continuation and declared clock/deadline. They MUST NOT send messages, mutate providers, submit reviews, merge, deploy or call write tools during evaluation. Execution credentials MUST exclude those powers. Evaluation MUST NOT perform external reads; collection happens before the snapshot cut. Current-round scratch computation remains subject to time/data limits.
2. Grain MUST execute requested actions through the same Grain action executor used by agent, operator and automation requests. Protected effects MUST resolve non-optional action guard bindings under AGB-1 through AGB-8, independently of task completion authority. Equivalent tools/actions and taskless requests MUST NOT omit resource policy. The executor uses registered authorized operations/tools available to agents. An agent MUST have required tools/permissions or be able to request them through the normal permission flow. Future optimized execution MUST reuse the same path, with no privileged alternate implementation and no requirement that optimization be enabled to make progress.
3. `$defs.button` contains label, registered `action_id`, `input_schema`, fixed/default inputs, evidence preconditions and confirmation requirements. The input schema MUST be a constrained subset of the registry's schema; it MUST NOT broaden it. Registry policy is the minimum confirmation and required reason. No executable code, callback URL or provider-defined permission check is allowed. Button availability is a server-derived convenience, not authority.
4. At action request or click, Grain MUST check current actor role/delegation, grants, human-only restrictions, current contract and evidence versions, live preconditions, input schema and required confirmation/reason. For external mutations, Grain MUST pass the expected head/resource version to a conditional operation where supported; if the source cannot enforce that condition, Grain MUST serialize its own writers, re-read immediately before execution and reconcile uncertain results before accepting outcome evidence. Those steps alone MUST NOT be claimed to prevent external races: protected admission additionally requires the AGB-4/AGB-5 conditional/exclusion boundary, otherwise Grain MUST refuse enforced execution. Revoked authority or stale evidence MUST refuse with a reason and refresh, not perform the action. Acknowledgment MUST record receipt only; Submit/approval MUST use their own registered actions. A note containing “approved” MUST NOT produce an approval event.
5. For the task completion profile, the operation ledger MUST durably record an immutable `action_event` with actor, action ID, inputs, reason when required, gate/contract/evidence scope, request ID and idempotency key before starting a side effect. Event phases are requested, started, succeeded, failed, unknown; append events rather than editing history. Action-profile operations, including taskless requests, use AGB-3 `operation_event` plus `receipt` records with equivalent intent/audit requirements. Use an outbox/intent transaction and operation-specific idempotency/reconciliation for the external boundary. A crash after an external success MUST reconcile its authoritative receipt before retrying; it MUST NOT blindly repeat. Gates MAY consume these events but a requested/started event is not evidence of successful side effect.
6. A waiver MUST be a Grain-owned `$defs.waiver` record with authorized actor, nonempty, non-whitespace reason, gate/provider/version/argument/contract/evidence scope, issue time, optional expiry and explicit invalidation keys. Grain MUST enforce invalidation on head, gate/schema/args, scoped evidence, policy or authority changes and revocation; defaults MUST invalidate on any scoped change. A provider MUST NOT create a waiver by returning state or prose. UI MUST display waived distinctly from met, with reason and actor. Waiver permission MUST be explicit and person-only by default; agents can request it, not grant it.
7. A completion waiver MUST NOT authorize a protected action or stand in for approval. Existing merge gate overrides retain `merge:force`, exact-head scope, reason, confirmation and their action audit; Submit retains human approver policy. Merge readiness supplies guard satisfaction only while all required action prerequisites hold; it MUST NOT confer caller authorization. AGB-6 governs separately authorized exact-action/head/guard overrides. Action overrides MUST NOT waive completion obligations. Observed merge/CL submission satisfies the integration gate for the desired integration outcome.

## 5. Aggregation, arbitration and progress {#MGS-5}

1. Required completion gates are an explicit conjunction; advisory gates do not block completion. Action guard aggregation is a separate conjunction under AGB-2: integration of the same PR MUST NOT be a prerequisite for executing its merge. Each required gate MUST be met or covered by a currently valid waiver. Empty gate sets MUST require an explicit admitted no-obligations contract, never result from discovery failure. Grain MUST decide lifecycle from the consistent bundle, not from a provider's requested task status.
2. Grain MUST first validate results and deduplicate work/actions across gates by registered operation/tool, target, canonical inputs and precondition scope, preserving all requesting gate IDs. Stable provider keys are hints; Grain computes identity. Conflicting requests MUST be serialized or surfaced for resolution, not executed in provider arrival order. Dependency order, task priority and deterministic stable-key ordering resolve eligible nonconflicting work; dependency cycles are errors.
3. There MUST be at most one active task agent run, enforced by a durable lease/unique active-run constraint with fencing tokens. Concurrent external operations are permitted only under registered resource locks and compatibility rules (for example independent CI and review reads). Two mutations of the same branch/head, merge and branch edit, or incompatible contract edits MUST serialize. Shared-resource operations across tasks MUST use the same locks. An evaluator pass is not a task agent run and MUST NOT bypass operation locks.
4. An event wait on any gate MUST NOT suppress independent actionable authorized work on another gate. Dispatch MUST require a new user request, actionable work or a justified continuation under lifecycle policy, available permissions, settled conflicting operations, admission and capacity. An unmet/error/pending status alone is not work. Missing permission blocks its dependent work, not unrelated work; global pause/budget policy may still hold the task.
5. Grain MUST persist progress as changes in authoritative evidence, completed operations, processed messages and settled child outcomes. Provider progress tokens, summaries and opaque-state churn MUST NOT alone reset no-progress/error counters or schedule another run. After two identical no-progress attempts on the same work/precondition identity, default policy MUST hold that work and escalate with evidence; changing this threshold requires recorded lifecycle policy. Provider failures MUST use a separate counter and MUST NOT consume an agent task-failure streak merely because a provider is down.
6. Default transient evaluator retry is exponential backoff from 30 seconds capped at 30 minutes with bounded jitter, persisted across restart; five consecutive failed evaluations raise a deduplicated operator blocker; ten hold automatic retries pending authorized resume. Same-round retransmissions and stale/churn restarts have the separate tighter bounds in MGS-11 and do not reset this counter. New relevant evidence MAY cause a bounded immediate retry but MUST NOT defeat provider-wide circuit/rate limits. Repeated identical errors MUST NOT emit unbounded comments/events or dispatch agents. Missing viable wake, exhausted polling, and unmet-without-remedy MUST name a driver and escalation. Independent work MAY continue.

## 6. Durable wakes and evaluation triggers {#MGS-6}

1. Grain MUST dirty evaluation on relevant CI/check/review/PR/CL events, head/base observations required by the predicate, child outcomes, user messages/actions, permission/role changes, contract/provider/schema changes and timer deadlines. Displayed state transitions alone are insufficient. Provider-authored summary/state/result storage MUST NOT be evidence-change triggers for that same evaluation loop. Explicit cross-gate dependencies MUST be versioned and acyclic.
2. Waits MUST name registered event kind, resource, predicate/scope, durable cursor, deadline, fallback polling where needed and escalation. Grain validates scope against the attachment and normalizes subscriptions; arbitrary event code or subscription URLs are forbidden. Persist subscription generation (contract/head scope), progress, last observed source version, journal cursor, next poll, backoff and timer firing state. Changing head/contract MUST retire old wait generations and create replacements.
3. Grain MUST avoid the snapshot-to-subscription lost-event race. Take snapshot at durable journal cursor C; atomically commit accepted results/state plus waits starting at C; replay relevant events after C before marking the bundle quiescent. If subscriptions are external, register from C when supported; otherwise establish collection before the snapshot and use bounded authoritative polling/reconciliation as the gap backstop. External events first enter the journal; a provider's cursor is never trusted to skip unseen evidence.
4. Event deliveries MUST be idempotent by source/event ID. Duplicate/out-of-order delivery MUST NOT regress authoritative source versions or resurrect old waits/approvals. On every wake, Grain MUST reread the authoritative current resource (or an observation with verified source version/freshness) before evaluating. Event payload alone MUST NOT establish success. A deleted/unreadable resource is unknown or an explicit failed outcome, not success.
5. Grain MUST coalesce relevant events per task and permit at most one accepted evaluation bundle per snapshot/contract epoch; an obsolete concurrent evaluation MUST lose its CAS. A wake evaluates first and dispatches an agent only if useful work remains. Dirty evidence arriving during evaluation MUST schedule a bounded next pass, not recurse synchronously forever.
6. Timers MUST be durable and recover due firings after restart using an idempotent firing key. Deadline expiry MUST trigger re-read, pending/error/unknown or escalation, never imply success. Without reliable events, default polling MUST back off from one minute to 30 minutes, bounded by the wait deadline; no more than 100 polls per wait generation before escalation unless policy explicitly extends it. A ten-minute default reconciliation sweep MUST recover missed events, expired evaluation/run leases and overdue timers. Deployments MAY tune intervals with persisted policy and a visible liveness bound.

## 7. Lifecycle, children and atomic close {#MGS-7}

1. Proposed tasks MUST await admission authority; their evaluations MAY preview but MUST NOT dispatch or close successfully. Admission records approved contract/policy revisions and authority epoch. Ready admitted tasks awaiting capacity MUST project waiting with a ready/capacity scheduling reason, distinct from an external gate wait. Active UI states MUST include running, waiting, needs answer, needs permission and needs acknowledgment; show every blocker irrespective of primary state. Primary precedence is running, needs answer, needs permission, needs acknowledgment, waiting. Scheduling/pause/error reasons remain separately visible, including when other work runs.
2. Terminal task outcomes MUST be succeeded, canceled or failed. Succeeded requires the closure predicate below. Cancel is an authorized stop, not satisfaction. Failed requires explicit Grain failure policy or authorized failure action and recorded reason; a provider exception/deadline MUST NOT alone imply task failure. A run's succeeded/failed outcome MUST NOT by itself become task outcome.
3. Pause, admission class, budget/usage limits, backoff, keep-running, close-versus-rest, failure exhaustion and standing person-closes behavior MUST be Grain lifecycle policies, not arbitrary gate predicates. Pause/budget blocks dispatch but does not erase evidence. Close-versus-rest=rest retains a satisfied task open and subscribed. Standing person-closes sessions MUST rest between turns; an authorized person's close event permits success only with remaining required obligations met/waived and operations/messages handled. Cancel remains available as canceled.
4. Child relationships MUST be explicit: `required_outcome` names its predicate (default success, optionally integration or explicit terminal closure), `advisory` supplies evidence but no completion hold, `independent` creates no completion obligation. Spawning a task MUST NOT implicitly attach a required outcome. Child closure MUST NOT imply success. Parent/child/dependency graph edits MUST reject cycles transactionally across concurrent edits; existing corrupt cycles MUST become visible blockers rather than recursive evaluation. Failed/canceled required children MUST remain unmet and offer authorized repair/replacement/waiver, not quietly count as delivered.
5. Grain MUST close atomically only when: authority epoch/contract/policy match; every required gate is met or validly waived on the still-current snapshot; all incoming user messages through the current watermark are processed; and active operations are settled or explicitly dispositioned under policy with recorded ownership and outcome handling. The close transaction MUST lock/CAS relevant task revision and message watermark, evidence vector, result/state revisions, waivers, and operation ledger, then append closure receipt and terminal outcome together. A concurrent message/evidence/action insertion MUST either precede and invalidate close or follow the committed closure and use closed-task/reopen policy. Child evidence invalidation MUST participate in the same version fence.
6. A live run MUST be gracefully stopped and settled before close, unless explicitly transferred as an operation under recorded policy. Do not label it succeeded merely because gates were met mid-run. Late branch writes/results invalidate closure preconditions. A pending post-merge review continuing under the existing override policy MAY be explicitly transferred to a repair/review owner with its evidence and obligations recorded; it MUST NOT be abandoned by closing the implementation task.
7. Later regressions MUST preserve the closure receipt and original evidence. Reopen or separate repair MUST follow an explicit policy with actor/reason and new authority/contract epoch; default is notification plus authorized repair. Closed-task messages remain recorded and undelivered until explicit reopening per existing policy, not treated as already processed. Acknowledgment means receipt, never approval or implicit waiver.

## 8. Persistence, APIs and migration {#MGS-8}

1. Grain MUST durably store contract revisions/authority epochs, attachment pins, bounded state/CAS versions, evaluation bundles, evidence/version vectors, action intents/events/idempotency, waiver scopes/revocations, subscriptions/cursors/deadlines, no-progress/error counters and closure receipts. Unique constraints and fencing MUST survive retries and daemon restart. Retention MUST keep decision evidence and audit references even if bulk snapshot pages expire.
2. Go `StateOf` and SQL `task_state` (SQLite and PostgreSQL) MUST select the same authority branch and lifecycle precedence. Migration MUST add fixtures covering all simultaneous-state/blocker cases and parity checks. Legacy report-completed, merge readiness and new succeeded MUST NOT share an ambiguous storage bit. Public legacy fields MUST be documented compatibility projections, not a second authority.
3. Future API/tools MUST expose versioned contract reads/conditional edits, per-gate result/evidence/blocker reads, registered action submission/status, waiver issue/revoke and lifecycle history. Mutations MUST carry expected contract/evidence versions and idempotency key; stale/conflict is 409, authorization failure 403, invalid input 400/422 with stable code and current refresh reference, unavailable provider 503 where applicable. No endpoint in this document is deployed. Agents MUST receive the same operation contracts and permission-request path as UI callers; shared API changes MUST keep both UIs working.
4. The UI MUST show per-gate status (including waived/unknown/error), summary, optional human text, evidence, all blockers, waits/deadlines, action state and typed buttons. Agent text/work MUST remain distinct from human presentation. Server-derived primary state, current evidence scope and confirmation apply to Angular; classic compatibility MUST NOT invent success for unknown new states.
5. Migration MUST follow the design's phases: retain collectors; shadow evaluators; compare legacy decisions; explicit per-task authority handoff; central transactional completion; then durable waiting/dispatch; remove old paths last. At handoff, fence active runs/operations, import legacy predicates with provenance, invalidate old decision waits, and atomically disable legacy lifecycle writes. There MUST never be two lifecycle authorities for the same task. During the interval before durable waiting/dispatch migration, legacy drivers MAY emit observations or proposals through a compatibility adapter to the single new owner, but MUST NOT retain direct lifecycle writes. Existing open tasks remain legacy until explicitly migrated.
6. Upgrades MUST deploy compatible readers before gate writers and fence old daemons. A daemon unable to interpret authority/protocol/schema versions MUST hold the task and expose a compatibility blocker, never revert to legacy. Rollback MUST preserve records and require explicit reverse handoff to a representable validated legacy contract; otherwise pause gate-owned execution for a compatible version. An unavailable required provider remains unknown with retries/escalation, never automatically waived, dropped or replaced.

## 9. Complete wire examples {#MGS-9}

[The example index](examples/README.md) maps each complete machine-readable transcript to its required outcome. Each `*.json` transcript validates against `$defs.transcript`; every call/reply/delivery is a complete envelope, not a patch or implied field omission. Requests and chained response digests are computed from canonical JSON. The local [example record registry](examples/evidence.schema.json) validates all delivered sample records; it illustrates registration, not a universal replacement for Task #45's provider fact schemas.

The complete tools/list example embeds the resolved envelope and input declaration, including pinned record-schema digests. The success transcript covers three calls, two pages and one final state CAS. Other transcripts cover repeated reads, denied and mixed-availability reads, permission revocation, bulk expiry on recovery, stale evidence, provider timeout, provider crash/exact retry, Grain crash/checkpoint recovery, partial required input, prefetch and cancellation. A controller_error step is diagnostic only and MUST NOT be accepted or CAS state. Event steps describe journal/storage/time events; they are not extra MCP messages. MCP wrappers are standard `tools/call` requests with each call's message as `arguments`, and replies as `result.structuredContent`.

## 10. Acceptance scenarios {#MGS-10}

Protected-operation scenarios additionally MUST satisfy [AGB-7](../action-bindings.spec.md#AGB-7), including bypass prevention and blocked-then-allowed agent merge. Lifecycle migration does not imply action enforcement admission.

These are requirements for later implementation tests, not tests or implementation added by this documentation PR.

| Scenario | Required observation |
|---|---|
| Initial/prefetched round returns valid final | One validated final receipt/state CAS; all page/byte/read budgets include prefetch. |
| Paged needs_data returns two rounds before final | Same snapshot/pins/clock; no gate result, state CAS, subscription, action, lifecycle, progress or agent/trigger dispatch during continuation. |
| Exact duplicate round vs later repeated page request | Exact retry replays stored request within counters; later repeat gets one no-data loop warning then unknown or bounded abort. |
| Provider asks denied/unknown reference | Indistinguishable unauthorized delivery without records; no scope expansion or missing-as-false/met. |
| Partial, unsupported or oversized required domain | Explicit unavailable marker; final unknown or error; Grain refuses met even with terminal page. |
| Snapshot pages lost/expired; driver restarts | Abort unavailable/reference_expired, never refill from current DB or extend old deadline; new snapshot only under bounded restart policy. |
| Revocation or freshness expiry between rounds | Abort/fence all affected bundle candidates/buttons; no further delivery/accepted state; restored permission requires fresh snapshot. |
| Provider crashes/lost reply; Grain crashes around checkpoint/commit | Deterministic exact request replay with no provider session, lease fencing and one logical round/final commit. |
| Provider timeout, late met or explicit cancellation | Abort diagnostic only; preserve durable state, no action/close; late response discarded and bounded retry/backoff. |
| Churn, many unique pages or request loop | Eight-round/64-read/64-page/8-MiB/30-second bounds do not renew; coalesced stale retry limit/hold/escalation survives restart. |
| Head changes while reviews return met | Reject old bundle/state/button; retire old waits; evaluate current head; no merge/close. |
| Message races atomic close | Earlier committed message blocks close until processed; later message is retained under closed-task/reopen policy. No lost message. |
| Two evaluation responses race state CAS | Exactly one accepted revision; loser cannot overwrite state, subscriptions or actions. |
| CI completes between snapshot and subscribe | Journal replay from C observes it without waiting for another event; authoritative re-read precedes decision. |
| Duplicate/out-of-order review/PR events | No version regression, duplicate action or stale approval resurrection. |
| Restart with due timer or operation intent | Recover timer once logically; reconcile side-effect receipt/idempotency before retry; no blind duplicate merge. |
| Required CI provider unavailable | Unknown/error, persisted capped backoff and escalation; no false success, legacy fallback or dispatch loop. |
| Provider returns arbitrary URL/code, forged evidence, oversized state or unknown action | Reject/sanitize as appropriate; no network fetch, execution or authority expansion; preserve old state. |
| Provider uses state to claim approval | Only authorized action/review records count; no approval from state/prose. |
| User loses permission after button rendered | Server refuses action; audit refusal and refresh; no side effect. |
| Waiver/review scope stale after new head, changed args or policy | Waiver invalid and review rechecked; distinct historical records remain. |
| Acknowledgment or note says approved | Receipt/note does not satisfy Submit, review or protected-action permission. |
| Scoped waiver issued without merge permission | Completion exception recorded, merge still refused. |
| Required child fails/cancels; advisory child still running | Required success unmet; advisory never blocks; explicit legacy closure predicate remains distinguishable. |
| Concurrent child edits create cycle | One edit rejected transactionally; no recursive deadlock. |
| Gate A waits for review while B can write report | One useful authorized run for B; A wait remains durable and visible. |
| Two gates request same repair; merge conflicts with branch write | One repair intent; conflicting operations serialize and recheck scope. |
| Evaluator churns summary/state or repeats identical work | No feedback wake; no progress credit; bounded no-progress attempts then hold/escalation. |
| Missed webhook, expired cursor or event service outage | Reconciliation/polling detects current truth; deadlines escalate, never succeed. |
| All gates met while a run can still push | Settle/fence run and re-read before close; late evidence invalidates old close attempt. |
| Migrate/rollback with older daemon or missing provider | One authority remains; incompatible daemon holds; no silent contract weakening. |
| Base failure did not reproduce; publishing remains broken | Recorded non-reproduction can satisfy base-green only; required publishing outcome remains unmet. |
| Review finishes with findings or Submit arrives early | Review task delivery may succeed; merge prerequisites remain blocked until clean review/explicit permitted override. |
| Regression after success; person-closes session healthy | Preserve historical success and use explicit repair/reopen; session rests and remains open. |

## 11. Grain-driven snapshot transport {#MGS-11}

This section is normative. It replaces the v1 draft's unspecified “registered read-only snapshot access handle” transport. V2.0 is a semantic protocol revision, not a backwards-compatible optional field addition. There is no v1 fallback. Snapshot IDs and reference/cursor IDs are scoped opaque identifiers resolved only by Grain. They are neither URLs nor bearer credentials. No provider-to-Grain callback, callback listener, new provider network reachability, namespace read tool or bidirectional RPC is required or authorized. A future callback transport is deferred and would require a separate versioned design and security review; it is not an implementation hook in v2.

Action-profile 3.0 composes this same transport under [AGB-3](../action-bindings.spec.md#AGB-3): only the negotiated outer request/response/discovery envelope and action authority context differ. References below to the outer v2 request/response/discovery select their AGB counterparts for that profile; snapshot version 2, inner page/delivery schemas, counters, digest/replay rules and final-only commit remain unchanged. There is no fallback or provider callback path.

### 11.1 Discovery and MCP binding

1. Each advertised `gate_<method>` tool MUST place a `$defs.discovery` object at `inputSchema["x-grain-gate"]`. Its `inputSchema` MUST otherwise validate the full `$defs.request` envelope, constraining `args` to its capability-style argument schema. Local resolved schema definitions only; no remote references. `x-grain-gate` is a JSON Schema annotation consumed by gate discovery, not a tool argument or capability grant. Discovery MUST reject a missing/unsupported declaration.
2. The declaration pins protocol 2.0, snapshot version 2, transport `grain_rounds`, continuation format version 1, recovery replay safety, and at most 32 input domains with supported registry record kinds, required/optional status and prefetch preference. Its record_schemas list contains at most 64 unique kinds and the canonical resolved local schema digest for every declared/inline kind; references MUST echo the matching digest. All declared kinds MUST have exactly one registry entry and undeclared kinds MUST NOT be delivered. Domain names and kinds MUST be unique in their respective arrays. The canonical declaration digest is `pin.input_declaration`; the host MUST verify it and the registry schemas against the immutable release at admission and execution. `pin.continuation_version` MUST equal the declaration. The registry MUST bind the approved immutable release to the configured server/process identity (for example an in-tree artifact or approved image digest) and fence configuration/credential epochs in the evidence vector. A provider-claimed version alone is insufficient; an unverifiable release binding is unsupported_version. A supported kind is not permission to read it. The attachment's read scope resolves registered selectors against its pinned canonical arguments; providers cannot add selectors, resource IDs or query expressions during evaluation.
3. Grain SHOULD prefetch first pages for declared `prefetch=true` domains in declaration order then reference-ID order, up to eight reads in initial round 0. Inline records and prefetched pages can supply a single-round fast path. Required inputs that do not fit MUST remain represented by references or explicit unavailability. Prefetch consumes the same page/read/byte/record budgets as subsequent reads.
4. Every round is an ordinary Grain-to-provider `tools/call` of the **same pinned tool** with `$defs.request` arguments; the result MUST be `$defs.response` JSON. Prefer MCP `structuredContent`; the existing client's single JSON text result fallback is also allowed. `isError:true`, JSON-RPC errors and transport errors are failures, never `needs_data`. No second snapshot-read MCP tool is exposed to the provider.
5. The existing [control-tool discovery/caller](../../../../pkg/capability/protocol/server.go), [JSON result decoder](../../../../pkg/capability/protocol/client.go) and [capability registry caller](../../../../pkg/capability/servers/servers.go) provide the call direction. Existing discovery retains non-mint/release/configure tools as control tools and `Server.CallTool` applies a context timeout. Gate declaration validation, rounds, pinned read-only isolation and tighter byte limits still require implementation; today's generic client caps (32 MiB HTTP input) do not enforce this spec. The gate driver MUST pass only remaining evaluation time, never a fresh 30 seconds per call. No runtime capability code changes are part of this PR.

### 11.2 Snapshot construction, completeness and retention

1. Before round 0, Grain MUST copy a bounded **materialized observation cut** into its own snapshot store: a short SQLite read transaction or PostgreSQL repeatable-read transaction reads the relevant DB projection, evidence version vector, contract/policy/permission epochs, message watermarks, child and operation facts and journal cursor together. It MUST copy redacted record JSON and fixed page membership/order (domain declaration order, then kind and record ID in bytewise ascending order), not just store mutable row IDs for later reads. A transactional publication/ready marker MUST make the complete manifest and page index visible together. No DB transaction stays open over an MCP call.
2. External facts MUST first be normalized and committed by authorized collectors (including Task #45's Observe adapters when available). The cut is of Grain's recorded observations, **not** an atomic historical view of independent external systems. Record versions/freshness and source identity MUST be preserved; the registered predicate's freshness requirements still apply. Artifact/log content not already captured as a bounded redacted immutable excerpt MUST be unavailable. Do not lazily fetch a live URL, reread a current DB row or promise upstream historical reads to fulfill a later page. A fresh external read belongs to collection and a new snapshot.
3. The same bundle snapshot/version vector is shared by all gates in one lifecycle decision. Delivery views MUST be separately redacted and scoped per attachment/provider/permission epoch; sharing storage MUST NOT leak another audience's records, reference existence, counts or cache behavior. Every domain in the declaration MUST be listed in `snapshot.domains`; absent, unsupported, unauthorized, over-limit and partially captured domains MUST also appear in `snapshot.unavailable` with a typed code and safe reason. Denial MUST NOT distinguish nonexistent from inaccessible resources. Out-of-scope domains MUST NOT appear as an invitation to expand.
4. Ready references name one registered kind/schema and a fixed ordered nonempty record set. `page_count` and `record_count` describe that set, not a promise that the domain is complete when it also has an unavailable marker. Inline records and page records MUST be disjoint and IDs/versions unique within the view. For a complete empty set, Grain MUST supply a registry-validated coverage/observation record that explicitly proves empty scope; missing records/references alone never prove absence. Reference metadata/counts are themselves authorized information.
5. All record `data` MUST validate against the locally registered kind/schema digest before persistence and delivery. Grain MUST redact before size accounting. The immutable release's kind allowlist, schema and predicate validator MUST agree; malformed or unsupported records MUST make the relevant domain unavailable, not become trusted evidence. Each record data schema MUST enforce finite field/collection sizes and at most 16 container levels. A partial set MAY be delivered with an unavailable marker; it MUST NOT be represented as complete. A single record that cannot fit a page is `resource_limit`; it MUST NOT be split/truncated into a favorable fact.
6. Bulk materialization MUST stop at the aggregate bounds in 11.6. Every DB/external adapter MUST use a bounded projection/scan and stop once it cannot produce another bounded record/page within the remaining byte/record/time budget; unbounded preloading or counting is forbidden. Grain MUST mark the affected domain unavailable, including any unenumerated remainder, and refuse `met` for any predicate needing that complete domain. It MUST NOT allocate an unbounded backing snapshot and only limit delivery. Exact counts of an oversized remainder need not be computed. Providers MAY return `unknown` with a provider/permission blocker and a safe missing-domain explanation after examining partial data. Grain MUST independently refuse `met` whenever a declared required domain or a registered predicate prerequisite is unavailable, incomplete, stale or unsupported. Required-domain delivery is complete only when every inline record and every materialized page for that domain has been delivered and acknowledged by a valid response digest; a complete backing catalog alone is insufficient. All cited records, including earlier rounds, MUST appear in that acknowledged delivery ledger. Optional absence permits `met` only when that predicate does not depend on it; providers cannot redefine this dependency in prose.
7. `snapshot.created_at` starts one fixed 60-second bulk retention window; `expires_at=created_at+60s` MUST be present on the manifest, references and pages. Grain MUST retain published bytes/indexes through that expiry even after completion, under the same ACL. Per-task/global storage admission MUST reserve the finite view budget before publication and refuse unavailable on capacity exhaustion, never evict an active snapshot to admit another. No refresh/extension of cursors, snapshot lifetime or evaluation deadline is allowed. On cancellation/revocation the index is immediately disabled for delivery, even while bytes await expiry. Cleanup deletes bulk bytes after expiry; the audit retention below is separate. Storage loss before expiry is `unavailable`, not permission to reconstruct pages from current data.
8. Grain MUST retain for task audit lifetime the decision's cited redacted records (including cited prior-round records), coverage/completeness and version metadata, pins, accepted final result, state revision, and action/closure receipts. Uncited bulk pages and request-carried continuation JSON expire after 60 seconds. Longer-lived diagnostics retain round IDs, hashes, counters and safe error reasons, not raw transient state. This avoids a short-lived handle becoming a broken audit reference.

### 11.3 Round identity, delivery and provider state

1. Grain allocates a `bundle_id` and snapshot; each attachment/mode attempt has a fresh `evaluation_id`. Round numbers are zero-based, strictly consecutive, maximum 0–7. `(evaluation_id, round)` is the round identity; MCP JSON-RPC request IDs are transport IDs only. `phase=initial` requires round 0, null `previous_response_digest` and null `continuation_state`. Later `phase=continue` requests chain the canonical previous response digest and echo its continuation JSON unchanged.
2. Across rounds Grain MUST keep byte-equivalent pins, arguments/digest, read-scope digest, permission revision, durable `gate_state` and expected revision, mode/migration/recovery context, contract/authority/policy revisions, manifest, limits, `now` and deadline. `now` is the evaluation's fixed declared clock. Only round, phase, previous-response digest, transient continuation, deliveries and request digest change. Lower effective limits and the deadline are fixed at initial construction. Snapshot ID is the handle; the controller resolves it using evaluation/task/provider/permission context, not possession of the ID alone.
3. Digests MUST use SHA-256 of RFC 8785 canonical JSON, written as `sha256:<64 lowercase hex>`. `request_digest` covers the entire request except that field. `previous_response_digest` covers the entire accepted prior `needs_data` response. A provider response MUST echo all identity/version fields required by its schema and `request_digest`. This is the delivery acknowledgment: a valid response acknowledges the exact request and its deliveries. No separate ack message, ack-induced wake or page-consumption write is needed. Hashes bind context; they are not authorization or signatures.
4. A `needs_data` response contains only shared identity, `kind=needs_data`, summary, 1–8 `page_request` objects and bounded `continuation_state`. It is **non-final**: it MUST NOT contain a verdict/status, `gate_state`, blockers/work/waits/buttons/actions or any lifecycle proposal. Grain MUST NOT accept a gate result, CAS durable state, install subscriptions, grant progress credit, execute actions or schedule an agent because of it. Only the existing driver's internal round advances. Transient ledger writes MUST be excluded from the evidence revision/journal that dirties gates and from trigger input streams.
5. Provider execution MUST be a replayable pure read-only function of the current request. V2 permits only request-carried continuation state (format version 1, arbitrary credential-free JSON bounded to 16 KiB/depth 16). Providers MAY use bounded scratch memory within a call but MUST NOT require a server-resident session, cache, filesystem, affinity or external read to resume. Stateless evaluators return null continuation; streaming evaluators encode their sufficient accumulator/cursors in it. If the accumulator cannot represent the predicate within its bounds, return final `unknown` or `resource_limit`, never drop relevant facts. An upgrade cannot reinterpret continuation under another release/version; abort and restart instead.
6. Transient continuation is not durable `gate_state`: it has no independent CAS revision or migration path and is meaningful only for this evaluation/pin. Grain may persist it for crash recovery within bulk TTL. The original durable state is supplied unchanged on every round; only a validated final result can propose its next value. Final error and controller aborts MUST preserve durable state. A successful non-error final (including unknown) is staged until bundle acceptance, then follows MGS-2 state CAS/atomic result+subscription rules once; final `met` remains subject to bundle validation and closure fencing. Modes migrate/recover use these same rounds, but their **final** result must obey MGS-2's unknown-only migration/recovery restrictions.

### 11.4 Read selection, loops and unavailability

1. A page request selects only `reference_id` plus `cursor` within the supplied snapshot/evaluation. `read_id` MUST be unique per logical evaluation read, including prefetch; it is echoed in the delivery. The first page uses null cursor. Each subsequent cursor MUST be exactly a `next_cursor` delivered earlier for that reference. No offsets, arbitrary record lookup, URL, namespace query, new domains, selector or page-size override is accepted. At most one next page per reference can be requested in a round; distinct references can be batched. A page cannot introduce new references or out-of-scope traversal edges. Serial paging may hit the round bound before the aggregate page bound; 64 pages is a ceiling, not a promise that every reference shape can be exhausted in eight rounds. Such a predicate must return unknown/resource_limit or use an explicitly narrower authorized contract, not skip pages.
2. Grain MUST validate the entire `needs_data` envelope before performing reads. Wrong evaluation/snapshot identity, duplicate read IDs, unknown fields or malformed cursors are `invalid_result` and abort the evaluation. For a syntactically valid undeclared/inaccessible reference, Grain MUST deliver `status=unavailable` with safe `unauthorized`, without distinguishing unknown IDs from denied ones. Unsupported/unavailable data similarly yields an error delivery. An unavailable delivery contains **no page or records** and uses $defs.read_error: unauthorized, unsupported_version, resource_limit, request_loop or unavailable, with retryable=false. These are data insufficiency notices for the next round, not instructions to retry that failed selection. Whole-snapshot loss/expiry, revocation and driver failures abort locally instead. It counts against read-request budgets. A batch can contain successful and unavailable deliveries in request order; the provider can return final unknown with a missing-data explanation.
3. Every successful `delivery` includes the original page request plus `$defs.page`; all echoed IDs/cursor/revision and expiry MUST match the retained manifest and index. The immutable `next_cursor` is null only at the end of that reference. A terminal page proves completion only for that reference; domain coverage is determined by the manifest's completeness markers. Grain MUST enforce registry/authorization checks again immediately before delivery, including cached pages.
4. Each `(reference_id,cursor)` may be delivered once per evaluation, except an exact retransmission of the same round. A later-round repeat with a fresh read ID receives unavailable `request_loop` (no records), giving the evaluator one opportunity to conclude unknown. Repeating any failed/rejected selection again, continuing after this loop warning without a final response, or exhausting rounds/read budgets MUST abort with `request_loop` or `resource_limit`. A provider requesting new but unneeded pages cannot exceed the fixed catalog and total budgets. It cannot replenish budgets by changing IDs.
5. Unavailability during reads latches that reference/domain incomplete for acceptance even if the original manifest was complete; the manifest itself stays immutable. `unauthorized` delivery for an out-of-scope selection does not invalidate independently complete declared inputs, but MUST NOT support any negative conclusion. Required data becoming unavailable blocks met. For a legitimate retained reference lost mid-evaluation, Grain MUST abort with `unavailable` rather than replace it. Expired retention yields `reference_expired`; it MUST NOT fall through to live reads or accept a late final. Providers MUST treat absent/denied/unsupported/oversized data as unknown where necessary, not empty/false.

### 11.5 Driver states, invalidation, retry and cancellation

| State | Event and validation | Next state / allowed effect |
|---|---|---|
| preparing | Authorize scope/pins, materialize/publish bounded view, persist initial request | calling round 0; no gate result |
| calling | Exact identity/hash/schema valid `needs_data`, remaining bounds | fulfilling; checkpoint response/counters only |
| fulfilling | Read/reauthorize retained selections, persist next request and echoed continuation | calling next round; no gate result/state/action |
| calling | Valid final, including all mode-specific rules | validating; no action before fences |
| validating | Deadline, permission/evidence vector and state CAS all current | accepted at bundle commit; atomically commit eligible finals/state/subscriptions once |
| any active | Relevant evidence, contract, pin, scope, freshness, authority or permission change | aborted stale/unauthorized; reject all candidate results/state |
| calling | Transient call failure with retry budget/time | retransmit identical round; no new evaluation or snapshot |
| any active | Deadline, cancellation, lost/expired snapshot, invalid response or exhausted limits | aborted; diagnostic/synthetic error only |
| accepted/aborted | Late, duplicate or conflicting response | Ignore/audit; no replayed result/state/action (conflicting late reply follows 11.5.5) |

1. No round or retry can reset the fixed 30-second evaluation clock, which starts before materialization. Materialization and all reads/calls/retries count. A bundle shares a start/deadline; gates may evaluate in parallel but not get renewed budget when queued. No call may begin at/after deadline. Completion after deadline is timeout even if met. Retention is checked before deadline on crash recovery: an already expired store reports reference_expired; otherwise an elapsed deadline reports timeout. Neither sends another provider call.
2. Grain MUST recheck **current** evaluation and record-read authorization on each fulfillment and before every outbound call, then compare the permission epoch at final acceptance. Revocation disables delivery, cancels active calls and invalidates the whole affected bundle, including previously sent data/results/buttons. An in-flight response cannot undo revocation. Already delivered bytes cannot be recalled; providers MUST have no persistent evidence cache under this protocol. Restored permission requires a fresh evaluation/snapshot/authorization check. An isolated out-of-scope request while evaluator permission remains valid can receive the safe denial described in 11.4.
3. Any relevant DB/collector update, including a new external observation, head/child/message/operation/waiver change, or freshness expiry MUST dirty the evidence vector and invalidate the bundle across all rounds/gates. Grain SHOULD cancel promptly; it MUST validate the vector in the final transaction and again at MGS-7 closure/action fences. No durable state from an invalidated evaluation is committed. For evaluate mode, all final candidates are staged until the bundle finishes (or remaining calls become synthetic failures). One transaction rechecks the shared vector/epochs and every non-error candidate state CAS, then commits the bundle’s eligible results/state/subscriptions together; a stale vector or CAS conflict rejects the whole bundle. Error diagnostics do not update state or count as met. Migration/recovery use their own single-attachment fenced transaction. Bundle acceptance itself must complete before the fixed deadline; time exhausted at commit leaves diagnostics only. External changes not yet observed cannot be transactionally fenced; collectors' freshness and conditional action checks in MGS-4 remain mandatory. This protocol makes no claim of atomic external truth.
4. Abort/restart MUST be coalesced by task: one active bundle and one dirty marker, not one fresh evaluation per needs_data/event. On invalidation, retry the newest snapshot at most three starts per task per rolling 60 seconds. After that, hold unknown with a visible churn blocker and a durable 60-second timer; do not continually retry on each arriving event. At most ten such windows without an accepted bundle require deduplicated escalation and an explicit authorized resume. Normal timeout/unavailable/provider-error retry uses persisted exponential backoff 30 seconds to 30 minutes with jitter; five failures raise a deduplicated blocker and ten hold retries pending authorized resume (MGS-5). These counters survive restart. Rolling start-rate timestamps never reset on success, restart or resume; the three-start bound remains hard. Only the consecutive failure/churn-escalation counters reset on an accepted bundle or authorized resume. An authorized resume does not bypass the rolling rate limit. Unrelated authorized useful work is governed by MGS-5, never by transient round events.
5. A call may be retransmitted at most once per round and at most twice across the evaluation, only for timeout/lost connection/unavailable/provider-crash failures while time remains. Grain MUST persist the canonical request before sending, reuse its round/digest/payload/now/deadline, and charge retransmitted wire bytes. The provider MUST return the same canonical response for the same request; no side effect or durable provider state is permitted. If differing duplicate responses are observed while the bundle is active, abort invalid_result. If a conflicting late reply arrives after acceptance, retain the original receipt/state for audit, mark that provider/result unusable for further decisions and invalidate its pending buttons/actions; require authorized provider repair/resume. Do not undo committed state, repeat a side effect or automatically reopen a closed task; MGS-7 regression policy governs any already-completed action/closure. First round-response insertion is unique; later duplicates cannot advance twice.
6. The driver ledger MUST persist evaluation identity/pins/vector/deadline/expiry, current owner lease epoch/expiry, current round's canonical request, accepted response/hash, counters, read selections and delivered record versions. Commit each needs_data checkpoint and next-round request before sending that request. A lease CAS fences stale drivers. The driver lease is five seconds, renewed every second while active and never beyond the evaluation deadline; takeover increments the owner epoch and all read/checkpoint/final writes verify it. Heartbeats do not advance evidence revisions. Before each transmission Grain MUST durably reserve its send attempt, retry slot when applicable and request bytes plus the maximum response bytes. Settle that reservation to actual bytes after receipt; a crash/uncertain send keeps the conservative reservation and a retransmission consumes another attempt, so crashes cannot reset wire/retry budgets. On Grain crash, a new owner may resume the retained exact request or advance from a checkpoint only if store/deadline/vector/permission pins remain valid; otherwise abort and use bounded fresh restart. Provider crash is an exact round retry, not gate_state recovery. No final/state double application: unique evaluation receipt plus expected-state CAS must be checked in the same result transaction. A crash after commit returns the existing receipt.
7. Cancellation is local to the driver: authorized cancel, task pause, contract/provider removal, owner fencing or bundle invalidation marks aborted and cancels its call context. No provider cancel callback/tool is required. The provider MUST honor context cancellation where observable and the declared deadline regardless; Grain rejects late replies. Use `canceled` for explicit cancellation, `stale_snapshot` for version invalidation, `unauthorized` for revocation. Cleanup is not an accepted gate result and cannot dispatch. Do not conflate canceling an evaluation with recording task cancellation.
8. Controller errors are synthesized as `$defs.final_response` with `kind=final,status=error`, current round/request identity, unchanged candidate gate_state, empty work/actions/buttons/waits, safe error and no state CAS/result acceptance. The status is a diagnostic projection only. Provider final error follows the same no-state rule. `timeout`, `unavailable` and transient `provider_error` are retryable within policy; `stale_snapshot`, `state_conflict`, `reference_expired` require a new snapshot/evaluation rather than continuing. `unauthorized`, `unsupported_version`, `invalid_request`, `invalid_result`, `resource_limit`, `request_loop` and `canceled` are not automatic same-round retries. Retryable means eligible under these bounds, not immediate agent work.

### 11.6 Unified v2 limits

The `limits` envelope MUST contain all these values (or lower positive limits where the schema permits; retry limits may be zero). They are **per evaluation across all rounds**, unless explicitly per round/page. Lower bounds never justify truncation/met. Byte counts use canonical UTF-8 JSON bytes, not compressed bytes. The json_depth limit applies separately to args, gate_state and continuation_state, with each value’s root container at depth 1. Registry record data has the same maximum depth. Every complete wire message additionally has a hard parser nesting limit of 32 containers, so nesting cannot cause unbounded allocation before payload checks.

| Bound | Default / hard maximum |
|---|---|
| Total elapsed time, including construction/reads/retries | 30,000 ms; fixed bundle deadline |
| Rounds | 8, including initial round |
| Entire inline snapshot manifest, including inline records/catalog | 262,144 bytes; at most 100 inline records |
| One page envelope / records | 131,072 bytes / 100 records |
| Distinct pages / aggregate page-envelope bytes | 64 / 8,388,608 bytes |
| All delivered distinct records (inline + pages) | 6,500 |
| Page requests per round / total, including prefetch and denials/repeats | 8 / 64 |
| Durable state / transient continuation / canonical args | 16,384 bytes each, depth 16 |
| Provider response / entire round request | 262,144 / 2,097,152 bytes |
| All request+response bytes, including exact retransmissions | 25,165,824 bytes (24 MiB); count invalid responses to cap abuse |
| Retransmissions per round / evaluation | 1 / 2; deadline still applies |
| Published snapshot bulk retention | 60,000 ms from creation; no extension |
| Domains / references | 32 / 64; no references introduced by pages |
| Automatic stale restarts / churn hold | 3 starts per rolling 60s / 60s hold; 10 held windows then escalation |
| Automatic failed evaluations | 10, with persisted 30s–30m exponential backoff, then escalation |

Page/read/byte limits are not multiplied by round count. Exact retransmission reuses stored deliveries without another logical read and does not charge unique page/record counters again; it does charge wire bytes and retry counters. An error delivery consumes a page-request slot but no distinct page bytes/records. A repeated selection never delivers data again. The driver MUST reserve worst-case bounded request size before reading a batch, refuse batches exceeding remaining limits, and bound parser/allocation sizes at MCP ingress/egress. It MUST NOT exceed limits to send a final continuation; at exhausted limits it records a local synthetic error. Aggregate accounting includes prefetched pages, manifest replay and every provider reply; bulk materialization itself is bounded by inline+page limits.

### 11.7 Normative sequences

Successful paging (all lines use the same snapshot and pins):

```mermaid
sequenceDiagram
  participant G as Grain driver
  participant S as Grain retained snapshot store
  participant P as Pinned gate tool
  G->>S: Authorize, copy observation cut, publish immutable pages
  G->>G: Persist round 0 request and fixed deadline
  G->>P: tools/call gate_checks (round 0, inline manifest)
  P-->>G: needs_data (ref checks, cursor null, accumulator)
  G->>S: Reauthorize, read retained page 1
  S-->>G: Versioned page, next_cursor c1
  G->>G: Checkpoint response and round 1 request
  G->>P: tools/call same tool (round 1, page 1, accumulator)
  P-->>G: needs_data (same ref, cursor c1, accumulator)
  G->>S: Reauthorize, read retained page 2
  S-->>G: Versioned page, next_cursor null
  G->>P: tools/call same tool (round 2, page 2, accumulator)
  P-->>G: final met, echoed digest, evidence, candidate gate_state
  G->>G: Transaction checks deadline/vector/permissions/state CAS
  G->>G: Commit final/state/subscriptions once; closure rechecks separately
```

```mermaid
sequenceDiagram

  participant S as Grain store
  participant P as Pinned gate tool

    G->>P: Round n+1 with unavailable unauthorized, no records
```
