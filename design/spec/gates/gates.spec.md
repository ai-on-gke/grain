# Configurable built-in gate specification

**Status:** proposed normative design; documentation/schema only, not implemented. No runtime, deployment, configuration, live permission, automatic follow-up filing or task migration is authorized.

**Specifies:** [Configurable built-in gates](../../design/gates.design.md). BCP 14 keywords apply. `BG-*` are stable requirement IDs. [contracts.schema.json](contracts.schema.json) defines closed configuration, result, action, exception and decision shapes; [catalogue.md](catalogue.md) defines predicates and configuration meanings; [compatibility.md](compatibility.md) identifies current source and deliberate changes. Shape validation MUST be followed by the semantic checks here. Examples are proposed records, not currently accepted APIs.
The exact [internal evaluator API](internal-api.spec.md) and [HTTP/tool API](http-api.spec.md),
[operation index](operations.json), [API schemas](api.schema.json) and
[API audit/readiness matrix](api-readiness.md) complete the callable contracts.
These documents are normative companions, not endpoint implementation.

## BG-1: Ownership and registration {#BG-1}

Grain MUST own task admission, lifecycle, authorization, dispatch arbitration and protected mutations. A gate is a read-only compiled evaluator of an explicitly attached requirement, guard or monitor. Gate success MUST NOT grant action permission, bypass pause/budget/capacity, approve work or change standing intent. Task completion and resource action policy are independent: legacy-completion tasks can still have protected actions.

A release MUST register each `(type,version)` exactly once with its closed configuration schema/digest, supported subjects/purposes, implementation identity, bounded read needs and allowed registered UI actions. V1's exact types/configuration are in the catalogue and schema. Unknown type/version, unsupported config field or mismatched schema/implementation digest MUST hold the required binding as unknown and reject new admission. Do not omit an unsupported requirement. Schemas are local, at most 64 KiB/depth 16; no remote references, code snippets, expression language, shell commands, URLs to fetch or arbitrary API selectors. A Grain binary build identity and gate version pin semantics; modifying a predicate requires a new version or an explicitly compatible bug-fix release recorded in receipts. Older binaries MUST hold unsupported contracts rather than reinterpret them.

The exact Go-style registry/evaluator, concrete configuration/context/result/state/action types,
read helpers, cancellation/error and acceptance contracts are normative in
[internal-api.spec.md](internal-api.spec.md). Package names, storage and locking
implementation remain internal freedom; their observable guarantees do not.

`Subject` is derived by the controller, including task/attempt if relevant, canonical resource/head/snapshot, actor/delegation, effective policy/contract revisions, authority epoch, fixed evaluation time and deadline. Evaluators MUST NOT choose another acting principal/task or inherit all agent grants. Internal access MUST use the caller/controller's approved scope and redact UI/agent evidence separately. Required hidden facts remain unknown with a safe permission blocker; attachment itself grants nothing. A registered evaluator may use existing DB and forge clients, with deadlines and service credentials retained by the controller. It receives no arbitrary mutation client. In-process code is trusted Grain code reviewed/released with Grain; read-only is a code/service boundary, not an isolation claim against malicious Go code.

There is one ordinary function call per evaluation. No remote envelope, callback, driver rounds, continuation state or custom snapshot paging is required. Canonical digests use RFC 8785 JSON and SHA-256 (`sha256:` plus 64 lowercase hex digits). Schema digests cover resolved local definitions; configuration digests cover materialized defaults and resolved subject identities. The context digest covers the exact aggregate `context_set` in [api.schema.json](api.schema.json): complete controller contexts plus effective attachments/configurations, actor/read scope, source-policy revision set and registry digest, sorted as [http-api.spec.md](http-api.spec.md) specifies. It identifies a stored evaluation cut, not a hash regenerated with a new evaluation ID/time on every click; it is generated internally, not an authority claim accepted from an API caller. Persist the exact hashed content with its receipt. Retain contracts, source revisions, decision/action receipts and exception audit for the task/resource audit lifetime and at least through every applicable exception/replay horizon; payload redaction/expiry must not erase identity or resurrect old authority. V1 evaluators have **no private durable state**. Accepted results/dependencies, dirty versions, retry times and existing domain progress/wait state are controller-owned records. Future stateful gate types need a versioned storage/migration contract before admission.

## BG-2: Configuration, inheritance and editing {#BG-2}

`gate_policy` is a proposed additive repository-settings field stored/exported through the existing configuration repository path for that repository's settings. Template records have proposed `gate_defaults` validating as `$defs.template_defaults` (a typed policy plus lifecycle intent/limits, pinned and materialized together); task storage has `gate_contract`. Deployment configuration changes still belong in its state repository (`grain/config` in this deployment), not this source PR. No current field/endpoint is claimed to accept these names. The schema's `$defs.policy` is the declaration at each layer; `$defs.contract` is the materialized task record. Read/config APIs MUST use these schemas and existing authorization/version-conditional update conventions.

1. Existing templates/tasks stay legacy until explicit opt-in; no global default silently migrates them. An opted-in template MUST explicitly declare its complete gate defaults and lifecycle intent, within repository ceilings. V1 does not infer integration obligations from a report string, intent name or resource attachment. For example a report template declares delivery(report) plus explicit receipt; a code-change template declares delivery(change) and integration(pr_merged), with any no-change exception handled by an authorized disposition/contract waiver. Imported no-work/child-report exceptions use the compatibility mapping rather than this new default. Repository policy supplies required completion defaults and live resource action guards. Template defaults are pinned by template revision and materialized **once at task creation** with validated field substitution from declared typed template inputs only. Missing default values or invalid targets fail filing atomically; do not create a task with dropped gates. Changes to a template affect new tasks only. A preview MUST show all effective attachments and inherited sources. Existing task rebase to a template is a reasoned conditional contract edit, not a silent refresh.
2. Effective completion requirements are the union of materialized repo/template defaults and explicit task attachments. Stable IDs are qualified as `source_kind/source_id/attachment_id` and must fit 256 characters after qualification; display labels are not identity. Identical IDs with differing definitions are invalid; semantically duplicate requirements can share evaluation work only when all subject/config/authorization/version fences agree, preserving every source binding. At most 64 effective completion attachments/task and 64 effective guards/resource/action; overflow holds/rejects instead of truncating. Monitoring has `required=false`; completion/guard has `required=true`. An empty required completion set is rejected; an explicit `delivery` or standing contract is required.
3. Repository/resource action guards are resolved **live** across deployment/repository policy and every active task binding protecting that canonical resource. The caller's task is provenance, not the policy selection key. A resource guard binding stays active until its policy owner explicitly retires it with a reason and revision check; closing/deleting its originating task, removing a resource reference or revoking observation access MUST NOT silently retire protection. Preserve its independent resource-policy index entry. Inheritance is additive: a local `required=false`, `checks mode=none`, weaker child predicate, later source, tool alias or alternate task cannot replace inherited requirements. Resolve the whole set and source revisions into an effective digest; missing coverage/index is unknown. A separately authorized, versioned explicit `unguarded_actions` record is required for an empty guard set. It is not a task-local escape hatch.
4. Only policy administrators for the corresponding repository/resource may edit inherited guards or declare unguarded actions. Template editors may configure defaults within repository ceilings; task editors may add obligations within allowed scopes. Removing, weakening, retargeting or changing a required predicate/version, adding/removing required children, or changing lifecycle intent requires a person with contract/policy authority, reason and expected contract/policy revision, unless that **exact** transformation was separately preauthorized. Agents may propose edits and perform ordinary remediation, never relax their own requirements or approve themselves. Task metadata edit rights do not imply this authority. New grants, waived requirements and action overrides are separate operations.
5. All accepted edits MUST atomically store before/after/provenance/actor/reason, advance revision and invalidate affected results, waits, buttons, waivers and unstarted intents. Guard changes invalidate resource decisions even when no task contract changes. Concurrent edits are CAS conflicts, not last-write-wins. Detect blocking cycles transactionally over explicit dispatch dependencies, required-child waits and action prerequisites; `integration` for the same merge/submit MUST NOT guard that action, directly or through a child. Advisory relations may cycle; unknown external graphs cannot be assumed safe.
6. Subject selectors are closed: acting `task`, a canonical exact `change`, or one `repository/ref`. Admission checks type/subject compatibility and all scopes. A task selector naming `self` is resolved at materialization; another task needs explicit relationship/read authority. Change selector `task_changes` is permitted only for the acting task's full versioned change-link set, never an arbitrary search. Checks/review/approval action guards resolve exactly one executing resource/head; taskless operations use resource context, not a forged task. For action policy only, change ID `*` means every change of that authority/repository/kind; it is allowed only from authorized deployment/repository/resource policy. It is not a query language, not accepted for concrete action requests, and cannot be introduced by a task/template to expand scope. Exact IDs match only that resource; `task_changes` resolves only the owning task's linked changes. Admission intersects every selector with source authority before live resource lookup. No resource attachment or `child-of`/spawned relation creates a completion requirement automatically.

## BG-3: Predicates, inputs and result contract {#BG-3}

Catalogue predicates and defaults are normative; legacy profiles require controller-recorded import provenance and are not selectable by new agent configuration. Registry semantic validation MUST enforce type/purpose/subject combinations and profile restrictions beyond JSON shape. Each result validates as `$defs.result`: evaluation/binding IDs and gate version, context digest, five-valued status, concise summary, optional human/agent text, versioned evidence, complete dependency list, typed blockers/work/waits/actions, observed/expiry times and nullable error. Grain derives identity/context fields; results from stale context cannot become current by copying IDs.

- `met`: sufficient authoritative, current and complete evidence proves this exact predicate.
- `unmet`: trustworthy evidence proves a required condition unsatisfied; include repair or explicit unavailable-remediation reason.
- `pending`: an identified existing process/event may satisfy the condition; name wait driver, resource, deadline and escalation.
- `unknown`: insufficient, inaccessible, stale, incomplete or unsupported evidence; never treated as false or success.
- `error`: evaluation failed (timeout, read/validation error or panic); no accepted predicate result, no completion/action permission.

`error` requires an error record; other statuses require error=null. An error/unknown may still explain remediation but MUST NOT issue effects. All actions are descriptors only. `work` uses a registered intent (`repair_checks`, `resolve_conflict`, `produce_report`, `update_change`, `review_change`, `repair_health`, `answer`, `request_access`, `reconcile_operation`) with canonical target, reason and expected context. Deduplicate by intent/target/head/predicate; a new summary/result ID is not new work. The controller checks current authorization and whether a useful run already exists before dispatch. Gate-private result text is not approval, immutable evidence or proof of external success.

V1 registered UI action names and schemas are finite: `reevaluate`, `retry_checks`, `request_review`, `answer`, `request_access`, `acknowledge`, `submit`, `accept_findings`, `waive_completion`, `override_action`, `reconcile_operation`. Each is mapped to an existing domain operation or a specified new gate-contract operation, not arbitrary tool dispatch. Names without a configured/authorized domain handler are not rendered executable. Server-side click handling resolves current binding/resource/head, checks expected contract/policy/context/versions and actor permissions, and applies domain idempotency. A displayed button conveys no authority. Agent view receives the equivalent named existing tool/action or an explicit “person required”, never a raw secret or privileged command.

Limits: one evaluation deadline 10 seconds (30-second whole task/guard aggregation); up to 8192 records/8 MiB examined through bounded internal helper queries, 128 dependencies/result, 128 evidence references, 32 work intents, 64 waits, 16 actions; result at most 128 KiB, text at most 8 KiB each. Whole contract at most 256 KiB. Exceeding bounds returns unknown `incomplete` or error `resource_limit`; never truncate into met. Capture only relevant fields/sets. Internal database pagination is allowed with stable collection versions; it is not a provider paging protocol.

## BG-4: Evidence, collections and decisions {#BG-4}

Every internal read helper MUST capture dependencies with its value: canonical key/subject/head, monotonic local version or source equality token plus local observation sequence, collection generation, query scope/digest, complete flag, source collection time, freshness expiry, authorization/policy revision and dirty/covered generation. The controller automatically captures **all** reads, including empty sets, absent records, policy inputs and inline facts; a gate cannot narrow the set by omitting citations. This is focused instrumentation in existing helpers, not a universal read-operation registry.

1. Read a bounded DB projection and its versions in one short read transaction. For forge reads, perform network collection outside transactions and commit/validate the observation and fences before using it. First access latches collection membership/order/generation; later pages/reads must match or restart evaluation. ABA, additions/removals, dismissed approvals, changed applicability and permission changes increment the appropriate local version. Dirty source hints invalidate evidence until recollection covers them.
2. Empty/negative claims require a complete scoped collection: no required checks, no findings, no incoming messages, no failed required children and no open health alerts each need a trusted set-generation/coverage fence. A 500-row scan or empty error response is not proof of absence. If a source provides no stable pagination generation, capture a bounded relevant immutable set in its adapter with explicit freshness/coverage limitations or return unknown. No universal full task snapshot is required. Mixed live reads from different generations cannot silently replace prior values.
3. Final decision validation MUST compare the union of core context and all required gate dependencies in one short DB write transaction: contract/authority epoch, evaluator version, effective policy/coverage, exact resource/head/base/snapshot, authorization, records/set versions, dirty/covered fences and expiry. A new relevant fact invalidates the decision even if its visible status is unchanged. Nonrequired monitors cannot authorize success. Missing/incomplete required data stays unknown. A failure may be displayed early while others run, but accepted readiness requires all dependencies validated together.
4. Immediately before protected dispatch or successful close, revalidate the stored decision receipt plus current permission/policy/resource fences. Closure serializes required-child outcome/link changes and incoming/processed message watermarks, settles/fences live writers and uncertain operations, and uniquely commits decision/outcome/state/waits. A concurrent child edit, message or head change either invalidates closure before commit or is a historical later event handled by explicit regression/reopen policy. Gate evaluation never marks messages processed: only recorded delivery plus run disposition/response or an authorized explicit no-agent disposition does so. Acknowledgment is not such a substitute for an unprocessed request.
5. Real external collection time controls freshness, not cache-return time. Default required source age budget is 300 seconds, bounded 0..3600 (zero means recollect in this persisted decision cycle, with validity bounded by source expiry and a <=10-second cycle deadline; it never refreshes cached collection time); effective validity is the minimum of source validity and policy budget. Checks/reviews/approvals additionally bind exact head/subject and applicable policy. Irreversible integration receipts may remain historical evidence, but current source identity, authorization and tracked set must still validate. Unavailable timestamps or missing source coverage cannot satisfy freshness-sensitive predicates.
6. This yields a consistent **Grain-recorded** decision cut, not global atomicity across independent services. GitHub head-conditional merge cannot freeze remote review dismissal or all base/policy changes. Enforced admission needs forge rules or proven exclusion protecting each promised condition at execution; otherwise report `boundary_unavailable`, do not claim prevention. Later-discovered changes invalidate pending work, but do not silently undo completed integration or automatically reopen tasks. Record observed cutoff/versions and apply explicit notify/reopen policy.

## BG-5: Central lifecycle, activity and useful work {#BG-5}

Each task MUST have exactly one completion authority, `legacy` or `builtins`, at a monotonic epoch. Legacy observations remain compatibility facts, not a second decision source. For migrated tasks all finish/goal/PR/CL/review/UI/recovery paths submit facts and requested dispositions to one central lifecycle function. Only it can accept completion/rest/failure/cancel and project task outcome. A run ending is not task completion. Preserve unresolved questions/access requests/suspension and actual pushed artifact precedence from `processResultFrom`.

A finite task may succeed only when all required completion gates are met or validly waived, no unprocessed relevant message/question remains, no live writer or uncertain operation can change the outcome, and closure fences pass. Required child **success** remains unmet on failure/cancel/closed-unmerged; legacy closure requirements stay visibly different. Explicit failure/cancellation is terminal without pretending requirements met, with actor/reason and outstanding-operation reconciliation. Person close chooses successful close (requires met/waived) or cancellation; it cannot manufacture success. Completed requests in standing `person_closes` sessions rest and remain open until an authorized close/cancel, preserving rollover/session lineage. `on_met=rest`, on-limit hold/notify, progress/run budgets and ordinary pause policies remain controller policies, not permanently false gates.

Expose `$defs.decision` with independent terminal outcome, activity, dispatch hold reasons and gate status. Precedence is: historical terminal outcome; live authorized run (`running`, with outstanding needs also visible); unresolved person question (`needs_answer`); denied/missing authority (`needs_permission`); required receipt (`needs_acknowledgment`); eligible useful work (`ready`, with admission/capacity/pause/budget holds separately); otherwise `waiting` with driver/deadline. All simultaneous blockers stay visible even when one activity is primary. Approval/admission, capacity, budget, pause and standing ownership are not gates and never become met because the task is waiting. Legacy UI readers must not project unknown/held into ready/completed.

Only explicit actionable work with current authority can create an agent run. Gate A waiting for CI/review/child does not block an independent report/repair for gate B. Whole-task holds name their scope, reason and release condition. Operations conflicting on the same resource/head serialize even across tasks; a waiting gate cannot spin a repair loop. Returning pending/unknown, changing text, reevaluation and heartbeat are not progress. Use existing run progress/budget accounting with recorded product/evidence movement, and retain TaskGoal no-progress defaults on import.

## BG-6: Wakes, timeouts and recovery {#BG-6}

Existing event producers own collection and evidence updates: `SyncPullRequests`, review/security/path reconciliation, CI completion/base/nightly collectors, message delivery, child/contract edits, and existing health/notification scans. They mark affected task/resource gate sets dirty **after commit**. Evaluators name registered interests (`task_message`, `child_outcome`, `change`, `checks`, `review`, `approval`, `health`, `timer`) plus canonical key and persisted deadline, not arbitrary callbacks or subscriptions. The controller owns the interest index and timer scan. If journal cursors exist, register/replay after the captured cursor; otherwise transactionally register an interest with the observed version then reread, ensuring no check-to-sleep gap.

One active aggregation plus one dirty marker per task/resource; new events coalesce. Event/timer wake reevaluates first, then decides if useful work exists; it does not automatically dispatch. Run the level reconciliation scan at least every 60 seconds, including after restart, so missed notifications recover from current DB/forge truth. Timers persist per owner/key; duplicate timers cannot create duplicate work. CI/review external wait deadline defaults to two hours (60 seconds..seven days); after deadline create one visible escalation, retain unmet/pending/unknown, never pass. Person waits remain durable with daily deduplicated reminders unless policy narrows them; reminders are not agents.

Read/timeout failures back off persistently from 30 seconds to 30 minutes with jitter. Five consecutive failures expose a deduplicated blocker; ten suspend automatic retries until authorized resume, with existing waits preserved. At most three stale aggregation restarts per subject per rolling 60 seconds; then wait for one persisted 60-second retry, without spinning on each event. Accepted fresh aggregation resets failure streak, not the rolling rate limit. Revocation invalidates results and removes unauthorized deliveries/interests immediately; grant restoration schedules fresh reads. A restart loads dirty/deadline/retry state, rejects expired results and rechecks current policy/authority; it does not reuse green badges as permits. No provider session or opaque state recovery is needed.

Result/wait/decision records use unique evaluation ID and expected subject/contract versions; retries cannot double-apply outcomes. Internal action intents survive independently: a crash after effect commit or a timeout cannot imply rollback. Reconcile a possibly successful effect before a retry and retain immutable success receipts even if gate evaluation later fails. Source event detection, subscriptions and occurrence dedup remain the trigger controller's responsibilities; gate reevaluation, waits, result churn and broker telemetry are not source occurrences.

## BG-7: Protected actions, registered buttons and exceptions {#BG-7}

Task #50's [AGB-1–8](action-bindings.spec.md) concepts remain mandatory, using in-process results. First enforced action adapters are existing PR merge and CL submit domain services (`change.merge`, `change.submit` are canonical design IDs, not deployed endpoints). Other effects such as deploy/publish/config apply/QA promotion retain existing policy and require their own admitted typed domain adapter before this design claims gate enforcement. Do not add a universal arbitrary action dispatcher.

Every equivalent admitted path MUST converge in its domain service: queue/automation, taskless calls, UI/API/CLI/controller MCP, capability tools, raw protocol proxies and delayed forge queue execution. Resolve current policy by canonical resource/effect, not task/tool name; union requirements from all protecting tasks. Missing guard store/coverage, unsupported evaluator, read denial or uncertain effects block. `integration` cannot guard the action producing integration. Caller execution permission, human approval evidence, guard success and exception authority are four separate checks.

A protected action request validates as `$defs.action_request`: typed canonical action/target, expected head/resource version, contract revision, authority epoch, policy/context/evidence digest expectations, request/idempotency identity and reason where required. The HTTP mutation and action expectation fields MUST agree; both are checked against current authoritative records before dispatch. Derive actor/delegation from authentication, never the body. Before execution: authorize; acquire shared canonical resource/effect lock and fenced lease; reread facts and evaluate required guards; validate dependencies and current policy/permissions; durably write intent; recheck dispatch conditions; issue expected-head merge or exact-reviewed-snapshot CL operation; persist/reconcile immutable receipt. No DB transaction spans external calls. Same idempotency identity returns existing authorized receipt; unequal canonical input with that identity is conflict. A timeout with possible side effect is `outcome_unknown`, held for reconciliation, not an automatic second merge/submit. A committed receipt survives a later evaluator/response failure. Queue enrollment itself is not proof that final execution was guarded.

Enforced admission MUST inventory and close direct protected-effect credentials/routes for that resource/cohort, including Git base pushes, raw PAT/SSH/App tokens, minted/refreshed credentials, CI/release identities, auto-submit and alternative hosts. Retain legitimate feature-branch writes only where proxy/rules prevent protected base effects. GitHub contents-write/no-admin/repository scope does not prove inability to merge; the current merge identity can fall back to push identity. If a bypass remains, hold/refuse enforced execution or declare observation-only with **no Grain protected execution** for that cohort. Independent external people/apps are outside Grain's guarantee unless separately constrained; authenticated external integration can satisfy integration evidence but is attributed external, not guard-approved. The initial legacy-authoritative diagnostic rollout is not an admitted built-in
protected-execution cohort; its existing legacy actions remain unchanged and gain
no new enforcement claim. This design changes no live rights.

Completion waivers and action overrides validate as `$defs.exception`, have immutable actor/reason/time/expiry/revocation audit, exact qualified binding IDs, predicate/config version, subject/head, evidence/dependency and policy/contract digests. They require distinct current authority and are checked on every use. Completion waiver never grants merge/submit permission or changes the recorded gate result; action override never waives completion. V1 action exceptions are one-operation, at most one hour, named eligible check/review guards only; human approval, authorization, conflicts, unknown identity, incomplete policy and execution-boundary failures are not overridable. Completion waivers expire within seven days or earlier context/source scope expiry and cannot suppress unprocessed messages/live effects. Head/policy/config/contract/required-child changes invalidate affected exceptions. An override must name all unsatisfied eligible guards; default legacy force import names CI only, not approval or future guards. Preserve explicitly imported base-repair eligibility rules, never the repair's own CI bypass. `accept_findings` is a distinct recorded disposition for exactly one review/head/reason; thread resolution or Submit is not acceptance, and another review's findings remain.

## BG-8: Views, implementation and migration {#BG-8}

The initial implementation/display increment MAY cover only two selected built-in
gates in observation-only mode with legacy logic authoritative. The exact
[read-only observation projection](http-api.spec.md#initial-observation-only-apidisplay-subset)
and observation_view schema are normative: diagnostic results have no lifecycle,
action, permission or dispatch authority and cannot be promoted into decisions.
The full future mutation/enforcement API remains authorized specification scope,
not a requirement that the initial increment implement every endpoint.
A day or two of observation is for operator review only; there MUST NOT be an
automatic elapsed-time cutover. Separate explicit authority handoff and resource
admission/qualification are required before effects. Existing legacy actions stay
under existing legacy policy during that initial unconverted increment.



Proposed task read view `gates` contains effective attachments/provenance, accepted result/evidence freshness, unmet reason, remediation/tool, person requirement, waits, valid waiver markers, and activity/terminal/dispatch holds. Repository/resource guard view additionally lists all inherited source revisions and protected operation readiness/authorization separately. Use existing task/config APIs with additive versioned projections; any new gate-policy/exception edit action must have explicit RBAC and schema registration before deployment. Do not claim the current MCP/CLI has such tools. New UI is Angular; classic/API compatibility remains permission-filtered. No denied view may confirm private child/resource existence or leak raw credentials. `gate_state`, remote provider installation and protocol negotiation are absent from v1.

Migration: readers and storage first; shadow built-ins compare with legacy decisions without effects. Materialize exact imported predicates and controller lifecycle policies with provenance; show intentional differences from [compatibility.md](compatibility.md). Settle/fence runs, outstanding effects and old workers, then atomically switch one task's authority/epoch and disable **every** legacy completion/rest/requeue writer for it, including PR/CL direct closure, review cleanup, goal `MetAt` shortcut, UI close/reopen and recovery. Collectors may continue emitting facts/proposals. Go and SQLite/Postgres `task_state` must select identical authority and precedence. Old binaries hold unsupported tasks/resources rather than fall back. Resource guard migration can proceed independently of lifecycle migration but only after all equivalent effect routes and credentials are fenced.

Rollback retains contracts, provenance, receipts, exceptions and watches/timers. Fence new workers and use one conditional reverse authority handoff only where the imported contract is representable under legacy semantics. Success-required children or multiple independent obligations may not be; hold for a compatible binary instead of silently dropping them. Rolling back lifecycle MUST NOT remove resource action guards. Restore revalidates policy/permissions and reconciles survived external effects before any replay. Existing concrete goal APIs/fields and autonomous goal-mode tools retain names/semantics until explicit import; no rename or Task 1 dependency.

Implementation breakdown: (1) registry/config materialization and versioned reads/shadow comparison; (2) central lifecycle and writer handoff, complete-set/message/child transaction fences, durable interest/timer recovery; (3) converge merge/submit guards, credential admission, exact-version effects and receipt recovery; (4) Angular/API/agent projections and qualified migrations. These are sequencing, not auto-filed tasks. Resource TDS providers and trigger TTS collectors can later feed ordinary authorized observations/events; they are neither required nor substituted for current clients.

Readiness review: the [API audit and matrix](api-readiness.md) records the closed operation/evidence schemas, authority/concurrency decisions and remaining implementation blockers. Schemas and examples specify initial catalogue/config/result/action shapes, precedence and no-private-state choice; they do not establish runtime or enforcement readiness. Runtime blockers are central writer/store changes, exact-head review/approval evidence and set generations, policy coverage/index, all-route guard admission, per-deployment credential proof, CL reviewed-snapshot adapter/exclusion, SQLite/Postgres parity and recovery qualification. QA custom stage enforcement and non-merge/submit protected effects need separate adapter admission; legacy tasks retain behavior meanwhile. No product decision about broker transport remains open. Recommended rollout is shadow first, finite imported tasks second, then small enforced resource cohorts after bypass probes. Remaining deployment choices are which cohort and retention/operational thresholds to enable within the stated bounds; choose conservative defaults above and require a separately approved configuration change. They do not block this documentation review and do not authorize implementation.
