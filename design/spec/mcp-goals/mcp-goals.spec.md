# MCP goal evaluation and lifecycle specification

**Status:** proposed, normative for the protocol described here; not implemented. Documentation approval does not migrate any task or authorize implementation/deployment/follow-up filing.

**Specifies:** [Extensible MCP goals](../../design/mcp-goals.design.md).

The words MUST, MUST NOT, SHOULD, SHOULD NOT and MAY have their BCP 14 meanings. Requirement IDs are stable. [wire.schema.json](wire.schema.json) is a JSON Schema 2020-12 document containing concrete request, response, attachment, action-event, waiver and reference-page schemas in `$defs`. Validate each message against its named definition, then apply the cross-field invariants below. These are documentation assets, not a new runtime validator or deployed endpoint.

## 1. Authority and attachment {#MGS-1}

1. Grain MUST own admission, lifecycle transitions, dispatch, operation arbitration, authorization and closure. An evaluator MUST NOT write these directly. Task completion authority MUST be exactly one of legacy or goals at a recorded authority epoch. Observation-only results MUST NOT affect legacy task decisions.
2. An extension MUST expose an MCP `tools/list` entry named `goal_<method>`, where method matches `^[a-z0-9][a-z0-9_-]{0,62}$`. Its `inputSchema` MUST describe the request envelope, with provider-specific capability-style `args`. Discovery MUST NOT attach a goal or authorize its reads/actions. `mint_*`, `release_*` and `configure` retain their capability meanings; `goal_*` MUST NOT be treated as a mint method.
3. An admitted contract MUST enumerate stable goal IDs, whether each is required, canonical provider identity and immutable release/artifact pin, tool name, goal version, argument schema digest, state version, validated canonical arguments and their digest. A schema digest MUST cover resolved local definitions; remote schema fetches MUST NOT occur during evaluation. Resolve capability-style defaults before hashing. Provider args MUST use the supported capability argument-schema subset; secret values and credentials MUST NOT be arguments.
4. Grain MUST separately authorize (a) contract attachment/editing, (b) evaluator access to the declared bounded read scope, (c) user/agent evidence reads and (d) every action. A required obligation with no read permission MUST remain required and unknown with a permission blocker. It MUST NOT implicitly mint access or waive itself.
5. Contract, policy and child-link edits MUST increment contract revision and invalidate affected results, waits, buttons and waivers. Removing/relaxing a requirement, changing success into closure, or replacing a provider MUST require an authorized person's reasoned approval unless that exact transformation was preauthorized in the contract. An agent MAY propose edits; it MUST NOT drop its own obligations to finish. Record before/after, actor, reason and authority epoch. Adding requirements MUST also respect caller authority and template constraints.
6. MCP annotations are hints, not authorization. Grain MUST enforce read-only execution independently of any `readOnlyHint`.

## 2. Requests, snapshots and state {#MGS-2}

1. `tools/call` arguments MUST validate against `$defs.request`. `mode` is `evaluate`, `migrate` or `recover`. The envelope includes protocol version, evaluation and attachment identity, deadline, exact pins/arguments, expected state revision, versioned state, contract revision, authority epoch, lifecycle policy revision and a versioned snapshot manifest. Grain MUST generate IDs and hashes; providers MUST NOT choose the authority context.
2. Snapshot `id` identifies immutable relevant evidence at `evidence_revision` and `cursor`. It MUST include contract, current head/change identities, authoritative observations, processed and incoming message watermarks, relevant children with relationship and outcomes, operation/action/waiver events, permissions metadata and available evidence references. Only Grain may advance the processed-message watermark, based on recorded delivery plus run disposition/response or an explicit authorized no-agent disposition; an evaluator summary/state MUST NOT mark a message processed. Full relevant state MUST be accessible within declared scope via bounded inline records and paginated snapshot-bound references. Necessary inaccessible facts MUST be marked unavailable with a reason, not silently omitted or read as false.
3. The initial inline payload MUST be at most 256 KiB UTF-8 JSON. References/pages MUST be bound to snapshot, audience/provider, task and expiry; access MUST recheck authorization and MUST NOT expand scope. Each page is at most 128 KiB and 100 records. A provider invocation may read at most 64 pages/8 MiB total within its deadline. Larger evidence requires a narrower authorized contract or an unknown result identifying the limit; arbitrary truncation MUST NOT produce met. A snapshot manifest MUST name included domains and all omitted/unavailable domains. Snapshots MUST NOT contain raw secret-bearing or unbounded transcript dumps. Logs/artifacts MUST use authorized redacted references and bounded excerpts.
4. Pages MUST validate against `$defs.page`, carry immutable record versions and remain at the original snapshot revision. Grain MUST supply a registered read-only snapshot access handle with the request or its transport context; reads take `$defs.page_request` and return `$defs.page`. The handle MUST authorize only that evaluation/snapshot and MUST NOT be a general namespace credential. A continuation token is opaque and read-only. Grain MUST fail expired or unauthorized references. A reference MUST NOT be an arbitrary provider-supplied fetch URL. Record `kind` selects a Grain registry schema (for example `check`, `review`, `child`, `message`, `permission`, `action_event`, `waiver`); its `data` MUST validate against that schema before provider delivery. Unknown record kinds are unavailable unless the pinned goal declares support.
5. All goal results used in a lifecycle/action decision MUST refer to one snapshot ID, evidence revision and contract revision. Relevant changes during evaluation MUST make the result bundle stale even if UI status did not change. Grain MUST reject stale responses before state persistence or actions. It MAY reuse unaffected cached evaluation work only by explicitly revalidating it into a new consistent bundle; it MUST NOT concatenate results from differing snapshots as if current.
6. `goal_state` MUST be opaque JSON interpreted only by the pinned provider, bounded to 16 KiB encoded UTF-8, depth 16, with no credentials. Grain MUST validate its envelope and compare-and-swap expected revision for every accepted update. State revision MUST increase on update, including null reset, and be scoped to attachment/provider/goal/state version. An accepted evaluation ID MUST be unique; retries MUST NOT apply state twice. Result, updated state, subscriptions and evaluation cursor MUST commit atomically, or none do. Provider state MUST NOT substitute for authoritative CI/review/approval evidence.
7. Version changes MUST use an explicit contract migration record with old/new pins and state version. `mode=migrate` supplies `previous_pin`, old state and current authoritative snapshot to the new pinned evaluator; it MUST return transformed state only, with status unknown, no actions/work/waits/buttons. Grain validates and CASes the migration, switches contract pins and schedules fresh evaluation atomically, invalidating prior results. A failed migration MUST preserve the old state/pin. No provider replacement may silently interpret old state.
8. `mode=recover` is allowed only when the pinned provider declares evidence replay safe. It receives null state and a reasoned recovery record; it MUST rebuild from authoritative evidence, return unknown and no work/actions/waits/buttons, and MUST NOT invent approvals. Otherwise recovery MUST hold for an authorized migration/repair. Preserve old state for audit. After recovery, evaluate afresh. Provider unavailability MUST NOT trigger automatic reset, downgrade or legacy fallback.
9. V1 defaults: evaluation timeout 30 seconds (including page reads), response at most 256 KiB, at most 32 work items, 32 action requests, 64 waits, 16 buttons and 128 evidence references. Grain MAY lower bounds by recorded deployment policy and MUST advertise effective limits in the request; it MUST reject oversized/deep JSON before allocating unbounded memory. Deadline expiry is a timeout, never met.

## 3. Result semantics and compatibility {#MGS-3}

1. Responses MUST validate against `$defs.response` and echo protocol, evaluation, goal, snapshot, contract, authority epoch, lifecycle policy, evidence and state revisions exactly. MCP `structuredContent` carries this object; any MCP text rendering is non-authoritative. V1 uses statuses `met`, `unmet`, `pending`, `error`, `unknown`:

| Status | Meaning | Required handling |
|---|---|---|
| met | The declared predicate holds on the snapshot | Grain validates required evidence and scope; eligible for aggregation, not immediate self-close. |
| unmet | Predicate is known false | Show blockers; dispatch only explicit useful authorized work. |
| pending | An identified external operation/event is still unresolved | At least one viable wait or in-flight operation reference is required. Other independent work can run. |
| error | Evaluation failed | Error code and retry classification required; not unmet or met. |
| unknown | Evidence, permission, compatibility or interpretation is insufficient | Explain missing information and recovery/wait path; MUST NOT default to met. |

2. Every response MUST carry a one-line summary (maximum 240 characters, no newline), evidence references, `goal_state` candidate, blockers, work, action requests, waits, buttons and optional separate `human_text` and `agent_text`. Evidence MUST reference records from the supplied authorized snapshot with immutable versions. Met MUST carry at least one reference, including a Grain-recorded no-work/report/person-action record where appropriate. Grain MUST verify evidence kind, subject, version, freshness and predicate-specific prerequisites using the registered contract; a fabricated ID or scope mismatch invalidates the whole response.
3. A blocker identifies kind (`answer`, `permission`, `acknowledgment`, `external`, `work`, `provider`, `policy`), a stable key, explanatory summary and optional related evidence. Text is untrusted presentation, never instructions with system authority. Grain MUST escape/sanitize display, redact known secrets in logs, avoid interpreting embedded links as action targets, and keep agent text labeled as provider output.
4. Work MUST identify stable key, target, summary, dependencies, evidence preconditions, and required registered tools/permissions. A provider MUST NOT make executable code or arbitrary URLs a structured operation. Agent work can include an ordinary task instruction such as investigate a cited failing test; it cannot confer a new grant. `action_requests` MUST name registered actions and validated JSON inputs, stable key, reason when required and expected evidence. Grain MUST reject unknown operation IDs rather than dynamically registering them.
5. For `met`, work/action requests and blockers MUST be empty; waits MAY request monitoring only under an explicit regression policy. For `error`, work/actions/buttons MUST be empty. A `pending` response with no viable wait/in-flight reference is `invalid_result`. Migration/recovery restrictions in MGS-2 override ordinary result semantics. A response MUST NOT request work whose dependency is its own unsatisfied output or otherwise form an action dependency cycle.
6. Wire v1 is exact: unknown envelope fields or unknown enum values MUST fail validation; extension payloads belong in registered `args`, record `data` or opaque `goal_state`, not ad hoc envelope keys. Compatible new optional protocol fields require negotiated minor support; required/semantic changes require a new protocol version. Grain MUST refuse unsupported pins/schema/protocol at attachment/admission or hold an already-admitted task unknown after an upgrade. No coercion of unknown status to false/success is permitted.
7. MCP transport failure, `isError:true`, malformed JSON, schema mismatch and deadline are protocol failures, not task verdicts. Grain MUST normalize failures to a synthetic error result without committing candidate state. Error codes are `timeout`, `unavailable`, `unauthorized`, `unsupported_version`, `invalid_request`, `invalid_result`, `state_conflict`, `stale_snapshot`, `reference_expired`, `resource_limit`, `provider_error`. Stale/conflict causes coalesced reevaluation, not agent dispatch. Invalid/persistent compatibility/authorization failures need operator recovery; transient timeout/unavailable/provider errors back off. Provider error text MUST NOT expose credentials.
8. Grain MUST retain accepted results, rejected-result diagnostic hashes/reasons, and closure/action receipts sufficient to explain decisions. Unknown/error in a required goal blocks success unless a separate valid waiver applies; advisory errors do not block success.

## 4. Actions, buttons and waivers {#MGS-4}

1. Initial evaluators MUST be pure bounded read-only functions of arguments, snapshot, state and declared clock/deadline. They MUST NOT send messages, mutate providers, submit reviews, merge, deploy or call write tools during evaluation. Execution credentials MUST exclude those powers. Read-only calls remain subject to time/data limits.
2. Grain MUST execute requested actions through the same registered authorized operations/tools available to agents. An agent MUST have required tools/permissions or be able to request them through the normal permission flow. Future optimized execution MUST reuse the same path, with no privileged alternate implementation and no requirement that optimization be enabled to make progress.
3. `$defs.button` contains label, registered `action_id`, `input_schema`, fixed/default inputs, evidence preconditions and confirmation requirements. The input schema MUST be a constrained subset of the registry's schema; it MUST NOT broaden it. Registry policy is the minimum confirmation and required reason. No executable code, callback URL or provider-defined permission check is allowed. Button availability is a server-derived convenience, not authority.
4. At action request or click, Grain MUST check current actor role/delegation, grants, human-only restrictions, current contract and evidence versions, live preconditions, input schema and required confirmation/reason. For external mutations, Grain MUST pass the expected head/resource version to a conditional operation where supported; if the source cannot enforce that condition, Grain MUST serialize its own writers, re-read immediately before execution and reconcile uncertain results before accepting outcome evidence. Revoked authority or stale evidence MUST refuse with a reason and refresh, not perform the action. Acknowledgment MUST record receipt only; Submit/approval MUST use their own registered actions. A note containing “approved” MUST NOT produce an approval event.
5. The operation ledger MUST durably record an immutable `action_event` with actor, action ID, inputs, reason when required, goal/contract/evidence scope, request ID and idempotency key before starting a side effect. Event phases are requested, started, succeeded, failed, unknown; append events rather than editing history. Use an outbox/intent transaction and operation-specific idempotency/reconciliation for the external boundary. A crash after an external success MUST reconcile its authoritative receipt before retrying; it MUST NOT blindly repeat. Goals MAY consume these events but a requested/started event is not evidence of successful side effect.
6. A waiver MUST be a Grain-owned `$defs.waiver` record with authorized actor, nonempty, non-whitespace reason, goal/provider/version/argument/contract/evidence scope, issue time, optional expiry and explicit invalidation keys. Grain MUST enforce invalidation on head, goal/schema/args, scoped evidence, policy or authority changes and revocation; defaults MUST invalidate on any scoped change. A provider MUST NOT create a waiver by returning state or prose. UI MUST display waived distinctly from met, with reason and actor. Waiver permission MUST be explicit and person-only by default; agents can request it, not grant it.
7. A completion waiver MUST NOT authorize a protected action or stand in for approval. Existing merge gate overrides retain `merge:force`, exact-head scope, reason, confirmation and their action audit; Submit retains human approver policy. Merge readiness authorizes the merge operation only while all required action prerequisites hold. Observed merge/CL submission satisfies the integration outcome goal.

## 5. Aggregation, arbitration and progress {#MGS-5}

1. Required goals are an explicit conjunction; advisory goals do not block completion. Each required goal MUST be met or covered by a currently valid waiver. Empty goal sets MUST require an explicit admitted no-obligations contract, never result from discovery failure. Grain MUST decide lifecycle from the consistent bundle, not from a provider's requested task status.
2. Grain MUST first validate results and deduplicate work/actions across goals by registered operation/tool, target, canonical inputs and precondition scope, preserving all requesting goal IDs. Stable provider keys are hints; Grain computes identity. Conflicting requests MUST be serialized or surfaced for resolution, not executed in provider arrival order. Dependency order, task priority and deterministic stable-key ordering resolve eligible nonconflicting work; dependency cycles are errors.
3. There MUST be at most one active task agent run, enforced by a durable lease/unique active-run constraint with fencing tokens. Concurrent external operations are permitted only under registered resource locks and compatibility rules (for example independent CI and review reads). Two mutations of the same branch/head, merge and branch edit, or incompatible contract edits MUST serialize. Shared-resource operations across tasks MUST use the same locks. An evaluator pass is not a task agent run and MUST NOT bypass operation locks.
4. An event wait on any goal MUST NOT suppress independent actionable authorized work on another goal. Dispatch MUST require a new user request, actionable work or a justified continuation under lifecycle policy, available permissions, settled conflicting operations, admission and capacity. An unmet/error/pending status alone is not work. Missing permission blocks its dependent work, not unrelated work; global pause/budget policy may still hold the task.
5. Grain MUST persist progress as changes in authoritative evidence, completed operations, processed messages and settled child outcomes. Provider progress tokens, summaries and opaque-state churn MUST NOT alone reset no-progress/error counters or schedule another run. After two identical no-progress attempts on the same work/precondition identity, default policy MUST hold that work and escalate with evidence; changing this threshold requires recorded lifecycle policy. Provider failures MUST use a separate counter and MUST NOT consume an agent task-failure streak merely because a provider is down.
6. Default transient evaluator retry is exponential backoff from 30 seconds capped at 30 minutes with bounded jitter, persisted across restart; five consecutive failures raise a deduplicated operator blocker. New relevant evidence MAY cause a bounded immediate retry but MUST NOT defeat provider-wide circuit/rate limits. Repeated identical errors MUST NOT emit unbounded comments/events or dispatch agents. Missing viable wake, exhausted polling, and unmet-without-remedy MUST name a driver and escalation. Independent work MAY continue.

## 6. Durable wakes and evaluation triggers {#MGS-6}

1. Grain MUST dirty evaluation on relevant CI/check/review/PR/CL events, head/base observations required by the predicate, child outcomes, user messages/actions, permission/role changes, contract/provider/schema changes and timer deadlines. Displayed state transitions alone are insufficient. Provider-authored summary/state/result storage MUST NOT be evidence-change triggers for that same evaluation loop. Explicit cross-goal dependencies MUST be versioned and acyclic.
2. Waits MUST name registered event kind, resource, predicate/scope, durable cursor, deadline, fallback polling where needed and escalation. Grain validates scope against the attachment and normalizes subscriptions; arbitrary event code or subscription URLs are forbidden. Persist subscription generation (contract/head scope), progress, last observed source version, journal cursor, next poll, backoff and timer firing state. Changing head/contract MUST retire old wait generations and create replacements.
3. Grain MUST avoid the snapshot-to-subscription lost-event race. Take snapshot at durable journal cursor C; atomically commit accepted results/state plus waits starting at C; replay relevant events after C before marking the bundle quiescent. If subscriptions are external, register from C when supported; otherwise establish collection before the snapshot and use bounded authoritative polling/reconciliation as the gap backstop. External events first enter the journal; a provider's cursor is never trusted to skip unseen evidence.
4. Event deliveries MUST be idempotent by source/event ID. Duplicate/out-of-order delivery MUST NOT regress authoritative source versions or resurrect old waits/approvals. On every wake, Grain MUST reread the authoritative current resource (or an observation with verified source version/freshness) before evaluating. Event payload alone MUST NOT establish success. A deleted/unreadable resource is unknown or an explicit failed outcome, not success.
5. Grain MUST coalesce relevant events per task and permit at most one accepted evaluation bundle per snapshot/contract epoch; an obsolete concurrent evaluation MUST lose its CAS. A wake evaluates first and dispatches an agent only if useful work remains. Dirty evidence arriving during evaluation MUST schedule a bounded next pass, not recurse synchronously forever.
6. Timers MUST be durable and recover due firings after restart using an idempotent firing key. Deadline expiry MUST trigger re-read, pending/error/unknown or escalation, never imply success. Without reliable events, default polling MUST back off from one minute to 30 minutes, bounded by the wait deadline; no more than 100 polls per wait generation before escalation unless policy explicitly extends it. A ten-minute default reconciliation sweep MUST recover missed events, expired evaluation/run leases and overdue timers. Deployments MAY tune intervals with persisted policy and a visible liveness bound.

## 7. Lifecycle, children and atomic close {#MGS-7}

1. Proposed tasks MUST await admission authority; their evaluations MAY preview but MUST NOT dispatch or close successfully. Admission records approved contract/policy revisions and authority epoch. Ready admitted tasks awaiting capacity MUST project waiting with a ready/capacity scheduling reason, distinct from an external goal wait. Active UI states MUST include running, waiting, needs answer, needs permission and needs acknowledgment; show every blocker irrespective of primary state. Primary precedence is running, needs answer, needs permission, needs acknowledgment, waiting. Scheduling/pause/error reasons remain separately visible, including when other work runs.
2. Terminal task outcomes MUST be succeeded, canceled or failed. Succeeded requires the closure predicate below. Cancel is an authorized stop, not satisfaction. Failed requires explicit Grain failure policy or authorized failure action and recorded reason; a provider exception/deadline MUST NOT alone imply task failure. A run's succeeded/failed outcome MUST NOT by itself become task outcome.
3. Pause, admission class, budget/usage limits, backoff, keep-running, close-versus-rest, failure exhaustion and standing person-closes behavior MUST be Grain lifecycle policies, not arbitrary goal predicates. Pause/budget blocks dispatch but does not erase evidence. Close-versus-rest=rest retains a satisfied task open and subscribed. Standing person-closes sessions MUST rest between turns; an authorized person's close event permits success only with remaining required obligations met/waived and operations/messages handled. Cancel remains available as canceled.
4. Child relationships MUST be explicit: `required_outcome` names its predicate (default success, optionally integration or explicit terminal closure), `advisory` supplies evidence but no completion hold, `independent` creates no completion obligation. Spawning a task MUST NOT implicitly attach a required outcome. Child closure MUST NOT imply success. Parent/child/dependency graph edits MUST reject cycles transactionally across concurrent edits; existing corrupt cycles MUST become visible blockers rather than recursive evaluation. Failed/canceled required children MUST remain unmet and offer authorized repair/replacement/waiver, not quietly count as delivered.
5. Grain MUST close atomically only when: authority epoch/contract/policy match; every required goal is met or validly waived on the still-current snapshot; all incoming user messages through the current watermark are processed; and active operations are settled or explicitly dispositioned under policy with recorded ownership and outcome handling. The close transaction MUST lock/CAS relevant task revision and message watermark, evidence vector, result/state revisions, waivers, and operation ledger, then append closure receipt and terminal outcome together. A concurrent message/evidence/action insertion MUST either precede and invalidate close or follow the committed closure and use closed-task/reopen policy. Child evidence invalidation MUST participate in the same version fence.
6. A live run MUST be gracefully stopped and settled before close, unless explicitly transferred as an operation under recorded policy. Do not label it succeeded merely because goals were met mid-run. Late branch writes/results invalidate closure preconditions. A pending post-merge review continuing under the existing override policy MAY be explicitly transferred to a repair/review owner with its evidence and obligations recorded; it MUST NOT be abandoned by closing the implementation task.
7. Later regressions MUST preserve the closure receipt and original evidence. Reopen or separate repair MUST follow an explicit policy with actor/reason and new authority/contract epoch; default is notification plus authorized repair. Closed-task messages remain recorded and undelivered until explicit reopening per existing policy, not treated as already processed. Acknowledgment means receipt, never approval or implicit waiver.

## 8. Persistence, APIs and migration {#MGS-8}

1. Grain MUST durably store contract revisions/authority epochs, attachment pins, bounded state/CAS versions, evaluation bundles, evidence/version vectors, action intents/events/idempotency, waiver scopes/revocations, subscriptions/cursors/deadlines, no-progress/error counters and closure receipts. Unique constraints and fencing MUST survive retries and daemon restart. Retention MUST keep decision evidence and audit references even if bulk snapshot pages expire.
2. Go `StateOf` and SQL `task_state` (SQLite and PostgreSQL) MUST select the same authority branch and lifecycle precedence. Migration MUST add fixtures covering all simultaneous-state/blocker cases and parity checks. Legacy report-completed, merge readiness and new succeeded MUST NOT share an ambiguous storage bit. Public legacy fields MUST be documented compatibility projections, not a second authority.
3. Future API/tools MUST expose versioned contract reads/conditional edits, per-goal result/evidence/blocker reads, registered action submission/status, waiver issue/revoke and lifecycle history. Mutations MUST carry expected contract/evidence versions and idempotency key; stale/conflict is 409, authorization failure 403, invalid input 400/422 with stable code and current refresh reference, unavailable provider 503 where applicable. No endpoint in this document is deployed. Agents MUST receive the same operation contracts and permission-request path as UI callers; shared API changes MUST keep both UIs working.
4. The UI MUST show per-goal status (including waived/unknown/error), summary, optional human text, evidence, all blockers, waits/deadlines, action state and typed buttons. Agent text/work MUST remain distinct from human presentation. Server-derived primary state, current evidence scope and confirmation apply to Angular; classic compatibility MUST NOT invent success for unknown new states.
5. Migration MUST follow the design's phases: retain collectors; shadow evaluators; compare legacy decisions; explicit per-task authority handoff; central transactional completion; then durable waiting/dispatch; remove old paths last. At handoff, fence active runs/operations, import legacy predicates with provenance, invalidate old decision waits, and atomically disable legacy lifecycle writes. There MUST never be two lifecycle authorities for the same task. Existing open tasks remain legacy until explicitly migrated.
6. Upgrades MUST deploy compatible readers before goal writers and fence old daemons. A daemon unable to interpret authority/protocol/schema versions MUST hold the task and expose a compatibility blocker, never revert to legacy. Rollback MUST preserve records and require explicit reverse handoff to a representable validated legacy contract; otherwise pause goal-owned execution for a compatible version. An unavailable required provider remains unknown with retries/escalation, never automatically waived, dropped or replaced.

If the authorized merge-ready goal instead requests an action, its action request can be `{"key":"merge-a1","action_id":"change.merge","inputs":{"change":123},"reason":null,"preconditions":[{"id":"pr:123","kind":"change","version":"head:a1/status:7"}]}`. This is not itself authorization. A typed receipt button can be `{"label":"Acknowledge report","action_id":"report.acknowledge","input_schema":{"type":"object","additionalProperties":false,"required":["report_id"],"properties":{"report_id":{"type":"string","enum":["report:7"]}}},"inputs":{"report_id":"report:7"},"confirmation":{"required":false,"reason_required":false,"text":null},"preconditions":[{"id":"report:7","kind":"report","version":"1"}]}`. The registry forbids treating that receipt action as Submit.

A successful `goal_integrated` response uses `status=met`, cites an updated authenticated `change` record with merged/submitted evidence, empties blockers/work/actions/waits/buttons, and reports the new consistent snapshot/revisions. Provider timeout instead produces Grain's synthetic `error` with `error={"code":"timeout","retryable":true,"message":"Evaluation deadline exceeded"}`, no candidate-state persistence and no agent dispatch solely because of the timeout.

## 10. Acceptance scenarios {#MGS-10}

These are requirements for later implementation tests, not tests or implementation added by this documentation PR.

| Scenario | Required observation |
|---|---|
| Head changes while reviews return met | Reject old bundle/state/button; retire old waits; evaluate current head; no merge/close. |
| Message races atomic close | Earlier committed message blocks close until processed; later message is retained under closed-task/reopen policy. No lost message. |
| Two evaluation responses race state CAS | Exactly one accepted revision; loser cannot overwrite state, subscriptions or actions. |
| CI completes between snapshot and subscribe | Journal replay from C observes it without waiting for another event; authoritative re-read precedes decision. |
| Duplicate/out-of-order review/PR events | No version regression, duplicate action or stale approval resurrection. |
| Restart with due timer or operation intent | Recover timer once logically; reconcile side-effect receipt/idempotency before retry; no blind duplicate merge. |
| Required CI provider unavailable | Unknown/error, persisted capped backoff and escalation; no false success, legacy fallback or dispatch loop. |
| Provider returns arbitrary URL/code, forged evidence, oversized state or unknown action | Reject/sanitize as appropriate; no network fetch, execution or authority expansion; preserve old state. |
| Provider uses state to claim approval | Only authorized action/review records count; no approval from state/prose. |
| User loses permission after button rendered | Server refuses action; audit refusal and refresh; no side effect. |
| Waiver/review scope stale after new head, changed args or policy | Waiver invalid and review rechecked; distinct historical records remain. |
| Acknowledgment or note says approved | Receipt/note does not satisfy Submit, review or protected-action permission. |
