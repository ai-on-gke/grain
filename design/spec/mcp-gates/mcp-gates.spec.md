# MCP gate evaluation and lifecycle specification

**Status:** proposed, normative for the protocol described here; not implemented. Documentation approval does not migrate any task or authorize implementation/deployment/follow-up filing.

**Specifies:** [Extensible MCP gates](../../design/mcp-gates.design.md).

The words MUST, MUST NOT, SHOULD, SHOULD NOT and MAY have their BCP 14 meanings. Requirement IDs are stable. [wire.schema.json](wire.schema.json) is a JSON Schema 2020-12 document containing concrete request, response, attachment, action-event, waiver and read-operation/page/result, discovery and disjoint continuation/final schemas in `$defs`. Validate each message against its named definition, then apply the cross-field invariants below. These are documentation assets, not a new runtime validator or deployed endpoint. The normative [action gate bindings extension](action-bindings.spec.md) and its [schema](action-bindings.schema.json) extend these requirements to protected operations, inherited resource policy and taskless callers. Brokered read transport remains in this wire schema; the separate action profile negotiates its authority context explicitly.

**Terminology:** Task goals such as `pr-merged`, `base-green` and `person-closes` retain their existing desired-outcome/standing-intent meaning and concrete APIs/configuration. Gates are this proposal's extensible evaluators/requirements for readiness and completion. All `gate_*` tool names and fields below belong only to the proposed extension; no legacy goal API or runtime behavior is renamed. The `MGS-*` requirement IDs remain stable from PR #1666.

## 1. Authority and attachment {#MGS-1}

1. Grain MUST own admission, lifecycle transitions, dispatch, operation arbitration, authorization and closure. An evaluator MUST NOT write these directly. Task completion authority MUST be exactly one of legacy or gates at a recorded authority epoch. Observation-only results MUST NOT affect legacy task decisions.
2. An extension MUST expose an MCP `tools/list` entry named `gate_<method>`, where method matches `^[a-z0-9][a-z0-9_-]{0,62}$`. Its `inputSchema` MUST describe the request envelope, with provider-specific capability-style `args`. Discovery MUST NOT attach a gate or authorize its reads/actions. `mint_*`, `release_*` and `configure` retain their capability meanings; `gate_*` MUST NOT be treated as a mint method.
3. An admitted contract MUST enumerate stable gate IDs, whether each is required, canonical provider identity and immutable release/artifact pin, tool name, gate version, argument schema digest, state version, validated canonical arguments and their digest. A schema digest MUST cover resolved local definitions; remote schema fetches MUST NOT occur during evaluation. Resolve capability-style defaults before hashing. Provider args MUST use the supported capability argument-schema subset; secret values and credentials MUST NOT be arguments.
4. Grain MUST separately authorize (a) contract attachment/editing, (b) evaluator access to the declared bounded read scope, (c) user/agent evidence reads and (d) every action. A required obligation with no read permission MUST remain required and unknown with a permission blocker. It MUST NOT implicitly mint access or waive itself.
5. Contract, policy and child-link edits MUST increment contract revision and invalidate affected results, waits, buttons and waivers. Removing/relaxing a requirement, changing success into closure, or replacing a provider MUST require an authorized person's reasoned approval unless that exact transformation was preauthorized in the contract. An agent MAY propose edits; it MUST NOT drop its own obligations to finish. Record before/after, actor, reason and authority epoch. Adding requirements MUST also respect caller authority and template constraints.
6. MCP annotations are hints, not authorization. Grain MUST enforce read-only execution independently of any `readOnlyHint`.

## 2. Requests, evidence contexts and state {#MGS-2}

1. Completion-profile tools/call arguments MUST validate against request for protocol 4.0; action-profile 5.0 uses AGB-3 over the same brokered transport. MGS-11 and [BR-1–4](brokered-reads.spec.md) define every mode/round. Grain generates evaluation/bundle/context IDs, hashes, exact pins/args, authority/contract/policy/permission revisions, expected durable state revision, fixed clock/deadline and registered mandatory input requirements. Mode is evaluate, migrate or recover.
2. evidence_context version 3 identifies a logical observation/dependency context, not a fully materialized immutable task snapshot. It carries core versions, journal cursor, incoming/processed watermarks, declared domains, explicit unavailable markers, registered requirement scope digests and bounded inline records. Grain alone advances processed watermark from recorded delivery/disposition, never provider summary/state. Relevant task, child, external, policy and action evidence is available through scoped registered reads or explicit unavailability.
3. Initial context is at most 256 KiB/100 records; one read-result page at most 128 KiB/100 records. All rounds/reads/retries share one 30-second deadline, 64 operation attempts, 8 MiB pages and 6,500 records under MGS-11 limits. Bounded source scans stop before overflow, never preload unbounded data or truncate into met.
4. Gates return non-final read_requests naming allowlisted operation/version and exact typed args; Grain authorizes/executes ordinary read adapters and delivers read_results in the next call to the same pinned evaluator. No provider callback, arbitrary object lookup, SQL/JSONPath, URLs, credentials or mutation is exposed. Read pages include stable subject/head, collection generation, coverage, source freshness, next cursor and automatically captured dependencies.
5. Every final acceptance/action/closure MUST validate the union of core and automatically tracked read dependencies as BR-3 specifies. Required read/predicate completeness cannot be bypassed by provider omission. Set/negative evidence has membership-generation dependencies; mutable facts, dirty hints, child/message/policy/head/permission changes invalidate the context. Only delivered bytes need retention; immutable full-task materialization is not required. All gates in one decision share a consistent validated context with separately authorized views. External systems do not become atomically frozen by Grain validation.
6. `gate_state` MUST be opaque JSON interpreted only by the pinned provider, bounded to 16 KiB encoded UTF-8, depth 16, with no credentials. Grain MUST validate its envelope and compare-and-swap expected revision for every accepted update. State revision MUST increase by exactly one for every accepted non-error final candidate, including identical values and null reset. It MUST be monotonic per attachment across explicit migrations/recovery and stored with provider/gate/state-version identity; revisions MUST NOT be reused under a new pin. Only a non-error final result can update state; read_requests and controller aborts MUST NOT. An accepted evaluation ID MUST be unique; retries MUST NOT apply state twice. Result, updated state, subscriptions and evaluation cursor MUST commit atomically, or none do. Provider state MUST NOT substitute for authoritative CI/review/approval evidence.
7. Version changes MUST use an explicit contract migration record with old/new pins and state version. `mode=migrate` supplies `previous_pin`, old state and current authoritative evidence context to the new pinned evaluator; it MUST return transformed state only, with status unknown, no actions/work/waits/buttons. Grain validates and CASes the migration, switches contract pins and schedules fresh evaluation atomically, invalidating prior results. A failed migration MUST preserve the old state/pin. No provider replacement may silently interpret old state.
8. `mode=recover` is allowed only when the pinned provider declares evidence replay safe. It receives null state and a reasoned recovery record; it MUST rebuild from authoritative evidence, return unknown and no work/actions/waits/buttons, and MUST NOT invent approvals. Otherwise recovery MUST hold for an authorized migration/repair. Preserve old state for audit. After recovery, evaluate afresh. Provider unavailability MUST NOT trigger automatic reset, downgrade or legacy fallback.
9. Unified MGS-11 limits cover reads, retained bytes, rounds and retries. Final response is at most 256 KiB, with at most 32 work items, 32 action requests, 64 waits, 16 buttons and 128 citations. Effective lower limits are fixed before round 0. Parsers and decoded allocations/concurrency MUST be bounded; deadline expiry is timeout, never met.

## 3. Result semantics and compatibility {#MGS-3}

1. Completion-profile responses MUST validate against the disjoint `$defs.response` union (action-profile 5.0 uses the AGB-3 union with the same disjoint continuation/final semantics) and echo protocol, bundle/evaluation/round, request digest, gate, evidence context, contract, authority epoch, lifecycle policy, permission/scope, evidence and state revisions exactly. A response is either non-final `kind=read_requests` (MGS-11) or `kind=final`. MCP `structuredContent` carries this object, with the existing client’s single JSON text result fallback allowed; human-readable renderings are non-authoritative. Only final responses have statuses `met`, `unmet`, `pending`, `error`, `unknown`:

| Status | Meaning | Required handling |
|---|---|---|
| met | The declared predicate holds on the evidence context | Grain validates required evidence and scope; eligible for aggregation, not immediate self-close. |
| unmet | Predicate is known false | Show blockers; dispatch only explicit useful authorized work. |
| pending | An identified external operation/event is still unresolved | At least one viable wait or in-flight operation reference is required. Other independent work can run. |
| error | Evaluation failed | Error code and retry classification required; not unmet or met. |
| unknown | Evidence, permission, compatibility or interpretation is insufficient | Explain missing information and recovery/wait path; MUST NOT default to met. |

2. Every **final** response MUST carry a one-line summary (maximum 240 characters, no newline), evidence references, `gate_state` candidate, blockers, work, action requests, waits, buttons and optional separate `human_text` and `agent_text`. Evidence MUST reference records from the supplied authorized evidence context with immutable versions. Met MUST carry at least one reference, including a Grain-recorded no-work/report/person-action record where appropriate. Grain MUST verify evidence kind, subject, version, freshness and predicate-specific prerequisites using the registered contract; a fabricated ID or scope mismatch invalidates the whole response.
3. A blocker identifies kind (`answer`, `permission`, `acknowledgment`, `external`, `work`, `provider`, `policy`), a stable key, explanatory summary and optional related evidence. Text is untrusted presentation, never instructions with system authority. Grain MUST escape/sanitize display, redact known secrets in logs, avoid interpreting embedded links as action targets, and keep agent text labeled as provider output.
4. Work MUST identify stable key, target, summary, dependencies, evidence preconditions, and required registered tools/permissions. A provider MUST NOT make executable code or arbitrary URLs a structured operation. Agent work can include an ordinary task instruction such as investigate a cited failing test; it cannot confer a new grant. `action_requests` MUST name registered actions and validated JSON inputs, stable key, reason when required and expected evidence. Grain MUST reject unknown operation IDs rather than dynamically registering them.
5. For `met`, work/action requests and blockers MUST be empty; waits MAY request monitoring only under an explicit regression policy. For `error`, work/actions/buttons MUST be empty. A `pending` response with no viable wait/in-flight reference is `invalid_result`. Migration/recovery restrictions in MGS-2 override ordinary result semantics. A response MUST NOT request work whose dependency is its own unsatisfied output or otherwise form an action dependency cycle.
6. Wire v4 is exact: unknown envelope fields or unknown enum values MUST fail validation; extension payloads belong in registered `args`, record `data` or opaque `gate_state`, not ad hoc envelope keys. Compatible new optional protocol fields require negotiated minor support; required/semantic changes require a new protocol version. Grain MUST refuse unsupported pins/schema/protocol at attachment/admission or hold an already-admitted task unknown after an upgrade. No coercion of unknown status to false/success is permitted.
7. MCP transport failure, `isError:true`, malformed JSON, schema mismatch and deadline are protocol failures, not task verdicts. Grain MUST normalize failures to a synthetic error result without committing candidate state. Error codes are `timeout`, `unavailable`, `unauthorized`, `unsupported_version`, `invalid_request`, `invalid_result`, `state_conflict`, `stale_snapshot`, `reference_expired`, `resource_limit`, `provider_error`, `request_loop`, `canceled`. MGS-11 defines read-error deliveries and retry/restart classification; a diagnostic synthetic final is not an accepted result. Stale/conflict causes coalesced reevaluation, not agent dispatch. Invalid/persistent compatibility/authorization failures need operator recovery; transient timeout/unavailable/provider errors back off. Provider error text MUST NOT expose credentials.
8. Grain MUST retain accepted results, rejected-result diagnostic hashes/reasons, and closure/action receipts sufficient to explain decisions. Unknown/error in a required gate blocks success unless a separate valid waiver applies; advisory errors do not block success.

## 4. Actions, buttons and waivers {#MGS-4}

1. Initial evaluators MUST be pure bounded replayable read-only functions of arguments, the retained evidence context view/current deliveries, durable state, bounded request-carried continuation and declared clock/deadline. They MUST NOT send messages, mutate providers, submit reviews, merge, deploy or call write tools during evaluation. Execution credentials MUST exclude those powers. Evaluation MUST NOT perform external reads; collection happens before the evidence context cut. Current-round scratch computation remains subject to time/data limits.
2. Grain MUST execute requested actions through the same Grain action executor used by agent, operator and automation requests. Protected effects MUST resolve non-optional action guard bindings under AGB-1 through AGB-8, independently of task completion authority. Equivalent tools/actions and taskless requests MUST NOT omit resource policy. The executor uses registered authorized operations/tools available to agents. An agent MUST have required tools/permissions or be able to request them through the normal permission flow. Future optimized execution MUST reuse the same path, with no privileged alternate implementation and no requirement that optimization be enabled to make progress.
3. `$defs.button` contains label, registered `action_id`, `input_schema`, fixed/default inputs, evidence preconditions and confirmation requirements. The input schema MUST be a constrained subset of the registry's schema; it MUST NOT broaden it. Registry policy is the minimum confirmation and required reason. No executable code, callback URL or provider-defined permission check is allowed. Button availability is a server-derived convenience, not authority.
4. At action request or click, Grain MUST check current actor role/delegation, grants, human-only restrictions, current contract and evidence versions, live preconditions, input schema and required confirmation/reason. For external mutations, Grain MUST pass the expected head/resource version to a conditional operation where supported; if the source cannot enforce that condition, Grain MUST serialize its own writers, re-read immediately before execution and reconcile uncertain results before accepting outcome evidence. Those steps alone MUST NOT be claimed to prevent external races: protected admission additionally requires the AGB-4/AGB-5 conditional/exclusion boundary, otherwise Grain MUST refuse enforced execution. Revoked authority or stale evidence MUST refuse with a reason and refresh, not perform the action. Acknowledgment MUST record receipt only; Submit/approval MUST use their own registered actions. A note containing “approved” MUST NOT produce an approval event.
5. For the task completion profile, the operation ledger MUST durably record an immutable `action_event` with actor, action ID, inputs, reason when required, gate/contract/evidence scope, request ID and idempotency key before starting a side effect. Event phases are requested, started, succeeded, failed, unknown; append events rather than editing history. Action-profile operations, including taskless requests, use AGB-3 `operation_event` plus `receipt` records with equivalent intent/audit requirements. Use an outbox/intent transaction and operation-specific idempotency/reconciliation for the external boundary. A crash after an external success MUST reconcile its authoritative receipt before retrying; it MUST NOT blindly repeat. Gates MAY consume these events but a requested/started event is not evidence of successful side effect.
6. A waiver MUST be a Grain-owned `$defs.waiver` record with authorized actor, nonempty, non-whitespace reason, gate/provider/version/argument/contract/evidence scope, issue time, optional expiry and explicit invalidation keys. Grain MUST enforce invalidation on head, gate/schema/args, scoped evidence, policy or authority changes and revocation; defaults MUST invalidate on any scoped change. A provider MUST NOT create a waiver by returning state or prose. UI MUST display waived distinctly from met, with reason and actor. Waiver permission MUST be explicit and person-only by default; agents can request it, not grant it.
7. A completion waiver MUST NOT authorize a protected action or stand in for approval. Existing merge gate overrides retain `merge:force`, exact-head scope, reason, confirmation and their action audit; Submit retains human approver policy. Merge readiness supplies guard satisfaction only while all required action prerequisites hold; it MUST NOT confer caller authorization. AGB-6 governs separately authorized exact-action/head/guard overrides. Action overrides MUST NOT waive completion obligations. Observed merge/CL submission satisfies the integration gate for the desired integration outcome.

## 5. Aggregation, arbitration and progress {#MGS-5}

1. Required completion gates are an explicit conjunction; advisory gates do not block completion. Action guard aggregation is a separate conjunction under AGB-2: integration of the same PR MUST NOT be a prerequisite for executing its merge. Each required gate MUST be met or covered by a currently valid waiver. Empty gate sets MUST require an explicit admitted no-obligations contract, never result from discovery failure. Grain MUST decide lifecycle from the consistent bundle, not from a provider's requested task status.
2. Grain MUST first validate results and deduplicate work/actions across gates by registered operation/tool, target, canonical inputs and precondition scope, preserving all requesting gate IDs. Stable provider keys are hints; Grain computes identity. Conflicting requests MUST be serialized or surfaced for resolution, not executed in provider arrival order. Dependency order, task priority and deterministic stable-key ordering resolve eligible nonconflicting work; dependency cycles are errors.
3. There MUST be at most one active task agent run, enforced by a durable lease/unique active-run constraint with fencing tokens. Concurrent external operations are permitted only under registered resource locks and compatibility rules (for example independent CI and review reads). Two mutations of the same branch/head, merge and branch edit, or incompatible contract edits MUST serialize. Shared-resource operations across tasks MUST use the same locks. An evaluator pass is not a task agent run and MUST NOT bypass operation locks.
4. An event wait on any gate MUST NOT suppress independent actionable authorized work on another gate. Dispatch MUST require a new user request, actionable work or a justified continuation under lifecycle policy, available permissions, settled conflicting operations, admission and capacity. An unmet/error/pending status alone is not work. Missing permission blocks its dependent work, not unrelated work; global pause/budget policy may still hold the task.
5. Grain MUST persist progress as changes in authoritative evidence, completed operations, processed messages and settled child outcomes. Provider progress tokens, summaries and opaque-state churn MUST NOT alone reset no-progress/error counters or schedule another run. After two identical no-progress attempts on the same work/precondition identity, default policy MUST hold that work and escalate with evidence; changing this threshold requires recorded lifecycle policy. Provider failures MUST use a separate counter and MUST NOT consume an agent task-failure streak merely because a provider is down.
6. Default transient evaluator retry is exponential backoff from 30 seconds capped at 30 minutes with bounded jitter, persisted across restart; five consecutive failed evaluations raise a deduplicated operator blocker; ten hold automatic retries pending authorized resume. Same-round retransmissions and stale/churn restarts have the separate tighter bounds in MGS-11 and do not reset this counter. New relevant evidence MAY cause a bounded immediate retry but MUST NOT defeat provider-wide circuit/rate limits. Repeated identical errors MUST NOT emit unbounded comments/events or dispatch agents. Missing viable wake, exhausted polling, and unmet-without-remedy MUST name a driver and escalation. Independent work MAY continue.

## 6. Durable wakes and evaluation triggers {#MGS-6}

1. Grain MUST dirty evaluation on relevant CI/check/review/PR/CL events, head/base observations required by the predicate, child outcomes, user messages/actions, permission/role changes, contract/provider/schema changes and timer deadlines. Displayed state transitions alone are insufficient. Provider-authored summary/state/result storage MUST NOT be evidence-change triggers for that same evaluation loop. Explicit cross-gate dependencies MUST be versioned and acyclic.
2. Waits MUST name registered event kind, resource, predicate/scope, durable cursor, deadline, fallback polling where needed and escalation. Grain validates scope against the attachment and normalizes subscriptions; arbitrary event code or subscription URLs are forbidden. Persist subscription generation (contract/head scope), progress, last observed source version, journal cursor, next poll, backoff and timer firing state. Changing head/contract MUST retire old wait generations and create replacements.
3. Grain MUST avoid the evidence context-to-subscription lost-event race. Take evidence context at durable journal cursor C; atomically commit accepted results/state plus waits starting at C; replay relevant events after C before marking the bundle quiescent. If subscriptions are external, register from C when supported; otherwise establish collection before the evidence context and use bounded authoritative polling/reconciliation as the gap backstop. External events first enter the journal; a provider's cursor is never trusted to skip unseen evidence.
4. Event deliveries MUST be idempotent by source/event ID. Duplicate/out-of-order delivery MUST NOT regress authoritative source versions or resurrect old waits/approvals. On every wake, Grain MUST reread the authoritative current resource (or an observation with verified source version/freshness) before evaluating. Event payload alone MUST NOT establish success. A deleted/unreadable resource is unknown or an explicit failed outcome, not success.
5. Grain MUST coalesce relevant events per task and permit at most one accepted evaluation bundle per evidence context/contract epoch; an obsolete concurrent evaluation MUST lose its CAS. A wake evaluates first and dispatches an agent only if useful work remains. Dirty evidence arriving during evaluation MUST schedule a bounded next pass, not recurse synchronously forever.
6. Timers MUST be durable and recover due firings after restart using an idempotent firing key. Deadline expiry MUST trigger re-read, pending/error/unknown or escalation, never imply success. Without reliable events, default polling MUST back off from one minute to 30 minutes, bounded by the wait deadline; no more than 100 polls per wait generation before escalation unless policy explicitly extends it. A ten-minute default reconciliation sweep MUST recover missed events, expired evaluation/run leases and overdue timers. Deployments MAY tune intervals with persisted policy and a visible liveness bound.

## 7. Lifecycle, children and atomic close {#MGS-7}

1. Proposed tasks MUST await admission authority; their evaluations MAY preview but MUST NOT dispatch or close successfully. Admission records approved contract/policy revisions and authority epoch. Ready admitted tasks awaiting capacity MUST project waiting with a ready/capacity scheduling reason, distinct from an external gate wait. Active UI states MUST include running, waiting, needs answer, needs permission and needs acknowledgment; show every blocker irrespective of primary state. Primary precedence is running, needs answer, needs permission, needs acknowledgment, waiting. Scheduling/pause/error reasons remain separately visible, including when other work runs.
2. Terminal task outcomes MUST be succeeded, canceled or failed. Succeeded requires the closure predicate below. Cancel is an authorized stop, not satisfaction. Failed requires explicit Grain failure policy or authorized failure action and recorded reason; a provider exception/deadline MUST NOT alone imply task failure. A run's succeeded/failed outcome MUST NOT by itself become task outcome.
3. Pause, admission class, budget/usage limits, backoff, keep-running, close-versus-rest, failure exhaustion and standing person-closes behavior MUST be Grain lifecycle policies, not arbitrary gate predicates. Pause/budget blocks dispatch but does not erase evidence. Close-versus-rest=rest retains a satisfied task open and subscribed. Standing person-closes sessions MUST rest between turns; an authorized person's close event permits success only with remaining required obligations met/waived and operations/messages handled. Cancel remains available as canceled.
4. Child relationships MUST be explicit: `required_outcome` names its predicate (default success, optionally integration or explicit terminal closure), `advisory` supplies evidence but no completion hold, `independent` creates no completion obligation. Spawning a task MUST NOT implicitly attach a required outcome. Child closure MUST NOT imply success. Parent/child/dependency graph edits MUST reject cycles transactionally across concurrent edits; existing corrupt cycles MUST become visible blockers rather than recursive evaluation. Failed/canceled required children MUST remain unmet and offer authorized repair/replacement/waiver, not quietly count as delivered.
5. Grain MUST close atomically only when: authority epoch/contract/policy match; every required gate is met or validly waived on the still-current evidence context; all incoming user messages through the current watermark are processed; and active operations are settled or explicitly dispositioned under policy with recorded ownership and outcome handling. The close transaction MUST lock/CAS relevant task revision and message watermark, evidence vector, result/state revisions, waivers, and operation ledger, then append closure receipt and terminal outcome together. A concurrent message/evidence/action insertion MUST either precede and invalidate close or follow the committed closure and use closed-task/reopen policy. Child evidence invalidation MUST participate in the same version fence.
6. A live run MUST be gracefully stopped and settled before close, unless explicitly transferred as an operation under recorded policy. Do not label it succeeded merely because gates were met mid-run. Late branch writes/results invalidate closure preconditions. A pending post-merge review continuing under the existing override policy MAY be explicitly transferred to a repair/review owner with its evidence and obligations recorded; it MUST NOT be abandoned by closing the implementation task.
7. Later regressions MUST preserve the closure receipt and original evidence. Reopen or separate repair MUST follow an explicit policy with actor/reason and new authority/contract epoch; default is notification plus authorized repair. Closed-task messages remain recorded and undelivered until explicit reopening per existing policy, not treated as already processed. Acknowledgment means receipt, never approval or implicit waiver.

## 8. Persistence, APIs and migration {#MGS-8}

1. Grain MUST durably store contract revisions/authority epochs, attachment pins, bounded state/CAS versions, evaluation bundles, evidence/version vectors, action intents/events/idempotency, waiver scopes/revocations, subscriptions/cursors/deadlines, no-progress/error counters and closure receipts. Unique constraints and fencing MUST survive retries and daemon restart. Retention MUST keep decision evidence and audit references even if bulk evidence context pages expire.
2. Go `StateOf` and SQL `task_state` (SQLite and PostgreSQL) MUST select the same authority branch and lifecycle precedence. Migration MUST add fixtures covering all simultaneous-state/blocker cases and parity checks. Legacy report-completed, merge readiness and new succeeded MUST NOT share an ambiguous storage bit. Public legacy fields MUST be documented compatibility projections, not a second authority.
3. Future API/tools MUST expose versioned contract reads/conditional edits, per-gate result/evidence/blocker reads, registered action submission/status, waiver issue/revoke and lifecycle history. Mutations MUST carry expected contract/evidence versions and idempotency key; stale/conflict is 409, authorization failure 403, invalid input 400/422 with stable code and current refresh reference, unavailable provider 503 where applicable. No endpoint in this document is deployed. Agents MUST receive the same operation contracts and permission-request path as UI callers; shared API changes MUST keep both UIs working.
4. The UI MUST show per-gate status (including waived/unknown/error), summary, optional human text, evidence, all blockers, waits/deadlines, action state and typed buttons. Agent text/work MUST remain distinct from human presentation. Server-derived primary state, current evidence scope and confirmation apply to Angular; classic compatibility MUST NOT invent success for unknown new states.
5. Migration MUST follow the design's phases: retain collectors; shadow evaluators; compare legacy decisions; explicit per-task authority handoff; central transactional completion; then durable waiting/dispatch; remove old paths last. At handoff, fence active runs/operations, import legacy predicates with provenance, invalidate old decision waits, and atomically disable legacy lifecycle writes. There MUST never be two lifecycle authorities for the same task. During the interval before durable waiting/dispatch migration, legacy drivers MAY emit observations or proposals through a compatibility adapter to the single new owner, but MUST NOT retain direct lifecycle writes. Existing open tasks remain legacy until explicitly migrated.
6. Upgrades MUST deploy compatible readers before gate writers and fence old daemons. A daemon unable to interpret authority/protocol/schema versions MUST hold the task and expose a compatibility blocker, never revert to legacy. Rollback MUST preserve records and require explicit reverse handoff to a representable validated legacy contract; otherwise pause gate-owned execution for a compatible version. An unavailable required provider remains unknown with retries/escalation, never automatically waived, dropped or replaced.

## 9. Complete wire examples {#MGS-9}

[The example index](examples/README.md) maps each complete machine-readable transcript to its required outcome. Each `*.json` transcript validates against `$defs.transcript`; every call/reply/delivery is a complete envelope, not a patch or implied field omission. Requests and chained response digests are computed from canonical JSON. The local [example record registry](examples/evidence.schema.json) validates all delivered sample records; it illustrates registration, not a universal replacement for Task #45's provider fact schemas.

The complete tools/list example embeds the resolved envelope and input declaration, including pinned record-schema digests. The success transcript covers three calls, two pages and one final state CAS. Other transcripts cover repeated reads, denied and mixed-availability reads, permission revocation, bulk expiry on recovery, stale evidence, provider timeout, provider crash/exact retry, Grain crash/checkpoint recovery, partial required input, prefetch and cancellation. A controller_error step is diagnostic only and MUST NOT be accepted or CAS state. Event steps describe journal/storage/time events; they are not extra MCP messages. MCP wrappers are standard `tools/call` requests with each call's message as `arguments`, and replies as `result.structuredContent`.

## 10. Acceptance scenarios {#MGS-10}

Protected-operation scenarios additionally MUST satisfy [AGB-7](action-bindings.spec.md#AGB-7), including bypass prevention and blocked-then-allowed agent merge. Lifecycle migration does not imply action enforcement admission.

These are requirements for later implementation tests, not tests or implementation added by this documentation PR.

| Scenario | Required observation |
|---|---|
| Initial/prefetched round returns valid final | One validated final receipt/state CAS; all page/byte/read budgets include prefetch. |
| Paged read_requests returns two rounds before final | Same evidence context/pins/clock; no gate result, state CAS, subscription, action, lifecycle, progress or agent/trigger dispatch during continuation. |
| Exact duplicate round vs later repeated page request | Exact retry replays stored request within counters; later repeat gets one no-data loop warning then unknown or bounded abort. |
| Provider asks denied/unknown reference | Indistinguishable unauthorized delivery without records; no scope expansion or missing-as-false/met. |
| Partial, unsupported or oversized required domain | Explicit unavailable marker; final unknown or error; Grain refuses met even with terminal page. |
| Snapshot pages lost/expired; driver restarts | Abort unavailable/reference_expired, never refill from current DB or extend old deadline; new evidence context only under bounded restart policy. |
| Revocation or freshness expiry between rounds | Abort/fence all affected bundle candidates/buttons; no further delivery/accepted state; restored permission requires fresh evidence context. |
| Provider crashes/lost reply; Grain crashes around checkpoint/commit | Deterministic exact request replay with no provider session, lease fencing and one logical round/final commit. |
| Provider timeout, late met or explicit cancellation | Abort diagnostic only; preserve durable state, no action/close; late response discarded and bounded retry/backoff. |
| Churn, many unique pages or request loop | Eight-round/64-read/64-page/8-MiB/30-second bounds do not renew; coalesced stale retry limit/hold/escalation survives restart. |
| Head changes while reviews return met | Reject old bundle/state/button; retire old waits; evaluate current head; no merge/close. |
| Message races atomic close | Earlier committed message blocks close until processed; later message is retained under closed-task/reopen policy. No lost message. |
| Two evaluation responses race state CAS | Exactly one accepted revision; loser cannot overwrite state, subscriptions or actions. |
| CI completes between evidence context and subscribe | Journal replay from C observes it without waiting for another event; authoritative re-read precedes decision. |
| Duplicate/out-of-order review/PR events | No version regression, duplicate action or stale approval resurrection. |
| Restart with due timer or operation intent | Recover timer once logically; reconcile side-effect receipt/idempotency before retry; no blind duplicate merge. |
| Required CI provider unavailable | Unknown/error, persisted capped backoff and escalation; no false success, legacy fallback or dispatch loop. |
| Provider returns arbitrary URL/code, forged evidence, oversized state or unknown action | Reject/sanitize as appropriate; no network fetch, execution or authority expansion; preserve old state. |
| Provider uses state to claim approval | Only authorized action/review records count; no approval from state/prose. |
| User loses permission after button rendered | Server refuses action; audit refusal and refresh; no side effect. |
| Waiver/review scope stale after new head, changed args or policy | Waiver invalid and review rechecked; distinct historical records remain. |
| Acknowledgment or note says approved | Receipt/note does not satisfy Submit, review or protected-action permission. |
| Scoped waiver issued without merge permission | Completion exception recorded, merge still refused. |
| Required child fails/cancels; advisory child still running | Required success unmet; advisory never blocks; explicit legacy closure predicate remains distinguishable. |
| Concurrent child edits create cycle | One edit rejected transactionally; no recursive deadlock. |
| Gate A waits for review while B can write report | One useful authorized run for B; A wait remains durable and visible. |
| Two gates request same repair; merge conflicts with branch write | One repair intent; conflicting operations serialize and recheck scope. |
| Evaluator churns summary/state or repeats identical work | No feedback wake; no progress credit; bounded no-progress attempts then hold/escalation. |
| Missed webhook, expired cursor or event service outage | Reconciliation/polling detects current truth; deadlines escalate, never succeed. |
| All gates met while a run can still push | Settle/fence run and re-read before close; late evidence invalidates old close attempt. |
| Migrate/rollback with older daemon or missing provider | One authority remains; incompatible daemon holds; no silent contract weakening. |
| Base failure did not reproduce; publishing remains broken | Recorded non-reproduction can satisfy base-green only; required publishing outcome remains unmet. |
| Review finishes with findings or Submit arrives early | Review task delivery may succeed; merge prerequisites remain blocked until clean review/explicit permitted override. |
| Regression after success; person-closes session healthy | Preserve historical success and use explicit repair/reopen; session rests and remains open. |

## 11. Grain-brokered read transport {#MGS-11}

This section supersedes Task #47's snapshot-page-only transport under the operator's Task #56 decision. Completion profile **4.0**, action profile **5.0**, evidence-context version **3**, brokered read-operation version **1.0** and continuation format **1** MUST be negotiated/pinned explicitly. There is no v2/3 fallback. [Brokered read contracts BR-1–4](brokered-reads.spec.md) and [exact schemas](read-operations.schema.json) are normative companions. This is an application convention carried over standard MCP, not native reverse tools/call.

### 11.1 Discovery and call direction

1. Each `gate_<method>` tool MUST advertise `inputSchema["x-grain-gate"]` conforming to discovery (AGB guard_discovery for action profile). It pins protocol/context/continuation versions, `transport=grain_brokered_reads`, evidence replay safety, ≤32 input domains, ≤64 registered record-schema digests and ≤32 read-operation schema pins. Every declared kind/operation and its adapter release must match the approved local registry; scope is separately authorized. Local resolved schemas only, no remote fetch. Immutable release must be bound to actual configured process/server/config/credential identity; self-reported pins are insufficient.
2. Each input domain names kinds, supported operations, required status and prefetch preference. Grain resolves registered scope selectors/mandatory predicate prerequisites from canonical attachment args/effective policy. Providers cannot add arbitrary selectors, resource IDs, grants or operations. Grain MAY preexecute up to eight declared prefetch reads into round 0 under exactly the same limits/authorization/dependency accounting. Required data that does not fit remains an explicit requirement or unavailable, not omitted as optional.
3. Each round is ordinary **Grain → same pinned provider** `tools/call`; result JSON is `$defs.response`, preferably MCP structuredContent with the existing JSON-text fallback allowed. Native JSON-RPC errors, MCP isError and transport failures are failures, never read requests. Grain executes allowlisted reads through BR-1's ordinary authorized adapter/capability path; only Grain initiates provider calls. No provider-to-Grain network connection/listener/token, new hostd requirement, callback server or colocation assumption exists.
4. Current [client](../../../pkg/capability/protocol/client.go), [control caller](../../../pkg/capability/protocol/server.go) and [registry](../../../pkg/capability/servers/servers.go) supply this outward direction and structured JSON decoding. Stdio/SSE readers skip server requests; empty client capabilities do not negotiate reverse dispatch. Standard resources expose server data to clients and list pagination does not page resource contents. No native facility supplies our authorization/consistency semantics. Gate/read-registry validation, provider isolation and byte caps still require implementation; generic 32 MiB HTTP cap is insufficient. All calls receive only remaining evaluation time.

### 11.2 Evidence context and consistency

1. Grain MUST create a bounded evidence context with core authority/permission/contract/policy/config/credential/head fences, incoming/processed watermarks, journal cursor and registered mandatory requirements, under a short consistent DB read. `evidence_context.id` is a logical bundle/dependency-ledger identity, not a whole materialized immutable task snapshot or access credential. Inline records are redacted/registry-validated with explicit domain availability. Only Grain advances processed-message watermark under recorded disposition rules.
2. BR-3's lazy dependency validation is REQUIRED: each bounded read transaction captures record revisions, set membership/coverage generation, subject/head, pin/auth/recovery epochs, dirty/covered state and source freshness together. Grain derives dependencies automatically, including successful empty reads; providers cannot omit them. Only returned bounded redacted bytes are retained. No DB transaction spans an MCP/external call. No mandatory full backing snapshot/page catalog is built before round 0.
3. Paginated reads require a stable versioned committed projection. Generation changes between pages invalidate the evaluation; there is no silent refill/splice from live data. External facts are normalized by authorized collectors and committed before use. Refresh outside the read transaction may force a new context; a changed dependency is never silently rebased. Provider-specific record/predicate mappings must prove completeness; missing/unsupported/stale/partially captured domains remain unavailable, not negative facts. Collection stops at byte/record/time limits without unbounded preloading/counting.
4. Before final acceptance, action or closure, Grain validates the entire core+dependency union/current authorization/freshness and complete acknowledged mandatory coverage as BR-3 specifies. All gates in one decision use one context and separately scoped views. A changed task/head/message/child/set/policy/permission/observation fence invalidates the bundle even if UI state did not change. No concatenation of results from incompatible contexts. A complete empty collection is positive coverage evidence with a collection-generation dependency; absence of records alone is not proof.
5. Context/read bytes and exact round requests expire 60 seconds from context creation, never extended by reads/retries. Lost/expired bytes abort; no live reconstruction. Retain copied cited evidence, dependencies and decision/closure receipts for audit lifetime under current read rights. Bulk cleanup cannot erase accepted evidence. Optional adapter-local immutable materialization is permitted only with BR-3's explicit bounded capture justification and current-version validation.

### 11.3 Round envelope and continuation

1. Grain creates bundle/evaluation IDs; round numbers are strictly consecutive, 0–15. Initial round has phase=initial, null previous_response_digest and continuation_state; subsequent phase=continue chains SHA-256 RFC 8785 digest of the accepted prior read_requests response and echoes its continuation unchanged. Request digest covers the entire canonical request except request_digest; response echoes it and every required identity/context field. Digests acknowledge exact delivered bytes, not authentication.
2. Pins, canonical args/digests, mode/state/expected revision, permission/scope, authority/contract/policy revisions, evidence_context, limits, fixed now and original deadline remain byte-equivalent across rounds. Only round/phase/prior digest, transient continuation, read_results and request digest change. The controller's private dependency ledger grows monotonically; it is not provider-authored state or an evolving context argument.
3. Non-final `kind=read_requests` carries only identity echoes, summary, 1–8 typed read_request objects and ≤16 KiB/depth-16 credential-free continuation. It MUST NOT carry a verdict, durable gate_state, work/actions/buttons/waits or lifecycle proposal. Grain executes no protected action and grants no progress/dispatch/subscriptions because of it. Only the internal driver advances. Round/read/checkpoint activity MUST NOT dirty evidence or feed trigger input.
4. Provider evaluation MUST be pure/replayable from this request and fixed clock, with no external read, callback, persistent session/cache/filesystem or affinity requirement. Bounded scratch memory is allowed. Continuation encodes a sufficient accumulator; overflow means final unknown/resource_limit, never omitted facts. Durable gate_state is unchanged on every round. Only validated non-error final candidates participate in state CAS; migrate/recover remain unknown-only/no work/actions/waits/buttons.

### 11.4 Read execution and completeness

1. Requests/results MUST validate against read-operations.schema.json and BR-2. Read IDs are unique within evaluation, independent of MCP transport IDs. Each operation/version/schema must be declared, registered, read-only and inside exact authorized subject/field scope. Args cannot select arbitrary tools, endpoints, credentials, shell/queries or mutations. Grain validates the whole non-final envelope before executing requests; per-read denials are safely delivered without existence disclosure.
2. Results are ordered to match requests. Successful page records, subject, full-args digest, collection generation, source timestamps and dependencies are checked and checkpointed. Unavailable results have no records/cursor; successful zero-row collections require authenticated complete-empty coverage. Required input/predicate insufficiency latches and independently prohibits met even if omitted by the evaluator. Citations must resolve to acknowledged delivered records/inline evidence; summaries and durable provider state are not authoritative evidence.
3. Lists use null initial cursor, registered stable order and authenticated context/scope/generation-bound next_cursor. Only a previously supplied next cursor may advance the same collection; one next page per collection per round. Independent reads can batch. Any generation/head/ACL change aborts stale_context. A returned terminal cursor alone does not prove completeness if coverage or a required domain is unavailable. Changing IDs/limit does not replenish budgets or bypass scope.
4. Same logical selection is delivered once except exact round retransmission. One later repeat gets request_loop without data, then final unknown/error is required; further repetition/continuation aborts. Exact pending adapter retry (at most once per logical read) is permitted only for a transient pre-delivery failure and charges the read-call budget. A delivered failure is not retried in this context. Stale_context/cursor_expired/revocation abort; no live replacement or silent negative fact.

### 11.5 Driver, retry and acceptance

| State | Event | Effect / next state |
|---|---|---|
| preparing | Authorize pins/core/prerequisites, persist bounded initial request | calling; no gate result |
| calling | Valid read_requests with remaining budgets | fulfilling; checkpoint reply only |
| fulfilling | Reauthorize and execute registered reads; record dependencies/results/next exact request | calling next round; no state CAS/action/dispatch |
| calling | Valid final | validating; no immediate success |
| validating | Core/dependencies/coverage/freshness/lease/state all current | atomic result/state/subscriptions/receipt, once |
| any | Stale/revoked/expired/canceled/limit/invalid | abort diagnostic, unchanged state, bounded backoff/restart |

1. One active driver lease per evaluation: five seconds, renewed every second, never beyond deadline. Takeover increments epoch; every read/checkpoint/final write CASes owner/context epochs. Persist pins/core/dependency vector, deadline/expiry, exact canonical request/accepted response/hash, read intents/results/counters and delivery versions before sending a subsequent round. No heartbeat/checkpoint is a source event.
2. Reserve attempts/retry slots and worst-case request+response bytes before each send; uncertain sends keep conservative reservations. Adapter attempts additionally reserve their call/page/byte/record budgets before reads. Bound input parsers before allocation; bounded wire is not sufficient without decoded-memory and per-installation concurrency admission. Counters/retention/deadlines survive crash and cannot reset through new read IDs.
3. Gate calls may retransmit identical stored bytes at most once per round/twice per evaluation for transient lost-reply/provider-crash failures, within original deadline/TTL. A gate retransmission does not execute reads again or charge unique data twice, but charges wire/retry counters. Provider returns same canonical response; conflicting duplicates abort, or quarantine a post-acceptance provider/result without undoing committed state/effects. Unique response/receipt keys and final expected-state CAS prevent double application.
4. An uncertain read is safe to repeat only because registry admission proves read-only execution, under BR-4's exact identity/version checks. Reuse saved bytes only with valid dependencies. Missing context/ledger/retained request, changed generation, revoked grant, unsupported pin or expiry aborts. A controller crash after final commit returns the existing receipt; provider crash is an exact round retry, not state reset/recovery.
5. Cancel/pause/contract or provider removal/lease loss/revocation/staleness cancels locally and fences late replies; no provider cancel callback is required. Controller errors project final/error with unchanged state and empty actions/work/waits/buttons, never accepted state. stale_context/state_conflict/cursor_expired require fresh context, not continuation. Retryable timeout/unavailable/provider_error remains subject to limits/backoff, never immediate agent work.
6. Coalesce one active bundle/dirty marker per task. Fresh starts are limited to three per rolling 60 seconds; churn then holds 60 seconds, ten held windows escalate. Automatic failed evaluations use persisted 30s–30m exponential backoff/jitter, blocker after five and hold after ten. Success/authorized resume may reset consecutive counters, never rolling rate limits. No page/read/round activity schedules another evaluation or autonomous task.

### 11.6 Unified bounds

All values are hard maxima across one evaluation and its retries, except explicitly per message/read. Request limits may be lowered before initial construction (retry limits may be zero). All canonical uncompressed UTF-8 JSON bytes count; JSON root depth for args/state/continuation/record data is ≤16, wire parser depth ≤32.

| Limit | Maximum |
|---|---|
| Total elapsed, including read/collection/construction/retry | 30,000 ms, one fixed bundle deadline |
| Rounds | 16, including initial |
| Inline context / records | 262,144 bytes / 100 |
| One read-result page / records | 131,072 bytes / 100 |
| Operation attempts including adapter retries / logical read requests | 64 / 64 |
| Reads requested per round | 8 |
| Aggregate retained/delivered page bytes / distinct records including inline | 8,388,608 bytes / 6,500 |
| Dependency ledger | 8,192 entries maximum; page metadata consumes the same byte budget |
| Durable state / continuation / canonical args | 16,384 bytes each, depth 16 |
| Gate response / whole round request | 262,144 / 2,097,152 bytes |
| All gate request+response wire bytes incl retransmissions | 25,165,824 bytes |
| Gate retransmissions per round / evaluation | 1 / 2 |
| Adapter transient retransmissions per logical read | 1; included in 64 operation attempts |
| Context/round/read-byte retention | 60,000 ms from creation, no extension |
| Domains / record kinds / declared operations | 32 / 64 / 32 |

Adapters must additionally enforce the same page/record/response bounds at their ingress/egress and bounded source scans, not allocate unbounded JSON then trim. Failed/denied/repeated logical reads consume request slots; adapter execution/retries consume call slots even without records. Exact gate retransmission reuses saved read_results/dependencies. Distinct page bytes/records count once; repeated wire bytes count every time. Sixteen rounds and one next page per collection can exhaust before 64 reads; ceilings are not a promise of unlimited collection traversal. Oversized necessary evidence means a narrower explicitly authorized contract/registered projection or unknown/resource_limit, never truncation/met.
