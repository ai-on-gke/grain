# Action gate bindings and protected operations

**Status:** proposed, normative; documentation/schema only, not implemented. No credential, grant, repository rule, runtime or task migration is authorized by this document. No follow-up tasks are filed by it.

**Extends:** [MCP gates](mcp-gates.spec.md), especially MGS-1 through MGS-5 and MGS-8. BCP 14 keywords apply. Stable requirements below use AGB IDs. [action-bindings.schema.json](action-bindings.schema.json) defines the control-plane objects and action evaluation profile; [examples](action-bindings.examples.json) are illustrative, never installed policy. JSON validation is followed by the semantic checks below.

## Purpose and authority {#AGB-1}

1. An **action gate binding** MUST explicitly attach required gate evaluators to a canonical protected operation, target selector and bounded resource/evidence scope. It is a guard aggregation purpose, distinct from task completion. Both purposes use pinned read-only MCP `gate_*` tools, the MGS result statuses, snapshot transport, state CAS, boundedness, waits and evidence rules. A `met` guard contributes a prerequisite; it does not grant caller authorization.
2. Grain MUST distinguish four concepts in contracts, APIs and UI: action guards (conditions before a mutation), required task completion obligations (outcomes after work), optional monitoring (no authority to block unless separately attached as a requirement), and existing concrete task goals/standing intent such as `pr-merged`, `base-green`, `person-closes`. No existing goal API is renamed or silently migrated. An evaluator attachment MAY serve multiple purposes only through separately recorded bindings and decision contexts; opaque state and result caches MUST remain isolated by purpose, binding and resource identity.
3. Example: merge requires current-head checks, accepted ordinary/security/path reviews and scoped operator approval when policy requires it. Task completion separately requires authoritative PR integration and successful required child outcomes. A merge binding MUST NOT require `integrated`/`pr-merged` for that same merge. Grain MUST reject direct and transitive prerequisite cycles, including a child outcome whose only producer is the blocked operation. Advisory monitoring and concrete task goals MUST NOT be imported as guards by name inference.
4. All Grain agent, person and automation requests for a protected operation MUST traverse one Grain action executor, including UI, CLI, MCP, API, queue, scheduled automation and provider-requested operations. Caller authorization and guard satisfaction MUST be separate decisions. Neither a satisfied guard, a callback/summary saying approved, cached success, nor a completion waiver grants mutation authority. An action override MUST NOT waive task completion obligations.

## Registry and non-optional policy resolution {#AGB-2}

1. The controller-owned registry MUST assign immutable `registry_id`, `revision`, canonical `action_id`, `action_version`, adapter pin, input-schema digest, effect class, supported resource kinds, authorization rule, minimum confirmation, lock domains, conditional execution and reconciliation strategy. IDs in examples (`change.merge`, `change.submit`, `deployment.promote`, `artifact.publish`) are proposed identities, not new deployed endpoints. Unknown action, version, resource kind or adapter MUST be refused, including an unclassified mutating tool.
2. Resource identity MUST use forge/authority plus immutable repository/resource IDs, kind and target ID; display names and URLs are aliases only. Repository renames, PR retargets, CL renumbering and deployment aliases MUST be resolved authoritatively before policy lookup. Registry aliases and different tool names with the same effect MUST normalize to the same operation family. Base-ref writes, merge API, auto-merge enablement, queue enrollment and provider-specific submission routes that can integrate a change MUST be covered or denied. A raw push to a protected base cannot be classified as an unguarded branch edit. Registry override eligibility MUST name fully qualified binding/gate identities, not colliding short IDs.
3. Grain MUST resolve applicable organization/authority, inherited repository, resource and attached task policies for **all callers**, including taskless operations. It MUST discover every active resource-attached task binding through a controller-maintained resource index, not just bindings on the caller's chosen task. Binding activation/deactivation and task-resource association are authorized conditional policy edits; task completion/deletion MUST NOT implicitly remove resource protection. A task-origin restriction persists until explicitly retired by its policy owner. Choosing another task, contract, alias, API or tool MUST NOT omit a guard.
4. Effective guards MUST be the conjunction/union of all applicable required sets. Gate identity is `(binding_id, binding_revision, gate_id)`; equal short IDs in different bindings MUST NOT overwrite one another. Identical pinned predicates MAY share evaluation work only after preserving all provenance and revalidating into each decision context. Conflicting predicates, incompatible pins, ambiguous selectors, incomplete discovery/indexes or inherited policy revisions MUST produce `policy_conflict`/`policy_unavailable`, never last-writer or weaker-policy wins. Only separately authorized controller policy edits can remove/relax inherited guards. Effective authorization requirements are also conjunctive; local policy cannot broaden registry/RBAC rights.
5. The executor MUST load an explicit policy coverage record for the resource and effect family. No matching required set is permitted only through an authorized, versioned **explicitly unguarded** policy decision; a missing binding, unsupported provider, failed discovery or empty accidental set MUST fail closed. Missing/read-denied/timed-out required providers stay required, unknown/error, with named remediation. Task lifecycle authority (legacy versus gates) MUST NOT change resource guard policy or exempt operations from it.

## Binding records and evaluator context {#AGB-3}

1. A `binding` MUST contain schema version, immutable ID/revision, controller policy provenance, registry identity/version, target selector, applicable caller kinds, optional origin task, required gate IDs, pinned evaluator attachments, bounded read/evidence selectors, preconditions, authorization requirements and invalidation keys. `caller_kinds` MUST cover person, agent and automation; the origin task is provenance, not a policy filter. In v1 selectors are exact resource IDs or all resources of a kind in one authority/repository (null `resource_id`); no provider-authored query language or arbitrary fetch URL is allowed. Missing paths needed for path review are unknown, not an empty diff.
2. The controller MUST validate that required gate IDs resolve uniquely to `required=true` attachments, all referenced pins/arguments/schema digests are valid, attachments share the binding revision, and every resource/evidence selector stays inside authorized scope. All listed attachments in this version are required; monitoring belongs in a separate purpose. Evidence/precondition predicates select controller-registered schemas, not executable expressions. The `head` field is the exact commit for a PR, reviewed snapshot for a CL, or immutable artifact digest for promotion/publication. Pinned example arguments `resource_source=action_context` and `head_source=action_context` select that bound context through the registered argument schema; they are not interpolated templates. Authorization names reference registered RBAC/delegation rules; they are not self-grants. Production digests MUST be computed over canonical resolved content with a collision-resistant hash; illustrative short digests are not deployable.
3. An `effective_policy` MUST preserve every source policy revision, binding revision, active contract revision and authority epoch, plus a canonical digest over the complete resolved guard manifest, pins, selectors, preconditions, registry and authorization requirements. The controller MUST generate it; a caller MUST NOT supply a favorable replacement. Policy edits MUST atomically invalidate pending decisions, approvals, buttons and overrides, and fence unstarted intents. Execution permits MUST be single-operation, bounded leases, not cached green badges.
4. `context` identifies operation, resolved action/registry version, exact resource/head/version/base, policy digest, evidence revision, snapshot, authorization revision, contract revisions and binding revisions. Approval evidence MUST bind the exact action/resource/head and applicable guard/policy scope with actor, authority, reason where required, expiry/revocation and immutable evidence version. Approval of H1 MUST NOT carry to H2. Evidence may persist historically, but the controller MUST verify applicability at each use.
5. Task #47 owns the snapshot transport and implementation-readiness work in wire protocol 2.0. This extension MUST preserve its Grain-driven rounds, copied immutable observation cut, declaration/record-schema pins, retained pages, reauthorization, request/response digest chain, cursors, counters, deadlines, replay/checkpoint and final-only commit rules. No callback handle, provider network fetch or second transport is introduced. The binding schema is a separate control-plane asset. Strict `wire.schema.json` v2 envelopes remain unchanged. Because v2 requires a task ID and cannot express taskless guard authority, the separate **action evaluation profile 3.0** adds required `action_context` to each request, nullable `task_id`, and `action_context_digest` to both disjoint `needs_data` and `final` responses. `guard_discovery` advertises outer protocol 3.0 with the unchanged snapshot version 2, `grain_rounds` transport and continuation version 1. Every other envelope field/conditional constraint is reused by reference from v2. Inner page requests, deliveries and page envelopes retain protocol 2.0; their request/evaluation/snapshot binding and budgets remain unchanged. This is an explicit semantic major envelope version, not a silently compatible v2 field. Pins MUST negotiate 3.0 before guard admission; v2 completion providers continue unchanged. Required providers without 3.0 block the action; no v2 fallback, synthetic task or null-to-ID coercion is allowed. Task #47's source is incorporated unchanged for transport; the action profile owns authority context only, with transport integration review still required before implementation.
6. Action-profile `contract_revision` is the controller-owned resolved guard-manifest revision; `authority_epoch` is the executor ownership epoch; `policy_revision` is the effective resource policy revision. `gate_id` is the fully qualified binding/gate identity; `task_id` is provenance or null, never the policy lookup key. The snapshot MUST include a registered `action_guard_context` record whose `data` validates as `context`, and all guard evidence from that same snapshot. Record version is the context digest. Context digest covers the entire context with `context_digest` omitted. Every continuation/final response MUST echo that digest in addition to the MGS fences. Controller validates it before any state/result commit. Tool discovery remains `gate_*`; no separate privileged evaluator protocol or write credential is introduced. All action-profile operation intents/transitions MUST use append-only `operation_event` records (including blocked and unknown attempts); success evidence uses `receipt`. Taskless records MUST NOT forge task-profile action events. Event identity/phase, canonical attempt digest, actor, context/decision references and lease epoch preserve the dispatch/recovery audit; receipt reference is required for succeeded.

## Executor transaction and failure semantics {#AGB-4}

1. `attempt` is an authenticated action request with canonical action/version, resolved target and expected head/resource version, expected policy digest, inputs, request ID and idempotency key; task ID MAY be null. The executor MUST derive the actor from authentication, check delegation, RBAC/grants, human-only restrictions and confirmation/reason, validate inputs and resolve policy itself. A claimed actor or expected digest is an expectation, never authority. Refuse unauthorized callers regardless of green guards, and audit refusal without leaking restricted evidence.
2. Grain MUST durably acquire a fenced lease and resource locks over the canonical target/effect, shared across tasks and callers. Locks MUST cover mutually exclusive branch edits/merges/submissions, guard-policy edits and conflicting promotions/publications. It MUST re-read authoritative resource identity, current head/base/version, permissions, policies and contracts, build one bounded snapshot and evaluate every required guard (or revalidate prior work into this exact context). Pending, unmet, unknown, error, invalid/stale/missing results or invalid overrides MUST block. Success from another head, binding, policy or context MUST NOT authorize execution.
3. Immediately before side effects, Grain MUST recheck lease ownership, authorization and all context fences and persist an immutable intent/outbox entry plus decision. Conditional expected-head/version execution MUST be used where available (GitHub merge uses expected SHA; a CL adapter must enforce the exact reviewed snapshot). A head move returns conflict without merging a newer head. Relevant policy, contract, permission, review dismissal, external resource change or evidence revision invalidates approval/decision even if the UI still displays green. Edits committed before intent dispatch MUST fence it. Policy edits racing an already dispatched external operation MUST mark it in flight/uncertain and reconcile actual outcome; they cannot retroactively prevent a completed side effect.
4. A Grain lock alone cannot exclude external writers or atomically freeze a forge's review/policy state. Where the provider cannot condition on **all required** versions, the adapter MUST document the remaining race and admit only a resource whose enforceable external exclusion/forge mechanism closes that race. Immediate re-read plus serialized Grain writers is necessary but insufficient for a universal prevention claim. If expected-version enforcement or external exclusion is inadequate for the promised guard, return `boundary_unavailable` and refuse enforced admission. Observation-only mode MAY report the gap; it MUST NOT claim enforcement. Provider merge queues/auto-merge deferred execution need an equally fenced final execution or admission MUST be refused; initial enqueue success is not merge success.
5. Provider evaluation timeout MUST yield a blocked provider error with persisted bounded retry/backoff and escalation; it MUST NOT dispatch an agent solely to retry, drop a guard, reuse stale met, or invoke a mutation. Evaluation results arriving after deadline, changed policy, changed head or lease loss MUST be rejected before state persistence. A known upstream refusal is failed, with structured remediation. No effect is reported as success until an authenticated authoritative receipt/current-state observation verifies it.
6. A mutation timeout, lost connection, crash after dispatch or lost lease with a possible side effect MUST record `unknown` and retain a resource hold pending reconciliation. A successor MUST inspect the durable operation ledger and query authoritative outcome before retry. Retry with the same idempotency key and identical canonical fingerprint MUST return/reconcile the existing operation; the same key with different action/head/inputs/policy MUST return `idempotency_conflict`. A new key MUST NOT bypass an uncertain operation's resource hold. If safely retryable with no side effect, recheck current authorization, policy and guards; never replay an old execution permit. Adapters without native idempotency MUST specify unique outcome identity and no-effect proof; absent that proof, hold for reasoned operator reconciliation instead of blindly repeating. A reconciled success is recorded once logically with immutable receipt provenance, even if callbacks duplicate or arrive out of order.
7. Successful execution MUST emit controller-authenticated `receipt` evidence containing exact action/registry, resource/head, before/after version, policy/context, actor, operation/idempotency identity and authoritative source evidence. Completion gates MAY consume this receipt or equivalent authenticated out-of-band observation, with source attribution; requested/started/unknown events and callback text are not success. A merge receipt alone does not satisfy required child outcomes. The executor MUST NOT close the task itself.
8. `decision` MUST return operation ID, separate authorization result, outcome, current context when available, guard results and scoped override references, structured blockers and remediation (registered action IDs/permissions/evidence references/refresh context), retryability and operation-status reference. Standard codes include `unauthorized`, `guard_unmet`, `provider_unavailable`, `stale_context`, `policy_conflict`, `policy_unavailable`, `boundary_unavailable`, `lease_lost`, `idempotency_conflict`, `outcome_unknown` and `upstream_refused`. Unknown/error block with remediation; no response text authorizes the next attempt. Transport maps unauthorized to 403, stale/conflict to 409, invalid input to 400/422 and unavailable provider/boundary to 503. Async/uncertain operations expose status, never a false success or an invitation to bypass.

## Enforceable boundary and admission {#AGB-5}

1. Enforcement MUST be established at the last Grain-controlled boundary before a protected effect, with privileged credentials available only to the executor's narrow adapter. Every agent-facing MCP tool, CLI, API proxy and automation path MUST route that effect through the executor or have no effective permission to perform it directly. Denying a friendly tool name is insufficient if curl, git, an alternate host, token mint/refresh, SSH, CI workflow, cloud IAM identity or direct provider tool can perform the same effect. Admission MUST inventory credential issuance, placements, refresh paths, daemon ambient credentials, proxy forwarding, automation identities and external integrations, with negative bypass probes and recorded ownership.
2. For GitHub integration the boundary MUST cover REST/GraphQL merge, auto-merge/queue mechanisms, direct protected-base ref updates via Git/REST/SSH and workflows/bots capable of those effects. A contents-write token commonly suffices for the merge API subject to repository rules; pull-request-write, token type or absence of administration permission MUST NOT be taken as proof it cannot merge. Fine-grained PAT/App permissions do not generally provide a standalone universal “push feature branches but never merge” permission. Named, personal, classic, installation, ambient and CI `GITHUB_TOKEN` credentials MUST be assessed by their effective rights on the actual repository, not their labels. A proxy retaining a broad secret server-side is useful only if it restricts protocol, target refs and all mutation routes and cannot be used as a generic authenticated tunnel.
3. For changelist submission the boundary MUST include `change.Provider.Submit`, any minted Submit grant, raw submit RPC/CLI, service account and provider-specific auto-submit. Submission authorization/approval is distinct from obtaining a provider credential. Require exact change identity and reviewed snapshot, fenced adapter execution, and authoritative submitted-target reconciliation, including renumbering. If a provider can only submit “latest” or the agent retains an unrestricted submit identity, enforced admission MUST be refused.
4. Initial additional operation families are deployment promotion and artifact publication. Promotion MUST bind environment/service and immutable artifact digest plus expected environment version; publication MUST bind registry/package/version and digest, distinguish immutable create from mutable tag movement and reconcile by digest. Cloud/GCP keys, signing credentials, registry/package tokens and refresh endpoints that permit direct deployment/upload/tag mutation are bypasses unless removed from admitted callers or constrained behind the action adapter. A signing receipt is not proof of publication. Each family needs its own registry adapter, authorization, locks, preconditions and idempotent reconciliation; a generic run-shell action MUST NOT substitute.
5. Repository/forge rules MAY strengthen the boundary after explicit separate authorization and verification of bypass lists, administrators, applications, ruleset exemptions, direct writes, queue behavior and required-check identity. They MUST NOT silently be claimed sufficient for arbitrary Grain guards, scoped operator approval or cross-system policy versions. This task changes no rules. Policy events and current-state reconciliation MUST detect externally performed actions, label them `external`, preserve actor/source and invalidate affected pending decisions. Grain can prevent actions through controlled routes and identities; it can only observe out-of-band people/credentials with independent rights. It MUST NOT describe those actions as prevented, Grain-approved or proof its guards passed.
6. Rollout MUST classify each resource/effect/caller cohort as `observe_only`, `enforced` or `refused`. `enforced` admission requires an operator-reviewed boundary inventory, exclusive executor control of relevant agent/automation credentials/routes, proven conditional/exclusion behavior, compatible providers, durable policy/ledger/fencing and tested recovery. Existing bypass-capable credentials in an admitted agent or automation cohort make enforced admission invalid; remain observation-only with **no Grain protected execution** or refuse/hold affected action requests until a separately authorized remediation removes/constrains the bypass. Legacy queue, Submit and automation mutation routes for that protected cohort MUST also be held or migrated; leaving them active is not observation-only isolation. Prompts and promises are not a mitigation. Independent human rights MAY remain only with an explicit documented out-of-band trust limit; a universal prevention claim requires excluding them too. Unsupported/stale boundary attestations MUST hold new protected actions. None of these future admission conditions authorizes live credential or policy modifications in this PR.

## Overrides and interface {#AGB-6}

1. An `override` MUST be a separately authorized, controller-owned, audited person action with non-whitespace reason, exact operation/action/version/resource/head, named guard references, policy/context digest, authorization revision, issuer, expiry, revocation and explicit invalidation keys. It MUST record the unmet/error guard dispositions as overridden, never met. Issuance MUST check distinct override authority (existing merge override retains `merge:force`) and registry eligibility; it MUST NOT grant the issuer/caller ordinary execution authority. Non-overridable guards, caller authorization, identity/precondition fences, lease ownership and uncertain-outcome holds MUST NOT be bypassed.
2. Overrides MUST invalidate on any scoped head/resource/base, guard/pin/args, binding/contract/policy, permission/authority, evidence, expiry or revocation change. They are single-operation exceptions; another operation/head needs new approval. Issuing an override changes evidence: Grain MUST create a new context and conditionally revalidate/rebind the explicit override before use, preserving the issue context for audit; it MUST NOT accept the stale issue digest as a current execution permit. An override covers only its named guards, all other required guards remain conjunctive. Broad “force everything” flags MUST be refused.
3. Completion waivers MUST NOT authorize protected actions; action overrides MUST NOT waive integration, child outcomes or any other completion obligation. Overriding a review prerequisite does not say a review succeeded. Completion may later be waived only through its separately authorized lifecycle process. A person without override authority can request a decision, not issue it by comment or button text.
4. UI/buttons MUST show canonical operation, exact head/resource, required guard results and source policy, caller authorization, blocked/unknown/overridden state, evidence freshness, remediation and pending/uncertain operation status. Show why an action is blocked and which authorized review, check, approval, permission or policy repair can resolve it. A button may request reevaluation/ordinary remediation or a separately confirmed scoped override if permitted; no “try another tool”/ungated fallback is allowed. Recheck every click server-side. New UI belongs in Angular; compatibility readers MUST not turn unknown into ready. UI/tool text is never an execution permit.

## Acceptance scenarios {#AGB-7}

These are required future implementation scenarios, not runtime tests implemented here. Schema/example checks cover shape only; they cannot prove credential isolation or conditional side effects.

| Scenario | Required result |
|---|---|
| End-to-end agent merge attempt | Agent with ordinary execution permission requests `change.merge` for PR 123/H1. Controller resolves inherited checks, ordinary/security/path review and scoped approval bindings. CI and approval are met, ordinary review is unmet: return `guard_unmet`, review evidence/remediation and no merge call. Record blocked attempt. After accepted review for H1 (all other current guards met), reevaluate one new context, acquire/recheck fenced lease and expected H1, write intent, conditionally merge and reconcile authoritative receipt. Completion consumes integration receipt but still waits for required child success. |
| Review arrives for H0 or head moves to H2 | H0 evidence cannot satisfy H1; H1 approval/review cannot permit H2. Stale response/state/button/override rejected; expected-head merge fails without merging H2. |
| Agent picks another task/tool/action alias, raw git base push or taskless API | Same canonical resource/effect resolves all active bindings, or route has no direct permission; no weaker task/alias path. Missing coverage/index fails closed. |
| Two tasks attach different guards to one PR | Union with qualified identities, one shared resource lock; neither task drops the other's guards. Incompatible predicates require authorized policy repair. |
| Missing provider, timeout, read denial or invalid schema/profile | Required guard stays unknown/error, structured remediation/backoff; zero mutation and no v2/null coercion or fallback. Independent task work may continue. |
| CI/review is dismissed, external base or policy changes during evaluation | Context invalidated; no state commit from stale result. Re-read/reevaluate; insufficient external atomicity yields boundary refusal. |
| Operator clicks after role revocation | Authorization refused even with met guards; no side effect. Approval is exact scope, not persistent permission. |
| Lease lost or concurrent edit/merge across tasks | Old owner fenced; serialize conflicting operations, re-read all versions and guards; only one logical operation. |
| Mutation succeeds then process crashes before receipt | Recover ledger, query forge, emit one reconciled receipt; same-key retry returns existing outcome, new key cannot bypass uncertain hold. |
| Mutation times out and source cannot prove success or no effect | `outcome_unknown`, resource held, structured operator reconciliation; never blind retry or success from callback text. |
| Duplicate callback or same key with changed inputs/head | Deduplicate authenticated observations; conflicting key rejected, no duplicated side effect or stale approval resurrection. |
| Guard override versus completion waiver | Exact-action/head/guard override needs distinct authority and invalidates on policy/head changes; completion waiver cannot merge. Merge override leaves required task children/outcomes intact. |
| Agent retains write PAT, submit token or registry refresh bypass | Refuse enforced admission; no Grain protected execution in observation-only cohort. Inventory records concrete missing boundary, never assumes write cannot merge. |
| Human independently merges on forge | Observe and attribute external integration; invalidate pending intents; do not report guard-authorized prevention. Completion may use authenticated integration fact under its own contract. |
| Queue or adapter cannot fence final execution | Hold/refuse enforced action, even if enqueue succeeded or immediate preflight was green. |
| Deployment version/tag changes or CL renumbers while request runs | Resolve immutable identity and versions, invalidate stale preflight; reconcile exact submitted/published/promoted outcome with provenance. |

## Migration responsibilities and unresolved blockers {#AGB-8}

The design's existing lifecycle migration remains separate. Resource action policy can govern legacy-completion and gate-completion tasks equally. Before protected-operation admission, implementation owners MUST inventory existing effective checks/review/Submit/bypass predicates and import them with provenance; no guard tightening/relaxation or token/rules change happens by documentation approval. Readers/schema negotiation precede writers; old daemons/adapters MUST be fenced out of enforced resources, never downgrade to an old ungated path. Rollback retains guard policy, evidence and holds; incompatible executors refuse mutations rather than reverting to direct merge.

| Responsibility | Required deliverable before enforced admission |
|---|---|
| Task #47 / snapshot transport owner | Preserve and implement snapshot/page resolution and round authorization, bounded evidence completeness and replay; review action-profile 3.0 composition and record registration with binding owner. No competing transport schema here. |
| Policy/registry owner | Stored versioned bindings, inherited coverage/index, alias/effect normalization, union/conflict rules, authorized conditional edits and cycle validation. |
| Authorization/security owner | Actual credential/tool/API/CI inventory per deployment and resource; effective permission probes; separately approved isolation/revocation/proxy/rule plan and boundary attestation. |
| Executor/forge and CL adapter owners | Unified route migration, durable intent/outbox, fenced cross-task locks/leases, exact-version conditional execution or proven exclusion, override eligibility and outcome reconciliation. |
| Evaluator owners | Pinned action-profile support, current-head check/review/approval predicates, scopes/state isolation and fail-closed unavailable behavior. |
| API/UI/lifecycle owners | Structured blocked/uncertain decisions, exact-scope override UX, authoritative receipt ingestion, separate completion aggregation and compatibility projections. |
| Release/operator owner | Verify admission scenarios, version negotiation, restart/retry/rollback fences, telemetry and explicit out-of-band trust limits before enabling a cohort. |

Remaining blockers are real: no general action executor/binding store or coverage index is implemented by this proposal; the current merge queue, UI submit and provider operations have separate paths; raw/minted/refreshed credentials can permit direct effects; GitHub lacks a universal branch-write-without-merge token scope; expected SHA alone cannot freeze every external review/policy condition; CL/promotion/publication adapters need proved conditional and reconciliation contracts; durable action ledger/lease/policy invalidation and profile 3.0 support must exist; per-deployment credential rights and human bypasses have not been audited live. Task #47's committed round protocol is preserved by dependency and byte comparison; direct task-record/message coordination was denied by this run's grants, so cross-owner implementation signoff is not claimed. No permission increase, automatic follow-up filing or implementation is requested by this PR.

### Documentation/schema validation

From the repository root, run `go test ./pkg/designdoc/...` and `git diff --check`. With Debian's `python3-jsonschema` installed, this offline check validates the schema assets and every example against its named definition; no endpoint or runtime validator is introduced:

```sh
python3 - <<'PY'
import json
from pathlib import Path
from jsonschema import Draft202012Validator, FormatChecker, RefResolver
root = Path("design/spec/mcp-gates").resolve()
schema = json.loads((root / "action-bindings.schema.json").read_text())
wire = json.loads((root / "wire.schema.json").read_text())
examples = json.loads((root / "action-bindings.examples.json").read_text())
for document in (schema, wire):
    Draft202012Validator.check_schema(document)
store = {schema["$id"]: schema, wire["$id"]: wire,
         (root / "wire.schema.json").as_uri(): wire,
         "https://grain.dev/spec/mcp-gates/wire.schema.json": wire}
def no_remote(uri):
    raise ValueError("Unexpected remote schema: " + uri)
resolver = RefResolver(base_uri=root.as_uri() + "/", referrer=schema,
                       store=store, handlers={"http": no_remote, "https": no_remote})
validator = Draft202012Validator({**schema, "$ref": "#/$defs/examples"},
                                 resolver=resolver, format_checker=FormatChecker())
validator.validate(examples)
print("Action schema and examples valid")
PY
```

The fixtures show four independent operation families, a resource-wide merge binding, task and taskless requests, a blocked merge followed by success after current-head review, an unused separately authorized override, a reconciled receipt and a separate non-final paged review request. `needs_data` is never guard success or an execution permit. The `enforced` boundary attestation in the fixture is hypothetical, not a statement about this deployment. Resource IDs, artifact/policy identities and boundary attestations are illustrative. The action request/context/argument/declaration hashes are computed over canonical fixture content; none attests a deployed provider or actual credential isolation. Shape validation cannot establish AGB semantic admission, live permission rights, CAS/lease fencing or external atomicity; those remain acceptance requirements above.
