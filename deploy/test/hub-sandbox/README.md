# Grain Registry — GCP Sandbox Test Deployment

Disposable, reproducible test/demo environment for `grain-registry` in a GCP
sandbox project (`deploy/test/hub-sandbox/`).

> **Scope note:** This directory provisions a lightweight single-project
> test/demo deployment for both **hosted GCE VM instances (`kind = instance`)**
> with nested virtualization (`/dev/kvm`) and **connected external `grain`
> daemons (`kind = connected`)** over `-hub-connect` outbound WebSocket mux
> tunnels, testing catalog discovery + subdomain routing. It intentionally keeps
> all resources minimal and self-contained so it does not pre-empt the
> production multi-replica deployment layout.

## Architecture

- **Registry Control Plane & Database (`instance.tf`, `files/startup.sh`)**: One
  private-IP `e2-small` Debian 12 GCE VM (no external IP, outbound egress via
  Cloud NAT to satisfy `constraints/compute.vmExternalIpAccess`) running:
  - `postgres:16-alpine` (pinned by digest) bound strictly to `127.0.0.1:5432` with persistent data
    on the VM boot disk (`/var/lib/grain-registry/pgdata`);
  - `grain-registry` built from `Dockerfile.hub` (`make image-registry`),
    configured with `compute.provider: "gce"` (N2 and C4 shapes across
    `us-central1-{a,b,c,f}`, nested virtualization enabled, user-configurable
    boot disk sizing `20–4000` GiB) and `config_repos.provider: "none"`,
    listening on `:8080` (IAP-protected control plane + `<entry>.<instance_domain>`
    router) and `:8081` (locked-down `PublicHandler`).
- **Shared Hosted-Instance PostgreSQL Pool (`sql.tf`, `files/sql-startup.sh`)**:
  One private-IP `e2-small` Debian 12 GCE VM (`<prefix>-sql`) running
  `postgres:16-alpine` on `5432/tcp` (firewall-restricted strictly to
  `<prefix>-vm` and `grain-instance`-tagged VMs on `<prefix>-net`), serving as
  `instance_sql.sql_instances` for per-instance database and credential
  provisioning (`grain_<entry>`). It serves TLS with a self-signed
  certificate; hosted VMs connect with `sslmode=require`, and so does the
  registry's own admin connection (`admin_dsn_template`), which carries the
  pool superuser password and each generated role password. Each hosted
  VM's database password (`cloud_sql_admin: false`) is generated by the
  registry and stored in Secret Manager as `grain-inst-<entry>-db-password`
  in the registry project — never in the VM's `grain-config` metadata — and
  `hosted-vm-startup.sh` reads it with the VM's own service account. When
  `bind_project_iam` is false (cross-project, or the default Compute Engine
  service account), the registry grants that account access to the one
  secret, which needs `secretmanager.secrets.setIamPolicy`
  (`roles/secretmanager.admin`, granted with `create_vm_service_account`;
  `roles/editor` alone does not include it).
- **Hosted GCE VM Instances (`files/hosted-vm-startup.sh`, `pkg/hub/providers/gcp`)**:
  Disposable `grain-vm-<entry>` VMs provisioned on demand from the registry UI
  or `grain hub create` with `enableNestedVirtualization: true` (`/dev/kvm`
  exposed to `grain-daemon` for Granule microVM sandboxes):
  - `n2-standard-2` / `c4-standard-2` (2 vCPUs, default 50 GiB `pd-balanced` / `hyperdisk-balanced`)
  - `n2-standard-4` (default) / `c4-standard-4` (4 vCPUs, default 100 GiB)
  - `n2-standard-8` / `c4-standard-8` (8 vCPUs, default 200 GiB)
  - `n2-standard-16` / `c4-standard-16` (16 vCPUs, default 400 GiB)
  - `n2-standard-64` (64 vCPUs, default 1,000 GiB `pd-balanced`)
- **Separate Hosted-VM Project (`hosted.tf`, `up.sh --hosted-project`)**:
  Hosted VMs (and their per-instance service accounts) can run in a project
  other than the registry's. `hosted.tf` then creates `<prefix>-hosted-net` /
  `<prefix>-hosted-subnet` (default `10.43.0.0/24`, Private Google Access,
  Cloud NAT) in that project, peers it bidirectionally with `<prefix>-net`, and
  adds CIDR-based firewall rules (peering cannot match source tags): registry VM
  IP -> `grain-instance` on `8080/tcp`, IAP -> `grain-instance` on `22/tcp`, and
  the hosted subnet -> `<prefix>-sql` on `5432/tcp`. Per-instance secrets stay in
  the registry project (`secrets.project`). The registry VM's service account
  needs `roles/compute.instanceAdmin.v1` and `roles/iam.serviceAccountAdmin`
  in the hosted project. It does not need project-wide
  `roles/iam.serviceAccountUser`: it grants itself that role on each
  per-instance account it creates (`compute.grant_self_act_as`, see
  `docs/hub.md`, "IAM the registry needs"). Pass
  `--manage-hosted-iam` when the deploying identity can set that project's IAM
  policy, otherwise have a project owner run:

  ```bash
  VM_SA="$(gcloud compute instances describe <prefix>-vm --zone us-central1-a \
    --project <registry-project> --format='value(serviceAccounts[0].email)')"
  for role in roles/compute.instanceAdmin.v1 roles/iam.serviceAccountAdmin; do
    gcloud projects add-iam-policy-binding <hosted-project> \
      --member="serviceAccount:${VM_SA}" --role="${role}" --condition=None
  done
  ```

  For example, to run the registry in `example-hub-project` and hosted VMs in
  `example-hosted-project`:

  ```bash
  ./deploy/test/hub-sandbox/up.sh \
    --project example-hub-project --admin owner@example.com \
    --hosted-project example-hosted-project \
    --hosted-credentials /path/to/example-hosted-project-key.json \
    --no-wait-cert
  ```
- **Signing Key (`kms.tf`)**: One Cloud KMS asymmetric signing key
  (`EC_SIGN_P256_SHA256`, `ASYMMETRIC_SIGN`) consumed by
  `pkg/hub/providers/gcp` to sign `X-Grain-Registry-Assertion` JWTs
  (`iss = "grain-registry"`) and publish `/.well-known/jwks.json`.
- **Routing, DNS & Admission (`lb.tf`)**: One `EXTERNAL_MANAGED` Global External
  Application Load Balancer on a reserved static IPv4 (`<a.b.c.d>`) using zero-DNS
  `sslip.io` hostnames:
  - Control plane: `https://<prefix>-<a-b-c-d>.sslip.io`
  - Routed entries: `https://<entry>.i-<prefix>-<a-b-c-d>.sslip.io`
  - **Backend 1 (`iap-bs` -> `:8080`, `timeout_sec = 86400`)**: Cloud IAP
    enabled (Google-managed OAuth client by default; a custom client via
    `configure-oauth.sh` when admitted users are outside the project's
    organization) with `roles/iap.httpsResourceAccessor`
    granted strictly to `--admin <owner@example.com>` (plus any `--extra-user`
    principals and the read-only verifier service account). Serves the registry
    UI/API (`/api/directory`, `/api/route`, `/api/entries`) and all
    `*.<instance_domain>` routed traffic.
  - **Backend 2 (`pub-bs` -> `:8081`, `timeout_sec = 86400`)**: IAP disabled;
    URL map routes strictly `/.well-known/jwks.json`, `/healthz`, and
    `X-Grain-Auth: token` (`grc_...` credential) calls on
    `/api/entries/<name>/heartbeat` and `/api/entries/<name>/connect`.
- **TLS Choice (`--tls-mode`, default `hybrid`)**:
  - `pkg/hub/api` refuses plain `http://` for non-loopback URLs.
  - In `hybrid` mode (default), the HTTPS proxy attaches:
    1. A **Google-managed SSL certificate** covering `<registry_host>` plus every
       pre-declared `--entry <name>` (`<name>.<instance_domain>`), giving
       browser-trusted TLS and zero custom CA flags on connected daemons once
       `ACTIVE` (~10–15 minutes);
    2. A **self-signed wildcard fallback certificate** covering
       `*.<instance_domain>` so dynamically added `<entry>.<instance_domain>`
       names still terminate TLS immediately (browser click-through, following
       the "TLS later" decision). `verify.sh` trusts this certificate from the
       `selfsigned_cert_pem` Terraform output rather than passing `curl -k`,
       because it sends the verifier service account's IAP bearer token.
  - Pass `--tls-mode self-signed` for instant provisioning without waiting for
    Google's ACME certificate issuance.

## Prerequisites

- Tools on the operator/deployer machine: `gcloud`, `terraform` (>= 1.5),
  `docker`, `jq`, `curl`, `openssl`.
- Active `gcloud` credentials with sandbox project permissions:
  - Minimum with a service-account deployer (`roles/editor` + IAP/KMS):
    `roles/editor`, `roles/iap.admin`, and `roles/cloudkms.admin` (plus
    `roles/iap.tunnelResourceAccessor` and `roles/compute.osAdminLogin` if
    running `register-entry.sh` over IAP SSH from the deployer machine). When
    `resourcemanager.projects.setIamPolicy` or `iam.serviceAccounts.getAccessToken` is
    absent, `up.sh` automatically reuses the project's default Compute Engine
    service account for the VM and the deployer's service account for IAP
    verification.
  - Or `roles/owner` (plus `roles/iap.tunnelResourceAccessor` for IAP SSH) on
    the target sandbox project.

## Quick Start

### 1. Bring up the test registry (`up.sh`)

```bash
./deploy/test/hub-sandbox/up.sh \
  --project my-gcp-sandbox \
  --admin alice@example.com \
  --entry alice
```

`up.sh` builds and pushes `Dockerfile.hub` to
`us-docker.pkg.dev/<project>/grain/grain-registry:<tag>`, creates a GCS state
bucket `gs://<project>-<prefix>-tfstate`, applies Terraform, reconciles the VM
over IAP SSH, waits for the Load Balancer's `/healthz` health checks and
Google-managed TLS, fetches `/.well-known/jwks.json` with TLS verified (never
`curl -k`), and registers the `alice` connected entry.

### 1a. Admitting users from another organization (custom OAuth client)

IAP starts on its Google-managed OAuth client, and that client only admits
users who belong to the project's own Google Cloud organization. If the
sandbox project sits in a different organization from the people you admit
(check with `gcloud projects get-ancestors <project>`), they get IAP's
"You don't have access" page even though `up.sh` granted them
`roles/iap.httpsResourceAccessor`. Service accounts in the project are not
affected, which is why `verify.sh` still passes.

The fix is a custom OAuth client. The IAP OAuth Admin API that could create
one was shut down in March 2026, so a project owner creates it by hand once:

1. Cloud Console > **Google Auth Platform > Branding**: set an app name and
   support email. Under **Audience** choose **External**, and keep Publishing
   status in **Testing** with only the admitted users added as test users (IAP
   requests only the non-sensitive `openid` and `email` scopes and still
   enforces `roles/iap.httpsResourceAccessor` at the edge).
2. **Google Auth Platform > Clients > Create client**, type **Web
   application**. Copy the client ID and secret; keep the secret out of the
   repository.
3. Apply it to the IAP backend. The secret is read from a hidden prompt (or
   `--client-secret-file`) and sent on stdin, never in argv:

   ```bash
   ./deploy/test/hub-sandbox/configure-oauth.sh \
     --project my-gcp-sandbox \
     --client-id 1234-abc.apps.googleusercontent.com
   ```

4. Edit the client and add the authorized redirect URI the script prints:
   `https://iap.googleapis.com/v1/oauth/clientIds/<CLIENT_ID>:handleRedirect`.

Terraform ignores the backend's OAuth client fields, so later `up.sh` runs
keep the custom client. `down.sh` deletes the backend service; the OAuth
client itself stays in the project until you delete it in the Console.
`configure-oauth.sh --project <id> --show` prints which client is active.

### 2. Provision a hosted GCE VM (`kind = instance`) or connect a `grain` daemon

**Hosted GCE VM (`kind = instance`, N2 / C4 with `/dev/kvm` nested virtualization):**

From the browser UI (`https://<registry_host>/new?kind=instance`), pick an N2 or
C4 shape (and optional custom boot disk size in GiB) and click **Create**, or
use the CLI:

```bash
grain hub create my-dev-vm \
  --hub-url "https://<registry_host>" \
  --shape n2-standard-4 \
  --disk-gb 150
```

When testing from a non-interactive service account (without a browser OAuth
session), use `instance-ctl.sh` over IAP SSH:

```bash
./deploy/test/hub-sandbox/instance-ctl.sh create \
  --project my-gcp-sandbox \
  --entry my-dev-vm \
  --owner alice@example.com \
  --shape n2-standard-4 \
  --disk-gb 150 \
  --allow-verifier-sa

./deploy/test/hub-sandbox/verify.sh \
  --project my-gcp-sandbox \
  --entry my-dev-vm

./deploy/test/hub-sandbox/instance-ctl.sh delete \
  --project my-gcp-sandbox \
  --entry my-dev-vm \
  --purge
```

**Connected external daemon (`kind = connected`) — Option A (`daemon-up.sh`):**

```bash
./deploy/test/hub-sandbox/daemon-up.sh \
  --project my-gcp-sandbox \
  --owner alice@example.com \
  --entry sandbox-daemon \
  --allow-principal user:colleague@example.com
```

`daemon-up.sh` builds a lightweight `grain-daemon` runtime image, creates a
private-IP `n2-standard-2` GCE VM (`--machine-type`; E2 types are refused
because they cannot run nested virtualization) on the sandbox subnet running `grain daemon` in
control-plane test mode (`-disable-native-sandboxes`) with
`GRAIN_HUB_CONNECT=true`, `GRAIN_HUB_ISSUER=grain-registry`,
`GRAIN_HUB_AUDIENCE=https://<entry>.<instance_domain>`,
`GRAIN_HUB_KEYS_URL=https://<registry_host>/.well-known/jwks.json`, and
`GRAIN_ALLOWED_PRINCIPALS`, registers the entry via `register-entry.sh`, runs
`grain hub register` on the VM, and verifies end-to-end tunnel routing via
`verify.sh`.

Tear down just the test daemon (keeping the sandbox registry running):

```bash
./deploy/test/hub-sandbox/daemon-down.sh \
  --project my-gcp-sandbox \
  --entry sandbox-daemon
```

**Option B — Connect an existing `setup.sh`-installed `grain-daemon.service` host:**

Using the `grc_...` registration token printed by `up.sh` (or minted later via
`register-entry.sh`):

```bash
sudo tee -a /etc/default/grain-daemon >/dev/null <<'EOF'
GRAIN_EXTRA_DOCKER_RUN_ARGS="-e GRAIN_HUB_CONNECT=true -e GRAIN_HUB_ISSUER=grain-registry -e GRAIN_HUB_AUDIENCE=https://<entry>.<instance_domain> -e GRAIN_HUB_KEYS_URL=https://<registry_host>/.well-known/jwks.json -e GRAIN_ALLOWED_PRINCIPALS=user:alice@example.com"
EOF
sudo systemctl restart grain-daemon.service

GRAIN_HUB_TOKEN="grc_<token>" grain hub register \
  -hub-url "https://<registry_host>" \
  "<entry>"
```

**To register another external daemon entry directly:**

```bash
./deploy/test/hub-sandbox/register-entry.sh \
  --project my-gcp-sandbox \
  --entry colleague \
  --owner alice@example.com \
  --allow-principal user:colleague@example.com
```

(If you also want a Google-managed browser-trusted TLS certificate for the new
entry's subdomain instead of the self-signed wildcard fallback, re-run `up.sh`
with `--entry alice --entry colleague:colleague@example.com` and
`--extra-user colleague@example.com`; each entry stays private to its owner
unless `--share-entries` or `register-entry.sh --allow-principal` is passed.)

### 3. Verify end-to-end (`verify.sh`)

```bash
./deploy/test/hub-sandbox/verify.sh \
  --project my-gcp-sandbox \
  --entry alice
```

Checks public JWKS, IAP unauthenticated rejection, `/api/directory` (live
heartbeat status, version, queue counts), `/api/route`, and an end-to-end HTTP
request routed over the outbound WebSocket mux tunnel to the connected daemon's
`registry` identity verifier.

### 4. Update the staging deployment for subsequent PRs

When developing changes in subsequent PRs (such as updating `cmd/grain-hub`,
`pkg/hub/...`, `ui-hub/`, or `pkg/daemon/...`), you can update the
running staging deployment in-place without destroying and recreating the load
balancer, IP address, TLS certificates, or database.

#### Updating the Registry VM (`grain-reg-vm`):

Run `up.sh` from your PR branch with `--no-wait-cert`:

```bash
./deploy/test/hub-sandbox/up.sh \
  --project my-gcp-sandbox \
  --admin alice@example.com \
  --no-wait-cert
```

This performs an in-place update:
1. Builds a fresh container image from `Dockerfile.hub` on the PR branch
   (which automatically compiles the `ui-hub/` SPA via `npm run build` and
   embeds the assets into `grain-registry`).
2. Pushes the image tag `us-docker.pkg.dev/<project>/grain/grain-registry:sandbox-<git-sha>`
   to Artifact Registry.
3. Applies Terraform in-place to update the `registry_image` metadata attribute
   on `grain-reg-vm`.
4. Executes `/usr/local/sbin/grain-registry-reconcile` over IAP SSH on `grain-reg-vm`,
   which pulls the new image and swaps the running container with zero downtime.
5. Verifies that the load balancer health checks report healthy.

> **Tip (Fast manual update without running Terraform):**
> If Terraform definitions (`*.tf`) were not changed, you can build/push the
> image and update instance metadata directly:
> ```bash
> # 1. Build and push image
> TAG="sandbox-$(git rev-parse --short HEAD)"
> docker build -f Dockerfile.hub -t "us-docker.pkg.dev/my-gcp-sandbox/grain/grain-registry:${TAG}" .
> docker push "us-docker.pkg.dev/my-gcp-sandbox/grain/grain-registry:${TAG}"
>
> # 2. Update image in VM metadata
> CURRENT_CFG="$(gcloud compute instances describe grain-reg-vm --project my-gcp-sandbox --zone us-central1-a --format='value(metadata.grain-registry-config)')"
> NEW_CFG="$(echo "${CURRENT_CFG}" | jq -c --arg img "us-docker.pkg.dev/my-gcp-sandbox/grain/grain-registry:${TAG}" '.registry_image = $img')"
> gcloud compute instances add-metadata grain-reg-vm --project my-gcp-sandbox --zone us-central1-a --metadata grain-registry-config="${NEW_CFG}"
>
> # 3. Trigger container restart on the VM
> gcloud compute ssh grain-reg-vm --project my-gcp-sandbox --zone us-central1-a --tunnel-through-iap --command "sudo /usr/local/sbin/grain-registry-reconcile"
> ```

#### Updating the Test Daemon VM (`grain-reg-daemon-sandbox-daemon`):

When testing daemon changes, tunnel client updates, or capability changes from a PR:

```bash
./deploy/test/hub-sandbox/daemon-up.sh \
  --project my-gcp-sandbox \
  --owner alice@example.com \
  --entry sandbox-daemon
```

This rebuilds the lightweight `grain-daemon` test runtime image, pushes it to
Artifact Registry, triggers a rolling update of the daemon container on the VM,
re-registers the entry, and runs `verify.sh`.

#### Verifying After an Update:

Run `verify.sh`:

```bash
./deploy/test/hub-sandbox/verify.sh \
  --project my-gcp-sandbox \
  --entry sandbox-daemon
```

Then visit `https://<registry_host>` in your browser to sign in via Cloud IAP
and interact with the updated Web UI and directory.

### 5. Tear down cleanly (`down.sh`)

```bash
./deploy/test/hub-sandbox/down.sh \
  --project my-gcp-sandbox
```

Destroys all Compute/LB/IAP/NAT/IAM resources via Terraform, schedules enabled
Cloud KMS signing key versions for destruction, deletes the sandbox image tags
pushed by `up.sh` (preserving any shared Artifact Registry repository), and
removes the GCS Terraform state bucket. Re-running `up.sh` afterwards
automatically re-imports the empty KMS key ring/key shell and creates a fresh
key version.

### Offline / Local Smoke Test

To test `registry.yaml` validation, `register-entry.sh` credential minting,
heartbeats, `/api/directory`, `/api/route`, and outbound-tunnel routing locally
without GCP credentials:

```bash
./deploy/test/hub-sandbox/local-smoke-test.sh
```
