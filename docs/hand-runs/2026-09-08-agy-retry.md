# Hand run: how long does agy retry a refused API call, and should grain bound it?

Task 419, the last of the three frameworks whose internal API retry this
repository had never measured.
`docs/hand-runs/2026-09-08-claude-resume.md` §5 raised the question, task
410 settled it for claude (ten internal attempts over 2m51s, left alone)
and task 418 settled it for codex (thirty requests over 25 seconds, left
alone). `pkg/agent/retry.go` carried a sentence saying agy's was still
unmeasured.

The same three questions: how many attempts does agy make against a
provider that refuses everything, over what wall clock, with what
backoff, and what does it finally emit; is there a
`CLAUDE_CODE_MAX_RETRIES` equivalent, and does it take 0; and given the
answers, should a grain run bound it.

The original 1.1.27 answer was much smaller than the other two frameworks
gave — **agy did not retry an HTTP refusal at all** — and asking it turned
up something larger that was not being asked about: **none of the
provider's own words survive into the stream grain reads**. The dated
remeasurement below records how 1.2.2 invalidated the retry premise and why
grain now bounds a model turn; §5's stream finding remains true, while the
later diagnostic capture lets production classify the hidden refusal.

## What was run, and against what

**A real binary, and no Gemini credential.** `agy 1.1.27`, fetched from
`https://antigravity.google/cli/install.sh` — on the day, the same
unpinned installer the Dockerfile and the live-agent workflow both ran, so
this was the agy a freshly built image would carry. That is no longer how
either of them installs it, and the difference is what the 2026-09-21 note
at the foot of this file is about: both now fetch one pinned release by
digest, and `.grain/workflows/live-agent.yml` derives the version it
installs from `ARG AGY_CLI_VERSION`. The provider is a stub of
Gemini's `generateContent` endpoint on loopback, pointed at through
`GOOGLE_GEMINI_BASE_URL`, which counts and timestamps every request and
answers each with a status and body of the probe's choosing. A real key
would prove nothing here: nobody can ask Google to be overloaded on
demand, and what is being counted is requests arriving.

This is the piece that did not exist before: `pkg/agent/claude`'s
measurement had a stub of `/v1/messages` and `pkg/agent/codex`'s had a
stub responses API, but agy's own live work
(`tests/e2e/live_resume_test.go`, `tests/e2e/live_hook_config_test.go`)
only ever pointed the binary at the real Google — so it could *resume* a
conversation but never be refused one, and every one of those tests needs
a credential nobody has created. `GOOGLE_GEMINI_BASE_URL` is what
makes a refusing stub possible, and it is agy's own: its changelog
introduces it beside `GEMINI_API_KEY` support, and `docs/agy-surface.md`
carries both entries (1.1.9 and the 1.1.11 fix for a session field a
custom endpoint may not support).

Every exec below used the argv `Framework.Run` builds and the private
HOME `writeAgyHome` writes — the MCP server, the permission rules and the
`modelProvider: "gemini"` that makes agy read `GEMINI_API_KEY` at all:

```
agy --input-format stream-json --output-format stream-json \
    --dangerously-skip-permissions --disable-slash-commands \
    --print-timeout 4m59s --model gemini-3.1-pro --effort high \
    --add-dir <sandbox>
```

with the user event on stdin. That is deliberate: the claude measurement
found its count was argv-dependent (ten attempts on the real argv, two on
a bare one), so a probe on a simplified command line measures nothing a
dispatch will see. §4 checks whether that holds for agy.

The refusal is Gemini's own: HTTP 503 with
`{"error":{"code":503,"message":"The model is overloaded. Please try
again later.","status":"UNAVAILABLE"}}` — the sentence and the status
`pkg/agent/antigravity/capacity.go` matches on.

## 1. One request, no retry, 0.15 seconds

```
exec finished in 2.04s (agy's own reported duration: 0.155s), exit status 1
requests: 2
  1  t=+0.00s  POST /v1beta/models/gemini-3.1-flash-lite-preview:streamGenerateContent?alt=sse
  2  t=+0.08s  POST /v1beta/models/gemini-3.1-pro-preview:streamGenerateContent?alt=sse
```

Two requests, but one turn: the flash-lite call is a side call agy makes
alongside every turn (it is made once per attempt, and it is retried in
lockstep with the model call in §3), and the `gemini-3.1-pro` call is the
turn itself. **The turn is attempted exactly once.** There is no ladder,
no backoff and nothing to wait through; the two seconds of wall clock are
agy starting up and forking its MCP child, not a retry.

The same run with `Retry-After: 2` and a `google.rpc.RetryInfo` detail of
`"retryDelay":"2s"` in the body: identical, one request. So the
changelog's "honoring the server-supplied retry delay instead of the
client's own backoff" (1.1.4) is not something the direct Gemini API route
does with an HTTP error status, whatever it does elsewhere.

Identical again for 429, 500, 502, 504 and 529: one model request each,
give up.

The stream, in full:

```json
{"event":"init","conversation_id":"4bc18dea-…","init":{"model":"gemini-3.1-pro","cwd":"…","tools":[…57 names…],"permission_mode":"always-proceed"}}
{"event":"step_update","step_update":{"step_index":0,"state":"DONE","step_type":"user_input"}}
{"event":"step_update","step_update":{"step_index":1,"state":"DONE","step_type":"agent_response","duration_seconds":0.00097}}
{"event":"step_update","step_update":{"step_index":2,"state":"DONE","step_type":"error_message"}}
{"event":"result","result":{"conversation_id":"4bc18dea-…","status":"ERROR","response":"","error":"Agent execution terminated due to error.","duration_seconds":0.1547,"num_turns":1,"usage":{…}}}
```

The exit status is 1, which is the half of the classification that does
hold up: `retryable` reads no marker at all off a run that succeeded. The
other half does not, and that is §5.

## 2. There is no `CLAUDE_CODE_MAX_RETRIES` equivalent, and nothing needing one

- `agy --help` lists 23 flags and no retry bound among them
  (`docs/agy-surface.md` has the whole list).
- The binary's own string table carries no environment variable name
  matching `*RETR*` at all. The only `max_retries` spellings in 210MB of
  binary are protobuf field tags of Google-internal services
  (`g3box_max_retries`), not anything a CLI user sets.
- `settings.json`, the file `writeAgyHome` already writes, documents no
  such key either.

Which is a different shape of answer from both of the others: claude has
a variable and grain declines to set it, codex has two config keys grain
cannot reach (§4 of the codex hand run), and agy has nothing to set
because there is no retry on this path to bound.

## 3. What agy *does* retry is the transport, three times over 2.4 seconds

The one ladder that exists. A provider that accepts the connection and
hangs up without a response, and a base URL with nothing listening on it,
both produce:

```
3 attempts, 5 requests, agy's reported duration 2.39s, exit status 1
  attempt 1  t=+0.00s   (flash-lite, then pro)
  attempt 2  t=+1.05s   (flash-lite, then pro)
  attempt 3  t=+2.38s   (pro)
{"event":"result","result":{"status":"ERROR","error":"There was a network issue connecting to the server, please try again.",…}}
```

Three attempts, gaps of roughly 1.0s and 1.3s. Two and a half seconds,
against claude's 2m51s and codex's 25s — and it is reached only when the
refusal is a transport fault rather than an HTTP status, which is the
less common way a provider says "not right now".

Worth naming for what it is not: this is not a capacity backoff. "There
was a network issue connecting to the server, please try again." matches
none of grain's markers either, so it lands in the same place §5
describes.

## 4. The count is not argv-dependent, unlike claude's

The same stub against a bare `agy --input-format stream-json
--output-format stream-json` — no `--model`, no `--effort`, no
`--add-dir`, and a hand-written HOME with nothing in it but
`modelProvider: "gemini"`:

```
1 model request, exec finished in 1.5s
```

Identical. Worth having measured rather than assumed, since claude's did
depend on the argv, but it stands to reason here: there is no ladder for
an argv to lengthen.

## 5. What this found that *is* worth acting on: the provider's words never reach the stream

Not the question asked, and much the most operationally interesting thing
here.

agy knows exactly what happened. Its own log file (`--log-file`) carries:

```
E …  errorreport.go:224] agent executor error: calling model: Error 503, Message: The model is overloaded. Please try again later., Status: UNAVAILABLE, Details: []
E …  errorreport.go:224] calling model: Error 503, Message: The model is overloaded. Please try again later., Status: UNAVAILABLE, Details: []
E …  session.go:226] Print mode: run ended with error and no response: Agent execution terminated due to error.
```

What reaches stdout — the stream-json this package parses, and the only
place `pkg/agent/antigravity` looks — is the last of those three lines and
nothing else. `"error":"Agent execution terminated due to error."` is what
`parseEvents` puts in `resultText`; the `error_message` step carries no
text at all (and `applyStep` does not read that step type in any case);
stderr is empty; the subprocess error is a bare `exit status 1`.

Run through this package's own classifiers, that text yields:

| classifier | result |
| --- | --- |
| `capacityFailure` | `nil` |
| `usageLimitFailure` | `nil` |
| `retryable` | `false` |

So, as things stand on agy 1.1.27:

- **`resume.go`'s retry loop never fires for a Gemini overload.** The
  whole point of it — hold the sandbox, exec agy again on the same
  conversation — is reached only through `capacityFailure`, and a real
  refusal does not reach it. A grain run refused by Gemini fails once and
  is over.
- **`orchestrator.RunDispatch` records it as an ordinary failed run**, not
  `model.CapacityOutcome`. It counts against `task_streak`, and five in a
  row retire a task that was never wrong. This is the exact failure
  `capacity.go`'s own header says the package exists to prevent.
- **A quota refusal is invisible too, and that one costs more.** The same
  probe with a 429 / `RESOURCE_EXHAUSTED` body, worded the way Google
  words a quota refusal (`"You exceeded your current quota…"` with a
  `RetryInfo` of `"retryDelay":"56s"`), produces the identical
  `"Agent execution terminated due to error."`. So `usagelimit.go` matches
  nothing, `agent.UsageLimitError` is never returned, and dispatch does
  not pause — it sends the next task straight at the same wall.

`capacity.go`'s and `usagelimit.go`'s marker lists are careful, well
argued and, on this route, matched against text that does not exist. The
tests behind them (`capacity_test.go`, `usagelimit_test.go`) assert
against streams this repository wrote for itself, which is precisely the
failure mode `.grain/workflows/live-agent.yml`'s header describes: a
faithful fake of our own beliefs.

Two caveats, stated so the follow-up is scoped honestly:

- This is the **direct Gemini API route** — `modelProvider: "gemini"` plus
  `GEMINI_API_KEY`, which is what `writeAgyHome` configures whenever a
  deployment has a key, and therefore what a dispatch does. A deployment
  with no key configured leaves agy on its own OAuth session against
  Antigravity's backend, which this probe cannot reach and which may
  render a refusal differently.
- Fixing it is not a marker to add. There is no text to match. The
  options are to pass `--log-file` into the private HOME and read the
  refusal out of it (a real change: `agyArgs`, plus a third input to both
  classifiers, plus owning the format of somebody else's log), or to
  treat exit-1-with-no-response as a soft capacity refusal (which would
  read every ordinary agent failure as the provider's fault — the
  direction `capacity.go` deliberately refuses to go for "internal"). That
  is a design decision with real downside either way, so it is filed as
  its own task rather than smuggled into this one.

## The original 1.1.27 decision

At this measurement, **grain did not bound agy's internal retry**, and
`pkg/agent/antigravity/resume.go`'s header carries the reasoning. It is
the same answer claude and codex got, reached by a shorter road:

- There is nothing to bound. One request on an HTTP refusal, three over
  2.4 seconds on a transport fault; no flag, no environment variable and
  no setting that changes either (§2, §3).
- Nor is there anything to want bounded. The complaint that made the
  question worth asking for claude — six quiet minutes inside
  `Framework.Run` with nothing on the transcript — does not arise: agy's
  contribution to a refused run's wall clock is a fifth of a second, and
  every second a refused agy run spends is `agent.RetryPolicy`'s own 30
  and 60, which write notes to the transcript as they go.
- And it cuts the other way from claude's argument. claude's ladder
  absorbs short outages so that grain's budget of two is kept for real
  ones; agy absorbs nothing, so `agent.DefaultTransientRetries` is the
  *only* backoff an agy run has. That is an argument for leaving grain's
  own retry exactly as generous as it is, not for adding to agy's.

Which also settles the last of the three sentences: `pkg/agent/retry.go`
said the frameworks' internal retries were unmeasured apart from claude's
and codex's, and now says what all three do.

## What was written down from the 1.1.27 run

- `pkg/agent/antigravity/live_retry_stub_test.go`:
  `TestLiveAgyRetriesARefusedTurnItself`, §1 as a probe that needs the
  binary and no credential — the refusing Gemini stub this task had to
  stand up, plus the argv and private HOME a dispatch builds. It asserts
  the shape the decision depends on rather than the numbers, which are a
  vendor's: that the exec fails, that the stub was reached at all (an agy
  that stopped honouring `GOOGLE_GEMINI_BASE_URL` would make the whole
  probe silently vacuous), and that it gives up inside 100 seconds — the
  same ceiling agent/codex uses, and the number that would have to move
  before the decision above was worth re-reading. The 1.2.2 run below is
  exactly the change that tripped it.
- `pkg/agent/antigravity/live_retry_stub_test.go`:
  `TestLiveAgyLosesTheProvidersRefusalText`, §5 as a probe that reports.
  It skips, loudly and with the version in the message, for as long as the

- `.grain/workflows/live-agent.yml`: both of them, run ahead of the
  credential gate, so an agy version bump that changes any of this says so
  the first night — which mattered more here than for the other two,

- `pkg/agent/antigravity/resume.go`'s header: the decision and §§1-3

- `pkg/agent/antigravity/antigravity_test.go`:

## Remeasured 2026-09-14: 1.2.2 retries beyond nine minutes

The unpinned installer now serves `agy 1.2.2`, and the premise above no
longer holds. (This is the release the measurement was taken from, and the
one the image has pinned since 2026-09-21; for the week in between it did
not, which is what the note at the foot of this file records.) The same probe, still using the real dispatch argv and private
HOME against the same persistent Gemini 503, was allowed to run for nine
minutes. It had not returned when the probe cancelled it. A final
production-argv capture (including `--log-file`) observed these eleven
requests in seven minutes:

| request | elapsed |
| ---: | ---: |
| 1 | 0.588s |
| 2 | 0.646s |
| 3 | 1.590s |
| 4 | 3.517s |
| 5 | 4.653s |
| 6 | 10.043s |
| 7 | 25.465s |
| 8 | 49.061s |
| 9 | 1m37.578s |
| 10 | 3m27.946s |
| 11 | 6m49.353s |

The extra early calls are the conversation-title side route. agy's
diagnostic identifies main model attempts 1 through 8 and the delay chosen
after each refusal: **4s, 5.382s, 15.411s, 23.587s, 48.508s, 1m50.354s,
3m21.384s, then 2m25.586s**. That last sleep puts attempt 9 beyond nine
minutes. The values are jittered — the separate nine-minute capture placed
attempts 7 and 8 at 3m14s and 6m30s — but the shape and operational result
are stable.

This is a lower-bound schedule, not a claim that attempt 9 is the last:
there was still no terminal result and none of the provider's refusal text
on stdout when either guard fired. That last fact preserves §5's finding.
Production grain can classify the refusal only because the later diagnostic
work described below reads agy's private log.

### Revised decision: bound a model turn at 100 seconds

Grain now cancels an Antigravity model turn after 100 seconds. That is the
ceiling the original live probe deliberately recorded as the point where a
vendor ladder had become minutes rather than runner noise; 1.2.2 crossed
it by a wide margin. agy still exposes no retry flag, environment variable
or settings key, so there is no narrower vendor control to set.

The deadline is semantic rather than an exec-wide timeout:

- It begins with an attempt and again when the last active tool finishes,
  and ends when the next `agent_response` completes.
- It is paused for tool calls. A deliberate `wait_for_checks` or
  `chat` wait therefore keeps the longer deadline owned by that grain
  tool and is not mistaken for a stuck model.
- It cancels the attempt's process group rather than lowering
  `--print-timeout`. The latter caps the whole multi-turn run and would
  revive the old bug where useful work died five minutes in.
- Once agy stops, grain reads the complete private diagnostic records
  already written for the refused requests. A 503 still becomes a
  capacity outcome and can enter the visible 30/60-second in-run retry;
  a quota refusal still becomes a usage-limit pause. With no refusal in
  the diagnostic, the run reports the 100-second model-turn deadline and
  spends no capacity retry.

The live probe now observes seven minutes of the vendor ladder, timestamps
every request, and requires at least ten requests plus expiry of its own
guard. Its schedule and refusal-text tests share that one exec, so the
second finding no longer starts another seven-minute ladder and collides
with the package's shared timeout. A third live probe drives Framework.Run; against 1.2.2 it cancelled at
1m40.120s after nine provider requests, and the private diagnostic still
produced a capacity outcome. Deterministic tests also cover tool-call
pausing, retry classification and timer retargeting.

## Follow-up: grain now classifies the private diagnostic

The later diagnostic capture work supplied the safe mechanics option 1
needed: a fresh 0600 log for each exec, inside its private HOME, with only
complete records from a bounded tail retained after credential redaction.
The classifiers now receive that current exec's excerpt alongside its
terminal stream and subprocess error. An overload therefore enters the
bounded in-run retry loop, while RESOURCE_EXHAUSTED returns
`agent.UsageLimitError` with Gemini's retry delay.

Diagnostics from earlier attempts remain in the transcript for an
operator, but cannot classify a later attempt. Grain also does not infer
anything from the generic terminal sentence or exit status alone, so an
ordinary agent failure remains an ordinary failure.

## 2026-09-21: the probes and the pinned binary had come apart

The remeasurement above was taken from the unpinned installer, which was
serving 1.2.2 by then. The image was not: `ARG AGY_CLI_VERSION` said
`1.1.27` and had said so since the CLIs were first pinned. Between those
two dates the live-agent workflow also moved from `.github/workflows/` to
`.grain/workflows/`, and the new copy installs the pinned release by
digest rather than running the installer. So the nightly ran 1.1.27
against probes written for 1.2.2, and failed every firing it produced a
verdict for:

- `TestLiveAgyRetriesARefusedTurnItself`: two requests in 1.805s, an empty
  bounded diagnostic, and the `probe.requests < 10` guard reporting that
  "its retry schedule changed". No schedule had changed. This is 1.1.27
  doing exactly what §1 of this document recorded it doing — not retrying
  an HTTP refusal at all — measured by a test that no longer expected it.
- `TestLiveAgyBoundsARefusedTurn`: no capacity classification, because
  with no retry there is no 503 in the private diagnostic for the
  classifier to read.

The pin has since moved to 1.2.2 (build `6061403484848128`, both digests
verified against the vendor artefact), so the deployment now ships the
release whose ladder `modelTurnTimeout` was sized for, and the nightly
measures the binary a dispatch runs.

What was missing was anything joining the two. `live_retry_stub_test.go`
now names the release its numbers came from in one constant,
`measuredAgyVersion`, and two guards hang off it:

- `TestMeasuredAgyIsTheAgyTheImagePins` compares that constant with the
  Dockerfile ARG. It needs no agy, so a commit that moves the pin fails in
  the ordinary package suite, beside the bump, rather than a week later in
  a nightly.
- `requireMeasuredAgy` compares it with the binary the live probes are
  about to exec, which is the case the unit test cannot see: a
  self-updated agy, a `GRAIN_AGY_PATH` pointing elsewhere, an install step
  that did not do what it said. The nightly fails naming both versions;
  a developer with some other agy on `$PATH` gets a skip that says which.

Both failure messages ask for a re-measurement rather than an edit. The
schedule in this document is what sized `modelTurnTimeout` and what
justified reading agy's private diagnostic at all, so a pin bump is the
moment to rerun the probe and reconsider both — on 1.1.27 neither would
have been needed, and nothing but this file would have said so.
