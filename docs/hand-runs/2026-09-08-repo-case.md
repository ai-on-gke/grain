# Hand run: `grain repo-case` now that it visits every table

`docs/test-plans/2026-09-06.md` section 5 asks for `grain repo-case` to
be run against a copy of a **real** deployment's data directory: report,
read the report, `-apply`, start a daemon on the copy, and then export
the state repository and read the diff -- the step the plan said was
worth the most, because "a rewrite of every table is a settings history
nobody can read afterwards".

`docs/hand-runs/2026-09-07-repo-case.md` could not get at real data and
said so. Neither could this run, for the same reason and with the same
error message, so **step 5 is still owed**; what is below is what could
be established without it, against the two fixes that run asked for.

## What was run, and what was not

**Still not run against a real deployment's data.** This sandbox has no
copy of any deployment's data directory. The state repository this
deployment's settings live in is refused to it exactly as before --
`bwsalmon/grain-home is not in scope for this sandbox`, 403, from the
only git host the sandbox can reach -- and there is no attachment, no
mount and no other route to a database with a year of real rows in it.
Arranging one is a thing a human has to do before this can be finished;
see "Still owed" at the bottom for what it would take and what it would
answer.

**Why it was worth running anyway.** Since the 2026-09-07 run, two of
its findings have been fixed, and both fixes change the answer that run
gave:

* `grain/task-314` added the eight repo-keyed tables the reconciliation
  was walking past -- `task_write`, `schedule_write`, `template_write`,
  `memory`, `memory_document`, `release_schedule`, `release_iteration`
  and **`task_run`**.
* the settings-import fix made `-apply` refuse while the state
  repository holds a commit this host has not loaded, and export what it
  wrote before it returns.

`task_run` is the table that makes the plan's own worry live again: it
is 302 MB of the 321 MB dump here, and the 2026-09-07 run's "the diff is
boring" verdict rested on it not being in the commit at all. The export
step therefore had to be measured again, and so did `-apply`'s cost, and
the new refusals, and whether a reconciliation now survives a start.

**What it was run against.** A synthetic store of the same shape as the
2026-09-07 one, extended to hold divergent rows in all eight of the new
tables, and built through `pkg/model`'s own API so every row is one
grain itself wrote (`ui.Client` is the one path it cannot use:
`canonicalRepo` there is precisely the code that stops a divergent
spelling from being stored today). The harness is beside this file.

* 6,000 tasks over a year, 7,500 runs with real `transcript` and
  `prompt` columns, 1,000 comments, 260 branches, 40 releases with their
  candidates, 12 schedules, 6 templates, 3 release trains with 4
  iterations each, per-repo configuration and a qualification plan;
* 299 MB on disk, 15,213 rows across the 24 repo-keyed tables;
* the five repositories are this deployment's own. 240 tasks are stored
  under `bwsalmon/Grain` and 68 under `BWSalmon/kontur`; 144 tasks read
  `bwsalmon/grain` under both spellings; and one repository,
  `Someone-Else/Unrelated`, is named nowhere in the allowlist and is
  there to be left alone.

Every number below is from a copy of that store, with a real bare state
repository behind it and a real `grain daemon` on top of it, on this
sandbox's 3 vCPU.

## 0. What it costs now

| step | 2026-09-07 | today |
| --- | --- | --- |
| copy the data directory (299 MB) | -- | 0.45 s |
| `grain state adopt` (first, whole export) | 27 s | 14.0 s |
| `grain repo-case` (report) | 0.32 s | 0.64 s |
| `grain repo-case -apply` | 0.39 s | **20.1 s** |
| `grain state sync` afterwards | 20 s | not needed: `-apply` does it |

The rewrite itself is still a fraction of a second -- it is one `UPDATE`
per (table, spelling) plus a row per merge, so it tracks the number of
spellings and not the number of rows. What `-apply` now costs is the
export it does itself, and that is a whole-dump export: `SyncNoted`
passes `forceChurn`, so `task_run.json`, `task_observation.json`,
`lease.json` and the CI tables are written out beside the settings
tables whether or not the reconciliation touched them. 20 seconds for
321 MB.

That is worth saying in an operator's terms: **`repo-case -apply` is no
longer a sub-second command that edits a database. It is an export**,
and on a deployment several times this size it will take several times
as long. It still needs the daemon stopped for the whole of it.

## 1. The report, with the eight new tables in it

982 rows across 24 report lines, one per (table, divergent
spelling) pair. The eight tables
`grain/task-314` added are all there, and this is the half of the report
that did not exist on 2026-09-07:

```
task_write:        BWSalmon/kontur -> bwsalmon/kontur,  5 rewritten
task_write:        bwsalmon/Grain  -> bwsalmon/grain,  20 rewritten, 15 merged
task_run:          BWSalmon/kontur -> bwsalmon/kontur,  70 rewritten
task_run:          bwsalmon/Grain  -> bwsalmon/grain,  229 rewritten
schedule_write:    bwsalmon/Grain  -> bwsalmon/grain,   1 rewritten,  1 merged
template_write:    bwsalmon/Grain  -> bwsalmon/grain,   1 rewritten
release_schedule:  bwsalmon/Grain  -> bwsalmon/grain,   1 rewritten
release_iteration: bwsalmon/Grain  -> bwsalmon/grain,   4 rewritten
memory:            BWSalmon/kontur -> bwsalmon/kontur,  1 rewritten
memory:            bwsalmon/Grain  -> bwsalmon/grain,   0 rewritten,  1 merged
memory_document:   bwsalmon/Grain  -> bwsalmon/grain,   0 rewritten,  1 merged
```

Every count was checked against the store rather than read off the
report, by a census that walks `model.RepoCaseTables()` itself and
groups each table by its own repo columns (`handrun -mode census`), so a
table the list gains is a table the census counts without being edited.
All 24 lines match it, `Someone-Else/Unrelated` appears in none of them,
and its rows -- 61 tasks, 66 read-scope rows, a `repo_config` and a
memory -- were untouched by the apply.

The report on the reconciled store afterwards says `every repo in this
store is already spelled that way: nothing to do`, which on 2026-09-07
it also said while six tables still held divergent rows. It is now true.

## 2. The export, which was the step the plan cared about

`-apply` committed and pushed one commit, and it is readable:

```
 tables/branch.json               |   80 +--
 tables/memory.json               |   16 +-
 tables/memory_document.json      |   10 -
 tables/qualification_config.json |    6 -
 tables/qualification_item.json   |   11 +-
 tables/release.json              |   12 +-
 tables/release_candidate.json    |   12 +-
 tables/release_iteration.json    |    8 +-
 tables/release_schedule.json     |    2 +-
 tables/repo_config.json          |   11 +-
 tables/schedule.json             |    4 +-
 tables/schedule_read.json        |    5 -
 tables/schedule_write.json       |    8 +-
 tables/task.json                 |  616 +++++++++---------
 tables/task_read.json            | 1302 ++++++-----------------------
 tables/task_run.json             |  598 ++++++++---------
 tables/task_write.json           |  140 +---
 tables/template.json             |    2 +-
 tables/template_write.json       |    2 +-
 19 files changed, 993 insertions(+), 1852 deletions(-)
```

**`tables/task_run.json` is in the commit now, and that is fine.** It is
302 MB and 135,146 lines, and 598 of those lines changed: git diffs by
line, so the largest file in the dump contributes a per-row diff exactly
like every other file, and a reviewer reads

```
     "target_owner": "bwsalmon",
-    "target_name": "Grain",
+    "target_name": "grain",
```

598 times in that file, the same way `task.json`'s own 616 lines read.
The plan's "a settings history nobody can read afterwards" does not
happen. What does happen is in bytes
rather than in lines:

* after `adopt`, the bare repository held 5.2 MB of loose objects for a
  321 MB dump;
* the reconciliation commit took it to 11 MB, because a file that
  changed by one line is stored as a whole new blob;
* `git gc --aggressive` took the whole repository to 3.1 MB, deltaing
  the two copies of `task_run.json` back together.

Driven separately on a store where **exactly one** row in the whole
database was divergent, and it a `task_run` row, the commit is

```
 tables/task_run.json | 2 +-
 1 file changed, 1 insertion(+), 1 deletion(-)
```

and it cost the same fresh blob (about 4.6 MB compressed here) as the
299-row one did. So the cost is per-commit-that-touches-the-file, not
per-row -- which is exactly the cost of any routine churn export the
daemon makes on its own clock, and the repository already carries one of
those per `ChurnInterval`. A reconciliation adds one. That is the whole
of it.

Two caveats on those byte figures, because they are the ones a real
deployment will not reproduce. This harness's transcripts are synthetic
and repetitive, so 302 MB compresses to about 4.6 MB; real transcripts
will not compress nearly that well, and both the push and the loose
objects scale with that. And an operator who never runs `git gc` on the
state repository keeps every copy.

## 3. The daemon on the reconciled copy, and the settings import

A real `grain daemon` was started on the reconciled copy, left running
for a start's worth of work, and stopped. Afterwards `repo-case` reports
nothing to do and the census finds no divergent spelling in any of the
24 tables. This is the case the 2026-09-07 run's finding 2 was about,
and the fix holds at this scale.

The refusal that fix added was driven end to end as well, on a third
copy, in the order that produces the failure:

1. adopt a state repository, seeded from the store, divergent rows and
   all;
2. somebody merges an ordinary settings change into it (a
   deployment-wide prompt extension);
3. `grain repo-case -apply`.

It refuses, exits 1, and writes nothing -- the census afterwards shows
all 982 divergent rows still exactly where they were:

```
this deployment's state repository holds a commit this host has not loaded,
on its remote:
  ...
The repository is authoritative for the settings tables -- repo_config, the
qualification plan, templates -- so the next start would import that commit's
version of them over these changes, leaving half of this rewrite in place and
putting the other half back. Nothing has been written.

Start the daemon once so it takes that commit up, stop it again, and run this
with -apply.
```

Following that instruction works: the start imports the merged change,
the `-apply` after it succeeds and exports, the merged prompt extension
is still in the dump afterwards, and a *second* start leaves the store
reconciled. The half-reconciled deployment the earlier run produced --
`repo_config` and the templates back in the old spelling while `task`
and `branch` stayed rewritten, and a template filing new tasks under the
old spelling -- does not happen any more.

### One residue: the way out of the refusal mints a few more divergent rows

The report before the start named 982 rows. The `-apply` after it
rewrote **985**.

The three extra rows are the start's own work: the two schedules stored
under `bwsalmon/Grain` came due while the daemon was up and filed two
tasks under that spelling, one of which also carried a divergent
read-scope row. Nothing is wrong with that -- a schedule stored in the
old spelling files tasks in the old spelling, which is the condition the
whole command exists to end -- and it is self-correcting, because the
`-apply` that follows rewrites them too.

It is worth a sentence in the procedure all the same, because the
operator is being *told* to start the daemon:

* keep that start as short as it takes to import the commit, and run
  `-apply` immediately after stopping it;
* the row count of the second run will not match the report from before
  the start, and that is expected rather than a sign something moved
  underneath it;
* any run those tasks dispatch in that window is dispatched against the
  old spelling, and pins it into `task_run` (which is now reconciled
  too, so it also comes out in the wash).

The refusal's own text says "start the daemon once so it takes that
commit up, stop it again" and does not say why the once and the again
matter. Filed as a task rather than changed here, since it is wording on
an operator-facing message that has tests around it.

## 4. The refusals, all four of them at once

`grain/task-314` brought three new conflict shapes with it, and the four
were driven together on one copy -- a release named `v1.3` under both
spellings, a release train with prefix `rel` under both, a task writing
both spellings with different base branches, and a repo memory under
both spellings with different text:

```
4 row(s) cannot be merged without deciding something grain has no basis to decide:
  task_write (t00400): bwsalmon/Grain vs bwsalmon/grain: both spellings are a write
    target here, with different base branches (main and release-1.4)
  release (v1.3): bwsalmon/Grain vs bwsalmon/grain: both spellings hold a row of this
    name, and they are two separate records: delete or rename one of them and run
    this again
  release_schedule (rel): bwsalmon/Grain vs bwsalmon/grain: both spellings hold a row
    of this name, and they are two separate records: delete or rename one of them and
    run this again
  memory: bwsalmon/Grain vs bwsalmon/grain: both spellings hold a memory, and the two
    texts differ: read both and delete or fold one into the other, then run this again
```

`-apply` prints the same four, exits 1, writes nothing -- every divergent
row was still in place afterwards, including the 900-odd that had nothing
to do with any of the four -- and the state repository has no new commit.
All or nothing still holds, and now holds across the new tables.

**The memory one is the conflict a real deployment is most likely to
meet, and it is worth expecting.** `mergeMemoryRow` folds two memories
only when the texts are identical or one of them is empty, and
`PutMemory` deletes a row rather than storing an empty text -- so in
practice *any* repository whose memory agent has written under both
spellings is a repository whose reconciliation refuses, whole, until a
human reads both memories and deletes one. On a deployment with a year
of memory writes that is the likeliest single reason for `-apply` to
refuse, and the fix is a minute in the UI, but it has to be done before
the reconciliation can proceed at all.

## 5. What this does and does not tell you about the real thing

Established here, at a year's scale, with the fixes in:

* the report names all 24 repo-keyed tables and its counts are exact;
* `-apply` is an export now, at 20 s per 321 MB, and needs the daemon
  down for all of it;
* the commit it leaves is readable, one line per row, `task_run.json`
  included, and costs the repository one churn-sized blob;
* the reconciliation survives a start, and the import refusal that makes
  that true fires, refuses whole, and has a way out that works;
* the four refusals name what they cannot decide and change nothing.

Not established, and not establishable here:

* what a year of *real* rows contains. The two things a synthetic store
  cannot have are still the two that would make this interesting: rows
  written by builds that no longer exist, and an operator's own history
  of typing repo names into a box. Nothing above predicts how many
  spellings this deployment actually holds, or in which tables, or
  whether any of them collide in a way that refuses.
* how far `task_run` is really involved. On this deployment the pinned
  columns arrived on 2026-09-07 (`Pin a run's push target to the repo it
  was dispatched against`) and repo names entering the store were
  canonicalised on 2026-09-05 (`Spell a repo the way the deployment
  already spells it`), so only runs dispatched in the last day or so
  *for tasks whose stored target is already divergent* can have a
  divergent `target_owner` at all. The real deployment's `task_run` line
  is likely to be a handful of rows or none, where this run made it 299
  deliberately, to measure the worst case.
* the compression and push figures, for the reason given in section 2.

## Still owed

Step 5, on the real deployment, exactly as the plan wrote it -- and the
fixes it was waiting on are both in, so the only thing between it and
being done is a copy of the data directory.

What that needs, concretely: a copy of `$GRAIN_DATA_DIR` from the host
(the `store/` directory is the whole of what `repo-case` reads; the
`state-repo/` beside it is what the export half needs), made available to
a sandbox -- as a task attachment, or by giving one run read access to a
snapshot. It must be a copy: nothing here should ever be pointed at the
live directory, and `-apply` writes to the state repository as well now.

What it would answer that this run cannot: how many rows this deployment
actually holds under a spelling of its own it no longer uses, in which
tables, whether any pair of them refuses, and -- for the one number that
is genuinely unknown -- what `-apply`'s export costs when
`tables/task_run.json` holds a year of real transcripts rather than
synthetic ones.
