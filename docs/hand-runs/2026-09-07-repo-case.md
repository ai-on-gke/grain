# Hand run: `grain repo-case -apply` against a year of rows

`docs/test-plans/2026-09-06.md` section 5, the reconciliation `#804`
shipped. What the plan asked for: run it on a copy of a real
deployment's data directory, read the report, apply it, start a daemon on
the copy, and then -- the step it said was worth the most -- export the
state repository and read the diff, because "a rewrite of every table is
a settings history nobody can read afterwards".

The diff is boring. Two other things are not.

## What was run, and what was not

**Not run against a real deployment's data.** This sandbox has no copy of
any deployment's data directory, and cannot reach one: the state
repository this deployment's settings live in (`bwsalmon/grain-home`) is
refused to it -- `bwsalmon/grain-home is not in scope for this sandbox`,
403 -- and there is no other route to a database with a year of real rows
in it. Step 5, the same run against the real deployment, is therefore not
done and is not attempted below; it is still owed, and the two findings
here are reasons to do it deliberately rather than casually.

**What was run instead.** A synthetic store of the same shape and size,
built through grain's own `pkg/model` API rather than by writing rows
into SQLite by hand, so every row is one grain itself wrote:

* 6,000 tasks spread over a year to the hour, 7,500 runs with real
  transcript columns on them, 2,000 observations, 1,000 comments, 1,380
  read-scope rows, 12,012 tags;
* 260 requested branches, 40 releases, 79 candidates, 12 schedules, 6
  templates, 3 qualification plans, per-repo configuration on five
  repos;
* 286 MB on disk, 30,350 rows across 22 tables.

The five repositories are this deployment's own, and the divergence is
the shape `#804` was written for -- an early era before `grain/task-32`
spelled repo names for whoever typed them. 240 tasks target
`bwsalmon/Grain` and 68 target `BWSalmon/kontur`; 144 tasks read
`bwsalmon/grain` under *both* spellings; a `repo_config`, a
qualification plan, a bound template, a schedule, 6 releases with their
candidates and 40 branches are stored divergently. One repository,
`Someone-Else/Unrelated`, is named nowhere in the allowlist and is there
to be left alone.

Everything below was run against that store, or against a copy of it, with
a real state repository (a local bare repo) behind it and a real
`grain daemon` on top of it.

## 0. Scale: the failure mode the plan was worried about did not happen

| step | wall clock |
| --- | --- |
| `grain repo-case` (report) | 0.32 s |
| `grain repo-case -apply` | 0.39 s |
| `grain state adopt` (the first, whole export) | 27 s |
| `grain state sync` after the rewrite | 20 s |
| `grain state check` over the result | 19 s |

The rewrite is one `UPDATE` per (table, divergent spelling) plus a row
per merge, so its cost tracks the number of *spellings*, not the number
of rows in the database: 521 rows moved in under four tenths of a second
against 286 MB. The database file did not grow, no journal was left
beside it, and a second report immediately afterwards had nothing to say.
"It is a database" was the plan's worry, and at this size it is not one.

## 1. The report, and whether every row it proposes to move belongs there

It proposed 521 rows across 14 tables, and every count is exactly right.
Checked against the store rather than read:

* `task`: 240 + 68, which is every task stored under either divergent
  spelling and no other.
* `task_read`: 0 rewritten and 144 merged -- and all 144 of those rows do
  have a canonical twin on the same task (`SELECT count(*) FROM task_read
  a JOIN task_read b ON a.task_id = b.task_id AND lower(a.owner) =
  lower(b.owner) ...` returns exactly 144), so "merged" is the right word
  for all of them and no read scope is being dropped.
* `branch` 30 + 10, `release` 6, `release_candidate` 15, `schedule` 2,
  `template` 1: each matches a `GROUP BY owner, repo` over the table.
* `Someone-Else/Unrelated` appears nowhere in the report, which is
  correct: this deployment names no spelling for it, so grain has no
  opinion to impose. Its 66 `task_read` rows and its `repo_config` were
  untouched by the apply as well.

The three merges it proposed are the three the code documents, and they
came out as documented:

```
repo_config          grain-ci,gcp-key            + gcp-key,kontur-ssh
                  -> grain-ci,gcp-key,kontur-ssh   (union, canonical first)
                     prompt extension and setup command taken from the
                     divergent side, which was the only side that set them
qualification_config canonical (approval on) kept; the divergent row said
                     nothing, so it yielded
qualification_item   tmpl-smoke merged (both schedule it once); tmpl-soak
                     rewritten in alongside
```

Two notes on that last one, neither a bug:

* the merged plan is the **union** of two plans. Before, a candidate of
  `bwsalmon/grain` fired 3 qualification tasks; after, 6. That is the
  only merge available -- dropping either side's items would throw away
  something somebody configured -- and the report does say so, at
  `1 row(s) rewritten, 1 merged`. It is worth an operator reading the
  qualification line of the report specifically.
* the rewritten item keeps its own `order_key`, so the merged plan has
  two items at `order_key` 1. `order_key` "decides nothing about
  dispatch" (schema.go), so this is display order only, but the plan now
  contains a tie that no plan written through the UI ever would.

## 2. `-apply`, and the refusal

The apply on the store above succeeded, wrote 521 rows, and a re-run
reported nothing left to do.

The other half of the plan's expectation -- "or it refuses something it
cannot merge mechanically and changes nothing at all" -- was driven
separately, on a store of the same shape holding two releases named
`v1.9`, one under each spelling:

```
1 row(s) cannot be merged without deciding something grain has no basis to decide:
  release (v1.9): bwsalmon/Grain vs bwsalmon/grain: both spellings hold a row of
  this name, and they are two separate records: delete or rename one of them and
  run this again
```

`-apply` printed the same thing, exited 1, and wrote nothing: tasks,
branches and `repo_config` were all still exactly as they had been, in
both spellings, including the 74 rows that had nothing to do with the
release. All or nothing holds.

## 3. The daemon on the copy

A real `grain daemon` was started on the reconciled copy. Nothing is
orphaned: `grain state check` over the export loads all 30,350 rows into
a throwaway database under the schema's own foreign keys and says `ok:
grain can load this`.

**The repos page had no duplicate rows to lose, before or after.** This
is worth saying plainly because the plan expected otherwise. `grain repo
list` -- the same derivation the page uses -- reports six repos on the
*unreconciled* copy, not eight: `#906` gave `repoSummaries` a `repoKey`
that folds two spellings into one row, so the ghost rows the
reconciliation was written to remove had already stopped being visible
there. The two lists are identical.

**What did change is the per-repo defaults, which is the half that
matters.** Before and after, on `bwsalmon/grain`:

```
before                                  after
own defaults:  grain-ci, gcp-key        own defaults:  grain-ci, gcp-key, kontur-ssh
own prompt extension: none              own prompt extension: "Read docs/design.md
                                          before changing anything under
                                          pkg/orchestrator."
what a run here is told: none           what a run here is told: the same text
```

Before the reconciliation the repos *list* row already said "prompt
extension; setup command" for `bwsalmon/grain` -- folded in from the
`bwsalmon/Grain` row -- while the repo's own page said it had none, and
`Store.GetRepoConfig` (`WHERE owner = ? AND name = ?`, exact) agreed with
the page: no run working in that repo was ever told any of it. That
disagreement between one surface and the dispatch path is the clearest
statement of what the reconciliation is for, and it is gone afterwards.

## 4. The state repository's next export: a boring diff

This was the step worth the most, and it passes.

`grain state sync` after the rewrite produced one commit touching 11
files, +382 −1,127 lines:

```
 tables/branch.json               |  80 ++---
 tables/qualification_config.json |   6 -
 tables/qualification_item.json   |  21 +-
 tables/release.json              |  12 +-
 tables/release_candidate.json    |  30 +-
 tables/repo_config.json          |  13 +-
 tables/schedule.json             |   4 +-
 tables/schedule_read.json        |   5 -
 tables/task.json                 | 616 ++++++++++++++++-----------------
 tables/task_read.json            | 720 ---------------------------------------
 tables/template.json             |   2 +-
```

and the diff reads as one line per row:

```
     "target_owner": "bwsalmon",
-    "target_name": "Grain",
+    "target_name": "grain",
```

Nothing was reordered where it would have hurt. `Export` sorts rows by
primary key, so a table whose primary key *starts* with the repo columns
does resort when they are rewritten -- but the two that do (`repo_config`,
`qualification_item`) are settings tables of a handful of rows each, and
their diffs are the most readable in the commit: one object removed, one
object's fields changed. Everything large is keyed by `id` or `task_id`,
so `task.json` and `branch.json` change in place and `task_read.json` is
pure deletions of the merged rows.

`tables/task_run.json` -- 283 MB of the 286 MB dump -- is not in the
commit at all. The reconciliation touches no churn-tier table, so the
export left those files byte-identical and git saw nothing. The whole
bare repository is 3.8 MB.

A reviewer can read this commit. That was the pass condition.

## Finding 1: six repo-keyed tables are never visited, and the report says the store is clean

`repoCaseTables`'s own doc comment says "Every repo-keyed table in
schema.go is here; a new one is a new entry rather than new code". Six
are not:

| table | repo columns | what it is |
| --- | --- | --- |
| `task_write` | `owner`, `name` | a task's extra write targets (`#840`) |
| `schedule_write` | `owner`, `name` | the same, on a schedule |
| `template_write` | `owner`, `name` | the same, on a template |
| `memory` | `owner`, `name` | a repo's stored memory |
| `release_schedule` | `owner`, `repo` | a release train |
| `release_iteration` | `owner`, `repo` | one cut of a train |

Every one of them post-dates `#804`'s own branch (`grain/task-34`), which
is the hazard the test plan itself flagged about that pull request: it
was written early and merged late, and the tables it names are the tables
that existed when it was written.

`TestRepoCaseVisitsEveryTableItNames` does not catch this, and the test
plan credits it with more than it does: it plans against an *empty* store
and asserts the plan is empty, which proves every table it names exists
and can be queried. It says nothing about a repo-keyed table the list
omits, which is the thing that would be "quietly skipped".

Demonstrated rather than read off the code. On a second copy of the same
store, with divergent rows added to all six tables:

```
$ grain repo-case -apply
rewrote 521 row(s).                # the same 521; none of the six is mentioned

task_write        bwsalmon/Grain 2, BWSalmon/kontur 1      (unchanged)
schedule_write    bwsalmon/Grain 1                         (unchanged)
template_write    bwsalmon/Grain 1                         (unchanged)
memory            bwsalmon/Grain 1, bwsalmon/grain 1       (unchanged)
release_schedule  bwsalmon/Grain 1                         (unchanged)
release_iteration bwsalmon/Grain 1                         (unchanged)
task (t00000, t00003, t00006)  all three now bwsalmon/grain

$ grain repo-case
every repo in this store is already spelled that way: nothing to do.
```

That last line is the worst of it: the tool an operator runs to find out
whether their deployment has any divergent rows tells them it does not,
while six tables still hold them.

What it costs, in the order it matters:

1. **A release train is invisible on the repo it belongs to, and a second
   one can be created over it.** `ListReleaseSchedulesForRepo` matches
   `WHERE owner = ? AND repo = ?` exactly, so a train stored under
   `bwsalmon/Grain` does not appear on `bwsalmon/grain`'s page after the
   reconciliation -- while the releases it cut *have* moved there, since
   `release` and `release_candidate` are both on the list. The
   duplicate-prefix check in `CreateReleaseSchedule` is exact too, so
   nothing stops an operator who cannot see it from creating a second
   train with the same prefix under the canonical spelling. The
   due-trains query is repo-blind (`WHERE enabled = 1 AND next_run_at <=
   ?`), so both would then fire, and both would publish `rel.latest` on
   one repository.
2. **A repo's memory is stranded and duplicated.** `GetMemory` is an
   exact match as well, so the divergent row is unreachable and the
   repository has two memories, one of which nothing will ever read
   again.
3. **The write targets are the mildest**, because `pkg/model/repo_scope.go`
   compares with `lower()` on both sides: a task whose `Writes` names
   `bwsalmon/Grain` is still allowed to land work there and still folds
   into `WorkRepos`. What is left is that the rows are in a spelling
   nothing else in the store uses any more, which is exactly the
   condition this command exists to end, and any read that is later
   written as an exact match inherits the bug.

Filing the fix as a task rather than making it here, because four of the
six need a merge rule decided and that is a judgement, not a mechanism:
`task_write`/`schedule_write`/`template_write` are keyed rows carrying a
`base` (two spellings naming one repo with *different* base branches is a
conflict, not a merge); `memory` carries prose (`pickText`'s rule, most
likely, but the newer `updated_at` is an argument the other way);
`release_schedule` has `prefix` as an identity within a repo, so two
trains with one prefix is the `release`-style refusal; `release_iteration`
is keyed by `(schedule_id, number)` and simply moves with its schedule.

## Finding 2: the next settings import undoes the reconciliation, silently

`grain repo-case`'s usage text says to stop the daemon before `-apply`,
"both so no reconcile cycle is mid-decision about a task whose target is
being rewritten and so the change is exported to the state repository as
one commit". It does not say what happens if the state repository has
moved on in the meantime, and what happens is that the rewrite is partly
thrown away.

`staterepo.Load` on a start where the repository's HEAD is not the commit
this host last loaded takes the settings tables from the repository's
dump (`applySettings`). That dump is whatever the last export wrote --
which, for an operator who stopped the daemon, applied the
reconciliation, and started it again while a settings pull request had
merged in between, is the *pre*-reconciliation spelling of every settings
table.

Driven end to end, on a third copy:

1. adopt a state repository; it is seeded from the database, divergent
   rows and all;
2. somebody merges an ordinary settings change (a deployment-wide prompt
   extension) into it;
3. `grain repo-case -apply` -- 521 rows, `repo_config` merged,
   `qualification_item` merged, no `bwsalmon/Grain` left anywhere;
4. start the daemon.

After the start:

```
repo_config       bwsalmon/Grain  gcp-key,kontur-ssh  "Read docs/design.md ..."
                  bwsalmon/grain  grain-ci,gcp-key    ""
qualification_item bwsalmon/Grain tmpl-smoke, tmpl-soak
                  bwsalmon/grain  tmpl-smoke, tmpl-e2e
task              bwsalmon/Grain  1        <- filed after the start
                  BWSalmon/kontur 1        <- filed after the start
```

The merge is undone, both `repo_config` rows are back, the qualification
plan is split in two again -- and the last two lines are the part that
makes this more than a partial revert. `template` is a settings table
too, so the template *bound* to `bwsalmon/Grain` came back with the rest
of them, and the schedule that fires it immediately filed **new** tasks
under the old spelling. The deployment is not merely back where it
started; it is minting divergent rows again.

Nothing says so. There is no journal line for the settings import -- the
only visible trace in the log is the setting that changed on purpose --
and `repo-case` has already exited, successfully, some minutes ago.

The store is left half-reconciled in a way `ApplyRepoCase`'s "all or
nothing" is otherwise careful to prevent: `task`, `branch`, `release`,
`release_candidate` and `schedule` are not settings tables, so those
stayed rewritten while `repo_config`, `qualification_*` and `template*`
went back.

None of this is `staterepo`'s fault -- the repository is authoritative
for settings, deliberately and for good reasons -- but it does mean a
reconciliation is not durable until it has been exported, and that
"export it before anything else touches the repository" is a step of the
procedure that is currently written down nowhere. The narrow fix is
probably in `repo-case` itself: a `-apply` that has just rewritten a
deployment's settings tables is in a better position to export them than
the operator is to remember to. Filed as a task.

## Smaller notes

* **A stored `poll_interval_ms` of 0 panics the reconcile loop.** Not a
  repo-case finding -- it came from this run's synthetic `grain_config`
  row, written through `Store.PutConfig` from `model.DefaultConfig()`,
  which leaves `PollInterval` and `MaxWorkers` at zero. The daemon starts,
  serves the UI, logs `ignoring -poll-interval=5m0s, stored config already
  has 0s`, and five minutes later: `panic: non-positive interval for
  NewTicker`, after which "the UI/API server above is still up, but
  nothing is dispatching or reconciling tasks". `grain state check` over a
  dump holding that row says `ok`. A settings pull request that sets or
  omits that column would reach the same place on a real deployment, so
  it is filed too.
* **`grain repo capabilities` reports "what a task gets" filtered to the
  capabilities this build offers**, which on a sandbox with no GitHub
  credential and no kontur drops `github` and `kontur-ssh` from the line
  while "own defaults" still lists them. Expected -- `RepoDefaults`'
  own doc comment says the effective set is filtered -- and mentioned
  only because it looks at first glance like the merge failed to take.

## Still owed

Step 5, and it is the one the plan cared about: the same run on the real
deployment. Nothing above substitutes for it, because the two things a
synthetic store cannot have are the two things that would make this
interesting -- rows written by builds that no longer exist, and an
operator's own history of typing repo names into a box. What this run
does establish is that the cost is negligible, the report is exact, the
refusal is whole, and the export is readable; and that before anybody
runs it on the real deployment, findings 1 and 2 are worth fixing, since
between them they mean a successful `-apply` can leave divergent rows
behind and can be undone by the next restart without anybody being told.

Both findings were fixed, and `docs/hand-runs/2026-09-08-repo-case.md`
re-ran everything below against the fixed command -- including the eight
tables finding 1 added, of which `task_run` is 302 MB of the dump and
changes what section 4 says the export costs. Step 5 itself is still
owed: that run could not reach a copy of the real data either.
