## Findings

Severity is the auditor's reading.

### 1. `propose_task` lets any auto-merge or auto-approving task's run file a queued task that restarts forever and sorts ahead of everything a person filed — **Medium**, reproduced

#287 (`cdc7c093`) adds `Task.KeepRunning` ("restarts this task
immediately when its run exits"; `taskKeepRunning`,
`markKeepRunningRequeued` in `pkg/orchestrator/finish.go`) and #285
(`9ed3ac7a`) adds the numeric `Task.Priority`, which now leads the
dispatch order (`taskQueueOrderSQL`, `pkg/model/store.go:1214`:
`priority DESC` before base-branch repairs, before `order_key`, before
approval time). Both are accepted on a proposal: `propose_task`'s
`keep_running` and `priority` (`pkg/daemon/mcpserver.go:1593-1623`),
`/cli/proposals` (`gitproxy.CLIProposeRequest.KeepRunning`, `.Priority`)
and `POST /api/tasks` carry them into `ui.CreateTaskRequest`, and
`Client.CreateTask` (`pkg/ui/client.go:1959-1967`, `:2516`) stores them
as sent: `priority` is only checked for `>= 0`, `keep_running` is not
checked at all.

Neither is weighed when the proposer's permission is applied:
`model.AutoSubmits` (`pkg/model/task.go:779`) looks at grants, reads and
landing repository only, and the `needsPersonWhy`/`HoldForApproval`
arms (`pkg/ui/client.go:2410-2460`) know nothing of either field. So a
run of any task with `auto_merge` or `auto_approve_proposals` — which
is every ordinary fix task on this deployment — can file, with no
person involved:

- a task that is **never finished**: its run's closing comment,
  `nothing_needed` or plain exit re-queues it (`finish.go:446-470`),
  holding an agent sandbox for as long as the deployment runs, and
  able to file more of the same; and
- a task with **`priority: 1000000`**, dispatched ahead of every
  base-branch repair, every `at_front` task a person filed and every
  queued task of a higher-trust proposer.

The same two fields are treated as person-only on the edit path:
`PATCH /api/tasks/{id}` with `keepRunning` is read as a grant of
`durable` (`addedGrantsInBody`, `pkg/ui/agent_api_gate.go:768`), which
`agentGrantRefusal` (`:609-630`) refuses to any agent, and a numeric
`priority` there needs `tasks:write` or `tasks:admin`. The filing path
has no such rule.

**Reproduced** with a throwaway `pkg/ui` test (not committed): a parent
created with `Approved: true, AutoMerge: true`, then
`client.CreateTask(ctx, CreateTaskRequest{Title: "forever",
ProposedBy: parent.ID, AutoMerge: true, KeepRunning: true, Priority:
&1000000})` — the `propose_task` path — produced a child in state
**`queued`** with `KeepRunning=true`, `Priority=1000000` and an empty
approval note; `Store.ListTasks` then ordered it first, ahead of a
person's `AtFront: true` task (priority 5). The sandbox CLI's own
`grain propose` holds every proposal (`SandboxCLIActions.ProposeTask`
sets `HoldForApproval: true`), so only the MCP and REST paths queue.

Fix task: filed (see closing note; title `fix(security): hold proposals
that set keep_running or a priority above the proposer's`).
Suggested fix: in `Client.CreateTask`, when `proposedBy != nil`, treat
`KeepRunning` and a `Priority` above the proposer's own as escalations
— clear `autoSubmit`/`sessionQueued`/`req.Approved` with a note the way
`EscalatedCapabilities` does (or clamp the priority to the proposer's
and refuse `keep_running` outright for agents, as `PATCH` does).
Regression test: `pkg/ui/hold_for_approval_test.go`,
`TestProposalWithKeepRunningOrHigherPriorityWaitsForAPerson`.

### 2. A pull request that edits the unclassified `scripts/github-ci-changes.sh` skips every `Tests` job and still reads as green — **Medium**, reproduced

#279 (`1b01799a`) gives `.github/workflows/tests.yml` a `changes` job
(`tests.yml:53-99`) that runs `scripts/github-ci-changes.sh` **from
the pull request's own head** and gates every other job on its
outputs (`if: needs.changes.outputs.go_program == 'true' && …`). Since
2026-10-31 this repository's merge gate is that workflow
(`ci_mode: github`), and `forge.FailingChecks`
(`pkg/forge/checks.go:154-170`) counts only `failure`, `timed_out` and
`startup_failure`: a **skipped** job is not a failing one, so a pull
request whose Go jobs all skip is green.

The script is not in any trust-boundary category:
`trustboundary.Classify([]string{"scripts/github-ci-changes.sh"})`
returns nothing (`pkg/trustboundary/trustboundary.go`: the
`github-workflows` category names `.github/workflows/` only, and
`ci-suppressions` — the `RequiresHuman` category for "which failures
to ignore", `.grain/baselines/` and `.grain/quarantine.yml` — does not
name it). So a run of an auto-merge task can land any Go change on
`main` with no test having run: its pull request edits
`is_ignored_by_go_program()` (`scripts/github-ci-changes.sh:109`) to
`return 0` alongside the code change; the `changes` job executes the
edited script, every `go*`, `granule`, `frontend`, `postgres`,
`run-host`, `ui-e2e` and `installer` job is skipped, `lint` passes,
the security hold does not fire (nothing classified changed), and
`auto_merge` merges it. The script's own "a change to me runs
everything" rule (`classify_file`, `:139`) is no protection, because
it is the edited script that evaluates it. `.github/workflows/tests.yml`
itself is at least classified (`github-workflows`, agent-reviewed);
the script that decides what that workflow runs is not.

**Reproduced** with a throwaway `pkg/trustboundary` test (not
committed): `Classify` returned no category for the script; a
temporary git repository with a base commit holding the real script and
a head commit changing `pkg/ui/x.go` and the one-line script edit,
run through the real script with `EVENT_NAME=pull_request`,
`BASE_SHA`/`HEAD_SHA` set and `GITHUB_OUTPUT` captured, produced
`go_program=false go_backend=false go_unit=false granule=false
frontend=false … go=false go-e2e=false … real-kubernetes=false` and
only `lint=true`.

Fix task: filed (see closing note; title `fix(security): classify the
GitHub CI path filter and fail it open when it changes`). Suggested
fix: (a) add `scripts/github-ci-changes.sh` to the `ci-suppressions`
category (`RequiresHuman`) in `pkg/trustboundary/trustboundary.go`,
so a change to it waits for a person like a baseline change does; and
(b) in `tests.yml`'s `changes` job, before running the script, have
an inline step compute `git diff --name-only "$BASE_SHA...$HEAD_SHA"`
and set every output to `true` when it names
`scripts/github-ci-changes.sh` or `.github/workflows/tests.yml`
(defence in depth: the decision is then made by the workflow file,
which is classified, rather than by the file under test).
Regression tests: `pkg/trustboundary` — `Classify` of the script
returns `ci-suppressions` with `RequiresHuman` true;
`tests/deploy/github_actions_tests_workflow_test.go` — the `changes`
job short-circuits to all-true when the script or workflow is in the
diff. This fix changes trust-boundary classification, so it is filed
`hold_for_approval: true`, `auto_merge: false`.

### 3. A write target or read repository removed from a standing session's declaration while the daemon is down stays on the session's task — **Low**, reproduced

#273 (`d51af780`) stops `syncConsoleSessionTask`
(`pkg/orchestrator/consolesessions.go:672`) from overwriting a
console-session task's grants, reads and writes from the config repo
on every cycle; it now applies the *difference* between the last
synced declaration and the current one, so an operator's edits made
directly on the task survive. The "last synced declaration" is an
in-process map (`consoleSessionSnapshots`,
`pkg/model/console_session.go:897`), empty after every restart. For
grants, #299 (`152aeff5`) made the no-snapshot case safe:
`mergeConsoleSessionGrants` drops any `GrantByGrain` grant the
declaration no longer names when `hasPrev` is false. For reads and
writes it did not: `mergeConsoleSessionReads` (`:869`) and
`mergeConsoleSessionWrites` (`:905`) keep every current entry when
`hasPrev` is false (`wasInPrev && !inSession` can never be true), and
only add what the declaration names. So a `writes:` or `reads:` entry
removed from `tables/console_session.json` (a config pull request a
person submitted — the table is in `NeverAutoMergePaths`) between a
daemon's stop and its first sync after restart — an upgrade, a
maintenance stop, or a crash — is never removed: the session's agent
keeps pushing to a repository the deployment's declared configuration
no longer lets it write, until somebody notices in the UI. A removal
that lands while the daemon is running is honoured.

**Reproduced** with a throwaway `pkg/orchestrator` internal test (not
committed): `mergeConsoleSessionWrites([a, b], [a], [a, b], true)`
returned `[a]`; `mergeConsoleSessionWrites([a, b], [a], nil, false)`
returned `[a, b]`; `mergeConsoleSessionGrants` with no snapshot
dropped a `GrantByGrain` grant the session no longer named.

Fix task: filed (see closing note; title `fix(security): make a
standing session's declared reads and writes authoritative after a
daemon restart`). Suggested fix: either persist
`ConsoleSessionConfigSnapshot` (a `console_session_sync` table keyed
by task id, written where `RecordSyncedConsoleSession` is called) so
`hasPrev` survives a restart, or, with no snapshot, drop current reads
and writes the declaration does not name unless they were recorded as
an operator's own edit (the way grants carry `Via`). Regression test:
`pkg/orchestrator/consolesessions_test.go`,
`TestConsoleSessionSyncDropsUndeclaredWritesWithoutSnapshot`.

## Examined and found sound

- **Fork workflow runs (#293).** Closes the 2026-10-31 report's finding
  1. `handleConcludedGitHubWorkflowRun`, `ensureGitHubWorkflowRunJobs`,
  `recordGitHubBaseBranchRelease` and `fireOneGitHubWorkflowRunSchedule`
  all return early for a run whose `head_repository` is not the
  repository itself (`isGitHubWorkflowRunForeignHead`) or whose event
  is not `push`, `schedule`, `workflow_dispatch`, `release` or
  `merge_group` (`isGitHubBranchWorkflowEvent` — `pull_request` and
  `pull_request_target` are refused). Both the webhook
  (`ghwebhook.Event.HeadRepo`, `WorkflowEvent`) and the poll
  (`github.WorkflowRun.HeadRepo`, `Event`) carry both fields;
  `isGitHubBaseBranch` no longer falls back to `main`/`master` without
  a client; `MatchesBranch` with no branches and no base now matches
  nothing, and the schedule path resolves the repository's default
  branch first. Fail closed.
- **`task://` siblings (#284).** Closes the 2026-10-30 report's finding
  1. `PermitsTaskRepo` no longer admits `TaskRepo`;
  `SandboxNamespaceScope` and the MCP roster populate `TaskReadRepos`
  from `api:tasks:read@owner/repo` grants only; the refusal names both
  ways in and says nothing about whether the task exists. #296's
  `globPruner` only prunes the walk; every descent still goes through
  `Resolve(ctx, scope, …)`.
- **Capability detach (#271).** The gate skips the "must hold it"
  check only for `attach: false`, and `SetCapabilityGrant` with
  `attach == false` calls `SetCapability(..., false)` and ignores
  `replace`, so a detach can only remove. Route scope and
  `agentRails` still apply.
- **Scope retirements (#291, #301).** `release-notes:read/write` is
  split out of `memory:*`; `releases:read` still reads (never writes)
  the weekly notes; `api:self-upgrade` expands to `deployment:upgrade`,
  which stays `Dangerous` (person-granted, refused to proposals and on
  the sandbox channel); `tests:write` is ordinary and reachable from
  the sandbox CLI, as `test-quarantine` was. `POST /api/tests/quarantine`
  files only a `HoldForApproval: true, AutoMerge: false` follow-up and
  returns YAML for the caller to commit on its own branch; the gate
  binds it to the acting task's repository
  (`agentCallRepo`). Migrations 71, 72, 75, 76 use
  `rewriteLegacyGrants`, which rewrites `task_grant`,
  `template_grant`, `schedule_grant`, `default_capabilities` and
  console sessions and leaves `ci_capabilities` alone.
- **`PATCH /api/tasks/{id}` grants (#273, #285, #289).** A body naming
  `capabilities`, `grants`, `keepRunning`, `priorityDispatch` or a
  boolean `priority` needs `capabilities:admin` and a reason, and
  every name goes through `agentGrantRefusal` with no "already stored"
  exemption, so an agent must hold every grant in a replacement list;
  `keepRunning` and boolean `priority` are read as `durable` and
  `priority-dispatch`, which no agent may grant. `tasks:admin` without
  `tasks:write` may send `{"priority": <int>}` and nothing else
  (`tasksAdminTaskPatchBodyAllowed`, which after #289 also refuses a
  boolean). The external-agent gate mirrors it.
- **Settings unlocked by default (#275).** `PUT /api/settings` (and
  the new `PUT /api/config` alias) still needs `settings:write`
  (dangerous), the `defaultcapabilities` escalation check still runs,
  and the agent-only arm sends an agent that flips `settings_locked`
  off through the config-repository path. `requiresAccess` keeps
  `GET/HEAD /api/config` open and nothing else. A direct write is
  exported to grain/config at once (`SyncAfterWrite`), so the repo
  reflects the database. This is a widening of what a person (or a
  person-granted dangerous scope) may do from the UI, chosen on
  purpose (design/spec/settings/settings-mutability.spec.md), not an
  agent escalation.
- **New Task form (#304).** `settings/new-task-form.yml` was already
  in `NeverAutoMergePaths`; `handleCreateTask` applies hidden-field
  defaults for a person's filing only, never an agent's, so a default
  cannot add a grant the gate did not see.
- **Declared columns (#324).** `repo_config.declared_*` are withheld
  from the export and refused on import, so a state-repo write cannot
  plant a prompt extension or setup command the target repository's
  default branch does not declare.
- **`ci_mode` (#274).** With `ci_mode: github` the forge gates on
  GitHub checks (`IgnoreGitHubCI` is derived from `gateIsGrainCI`, not
  independent); a default `grain-ci` grant no longer counts as a Grain
  CI verdict (`GrantedExplicitly`), an explicit one still does;
  `/cli/ci/wait` on such a repository polls the task's own branch's
  checks and needs no CI grant for that (the same as
  `wait_for_checks`). Base-branch CI and release rows on such a
  repository are cancelled with a reason, not left in flight.
- **Warm session sandboxes on adopted runs (#289).** Parked only for
  the same task, only when `sessionGrantsKey` and `sessionSandboxKey`
  of the latest task match the keys recorded for the run, never for a
  task holding a scarce grant, and never after a degraded rebuild; a
  run with no recorded keys is not parked. The granule exec change is
  stream lifecycle only.
- **Priority dispatch and budget (#307).** Console sessions and
  `priority-dispatch` holders (person-granted) are admitted past the
  budget's ceilings but not past the disk floor or a full cluster;
  the refusal now says which gate declined.
- **Branch names (#282).** The slug is ASCII letters, digits and
  hyphens, the name is capped at 244 bytes, and `ValidBranchName`
  still refuses `..`, `//`, `.lock` and leading dots; the task id
  keeps names unique whatever the title.
- **Sandbox CLI proxy discovery (#292), image cleanup (#227), hostd
  wording (#313), CI 503 (#316), config PR staleness (#310), proposal
  wording (#283), gate logs (#295), re-check cadence (#297), demo and
  githubsim (#323, #312), `.grain/workflows` triggers (#272),
  deploy-gke removal (#300).** No new network fetch, credential path
  or authority.
