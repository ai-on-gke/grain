## Findings

### 1. The bulk grant rewriters are outside every trust-boundary category (medium, reproduced)

**Where.** `pkg/model/legacy_grant_migration.go` (`rewriteLegacyGrants`,
`rewriteLegacyGrantsMulti`, `rewriteCapabilityListColumn`,
`rewriteCapabilityListColumnMulti`, `rewriteConsoleSessionGrantsMulti`,
`foldRetiredCatalogueInProcess`), `pkg/model/retired_bare_name_migration.go`
(`MigrateRetiredBareCapabilityNames`, `settleRetiredBareNames`; new in
#1586), `pkg/model/runtime_grant_retirement.go`
(`Store.RewriteRetiredGrants`, `runtimeExpansion`,
`SetRuntimeGrantExpansions`), and the `Migration.Up` entries in
`pkg/model/migrations.go` that hand those functions a rename map
(sixteen of them today, versions 67 onwards, plus 153).
`trustboundary.Classify` of all four paths is nil at `91e5103fd` (v36).

**What they do.** `rewriteLegacyGrantsMulti(renames)` runs, inside the
store's migration transaction on every deployment's next start and
inside `staterepo.importInto`'s transaction on every state-repository
import (`ApplyDataMigrations`), an `INSERT INTO task_grant /
template_grant / schedule_grant ... SELECT owner, <to> ... WHERE
capability = <from>` for every extra grant a name maps to, then a
`DELETE`/`UPDATE` of the original, and the same rewrite over
`task_grant_wait`, `grain_config.default_capabilities`,
`repo_config.default_capabilities` and the console sessions' grants;
`Store.RewriteRetiredGrants` does the same at daemon start for the
`local-scripts:<name>` runtime retirements, and adds
`repo_config.ci_capabilities`. The *decision tables* those rewrites are
meant to apply -- `CanonicalLegacyGrant`, `CanonicalLegacyGrants`,
`RetiredGrantRefusal` in `pkg/model/agent_api.go` -- are classified
(auth-routes, v31), as is every other place a grant is compared or
admitted (`pkg/model/canonical_grant.go`, `capability_ref.go`,
`capability_catalogue.go`, `template_grants.go`, `auto_submit.go`,
capabilities-secrets). The rewriters that *write* grants on the strength
of a literal map are not.

**Failure mode.** A pull request that touches only
`pkg/model/migrations.go` (or `legacy_grant_migration.go`) and adds a
migration `Up: rewriteLegacyGrantsMulti(map[string][]string{"github#read-issues":
{"github#read-issues", "api:admin"}})` is classified as touching nothing
on the list: no security hold is raised, no security-review task is
filed, and -- in this deployment, where agent tasks' pull requests merge
on their own once checks pass -- it merges unattended. On every
deployment that then upgrades, every task, template and schedule that
holds `github#read-issues` (or whichever common grant the map names)
gains `api:admin`, and so does every repository's default and CI
capability list; on a state-repository import of an older dump the same
happens. Nothing downstream re-checks: `Via` is provenance only, and the
grant is thereafter an ordinary stored grant that `GrantsSubsetOf`,
`TemplateWithinTask` and the cross-task rail all honour. The 2026-11-17,
11-18 and 11-19 reviews each filed the same class (code the hold's
decision depends on, outside the list); this is the write side of the
grant model rather than the read side, and the migration that landed in
this range (#1586) was held only because it also touched
`pkg/staterepo/dump.go`.

**Reproduced.** A throwaway `package model` test (not committed) asserted
`trustboundary.Classify` of the four files is nil, opened a SQLite
store, stored a task with the single grant `github#read-issues`, ran
`rewriteLegacyGrantsMulti(map[string][]string{"github#read-issues":
{"github#read-issues", "api:admin"}})` in a transaction and read the task
back: its grants were `[api:admin]`.

**Severity.** Medium: it needs a merged pull request, and the rewriters
log every row they change, but the hold exists so that exactly this kind
of change waits for a person, and an auto-merge task on this repository
can land it without one. Not exploitable from a sandbox, an agent API
call or a pull-request run.

**Fix task.** Filed as `fix(security): classify the bulk grant rewriters
(pkg/model/legacy_grant_migration.go, retired_bare_name_migration.go,
runtime_grant_retirement.go) under capabilities-secrets`
(trust-boundary/v38 or the next free version; `auto_merge: false`,
`hold_for_approval: true`, since it changes the list). The task is to
add the three files to `capabilities-secrets`, and for
`pkg/model/migrations.go` either add it too or -- preferably, so a plain

## Examined and found sound

- **Gate-observation scope** (#1903, #1905). `gateObservationScope`
  intersects every restriction on the context -- the acting task's or
  external agent's `call.grants`, a direct external-agent token's
  resolved set (an unresolvable one intersects with the empty set), a
  limited RBAC role's `set.Without(deny)`, a CI API call's scopes on its
  one repository (`ciAPICallGrantSet`, which drops any scope
  `CIAPIScopeRefusal` refuses), and, when none of those applies but the
  principal is `PrincipalAgent`, the empty set -- and hashes the result
  into the `authorizationRevision` fence the observation cache is keyed
  by. Before #1903 only `agentCall` and `role` were consulted, so an
  external token or CI API token read with the trusted internal ceiling
  and shared its cache fence; that is task 7301 (from the 11-19 review's
  7297), closed here. `collectGateChecksScoped`, `observationVisible`'s
  `ciReadable` and the qualification collector's `ci:read` callback now
  all require `allows("ci:read", repo)` *and* `requirePullRequestScopes`,
  strictly narrower than either alone. `redactGateHistoryScopes` replaces
  its agent-only `call.grants.Allows("tasks:read")` with
  `taskReadableForContext`, which covers tokens, roles and CI API calls
  too; when the parent task cannot be read it leaves the sidecars
  unredacted, as the previous early return did (pre-existing, not a
  change in this range, and the parent has already passed the route's
  own `taskReadable` fence by then).
- **Task-detail cache** (#1905). `taskDetailCache` now caches the
  domain-only legacy body for gate-observed tasks too, keyed by the
  store's change token as it always was for other tasks, and splices
  `gateObservations(ctx, task)` -- computed per read with the caller's
  own scope -- onto it, hashing the spliced body into the ETag so a 304
  can never serve one caller another's observations. The legacy body
  itself carries nothing per-caller that was not already cached across
  callers before the range; `handleGetTask` sits behind the
  `/api/tasks/{id}` repo fence in `agent_api_gate.go` and
  `access_roles.go`, and `handleTaskSummaries` still checks
  `readable(entry.repo)` before touching a cached entry.
- **CI merge gate from recorded checks** (#1632).
  `ComputeMergeGatesWithChecks` is called only from the task-detail
  builder (`pkg/ui/client.go`) and `PullRequestStatusOf` (display and
  `grain pr status`). Every decision -- `forceOverridesGates` (which
  ignores the CI gate by design), `SubmitPullRequest`'s override check,
  `accept_findings.go`, the state-repo gate observations -- still calls
  `ComputeMergeGates`, which passes `nil` checks and so behaves as before.
  `RecordedHeadChecks` reads only finished `GitHubCIJob` rows, treats
  "every recorded check passed" as *running* unless the commit has been
  quiet for an hour or the previous commit's job set is complete, and
  returns `Unsettled` when the head grain last classified has moved on.
  `headChecksOf` consults `RepoUsesGrainCI` first and returns nil for a
  repository grain CI judges. Merge gates v32 (#1902) put
  `merge_gates.go` under hold-policy, so #1632's edit to it was held and
  reviewed.
- **Schema-downgrade refusal** (#1505, #1872). `CheckTargetSchema` is
  called before `Start`, `StartScheduled`, `StartImageWith`
  (`validateImage`, after the image has been pinned to the installed
  registry), `StartRollback` and the schedule route; a target whose
  schema is lower than the store's is refused before any pull, ref-file
  write or restart. `cheapTargetSchema` reads the
  `io.grain.schema-version` label out of the same digest-held config
  blob `registryImageLabels` already read the revision from (every blob
  hashed against its digest), or a static release→schema table, and
  falls back to running `version --json` in the pulled image; an unknown
  schema is treated as it was before the range (the Prepare/CheckArgs
  path), never as a reason to skip anything. The daemon side refuses to
  write a downgrade note (`ErrSchemaDowngradeRefused`) and
  `openStoreForSchemaUpgrade` refuses to act on a note whose
  `OperatorDowngrade` is false when the store is newer than the build;
  the only writer of a true one is `grain db downgrade`, an offline host
  command that `RefuseWhileDaemonAttached` keeps off a live deployment.
  `clearSupersededScheduledUpgrade` runs only after the upgrader
  accepted the immediate start. Strictly tighter than before.
- **Git-proxy login-page retry** (#1913). `RoundTrip` retries only what
  `loginRetryable` admits -- REST `GET`/`HEAD`, `info/refs` reads and
  `git-upload-pack` -- never `git-receive-pack` or a REST write; the
  body is buffered for replay only up to 8 MiB (`replayableBody`) and
  otherwise sent once; a front end's own redirect (`Redirected`) is
  returned at once; the source's `RetryLogin` can veto; each try goes
  through `roundTripOnce` and so through `checkHost` again; and the
  retry log line passes the endpoint through `redactQuery`. The hostd
  side (`hostGitServeForge`, `hostGitServeForgeDownload`) now calls
  `roundTripOnce` so the host never retries on grain's behalf, and
  carries `LoginRedirected` back in the result. `finishLoginLapsed`
  matches a `LoginRedirectError` or the proxy's own marker in an error's
  text to record the run as `EnvironmentOutcome` and park the task on
  host credentials rather than failing it; the text comes from the
  host's forge call, not the sandbox, and the worst a crafted match buys
  is a run kept off the failure streak.
