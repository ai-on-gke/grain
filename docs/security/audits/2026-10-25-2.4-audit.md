- **Auditor:** grain task 907 (agent)
- **Base audited:** `origin/main` at `e8d1d88e4`
- **Method:** the four attack surfaces the audit task named were mapped
  against the tree, the existing security suites were run
  (`pkg/trustboundary`, `pkg/ui`, `pkg/capability/...`, `pkg/mcp`,
  `pkg/orchestrator`, `pkg/sandboximage`, `pkg/k8s`, `pkg/kubectlgate`,
  `pkg/granule`, `pkg/staterepo`, `pkg/safepath`, `tests/security`),
  the code was read, and every finding below marked *reproduced* was

  are not committed; each fix task names the regression test to add in
  its place. Fix tasks were filed one per finding with `propose_task`
  (`repo: bwsalmon/grain`, `branch: main`), as the audit task asked.

## Findings

Severity is the auditor's reading. Each has a fix task; the task ids
are in the closing note on task 907.

### 1. `granule forward` lets the guest choose the controller's dial target — **High**, reproduced

`third_party/granule/pkg/forward/forward.go` `readLoop` hands every
`frameOpen` payload to `handleIncomingOpen`, which dials it verbatim.
The controller end of that mux is the grain daemon
(`pkg/granule/forward.go` `ForwardKubectl` → `forward.RunClient`,
started by `k8sGranuleSandbox.startForward`); the guest end is the
sandbox VM's guest agent (`third_party/granule/pkg/agent/session.go`
`serveForward`). The `-R` specs the controller was configured with are
never consulted on an incoming Open, so a guest that writes its own
frames (root in the VM, which passwordless sudo gives every run) gets
the daemon to open a TCP connection to any `host:port` it can reach —
the metadata server, the daemon's own loopback listeners that were
deliberately not forwarded, cluster services — through a sandbox whose
own network is `CHV_NET_MODE=none`. It is the inverse of SSH `-R`,
where the client decides the connect target from its own
configuration. Reproduced: with one spec `127.0.0.1:9728`, an Open
naming another local listener was dialed.

Fix: an allowlist of `TargetAddr()`s built from the specs on each
side, enforced before dialing, with a `frameOpenErr` back; tests in
`forward_test.go` and `pkg/granule/forward_test.go`.

### 2. Agent API capability attach bypasses the grant-escalation check — **Medium/High**, reproduced

`agentGrantEscalation` (`pkg/ui/agent_api_gate.go`) finds grants in a
body by key name (`*capabilit*`, `grants`). `POST
/api/tasks/{id}/capabilities` (`capabilities:admin`) takes its grant as
`id` or `grant` (`setCapabilityRequest`, `pkg/ui/tasks.go`), neither of
which is scanned. A run holding `api:capabilities:admin` attached
`api:deployment:upgrade`, `api:secrets:write` and `self-debug` to
another task with 200s — grants it does not hold and grants the
vocabulary says only a person may give.

Fix: check the fields this route actually uses (structurally, by
pattern), normalise before comparing, and a table test over every
grant-bearing key of every `capabilities:admin` route.

### 3. `review_template_id` files an auto-approved, auto-merge review with any template's grants — **Medium/High**

`proposedReviewTemplate` (`pkg/orchestrator/finish.go`) and
`validReviewTemplate` (`pkg/ui/client.go`) accept any existing
template; `agentFilingEscalation`'s `templateid` rules do not run for
`reviewtemplateid`. When the work finishes, `putStackedReview`
(`pkg/orchestrator/review.go`) files a task with the template's
`Grants`, `Reads`, `Writes`, `Approval` set and `AutoMerge: true`, on
the proposer's own branch. A run with only `propose_task` or
`tasks:write` thereby picks the template whose grants it wants.

Fix: one template-escalation rule applied to `templateId`,
`reviewTemplateId` and `review_template_id`, with a belt-and-braces
check at `putStackedReview`.

### 4. A stacked review/fix merge enrols the task branch as a watched base branch — **High**, reproduced

`recordPostMergeCI` (`pkg/orchestrator/sync.go`) runs for every merged
pull request, stacked ones included, and `noteBaseBranchMerge` writes
a `BaseBranchCI` row for `detail.BaseRef` — the reviewed task's
`grain/<deploy>/task-<N>` branch. `startDueBaseBranchRelease`
(`basebranchrelease.go`) then starts a `TrustedRelease` run with the
repository's release secrets and publishing capabilities on that
branch, reading the workflow at that ref; `checkReleaseRef` lets any
`ci:write` holder start one by hand; the branch is judged, repaired and
read by the merge queue's base gate. Reproduced at the row level: a
merge with `BaseRef: grain/049f1e09/task-123` left a row for it.

Fix: skip stacked merges in `recordPostMergeCI`; refuse task branches
in `startBaseBranchRelease`, `ci.Service.Start` (`TrustedRelease`) and
`watchedBaseBranches`; sweep existing rows.

### 5. Staging proxy passes a sandbox's `Set-Cookie` onto grain's origin — **Low**

`handleStagingProxy` (`pkg/ui/persistent_sandboxes.go`) strips grain's
cookies and `Authorization` outbound and adds a CSP `sandbox` to
responses, but response `Set-Cookie` headers reach the browser on
grain's origin, so the staging build can overwrite `grain_*` cookies.

Fix: drop `grain_*` `Set-Cookie`s and scope the rest to the staging
subpath (or drop all), with a test over a 200 and a 101.

### 6. `trust-boundary/v5` does not cover the 2.4 boundary code — **Gap**

`trustboundary.Classify` returns no category for
`pkg/ui/agent_api_gate.go`, `pkg/ui/route_scopes.go`,
`pkg/model/agent_api.go` (where `Dangerous: true` lives),
`pkg/ui/config_refusal.go`, `pkg/ui/persistent_sandboxes.go`,
`pkg/policy/`, `pkg/jwks/`, `pkg/hostd/`, `pkg/localexec/`,
`pkg/runhost/`, `pkg/k8s/`, `pkg/sandboximage/`, `pkg/staterepo/`,
`pkg/redact/`, `pkg/daemon/run.go` or `third_party/granule/` — so a
change to any of them, finding 1's fix included, merges itself today.

Fix: `trust-boundary/v6` adding them, plus a coverage test over a
fixed list of known boundary files.

## Looked at and found sound

- Pod manifests: `automountServiceAccountToken: false`, `restartPolicy:
  Never`, typed `CharDevice` hostPath for `/dev/kvm`, no `hostNetwork`/
  `hostPID`; the namespace's Pod Security level is the operator's
  explicit decision (`deploy/kubernetes/grain.yaml`,
  `grain-granule.yaml`), with the trade-off written down.
- `KubectlExecRunner`: argv after `--`, `statusTrailerScript` runs
  `"$@"` with no quoting, the trailer cannot turn a non-zero kubectl
  exit into success, retries happen only before the command ran.
- `kubectlForwardCommand` and `hostShellPassthrough` pass allowlisted
  variables only (the `exec-env-implicit` baseline names
  `kubectl_exec_runner.go` for the daemon-side kubectl, which is fine).
- Capability port grants are refused on `ReservedGuestPorts`
  (`protocol.Pass`), and external capability servers' placements are
  held to clean absolute, non-reserved paths and sane modes
  (`validatePlacements`). In-tree placements use fixed paths.
- `hostd`'s allowlist resolves symlinks on both sides
  (`safepath.Within`), refuses `..`, `~`, NUL, `LD_*` and identity
  variables unless named exactly, and never forwards the daemon's
  environment.
- `checkRepoPerson` / `withholdReleaseSecrets` keep manual and release
  events started by non-persons from placing release secrets;
  `trustedCommit` strips them from a commit that is not on its branch.
- The external config repository refuses every configuration write
  with a 409 (`guardConfigWrite`), rehearsed so a guarded route cannot
  answer around it.
- `.grain/baselines/path-containment.txt` and
  `route-authorization.txt` are empty and the ratchets pass.
