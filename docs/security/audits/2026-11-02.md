## Findings

Severity is the auditor's reading.

### 1. The gcp-key agent service account — whose raw key grain pushes into task sandboxes — is on the default IAP allowlist, so a sandbox holding one is the operator — **High**, reproduced

#395 (`5c273a66`) changes what a single-tenant daemon does with a
request a proxy vouches for. Before it, `singleTenantRefusesIdentity`
(`pkg/ui/single_tenant.go`, removed) answered 401 to any `/api/*` or
`/mcp` request whose IAP assertion verified, and `extractPrincipal`
dropped every person: a caller behind IAP still had to present the
access code. After it, `singleTenantGate` (`pkg/ui/accesscode.go:576`)
lets a verified identity through when `checkAllowedPrincipal`
(`pkg/ui/allowlist.go:187`) admits it, `extractPrincipal`
(`pkg/ui/principal.go`) makes it the request's principal, and — by
design (design/design/authentication.design.md §2, "same powers for
everyone") — every admitted principal is an operator. A
`.gserviceaccount.com` address becomes the new `model.PrincipalService`,
which `Client.CreateExternalAgentToken`
(`pkg/ui/external_agents.go:154`, `:240`), `authMethod`
(`pkg/ui/auth.go:104`) and `pkg/ui/teams.go` treat exactly as a person.

The allowlist that decides this, when `-ui-allowed-principals` and
`$GRAIN_ALLOWED_PRINCIPALS` are unset, is `defaultAllowedPrincipalEntries`
(`pkg/ui/allowlist.go:112-164`): the owner (`Config.Actor`), plus
`Config.ProvisionedServiceAccounts`, plus every address
`gcpkey.PoolEmails(mc.GCPServiceAccountEmail, mc.GCPServiceAccountCount,
mc.GCPProject)` yields, plus `grain-daemon@<project>`.
`ProvisionedServiceAccounts` is built the same way
(`pkg/daemon/ui_server.go:121-124`). `GCPServiceAccountEmail` is, per
its own doc (`pkg/model/config.go:170`), "the narrow agent service
account gcp-key mints keys for": `pkg/capability/gcpkey` mints **a real
key** for it and pushes the key into the sandbox of every task granted
`gcp-key`. And `CollectDesiredIAPMembers` (`pkg/daemon/iap.go:48`) puts
that very account on the IAP `roles/iap.httpsResourceAccessor` binding
of every IAP target the deployment names, so IAP lets it in.

So on an IAP-fronted deployment with gcp-key configured and no explicit
allowlist — the documented default — a run of any task holding
`gcp-key` can, from its sandbox:

1. sign a self-issued JWT with the key it was given and exchange it at
   Google's token endpoint for an ID token with
   `target_audience=<IAP client id>` (what `gcloud auth
   print-identity-token --audiences=…` does with a key file);
2. call `https://<iap host>/api/...` with it; IAP admits the account
   (reconciled onto the binding) and forwards
   `X-Goog-IAP-JWT-Assertion` naming `grain-agent[-N]@<project>…`;
3. be admitted by the default allowlist as `{service, grain-agent…}`
   with no access code, pass the CSRF check (no browser headers), and
   act as the operator: `PUT /api/settings`, `secrets:write` routes,
   `POST /api/tasks/{id}/approve`, `merge:force`, and — the durable
   form — `POST /api/external-agents/tokens` minting a standing `gma_`
   credential with every dangerous scope, which outlives the task, its
   key and its sandbox.

The agent API gate does not apply: it judges requests carrying an
acting-task header or an external token, and this request carries
neither. The reach depends on the pool shape: with the default single
account (`GCPServiceAccountCount` 0 or 1) the address the reconciler
puts on IAP, the address the allowlist admits and the account whose
key is in the sandbox are one and the same; with a numbered pool the
reconciler names only the base address, so `grain-agent-N@` passes IAP
only where the operator put the pool there (as a sandbox relay through
the IAP gateway needs). Nothing in `pkg/trustboundary` holds #395 for a
person either: `server.go`, `principal.go`, `auth.go` and `csrf.go` are
`auth-routes` (agent-reviewed, not `RequiresHuman`), and
`pkg/ui/allowlist.go`, `verifier.go`, `accesscode.go` and
`single_tenant.go` — where the gate and the allowlist live — are not
classified at all.

**Reproduced** with a throwaway `pkg/ui` test (not committed) built on
the harness of `verifier_allowlist_test.go`: a `testServer` with
`Config.Actor = owner@example.com`, no `AllowedPrincipals`, and the
store's `GCPProject = my-proj`, `GCPServiceAccountEmail =
grain-agent@my-proj.iam.gserviceaccount.com`,
`GCPServiceAccountCount = 2`; a signed IAP assertion for
`grain-agent-1@my-proj.iam.gserviceaccount.com`; no access code. `POST
/api/external-agents/tokens` with
`{"scopes":["tasks:admin","settings:write","secrets:write","capabilities:admin","merge:force","deployment:upgrade","deployment:reboot"]}`
answered **201** with a `gma_…` token; `GET /api/settings` and `GET
/api/deployment/audit-logs` answered 200; `GET /api/auth/user` reported
`{"authenticated":true,"user":"grain-agent-1@…","authMethod":"iap"}`.
The same request for `grain-agent-7@…` (outside the pool) was 403 and
with no header 401. The repository's own
`TestAllowedPrincipalsDefaultsAndCloudIdentityGroups` pins
`grain-agent-0@`/`grain-agent-1@` as admitted, so the behaviour is
deliberate at the allowlist level; what it hands over was not weighed.

Fix task: filed (see closing note; title `fix(security): keep the
gcp-key agent service accounts off the default IAP allowlist`).
Suggested fix: in `defaultAllowedPrincipalEntries` and
`pkg/daemon/ui_server.go`, admit only the owner (and, if a daemon-side
identity is needed for hostd/relay, an account whose credential never
enters a sandbox — never `gcpkey.PoolEmails(...)`); refuse in
`ParseAllowedPrincipals`/at startup an explicit `serviceAccount:` entry
that names a gcp-key pool account, with a message saying why; and have
`CreateExternalAgentToken`'s `needsPerson` arm accept
`PrincipalService` only for an account the operator listed explicitly,
not a default. Add `pkg/ui/allowlist.go`, `verifier.go`,
`accesscode.go` and `single_tenant.go` to the `auth-routes` category in
`pkg/trustboundary/trustboundary.go`, so the next edit to the gate is
at least agent-reviewed. Because the change edits authorization, it
should land held for a person. Regression test: `pkg/ui/verifier_allowlist_test.go`,
`TestGCPKeyPoolAccountsAreNotAdmittedByDefault` — the pool accounts get
403 from `/api/tasks` and `/api/external-agents/tokens` with a verified
assertion and no access code, while the owner still gets 200; and a
`tests/security` route test that a `PrincipalService` not named in an
explicit allowlist cannot mint a dangerous external-agent token.

## Examined and found sound

- **In-process grain server (#311, #385).** `grain#host-exec` is
  `protocol.RequirePersonGrant` at `pkg/model` init, so
  `IsDangerousGrant`, `IsPersonOnlyGrant`, `EscalatedCapabilities`
  (`protocol.Covers` never covers a `GrantByPerson` ref) and
  `agentGrantRefusal` all refuse it — including from a parent that
  holds it, and under the retired `self-repair` spelling. `grain#sql`
  is person-only when and only when `with.write` is the JSON boolean
  `true`; a string `"true"`, a number or `Write` is neither dangerous
  nor a write (`ParseGrainSQLGrant`, `task_db.go` `taskHasDBWrite`), and
  the method's schema (`additionalProperties: false`, boolean) refuses
  the pass. Confirmed with a throwaway `pkg/model`/`pkg/ui` test (not
  committed): every spelling above refused, read-only `sql` held by the
  parent covered. The daemon decides writes server-side
  (`handleTaskDBQuery` → `ValidateReadOnlyQuery` + `QueryReadOnly`);
  the MCP `AllowWrite` is an offer. `grantTools` keys the host tool on
  the exact recorded grant, so a bare `grain#host-exec` yields no tool.
  `mintCapabilityPass` skips the unisolated-sandbox refusal only when
  no *external* ref is held; the in-process server opens no listener.
  Migrations 80–84 use `rewriteLegacyGrants` and now also rewrite
  `repo_config.ci_capabilities` (#389).
- **Writable grain/config for the Director (#334).** The git proxy
  grants, in grain/config only, refs strictly under
  `refs/heads/grain/config/<task-id>/` to the live run of a task whose
  `task_write` rows name the config repo (`GitConfigProposalPrefix`);
  `main` and other tasks' prefixes stay refused. `ProposeConfigChange`
  checks `IsConfigProposalBranch(id, branch)` against the acting task's
  own id; the three routes are `internal` (no scope grants them;
  `authorizeAgentCall` refuses; the handler refuses an external token
  again). `MergeConfigChange` merges `pending.HeadSHA` only, after
  re-resolving the branch (`ErrConfigChangeMoved` otherwise) and
  re-running `ValidateCandidateConfig` on the merge tree; the person
  approving saw that commit's diff. `propose_config_change` is offered
  only to `writesConfigRepo` tasks.
- **Key folding (#381).** `gateKey` maps every rune to the lower case
  of the smallest member of its `SimpleFold` orbit, which is exactly
  the equivalence `encoding/json`'s `foldName` uses, so a key JSON
  would route to `priorityDispatch`/`keepRunning`/`capabilities` is
  seen by the gate; the only divergence (`İ`, which `ToLower` maps to
  ASCII `i` but JSON does not fold) over-refuses. Confirmed with a
  throwaway test (`priorityDiſpatch`, Kelvin-sign `keep_running`).
- **Yesterday's fixes.** #360: `PersonOnlyProposalSettings` holds
  `keep_running` and a priority above

  and `relayProposedTasks` (confirmed by test). A `tasks:write` holder
  may still `PATCH` any task's numeric priority, which is that scope's
  stated power ("edit, reorder"), person-granted. #358: the `guard`
  step decides from the workflow file, before the script runs, and
  `push`/`merge_group` run everything; the script is `RequiresHuman`.
  #359: `console_session_sync` persists the snapshot; `hasPrev`
  survives a restart.
- **Agent gate narrowings (#388, #366, #325).** Response redaction only
  removes fields; `networkAccessWidens` reads both sides as dispatch
  does, so an inherited `none` can no longer be widened to `""` on an
  open deployment either; the one rail opened — a note between
  `related` tasks to a session the actor does not own — is a message,
  not an action on the session's run.
- **Workflow-run review grants (#390).** `api:ci-read@<repo>` is
  read-only and bound to the target repository; `ciReadRepoScope`
  never lets `-pr-repo` stand in for a grant scoped elsewhere.
- **`task://` siblings in `grain task list` (#371).** Same predicate
  as the namespace (`PermitsTask || PermitsTaskRepo`).
- **`src://core` (#252).** Served out of the module cache through
  `safepath.Within`; the `.git` refusal runs before the overlay; the
  layer wins a path both have.
- **Release train (#408).** Verdicts come from the repository's own
  `push`/`schedule`/`workflow_dispatch` runs on `main`
  (`head_repository == repository`), never a pull request's; live runs
  refuse to proceed without `GRAIN_API_URL`/`RELEASE_STAGING_URL`;
  `actions: read` is the only new permission.
- **Attachments (#394).** `placeMessageAttachments` and
  `formatMessageBody` now go through `orchestrator.AttachmentPath`,
  whose `attachmentFilename` drops directory components (either
  separator) and control characters; before this change the chat and
  addenda paths wrote `attachments/<id>-<raw filename>`. Low in effect
  (the write lands inside the sandbox), but worth recording as closed.
- **hostd socket (#374).** Bound inside a fresh `0700` directory,
  chmod `0600`, then renamed into place; no window at a wider mode.
- **GraphQL on GHES (#412), `-grit-url` (#331), drain cap (#379),
  Retry (#416: only a `PrincipalHuman` lifts a person's stop),
  `settings_locked` without a config repo (#401: still
  `settings:write`), attribution rows (#404, #242), source-export
  ceiling (#349), namespace paging (#382, #318), sandbox CLI flag
  refusal (#330), demo/githubsim (#386), `tests.yml` timeouts (#370),
  suite layout (#276).** No new network fetch, credential path or
  authority.
