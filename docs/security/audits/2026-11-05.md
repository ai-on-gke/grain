## Findings

Two findings. Finding 1 is a new authorization layer -- roles for
verified-identity sessions -- that gates each route by scope but lets a
limited role hand a task every grant, auto-merge and approval the role
itself does not hold, which the agent gate refuses every agent. Finding
2 is the recurring shape: the day's new authorization code, including
the role gate itself, is not on the trust-boundary list.

### 1. A limited access role escalates to every scope by filing or editing a task -- **High**, reproduced

**Who can do what.** A person admitted by an allowlist entry whose role
holds `tasks:write` -- the built-in `grain/contributor` (#684:
`grain/viewer` plus `tasks:write` and `ci:write`), or any custom role
with it -- can `POST /api/tasks` or `PATCH /api/tasks/{id}` with
`capabilities` naming any grant (`api:grain/operator`,
`api:settings:write`, `api:secrets:write`, `api:access:write`, a
`gcp#gcp-key` set, …), `autoMerge: true`, `approved: true` and `writes`
to repositories the role does not reach. The task is filed `queued` and
approved by them, and its run then exercises those grants through the
agent API and the sandbox: the person who may only read settings gets an
agent that writes them, auto-merges its pull request without review, and
pushes to a second repository. Nothing in the role gate or the handlers
holds a filing to the filer's role.

**Where.** `pkg/ui/access_roles.go`: `roleGate` (`:288`) calls
`authorizeRoleCall` (`:318`), which checks only the route's scope
(`roleScopeOf`) and the repository `agentCallRepo` names, then calls
`next`. The handlers (`handleCreateTask`, `pkg/ui/tasks.go:2397`;
`handleUpdateTask`, `:2465`) see `requestPerson(ctx) != ""` and take the
body as a person's: `ui.Client.CreateTask` records `Approval` for a
human requester, keeps `AutoMerge`, `Writes` and every capability. For
contrast, the agent gate runs `agentFilingEscalation`
(`pkg/ui/agent_api_gate.go:1043`) and `agentGrantEscalationFrom` (`:635`)
on the same body -- refusing grants the acting task does not hold,
`autoMerge` (`errAgentAutoMerge`), `approved` without `tasks:admin`,
`writes`/`reads` outside its scope -- and holds `PATCH /api/tasks/{id}`
with `capabilities` to `capabilities:admin` plus a reason (`:375`,
`:1709`); the external-agent gate does the same
(`externalAgentFilingEscalation`, `:1939`). The design
(`docs/design/access-rbac.md` §5) says a person is "held to their role"
and §3-4 guard the one escalation it considered -- re-roling the
allowlist (`checkAccessRoleAssignment`, `noWiderThan`,
`pkg/ui/access_principals.go:381-440`) -- but filing is not mentioned.

**Reproduced.** A throwaway `pkg/ui` test on `newRoleHarness`
(`access_roles_test.go`'s harness; not committed): allowlist
`user:con@example.com` with role `grain/contributor`; `GET
/api/auth/user` reports `full=false` with `tasks:write`, `ci:write` and
the `:read` scopes. `POST /api/tasks` as that session with
`{"repo":"acme/widgets","title":"escalate","body":"x","capabilities":["api:settings:write","api:secrets:write","api:access:write","api:grain/operator"],"autoMerge":true,"approved":true,"writes":[{"repo":"acme/other"}]}`
answered **201**: `state: queued`, `approvedBy: con@example.com`,
`autoMerge: true`, `writes: [acme/other]`, `capabilities:
[api:access:write, api:grain/operator, api:secrets:write,
api:settings:write]`, and the stored task carries all four grants.
`PATCH /api/tasks/7` with
`{"capabilities":["api:grain/operator","api:secrets:write"],"autoMerge":true}`
on a seeded task answered **200** and the task now holds both grants
with auto-merge on.

**Severity.** High. `grain/contributor` is the role the design offers
for people who should "file and edit tasks" and nothing more; with it,
every scope of the vocabulary -- the ones marked dangerous, which §4
says only an unlimited admin assigns -- is one filing away, with
auto-merge to land the result. The only mitigation is that the
allowlist is still operator-managed and roles are two hours old: no
deployment has had time to rely on them.

**Fix task filed:** `fix(security): hold a limited access role's task
filings and edits to the role's own scopes`, filed from task 3168 with
`propose_task` (`auto_merge: false`, `hold_for_approval: true`, since it
changes authorization rules). The fix runs the agent's escalation rules
for a limited role in `authorizeRoleCall` after the scope and repository
check: `agentGrantEscalationFrom(held, pattern, body,
s.storedFieldGrants(…), s.tasks.normalizeCapabilityID)` with `held` the
role's `api:<role>` grants (so a grant the role's set does not cover is
refused, and a set marked `Person` is refused outright for a limited
role), and a filing-escalation pass over the same keys
`externalAgentFilingEscalation` reads (`autoMerge`, `approved`,
`interactive`, `autoApproveProposals`, `writes`, `reads`, `readsAll`,
`networkAccess`, `priority`, `keepRunning`, `fixesBaseBranch`,
`templateId`/`reviewTemplateId`, `repo`), each held to the role's
scopes on the repository (`tasks:admin` for `approved`, `merge:write`
or refusal for `autoMerge`, the role's reach for `writes`/`reads`); and
holds `PATCH /api/tasks/{id}` and `POST /api/tasks/{id}/capabilities`
that touch grants to `capabilities:admin` as the agent gate does.
Regression tests: `TestContributorRoleCannotEscalateThroughFiling` in
`pkg/ui/access_roles_test.go` (the two requests above → 403 naming the
role and the first refused key; a filing with no escalating key → 201;

## Examined and found sound

- **Host-script per-call approval (#721).** An `approve: true` script's
  exec waits in `hostScripts.approve` on `localexec.Approver.Approve`
  with the same `argv` and `stdin` bytes the run then uses
  (`ServeHTTP` → `h.run(…, bytes.NewReader(stdin), …)`): no swap between
  what the person saw (args, stdin size, SHA-256, preview) and what
  runs. A grant with no approver fails closed ("needs a person's
  approval, and this grant has no way to ask for it"); a denial,
  timeout (`s.Timeout`), request cancel or grant release each refuse
  with 403 and an audit record; `approving` counts against `MaxCalls`
  so waiting calls cannot exceed the cap. The approval request is made
  by the capability server (daemon-side or on a hostd), not the
  sandbox: the `ghsa_` token travels from `capabilityAdmitterFor`
  (`capability_pass.go`) into the mint context and on to the server
  only when its `mint_<name>` schema advertises `approval`
  (`protocol.Server.Mint`); the sandbox receives only the per-attempt
  host-script token in its descriptor. The token is 256-bit random,
  task-scoped, bounded by the pass deadline plus grace, revoked when the
  pass is released, compared in constant time, and
  `authenticateApprovalCallback` refuses it on any route but
  `POST /api/tasks/{its task}/local-script-approvals{,/{id}/wait,/{id}/expire}`
  (403), so it cannot **answer** (`handleAnswerLocalScriptApproval`
  refuses any `PrincipalAgent`, and the token's principal is one). The
  callback request drops `ActingTaskHeader` and each handler re-checks
  `p.ID == {id}`. `localscripts.Untrusted` (scheduled runs never get
  migrated local scripts) is restated verbatim as
  `task.Origin.Reason == model.ReasonSchedule`. `decodeExecBody` bounds
  the body to `MaxArgs·(2·MaxArgLen+1) + len("---") + 2 + MaxStdin`
  before decoding and refuses NUL bytes and over-long arguments as
  before. The approval `Request` keeps a 4 KiB preview and a SHA-256 of
  stdin; the answer comment carries both.
- **The approval-callback listener (#721) -- a note, not a finding.**
  `startUIServer` serves the full UI handler on a second loopback
  listener (`127.0.0.1:<random>`) *without* `HostGuard`, the DNS-rebinding
  defence (grain#2380). Dropping it was unnecessary -- `HTTPApprover`
  sends an IP-literal `Host`, which `HostGuard` always allows -- and it
  removes the guard from a listener a rebound page on the same machine
  could reach by port scan. What such a page gets is what an
  unauthenticated loopback caller gets: the access-code page
  (`singleTenantOpenRoute`), `whoami`, the hostd install script, and
  guesses at a 160-bit access code that loopback is exempt from
  rate-limiting (`accessLimitExempt`) -- no concrete failure mode, since
  the rebound origin carries none of the daemon's cookies and the code
  is not guessable. Finding 2's fix task asks for `ui.HostGuard(srv,
  "127.0.0.1:0", nil)` around the callback handler while the file is
  being classified; no separate task.
- **Hostd placement (#641).** Which hostd a run's agent CLI goes to is
  now the model connection's (`AgentBackend.Hostd`, `HostdFallback`),
  and a `run: hostd` capability server's is its own entry's
  (`ServerConfig.Hostd`); a task, template, schedule, repository setting
  or declaration that still names one is refused (`TaskHostdRefusal`),
  never ignored, and `PUT /api/tasks/{id}/hostd` is a 400. The old
  agent-gate rule (`agentMayRouteHostd`: an agent may route work only to
  the default hostd or its own) went with the lever it guarded; an
  agent that names a connection (`model`/`agentBackendId` on a filing or
  `propose_task`) now lands its proposal's CLI on that connection's
  hostd, but it could already land it on that connection's credential,
  and a connection in the rotation already receives any task's run: the
  placement is the operator's decision about that connection, no longer
  the filer's about any connection. Selection matches only **registry**
  labels, never the labels a hostd asserts in its hello (`SelectHostd`,
  `placedOn`/`hostdLabels`), which keeps the 11-03 §1 fix. Settings
  checks a selector against the registry (`checkHostdSelector`: unknown
  or revoked names and unmatched labels refused) and `run: hostd`
  against the target hostd's allowlist (`checkRunLocation` →
  `HostCapabilityEntriesFor`). A placed server is attached in its own
  hostd's registry with that hostd's client and receives its resolved
  secrets there; a run whose connection is on A and whose grant is on B
  reaches B's registry (`hostdRoutedServers.Lookup`), and each audit
  record names the hostd its server ran on (`setAuditRecordHostds`).
  `tests/security/hostd_routing_test.go` was rewritten for the new
  shape and passes.
- **Access roles (#684), apart from finding 1.** Unknown roles grant
  nothing (`Missing`, `Full == false`); an entry's default is
  `grain/operator`, so every pre-existing entry keeps full access
  (migration 110). A group lookup that fails leaves that group's role
  out unless the role denies scopes, in which case the caller is
  refused rather than widened. `roleGate` is fail-closed: a route with
  no grantable scope, or an `internal` route absent from
  `humanRouteScopes`, is refused to every limited role, and
  `operatorOnlyRoutes` keeps `/api/mcp`, `/mcp`, `/staging/` and the
  run-side plumbing from limited roles. The access-code session wins
  over a verified identity (unlimited by design). The only handler
  registered outside `Server.route`, `PUT /api/config`, is wrapped as
  `PUT /api/settings`. Re-roling the allowlist is guarded: a limited
  caller may not touch an entry whose role is `Person`, denies scopes,
  or is wider than their own (`noWiderThan`), and assigning a `Person`
  role needs the access code and a reason. The acting-task header is
  judged after the role gate, so it cannot widen a person.
- **External-agent CLI routes (#685).** `GET /api/tasks/wait` is judged
  on every task id it names (`tasksWaitCallRepo`: the first repository
  the grant refuses is the one the gate names; an unknown id is judged
  on `""`, so only a grant for every repository reaches it and the
  handler answers 404). `GET /api/inbox` for a `gma_` token filters by
  the token's `tasks:read` repositories, including notifications raised
  without a repository (looked up through their task); a task's own
  agent with a repository-limited grant is refused for naming no
  repository unless it sends `?repo=`, which the handler applies. `POST
  /api/tasks/{id}/reply` posts only when `CheckReply` says the task is
  parked on a question -- never on a secret request, a config-change or
  an access request -- and is not on `selfMutableTaskRoutes`, so a run
  cannot answer its own question.
- **Release-asset upgrades (#661).** `PUT /api/upgrade/source` needs
  `deployment:upgrade` (dangerous, sandbox-denied) and
  `SetImageSource` refuses a release repository outside the operator's
  set (`validateReleaseRepositoryLocked`: the `-upgrade-release-repo`
  flag, the track's default, the effective image repository and the
  known successor repositories); the flag or env var locks the setting
  (`ErrImageSourceLocked`); every change is recorded in `config_audit`.
  Each tarball's SHA-256 must match both `images.json` and the `.sha256`
  sidecar, the loaded image's ID must match `imageId`, a
  `-upgrade-verify-cmd` deployment defaults to `registry` and refuses
  `release-assets` unless the operator chose it, integrity failures
  never fall back, and `Authorization` is stripped across a cross-host
  redirect. The host-git `forge_download` tool writes only into a
  placeholder the daemon pre-created, under the containment listed
  above.
- **Scratch-branch fixtures (#621).** A proposal self-approves and
  auto-merges as a fixture only when it targets the parent's own
  repository (not the config repository), its base is the parent's
  `qualification/<id>` branch, it carries no `writes`, no change target,
  no ungranted reads and a subset of the parent's grants, and the
  parent's repository-declared template's `push:` list covers that
  branch (`model.ScratchFixture`, `Store.PushesOwnScratchBranch`) --
  the same permission the git proxy enforces on the push; the
  self-approval is still bounded by `ExceededAutoSubmitLimit`.
- **Hostd offers cache (#719).** Only an *unreachable* answer is cached
  (15 s, keyed on the socket's mtime or the remote session); a reachable
  hostd's offers are re-read every time, so allowlist edits and
  revocations take effect at once.
- **`gcp#gcp-key` arguments (#662).** The deprecated `account` (which
  could select a person-granted set under another name) and `activate`
  are refused by `CheckGCPKeyGrantArgs`; stored and state-repo grants
  in the old form are rewritten to `permission_set` only against the
  configured sets (`RewriteGCPKeyCatalogue`), for one release.
- **`scripts/setup.sh` (#718).** A hardening: `grain-postgres.service`
  now starts `initdb` with `--auth=scram-sha-256`, and an existing
  cluster's `trust` lines for `local`, `127.0.0.1/32` and `::1/128`
  are rewritten to `scram-sha-256` (the file is checked not to be a
  symlink, written at 0600 as the grain user) -- closing the loophole
  that any process on a `--network host` machine could connect as
  `grain` with no password.
- **Trust-boundary list (v16, #641; #675).** The entries added exist
  in the tree and the dropped `taskhostd.go` no longer does;
  `TestClassify…` covers them; `.grain/suites` and `.grain/templates`
  changes (#621, #690) are `grain-config`, which the hold already
  classifies.
