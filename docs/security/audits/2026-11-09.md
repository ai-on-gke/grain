## Findings

One finding, Low. Nothing Medium or above.

### 1. A limited role's approve / run-now does not check the task's review template, so it releases a review task holding writes, reads and grants outside the role's ceiling -- **Low**, reproduced

**Who can do what.** #987 (`0851a007`) added `roleApprovalWithin`
(`pkg/ui/access_roles.go:947-997`) so that a limited verified-identity
role approving a stored task -- `POST /api/tasks/{id}/approve`, or
`run-now` on an unapproved task -- is held to what `filingEscalation`
would have let it file: `tasks:admin` on the task's repository, then
`autoMerge`, `keepRunning`, admission, each of `task.Grants`,
`ConfigRepoProposalHold`, `ChangeTargetNeedsPersonApproval`,
`networkAccess`, and `tasks:write` / `tasks:read` over `task.Writes` and
`task.Reads`. It does not look at `task.ReviewTemplateID`.

`filingEscalation` does (`pkg/ui/agent_api_gate.go`, case
`"reviewtemplateid"`): a limited role filing a task that names a review
template is refused unless `roleTemplateWithin` accepts the template's
grants, writes and reads, "because a review is filed approved and
auto-merge". The orchestrator honours that: once the reviewed task's
pull request is open and its run over, `fileReviewTask` →
`newReview` (`pkg/orchestrator/review.go:429-548`) files the review
with `Approval` set, `AutoMerge: true`, `Reads: tmpl.Reads`, `Writes:
WritesBesides(tmpl.Writes, …)` and `Grants: ReviewGrants(tmpl.Grants,
task)`. `ReviewGrants` drops only *person-only* grants the reviewed task
does not hold; it keeps every other grant, and it never filters reads or
writes.

So a role holding `tasks:admin` (and `tasks:write`, `tasks:read`) on
`acme/widgets` only can approve a stored `acme/widgets` task whose
`ReviewTemplateID` names a template with `writes: [acme/gadgets]`,
`reads: [acme/gadgets]` and a grant such as `api:tasks:write` -- and
grain then files, approved and auto-merging, a review task that pushes
to and reads `acme/gadgets` and holds `api:tasks:write`, none of which
the role could have handed out. The same role is refused 403 when it
tries to file that task itself. The task to approve has to be there
already: filed unapproved by an unlimited person, or proposed by an
agent whose own task holds those writes (`ReviewTemplateWithinTask`
bounds a proposal's review template by its proposer's grants, which is
why this is Low -- nothing new is minted, but the role's ceiling, which
is what #987 exists to enforce, is bypassed on exactly the field the
commit message says it mirrors from templates and schedules).

**Reproduced.** A throwaway `pkg/ui` test (not committed) installed a
`widgets-admin` scope set (`tasks:read, tasks:write, tasks:admin,
dispatch:read, dispatch:write` on `acme/widgets`), stored template
`heavy-review` with `Writes: [acme/gadgets]`, `Reads: [acme/gadgets]`,
`Grants: [api:tasks:write]`, and:

- `POST /api/tasks` as `wade@example.com` with `reviewTemplateId:
  heavy-review` → **403** `cannot set reviewTemplateId: cannot grant
  api:tasks:write, which the role does not hold` (the control);
- stored task `9501` (`Target: acme/widgets`, `ReviewTemplateID:
  heavy-review`, unapproved), then `POST /api/tasks/9501/approve` as the
  same role → **200**, `approvedBy: wade@example.com`, state `queued`.

A second throwaway (`pkg/model`) confirmed `ReviewGrants` keeps
`api:tasks:write` and `api:ci-read@acme/gadgets` (not person-only) and
drops `api:tasks:admin` / `api:settings:write`, so the review filed from
`heavy-review` would carry the non-dangerous grant and both repository
targets.

**Severity.** Low. It needs a stored task that already names such a
template (filed by somebody allowed to), the review is filed only after
that task has opened a pull request, and person-only grants are still
dropped at filing. What it defeats is the invariant #987 states for
limited roles ("every grant, setting, write and read task carries must
be one filingEscalation would have let it set"), on a field
`filingEscalation` itself treats as grant-bearing.

**Fix task filed:** `fix(security): hold a limited role's approve and
run-now to the task's review template as filing is` --
`auto_merge: false`, `hold_for_approval: true` (`pkg/ui/access_roles.go`
is `auth-routes`). In `roleApprovalWithin`, when
`task.ReviewTemplateID != ""` and it is not
`model.DefaultReviewTemplateID(*task.Target)`, load the template and
run `roleTemplateWithin(a, "reviewTemplateId", *tmpl, allowedRepo,
normalize)`, the same call `filingEscalation`'s `"reviewtemplateid"`
case makes for a role (a missing template passes, as it does there).
Regression test: a case in
`TestLimitedRoleApprovalIsHeldToTasksAdminAndTheRolesCeiling`
(`pkg/ui/access_roles_test.go`) seeding a template whose `Writes`,
`Reads` or `Grants` exceed `widgets-admin` and a task naming it in
`ReviewTemplateID`, asserting both `approve` and `run-now` answer 403
naming `reviewTemplateId` and the role on REST and `POST /api/mcp`, the
task stays unapproved, and the repository's default review template is
still accepted.

- **`gcp` token-mode gained `POST /runs/<attempt>/introspect` (#984).**
  It answers RFC 7662 `active/username/exp` for a token the sandbox
  presents in the form body, matched by SHA-256 against the tokens this
  attempt minted (`lookupMinted`, constant-time compare, capped at 64,
  bounded by the grant's deadline). It discloses only the account name
  and expiry to a caller already holding the token, which GCP's own
  tokeninfo would tell it; the per-attempt secret is still required for
  minting. Fine as designed.
- **`relayProposedTasks` now decodes a proposal's unified `grants:`

  `proposedWrites`, the capability loop (now spelled through
  `StoredGrantSpelling`) and `EscalatedCapabilities` read; the proposal

  skips the proposal with a log line rather than filing it bare. No
  widening found; `pkg/model/canonical_grant.go` is now classified
  (v25), so later edits there hold.
- **`checkCapabilitiesBeforeMigration` (#942)** relaxes `grain state
  check -migrate` / `prepare-upgrade` on an older-schema dump to
  structure and secret references only, and then re-runs the full
  `checkCapabilities` on the migrated configuration
  (`checkMigratedCapabilities`). Current-schema checks and the live
  state-repo sync (`pkg/orchestrator/sync.go`, unchanged) are not
