## Findings

Two findings. Finding 1 is a small, concrete gap in an authorization
rule the day's console-session change opened; finding 2 is the
recurring shape -- the day's new authorization code is not on the
trust-boundary list, so an agent's auto-merge pull request can change
it with no hold -- for a day that added more such code than most.

### 1. A session's own run can turn on `readsAll` and read every working repository, which the gate forbids it to do by name -- **Low**, reproduced

**Who can do what.** The run of a standing session whose task holds
`api:sessions:write` -- a scope no preset carries and an agent cannot
give itself, so one a person granted -- on a session a person opted out
of reading every repository (`readsAll: false`, #539), can `PUT
/api/console-sessions/{id}` with `{"readsAll": true}` on its own session.
The gate admits it, the setting flips, and from the next reconcile the
session's task reads every repository in `repo_config`
(`ConsoleSessionAutoReads`), on a daemon whose settings are not managed
by a config repository. The same run asking for one of those
repositories by name -- `{"reads": ["acme/secret-repo"]}` -- is refused:
"an agent cannot grant read access to acme/secret-repo, which its own
task cannot read". The two requests give the same thing; only one is
checked.

**Where.** `pkg/ui/agent_api_gate.go` `agentFilingEscalation` (`:1007`)
inspects a body's `reads` (`:1034`), `writes` (`:1024`),
`tasksApproved`/`autoApproveProposals` (`:1049`), `networkAccess`,
`hostd`/`defaultHostd` (`:1059`), `autoMerge`, `templateId` -- and has
no case for `readsAll` / `reads_all`, which
`pkg/ui/console_sessions.go` `UpdateConsoleSession` (`:599`) applies.
The own-session rule (`:551-556`) lets a session's run reach `PUT
/api/console-sessions/{id}` for its own session, which is right for a
title; `readsAll` arrived with #539 (`pkg/model/console_session_reach.go`,
`ReadsAllRepos` `:77`, `ConsoleSessionAutoReads` `:160`) and the gate
was not taught it. `checkSettingsWritable` (`:602`) refuses the write
only where a config repository owns settings.

**Reproduced** with a throwaway `pkg/ui` test (not committed): a
director session with `Capabilities: [self-debug, api:sessions:write]`
and `ReadsAll: &false`, its task filed with `FileConsoleSessionTask`
(reads `acme/grain-config` only), `TargetRepos: [acme/widgets,
acme/docs, acme/secret-repo]`; `asAgent(taskID, PUT,
/api/console-sessions/director, {"reads":["acme/secret-repo"]})` →
**403** with the refusal above; `{"readsAll":true}` → **200**, the
response's session now `readsAll: true, autoReads: [acme/docs,
acme/secret-repo, acme/widgets]`. With a `StateRepo` configured the
second request is a 409 `config_managed_externally` instead -- the gate
still let it through; the settings store refused it.

**Severity.** Low: it needs a person to have granted the session
`api:sessions:write` *and* to have opted it out of `readsAll` -- the
default since #539 is on -- and it widens reads, not writes. It is a
real hole in a rule that is otherwise airtight, on a surface
(`console-sessions`) agents may only touch for their own session.

**Fix task:** filed (see closing note; title `fix(security): hold a
session run's readsAll edit to the gate's reads rule`). Fix: in
`agentFilingEscalation`, a `case "readsall", "reads_all":` that refuses
`true` unless the acting task already reads every working repository
(`model.ConsoleSessionAutoReads` of its own session is a subset of
`acting.Reads`) -- or, simpler and matching `tasksApproved`, refuses an
agent turning it on at all: it is an operator's per-session opt-out.
Regression test: `pkg/ui/agent_api_test.go`
`TestSessionRunCannotTurnOnReadsAll` -- the scenario above returns 403
for `{"readsAll": true}` and still 200 for `{"title": "x"}`. Because it
changes authorization rules in `agent_api_gate.go`, it should land held
for a person (`hold_for_approval: true`, `auto_merge: false`).

### 2. The day's new authorization code is unclassified, so an agent's auto-merge pull request can change it with no security hold -- **Medium**, reproduced

**Who can do what.** Any task with an auto-merge pull request against
`ai-on-gke/grain` -- the default for the deployment's own fix tasks --
can edit the files below and merge with no security review, no hold and
no person's Submit, because `trustboundary.Classify` returns nothing for

## Examined and found sound

What was read across the boundary and why it holds, so tomorrow can
tell what was looked at.

- **`/api/hostd/install.sh` (#541).** Open route (`singleTenantOpenRoute`,
  `requiresAccess`) serving an embedded script with three placeholders;
  the daemon URL is `r.Host` as the caller reached it (a liar gets a
  script that dials their own host), release and image are filled only
  for a caller the access gate would admit, and a bearer shaped like an
  access code is counted against the same rate limiter so the route
  cannot be used to guess the code. Each value is held to a character
  class before it reaches a single-quoted shell string or the systemd
  unit. The script refuses to take the token on the command line, reads
  it from `$GRAIN_HOSTD_TOKEN` or stdin, writes it `0400` to the hostd
  user through `mktemp` + `mv` and refuses a symlinked target; a
  downloaded binary needs `--sha256` and must say it is a grain hostd
  of the daemon's release. `hostdInstallRoute` is GET/HEAD on the exact
  path.
- **`request_access` (#648).** The check route is `internal` and called
  by the mcpserver for the run's own task; grant/deny are `internal`
  and refuse any non-`PrincipalHuman` actor (`pendingAccessToDecide`)
  and any external token before reading the body. Granting goes through
  `UpdateTask` and `SetCapabilityGrant` -- the task pane's own paths --
  so repository allowlists, catalogue refusals and grant normalization
  apply; an item the task already holds is skipped; a Dangerous grant
  goes through only because a person chose it, and the card says so.
  Decisions are recorded with who made them and posted into the
  conversation; a denial tells the next run not to ask again.
- **Controller MCP (#511).** The endpoint re-dispatches every
  `grain_invoke` through the real mux, so `agentAPIGate` (acting task
  scopes, sandbox-channel denials, external-token repo limits,
  `isNoTaskContextRoute`, reason-required DELETEs) runs on each call
  with the outer principal, headers and `RemoteAddr`; the pre-check in
  `allowsRoute` is a listing filter, not the gate. An external token's
  `X-Grain-Acting-Task` is ignored rather than widened to a task's
  grants. The sandbox side reaches it only through
  `protocol.NewEndpointProxy`, which forwards an allowlist of five
  headers and then `Set`s its own, so a sandbox process cannot supply
  its own acting task or access code; the proxy refuses redirects and
  never dials the nominal host (it goes through `LoopbackRoundTrip`
  in-process). `grain_submit_task` files through `POST /api/tasks`
  with `approve` defaulting to false. The `X-Grain-Access-Code` header
  (new) is held to the same rate limiter as a bearer code
  (`accessCodeCandidate`).
- **gcp permission sets, token mode and person-granted values (#631).**
  The token data plane is a loopback listener forwarded per attempt;
  `/runs/<attempt>/token` and `/id-token` need the attempt's own random
  per-attempt secret (constant-time compared), are forgotten at
  release, and mint by impersonation under the current configuration
  with the grant's deadline, so nothing in the sandbox outlives the
  attempt and GCP never sees the secret. `x-grain-person-granted`
  values are read from the server's advertised schema at discovery and
  make a grant `GrantByPerson` whether named through `permission_set`
  or the deprecated `account` alias (including `"default"` when the
  first set is reserved), and a grant that leaves the argument out is
  judged by the schema default -- the branch's own commits closed the
  alias bypass before merging. Observation only: `personGrantedArgs` is
  empty between a daemon start and the server's first `tools/list`, so
  `GrantKindOf` would say `GrantCovered` for a reserved value in that
  window; `Covers` still needs the parent to hold the equal grant, so
  the window does not let an agent mint one it was not given.
- **In-process release server (#614).** `release#image-signing`,
  `registry-push`, `package-publish` are CI-only three times over: left
  out of a job's pass by `ciCapabilityRefs` on any event the rule does
  not admit, refused by `Permits`, and refused by the method's own
  `Mint` when the context carries no `model.CIMint` or the wrong event.
  `RepoGranted` keeps them to a repository's CI capabilities list, and
  `agent_api_gate.go:929` keeps an agent from adding one. The retired
  providers' `Resolve`/`Materialize`/`Revoke` are reused unchanged, with
  the secret store's audit naming the job.
- **Allowed users and groups in the database (#580).** Entries are
  `user:` or `group:` only; service accounts and domains are refused at
  normalization; the gcp-key pool accounts are dropped on import; the
  tables are explicitly *not* state-repo settings ("so a bad or
  compromised config-repo pull request can neither lock operators out
  nor grant sign-in access"); `access:write` is Dangerous; a service
  account that owns an active hostd row may dial `/api/hostd/connect`
  (where its per-hostd token and owner match still apply) without
  being admitted to the UI; a person is now the only issuer of a
  dangerous-scope external token. Changing a hostd's owner drops its
  live session (#599).
- **Hostd routing (#565, #598, #551, #549, #550, #582).** Selection
  matches the registry row's labels only -- yesterday's finding 1 --
  with the hostd's self-asserted labels shown and never matched. A
  repository's `defaultHostd` and a template's `hostd` are held to
  `agentMayRouteHostd` in the same escalation gate as a filing's own
  pin. Capability passes record the hostd they were minted on and are
  released through the same servers; recovery only decides rows the
  hostd owns.
- **Auto-merge after holds (#609) and human-only reclassification.**
  `restoreAfterHolds` turns auto-merge back on only when the write
  drops the last of grain's own hold links *and* a
  `trust-boundary-cleared` link with a target stands, no approval is
  pending, nobody declined and nothing awaits a person; links are not
  writable through `PATCH /api/tasks` (`UpdateTaskRequest` has no
  `links`), and the clearance is bound to the head SHA the merge is
  checked against. Review findings and closed fixes now mark the task
  `AwaitPersonForAutoMerge`, which `heldForHuman` honours. A human-only
  hold is re-read on a new head and let go only if the head no longer
  touches what held it; `!known` still fails closed.
- **Release approval on GitHub Actions (#607, #590).** `DecideRelease`
  checks `PrincipalHuman` before anything; the record (repo, version,
  decision, `-pending` commit, approver, soak and breaking answers,
  15-minute expiry) is signed with an ECDSA key under the data
  directory (`attest.FileSigner`) and verified in `promote-release.yml`
  by `verify-release-approval.sh` against a repository variable, with a
  by-hand dispatch still refusing `[bot]`/`grain-ci*` actors;
  `promote-release.yml` is `workflow_dispatch` only. All of it is
  `release-promotion` (RequiresHuman) at v13.
- **Trust-boundary v12 narrowing (#608).** `release-images.sh`,
  `release-from-trunk.sh`, `release.yml`, `promote.yml` moved from
  RequiresHuman `release-promotion` to review-releasable
  `release-machinery`, with a `Review` checklist the automated reviewer
  must clear (cannot move `vX.Y.Z`/`latest`, no wider `permissions:` or
  secrets, no weaker person check, no `RELEASE_MAJOR` raise). This is a
  deliberate loosening the operator submitted under `hold-policy`
  (releases playbook §0.3); it is recorded here so the next night knows
  the publishing workflow now merges on a clean automated review. The
  new `TemplatePush` guard (a template's `push:` set) is RequiresHuman
  and fails closed when either side cannot be read.
- **GitHub workflows.** `rc-qualification.yml`'s `workflow_run` trigger
  checks out `main`, reads nothing from the triggering run, and holds
  `actions: write` for re-runs and cancels only; `tests.yml`'s change is
  a package list and a timeout. No `pull_request_target`, no new
  `secrets.*` in pull-request-triggered jobs, no `${{ github.event.* }}`
  in `run:` lines.
- **`git_ref` schedules (#624).** A repository's declaration may not
  watch `grain/config`; the daemon polls with its own credential only a
  repository in `TargetRepos` ("a declaration is not a way to have the
  daemon read a repository nobody put on the list"); a firing carries
  the ref's commit, not content.
- **Release-triggered upgrade (#605).** Opt-in mode; polls the
  deployment's own image registry for the newest non-rc, non-retracted
  tag in its edition, waits an hour of settle, then schedules through
  the same row an operator's "upgrade once idle" writes. No webhook
  input.
- **Access-code deep link (#564).** `localReturnPath` accepts a single
  leading `/`, refuses `//`, `/\`, backslashes, control characters,
  `#`, any scheme/host/userinfo and `/api/` paths; the gate never
  echoes a return path, the page's script fills it from the address
  bar.
- **Verifier unavailable (#633, #579).** A verifier that cannot answer
  yet is a 503 with `Retry-After`, still refusing -- for people, the
  API and a dialing hostd alike; a bad assertion stays 401.
- **State-repo sync (#575, #612, #624).** Unapplied config commits
  found across a schema upgrade go through `applySettingsFromDirs`, the
  normal validated apply, or are reported; the mirror check is a
  warning.
- **Console sessions read every working repo by default (#539).** A
  design decision an operator made; agents cannot create sessions
  (`isNoTaskContextRoute`, the gate's own-session rule), the CI-read
  default is `GrantByDefault` and declinable, and re-adding a declined
  default is an added grant the gate checks against the acting task.
  Finding 1 is the one edge the gate missed.
- **Merge queue (#413, #597, #604).** Lanes merge up to 5 per cycle
  with no ordering; a 405/403/422 right after another merge moved the
  base is re-judged next cycle, never forced; nothing hands auto-merge
  back on grain's judgement past `heldForHuman`.
