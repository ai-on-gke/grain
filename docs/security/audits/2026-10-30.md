### 1. `task://` serves every sibling task's prompt, conversation and transcripts to a run holding no grant — **Medium**, reproduced

PR #209 (`905f3e4e`, task-1925, commit `f3265d97` "let task://<id> read
tasks in the caller's repositories") changes `pkg/namespace/stage2.go`
`resolveTask` and `pkg/model/store.go` `SandboxNamespaceScope`. Before
it, `task://<id>` answered only the run's own task unless the run held
`self-debug` or an unscoped `api:tasks:read` (`Scope.PermitsTask`),
which is what `docs/design/grain-namespace.md` (§ roots table and
§"Access control": "`task://` … requires `self-debug`, 403 otherwise")
and `docs/design/sandbox-first-agent-surface.md` ("`task://<own-task-id>/…`
own task metadata, comments, handover") say. Now `Scope.TaskReadRepos`
is filled from the task's **target, reads and writes** as well as from
`api:tasks:read@repo` grants, and `PermitsTaskRepo` also admits any task
whose repository equals `Scope.TaskRepo`. Nothing is required of the
caller beyond working in the same repository.

The whole of `task://<id>/` is served that way, not just the record:
`prompt.md`, `conversation.md` (every comment, the person's included),
`handover.md`, `transcript.md` and `attempts/<n>/{prompt,transcript}.md`
— the attempt transcripts are read from `run_transcripts` unredacted
(`ui.Client.AttemptTranscript`).

The agent API does not agree with it: `GET /api/tasks/{id}`,
`/prompt` and `/attempts/{n}/transcript` are `tasks:read`, which a task
with no `api:` grant does not hold (`authorizeAgentCall` refuses before
`agentMayRead` is consulted), and #142 in the same day's merges made
`GET /api/tasks/{id}/messages` for another task `task-admin`-only. The
MCP `read_grain_task*` tools are `self-debug`'s. `task://` is now the
one door of the three that opens with nothing.

**Reproduced** with a throwaway test in `pkg/namespace` (not
committed): `Scope{TaskIDStr: "100", TaskRepo: "acme/widgets"}` with no
grants, against a `stubTaskProvider` holding task 101 in `acme/widgets`
with a prompt, a conversation and one attempt. `GET /fs/task/101/`
`prompt.md`, `conversation.md`, `transcript.md`,
`attempts/1/transcript.md` and `attempts/1/prompt.md` all answered
**200** with the sibling's text. (The merged test
`TestTaskReadsTasksInTheScopesRepositories` pins the record read for
the same bare scope.) `SandboxNamespaceScope` sets `TaskRepo` for every
run whose task has a target, so this is every task sandbox.

**Who can do what they should not:** the agent of any task in
repository R — an auto-filed proposal, an imported issue (#194) once
approved, a schedule firing, a CI-fix task — with no capability and no
API grant reads the prompt body a person wrote, every comment a person
left, and the complete tool-call transcripts of every other task in R,
including tasks that hold capabilities it does not (a release task with
`package-publish`, a task with `gcp-key` or a `localscripts` secret,
whose transcript shows what its commands printed), and of tasks in any
repository its `reads:` names. The transcript is the one place a
placed credential's material routinely ends up in clear (an agent that
`cat`s a key file or echoes a token). A task on grain/config with
`reads: [ai-on-gke/grain]` reads every core task's transcript, and the
reverse. The operator approved the record read; the design documents
and the API's own rule say the rest needs a grant.

**Fix (an authorization rule; hold for a person):** in
`pkg/model/store.go` `SandboxNamespaceScope`, fill `TaskReadRepos` from
`apiSet.Repos("tasks:read")` only (drop the `addTaskRepo` calls for
target, reads and writes), and in `pkg/namespace/stage2.go`
`PermitsTaskRepo` drop the `s.TaskRepo` clause, so a sibling is readable
exactly when `api:tasks:read[@repo]` or `self-debug` says so — the same
rule as `GET /api/tasks/{id}` — and `grain task read <sibling>` tells
the agent which grant to ask for, as the API already does. If the
product wants grant-less sibling reads, keep them to `record.md` and
`summary.md` and leave `prompt.md`, `conversation.md`, `handover.md`
and `attempts/` behind the grant. Update
`docs/design/grain-namespace.md` either way.

**Regression test:** `TestTaskReadsSiblingsOnlyWithATasksReadGrant` in
`pkg/namespace/namespace_test.go` (replacing the "bare scope still reads
its siblings" half of `TestTaskReadsTasksInTheScopesRepositories`): a
scope with `TaskRepo` set and no `TaskReadRepos` gets 403 on
`task://<sibling>/{record,prompt,conversation,transcript}.md` and
`attempts/1/transcript.md`, and 200 once `TaskReadRepos` names the
repository; plus a `pkg/model` store test that `SandboxNamespaceScope`
for a task with target, reads and writes but no `api:` grant returns an
empty `TaskReadRepos`.

**Fix task:** filed by this run (see closing note),
`auto_merge: false`, `hold_for_approval: true`.

### 2. `NeverAutoMergePaths` still omits the tables that carry approval and auto-merge switches — **Low**, reproduced

PR #166 (`851afd8e`, task-1815) is the fix for the 2026-10-29 report's
finding 2 and adds the template, schedule, standing/persistent-sandbox
and `gcp_key` tables to the ceiling. The previous report's list also
named `tables/custom_field.json` and `tables/qualification_*.json`;
those were left out, and the day's reading turned up one more. Of
`staterepo.SettingsTables` (`pkg/staterepo/bind.go:303`, what
`staterepo.Apply` imports into the running daemon), these are outside
the ceiling:

- `tables/qualification_config.json` (+ `qualification_item`,
  `qualification_item_depends_on`): a repository's qualification plan,
  whose `RequireApproval` is "requiring a human's approval before any of
  a run's tasks may dispatch" and whose `AutoPromote` promotes a
  candidate once its run passes (`pkg/model/qualification.go:57-69`,
  `orchestrator/qualifications.go:87`).
- `tables/suite.json` (+ `suite_item`, `suite_sequence`): a suite's
  `RequireApproval`, `AutoMerge` and `AutoApproveProposals`, copied onto
  every task a suite run files (`pkg/model/suite_store.go:582-627`).
- `tables/custom_field.json`, `tables/board*.json`: not security-bearing
  on their own; listed for completeness.

**Reproduced** with a throwaway test in `pkg/trustboundary` (not
committed): for each of `tables/qualification_config.json`,
`tables/qualification_item.json`, `tables/suite.json`,
`tables/custom_field.json`, `IsNeverAutoMergePath` is **false**,
`ValidateConfigPolicy(ConfigPolicy{AutoMergePaths: []string{p}})` is
**nil**, and `ClassifyState([]string{p}, p)` returns **no match**.

**Who can do what they should not:** as in the previous report — once
an operator has put one of those paths in `auto_merge_paths`, which the
validator accepts although the ceiling's doc comment promises the
contrary, a task with `writes:` on grain/config and auto-merge lands,
and the daemon applies, a suite row that files auto-merging,
auto-approved tasks, or a qualification plan that dispatches its run's
tasks without a person and auto-promotes. The precondition is still an
operator mistake, hence Low; the ceiling exists to make it impossible.

**Fix (a `pkg/trustboundary` change; hold for a person):** add
`tables/suite.json`, `tables/suite_item.json`,
`tables/suite_sequence.json`, `tables/qualification_config.json`,
`tables/qualification_item.json`,
`tables/qualification_item_depends_on.json` to `NeverAutoMergePaths`
(`pkg/trustboundary/trustboundary.go`), and consider closing the class
for good with a test that every `staterepo.SettingsTables` entry whose
row type carries an approval, auto-merge, grant or secret field is in
the ceiling.

**Regression test:** extend
`TestNeverAutoMergePathsCoverGrantAndSecretTables` in
`pkg/trustboundary/state_test.go` with the six paths, and
`pkg/staterepo/settingstables_held_test.go` with `suite` and
`qualification_config`.

**Fix task:** filed by this run (see closing note),
`auto_merge: false`, `hold_for_approval: true`.

## Observations (not filed)

- **Imported issues approved by repository setting (#194).**
  `fileImportedIssue` approves the task when
  `RepoConfig.IssueImport.Approved` is set, with the repository's
  default grants. For a public repository that is "anyone who can open
  an issue writes an approved task's prompt". The setting is a person's
  (repo_config is in the ceiling, and the API path is `repos:write`,
  refused on the sandbox channel) and defaults off; its Settings copy
  should say what it means.
- **Fork heads as a task's branch (#178).** A person files the task; the
  run checks out `refs/pull/N/head` of a fork into a sandbox holding the
  repository's credential. That is the external-PR adoption design, and
  the same as a person running a contributor's branch; the task's
  prompt extension and hooks come from grain, not the tree.
- **Warm session sandboxes (#198).** Between turns the sandbox keeps its
  attempt-bound proxy token for the idle TTL (30m default). The proxy
  refuses it meanwhile: `resolveSandboxScope` refuses `/fs/`, `/cli/`
  and `/api/` without a live run, and `Store.GitScope`
  (`liveRunTarget`) answers no scope for git, so a background process
  the agent left has no authority until the next turn mints a fresh
  token for its attempt. The grants-changed release closes the
  withdrawn-grant case. Noted so the next review knows it was looked
  at.
- **`-grit-url` attestation keys cannot be pinned** (#176's own report):
  a proxy between the daemon and `grit serve` that can also answer the

## Examined and found sound

- **Agent API gate after #209, #171, #141, #142, #193.** The ratchet
  passes; `grain-ci` opens only reads, only for repositories the task's
  runs may read, and a CI run id that does not resolve to a repository
  is refused. `GET /api/tasks` for a repo-limited `tasks:read` is
  narrowed to the one repository or refused. Grant escalation on
  `capabilities` bodies checks every scope and repository a passed-on
  set reaches. `OpenConfigPullRequest` is human-only and held.
- **Sandbox CLI `/cli/ci/runs?task=`, `/cli/pr/status?task=|ref=`,
  `/cli/ci/run?id=` (#209).** Each goes through `scope.PermitsCI(repo)`
  on the resolved repository; a task or run outside it is answered as
  one that does not exist.
- **Event-gated CI capabilities (#180).** Traced from
  `handleStartCIRun` through `ci.Service.Start`, `prepareJob`,
  `readoptJob` and `ResolveCICapabilities`; the sandbox CLI's
  `grain ci retrigger`/`run-job` reach the same handler with an agent
  actor and are withheld alike.
- **Git signing (#164).** `resolveSigningCredential` requires a target
  repository, `Authorize(…, "git-receive-pack")`, an ambient credential
  and a configured signing key; the placeholder and
  `PrimaryAmbientCredential` fallbacks are gone, and the payload must be
  a commit or tag object. Closes the 2026-10-29 finding 1.
- **CL Submit gate (#182).** `taskReviewCleared` is satisfied only by a
  `LinkCLReviewCleared` link, which only `orchestrator/clreviews.go`
  writes.
- **Infra-review proposals (#197).** A proposal that names a source
  repository the deployment works in skips the tuning-parameter
  allowlist and takes the ordinary proposal path (catalogue, hold
  policy, `parkUnreached`); an unknown repository does not.
- **hostd built-ins (#207).** Implicit entries run `BuiltinCommand`
  only when it is an absolute, clean path to a regular file owned by
  `AllowlistOwners` and not group/other-writable; fixed args, `ProxyVars`
  env, `GRAIN_CAPABILITY_PROBE` on `ExtraArgs` entries.
- **Plain-git credential test (#165).** Sends the stored credential only
  to the stored host's base URL through the proxy's own forwarder;
  owner/name go through `model.ParseRepo`.
- **`scripts/setup.sh` (#136, #140).** Warning filtering and readiness
  text; no new network fetch or credential on argv.
