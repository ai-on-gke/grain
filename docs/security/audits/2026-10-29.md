### 1. The host-side git signing oracle signs for a sandbox the proxy authorises for no repository — **Medium**, reproduced

PR #85 (`25f78fde`, task-1584) adds `POST /_grain/git-sign` to the
sandbox proxy (`pkg/gitproxy/sign.go`): a sandbox posts a commit or tag
payload and the host signs it with the host account's own SSH signing
key (`ssh-keygen -Y sign -n git`), so commits pushed under an ambient
credential verify as the host's owner on GitHub. The private key never
leaves the host; the check this depends on is `resolveSigningCredential`
(`sign.go:71-111`), documented as serving "a sandbox whose target
repository uses an ambient credential with SSH commit signing
configured".

The code is wider than the comment. `resolveSigningCredential` takes
the sandbox's target from `sandboxTargetRepo`, but when that resolves
nothing — a `no_repo` task, or any sandbox the authorizer grants no
repository — it falls through to `resolveCredential(ctx, sandbox, "",
"owner", "repo")` (`sign.go:94`, a placeholder repository), and if that
yields nothing, to `p.Credentials.PrimaryAmbientCredential()`
(`sign.go:98-100`), the first `*.ambient.json` in the credential
directory. Nothing in the path asks whether the sandbox may *write* the
repository it claims, and the payload itself is unconstrained beyond
`MaxGitSignPayloadBytes` (1 MiB): any bytes are signed in the `git`
namespace.

**Reproduced** with a throwaway test in `pkg/gitproxy` (not committed):
a `GitProxy` with `stubAuthorizer{allow: {}}` (the sandbox is authorised
for no repository — `GET /owner/repo.git/info/refs` through the same
proxy answers 404), an ambient credential `op` set up as
`TestEndToEndSandboxSSHCommitAndTagSigningViaGitProxy` does, and a
sandbox token for `sandbox-norepo`. `POST /_grain/git-sign` with a
hand-written commit object (`tree 4b825dc…`, author/committer `Olive
Signer <olive@example.com>`, message `forged`) and basic auth
`sandbox:<token>` answered **200** with a `-----BEGIN SSH
SIGNATURE-----` block, both with no credential override and with
`fixedOverride("op")`.

**Who can do what they should not:** the agent of any task that has a
sandbox but no repository grant (a `no_repo` task, a task whose
`writes:` is empty, a CI sandbox of a repository with a non-ambient
credential once the fallback is reached) can obtain the host owner's
SSH signature over arbitrary git commit and tag objects — including
commits naming any tree, parent, author and message — in a deployment
that has configured one ambient credential with signing. The object can
leave the sandbox in a comment, an attachment or a pull request body and
be pushed by anybody to any repository, where it verifies as the host
owner. The ambient design already lets a sandbox push *as* the host
owner to repositories it is granted; this lets a sandbox granted nothing
mint verified objects for repositories it may not touch.

**Fix:** in `resolveSigningCredential`, require `sandboxTargetRepo` to
name a repository and `p.Authorizer.Authorize(ctx, sandbox, owner,
repo, "write")` (or the equivalent `WriteScopes`/`GitScope` write check)
to pass; delete the `"owner"/"repo"` placeholder resolution and the
`PrimaryAmbientCredential` fallback (lines 93-100). Optionally, parse the
payload with `git hash-object --stdin -t commit|tag` semantics and refuse
anything that is not a well-formed commit or tag object.

**Regression test:** `TestGitSignRefusesSandboxWithoutWritableRepository`
in `pkg/gitproxy/sign_test.go`: the set-up above, asserting 403 for an
empty authorizer, 403 for a sandbox with read-only scope on
`owner/repo`, and 200 only for a sandbox with write scope on a
repository whose credential is ambient.

**Fix task:** filed by this run (see closing note), `auto_merge: true`
(`pkg/gitproxy` is `credential-proxy`, which already gets a security
review before merge).

### 2. `NeverAutoMergePaths` omits the tables that bind secrets and grant capabilities — **Low**, reproduced

PR #92 (`8eec1bc1`, task-1591) is the fix for the 2026-10-26 report's
finding 1: every path in `grain/config` is now `StatePrivilege`
(`RequiresHuman`) unless `settings/config-policy.yml` on the base branch
lists it in `auto_merge_paths`, and `NeverAutoMergePaths`
(`pkg/trustboundary/trustboundary.go:375-401`) is "the hardcoded ceiling
of config-repository path globs that always require a human Submit …
even if a pattern in `settings/config-policy.yml` would otherwise match
them". `ValidateConfigPolicy` refuses a pattern that overlaps the
ceiling, and `ClassifyState` checks the ceiling before the policy, so
the ceiling is what bounds an over-broad or mistaken policy.

The ceiling lists the settings documents, `grain_config`, `repo_config`,
`api_scope_set`, the credential tables, `agent_backend`,
`console_session`, `repo_workflow`, scripts, workflows and
`schema-version`. It does **not** list these `SettingsTables`
(`pkg/staterepo/bind.go:303`) that `staterepo.Apply` imports into the
running daemon on the next tick:

- `tables/standing_sandbox.json`, `tables/standing_sandbox_secret.json`,
  `tables/standing_sandbox_env.json`, `tables/persistent_sandbox.json`
  — a standing sandbox's image and the secret-store keys injected into
  it as environment variables (the exact rows the 2026-10-26 report
  named);
- `tables/gcp_key.json`;
- `tables/template_grant.json`, `tables/schedule_grant.json`,
  `tables/template_write.json`, `tables/schedule_write.json` — the
  capability grants and extra write repositories of templates and
  schedules, for a deployment whose dump still carries them as tables
  rather than only in `settings/templates.yml`;
- `tables/custom_field.json`, `tables/qualification_*.json`.

**Reproduced** with a throwaway test in `pkg/trustboundary` (not
committed): `ValidateConfigPolicy` accepts `auto_merge_paths` of
`tables/standing_sandbox_secret.json`, `tables/standing_sandbox.json`,
`tables/standing_sandbox_env.json`, `tables/persistent_sandbox.json`,
`tables/gcp_key.json`, `tables/template_grant.json`,
`tables/schedule_grant.json`, `tables/custom_field.json` with no error,
and `ClassifyState([...those paths...], policy.AutoMergePaths...)`
returns **no match**, i.e. no hold.

**Who can do what they should not:** once an operator has put any of
those paths in the policy — which the validator and the state check
accept without comment, although the ceiling's own doc promises they are
held regardless — a task with `writes:` on `grain/config` and
auto-merge (a director session's proposals inherit it) merges, and the
daemon applies, a row that binds a deployment secret into a standing
sandbox it then reads, or grants a template a capability, with no person
involved. The precondition is an operator mistake, which is why this is
Low; the ceiling exists to make that mistake impossible, and today it
does not.

**Fix:** add `tables/standing_sandbox.json`,
`tables/standing_sandbox_secret.json`, `tables/standing_sandbox_env.json`,
`tables/persistent_sandbox.json`, `tables/gcp_key.json`,
`tables/template_grant.json`, `tables/template_write.json`,
`tables/schedule_grant.json`, `tables/schedule_write.json` to
`NeverAutoMergePaths` (or `tables/**` minus an explicit benign allow-list
such as `board*`, `suite*`, `custom_field`), and add a test that every
table in `staterepo.SettingsTables` whose rows carry a secret, a grant or
a write repository is covered by the ceiling, so a table added later is
held until somebody lists it.

**Regression test:** `TestNeverAutoMergePathsCoverGrantAndSecretTables`
in `pkg/trustboundary/state_test.go` (table-driven over the paths above,
asserting `IsNeverAutoMergePath` is true and `ValidateConfigPolicy`
refuses each as an `auto_merge_paths` entry), plus the
`staterepo.SettingsTables` cross-check in `pkg/staterepo`.

**Fix task:** filed by this run (see closing note), `auto_merge: false`,
`hold_for_approval: true` — it changes `pkg/trustboundary`
classification.

## Examined and found sound

So the next night can tell what was looked at:

- **External agent API (`POST /mcp`, #104).** A `gma_` bearer is
  authenticated in `Server.ServeHTTP` before the access-code gate
  (`authenticateExternalAgent`: setting on, hash lookup, revoked,
  expired, limiter), becomes `PrincipalAgent("external:<name>")`, and
  every route it reaches goes through `agentAPIGate`'s external path:
  `internal`/empty scopes refused, `noTaskContextRoutes` refused, scope
  and repository checked against `ResolveExternalAgentGrants`, a reason
  required on dangerous and DELETE routes, body-grant escalation and
  token-rotation escalation checked. `/staging/{name}/{path...}` is
  routed through the gate as `internal`, so a bearer (or an acting task)
  cannot reach a persistent sandbox's service. Issuing, rotating and revoking tokens is
  `capabilities:admin`, a Dangerous scope: person-granted only and never
  reachable on the sandbox-cli channel. `handleMCP` refuses a cookie
  session without a bearer. Not exhaustively re-derived: the
  `externalAgentRails`/`externalAgentFilingEscalation` bodies.
- **Sandbox CLI proxy (`/api/`, `/cli/`, `/cap/`, #101, #112).**
  `forwardToAPI` strips `Authorization` and every `X-Grain-*` header,
  sets `X-Grain-Acting-Task` from the sandbox's resolved scope (refusing
  a run with no task), and `X-Grain-Channel: sandbox-cli`, under which
  `authorizeAgentCall` refuses Dangerous, `deployment:*` (bar read),
  `dispatch:write`, `repos:write`, `sessions:write` and all `internal`
  routes. `grain task propose` from a sandbox is forced to
  `hold_for_approval=true`, `auto_merge=false`, no `supersedes`, and
  capped per attempt. `/cap/<server>/mcp` only reaches servers
  registered for this run or CI sandbox, refuses a `tools/call` naming a
  tool the server did not list or that resolved model-only (default
  model-only for external servers), rejects JSON bodies with
  case-ambiguous duplicate keys, bounds the body at 4 MiB, and strips the
  proxy credential before forwarding. *Observation, not filed:* only
  `tools/call` is inspected; `resources/read`, `prompts/get` and
  `completion/complete` are forwarded to a server that has at least one
  sandbox-callable tool, with the grant's credentials injected. No
  in-tree capability server serves resources or prompts, so there is no
  concrete failure today; the spec's §5.2.6 should say whether those
  methods are sandbox-callable.
- **Sandbox-access acceptor (#108, #124, #128).** TLS 1.3 only, client
  certificate required and verified against the per-deployment CA, CN
  and single URI SAN must both name the sandbox in the handshake line,
  token compared as SHA-256 in constant time, credential expiry and the
  certificate's `NotAfter` both bound the admission, `Live` consulted,
  and registration with granule happens under the same mutex as the
  hash check so a `Revoke` that lands mid-admission is not undone
  (`cd663647`). Credentials are minted into a Secret owned by the pod and
  mounted read-only into the sandbox container only; the hash store
  persists hashes, never tokens. The in-sandbox guest cannot reach the
  acceptor (`1eb87572`'s inline-mode probe).
- **Config-repo hold (#92).** Default-deny for every path; the policy is
  read from the default branch (`StateRepoPullRequestClient.ReadFile`
  pins `settings/config-policy.yml` to `defaultBase`, the REST
  `FileReader` likewise), a read or parse error holds everything;
  `ValidateConfigPolicy`'s overlap check handles `*`, `?`, `[…]` and
  `**` segments; `IsNeverAutoMergePath` is evaluated before the policy,
  so finding 2 is the only way round it.
- **Capability catalogue (#107).** `settings/capabilities.yml` is in the
  ceiling; `ValidateCapabilitiesFile` runs in the state check;
  end-of-run proposals are judged against the catalogue and the hold
  fails closed (`fe95544f`), relaying a refused grant to a person
  (`669641b7`).
- **hostd dial-out (#97) and `GET /api/hostd/connect`.** `internal`
  scope; the route authenticates in its own protocol like the
  model-server connect routes (`executorBootstrapRoute`), so an acting
  task or external bearer is refused by the gate.
- **Route scopes.** Every new route carries a scope; `tests/security`'s
  route-authorization ratchet passes with no baseline change; CL
  `change-mail`/`change-publish`/`change-sync` are `tasks:write` and the
  UI handlers additionally refuse agents (`f50b9575`).
- **`scripts/setup.sh` (#86, #95, #100, #106).** Registry tokens are
  passed on stdin to `docker login`, never on a command line; no new
  `curl | sh`; the Google install-track detection was removed rather than
  loosened.
