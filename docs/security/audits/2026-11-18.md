## Findings

### 1. `pkg/model/merge_gates.go`, which the hold-release paths consult, is outside the trust-boundary list, so a change that weakens it merges without a security hold

**Severity.** Medium, as the previous reviews rated the same class of gap
(v22 `pkg/webauth/`, v23 the human-review hold, v28 the six script and
package siblings, v29 `access_code_mode.go`, and the 2026-11-17 review's
finding 1). **Reproduced.**

**Where.** `pkg/trustboundary/trustboundary.go` (`Version =
"trust-boundary/v30"`, `Categories`), which `pkg/orchestrator/securityhold.go`
consults (`trustboundary.Classify(files)`) to decide whether a pull
request is held for a security review. `pkg/model/merge_gates.go` holds:

- `HasReviewFindings` (line 145) and `HasPendingReviewHold` (line 219):
  what `pkg/orchestrator/securityhold.go` line 681,
  `pkg/orchestrator/pathtriggerhold.go` lines 380, 739 and 823,
  `pkg/orchestrator/mergegates.go` line 342 and
  `pkg/model/task_auto_merge.go` line 241 test before handing a task its
  auto-merge back once a hold clears;
- `ClearReviewFindingsForGate` (line 193), the only path besides
  `AcceptReviewFindings` that removes a review's findings from a task
  (`mergegates.go` line 340, on a clean re-review);
- `ComputeMergeGates` (line 332), which `pkg/orchestrator/mergegates.go`
  line 377 uses to decide whether a recorded force-merge override still
  covers the head (every gate but CI must read satisfied);
- `GateOverrides`, `LatestGateOverride`, `NormalizeOverrideGates` and
  `GateOverriddenBy` (lines 261-319), the force-merge override records
  themselves.

`pkg/model/task_auto_merge.go` is in hold-policy precisely as "the
store-level guard that keeps auto-merge off a held task, and the one
place it is handed back once the hold clears"; `merge_gates.go` is the
predicate that guard and the hold's own release read, and `Classify`
returns nil for it.

**Who can do what.** Anyone who can land a green pull request on `main`
unattended -- an agent task filed by a role holding `tasks:write` with
`autoMerge`, a `base-green` repair, or an external contributor whose pull
request is set to auto-merge -- can, with no security review filed,
change `HasReviewFindings` to ignore `LinkReviewFindings` (or
`LinkReviewQuestions`, or the `HumanReviewSecurityFindings` reason), after
which `securityhold.go` line 681 restores `AutoMerge` on a change whose
security review left findings as soon as the trust-boundary clearance is
recorded, and `pathtriggerhold.go` does the same for a gating trigger
review; or change `GateOverriddenBy`/`LatestGateOverride` so a force-merge
override recorded at one head covers another. The 2026-11-17 review
closed the same door for `AcceptReviewFindings`; this is the predicate
on the other side of it.

**This range.** #1760 (`1f5e09c54`) changed `ClearReviewFindingsForGate`
and `ComputeMergeGates` in this file and `findingsGateCovers`,
`questionsGate` and `AcceptReviewFindings` in
`pkg/model/review_findings_accept.go` (which gate a template-less
sensitive trigger's findings sit on, and what accepting one gate clears).
The change itself is sound -- read below -- but of its twelve files the
only one `Classify` puts on the list is
`pkg/orchestrator/pathtriggerreview_test.go` (exec-sandbox, by the
`pkg/orchestrator/` prefix). Had the pull request not touched that test,
the security hold would not have fired on a change to what accepting
findings clears.

  `pkg/ui/gate_checks.go` `collectGateChecksScoped`,
  `pkg/daemon/ui_server.go` `GateCheckSource: ciWorkflowReadSource(...)`).
  Subjects come only from the task's own `fixes`/`external-pr`/
  `changelist` links (`model.CheckSubjects`, never from the request);
  an agent or limited role is refused the whole collection without
  `ci:read` on every subject's repository (`requirePullRequestScopes`,
  `errGateCheckDenied`), results are re-checked against
  `taskReadableForContext` before display (`observationVisible`), the
  read is bounded (8 subjects, 1 MiB and 512 jobs of definitions, 3s,
  a backoff cache in `GateObservationRetry`), and a collection error
  surfaces as a fixed "unavailable" view, never the error text. The
  reads happen before the visibility check, so a viewer who can read the
  task but not a linked repository can still cause a (cached, bounded)
  fetch of that repository's `.grain/` at its base commit with the
  deployment's credential, and sees nothing of it.
- **`ui/e2e/run-frozen.mjs` and `ui/e2e/FROZEN_SPECS` are unclassified**
  (#1402). Right as it stands: `run-frozen.mjs` only runs the non-gating
  lane, and `FROZEN_SPECS` only stops new classic specs being added
  (`TestNoNewClassicE2ESpecs`); neither can take a test out of the
  gating `ui e2e` job. The `GRAIN_E2E_LANE` switch in `frozen.js` can
  only turn the `grepInvert` *off* (run more), never on.
- **`pkg/daemon/loose_credentials.go` is unclassified.** It moves
  plaintext credentials into the store and, since #1512, deletes the
  rollback copies. #1512 was held anyway because `pkg/gitproxy/credstore.go`

  `permissions: contents: read` (workflow-wide), `persist-credentials:
  false`, no secret, no `pull_request_target`; `continue-on-error` is on
  the suite step only, and the job is not a required check. `scripts/
  github-ci-changes.sh` gains one rule (`ui/e2e/*` → `go_unit=true`),
  which runs more, not less.
- **Deleting the `.migrated` plaintext copies** (#1512,
  `pkg/gitproxy/credstore.go` `RetireMigratedCopy`/`DeleteMigratedCopies`,
  `pkg/daemon/loose_credentials.go` `deleteMigratedCopies`,
  `pkg/daemon/ca_store.go`, `pkg/releaseapproval/keystore.go`). Only ever
  removes a file, and only once the store holds a value for it (the
  store is re-read, not the in-memory snapshot); a copy with no store
  value is kept with a warning (`ErrNoStoreValue`). File names come from
  `os.ReadDir` and must pass `storedFileName`; nothing is written. The
  relay token copy is deleted unconditionally, which is right: the relay
  is gone and nothing reads or restores it. `GRAIN_GITHUB_CREDENTIALS=files`
  still reverses the move first.
- **Capability-server start failures** (#1471). The data-plane listener
  still refuses anything but loopback (`intree/dataplane.go` `listen`);
  the new `validPort` only turns a bind error into a flag error. The
  `startFailure` flag travels as `structuredContent` on the `isError`
  result, and what reaches `Status.StartError`, `grain health` and
  `/api/sandbox-health`'s `CapabilityServerDown.StartError` is
  `startErrorLabel(msg)`: the fixed string `"could not start"` or
  `"could not start: port N in use"`, computed from the already-`Scrub`bed
  message. No secret value can reach it. `RotateManaged`, `Statuses` and
  the disabled branch clear the new field with the others.
- **Accept findings on the targeted-review gate** (#1760,
  `pkg/ui/accept_findings.go`, `pkg/model/review_findings_accept.go`,
  `pkg/model/merge_gates.go`). Still a person only (`PrincipalHuman`) with
  an unlimited role (`!a.Full` refused). `findingsGateCovers` now sends a
  `trigger:<name>` record to `targeted-review` when the trigger is a
  template-less sensitive one (`LinkTargetedReviewTrigger`) and to
  `review` otherwise, so accepting `review` no longer clears a targeted
  trigger's findings -- narrower than before. `reviewGatesSettled`, which
  decides whether acceptance hands auto-merge back, now also refuses
  while a `LinkBrokenRulesHold`, `LinkQAHold` or
  `LinkMergePolicyWithdrawn` stands. Review questions are cleared only
  when no findings of that review remain on their gate.
- **Staging proxy credential stripping** (#1763,
  `pkg/ui/persistent_sandboxes.go` `stripStagingCredentials`,
  `isGrainCookie`; `tests/security/staging_proxy_credentials_test.go`).
  Strictly more is dropped before a request reaches `/staging/<name>/`:
  `Proxy-Authorization`, the tunnel/hub/subject/on-behalf-of headers, the
  access-code and acting-task headers, every registered verifier's
  headers, the IAP assertion headers, every `__Host-` cookie, and the
  IAP session cookies. The new security test plants a verifier session
  cookie, an IAP cookie and a `__Host-` cookie in the upstream's response
  and asserts none of it reaches the browser.
- **Gate observations' scope** (#1813, `pkg/ui/gate_observations.go`,
  `pkg/ui/refs.go`). The sidecar is refused outright when the viewer
  cannot read the task's own repository, `taskReadScopedForContext`
  callers (agents, external tokens, CI API) get predictions only, and
  every binding, evidence and dependency subject is re-checked against
  the viewer's repository reads, history included, before anything is
  returned (`observationVisible`). `taskReadableForContext` is the same
  decision `handleRefSummary` already used, lifted off the request.
- **Schedule publishing hold follows the bound template** (#1762,
  `pkg/model/schedule_fire.go`, `schedule_publishing_hold.go`
  `scheduleFiringTarget`). The hold is now checked against the
  repository and base `ComposeScheduleTask` actually files to, rather
  than a stale `sched.Base`; an empty base matches a hold on *any* branch
  of that repository (`publishingHold` line 64), so the release train is
  held more often, never less. `TestBoundTemplateDefaultBranchBaseGovernsPublishingHold`
  pins both directions.
- **Review feedback and earlier-review context** (#1808, #1806,
  `pkg/orchestrator/reviewfeedback.go`, `reviewcontext.go`). When GitHub
  refuses the draft review (422), the findings now also go to the
  reviewed task's conversation as questions, under the same
  `noteFindingsOnReviewedTask` that a posted draft uses; the hold and

  a re-allocation of the same 2 KiB cap; `senderTrusted` and the
  incremental base are untouched.
- **Cancelled image upgrade cleanup** (#1464, `pkg/upgrade/image.go`
  `removeCheckContainers`). `docker ps -aq --filter label=grain.upgrade-check=<sha256(RefFile)[:12 hex]>`
  then `docker rm -f` of exactly those ids; a custom `RunCmd` disables

- **Scheduled upgrade's busy count** (#1799, `pkg/orchestrator/scheduledupgrade.go`,
