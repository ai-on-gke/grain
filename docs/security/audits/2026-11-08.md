## Examined and found sound

- **Human-review hold doors (#758).** `POST /api/tasks/{id}/human-review`
  is `tasks:write` but `RequestHumanReview` refuses an agent acting as
  any task but its own review task, requires `Origin.Reason ==
  ReasonReview`, and holds the *reviewed* task, never an arbitrary one.
  `POST .../human-review/release` is `tasks:write` too, but
  `ReleaseHumanReviewHold` and `mutate`'s "edit that ends a hold" path
  both go through `mayReleaseHumanReview`, which keys on the principal's
  *kind* (`PrincipalAgent` and `PrincipalAutomation` refused) rather
  than its scope -- so no api grant, `tasks:admin` included, lets a run
  or a `gma_` token (both `PrincipalAgent`) release one. A delegated
  registry service (`PrincipalService` acting for a verified person)
  may, which is the design. The store's `ReleaseHumanReviewHold` repeats
  the check (`human_review_hold.go:389`).
- **Agent approval rail (#785).** `agentApprovalRail` runs on `POST
  /api/tasks/{id}/approve` and `run-now` whatever the acting task holds
  (`tasks:admin`, `dispatch:write`), refuses a task in the caller's own
  `LinkProposedBy` lineage (bounded walk, 256, cycle-safe) and anything
  `proposalPersonHolds` lists: `hold_for_approval`, grain/config
  targets, person-approval change targets, `requires_person` catalogue
  entries, person-only grants, declared push sets, auto-merge the caller
  could not inherit, admission above standard, and capabilities, writes
  or reads the proposer does not hold. Every other approval path was
  checked: `POST /api/notifications/{id}/investigate` is `internal` and
  refuses `PrincipalAgent`; `config-change/approve` is `internal`;
  `pending-releases/{version}/approve` and `candidates/{id}/qualification/approve`
  (`releases:write`) are person-only in `DecideRelease`.
- **`capabilities:detach` (#787).** Reaches only the three listed
  `capabilities:admin` routes, needs a reason header, refuses a standing
  session's task (its own included), and `capabilitiesDetachBodyAllowed`
  admits only `"attach": false` without `replace` on a task, or a
  repository list every entry of which is already stored
  (`grantAlreadyStored` through `normalizeCapabilityID`). The handler
  behind it (`handleSetCapability` → `SetCapabilityGrant` with
  `attach=false` → `SetCapability`) only ever deletes grants, and the
  legacy `priority-dispatch`/`durable` aliases with `attach=false`
  only lower admission.
- **MCP per-tool role check (#827).** `resolveMCPCallerAccess` now
  intersects a limited or delegated role's set (minus its deny set)
  with an external token's or acting task's grants, and `invokeRouteTool`
  calls `authorizeMCPRoleScope`/`authorizeMCPRoleCall` before the
  route's own gate. A `Full` undelegated role keeps its previous reach.
  This closes the 11-05 report's observation that `/api/mcp` bypassed
  the role gate's per-route table.
- **Hostd enrollment (#768, #786).** `POST /api/hostd/join`,
  `.../join/{id}/poll` and `.../renew` are the only unauthenticated
  routes (`hostdEnrollOpenRoute`, exact-path matched, POST only). A
  join needs a live enrollment code (`LookupHostEnrollmentCode`,
  revoked/expired/exhausted refused), an Ed25519-signed request
  (`hostd.VerifyJoinSubmit` with a nonce replay cache), an optional
  GitHub identity when the code names `allowed_principals`, and is
  capped per code and per identity; it creates a *pending* request and
  returns a pairing code. The credential is handed out only by
  `ClaimAcceptedHostJoinRequest` after a person's accept
  (`capabilities:admin`/operator-only), and the poll is signed by the
  join's own key. Rekey requires the current credential *and* the bound
  key (`SameHostPublicKey`); renew requires a key-bound host with an
  active connection and a fresh proof against the shared replay cache.
- **Pending-release approval on GitHub Actions (#824).** `DecideRelease`
  refuses any non-human actor before reading the release;
  `dispatchGitHubRelease` reads the `vX.Y.Z-pending` tag's commit, refuses
  a version already answered (`GetReleaseApprovalDecision`), signs a
  `releaseapproval.Record` binding repo, version, decision, commit,
  approver and a lifetime, and passes record + signature as
  `workflow_dispatch` inputs, so the workflow can verify a person
  decided *this* commit.
- **Grant retirement migrations.** `migrateSelfDebugGrants`,
  `migrateReadIssuesGrants`, `migrateGitHubSandboxGrants`, the
  `github-credential:<name>` → `repo#credential` rewrite and the
  `grain-ci` capability-policy rewrite (120) are 1:1 renames applied to
  the three grant tables, repository defaults, `ci_capabilities`,
  standing sessions and policy rules; none maps a narrower grant onto a
  wider one. `api:self-debug` expands to `tasks:read` +
  `deployment:read` only; the source checkout moved to `grain#source`,
  whose grant kind the capability protocol decides.
- **`GET /api/events` and repo-narrowed task reads (#731, #734).**
  `eventsReadable` and `taskReadable` refuse a bare `PrincipalAgent`
  with no call context, require `tasks:read`, and narrow a repo-limited
  agent, `gma_` token or limited role to the repositories its set
  allows; `latestAuthorizedBaseline` keeps a scoped caller from
  observing other repositories' sequence numbers.
  `isRepoNarrowedTasksRead` admits `GET /api/tasks?externalRef=` and
  `GET /api/refs/{ref}/summary` without `?repo=` only because their
  handlers filter by `taskReadable`.
- **Registry routes on a grain (#741).** `GET /api/registry` returns a
  snapshot through `redactRegistryText`; changing the registry URL,
  entry, owner group or auth target needs `secrets:write` for a limited
  role (`checkRegistryAuthTargetWrite`); the registration token is
  reported as set/unset only.
- **`pkg/staterepo` SSH key (#807).** The key path is shell-quoted into
  `GIT_SSH_COMMAND` and reaches only `ssh -i`; it is deployment
  configuration (`settings:write`, dangerous), not state-repo content.
- **`RequestActor` / `agentOnBehalfOf` (#639).** `OnBehalfOf` is set for
  an agent only from a verified human in grain's own records (the task's
  approval or the session turn's author) and is used for labels and
  audit rows only; every authorization decision read (`mayReleaseHumanReview`,
  `DecideRelease`, `InvestigateNotification`, the approval rail) keys on
  `Actor`.
- **Security hold (#758).** `holdForTrustBoundary` still withdraws
  auto-merge before filing the review; a non-releasable hold now also
  raises the human-review link, and a review that leaves findings keeps
  the hold until a person's Submit.
- **Granule re-vendor (#776, #802).** Deletions only on the Go side
  (legacy forward); nothing added to exec or forward.
