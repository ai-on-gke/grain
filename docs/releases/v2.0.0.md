# v2.0.0

Released 2026-10-21 from commit `cf5f64900`. Changes since `v1.13.0` (`82945c620`):
https://github.com/ai-on-gke/grain/compare/v1.13.0...v2.0.0

There was no `v1.14.0`: its candidate held only the single-tenant reset's first stage.

grain 2.0 is the first single-tenant release. It is a fresh start: **there is no in-place upgrade from
any 1.x deployment** (see "Breaking changes" below). From 2.0.0 on, **every later release
upgrades a 2.0 deployment in place**.

## Highlights

- **Single-tenant only.** A deployment serves one owner. Teams, team roles, Admin mode,
  accounts and passwords are gone, and so are `/api/teams*` and the `user` and `team` tables.
  The deployment's **access code** is the only sign-in, from localhost too
  ([docs/access-code.md](../access-code.md)). `grain access-code` prints it. Whoever holds it is
  the deployment's owner, and settings that used to be a team's are the deployment's
  (Settings, not "Team settings").
- **Two builds, two daemon images.** Everything Google-internal lives under `google/`. The
  Google build is `./google/cmd/grain`, which `make build` still builds by default. The core
  build, with no Google-internal code, is `./cmd/grain` (`make build MAIN_grain=./cmd/grain`).
  `google/boundary_test.go` keeps core free of `google/` imports. Only the Google build has the
  `forgecli` git forge, depot and GHOP support, and the Cloudtop installer. Release CI publishes
  each build as its own image, with the same tags (`sha-<short>`, `main`, `candidate`, the rc
  tags, `vX.Y.Z` and `latest`), and both are signed:

  | Image | Built from | Installed by |
  |---|---|---|
  | `ghcr.io/bwsalmon/grain/google-grain` | `./google/cmd/grain` (Google build) | install track `google`: Cloudtops, `*.c.corp.example`, `/opt/corp/bin` and the other signals in `pkg/installtrack` |
  | `ghcr.io/bwsalmon/grain/grain` | `./cmd/grain` (core build) | install track `oss`: everyone else |

  The `guest` and `k8s-sandbox` images stay shared by both builds. `grain version -track` says
  which track a deployment is on.
- **The Silo hub is removed** ([docs/hub-removed.md](../hub-removed.md)). That covers the hub
  connection, `grain hub`, hub filings and hub-aware proposals. The local policy and its audit log
  stay.
- **corp-research on by default** in fresh Google-build installs
  ([google/docs/corp-research.md](../../google/docs/corp-research.md)). An existing deployment's
  default capabilities are left as they are.
- **Cloudtop installs start with no git connection.** `google/scripts/cloudtop-install.sh` no
  longer seeds an ambient `depot.code.corp.example` connection, because most people don't have depot
  access yet. Add GitHub or depot in Settings → Git, or re-run with `--depot`
  ([google/docs/cloudtop-install.md](../../google/docs/cloudtop-install.md)).
- **The Grainfile Format docs.** [docs/grainfile-format.md](../grainfile-format.md) describes what
  grain keeps to itself and what it writes out as Grainfiles. The v1 specification
  ([docs/grainfile-v1.md](../grainfile-v1.md), [docs/grainfiles-spec.md](../grainfiles-spec.md)) covers
  repo and issue import and export, and capabilities by URL.

- **One install root: `/var/lib/grain/{data,scratch}`** (#4260). `scripts/setup.sh` installs 2.0
  under `/var/lib/grain`, split in two: `data/` (`GRAIN_DATA_DIR`) is the state to back up --
  the store, secrets, `secrets.key`, `local-api-token`, `bin/` -- and `scratch/`
  (`GRAIN_SANDBOX_DIR`) is disposable run space and caches. Either half can be a mount of its
  own. `--uninstall` keeps `data/` and removes `scratch/`; `--purge` removes both. An explicit
  `GRAIN_DATA_DIR` or `GRAIN_SANDBOX_DIR` still wins, and the Terraform GCP module mounts its
  disks at the same two paths.
- **One header rail per page** (#4281). The global top bar and each page's own header are now a
  single sticky row: the page's title as crumbs (`repositories / acme/widgets / releases`), the
  page's own actions, and the alerts bell, System and Settings at the far end. A row that doesn't
  fit folds into a "more" menu instead of wrapping. On phones, the bell and gear stay in the
  phone bar.
- **The rendezvous relay is removed** (#4291, [docs/relay-removed.md](../relay-removed.md)). The
  Cloud Run relay server, `grain relay`, `/api/relay-settings`, the Relay settings section, the
  remote executor's relay dial path and the Terraform relay module are gone. Remote executors
  connect directly (`-executor-addr`, `/api/executors/connect`), and a GCP deployment is reached
  through the IAP tunnel or the IAP load balancer.
- **grain/config is the only config repository** (#4280). Per-team configuration repositories are
  gone with the teams. The git proxy answers any `grain/config-<name>` with "not found", and a
  leftover `team-state-repos/` directory is logged once at startup and left in place.

## Breaking changes

- **No in-place upgrade from v1.x.** A 2.0 build refuses a data dir or state repository written
  by any 1.x release. It names the schema it found ("from before the single-tenant baseline")
  and changes nothing, so the 1.x build can still run on it. To move a deployment to 2.0:
  1. Install 2.0 fresh, on an empty data dir: `scripts/setup.sh`, or
     `google/scripts/cloudtop-install.sh` on a Cloudtop.
  2. Bring the old deployment's git and model connections across with
     `grain connections -data-dir DIR import <seed.yaml>`. You write the YAML from the old
     deployment's settings ([docs/connections-and-models.md](../connections-and-models.md)), and
     the import stores each credential file with mode 0600.
  3. Add its repositories again. Each repository's own `.grain/` declarations (templates,
     schedules, workflows) return with it.
  4. Use the old state repository (`grain/config`) as the record of the rest. A 2.0 build won't
     import a 1.x dump, which is at schema 17, but the dump is a git repository of plain files.
     The deployment's settings documents, templates, schedules and memory notes in it are
     readable there, and can be added to the new deployment again.
- **grain-eu is retired.** It stays on its pinned multi-team build and is never upgraded to 2.0.
- **`ghcr.io/bwsalmon/grain/grain` is now the core build.** Before 2.0 it was the only daemon
  image, and it was the Google build. Now the Google build is
  `ghcr.io/bwsalmon/grain/google-grain`.
  - A deployment on the **google** track that still names `grain/grain` moves to `google-grain`
    on its next upgrade, keeping its channel: `grain/grain:main` becomes `google-grain:main`.
    This holds whether the upgrade comes from the Upgrade pane, which picks the repository from
    the detected track, or from re-running `scripts/setup.sh` or
    `google/scripts/cloudtop-install.sh`. It never moves onto the core build.
  - A deployment on the **oss** track stays on `grain/grain` and gets the core build from then
    on. That build drops the Google-internal features listed above, which an OSS install has no
    use for. To stay on the Google build anyway, set `GRAIN_INSTALL_TRACK=google` or
    `GRAIN_IMAGE=ghcr.io/bwsalmon/grain/google-grain` and re-run `scripts/setup.sh`.
  - A Kubernetes deployment (`deploy/kubernetes`) names its image in its manifest, and its
    upgrades stay in that repository. The manifests name `grain/grain`, the core build; point
    them at `google-grain` for the Google build.
- **New install paths.** A fresh install refuses when `/var/lib/grain` itself holds a 1.x flat
  data directory, and says how to move it. 1.x's `/var/lib/grain-sandbox` is not used.
- **Relay settings no longer start a daemon.** A daemon given any `-relay-*` flag or
  `GRAIN_RELAY_*` variable refuses to start and points at
  [docs/relay-removed.md](../relay-removed.md). A stored relay setting or token is ignored.
- **The API is single-tenant.** The team routes, `/api/config`'s `teams` and `tenancy`, and the
  `team` field on schedule and suite requests are gone. Clients that sent a team should stop.

## How this was verified

`v2.0.0` is candidate commit `cf5f64900`. That is `v2.0.0-rc.1` (`d9a255de3`, cut 2026-10-21) plus
the two-daemon-image release (#4311, ported as #4314) and the container test fix that let it publish
(#4315, ported as #4316). The owner chose to release before the 8-hour soak (task 4827), which runs
afterwards, with its fixes going into 2.x patch releases.

- **Release workflow on `candidate`: green** at `cf5f64900` (grain CI run `e801152028f0a768`) and
  at rc.1 (`8ad09298fe02eeb6`). `tests/container` (against both `grain` and `google-grain`) and
  `tests/installer` passed before anything was published. Run `e801152028f0a768` published
  `grain`, `google-grain`, `guest` and `k8s-sandbox` at `sha-cf5f649`. The images are unsigned,
  because this deployment's CI has no image-signing key.
- **Pull-request suite (`tests.yml`) at the rc.1 commit: green** (run `5ec397049bd6b4ec`: frontend,
  go, installer, lint, package cache, postgres, run host, terraform, ui e2e).
- **The candidate gate was skipped (`CANDIDATE_GATE=off`).** `nightly`, `gcp-smoke`, `live-agent`,
  `live-frameworks`, `live-secrets-repo` and `post-reset-e2e` were not run on this candidate. The
  agent that cut the release had no way to dispatch them: no `grain` CLI in its sandbox, and CI
  tools that run only the push workflow's jobs. Scheduled runs don't fire on the deployment that
  cut it. With no runs, the gate read `missing` for each and held on the required `nightly`. Every
  suite that did run was green, which is the condition the owner set for skipping the gate. The
  manual qualification rows in `docs/release-candidate-management.md` were not part of this release.

## Upgrading after 2.0

From 2.0.0 on, every release upgrades a 2.0 deployment in place, through the Upgrade pane or
`scripts/setup.sh`. Each schema change ships an in-place migration that runs on SQLite and on
Postgres, so the store never leaves its database. Every build is tested against a store and a
state-repository dump frozen at 2.0.0 ([docs/data-model.md](../data-model.md), "Schema changes
after 2.0").
