# v3.5.1

Cut 2026-11-11 from commit `4e29f7be9`. Changes since `v3.5.0` (`c078507ab`):
https://github.com/ai-on-gke/grain/compare/v3.5.0...v3.5.1

## Highlights

- **A patch release of two fixes.** `v3.5.1` is `v3.5.0` plus three commits from `main`,
  cherry-picked unchanged with `-x`, and nothing else. It was cut by `scripts/release-patch.sh`
  as `docs/release-candidate-management.md` section 9 describes.
  - **`grain_submit_task` works for Gemini-backed runs again (#1155).** The controller MCP
    server declared `grain_submit_task`'s `grants` property as an array with no `items`
    schema. Gemini validates every declared tool and rejected the whole tool list with
    `INVALID_ARGUMENT (...items: missing field)`, so Gemini runs holding `api:*` grants lost
    the controller's tools. The array now has an `items` schema, and a test audits every
    controller and sandbox MCP tool schema for arrays without one.
  - **Adding a repository on a non-default git host keeps its host (#1171).** Adding
    `<host>/<owner>/<name>` through `POST /api/repos` without a clone URL stored it as
    `<owner>/<name>` on the default host, because `githubSpelling` asked `RepoNames` with
    only owner and name and trusted the forge's hostless `full_name`. Tasks against that
    repository were then parked off the allowlist. `ui.RepoNames.RepoFullName` now takes the
    host, lookups go through each host's own git connection, and the parsed name keeps
    `repo.Host`. Issue import and `gitproxy.Reach` keep a non-default host the same way.
    Target repositories that were already stored without their host are not rewritten.
    Instead, `/repos`, Settings → Repositories, System → Health, System → Sandboxes and
    `grain health` warn "this entry resolves to <default host>; did you mean
    <host/owner/name>?".
  - The second #1171 commit is its security-review follow-up.
    `GET /api/deployment/reachable-repos` now intersects a person's RBAC role with the acting
    task's grants, rather than letting `X-Grain-Acting-Task` widen it. It always returns
    `hostMismatches: []` when there are none. The repository-name lookup now fails closed
    when it has no store.
  - The Google edition does not implement `ui.RepoNames` of its own, so it needs no change
    beyond building on this release.
- **How this release was qualified.**
  - Each pick's range-diff against its original (`dbc39450b`, `8f2198464`, `be0dc47cb`) is
    empty apart from the `(cherry picked from commit ...)` line. All three applied cleanly to
    `v3.5.0` with no other prerequisites. #1171's unrelated
    `fix(ui-ng): regenerate the Angular route table for the rollover route` and its merge
    commits were not picked.
  - `go build ./...`, `go vet ./pkg/...` and `go test ./...` were run on the release tree
    (task 4226). One test failed in the full run: `pkg/orchestrator`
    `TestKillStepRunnerKillsItsOwnRunner`, a 10s timing test outside the picks. It passed when
    re-run alone (`-count=3`) and with the whole `pkg/orchestrator` package. The pull-request
    `Tests` workflow could not run on the release tree, because its commits are already on
    `main` and a pull request for them would merge nothing. All three picks passed it on
    `main` through #1155 and #1171.
  - The release workflow (`release.yml`) on `release/v3.5.1` passed at `4e29f7be9`: the
    release images, with the container and installer tests, and the release assets.
    `scripts/patch-tag-guard.sh v3.5.1` accepts the tag as cut on `release/v3.5.1` from
    `v3.5.0`.
  - The long suites (`nightly`, live suites) were not run. These targeted fixes don't need
    them: one is a tool-schema change, and the other is the repository-name lookup and the
    reachable-repos endpoint, which the Go tests above cover.
