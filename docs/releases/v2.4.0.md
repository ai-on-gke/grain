# v2.4.0

Not yet released. Candidate `v2.4.0-rc.1` was cut on 2026-10-26 at `253bee735`. This file was
written by hand before the promotion (as `v2.0.0.md` was), so the cut leaves it as it is. The
agent that promotes v2.4.0 replaces this paragraph with the "Released ... from commit" line and
adds to the lists at the end anything that landed on `candidate` after rc.1.

Changes since `v2.1.1` (`3373f533f`):
https://github.com/ai-on-gke/grain/compare/v2.1.1...v2.4.0

**v2.4.0 is the first release since v2.1.1.** v2.2.0 and v2.3.0 were never released. Their
candidates (`v2.2.0-rc.1`, `v2.3.0-rc.1`) were held at the candidate gate because the required
nightly kept being cancelled for lack of sandbox capacity, so there are no `v2.2.0` or `v2.3.0`
tags and everything those candidates carried ships here first. These notes cover all of it,
including the breaking changes first written down for v2.3.0 ([v2.3.0.md](v2.3.0.md) is now a
pointer here).

**Read "Breaking changes" before upgrading.** The biggest one is that host mode is gone: a
deployment that runs the daemon as a plain systemd service has to re-run its installer once.

## Highlights

### New in this release

- **grain hostd, and one install shape.** Every machine install now runs the daemon in the
  release container, with `grain-hostd.service` beside it. hostd runs allowlisted host CLIs (agy
  on the Google track) and `run: host` capability servers on the machine, as `GRAIN_USER`. It
  keeps detached host runs alive across a daemon upgrade, drains for upgrades and is upgraded from
  the daemon's own image. Settings and `grain hostd -status` show its build and the runs it holds.
  See "Breaking changes" and
  [docs/design/cli-run-location.md](../design/cli-run-location.md).
- **Capability servers.** Capabilities are now served over a control-plane protocol
  ([docs/capabilities.md](../capabilities.md),
  [docs/capability-servers-ui.md](../capability-servers-ui.md)):
  - grain's in-tree servers (`grain capability <name>`) register themselves under canonical IDs
    (`https://grain.dev/capabilities/<name>`). Each one is configured in Settings → Credentials →
    Capability servers through a form built from its schema, with a **Test** button, a policy
    editor and a list of who holds it.
  - A grant can name a capability by reference, with arguments
    (`https://grain.dev/capabilities/gcp#gcp-key` with a `permission_set`). It is minted when a
    task is admitted and when a grain CI job starts. A CI job gets only the grants it declares,
    and `capabilities: []` gets none.
  - **gcp-key** is rebuilt on admin accounts and permission sets. Each set names an admin, a
    project, roles, an optional bucket scope, a lease limit and a pool size, and the server
    creates and reaps the service accounts itself
    ([docs/gcp-key-permission-sets.md](../gcp-key-permission-sets.md)).
  - **host-script** turns operator bash scripts into sandbox commands. They are edited and
    tested in Settings ([docs/host-scripts.md](../host-scripts.md)).
  - **config-map** places configured files and secret files in a sandbox. It replaces `skill`.
  - The git, model-proxy and self-debug servers take their credentials through Settings.
- **The agent API.** Every route of grain's own API now has a permission scope
  ([docs/agent-api.md](../agent-api.md)). A task granted `api:<scope>`, a preset such as
  `api:pipeline-control` or `api:self-upgrade`, or a repo-limited `api:<scope>@owner/name` gets one
  MCP tool per route under that scope, and the daemon checks every call it makes. Agents can never
  submit work, turn on auto-merge or approve anything their own task could not have proposed.
  The capability pickers have a "Grain API" group.
- **Running work while the pipeline is paused.** **Run now** gets a task past an operator's
  pipeline pause (manual mode), which System → Pipeline now names. Console sessions start under a
  pause too.
- **Kubernetes sandboxes.**
  - Both backends, `kubernetes` and `kubernetes-granule`, are offered by default in Settings →
    Sandboxes. Their settings are stored with the rest of the configuration (`grain_config`) and
    come prefilled for the install track.
  - `kubernetes-granule` can run off-cluster: a deployment reaches the cluster with a kubeconfig
    and carries sandbox traffic over `granule forward` ([docs/k8s-granule-design.md](../k8s-granule-design.md)).
  - Pod CPU and memory requests follow the overcommit ratios. The sandbox budget reads the
    nodes' allocatable capacity and follows cluster autoscaling.
- **Sandbox budget.**
  - An **auto overcommit** controller tunes the CPU and memory overcommit to what the host can
    take. Settings and the CLI show its state ([docs/design/auto-overcommit.md](../design/auto-overcommit.md)).
  - The OOM killer picks sandboxes, never the daemon or hostd. A sandbox that is OOM-killed is
    retried as an infrastructure failure, with more memory.
  - Admission is enforced for every kind of sandbox, and live usage is reconciled against it.
- **Persistent and staging sandboxes.** A persistent sandbox refreshes when its ref moves, and
  shows the commit it runs and when it last refreshed. Staging environments are listed in the
  sidebar, linked to their host port or `/staging/` sub-path
  ([docs/persistent-sandboxes.md](../persistent-sandboxes.md)).
- **Sandbox images.** Minimal `guest-base` and `k8s-sandbox-base` images are published beside
  `guest` and `k8s-sandbox`, with an explicit, versioned contract for building your own
  ([docs/sandbox-image-contract.md](../sandbox-image-contract.md)).
- **External config repository.** Settings → Config Repo → "Use external config repository"
  makes a remote `grain/config` the source of truth. grain applies what merges there and never
  pushes to it. In that mode the UI and API refuse configuration writes, and the refusal gives
  the exact edit to commit instead ([docs/external-config-repo.md](../external-config-repo.md)).
- **Merge queue.**
  - A per-repository **Merge when green and clean** switch (`merge_on_green`) lets green pull
    requests merge past pending ones, and queues newcomers at the back.
  - The queue records why each batch was abandoned, and what each red base branch held back.
  - Base-branch repairs can go past a full sandbox budget. They can also merge without a human,
    if an option allows it.
  - A grain CI run that a person cancels goes back to the task's agent, and is rerun, instead of
    stalling.
- **The pipeline steward** is a standing job that watches the pipeline and acts on stalls
  ([docs/pipeline-steward.md](../pipeline-steward.md)). Liveness is classified by reason, and a
  stall is escalated instead of annotated.
- **Reviews fix and go through.** A pre-merge reviewer fixes what it can and lets the change go
  on. It holds a change only on a question for its owner, which shows up as the owner's decision.
- **Sessions and templates.** A session starts from its first message, and a standing session
  can choose its model. Templates can be **interactive**. Every running task's agent can be sent a
  notice at once.
- **Models.** A deployment can have several default models, tried in order, across frameworks,
  whenever an earlier one is paused, busy or unserved. agy's quota pauses last until the reset
  time it names.
- **Smaller additions.**
  - Task branches carry a few words of the title (`grain/<deployment>/task-56-fix-the-parser`).
  - Schedules can repeat every N minutes, with a ten-minute minimum.
  - An agent can park its own task until a time (`wait_for_task` `resume_at`), and hold a
    proposal for approval on purpose.
  - A closing note's images show in the pull request description.
  - The "Queued for merge" state and board column are now "Merging". "Blocked" is a state oval
    of its own.
  - Every build carries a semver build version (`v2.4.0-dev.N+<sha>` between releases).

### Fixes that matter

- **Upgrading out of host mode.** grain's git repositories are kept in the `files` ref format. A
  state or secrets repository that a newer host git made with reftable refs is converted by the
  installer, or refused with the exact command to run, instead of the daemon crash-looping on
  "unknown repository extension found: refstorage".
- **Installer.** An install whose daemon exits right after it starts now fails. The readiness
  summary names hostd's CLIs and each CLI's run location.
- **Security.** The trust-boundary list (v6) covers the 2.4 subsystems: the agent API, the
  config-repo guard, the staging proxy, k8s, hostd, granule and the state repository. A change to
  any of them gets a security hold. Security reviews are no longer filed twice for an unchanged
  head. Other hardening:
  - Staging apps cannot set grain's cookies.
  - Review templates are held to the proposer's own grants.
  - `granule forward` dials only its own targets.
  - A CLI container image that docker would read as a flag is refused.
- **CI and merging.**
  - A closed, unmerged task's in-flight CI is cancelled.
  - A run that errored for a missing capability is rerun once the capability is granted.
  - A human's Submit is pinned to the pull request head.
  - Port PRs that have landed or are obsolete are closed.
  - Stacked tasks are retargeted when their upstream branch merges.
  - `MergePullRequest` falls back to squash and rebase.
- **Kubernetes reliability.** kubectl is paced and retries dial timeouts. Granule pods get
  memory headroom for the VMM. A CI step on a remote sandbox is no longer clamped to 600s.
- **Upgrades.** The Upgrade pane does nothing when the target version has not changed.

## Breaking changes

- **Host mode is removed.** `GRAIN_INSTALL_MODE=host`, the daemon as a plain systemd service on
  the machine, is gone from `scripts/setup.sh` and `google/scripts/cloudtop-install.sh`, along
  with `GRAIN_HOST_BINARY` and `GRAIN_HOST_SOURCE_DIR`. Every machine install now runs the
  daemon in the release container. `GRAIN_INSTALL_MODE=host` is refused before anything is
  written, and the refusal names the command below. Kubernetes installs are unchanged.

  **If your deployment runs in host mode, run its installer once to move it:**

  ```
  sudo ./scripts/setup.sh                    # a core-track machine install
  ./google/scripts/cloudtop-install.sh       # a Cloudtop (no sudo in front)
  ```

  The re-run moves the install to container mode plus grain hostd. It keeps the data directory
  (`/var/lib/grain/data` and `/var/lib/grain/scratch` by default) and the unit name
  (`grain-daemon.service`). It converts any reftable git repository in the data directory to
  the `files` format the image's git can read, or stops and names the command to do it. It also
  removes what only host mode left on the machine: the nft sudoers rule, the copy of grain's
  source under `/usr/local/share/grain/src`, and the systemd drop-in that a host-mode Upgrade
  wrote.

  A host-mode install that is upgraded to this release with the **Upgrade button** still comes
  back up, because its old unit takes the new binary out of the new image. It warns that it is
  unmigrated, and refuses every further upgrade from the UI with the command above, so its next
  upgrade is the installer's migration.

- **grain hostd is installed by default.** Every machine install gets `grain-hostd.service`,
  which runs allowlisted host CLIs (agy on the Google track) and `run: host` capability servers
  on the machine, as `GRAIN_USER`. The allowlist, `/etc/grain/hostd.yaml`, names agy on the
  Google track. On the core track it is empty, ready for an operator to add entries.
  `GRAIN_HOSTD=0` leaves hostd out, and on a re-run removes an installed one together with its
  socket mount. Without hostd everything runs in the container, nothing runs as you on the bare
  machine, and "host" is not offered as a run location, as on Kubernetes. The installer's
  readiness report and Settings -> Models say which of the two an install is.
- **Run locations are `container` or `host`; `auto` and the per-CLI image are gone.** The per-run
  `docker run` launcher that `container` meant on a daemon on the bare machine is removed with
  host mode, and so is `auto`, whose only meaning was a `--version` probe there. In the release
  container nothing changes: `container` is a subprocess beside the daemon, `host` is grain hostd,
  and the default that read `auto` reads `container`.
  - A stored `auto` (and any image override) in Settings -> Models is dropped when the daemon
    reads it, so that CLI falls back to its default. The next save writes the cleaned value.
  - `GRAIN_CLAUDE_RUN`, `GRAIN_CODEX_RUN` and `GRAIN_AGY_RUN` take `host` or `container`.
    `auto` is accepted for this release with a warning and dropped; set one of the two instead.
  - `-claude-run=auto` (and its neighbours) is accepted and ignored, and `-cli-image`,
    `-cli-image-file` and `-cli-container-engine` are defined and ignored for this release, so a
    unit an older installer wrote still starts. They go in a later release.
  - A development daemon on the bare machine (`grain demo`, a local `grain daemon`) offers only
    `host`. A `container` stored or flagged there runs on the host, with a warning in Settings.
    CLI containers an older daemon of that kind left behind are no longer reaped at start:
    `docker rm -f $(docker ps -aq --filter label=dev.grain.cli.deployment)` removes them.
- **`--git` on a Cloudtop no longer adds an ambient git connection.** An ambient connection
  borrows your own gh/ggh login, which only a daemon on the bare machine could use, and no
  installer makes one any more. Add a token connection or a GitHub App in Settings -> Git. (A
  containerised daemon with hostd can still use your login through hostd's host-git server.)
- **Kubernetes sandbox settings are stored, and the `-k8s-*` flags only seed them.** The
  Kubernetes sandbox options live in `grain_config`, so they are exported to the config repo's
  `tables/grain_config.json` and edited in Settings → Sandboxes, `grain settings` or `grain sync`.
  A `-k8s-*` flag fills the stored value only on first use. Once a stored value exists, the flag
  is ignored and the daemon warns about the difference. To change one, change the setting, not
  the unit. Both Kubernetes backends now show as available in Settings → Sandboxes.
- **The `skill` capability is now `config-map`.** The built-in `skill` server, which needed a
  `-dir` flag and had no settings, is replaced by `config-map`
  (`https://grain.dev/capabilities/config-map`), configured in Settings. A stored `skill` entry
  is migrated to `config-map` and its ID is accepted as an alias. The `grain capability skill`
  subcommand still runs. config-map starts as needing configuration, so check its files after
  upgrading.
- **`self-debug` is an agent API preset, and it reaches more.** The built-in self-debug server
  is retired. A `self-debug` grant now means `api:tasks:read` and `api:deployment:read`. The
  second includes host, sandbox and upgrade status and the daemon's redacted logs (daemon
  journal, dmesg, git-proxy audit log), which the old grant did not. An unconfigured self-debug
  server entry is dropped at start. Review who holds the grant.
- **gcp-key moves to permission sets.** A `gcp` server configured the old way (`-project`, a
  fixed `-account ...*N` pool and `GCP_MINTER_KEY`) is migrated at start to an admin `minter`
  and a `sandbox-agent` set over exactly the old accounts. Grants with no arguments get that set.
  New sets create accounts named `grain-<deployment id>-<set>-<n>`. An admin needs the custom
  `grainGcpKeyAdmin` role. See [docs/gcp-key-permission-sets.md](../gcp-key-permission-sets.md)
  for retiring the old pool. Do not point the in-process provider and a server at the same
  accounts.
- **A config repository with a remote is read-only from grain.** Setting a remote on
  `grain/config` turns on external mode, which is not a mirror. grain pulls from the remote and
  never exports to it or pushes. Settings that the repository manages are read-only in the UI,
  and API writes to them answer `409 Conflict` with the edit to make in the repository
  ([docs/external-config-repo.md](../external-config-repo.md)). Without a remote, grain hosts
  `grain/config` itself, as before.
- **grain CI jobs get only the capabilities they declare.** Scarce grants (such as `gcp-key`)
  are minted for a job only when the job asks for them. A job that relied on the old blanket
  grant has to name the capability in its `capabilities:`.
- **The default task branch name has the title in it.** The default template is now
  `grain/{deployment}/task-{id}-{slug}` (it was `grain/{deployment}/task-{id}`). A deployment
  that saved a template of its own keeps it. Anything that finds task branches by exact name
  should match the prefix instead. A `{slug}` can only go at the very end, straight after
  `{id}-`, and Settings refuses any other placement.
- **Agents can no longer submit or turn on auto-merge through the API.** A run holding
  `tasks:write` cannot submit a task, set `autoMerge`, approve its own filings or file into
  repositories its task cannot reach. Letting a change merge unreviewed is a person's decision.

## Ports

grain's fixed, operator-facing ports now start with 42 (4200-4299); see
[docs/ports.md](../ports.md) for the table and the ranges reserved in it. Nothing a deployment
listens on moves:

- **`grain demo` serves on `127.0.0.1:4290`** by default, not `127.0.0.1:8420`. `-addr
  127.0.0.1:8420` still works for a script or bookmark that wants the old one.
- **`npm run dev` in `ui/` proxies `/api` to `localhost:4242`**, the daemon's default since
  v2.0.0, not to the old `8420`.
- The `-executor-addr` help now suggests `:4243`. A deployment already listening on `:8422`
  keeps it: the flag takes whatever port it is given.
- The sandbox-facing ports (`9728` git proxy, `9729` package cache, and the rest of the
  `-sandbox-port-base` block) are unchanged.

## Rollback

**Back up the data directory before you upgrade.** v2.4.0 migrates the store in place, from
schema 27 to 39. A v2.1.1 daemon refuses a store that is newer than it knows ("schema too new"),
so the only way back to v2.1.1 is a copy of `GRAIN_DATA_DIR` (`/var/lib/grain/data` by
default) taken before the upgrade. `GRAIN_SANDBOX_DIR` is disposable and needs no backup.

To roll back, stop grain, put the backed-up data directory back, and re-run the installer with
the previous release's tag. That is `v2.1.1`: there are no `v2.2.0` or `v2.3.0` tags.

```
sudo systemctl stop grain-daemon.service grain-hostd.service
# restore /var/lib/grain/data from the copy taken before the upgrade
GRAIN_IMAGE_TAG=v2.1.1 sudo ./scripts/setup.sh
```

That runs the older image in the same container unit. Whatever the deployment did on v2.4.0
after the backup is not carried back. v2.1.1's installer does not know grain hostd and leaves
`grain-hostd.service` in place; `sudo systemctl disable --now grain-hostd.service` stops it.
Rolling back to **host mode** is not supported after this release.

See [docs/design/cli-run-location.md](../design/cli-run-location.md) ("Installed by setup.sh"
and "Trust levels") for what each install shape trusts grain with.
