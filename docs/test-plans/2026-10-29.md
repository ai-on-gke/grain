## §3. Config-repo policy — the `settings/capabilities.yml` capability catalogue and human Submit for every config PR

### What changed
- **Capability catalogue** (`d656e165`, `fe95544f`, `bd7de6d3`, `669641b7`, PR #107; design `97723638`, PR #88): `settings/capabilities.yml` in `grain/config` declares every capability server/method, in-process capability, agent API preset and raw scope rule, who may hold each (`repos`, `templates`, `kinds`, `ci_only`, `requires_person`, `requires_person_when`) and default task/CI grants per deployment and per repo. It is stored in `grain_config.capability_policy` (no migration); without the file, behaviour is unchanged. `staterepo.Check` refuses a file that does not parse, is inconsistent, names secrets by value, or refuses a grant a template/schedule carries. Enforcement: `POST /api/tasks`/`propose_task` 400 on an explicitly requested refused grant and drop refused defaults; a `requires_person` grant files the task proposed; `POST /api/tasks/{id}/capabilities` judged per task (403 for an agent attaching a `requires_person` grant); `PATCH` to another repo re-judges; a dispatch hold parks a refused queued task under the capability-catalogue grant wait; CI jobs judged as kind `ci`. End-of-run proposal replay now asks the catalogue too, and a refused grant the run asked for is filed for a person.
- **Every config-repo PR held for a human Submit** (`fdd09a6f`, `687b9980`, PR #92): `trustboundary.ClassifyState` treats every changed path in `grain/config` as privileged unless `settings/config-policy.yml` `auto_merge_paths` (read only from the config repo's `main`) opts it in, under a hard `NeverAutoMergePaths` ceiling that `staterepo.Check` enforces.

### What CI proves
- Model and staterepo unit tests for the catalogue evaluator, projection and `Check`; `pkg/orchestrator/catalogue_hold_internal_test.go`; `pkg/daemon/statepullrequests_diff_test.go`; the security-hold v2 e2e walkthrough updated for trust-boundary v9.

### What is NOT proved
1. **A real config repo round trip**: committing `settings/capabilities.yml` to the demo's state repo, seeing it imported (and exported back), and the UI's capability picker / `/settings/capabilities` reflecting what it allows.
2. **Every enforcement point against a live daemon**: 400 on a refused explicit grant, the dropped default, the proposed (held) task for `requires_person`, the agent 403 on attach, repo-move re-judging, the dispatch hold's reason on a task already queued before the file landed, and a CI job refused a grant.
3. **`staterepo.Check` refusals** for each class of bad file, as an operator sees them on the config PR.
4. **The config-policy hold**: a config PR touching an opted-in path auto-merges; one touching anything else, or a path under `NeverAutoMergePaths` even if listed, waits for a person's Submit; an `auto_merge_paths` change made on a branch is not honoured.

### Walkthrough & test procedures
1. Shared environment. Find the demo's state repo (`grain demo` keeps one under its data dir; `grain settings`/docs name it) and clone it.
2. Write a catalogue that (a) refuses `gcp` outside one repo, (b) marks one capability `requires_person`, (c) adds a CI default. Commit to its `main` and let the daemon import it; confirm `GET /api/settings` (or the capability-policy route) shows it.
3. Exercise each enforcement point in gap 2 over HTTP with the access code and with an agent token, and in the UI's new-task form; confirm each refusal names the catalogue rule.
4. Push bad files (unknown key, secret by value, inconsistent server/method, refusing a grant a template carries) as config PRs; confirm the PR's check refuses with a readable reason.
5. With `githubsim`, open config PRs touching an `auto_merge_paths` path, an unlisted path, and a `NeverAutoMergePaths` path; confirm only the first auto-merges and the others show the human-Submit hold in the UI.
6. Record in `docs/test-runs/<date>-capability-catalogue-config-policy.md`.

## §4. Sandbox-first agent surface — `grain cap`, the MCP control roster, sandbox-proxy hardening, and SSH commit signing

### What changed
- **`grain cap`** (`8a850a45`, `bc6a1df8`, PR #112): a granted capability's tools are split into model-only (wired to the agent's MCP) and sandbox-callable (served at the sandbox proxy's `/cap/`, `/cap/<server>`, `/cap/<server>/mcp` and listed as `grain cap <server> <tool>` in a `<capability-cli>` prompt block). Every `tools/call` (including inside a batch) to a model-only or unlisted tool gets 403 before anything reaches the server; the proxy token and `X-Grain-*` headers are stripped; calls count as `cap__<server>__<tool>`. In-sandbox: `grain cap list`, `grain cap <server> <tool> --help` (flags from `inputSchema`), `--json`. CI jobs get `/home/debian/.grain/mcp.json` pointing at the same route. `POST /api/capability-servers/test` reports each method's resolved `delivery`. Bodies whose keys differ only in case are refused.
- **Control roster** (`d9897e69`, `2c29454d`, `ea85f8f7`, `ed7129ef`, PR #120): `grain mcpserver -mcp-surface=control|full`, default `control` whenever a sandbox flag is set: only the sandbox tools, run-ending/parking/escalation tools, tools of grants no sandbox may reach, refused agent API routes and local scripts; everything else is a `grain` CLI command. Runs without `grain-ci`, and CL tasks, keep the PR/checks tools. `read_grain_metrics` reports each tool's surface. Antigravity: `enter_plan_mode`/`schedule` denied with a pointer, plan mode off.
- **Hardening** (`86ab223c`, `c7773252`, `118c1b55`, `fcf70b76`, `ff53609b`, `801b61f2`, `49b22600`, `6019d829`, PR #101): sandbox CLI proposal keys hashed (`proposal:<task>:<sha256>`) instead of raw `--id` tags; `/api/` and `/cap/` forwarding refused for a run with no task; acting headers overwritten; proxy token kept off external capability servers; `api:releases:write` can no longer write the weekly release notes as a person.
- **SSH commit signing for ambient git credentials** (`c5960c3f`, PR #85): the host's `gpg.format=ssh` signing key is discovered and sandboxes sign via `POST /_grain/git-sign` without the private key entering the sandbox.

## §5. External agents over MCP/HTTP (`POST /mcp`, `gma_` credentials)

### What changed
- `007f8f01`, `f47007e7`, `8e12197d`, `fbbfbf5b`, PR #104: with `external_agent_api` on (off by default; schema 59), grain serves its generated `api_*` tools over Streamable HTTP at `POST /mcp` to external agents holding `gma_<hex>` bearer credentials (SHA-256 hashed in `external_agent_token`). Routes `/api/external-agents/tokens` list/create/rotate/revoke/delete and a revoke-all kill switch; issuing a credential with a dangerous or `requires_person` scope set needs a human. Tools filtered by the credential's scopes, task-context routes excluded, explicit repo required on `POST /api/tasks`, per-credential rate limits and concurrency caps, 4 MiB bodies, `409 config_managed_externally` preserved, calls attributed to `external:<name>` in the journal and task conversations. Filed work is held to repositories the credential's scope reaches (`tasks:write@owner/name` no longer reaches others); credential names are unique case-insensitively. `gma_` credentials are refused on every internal route.

3. **Limits**: rate limit and concurrency cap responses, a >4 MiB body, a repo-scoped credential filing work with `writes:`/`reads:` on another repo.

## §8. Sandbox images across GCP projects — `-sandbox-image-mirror` and Artifact Registry/GCR authentication

### What changed
- **Guest image mirror** (`45b4699c`, PR #132; migration renumbered to 63 in `885e4ee0`): `-sandbox-image-mirror` / `sandbox_image_mirror` / `sandboxImageMirror` (with automatic derivation for cross-project guest repos) makes the daemon at startup, on live config change and during an upgrade's `stageImage` pull the build-stamped `DefaultSandboxImage`, push it to the cluster's mirror repo, use the mirror's RepoDigest as the stock image (no custom-image drift warning), and clean old mirrored tags; a cluster pull-connectivity check suggests the mirror on cross-project/403.
- **Registry auth** (`9389378e`, `f934dd69`, `d0ac43a9`, `cdd4c798`, `98e28f76`, PR #106): `pkg/registryauth` resolves a Google OAuth2 token (gcloud credential, else metadata server, cached briefly); upgrade pulls, `RegistryManifestDigest`, `ListRegistryTags`, Settings' image checks send it only to bare `*-docker.pkg.dev`/`gcr.io` hosts, never across a redirect; `scripts/setup.sh` logs docker in as `oauth2accesstoken` via stdin.

### What CI proves
- `pkg/daemon/sandboximage_test.go`, `pkg/registryauth/registryauth_test.go`, `pkg/upgrade/google_registry_test.go`, `pkg/ui/google_registry_internal_test.go`, `pkg/cli` settings and daemon help goldens.

### What is NOT proved
1. **A mirror round trip against a real registry protocol**: a local `registry:2` (or `go-containerregistry`'s in-process registry) standing in for both the source and the mirror, a daemon started with `-sandbox-image-mirror` pulling, pushing and resolving the digest, the Settings sandbox image card showing it as stock, and old tags cleaned after a second build.
2. **Live config**: `grain settings` setting `sandboxImageMirror` on a running daemon and the mirror happening without a restart; clearing it.
3. **Token scoping over real HTTP**: a fake `*-docker.pkg.dev` host (via a resolver override or `httptest` with a matching `Host`) that redirects blobs to another host — the token reaches the first and never the second; a non-Google registry never sees it.

## §9. CI execution — the `grit` backend (`-grit-url`) and CI behaviour during daemon shutdown

### What changed
- **ci.Runner over `gritapi.Backend`** (`bc0d14c4`, `4a4ca911`, `11f47fbd`, PR #93): `grain daemon -grit-url -grit-client-token` runs CI through a separate `grit serve` with a durable mutation outbox, persisted `/v1/events` cursor with `410 cursor_gone` resync, per-request resolved capability secrets, and DSSE attestation verification before verdicts are recorded; direct or reverse-tunnel `/v1/session` (`grit serve -grain-url`). Embedded CI remains the default. Engine moved to `pkg/grit/engine` (`ed18c230`, PR #89).
- **Shutdown** (`4d8c7c53`, PR #96; `96141736`, PR #94): once shutdown begins the engine stops scheduling jobs, steps and retries; in-flight persistent-sandbox steps detach for readoption; failures in the shutdown window are recorded interrupted/cancelled and re-run by the next daemon; `/cli/ci/wait` and `/cli/ci/run-job` slices return `running` with `resume_run_id` at once; server shutdowns bounded at 10s.

### What CI proves
- `pkg/ci/backend_runner_test.go`, the Local/Client contract suite, `cmd/grit/main_test.go`, `pkg/daemon/shutdown_budget_test.go`, `pkg/gitproxy/cli_actions_test.go`, `pkg/ci` service tests.

### What is NOT proved
1. **Two real processes**: `grit serve` and `grain daemon -grit-url` running a repo's `.grain/workflows` end to end (a demo repo with a small workflow), verdicts appearing in `/ci` and on the task; the reverse-tunnel mode; `grit` restarting mid-run and the cursor resync; a tampered attestation refused.
2. **Shutdown under load**: `SIGTERM` to a daemon with queued, running and retrying CI jobs and a sandbox blocked in `grain ci wait`; measured shutdown time; the next daemon re-running the interrupted ones and the waiter resuming with `resume_run_id`.

### Walkthrough & test procedures
1. Build `grain` and `grit`. Start `grit serve` and a daemon with `-grit-url`/`-grit-client-token` and a temp data dir with a local repo (or `grain demo` if it accepts the flags); push a commit with a two-job workflow and follow it in the UI and `grain ci` CLI.
2. Restart `grit` mid-run; then repeat with `grit serve -grain-url` (reverse tunnel). Corrupt an attestation (test hook or a proxy in between) and confirm the verdict is refused.
3. With embedded CI, queue several jobs (one with a retry), start a `grain ci wait` from a sandbox, `SIGTERM` the daemon, time the exit, restart, and check the run records and the waiter.
4. Record in `docs/test-runs/<date>-grit-backend-ci-shutdown.md`.
