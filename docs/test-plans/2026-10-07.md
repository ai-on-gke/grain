## 1. Work trees: proposals filed at their tree's root

Commits:
- `527548296` (`main` `13765a492`, Fixes #2311): `putTask` resolves a new task's origin with
  `treeOrigin` (`pkg/model/work_origin_store.go`).
  - It walks up `proposed-by` links, and through any `task:` origin it meets, until it reaches a
    task with an origin of its own or a task nobody filed.
  - Before, a task filed by a parent with no stored origin took the parent itself as its origin.
    So every tree from before origins existed, whose root had no issue, split into a new tree at
    each parent that proposed work.
  - A named task origin (a run naming itself in `propose_task`'s `origin`) is resolved the same
    way, so it lands at the tree's root rather than at the named task.
  - A cycle in `proposed-by` links stops the walk at the task where the cycle is found. A task
    that is not stored is taken as a root.
- The same commit adds `Store.repairWorkOrigins`, called from `Store.Init` on every open.
  - It selects tasks whose `origin_ref` is `task:<id>` where `<id>` either has a parent or has an
    origin of its own, and rewrites each to `treeOrigin` of that id.
  - It is meant to be a no-op once the rows are right.
  - It uses `'task:' || id` string concatenation, as an older migration in `store.go` already does.
- `docs/work-trees.md` describes both.

### Existing coverage
- `pkg/model/work_origin_test.go` (+92 lines): inheritance through an origin-less parent, a named
  mid-tree origin, and a repair of a pre-fix row. These run on the default (SQLite) store.
- `ui/e2e/work-tree.spec.js` covers the task view's tree as it was before this fix. It does not
  build a tree from before origins.

### Gaps
- **PostgreSQL.** The repair's query (`LIKE`, `||`, `IN (SELECT DISTINCT …)`) and the walk's
  correlated `MIN(target)` subquery have only run on SQLite. Nobody has opened a PostgreSQL store
  holding pre-fix rows.
- **A real pre-fix database.** The unit test writes the stale row by hand. Nobody has built a tree
  with the binary from before the fix (`527548296^`), through the real `propose_task` path, and then
  opened the same data directory with the fixed binary.
- **Idempotence and cost on open.** Nobody has checked that a second open writes nothing, or timed
  the repair on a store with tens of thousands of tasks and links (this deployment's store is past
  2,400 tasks). The query runs on every daemon start.
- **What a person sees.** After the repair, does the task view's origin line ("generated from" and
  the origin beside it) and the tree view put every task under the true root? Does a GitHub
  progress comment (`TasksWithOrigin`) now list the whole tree, and does the old, smaller tree's
  comment stop being updated, or keep stale rows?
- **Mixed trees.** A tree whose root has a GitHub origin and whose middle has a chat-filed branch;
  a chat (standing session) as the root; a task whose stored origin names a deleted task. None of
  these has been walked.
- **MCP path.** A fake-agent run calling `propose_task` with `origin` set to its own task id, and
  one with `origin` set to a pull request, through the real MCP handler.

### Walkthrough & test procedure
1. **Pre-fix data, real path.** `grain demo` always runs on a throwaway store (it has no
   `-data-dir`), so make the pre-fix data with the store itself. In a `git worktree` at
   `527548296^`, write a small Go program that opens a SQLite store file with the same
   constructor the daemon uses, and builds a three-level tree with no origin at the root. File
   task A, then B as a proposal of A, and C as a proposal of B, through the same store calls
   `propose_task`'s MCP handler makes (read `pkg/mcp` for them; not raw SQL). Record each task's
   stored origin with `sqlite3`. Expect B and C to carry `task:A` and `task:B`. Open the same file
   from the fixed tree and assert C now carries `task:A`. Open it once more and assert nothing is
   written: compare row checksums, or wrap the store's DB in a counting driver in a Go test. If
   `grain daemon -data-dir <dir>` starts locally without GitHub credentials, also start the fixed
   daemon on a copy of that store, and record whether it does.
2. **PostgreSQL.** Repeat step 1's assertion in a Go test against the `postgres` CI job's
   database (see how `pkg/model/postgres/*_test.go` gets its DSN). Seed the pre-fix rows through
   the store's API with the walk disabled, or by writing `origin_ref` directly, as the SQLite test
   does. Add this test permanently.
3. **Scale.** In a Go benchmark or test, seed 20,000 tasks in 2,000 trees (half pre-fix shaped)
   and time `Store.Init` with and without stale rows, on SQLite and PostgreSQL. Record the times.
   If an already-repaired open costs more than ~1 s, file a follow-up (do not optimise in this
   task unless it is a missing index).
4. **UI.** If step 1's daemon started, open C's task view and the tree view against the repaired
   store in Playwright. Otherwise, in `grain demo`, build an origin-less A → B → C tree through
   the real API and MCP path on the fixed build. Assert that C sits under A, that the origin line
   names A, and that no tree is rooted at B. Screenshot both. Say in the report which store was
   used.
5. **Progress comments.** With `grain demo -github-sim` on `main` only (it is not on
   `candidate`), or a Go test with a fake GitHub client on `candidate`: give A a GitHub issue
   origin, then run the origin-comment writer. Assert one comment lists A, B and C, and that no

6. **Edge cases (Go tests):** a stored `proposed-by` cycle; an origin naming a deleted task; a

7. Report in `docs/test-runs/<date>-work-tree-origin-repair.md`.

## 4. Release names that git cannot use as a branch are refused

Commits:
- `b8c807bef` (`main` `c813631ef`): `model.ValidReleaseName` refuses `..`, a trailing `.` and a
  trailing `.lock`, on top of its charset (`^[A-Za-z0-9][A-Za-z0-9._-]*$`) and the `.latest` /
  `.rc.N` collision checks. The 2026-10-06 walkthrough had created `v3.0..x` with a 200.
- A release's name is its prod branch, and the stem of `<name>.latest` and `<name>.rc.N`.

### Existing coverage
- `pkg/model/sqlite/release_store_test.go` and `pkg/model/postgres/release_store_test.go` (the
  three new refusals).
- Playwright: `ui/e2e/team_repo_defaults_release_names.spec.js`, "refuses a release name git
  cannot use as a branch".

### Gaps
- **Is the rule now complete?** Nobody has checked `ValidReleaseName` against
  `git check-ref-format --branch` for every derived branch (`name`, `name.latest`, `name.rc.1`)
  over a generated corpus. With this charset the remaining rules look covered, but that is an
  argument, not a test. The reverse matters too: names git accepts that grain refuses (for
  example `v3.0-lock`, `a.b.c`) must still be accepted.
- **Rows stored before the fix.** A deployment that already stored `v3.0..x` still has it. What do
  the releases pane, `grain` CLI release commands, the reconciler and the cut schedule do with
  it? Does the reconciler log one clear error, or retry every tick? Can a person delete or rename
  it from the UI?
- **Every entry point.** The UI pane is tested. The CLI (if it creates releases) and a direct
  `POST` must give the same refusal and the same readable message, not a bare 500.
- **The `.rc.N` and `.latest` stems on promote/cut.** `CutCandidate` and `PromoteCandidate` with
  a name at the charset's edges (63+ characters, all digits, `_` and `-` runs) against a real git
  repository: the branches must actually be created.

### Walkthrough & test procedure
1. A Go test in `pkg/model` that generates names (all of the charset's two- and three-character
   strings, plus targeted cases: `..`, `.lock`, trailing `.`, `-lock`, `.latest`, `.rc.7`,
   `rc.7`, long names). For each, assert `ValidReleaseName(n)` is true exactly when
   `git check-ref-format --branch` accepts `n`, `n.latest` and `n.rc.1`, and `n` does not collide
   with the derived suffixes. Skip the test if `git` is missing. Keep it if it is fast (under 5 s).
2. `grain demo`: create releases in the releases pane and through `curl` with `v3.0..x`,
   `v3.lock`, `v3.` and `v3.0-lock`. Assert three refusals with a message a person can act on,
   and one success. Run any `grain` CLI release subcommand that takes a name (check
   `cmd/grain` for one) the same way.
3. Pre-fix rows: `grain demo` has no persistent store. So store `v3.0..x` through the store
   (for example, a Go test that writes the row with `CreateRelease` from a `b8c807bef^` worktree,
   or with a direct `INSERT` into a copy of the demo's SQLite schema), then open it with the fixed
   tree. Use `grain daemon -data-dir` if it starts locally. Record what the releases pane (or the
   releases API) shows, what the reconciler logs
   over five minutes (once, or every tick?), and whether the row can be deleted from the UI or
   API. A tight retry loop, a 500 on the pane, or a row that cannot be removed is a finding. Fix
   it if it is scoped: for example, the reconciler skips an invalid name with one warning.
4. Against a throwaway local bare repository (or the demo's githubsim on `main`), cut and promote
   a release named at the charset's edges, and assert the branches exist with `git ls-remote`.
5. Report in `docs/test-runs/<date>-release-name-validation.md`.

## 6. `main` only: the Silo gateway's egress byte counts

Commits:
- `11dbb21e1`: `countedConn` in `pkg/silo/gateway/proxy.go` gains a `sync.WaitGroup`. `Write`
  calls `Add(1)` before writing and `Done()` after counting. `forward`'s deferred audit calls
  `cc.wg.Wait()` before reading `ec.out`.
  - The reason: `net/http`'s Transport writes a request on a background goroutine
    (`persistConn.writeLoop`), so `ServeHTTP` could return before the last `Write` was counted,
    and the audit said `bytes_out: 0`.
  - The transport uses `DisableKeepAlives: true`, so one `countedConn` serves one request.
- No test was added with the fix.
- Borders 2026-10-06 §11 (Silo after part 1), whose report (`<date>-silo-v1-part2.md`) may already
  cover the gateway's proxy. Read it first if it has landed.

### Existing coverage
- `pkg/silo/gateway` tests for the egress proxy and its policy (from `3b0e1872a` and
  `c4c03e8e4`). None asserts `bytes_out` for a request with a body, under load.

### Gaps
- **No regression test.** The fix was argued from the race, and nothing pins it.
- **The fix may only narrow the race.** A `WaitGroup`'s `Add` with a positive delta, made while the
  counter is zero, must happen before `Wait`. If the writer goroutine has not yet *entered*
  `Write` for some part of the request when `forward` calls `Wait`, `Wait` returns at once and that
  part is still uncounted. That can happen to the body, for example, when the upstream replies
  before reading it (a 413, a 401, or a 100-continue refusal). The `-race` detector, or Go's
  "WaitGroup is reused before previous Wait has returned" panic, may also fire under load.
- **HTTPS / CONNECT.** If the gateway tunnels CONNECT through a different path, are its counts
  right? Is it the same `countedConn`?
- **The audit as a whole.** Large uploads (100 MB), chunked bodies, a client that aborts mid-body,
  and an upstream that resets: are `bytes_out` / `bytes_in` within a header's size of the truth,
  and is every request audited exactly once?

### Walkthrough & test procedure
1. Check out `main`, and confirm `11dbb21e1` is in it with `git branch -r --contains`.
2. Write a Go test in `pkg/silo/gateway` that runs the gateway in front of an `httptest` upstream.
   POST bodies of 0 B, 1 KiB, 64 KiB and 8 MiB, 200 times each, with `-race` and `-count=5`.
   Assert every audit record's `bytes_out` is at least the body length plus the request line,
   and that `bytes_in` is at least the response body length.
3. The same, with an upstream that replies 413 at once, without reading the body, and one that
   closes after headers. Record whether `bytes_out` is undercounted. If it is, fix the counting
   so it cannot race: for example, count on the transport's request-body wrapper as well, or
   count in `Write` with the totals read only after the upstream connection is closed and every
   `Write` has returned. Use a synchronization that is valid when no `Write` is in flight at
   `Wait`, and keep the test.
4. CONNECT/HTTPS through the gateway (if supported): an `httptest.NewTLSServer` upstream, 8 MiB
   up and down. Assert both counts.
5. Run `go test -race ./pkg/silo/...` 20 times in a loop and record any failure.
6. Report in `docs/test-runs/<date>-silo-gateway-egress-counts.md`.
