# Nightly new features test plan: September 29, 2026

This plan covers all features and behavioral changes merged into `candidate` and `main` over the past
day (following `docs/test-plans/2026-09-28.md` and subsequent runs) through `57e519bde`
(PR #2274). It encompasses over 35 merged pull requests and 80+ commits.

Key focus areas in this batch include:
1. **Team-Scoped Repository Architecture, Declarative Sync & Global Repo Elimination**: Full elimination of global TargetRepos, AgentGitName, AgentGitEmail, GitHubPostingCredential, and IgnoreGitHubCI from Config, CLI flags, UI, and database schemas in favor of strict team ownership. Introduction of `team_repo_config` model and storage, hierarchical Git proxy credential ladder (`(team, repo)` -> `team` -> `deployment`), declarative sync and export (`repos/<owner>/<name>.yaml`), and team-scoped repository settings UI management in `RepoPage.jsx`.
2. **Unpacked 4-Pane Team Settings Architecture & Self-Service Team Creation**: Full restoration of the unpacked 4-pane Team Settings layout (`TeamProfilePanel`, `TeamMembersPanel`, `TeamCapacityPanel`, `TeamGitPanel`), self-service team creation modal dialog (`CreateTeamDialog`) allowing any user to instantiate teams with automatic admin promotion, credential sharing/copying across owned teams, and active team URL synchronization.
3. **Holistic Base Branch Repair Engine for Multi-Fault Test Suites**: Revamped base branch repair agent prompts instructing repair agents that they are fixing the root base branch itself, directing them to take a holistic approach across all failing CI jobs simultaneously, disregard shared base fault skips, and iterate until all required jobs pass cleanly.
4. **UI Navigation, Sidebar Split-Button Task Intake & In-App Upgrade Flows**: Restored split-button creation dropdown on `+ New task` button in sidebar for direct template selection vs custom prompt dispatch, version propagation and in-app confirmation dialog on `UpgradePanel`, removal of merged task dissolution animations for optimal performance, and dedicated eigenmode icons for suites and metrics.
5. **Release Candidate (v1.2.0) Architecture & Symmetrical Cross-Branch Porting**: Release candidate stabilization (`candidate` branch), symmetrical backporting and forward-porting between `candidate` and `main`, release candidate triage documentation, and automated pipeline recovery verification.

Each section outlines what existing tests prove, the critical unproven gaps across real sandbox/browser environments, and concrete walkthrough steps.

## 1. Team-Scoped Repository Architecture, Declarative Sync & Global Repo Elimination

`f386abe49` (PR #2274, task-1031), `b972ead56` (PR #2268, task-1002), `2af24715c`, `72e2cb7aa` (PR #2264, task-1013), `b3d01012d` & `bb1aa718f` (PR #2259, task-999), `160c1e4b5` (PR #2253, task-998), and `962336362` (PR #2243, task-976) complete the transition to team-owned repositories and eliminate global repository configurations.

Concretely:
- `pkg/model/config.go` & `pkg/model/schema.go`: Completely remove `TargetRepos`, `AgentGitName`, `AgentGitEmail`, `GitHubPostingCredential`, and `IgnoreGitHubCI` from global system configuration, CLI flags (`--target-repos`, `--agent-git-name`, etc.), and database schema. All target repository declarations and Git identities are now strictly team-owned (`Team.TargetRepos`, `Team.AgentGitName`, `Team.AgentGitEmail`, `Team.GitCredential`).
- `pkg/model/team_repo_config.go` & `pkg/model/team_repo_config_store.go`: Introduce `team_repo_config` database table and models supporting granular per-team per-repository overrides for setup commands, prompt extensions, default capabilities, CI mode (`ci_mode`), Git credentials, and repair templates.
- `pkg/gitproxy/` & `pkg/model/store.go`: Implement hierarchical Git proxy credential resolution ladder: evaluates (1) explicit task grants (`github-credential:<name>`), (2) team-repo specific credentials from `TeamRepoConfig`, (3) team default credentials from `Team.GitCredential`, and (4) falls back to deployment credentials.
- `pkg/repodecl/team_repo.go` & `pkg/staterepo/team_config.go`: Implement declarative parsing and export of per-team repository configurations in team config state repositories under `repos/<owner>/<name>.yaml` and `repos.yaml`.
- `pkg/ui/teams.go` & `ui/src/components/RepoPage.jsx`: Add team-scoped repository configuration REST API endpoints (`GET/PUT/DELETE /api/teams/{id}/repos/{owner}/{name}`) and frontend settings management.
- `pkg/orchestrator/run.go`, `cmd/grain/ci.go`: Orchestrator resolves per-team repository settings during task dispatch, sandbox checkout, prompt extension composition, and CI capability injection.

### Existing coverage
- `pkg/model/sqlite/team_repo_config_test.go` and `pkg/model/postgres/team_repo_config_test.go` test CRUD operations and database constraints.
- `pkg/gitproxy/team_repo_credentials_test.go` tests credential override resolution across all four hierarchy levels.
- `pkg/repodecl/team_repo_test.go` and `pkg/staterepo/team_config_test.go` verify YAML serialization, declarative parsing, and state repository apply/export.
- `pkg/ui/team_repo_config_test.go` tests HTTP handlers, authorization checks, and invalid payload rejection.
- `pkg/orchestrator/team_repo_dispatch_internal_test.go` tests dispatch-time capability and setup script resolution.

### Gaps and unproven behaviours
- **Multi-Team Cross-Repo Isolation in Live Sandboxes**: Unproven in a live daemon environment whether two distinct teams targeting the same GitHub repository receive strictly their own team's Git credentials, custom setup scripts, and prompt extensions during agent sandbox checkout and task execution without leaking across teams.
- **Git Proxy Per-Repo Token Routing Under Concurrent Pulls**: Ensuring that concurrent git operations from multiple sandboxes targeting different repositories correctly resolve repo-specific tokens through the Git proxy daemon.
- **Declarative Team Config Repo Round-Trip**: Verifying that committing `repos/<owner>/<name>.yaml` to a team state repository automatically syncs into the live database and reflects in the UI `RepoPage` without server restart.

### Walkthrough & test procedure
1. Launch `grain demo` with multi-team mode enabled.
2. Create Team Alpha and Team Beta, both targeting repository `example/repo`.
3. In Team Alpha, configure a custom setup command (`echo "alpha setup" > /tmp/team.txt`) and custom Git token via `RepoPage.jsx` or API.
4. In Team Beta, configure a different setup command (`echo "beta setup" > /tmp/team.txt`) and distinct Git token.
5. Dispatch Task A under Team Alpha and Task B under Team Beta.
6. Verify in Task A's sandbox that `/tmp/team.txt` contains `"alpha setup"` and git pushes use Team Alpha's token.
7. Verify in Task B's sandbox that `/tmp/team.txt` contains `"beta setup"` and git pushes use Team Beta's token.
8. Export team configuration to state repo, edit `repos/example/repo.yaml`, push, and verify live sync updates the database.

## 3. Holistic Base Branch Repair Engine for Multi-Fault Test Suites

`98ecc3430` (PR #2261, task-1010) enhances the autonomous base branch repair system to handle complex multi-fault breakages.

Concretely:
- `pkg/orchestrator/basebranchci.go`: Overhauls the prompt construction for base branch repair tasks. When base branch CI fails across multiple jobs (e.g. `tests/go` and `lint` and `tests/ui`), the repair prompt explicitly informs the assigned agent that it is fixing the root base branch itself.
- Instructs the repair agent to take a holistic approach across all failing jobs rather than halting after resolving the first error.
- Instructs the agent to disregard "shared base fault" skips (which normal feature branch agents use to defer base errors) and persist in diagnosing and fixing every failure.
- `pkg/model/system_template.go`: Updates system templates for base branch repair with multi-fault diagnostic guidance, ensuring agents iterate until all required jobs pass before submitting their fix.

### Existing coverage
- `pkg/orchestrator/basebranchci_internal_test.go` verifies prompt formatting, multi-job failure aggregation, and single-flight lock acquisition.
- `pkg/model/system_template_test.go` tests repair prompt template rendering with single vs multiple failing jobs.

### Gaps and unproven behaviours
- **Live Multi-Fault Base Branch Breakage & Autonomous Repair**: Unproven in an active environment whether introducing multiple simultaneous failures (e.g. syntax error in Go + lint error in JS) on `main`/`candidate` causes the orchestrator to generate a holistic repair task, and whether the repair agent successfully addresses both faults in a single attempt.
- **Single-Flight Lock Deduplication Under Multi-Push**: Verifying that while a holistic repair task is actively running, subsequent CI webhook triggers or base CI polls do not spawn duplicate repair runs.
- **Auto-Merge Gate Enforcement**: Verifying that the repair pull request only merges when *all* failing jobs transition from red to green.

### Walkthrough & test procedure
1. In a test environment, introduce two distinct breaking changes onto the `candidate` base branch (e.g. breaking Go unit test in `pkg/model` and broken frontend test in `ui/`).
2. Trigger base branch CI; observe failure in multiple workflow jobs.
3. Verify orchestrator detects the broken base and dispatches a single holistic repair task with the updated repair prompt.
4. Inspect the repair task prompt; confirm it explicitly lists all failing jobs, notes base repair authority, and commands holistic multi-fault remediation.
5. Allow the repair agent to investigate, edit files across backend and frontend, and run CI checks.
6. Verify the repair pull request passes all required jobs and merges automatically into `candidate`, restoring base branch health.

Filed: **Walkthrough: Holistic Base Branch Repair Engine for Multi-Fault Suites (docs/test-plans/2026-09-29.md §3)**
