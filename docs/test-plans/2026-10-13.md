## 1. Mark a Task as Fixing a Red Base Branch

**Commits:** `6d3587d75`, `4b9fe38eb`, `19c83cad9`

### What changed
- While a base branch is confirmed red, `linkBrokenBaseDependents` links every ready task on it to wait
  on the branch's repair. A task a person filed to fix the branch was made to wait on the repair it was
  meant to be.
- A task can now be marked "This fixes a red `<base>`". The mark can be set in four places:
  - a checkbox in the New task dialog;
  - the task pane's Actions;
  - `fixesBaseBranch` on task create/PATCH;
  - `fixes_base_branch` on `propose_task`, on both the live and the relayed path.
- The mark is the repair's own branch tag (`base-ci-repair:<repo>:<branch>`) plus `fixes-base-branch`.
  So `isBaseRepair`, `openBaseRepair`, single flight and the merge queue's inherited-red wait all treat
  the task as the branch's repair.
- How a marked task behaves:
  - It is never linked to wait.
  - Marking a task that is already waiting drops the link (`DropBaseRepairWaits`) and comments.
  - Once approved and not deferred, it counts as the open repair, so grain files none of its own. An
    unapproved proposal does not count.
  - It runs alongside a grain repair that is already running, with a warning comment.
  - On green it is left open and gets one comment.
  - The tasks linked to wait on it are released. Their links carry `base-ci-wait:<repair id>`.
- Grain's own repair cannot be unmarked. Only people who can edit or file tasks in the repo can set the
  mark.
- `4b9fe38eb` moves the checkbox's help text out of a MUI Tooltip. The Tooltip had put "base branch"
  into the checkbox's aria-label.
- `19c83cad9` changes the repository overview. Its header keeps the unjudged-gate sentence. The release
  pane below now shows only a judged-but-late gate.

### What CI proves
- `pkg/orchestrator/baserepairlink_internal_test.go` covers linking, dropping, counting as the open
  repair, single flight, release on green, and unapproved proposals.
- `pkg/ui/fixes_base_branch_test.go` covers create/PATCH and permissions.
- Vitests cover `NewTaskOverlay` and `detail/Actions`.
- `base-branch-gate-warnings-walkthrough.spec.js` covers the overview wording.

### What is NOT proved
- The whole flow on a real orchestrator cycle with a forge: the branch goes red, tasks get linked, a
  person files a marked fix, the fix lands, and the branch goes green.
- What the user sees in the browser: the checkbox, the comment on a task that was waiting, the
  Inbox/Repository wording while the marked task is the open repair, and the green comment.
- That a member without edit rights cannot set the mark, and a viewer cannot see the control.
- `fixes_base_branch` through a real agent run's `propose_task` (relayed path).
- Retargeting a marked task to another base moves the mark.

### Walkthrough procedure
1. Start `grain demo -github-sim -fake-ci` (add `-merge-queue-states` if it helps) and Playwright.
2. Make `main` red on the simulated forge with a failing base-branch CI verdict, so grain confirms it red.
3. Check that ordinary ready tasks on `main` gain a depends-on link to grain's repair. The link must
   carry `base-ci-wait:`.
4. Open New task, tick "This fixes a red main" and file it. Check that:
   - it is not linked to wait;
   - grain files no repair of its own while it is approved;
   - the other tasks wait on it.
5. Mark a task that is already waiting from the task pane. The link is dropped and a comment says so.
6. As a viewer, the control is absent or disabled. As a team member who cannot edit, PATCH
   `fixesBaseBranch` returns 403.
7. Try to unmark grain's own repair. It is refused.
8. Turn `main` green. Grain's repair closes. The marked task stays open with one comment. Waiting tasks
   are released, and a depends-on link a person added stays.
9. Change a marked task's base to `candidate`. The tag follows.
10. On the repository overview, check that the unjudged-gate sentence appears once.
11. Drive `propose_task` with `fixes_base_branch: true` through the demo's mock MCP tools and confirm the
    filed task carries the mark.

## 2. Merge Queue Lanes, Contention Telemetry and Exact-Base Failure Eviction

**Commits:** `5c2776f62`, `0c7590e63`, `397e91eb0`, `cbad2978a`

### What changed
- **Lanes.** The merge queue decides order and capacity per (repo, base branch) lane
  (`pkg/orchestrator/mergelane.go`). Before this, a `main` change waiting on CI held every `candidate`
  change too.
  - `collectBatchCandidates` walks every member.
  - `mergeWalk` keys its slot and merge count on the lane.
  - `max_merges_per_repo` now applies per lane. The admin label reads "Max merges per repo branch".
  - Row notes name the lane: "behind task t2 in the acme/widgets candidate queue".
  - `MergeQueueHeads` returns one head per lane.
- **Contention telemetry.** It is now recorded as it happens, in `merge_queue_contention`:
  - A rebase, plus its retest, when a base is merged into a stale head.
  - A retest for every flake recheck and for every halved batch.
  - Queue wait runs from `MergeQueueEnteredAt` to the merge, and zero waits are kept.
  - `ContentionRate` is per landed change.
- **CI cache.** `ci_job.base_commit` is persisted.
  - `PurgeNegativeEntries` evicts failures recorded against exactly the given base.
  - A green base verdict no longer calls `ClearCache` across the whole deployment.
  - Merge-batch requests pass the batch's BaseCommit.

### What CI proves
- Lane unit tests in `pkg/orchestrator`, `pkg/metrics/merges_test.go`, and the ci store/dircache tests.
- The contention walkthrough test, updated to the new meaning (`397e91eb0`).

### What is NOT proved
- Two lanes of one repo progressing independently in a real queue: a `main` change held in CI while
  `candidate` changes batch and merge, with the row notes and the Merge Queue page showing per-lane
  wording.
- A task with no declared base falling back to the whole-repo stop.
- The contention numbers in the merges report (Metrics → Merges `contention`) matching a queue that
  really rebased, rechecked a flake and halved a batch.
- That a passing cache entry survives a green base verdict, and that a failure cached under base X is
  not replayed onto a run against base Y, in a real CI run.

### Walkthrough procedure
1. Start `grain demo -github-sim -fake-ci -merge-queue-states` with two branches (`main`, `candidate`)
   on one repo. Set `max_merges_per_repo` to 1.
2. Queue A1 on `main` with CI held pending, and B1 and B2 on `candidate` green. Check that:
   - B1 and B2 merge or batch while A1 waits;
   - each row's note names its own lane;
   - the label reads "Max merges per repo branch".
3. Add a task with no declared base and confirm the documented conservative behaviour.
4. Force a stale head, a flaky first verdict (fail, then pass on recheck) and a failing batch that
   halves. Read the merges report's `contention` and check the counts against what happened, including a
   zero-wait sample.
5. Use a real `grain ci` (or `-fake-ci` with the real DirCache):
   - Fail a job at base X, then turn the base green at X. Only that failure is evicted, and an unrelated
     passing entry is still a hit.
   - Run the same fingerprint against base Y. The X failure is not replayed.
   - Read `base_commit` back through the CI run API.

## 3. Scheduled Workflows on `candidate`, Reviews Only on Failure, Last Run Shown

**Commits:** `3d294d2c3`, `68f569693`, `983e5692c`, `c3c8a7a4f`

### What changed
- A `.grain/schedules` file can say `workflow: <stem>` with `base:`. It fires a trusted schedule CI run
  of that workflow on the base, then files the review titled with the base ("Review last night's
  "nightly" workflow run on candidate").
  - It is refused for a missing workflow, one with no `on: schedule`, a `.yaml` file, or
    `overlap: allow`.
  - It cannot be combined with `template:` or `suite:`.
  - Five `*-candidate.yml` schedules were added: nightly, gcp-smoke, live-agent, live-frameworks and
    live-secrets-repo.
- A firing whose run concluded success, with at least one passing job, settles with `ReviewNotNeeded`
  and files no review. Failure, errored, cancelled, lost, never-started, waited-out and a jobless success
  still file one. `review: always` opts back in.
- The schedules list and schedule pane show the last workflow run, linking the run and any review. They
  show a "Reviews every run" chip. `list_ci_runs` says "Started by schedule <id>."
- Saving a template resyncs the display copy on every schedule that names it (`syncTemplateCache`).

### What CI proves
- `pkg/ci/cron_test.go`, declschema and model schedule tests, and `pkg/ui/workflow_schedule_test.go`.
- The `SchedulesList` vitest, and `pkg/ui/templates_test.go`, with `4dd48467a` for the rename in e2e.

### What is NOT proved
- A `workflow:` schedule firing in a real daemon, then running the workflow's schedule-event jobs on the
  base, then settling or filing the review on that base with the right title and opening comment.
- Each refusal surfacing readably in the repo's declaration warnings and in the sync log.
- A green run with `review: always` filing a review. A green run without it filing none. A restart
  between run end and settlement filing exactly one review or none.
- The last-run line and links in the browser, and the "Started by schedule" line in `list_ci_runs`.
- `overlap: skip` honouring a settled-without-review firing.

### Walkthrough procedure
1. Start `grain demo -github-sim -fake-ci` and declare a small workflow with `on: schedule`. Add
   `.grain/schedules/x-candidate.yml` with `workflow: x`, `base: candidate`, `overlap: skip`. Fire it
   with Run now.
2. Let the run pass. No review task is filed, and the schedule row shows the run as passed with "no
   review needed".
3. Make it fail and fire again. One review is filed on `candidate` with the documented title and an

4. Set `review: always` and fire a passing run. A review is filed, and the chip shows.
5. Kill the daemon after the run ends but before settlement, then restart. Exactly one outcome follows.
6. Declare each refused form (missing workflow, no `on: schedule`, `.yaml`, `overlap: allow`,
   `workflow:` together with `template:`). Each warning is readable on the repository page.
7. Edit a template's title. The schedules list, the Run now confirmation and a refused template delete

## 4. Candidate Promotion Gated on Its Own Runs

**Commits:** `517e22d8e`, `c452efde2`

### What changed
`scripts/candidate-gate.sh <verdicts-file> <candidate-commit> [<rc-base-ref>]` applies the promotion
policy to a verdicts file the cutting agent writes. `release-candidate-cut.sh` calls it before tagging.

- Verdicts are one per workflow: `pass`, `known`, `infra`, `regression` or `missing`, each with the tested
  commit.
- `nightly` is required. Anything but `pass` or `known` (with a reason) holds. That includes a run that
  is missing, still running, or tested a commit outside the candidate.
- The live suites are advisory and hold only on `regression`.
- A missing verdicts file holds. `CANDIDATE_GATE=off` promotes without one.
- A held cut tags nothing and leaves `latest` alone, but still back-merges and cuts the next rc. The
  next promotion's release notes run from the newest existing release tag.
- The release watchdog runs the gate every six hours. The cut template gains step 1b.

### What CI proves
- The cut-script tests, which opt out with `CANDIDATE_GATE=off`, and the new gate-policy and held-cut
  tests.

### What is NOT proved
- A full cut against a scratch git repository (a bare origin with `main`, `candidate`, tags) for each
  policy case. That includes checking that a hold really leaves `latest` and tags untouched and still
  cuts the next rc.
- A commit outside the candidate (not an ancestor of it) being treated as missing.
- Release notes after a held minor covering the held minor's changes.
- The verdicts file a real agent would build from `list_ci_runs`/`get_ci_log` for the `*-candidate.yml`
  runs. Its format (comments, `-` commit, multi-word reasons) must parse.

### Walkthrough procedure
1. Build a scratch repository with a bare origin, `main`, `candidate`, `v1.8.0`, `v1.9.0-rc.N` and
   `latest`. Run `scripts/release-candidate-cut.sh` in it with `CANDIDATE_GATE_FILE` for each case:
   - all pass;
   - nightly `known` with a reason;
   - nightly `known` without a reason;
   - nightly `missing`;
   - nightly on a commit not in the candidate;
   - live-agent `infra`;
   - live-agent `regression`;
   - no file;
   - `CANDIDATE_GATE=off`.
2. For each case, record the exit code, the "Candidate gate:" line, the tags and `latest`, and the
   back-merge and next-rc results.
3. After a held cut, run a promoting cut. Its release notes include the held minor's changes.
4. Run the watchdog's gate invocation as the template describes. It reports without tagging.
5. Feed malformed lines (bad verdict word, too few fields). Each is a readable refusal, not a silent pass.

## 5. Model Proxy Forwards With the Run's Team Connection

**Commits:** `63e5aea06`, `77b09ad9c`, `01e41d2ae`, `cff10a84c`

### What changed
- A model-proxy token records a Connection when it is minted, and the connection is persisted with the
  token. It is either:
  - the connection that owns the run agent's credential (a `CredentialBackendID` borrower records its
    source), or
  - the team's own enabled, unpaused connection for the vendor.
- `ServeHTTP` forwards with that connection's key. It refuses, in the vendor's error shape:
  - a team with no connection ("team X has no Claude connection");
  - Vertex, ambient-login and codex-subscription connections;
  - a paused connection.
- There is no fallback to the deployment-wide secrets.
- A usage-limit answer from the vendor pauses that connection through the orchestrator's Pause, so proxy
  traffic and agent runs on one key pause together.
- Audit entries name the team and the connection.

### What CI proves
- `pkg/capability/modelproxy` and `pkg/daemon/modelproxy_connection_test.go`. These cover two teams, a
  team with no connection, a borrower, Vertex and subscription refusals, a usage limit pausing exactly
  one connection, and a persisted token keeping its connection.

### What is NOT proved
- A real sandbox run's traffic through the proxy. The tests drive `WireModelProxy` directly, not a run
  that minted its token through `RunDispatch`.
- The request reaching a stub vendor carrying team A's key, never B's or the legacy secret.
- The paused banner (10-11/10-12 per-connection pauses) naming the connection the proxy paused.
- The audit entries in the team audit log/API.
- A deployment upgraded from one that held only the legacy secret: the default team's migrated
  connection forwards, and a non-default team without a connection is refused readably.

### Walkthrough procedure
1. Run a real daemon (or `grain demo` with the model proxy wired) with stub Anthropic, OpenAI and Gemini
   endpoints that record the key they receive. Create teams A and B, each with a Claude connection, and
   team C with none.
2. Dispatch a run on A that calls the proxy. The stub sees A's key. Repeat for B.
3. Dispatch a run on C. It is refused with "team C has no Claude connection" in Anthropic's error shape.
4. Make A borrow B's backend. The stub sees B's key, and the audit names B's connection.
5. Have the stub answer a usage limit for A. A's connection pauses: the banner names it, A's next proxy
   call and A's next agent dispatch are both held, and B keeps forwarding.
6. Restart the daemon mid-run. The persisted token still forwards with the same connection.
7. Start from a store that holds only the legacy deployment secret. The default team forwards after
   migration.

## 6. Codex Shared-Login Renewal

**Commits:** `237c93a12`, `d5273f758`

### What changed
`codex.Refresher` runs in the daemon over every backend's `codex-auth-*.json`, the shared
`codex-auth.json` and `-codex-auth-file`. `grain executor` runs it over its own login.

- When it refreshes:
  - It reads the access token's JWT `exp` and refreshes halfway through the token's life, never later
    than 10 minutes before exp.
  - It uses codex's own grant and honours `CODEX_REFRESH_TOKEN_URL_OVERRIDE`.
- How it writes:
  - It takes an in-process mutex plus an flock beside the login, and re-reads under the lock.
  - It merges the new tokens and keeps unknown keys.
  - It writes atomically with mode 0600 over the file the path resolves to, so symlinks keep working.
- Permanent refusals (`refresh_token_reused`, `invalid_grant`, any 401, ...) are recorded beside the
  login, keyed to the refused token, and shown in the backend's login status in Settings. The file is
  never deleted, and a new upload clears the record. UI upload and clear take the same lock.
- `d5273f758` fixes a `-race` hit on the refresher's copy of the config.

### What CI proves
- `pkg/agent/codex/refresh_test.go`, `codex_login_files_test.go`, and the 2988 probe's `+refresher`
  cases. The live probe ran by hand against codex 0.153.0, not in CI.

### What is NOT proved
- A real daemon with a stub token authority and several backends whose logins are symlinked into run
  directories: one refresh per login per half-life, the symlink still valid, 0600 kept, unknown keys
  kept.
- Two processes (daemon and `grain executor`) sharing one file: exactly one refresh.
- A permanent refusal shown in Settings → backend login status, surviving a restart, and cleared by a
  new upload through the UI.
- An upload racing a refresh: the upload wins and is not overwritten by stale tokens.

### Walkthrough procedure
1. Start a stub OAuth authority that counts refreshes and can answer `refresh_token_reused`. Write
   logins whose JWT `exp` is a few minutes out, under two backends and the shared file, with a symlink
   from a run directory.
2. Start the daemon with `CODEX_REFRESH_TOKEN_URL_OVERRIDE` pointing at the stub. Check the refresh
   timing, the file mode, the kept keys and the symlink target.
3. Start `grain executor` on the same file. The authority sees one refresh, not two.
4. Make the authority refuse. Settings shows the refusal for that backend, and it is still shown after a
   restart. Upload a new login in the UI: the record is cleared and the file is not deleted.
5. Fire an upload during a refresh held open by the stub. The upload's tokens persist.
6. If a codex CLI is available, run one codex run against the stub after renewal. It makes no refresh of
   its own.

## 7. Run Hosts (Non-Disruptive Upgrade Stage 2, Single Machine)

**Commits:** `3f4fd4308`, `d7f97980a`, `4d0db5235`, `bb68cba96`, `88802f12e`, `1238ffaab`, `4da804cdd`

### What changed
- `pkg/runhost` runs one agent run's CLI (and the mcpserver it forks) in a sibling docker container, and
  reads it back through an append-only spool from a cursor.
  - Containers carry labels for deployment, task, run, generation, protocol, deadline and spool.
  - Protocol skew N-1 is accepted. An unreadable or newer protocol is refused by name.
  - The spool holds `command.json`, `env` (removed once read), `stdin`, `stdout`, `stderr` and
    `exit.json`.
  - `grain runhost exec` is the entrypoint, and it enforces the deadline label on itself.
- `task_run_spool_cursor` holds the read cursor, and `FinishRun` clears it.
- `orchestrator.RecoverRunHosts` runs the adoption decision at startup:
  - Unclaimed run hosts are freed.
  - Live rows whose run host is gone, refused by protocol, or past deadline are finished interrupted with
    that reason.
  - A match is finished with a reason saying that post-processing resume is not built yet.
- `-run-host-image` (with `-run-host-credential-dir`) drives claude runs in run hosts. codex stays local.
- The docker CLI gets only PATH, HOME, XDG_RUNTIME_DIR and DOCKER_*.

### What CI proves
- `runhost_test.go`, `adopt_test.go` (Decide table), `runhosts_test.go`, `spool_cursor_test.go`.
- The "run host" CI job runs `TestDockerRunHostSurvivesADaemonRestart` with real docker.
- `docs/test-runs/2026-10-12-run-hosts.md` records that run.

### What is NOT proved
- A real `grain daemon -run-host-image` running a claude run (stub model endpoint) end to end: the
  container labelled, the transcript in the task pane, the cursor rows advancing and cleared at finish.
- A daemon restart mid-run with a real store: the run is finished with the matched-run reason (not the
  generic one), and the container is removed or freed.
- Each adoption outcome from a real startup:
  - a container with no row;
  - a row whose container is gone;
  - a protocol label one ahead;
  - a deadline in the past.
- The `env` spool file removed once read, and secrets absent from `docker inspect` labels and env.
- That `-run-host-image` unset changes nothing, and that a codex run stays local with the flag set.

### Walkthrough procedure
1. Build the run-host image from the tree (stage `.grain-ca.crt` as the Docker notes say). Start a
   daemon with `-run-host-image` and a stub Anthropic endpoint, with a claude CLI available, or the
   repository's fake claude binary if that is all the image can carry. Record which.
2. Start a run. `docker ps` shows the sibling with all labels, the cursor rows advance, and the
   transcript streams in the UI.
3. Run `docker inspect`. It shows no credential in env or labels, and the spool's `env` file is gone
   once read.
4. Stop the daemon mid-run, then restart. The container is still there while the daemon is down, and the
   startup pass finishes the run with the documented reason.

- The skip line's wording in the task's comments.
- The tuning refusal comment on a real runner task in the UI.

## 12. Git Proxy: Self-Debug Read of grain's Source, Inflate Total, Spooled Push

**Commits:** `fee51eb3d`, `c7bb60106`, `4ebe6accc`, `70d5b3f98`

### What changed
- **Self-debug read.** `Store.GitScope` adds `bwsalmon/grain` (`model.GrainSourceRepo()`) to a live run's
  reads when its task holds `self-debug` and its team holds the grant deployment-wide.
  - The read is fetch-only. Pushes stay refused even with `git-push-any-ref`.
  - A team-scoped holder gets no `grain-src/` and falls back on `read_grain_source`.
- **Inflate total** (`4ebe6accc`, adapted for candidate's streaming walk). The pack walk bounds the total
  it inflates at 256 MiB plus 8× the compressed bytes read so far. Past that it fails closed with the
  usual fast-forward refusal.
- **Spooled push** (`70d5b3f98`). A push over the spool threshold is walked from its spool file through
  an `io.SectionReader`. It is never read back whole.

### What CI proves
- `tests/security` `TestGitProxySelfDebugGrantIsAReadOfGrainsSourceOnly` (including the team-scoped
  sandbox-d), and `TestGitScopeReadsGrainsSourceForASelfDebugRun`.
- `TestReadPackCommitsBoundsWhatThePackInflates`, `TestReadPackCommitsReadsPastABlobOverTheObjectBound`,
  `TestGitProxySpooledPushAllocatesByThresholdNotPushSize`, and the 40 MiB live fast-forward test.

### What is NOT proved
- A real run on a demo or daemon with `self-debug`:
  - default team: `grain-src/` cloned and pinned to the build;
  - a team Settings widened the grant to: same;
  - team-scoped: none, with the prompt's "unauthorized" section present.

  The access must show in the team audit log (10-12 §1).
- A real `git push` of a zlib-bomb pack (many highly compressible blobs) through the proxy over HTTP:
  refused within a bounded time and bounded memory, then an ordinary push succeeds.
- A spooled multi-hundred-MiB push measured by RSS on the live proxy, not only `testing.AllocsPerRun`.

### Walkthrough procedure
1. Run `grain demo -github-sim` (or a daemon with a forge stub) with `bwsalmon/grain` served by the sim.
   Dispatch self-debug tasks on the default team, a widened team and a team-scoped team. Record
   `grain-src/` presence, the clone ref, and the prompt section, then try a push to grain from each.
2. Build a pack with 64+ blobs of zeros (and a commit), and push it with real git over HTTP through the
   proxy to a fast-forward-checked ref. Record time, peak RSS and the refusal text, then push a normal
   fast-forward.
3. Push 300 MiB at the default spool threshold. Record peak RSS and that the spool file is cleaned up.
