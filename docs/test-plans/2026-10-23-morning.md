## 1. `grain hostd` Protocol 2: Detached Processes, Drain and Version Handshake

**Commits (main only):** `a1ea68161` (protocol 2), `b82d33cb6` (`runhost.DecideHostd`, design doc), `dacee7e00` (protocol-1 table entries cancel promptly), `d4710cf06` (test naming)

### What changed
- **Detached starts (`Request.Detach`, with run and task ids):**
  - stdout and stderr go to a spool under hostd's `-state-dir`, with the run host's layout: append-only streams, and `exit.json` written once by rename;
  - when the daemon's connection drops, the process keeps running until its own deadline, and only its stdin is closed;
  - a detached process that ends with no daemon attached keeps its final spool for 24 h, across a hostd restart too.
- **New ops:**
  - `OpProcesses` lists id, run, task, entry, pid, start, deadline, spool and each stream's end;
  - `OpAttach` re-attaches from a cursor, so a second daemon reads the rest with no hole and no duplicate;
  - `OpCancel` releases a process nobody claims.
- **Drain:** `OpDrain`, `grain hostd -drain` or SIGUSR1.
  - New starts get a distinct draining refusal (`IsDraining`).
  - Running children carry on; when they have ended, hostd exits so systemd starts the new binary.
  - The allowlist's `drain_cap` (default 1 h) bounds the wait. At the cap, the remaining children are cancelled, and that is logged.
- **Handshake:** `OpHello` exchanges `{protocol_version, min_compatible, build}`. `ProtocolVersion = 2` and `MinCompatible = 1`. A hostd that predates it answers "unknown op" and is taken as protocol 1.
- **`runhost.DecideHostd` (`b82d33cb6`):** maps hostd's listing onto the run-host adoption table:
  - a live row matched to a process is adopted, with the gap credited as wait time;
  - an unmatched process is released;
  - a process past its deadline is finished and released;
  - past one version of skew, every matched row is finished with the mismatch as its reason.
- **Not wired yet:** per the commit and `docs/design/cli-run-location.md` "Upgrades and host runs", **no daemon starts anything detached yet**. Daemon behaviour today is unchanged, so this feature can only be exercised at the hostd protocol level.

### What CI proves
- `pkg/hostd/detach_linux_test.go`: detach, spool, attach from a cursor, drain, `drain_cap`, the hello handshake, and protocol-1 entries being listed and cancelled promptly. These use an in-process server on a temporary socket.
- `pkg/runhost/hostd_test.go`: the `DecideHostd` table (adopt, release, finish past deadline, version skew).

### What is NOT proved
- `grain hostd` as a **real separate process**, built from the tree and run under its own uid, with a root-owned allowlist:
  - a detached child surviving its client's process being **killed** (SIGKILL, not a clean close);
  - a second client process attaching from the first one's last cursor, with byte-exact output;
  - the `exit.json` and 24 h retention surviving a **hostd restart**, with the restarted hostd's `OpProcesses` still listing the finished process.
- `grain hostd -drain` and `kill -USR1` against the running server:
  - a start made during the drain is refused with the draining error, and the CLI's own exit status and message say so;
  - hostd exits once the last child ends;
  - a low `drain_cap` (for example `1m`) cancels a long child and logs it.
- That a protocol-1 client (a binary built from `origin/candidate` before the cut, or a hand-built hello-less request) still gets served by a protocol-2 hostd, and the other way round: a protocol-2 client against an older hostd binary is taken as protocol 1, and does not try to detach.
- `grain hostd -check` on an allowlist with `drain_cap` set, unset and invalid.
- Under a `systemd-run --user` (or system) unit with `Restart=always`, that the drain exits cleanly and the unit comes back up on the new binary.

### Walkthrough procedure

2. Build `grain` from `origin/candidate` (`go build -o /tmp/grain-new ./cmd/grain`). Also build a pre-protocol-2 binary from `a1ea68161^` (`/tmp/grain-old`).

## 2. Capability Server Grants with Arguments: API, Schema Forms, Chips and Settings Table

**Commits (main only):** `7535def4e` (API and demo server), `d981a1a64` (forms and chips), `4e1b3a706` (docs, Vitest, `attach` required), `b983dec43` (layout fixes), `ee6752e63` (contact sheets)

### What changed
- **Registry and API (`7535def4e`):**
  - the registry's server status carries each method's description, normalized args schema and `stateful` (it has a `release_<method>`);
  - `GET /api/capability-methods` lists every attached method with its schema;
  - `POST /api/capability-grants/check` normalizes grants exactly as task creation does, without writing. A recorded grant that no longer validates, or now normalizes differently, is reported rather than rewritten;
  - both routes are `trusted` in `tests/security/routes_test.go`.
- **Task capabilities route:** `POST /api/tasks/{id}/capabilities` now also takes `{capability, with, attach}`, `{grant, attach}` (a recorded `<ref>=<json>` string) and `replace`, which edits a grant in place.
  - `{id, attach}` is unchanged. Equal grants still dedup.
  - A schema refusal comes back with a `fields` map keyed by argument path, from this route and from task creation.
  - A grant body naming a capability must say `attach`, so a misspelt body is a 400, not a silent detach (`4e1b3a706`).
- **`/api/config`** carries `capabilityMethods` as a count only. The pickers fetch schemas from the trusted route only when there are some.
- **Demo:** `grain demo` attaches a real loopback capability server, `https://capabilities.demo.grain.example/cloud`. Its `cloud-key` method uses enum, pattern, bounds, boolean, array, `$defs` and default arguments.
- **UI (`d981a1a64`, `b983dec43`):**
  - `CapabilityArgsForm` renders the enforced keywords: enum/const as a select, boolean as a switch, strings with live pattern and length checks, bounded numbers, arrays as add/remove lists, `$ref`/`$defs` objects, and `oneOf`/`anyOf` as a variant picker. Anything it cannot draw becomes a JSON editor that the server checks;
  - secret-looking arguments are not offered;
  - `CapabilityMethodGrants` shows chips ("cloud-key · account: staging"). Clicking a chip edits it in place, "Add another" grants the method again, and a stale grant is flagged;
  - it is used in New task, the task pane (`CapabilityToggles`), and the template and schedule editors;
  - Settings → Credentials → Capability servers has a method table: arguments, type, required, default, allowed values or pattern, description, stateful.

  - Specifically: a template with a grant with arguments, instantiated into a task, carries the same normalized grant; a schedule's grant reaches the task it files.

  - record a grant on a task;
  - change the demo server's schema, or detach the server and reattach it with a narrower enum;
  - the chip is flagged and not rewritten, and `/api/capability-grants/check` reports it.
- **Running-task edits:** the "applies on the next run" behaviour, with a grant edited on a running task.

- **The no-secrets rule:** an argument named like a secret (`token`, `password`) is not offered in the form, and a raw API call carrying one is refused or flagged.
- **Removal:** `{grant, attach:false}` on a chip detaches exactly that grant when two grants of the same method exist.

## 3. Container Mode Plus `grain hostd` as the Cloudtop and Google-Track Install Shape

**Commits (main only):** `3697762f8` (installer), `3d0093132` (installer end-to-end test, `GRAIN_LOCAL_API_TOKEN_FILE`, `--git` picks host mode), `599cda734` (shellcheck), `31645a83d` (docs)

### What changed
- **`scripts/setup.sh`** gets `GRAIN_HOSTD` (`auto`, `1`, `0`). `auto` installs hostd for a container-mode deployment on the Google track, and keeps it wherever the installed unit already passes `-hostd-socket`. With hostd:
  - the image's own `grain` is extracted to `/usr/local/bin/grain`, and is re-extracted by an `ExecStartPre` on every start, so an upgrade brings the host binary along;
  - `grain-hostd.service` runs `grain hostd` as `GRAIN_USER`, with `RuntimeDirectory=grain-hostd` (preserved), a `StateDirectory`, and the corp proxy from `/etc/grain/hostd.env`. The daemon unit only `Wants=` it and starts `After=` it;
  - `/etc/grain/hostd.yaml` is written once, root 0644, with an agy entry on the Google track. A re-run keeps the operator's edits and only restores the owner and mode;
  - `docker_run_args` mounts `/run/grain-hostd` (the directory) and sets `TMPDIR` to `GRAIN_SANDBOX_DIR/tmp`. `/etc/grain` is not mounted;
  - agy is neither mounted nor passed as `-agy-path`; the daemon gets `-hostd-socket`;
  - the install reports whether `GRAIN_USER` can reach the docker socket.
- **`google/scripts/cloudtop-install.sh`** defaults to container mode.
  - Host mode is an explicit opt-in, recorded as `GRAIN_HOST_MODE_OPT_IN=1`.
  - Re-running on an older host-mode Cloudtop migrates it to container mode plus hostd, keeping the data dir and `grain-daemon.service`.
  - `GRAIN_INSTALL_MODE=host` rolls back, and later re-runs keep the rollback.
  - `--git` with no mode picks host mode, because the ambient `gh`/`forgecli` login exists only on the host.
- **The agy allowlist entry** sets `GRAIN_LOCAL_API_TOKEN_FILE`, so a host-run `grain mcpserver` can reach the daemon's API (found by `3d0093132`'s test).

### What CI proves
- `google/scripts/cloudtop_install_test.go` and `tests/deploy/deploy_test.go`: the generated script and unit shapes.
- `tests/installer/zz_hostd_test.go` (`TestGoogleTrackRunsAgyThroughHostdAndMigratesFromAndBackToHostMode`), with a fake claude and a fake agy (`tests/installer/fakeagy`), runs in the installer CI job. It covers:
  - migration from host mode, and rollback;
  - agy through hostd forking the host's `grain mcpserver` and making two tool calls;
  - cancel and allowlist `max_duration`;
  - a `run: host` capability server;
  - the allowlist being unreachable from the container.

### What is NOT proved
- **The plain `scripts/setup.sh` track** with `GRAIN_HOSTD=1` and `GRAIN_HOSTD=0`, rather than the Google track:
  - explicit `1` on a non-Google install writes an allowlist with no agy entry and still starts `grain-hostd.service`;
  - `0` on a re-run removes it, or leaves it, as documented.
- **Upgrade path:** an image upgrade (`grain upgrade` or a unit restart onto a newer tag) re-extracting `/usr/local/bin/grain` through `ExecStartPre`. The host binary's `grain version` should match the container's afterwards.
- **hostd restarts:** restarting `grain-hostd.service` while the daemon runs. The daemon must see the new socket through the directory mount, without its own restart.
- **Re-runs:** running the installer twice in a row in container mode is idempotent. The units are unchanged, the allowlist is unchanged, and no service restarts beyond the documented ones.
- **Docs:** that what `google/docs/cloudtop-install.md` and the README's install notes describe matches what an install actually leaves on disk (units, paths, modes, env files).
- **Failure messages:** that the "cannot reach the docker socket" report is accurate when `GRAIN_USER` is not in the `docker` group.

4. Run the installer twice in container mode. Diff the unit files and allowlist between runs, and check `systemctl show -p ActiveEnterTimestamp` for unexpected restarts.
