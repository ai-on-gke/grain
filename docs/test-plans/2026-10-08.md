## 1. Typed Git Credentials & SSH Smart HTTP Bridging

**Commits:** `1ce752d23`, `9e6a5066f`, `3c0b66dea`, `3c2b455d8`, `affa117d8`

### What changed
- Git credentials can now be an SSH key stored as `<name>.ssh.json` (alongside PAT `<name>.token` and GitHub App `<name>.app.json`).
- SSH keys support Ed25519 or RSA private keys, optional passphrases, custom SSH port/user, and pinned `known_hosts`. GitHub's published Ed25519 and ECDSA host keys are defaults on `github.com`.
- Sandbox containers continue speaking smart HTTP to `gitproxy`. When upstream uses an SSH credential, `gitproxy` (`pkg/gitproxy/sshforward.go`) bridges smart HTTP to upstream SSH (`git-upload-pack`, `git-receive-pack`) per HTTP request, replaying negotiations and streaming responses.
- An SSH credential may pair with an `api_credential` (PAT or App) for GitHub REST API calls (such as opening and merging PRs). If unpaired, git operations succeed but PR operations fail fast with `GitOnlyReason` ("repository is git-only").
- The UI in Team Settings ▸ Git identity (`ui/src/components/TeamGitPanel.jsx`) provides a typed credential editor supporting PAT, SSH key, GitHub App, and None (public).
- A Test button performs an active `ls-remote` over SSH to test connectivity and host key verification.
- `GET /api/teams/{id}/github-credential` returns non-secret metadata (key fingerprint, login, paired API status, git-only warning).

### What CI proves
- `pkg/gitproxy/ssh_live_test.go` and `sshkey_test.go` verify protocol v0/v2 clone, fetch, and push against an in-process SSH daemon, as well as passphrase decryption and host key pinning.
- `pkg/ui/team_git_credential_types_test.go` tests validation of PUT payloads across all types.
- `tests/security/routes_test.go` tests that credential routes require team membership.

### What is NOT proved
- End-to-end integration through `grain demo` where a user configures an SSH key in Team settings, tests the connection in the browser UI, executes a task that clones and pushes through `gitproxy` using the bridged SSH connection, and verifies PR creation behavior when an API token is paired vs unpaired.
- Verification of host key refusal behavior in the UI when connecting to non-github.com hosts without known_hosts entries.

### Walkthrough procedure
1. Launch `grain demo` with Playwright browser test.
2. Navigate to Team Settings ▸ Git identity.
3. Configure an SSH credential with a valid test Ed25519 key against a simulated SSH Git server.
4. Verify the UI displays the key fingerprint and "git-only" warning when no API token is paired.
5. Click "Test connection" and verify successful `ls-remote` status.
6. Trigger a task on the team; confirm `git clone` and `git push` succeed through the HTTP-to-SSH bridge.
7. Attempt to open a PR on an unpaired SSH repo; verify the clear "git-only" refusal message.
8. Add a paired API token; verify PR creation succeeds.

## 2. Declared Push Sets & `git-push-any-ref` Team Capability

**Commits:** `1b622135b`, `97edf2e95`, `71ba044ac`, `50576a8fe`, `283384c87`, `5555baf11`, `4ae617d0e`

### What changed
- Repository templates (`.grain/templates/*.yml`) can now declare explicit ref patterns under `push:` (e.g. `refs/heads/candidate`, `refs/tags/v*`), with optional `force: true` or `delete: true`.
- Stored in `repo_declaration_push`, written only by default-branch declaration syncs.
- `gitproxy` inspects push commands (`pkg/gitproxy/refupdates.go`) and validates non-task-branch updates against the template's declared push set. Fast-forward updates are strictly verified by walking commit packfiles (`pkg/gitproxy/pack.go`).
- `git-push-any-ref` is converted from an admin-only capability into a standard team capability grantable by any team.
- The UI displays declared push sets on Task Detail ("May also push") and on the Repository declarations page.
- Release candidate cut template (`.grain/templates/release-candidate.yml`) declares its push refs instead of requiring admin capability.

### What CI proves
- `pkg/gitproxy/declared_push_test.go` tests ref matching, glob parsing, force/delete restrictions, and pack commit ancestry checks.
- `pkg/repodecl/push_test.go` tests YAML parsing of `push:` blocks.
- `ui/src/components/detail/Declared.test.jsx` tests rendering of the "May also push" badges.

### What is NOT proved
- End-to-end task execution in a real sandbox where a task filed from a template with declared `push:` pushes to a declared branch, while attempting to push to an undeclared branch is blocked by `gitproxy` with an informative audit refusal.
- Verification that modifying `.grain/templates` on a task branch does NOT widen the push set (enforcing default-branch provenance).
- Verifying UI Task Detail displays the declared push set correctly in `grain demo`.

### Walkthrough procedure
1. Launch `grain demo`.
2. Seed a template with `push:` allowing `refs/heads/staging` (fast-forward only).
3. File a task from this template. Verify Task Detail shows "May also push: refs/heads/staging".
4. Within the task sandbox, push a commit to `origin staging`; confirm success.
5. Attempt a force push (`git push -f origin staging`); verify rejection by `gitproxy` with refusal naming force push not permitted.
6. Attempt to push to `origin main` (undeclared); verify rejection by `gitproxy`.
7. Grant the team `git-push-any-ref`; verify ad-hoc push permissions work as expected.

## 3. Settings State-Repo Three-Way Merge, Backups & Sync Failure Alerting

**Commits:** `aca22f7df`, `0c2d1fce3`, `1338ded2f`, `f7d8bb9b5`, `5699f2870`, `6543cf760`

### What changed
- State repository imports now perform a true three-way merge (`pkg/staterepo/merge.go`) against the last agreed commit (`loadedHead` or merge-base). Database rows added or modified locally that were untouched upstream are preserved rather than overwritten.
- Ambiguous imports return `ErrNotApplied` / `ErrNoMergeBase` and refuse to overwrite data.
- Table snapshotting (`pkg/staterepo/snapshot.go`): Prior to mutating settings or memory tables on SQLite, the daemon snapshots tables into `<dataDir>/settings-snapshots/<timestamp>-<head>` with a manifest. Snapshots retain the last 10 / 7 days.
- CLI subcommand `grain state restore-snapshot <dir>` restores settings tables from a snapshot.
- Sync failure detection: `StateManager` tracks consecutive export failures. If sync fails for >5 minutes, `ui.StateRepoSyncFailure` triggers:
  - Persistent red warning banner in the UI header ("Settings have not been exported to grain/config since <time>: <error>").
  - An inbox item for deployment administrators.
  - Reported in `read_deployment_health` via `/api/sandboxes`.

### What CI proves
- `pkg/model/postgres/staterepo_roundtrip_test.go` and `pkg/staterepo/soak_test.go` test 3-way merge logic and Postgres syntax compatibility.
- `cmd/grain/state_test.go` and `pkg/staterepo/snapshot_test.go` test snapshot creation and restore.
- `ui/src/components/StateSyncFailingBanner.test.jsx` tests rendering of the warning banner.

### What is NOT proved
- Live end-to-end rehearsal of the failure lifecycle: inducing a state-repo export failure in `grain demo`, waiting 5 minutes (or accelerating the ticker), verifying the banner appears across UI pages and in the Admin inbox, fixing the export failure, and observing automatic banner dismissal.
- Live CLI verification of `grain state restore-snapshot` restoring modified configuration without restarting the daemon into an inconsistent state.

### Walkthrough procedure
1. Launch `grain demo` with state repo enabled.
2. Modify a setting in the UI (e.g. team description). Verify normal export.
3. Make the state repo upstream unwritable (e.g. chmod 000 or fake git proxy failure) to induce sync failure.
4. Advance time past 5 minutes; verify the StateSyncFailingBanner appears in the UI and an alert is added to the admin Inbox.
5. In the UI, edit another setting; verify local edit is preserved in the database.
6. Verify snapshot directory contains pre-mutation snapshots.
7. Run `grain state restore-snapshot` on a previous snapshot; verify restored values.
8. Restore state repo writability; verify sync succeeds and the warning banner automatically clears.

## 4. Team Dispatch Pause & Scoped `self-debug` / `pipeline-control`

**Commits:** `6febf9dfb`, `ba57807bf`, `feee05ac9`, `d0dcbb7e8`

### What changed
- Teams can pause and resume their own task dispatch independently:
  - Table `team_pipeline_pause` stores per-team pause status.
  - Endpoints `GET/POST/DELETE /api/teams/{id}/pipeline-pause` accessible to team admins and team tasks with `pipeline-control`.
  - UI shows a dedicated banner for paused teams ("Team <name> paused by <user>... Other teams keep dispatching") with a "Resume team" button.

## 5. Repository Declarations Capabilities Bounded by Team Grants

**Commits:** `7772454c1`, `9e8efc1e7`, `a2c4c614f`

### What changed
- Declarations in `.grain/templates/*.yml` and `.grain/schedules/*.yml` may declare arbitrary capabilities (e.g. `capabilities: [gcp-key, self-debug]`).
- Team authorization acts as an enforcement boundary:
  - If the team running the task holds the requested capability, the grant succeeds.
  - If the team does not hold the capability, the unauthorized capabilities are stripped before task execution, and an explanatory comment is posted to the task conversation detailing what was stripped and why.
- Route `PUT /api/teams/{team}/repos/{owner}/{name}/config` validates default and CI capabilities, refusing unknown or invalid capability IDs (`a2c4c614f`).
- Trigger `.grain/triggers/grain-declarations.yml` protects `.grain/**` against unreviewed modifications.

### What CI proves
- `pkg/repodecl/repodecl_test.go` and `pkg/model/compose_test.go` test capability parsing and stripping.
- `pkg/ui/team_repo_config_test.go` tests rejection of unknown capability IDs.

### What is NOT proved
- Real browser and dispatch walkthrough: filing a task from a template requesting both authorized and unauthorized capabilities for a team; verifying that the unauthorized capability is stripped, the task conversation receives the explanatory comment, and the sandbox VM launches with only authorized capability files.
- UI validation when editing team repo configuration: verifying the form prevents saving unrecognized capability IDs with inline error feedback.

### Walkthrough procedure
1. Launch `grain demo`.
2. Configure a repository template requesting capabilities `[self-debug, gcp-key]`.
3. Set team permissions such that `self-debug` is allowed, but `gcp-key` is not.
4. File a task using this template for the team.
5. Verify the filed task has `self-debug` attached and `gcp-key` stripped.
6. Check task conversation: confirm an explanatory comment explains that `gcp-key` was stripped due to team authorization boundaries.
7. Inspect sandbox container/VM: verify only `self-debug` environment/files are present.

## 6. Team-Scoped Memory Layers & Isolation

**Commits:** `e68d82dcb`, `d0921dec5`, `653d1ffa4`, `2e4278a94`, `bb59ae1d6`, `7f7d98594`

### What changed
- Agent prompt memory resolution is now structured in three distinct hierarchical layers:
  1. Deployment memory (`memory/deployment.md`)
  2. Team memory (`memory/teams/<team>/team.md`)
  3. Team-repo memory (`memory/teams/<team>/<owner>/<name>.md`)
- Legacy repo memory (`memory/repos/<owner>/<name>.md`) is mapped to the team owning the repo.
- The `memory` capability is now team-scoped: non-admin teams can grant memory read/write for their own team and team-repo layers. Deployment-level memory modification remains restricted to system admins.
- State repo exports and imports memory documents under the team hierarchy.
- Background memory agent system schedules are seeded per team.
- Team Settings ▸ Models ▸ Memory panel is scoped to show only memories for the team's repositories (`7f7d98594`).

### What CI proves
- `pkg/orchestrator/memory_prompt_internal_test.go` verifies memory isolation in prompt rendering across teams.
- `pkg/ui/memory_test.go` verifies memory API endpoints enforce team isolation.
- `ui/src/components/MemoryPanel.test.jsx` verifies the UI filters out memories belonging to other teams.

### What is NOT proved
- End-to-end multi-team walkthrough: agent tasks run concurrently under Team A and Team B on the same repository; Team A writes a memory entry using MCP memory tools; verify Team A's subsequent runs receive the memory in their prompt, while Team B's runs never see Team A's memories.
- Verifying the state repo round-trip accurately dumps and restores team memory documents under `memory/teams/`.

### Walkthrough procedure
1. Launch `grain demo`.
2. For Team Alpha, create a memory document via the UI or API under team scope.
3. For Team Beta, verify the memory document does NOT appear in Team Beta's settings or MemoryPanel.
4. Run an agent task under Team Alpha; verify prompt includes Team Alpha's memory layer.
5. Run an agent task under Team Beta; verify prompt excludes Team Alpha's memory layer.
6. Verify export to state repo correctly writes to `memory/teams/alpha/team.md`.
