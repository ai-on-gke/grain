## Branch situation & how follow-up tasks should handle it

Releases are cut from `main` by the continuous train (`.grain/settings.yml`, `scripts/release.conf`), with no daily cap. From PR #1290 every release also has a **release manager** task that checks in hourly. A `fix:` a walkthrough lands on `main` ships with the next rc and needs **no backport task**. The exception is a defect the operator asks to patch on `release/v3.5.1` or `release/v3.1.1`. For that, fix `main` first, then propose a backport with `writes: [{repo: "ai-on-gke/grain", base: "release/vX.Y.Z"}]` and `Backported-from: <sha>`.

Every follow-up walkthrough task filed from this plan targets `main` (`repo: "ai-on-gke/grain"`, `branch: "main"`) and depends on [Task #4725](/tasks/4725), so `docs/test-plans/2026-11-13.md` is on `main` when each walkthrough begins. Each proposal asks for unattended `auto_merge: true` once CI is green. The operator who approves the proposal decides whether to grant auto-merge on `main`.

The gate is **GitHub Actions**: `Tests` in `.github/workflows/tests.yml` (from PR #1410 this includes a separate **`ui-ng e2e`** job), `plc-tests.yml` when `grain-plc/` is touched, `cla/google` and the workflow/hygiene scans. From PR #1229 every grain-opened PR also gets a **gating code review** (`.grain/triggers/every-pr.yml`), and edits to classified paths still get the security review. Inside a sandbox, open the PR with `grain pr open` and wait on its checks with `grain ci wait` (with `timeout: 600000`, no `--jobs` flag). From PR #1302, `grain ci retrigger` re-runs the PR head's failed Actions jobs **without pushing a commit**. Prefer it over an empty commit after a flake or runner outage, because an empty commit moves the head. If a check is already red on `origin/main` before your branch touches it, merge `origin/main` and report the breakage rather than weakening the check.

## §4. Runs that need a person: `ask_question`, relayed answers, liveness and wakes

### What changed
- **`ask_question` mandate** (`81908b92`, PR #1218): every prompt carries `model.PersonActionInstruction`. A run whose outcome needs a person to act ends with `ask_question`, whose `summary` names the action. `comment_on_issue` takes an optional `summary` shown in the Inbox and task list.
- **Relayed answers** (`3b87db80`, PR #1217): `POST /api/tasks/{id}/comments` takes `relay: true` (`grain task message <id> --relay` in a sandbox). It is allowed only for a console session attributed on behalf of a verified person. The comment counts as that person's reply and wakes an `awaiting_reply` task.
- **Liveness** (`f0d02bc6`, PR #1396): `model.BlockerHoldOf` names blockers that only a person can close (failed out, never approved, asking, paused, deferred with no wake, awaiting Submit). Their dependents show in the Inbox, `grain task list --stalled` and `list_grain_tasks(stalled)`.
- **Wakes:** a park's own depends-on links are dropped on resume (PR #1394). `resume_later` CI waits whose run ended in an error wake, with a `-ci-wake-backstop` (default 6h) (PR #1212). Message holds wake on every post (PR #1308). Report-only sub-tasks close when they answer (PR #1216).
- **Handover and the rail:** handover prompts point at `grain handover write` (PR #1383). Grain's own notices don't age a handover (PR #1382). Resumed durable runs get brief and context upkeep (PR #1334). Brief, compact and rollover are held to the cross-task rail (`754e38d7`, PR #1276). ## §7. GitHub Actions CI for agents

### What changed
- **`grain ci retrigger` / `run-job` on Actions** (`a3005561`, PR #1302): on a `ci_mode: github` repository, both re-run the Actions runs at the head of the task's own PR through the daemon's forge connection, with no commit pushed. `retrigger` calls `.../runs/{id}/rerun-failed-jobs` (or `.../rerun` with `--all`), and `run-job <job>` calls `.../jobs/{id}/rerun`. `--jobs` accepts one job, exactly the failed jobs, or all jobs. The host's `grain ci retrigger gha:…` prints `grain ci wait <gha id>`.
- **One repair when `main`'s gating workflow goes red** (`5c3ef7bc`, PR #1291): `githubbaserepair.go` treats a red default-branch run of `tests.yml`/`test.yml`/`ci.yml` the way Stage 1 repairs treat `nightly.yml`, reusing `stage1repair.go`'s filing. The workflow-run poll remembers each repo's default branch for an hour.
- **Runner DNS outages are waited out**, not spent as PR repairs (PR #1262). The CI job API token is exported in every step, host sandboxes included (PR #1319). Trusted Grain CI jobs are registered as Go build-cache writers (PR #1261), and sandboxes can no longer write the shared Go build cache (PR #1230). `grain health` skips dropped workflow crons covered by grain-CI schedules (PR #1348). Live test steps skip when their CLI never installed (PR #1214).

### What CI proves
- `pkg/ui` rerun tests against a fake forge, sandbox CLI spec, `TestGitHubWorkflowRunScheduleLoopOverSim`, base-repair unit tests, pkgcache isolation tests.

### What is NOT proved
1. **Retrigger from a sandbox** over the GitHub simulator: a task's PR with two failed jobs. `grain ci retrigger` re-runs both without moving the head SHA (approvals and reviews are kept). `--all` re-runs every job. `run-job <name>` re-runs one. A `--jobs` selection that is neither one job, the failed set nor all is refused with the documented message. A task cannot re-run another task's PR.
2. **Host retrigger:** `grain ci retrigger gha:<owner>:<name>:<run>` from the host prints the `grain ci wait <id>` line, and that command waits.
3. **Base repair:** turn the simulator's `tests.yml` run on `main` red. Exactly one repair task is filed, a second red run does not file a duplicate while it is open, and green closes the loop. An unchanged poll costs only 304s.
4. **DNS outage:** fake CI fails a PR's jobs at setup with `Temporary failure resolving`. No PR repair is filed, and the task waits and re-runs when the outage clears.
5. **Cache isolation:** a sandbox run that tries to write the shared Go build cache fails or is redirected. A trusted Grain CI job writes it, and a later sandbox reads the hit.

1. Real daemon with `-github-sim` in `ci_mode: github`, a fake agent that runs `grain ci retrigger`, and fake CI for item 4. Helpers in `docs/test-runs/2026-11-13-actions-ci-for-agents/`.
