# Test plan: the 2026-09-06 batch

What landed on `main` between `fbba060c` (where
`docs/test-plans/2026-09-05.md` stopped) and `9b722c79`, and what it
would take to believe it works. Ninety-four pull requests: `#829`
through `#930`, plus `#804` (`grain/task-34`, an older branch merged
late) and three `claude/` branches somebody drove by hand. The last ten
were merged in the small hours of 2026-09-07; they are the same
day's work and are covered here, the same way yesterday's plan covered
the tail of its own day.

This is a plan, not a report: nothing below has been run by hand for this
document. Each section says what the change already proves in CI, what it
does not, and what a person would have to do to find out. Where the
answer is "write a test", the task is named at the end of the section;
where it is "somebody has to try it on a real machine", the steps are
written out so the run is repeatable and its result means something.

Two things make this batch read differently from the last one. The first
is that eight of its pull requests *are* the last plan's own follow-up
work -- `grain/task-118`, `-119`, `-121`, `-122`, `-125`, `-126`, `-127`
and `-129` are the tasks that plan filed, and the sections below credit
them as that rather than claiming their coverage as new. The second is that the day's largest new
thing, grain's own CI, shipped as a library with no caller: that is
section 1, and it is the one place where the honest answer to "what would
a hand run look like" is "there is nothing yet to run by hand".

## How to read the coverage claims

The six places tests run are the same six yesterday's plan tabulated, and
its table still holds, with three changes this batch made to it:

* `tests.yml`'s `go` job no longer runs `npm test`. `#848` moved the
  frontend suite off that job's critical path into a job of its own, so
  a red frontend suite is now a separate check rather than a Go job that
  never got to `go test`. It still runs on every pull request.
* there is a new nightly, `.github/workflows/nightly.yml` (`#848`, with
  the review prompt in `docs/nightly-test-review.md`). It
  runs the soak, the load test and repeated suites -- everything that is
  more rigorous for being slower -- at 02:11 UTC, blocks nothing, and is
  *expected* to be red sometimes. Nothing below counts it as coverage
  until somebody has read a week of it.
* there is a second new nightly, `.github/workflows/live-secrets-repo.yml`
  (`#863`), which is the only check in this repository that pushes to a
  real GitHub remote. It is the last plan's section 3 gap, closed.

The three standing caveats from that plan are unchanged and every gap
below is still one of them: a green `go` job is not coverage of a suite
that skipped itself; nothing in CI deploys grain the way an operator
deploys it; and nothing in CI touches real GitHub except through
`pkg/github/githubsim` and the two live nightlies.

## 1. grain's own CI

Shipped: `#927` `pkg/ci` -- a workflow format, a planner, an engine, a
run store and a service -- plus the `grain-ci` capability
(`pkg/capability/grainci`), the four `/api/ci/runs` routes, and this
repository's own `.grain/workflows/tests.yml`. That is the whole of it:
one pull request, and nothing else in the batch touches the package.

**Proved already.** For a package this new the unit coverage is good and
unusually pointed. `pkg/ci/workflow_test.go` proves the parser accepts
GitHub's spelling and *refuses* what it does not implement rather than
ignoring it -- which is the whole safety argument for looking like
Actions. `plan_test.go` covers branch and event matching, `needs` across
files, and the fingerprint that decides when two requests are the same
work. `engine_test.go` is the substantial one: step order, first failure
stopping the rest, `continue-on-error`, `needs` skipping what cannot run,
concurrency up to the limit, a sandbox that cannot be built, an engine
with no backend at all, cancellation, environment layering, and all four
cache behaviours. `service_test.go` covers the asynchronous start, the
de-duplication of an identical in-flight run, cancellation and run-store
eviction. `pkg/ui/ci_test.go` drives the routes, including the two
refusals that matter (a repo `grain-ci` is not enabled for, and a
deployment with nothing wired). `tests/deploy/grain_workflows_test.go`
parses *this* repository's `.grain/workflows` with the parser that would
run it, so the file cannot drift into naming a make target the Makefile
dropped.

**Not proved.** All of it, in the sense that matters:

* **nothing constructs a `ci.Service` or a `ci.Engine` outside tests.**
  `grep` for either in `cmd/` finds nothing, `ui.Server.CI` is never
  assigned, and no type outside `pkg/ci`'s own test files implements
  `ci.Sandboxes`. `pkg/ci/sandbox.go` names `cmd/grain` as where the
  adapter between `orchestrator.Sandboxes` and `ci.Sandboxes` lives, and
  that adapter does not exist yet. So the API 404s on every deployment,
  the capability grants a thing that cannot happen, and the engine has
  never acquired a machine that boots. Every green test above runs
  against a fake backend whose `Exec` returns what the test wrote.
* the checkout is the part of the design that has never been tried. A
  job's sandbox is supposed to arrive with the commit already checked
  out, which is precisely what lets the format have no `uses:` -- and
  what a real backend would have to do, through the git proxy, with
  whatever credential the checkout needs and the job must not keep.
* **the security property is asserted by absence.** "A CI job's sandbox
  is given no capability material, no minted key and no GitHub
  credential" is the argument that makes a workflow file safe for any
  agent to rewrite. Today it is true because there is no code that could
  pass one. The moment the adapter above exists it becomes a property a
  test has to hold, and no test holds it.
* `DefaultMaxRunTime` (two hours) is the backstop for a backend that has
  stopped answering in a way no job notices. Nothing exercises it.
* the workflow file itself claims a sandbox reaches no network and runs
  `go test` against the guest image's module cache. Nobody has run it, so
  "a dependency added since that image was built fails here and passes on
  GitHub" is a prediction rather than an observation.

**Hand run.** Not yet possible, and saying so is the finding. Once the
adapter and the wiring exist, the run is: turn `grain-ci` on for one task
in the picker, push a branch, `POST /api/ci/runs` with that repo and
branch, watch two sandboxes appear in the sandbox list under names that
say which job they are, and confirm the two jobs' verdicts match what
`.github/workflows/tests.yml` said about the same commit. Then do it
again with `curl` inside a step, and with a step that reads
`~/.grain/secrets`, and confirm both find nothing.

Filed: the wiring plus an end-to-end test of one real job, and, on top of
it, a test that pins the no-credential property.

## 6. Settings resets: the journal, the pull request, the pane

Shipped: `#891` the journal saying what a merged settings file reset and
to what; `#897` the same said on the merged pull request, capped, with
the state repo's README saying where it lands; `#900` the decision about
the third surface, written down in
`docs/state-pane-reset-notice.md`; `#908` that third surface built -- an
undelivered reset carried on the State pane, with a marker on the rail,
pinned on every surface it crosses; `#861` the check's own warning for a
column a file omits.

**Proved already.** More than the feature's newness suggests. The seam is
honest -- `reportResets` writes the journal line and cannot fail,
`announceResets` hands the same values to whatever the deployment can
reach -- and both halves are covered:
`pkg/staterepo/resets_test.go`, `undelivered_test.go` and
`undelivered_internal_test.go` on the reading side;
`cmd/grain/stateresets_test.go` on the comment, including a refused
comment reported as a failure, a comment that stays within what GitHub
will accept, values quoted rather than rendered, and the three cases that
post nothing at all; and `state_reset_notice_test.go` on the pane,
including that only an *undelivered* reset reaches the pane and the rail
and that an ordinary merge leaves no notice.

**Not proved.** Every one of those runs against a fake GitHub, and the
whole point of this feature is a person seeing it. Nobody has watched a
real deployment's credential post one of these on a real merged pull
request; nobody has had GitHub refuse one for a real reason (a locked
conversation, a rate limit, a repository the credential lost access to)
rather than because a stub was told to say no; and nobody has dismissed
the pane notice and then wanted it back. The gap is not the logic. It is
that the failure this feature exists for has only ever been simulated.

**Hand run.** On a throwaway deployment with a state repository on real
GitHub:

1. Open a pull request against the settings file that removes one column
   from one table. Expected: `grain state check` warns on the pull
   request, naming the column and the default it would land on.
2. Merge it. Expected: the journal line names the value that was lost,
   not just the default; a comment appears on the merged pull request
   saying the same; the State pane says nothing, because the comment was
   delivered.
3. Revoke or narrow the credential the deployment comments with, then
   merge a second such change. Expected: the journal still records it,
   the comment fails, and the State pane carries the notice with a marker
   on the rail. Dismiss it and confirm it stays dismissed across a
   reload and a daemon restart.
4. Merge a settings file that omits a dozen columns. Expected: one
   comment, capped, still readable.

Filed: this pass. Steps 3 and 4 are the ones worth insisting on. Done, in
`docs/hand-runs/2026-09-07-settings-reset-notice.md` -- all four steps
against a real daemon and a real state repository, with real GitHub
refusing in step 3 and a stand-in accepting where GitHub had to say yes,
since the sandbox had no credential that may write there. What is still
owed is a comment GitHub actually accepted, and the two 403 wordings
`IsPermissionDenied` keys on.

## 8. The merge queue's repairs and escalations

Shipped: `#876` green pull requests let past a conflicted head, with the
docs and e2e expectations updated; `#886` a run that never started
escalated rather than repaired; `#898` the one startup failure a pull
request's own branch caused, repaired, with the escalation's claim kept
inside what it checked; `#909` repairs told to fix breakage they did not
cause; `#917` a repaired head given one more refresh before escalating;
`#925` selfrepair's Confirm answered only once it is provably waiting.
And, since every one of those is a decision made from what GitHub says
about a check run: `#858` a run that failed before any job of it started,
reported rather than shrugged at; `#920` what a run with no steps under
its jobs actually means; `#905` grain's own rendered state-check workflow
probed where Actions work, and what that probe settled before it was
removed again.

**Proved already.** `pkg/orchestrator/mergequeue_test.go` and
`mergequeue_refresh_test.go`, plus `tests/e2e/mergequeue_conflict_test.go`,
`mergequeue_more_test.go` and `mergequeue_refresh_test.go` -- the e2e
suite drives these against `githubsim`'s real bare repository, so the git
half of "conflicted head" is real even though the API half is simulated.
`docs/merge-queue-staleness.md` was updated in step with `#876` and
`#917`, which is the thing that most often rots.

**Not proved.** The distinction this batch turns on -- did this run fail
because of the head it was merged onto, because of its own branch, or
because it never started -- is read off CI's own reporting, and CI's own
reporting is the simulator's. A real GitHub check run that is queued, or
cancelled, or reported by an App that stopped answering, is a shape no
test has produced. The escalation path in particular now has three
branches and a "one more refresh" counter, and the counter has never met
a real repository where the refresh takes minutes.

**Hand run.** On this repository, deliberately: open two pull requests
where the second conflicts with the first, let the queue merge the first,
and watch what the second is told; push a branch whose own build is
broken and confirm it is escalated rather than repaired round and round;
cancel a check run by hand mid-queue and confirm the "never started"
branch fires. All three are observable on `bwsalmon/grain` itself,
which is the only real repository this deployment's queue runs against.

Filed: this pass. Partly done, in
`docs/hand-runs/2026-09-07-merge-queue.md`: grain's own decision in all
three scenarios was driven and read, and the check-run shapes were read
off real GitHub rather than off the simulator -- which turned the third
scenario's expectation around, since a cancelled check is neither a
failure nor a run that never started, and a head carrying one merged.
That last part was filed as a decision and answered on 2026-09-08: it no
longer merges, it holds as `PENDING` and reaches a person at the stall
deadline. The hand run's section 3 carries both readings. What still
needs a credential is listed there.

## 10. How a run ends

Shipped: `#887` `awaiting_ack` -- the post-run state for a run whose whole
product is a comment, and for auto-merge with nothing to merge -- pinned
in the store's derivation, in three isolation tests, and where the
vocabulary is written by hand; `#888` a provider capacity refusal told
apart from a quota one, with the capacity ending covered and written
down; `#904` a dropped `agy` conversation resumed rather than failing the
run, with the retry given its config back; `#913` a usage-limit pause
scoped to the framework whose credential hit it, said in `grain pause`
and `/api/config`.

**Proved already.** `pkg/model/state_test.go` holds the three arms of
`awaiting_ack` (it is reached by a comment-only finish, only
acknowledging leaves it, and the transition names the completion
moment), `tests/e2e/finish_paths_test.go` drives a comment-only run to it
end to end, and the UI carries it through `ui/src/state.js`, `board.js`
and `InboxPage.jsx` with tests on each. Capacity has a test per framework
(`pkg/agent/claude`, `codex`, `antigravity`) plus `pkg/agent/capacity_test.go`,
`pkg/dispatch/capacity_test.go` and `pkg/orchestrator/capacity_test.go`.
Resume has `pkg/agent/antigravity/resume_test.go` and the gated
`tests/e2e/live_resume_test.go`, which needs a real key.

**Not proved.** Capacity is the weak one, and unavoidably so. The markers
are well chosen -- `overloaded_error` and `api error: 529` are tokens a
provider writes and a repository does not, which is the same care
`usagelimit.go` takes about a bare `429` -- but they are matched against
text in somebody else's product, and no test anywhere has seen that text
arrive for real. `live-agent.yml` exercises a real credential nightly and
never a refused one. So when a provider rewords its refusal, every test
here still passes, the phrase matches nothing, and the run is read as an
ordinary failure: five of those retire a task that was never wrong. The
failure is silent by construction, which is what makes it worth
something more than another fixture.

Filed: not a test but an instrument -- when a run fails and matches
neither the capacity markers nor the usage-limit ones, keep the tail of
what the provider actually said, somewhere an operator can read a week of
them. That is the only way this repository will ever find out that a
marker has stopped matching.

## 13. granule and the sandbox guest

Shipped: `#852` the kontur fork layer tested against a fake kontur
binary; `#860` how a granule ends -- one Result, and a heartbeat that
stops at it; `#872` the record stream when stdout fails and at close;
`#910` granule's argument refusal pinned; `#864` the provisioning tar's

published from cache when its inputs are unchanged, the kontur base image

**Proved already.** `pkg/granule/guest_test.go`,
`run_internal_test.go` and `cmd/granule/main_test.go` cover the fork
layer, the ending and the refusals without needing a VM; the real-VM jobs
still cover a booted guest.

**Not proved.** The guest cache is the risk, and it is better guarded
than it first looks: `tests/deploy/deploy_test.go` runs
`guest-inputs.sh` and fails when a script under `scripts/kontur` reads a
path no entry of that list covers, so the obvious way to leave an input
out is caught in the pull request that leaves it out. What that check
cannot see is an input that is not a path in this repository -- an
upstream package version, a base image tag resolved at build time, a
default that changed in a tool the provision step shells out to. If any
of those moves, the hash does not, and CI republishes a stale guest while
going *faster*, which is the failure mode nobody investigates. Nothing
anywhere compares a cache-hit guest with a freshly built one.

Filed: a periodic (nightly) guest build that ignores the cache and
compares what it produces with what the cache would have served.
