## Branch situation & how follow-up tasks should handle it

Releases are cut from `main` by the continuous train (`.grain/settings.yml`, `scripts/release.conf`), and `v3.13.0` is `latest`. A `fix:` that a walkthrough lands on `main` ships with the next rc and needs **no backport task**. The exception is an operator asking for a patch to `release/v3.5.1` or `release/v3.1.1`: then fix `main` first and propose a backport with `writes: [{repo: "ai-on-gke/grain", base: "release/vX.Y.Z"}]` and `Backported-from: <sha>`.

Every follow-up walkthrough task filed from this plan targets `main` (`repo: "ai-on-gke/grain"`, `branch: "main"`) and depends on [Task #6587](/tasks/6587), so `docs/test-plans/2026-11-17.md` is on `main` when each walkthrough starts. Each proposal asks for unattended `auto_merge: true` once CI is green. Whoever approves the proposal decides whether to grant auto-merge on `main`.

The gate is **GitHub Actions**: `Tests` in `.github/workflows/tests.yml` (including `ui-ng e2e`), `plc-tests.yml` when `grain-plc/` is touched, `cla/google`, the workflow/hygiene scans, and the every-PR gating review. Inside a sandbox:
- Open the PR with `grain pr open` and wait on checks with `grain ci wait` (`timeout: 600000`, no `--jobs` flag).
- Do not rely on the MCP `pull_request_status`, `base_branch_status` or `wait_for_checks` tools, and never chain `grain pr status` ahead of `grain ci wait`.
- If a check is already red on `origin/main`, merge `origin/main` and report the unrelated base breakage rather than weakening the check.

## §3. Autonomous Goal Mode

### What changed
- **PR #1690 (`a7b578cd3`):**
  - `Task` gains `GoalModeConfig` (`goalMode: {enabled, maxPasses, wallClockMinutes, mockMissingSecrets, …}`), `GoalAssumption`, `GoalDeliverable`, `GoalScorecard` (`pkg/model/goal_mode.go`).
  - Enabling or disabling `goalMode` on `POST /api/tasks` / `PATCH /api/tasks/{id}` needs `tasks:admin`; an agent cannot enable it (or `mockMissingSecrets`) for a child when its own task does not have it (`pkg/ui/agent_api_gate.go`).
  - In a goal run the MCP server hides `ask_question` and `request_access` (and `request_secret` with `mockMissingSecrets`), and adds `record_assumption` and `complete_goal` (`pkg/mcp/goal_tools.go`); `complete_goal` requires `verified: true` on every deliverable and is wired into stop-rule closing checks and the Claude/Antigravity hook policies.
  - The orchestrator runs bounded multi-pass verification (`maxPasses`, `wallClockMinutes`) over assumptions, scorecards, git changes and test evidence, and writes JSONL pass metrics (`pkg/orchestrator/goal_mode.go`, `goal_perf.go`). `finish.go` (trust boundary) changed.
  - `/next/`: Supervised vs Autonomous Goal posture on New task, `<g-task-goal-card>` (scorecard, assumptions, Revise, Switch to Supervised) on Task detail and Inbox, goal badges on Tasks / Agents / Workstreams.

### What CI proves
- `pkg/mcp/goal_tools_test.go` (tool sets per posture), `pkg/ui/goal_mode_access_internal_test.go` (escalation refusals), orchestrator goal-mode unit tests, `ui-ng/e2e/next-goal-mode.spec.ts` over demo data.

### What is NOT proved
1. **A real goal run:** a fake agent in a real daemon sees no `ask_question` / `request_access` in `tools/list`, calls `record_assumption` twice and `complete_goal` with one unverified deliverable (refused) then all verified (accepted). The task closes through the stop rule with the scorecard on `GET /api/tasks/{id}`.
2. **Bounds:** `maxPasses` reached and `wallClockMinutes` exceeded each end the run with a clear reason, not a silent retry loop; the JSONL pass metrics land where documented and are bounded in size.
3. **Fallbacks when a tool is hidden:** an agent that calls `ask_question` anyway (stale tool list, CLI `grain ask`) is refused, not parked in `awaiting_reply`. With `mockMissingSecrets`, `request_secret` is hidden and the run does not hang waiting for a secret.
4. **Switch to Supervised** mid-run and **Revise** from the Inbox: the next dispatch has `ask_question` again; the goal card and badges update on `/next/tasks/<id>`, `/next/inbox`, `/next/agents`, `/next/workstreams` without reload.
5. **Authority on a live daemon:** a `tasks:write` person, an agent token, and a `propose_task` from a supervised parent are all refused `goalMode`; a goal parent's child may inherit it only as the gate allows. Check `grain create` and the CLI have the same rule.
6. **Frameworks:** the hook policy wiring for Claude and Antigravity (and Codex, which the PR does not name) — does `complete_goal` gating work on each framework the deployment can dispatch?

### Walkthrough & test procedures
1. Real daemon over SQLite and PostgreSQL with the fake-agent harness; script the agent to call the MCP tools in order (`docs/test-runs/2026-11-15-resume-later-release/` shows a scripted agent calling MCP tools).

## §4. Built-in gate observations (shadow only)

### What changed
- **PR #1739 (`6bd221161`):** new `pkg/gates` with a fixed, versioned registry of pure evaluators `delivery(report/current_v1)` and `acknowledgment(explicit_receipt)`. Collection is **off by default**; `GRAIN_GATE_OBSERVATION_TASKS=<ids>` (≤ 32 unique ids; invalid or too many disables it with a startup log reason) turns it on for those tasks. Ordinary permission-filtered task reads collect bounded evidence and persist shadow observations, retry backoff and comparison history; nothing writes lifecycle tables, waits, dispatch signals or events. `/next/` task detail shows the observations labelled observation-only. Bounds: 72 h / 1,024 samples per task, 32 current caches, 32,768 samples globally. Operator steps: `docs/gate-observations.md`.
- **PR #1803 (`07e43408c`):** stale failures no longer replace newer accepted observations; failures coalesce during backoff; indexed history pruning; bounded SQLite lock acquisition on a leased connection; review notes in `docs/gate-observation-review.md`.

### What CI proves
- `pkg/gates` evaluator tests; `pkg/model/gateobservationtest` shared SQLite/Postgres suites (restart, eviction, retention at capacity, concurrent retries, index upgrade); legacy noninterference snapshots; `ui-ng/e2e/next-gate-observations.spec.js`.

### What is NOT proved
1. **The documented rollout on a real daemon:** start with `GRAIN_GATE_OBSERVATION_TASKS` naming an analysis task awaiting receipt, one acknowledged by a verified person, and a code task (expected "unknown, not applicable"). Each `/next/tasks/<id>` shows the panel; the other tasks show none. Bad values (33 ids, a duplicate, `abc`) disable it with the logged reason.
2. **Noninterference under real dispatch:** with collection on, the allowlisted tasks' state transitions, waits, Inbox items and notifications are identical to a run with it off (diff `GET /api/tasks/{id}?fields=full` and the event stream).
3. **Restart and disable:** observations survive a daemon restart; removing the variable hides the panel and leaves the tables alone; re-enabling resumes generations without key collisions (the PR #1739 eviction fix).
4. **Authorization and redaction:** a person who cannot read a task cannot read its observations through `GET /api/tasks/{id}` or the summaries endpoint; error text is the safe form.
5. **Read cost:** collection runs on ordinary reads. Measure `/next/tasks` and `GET /api/tasks/summaries` latency with 32 allowlisted tasks open in several tabs, on SQLite (the leased-connection lock) and PostgreSQL.

### Walkthrough & test procedures
1. Real daemon over SQLite and PostgreSQL, following `docs/gate-observations.md` exactly; record where the doc is wrong or unclear and fix it.
2. Items 2–3 with the fake-agent harness and a scripted human acknowledgment.
3. Item 4 with a repo-scoped role; item 5 with a small load script under `docs/test-runs/2026-11-17-gate-observations/`.

## §5. PR feedback wakes waiting tasks; review context and merge-queue fixes

### What changed
- **PR #1713 (`c1a0b5a5d`):** a task parked on `resume_later` (CI) or an ordinary `ask_question` gets **one** dispatch for new trusted PR conversation comments, submitted reviews and inline comments. Source identities and quoted feedback persist atomically (schema **152**, runtime feedback receipts) and are shared with inline-thread polling; the original CI suspension, head evidence and pending question are kept. Self-trigger loops are suppressed by App identity, delegated-author signatures, draft/relayed review provenance and collaborator checks. Feedback received during a run stays pending until shown; truncated addenda wait for the full prompt. Pause/stop, closed tasks, permission and review-decision holds, dependencies and future scheduling are respected.
- **PR #1548 (`d0b729f94`):** `grain pr threads` in a review sandbox falls back to the reviewed PR on the upstream repository (fork deployments); parallel reviews pointed at `grain pr threads`; queued reviews refreshed with the cycle's GitHub client; in-place reviews no longer told they pushed nothing.
- **PR #1465 (`cc2916260`):** the merge queue splits an unfixable red into the branch's own and the declared-unfixable checks even while a gating review holds auto-merge; re-reviews stay incremental after a carried base merge; a git connection's merge credential shows on its list route.

### What CI proves
- `TestPRFeedback*` (redelivery, coalescing, truncation, protected controls, link replacement), GitHub/orchestrator/dispatch/model/migration suites, review-context and merge-queue regressions; the 2026-11-14 review-context and 2026-11-13 merge-and-reviews reports.

### What is NOT proved
1. **End to end with the GitHub sim and webhooks:** park a task on `resume_later(ci)`, post a trusted comment → exactly one dispatch whose prompt quotes it with author and link, the CI wait still in place after. Repeat for `ask_question` (the question stays pending), a submitted review, and an inline comment.
2. **Untrusted and self sources:** a non-collaborator comment, grain's own relayed review, a draft review and a comment signed as delegated author do **not** wake the task.
3. **Interaction with the 2026-11-15 `resume_later` release work** (PR #1590) and goal mode (§3): a goal-mode task with no `ask_question` parked on CI; a task resting on `resume_later(message: true)` gets one dispatch, not two.
4. **Webhook redelivery and daemon restart** between receipt and dispatch on SQLite and PostgreSQL: no second delivery, no lost one.
5. **Holds:** a paused task, a task with an open dependency and a `not_before` in the future are not woken; they show the feedback once they run.
6. **Fork deployment** (`RepoConfig.UpstreamRepo`): `grain pr threads` inside a review sandbox shows the upstream PR's threads; reply/resolve stay scoped to the task's own PR.

### Walkthrough & test procedures
1. Real daemon with `docs/test-runs/2026-11-14-review-context/`'s GitHub sim harness over SQLite and PostgreSQL. Items 1–5 each as a scripted case, with the sim's webhook replay used for item 4.
