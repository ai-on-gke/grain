# Test plan: the 2026-09-07 batch

What landed on `main` between `9b722c79` (where
`docs/test-plans/2026-09-06.md` stopped) and `e8f98d95`, the last merge
dated 2026-09-07, and what it would take to believe it works. A hundred
and thirty-seven pull requests, `#931` through `#1076`, filed as
`grain/task-83` through `grain/task-428`.

This is a plan, not a report: nothing below has been run by hand for this
document. Each section says what the change already proves in CI, what it
does not, and what a person would have to do to find out. Where the
answer is "write a test", the task is named at the end of the section;
where it is "somebody has to try it on a real machine", the steps are
written out so the run is repeatable and its result means something.

Two boundaries are worth stating, because both are different from the
last two plans'.

The first is where this batch stops. The previous two plans each swept up
the small hours of the following morning as "the same day's work". This
one does not. The merges of 2026-09-08's first hour are mostly the
previous day's queue draining, but they are interleaved with that day's
own new things -- a director, a chat turn inside one run, a composition
layer that decides what a firing files -- which were still landing while
this was written. Splitting those by the clock rather than by the subject
would have put half of each feature in a different file, so everything
after 23:25 UTC on 2026-09-07 is left to the next plan.

The second is where this document was written. `rel.latest`, the release
train, was cut at `327a0c80` (`#1063`, 20:54), so the last dozen pull
requests of the batch -- `#1064` through `#1076`, the framework retry
measurements and the target-repo work of the evening -- are on `main` and
not on the branch this file lands on. Nothing below claims a section is
released; where a change is main-only it says so.

## How to read the coverage claims

The six places tests run are the ones the last two plans tabulated. Five
changes this batch made to that table:

* there is a third live nightly, `.github/workflows/live-frameworks.yml`
  (`#1003`, 06:19 UTC), which runs claude's and codex's live suites
  against real CLIs and real credentials. It is the first check in this
  repository that spends provider credit on a schedule, and like the
  other two it blocks nothing.
* `nightly.yml` gained `guest-cache-drift` (`#986`), which builds the
  sandbox guest with the cache ignored and diffs it against what the
  cache would have served -- the 2026-09-06 plan's section 13 gap,
  closed -- and learned to put the drifted values in the annotation
  rather than only their count (`#1050`).
* the nightly's repeated e2e run is now three passes over three stores
  rather than three over one (`#958`), which is what makes a repeat
  capable of finding cross-run state rather than only flakes.
* every merge to `main` now gets a concurrency group of its own
  (`#957`), so two merges no longer cancel each other's checks.
* and grain's own CI can now run this repository's `.grain/workflows`
  for real (section 1). It is not one of the six places: nothing runs
  it without a person asking.

The three standing caveats are unchanged and every gap below is still
one of them: a green `go` job is not coverage of a suite that skipped
itself; nothing in CI deploys grain the way an operator deploys it; and
nothing in CI touches real GitHub except through `pkg/github/githubsim`
and the live nightlies.

## 1. grain CI, wired to real machines -- and holding the merge

Shipped, and it is the batch's largest thing by some way: `#961` the
adapter the last plan said did not exist (`cmd/grain/ci.go`, plus
`gitproxy.ReadScopes` for the scope a job holds); `#971` a step's script
over `orchestrator.SandboxShell` rather than over the `run_command`
tool, because `run_command`'s ten-minute clamp and output cap are both
fatal to a CI job; `#973` the `grain-ci` capability, `model.CI` and the
schema behind them; `#976`/`#1025` a job cache and an operator's view of
it; `#979` a repository's declared workflows read from the CLI; `#975`
`grain ci` and the CI tab of the System pane; `#994` a deliberately
hostile workflow run through the real adapter; `#1017` a shared gate, so
CI jobs and agent runs draw on one pool and a CI job's sandbox is one the
health pane counts; `#1020` an empty plan whose run key still tells
branches apart; `#1021` the verdict holding the merge queue; `#1022` a
run store that outlives the process; `#1026` a job's sandbox named
short enough to be a kontur VM; `#1016` which commit a run was for;
`#1055` a curated environment for a host-backend step rather than the
daemon's own.

**Proved already.** More than the last plan could say, and in the right
places. `pkg/orchestrator/ci_test.go` holds the merge policy in fourteen
tests, and holds it from both ends: a red run and a still-going run hold
the queue, a run with nothing to run merges, a verdict about another
commit holds nothing, a cancelled run holds nothing, and a red run on a
task without the capability holds nothing. `cmd/grain/ci_test.go` covers
the adapter itself -- checkout at the commit under test, checkout of the
branch when there is no commit, the scope dropped and the sandbox
destroyed on release, a failed checkout releasing the sandbox it failed
in, and a backend failure that leaves no scope behind. `ci_shell_test.go`
covers the shell preference and its fallback; `ci_capacity_test.go` that
the engine is gated on the pool as it stands and that a CI sandbox is one
the health pane counts; `pkg/ci/gate_test.go` that no more permits are
handed out than the limit, across runs; `runstore_stored_test.go` that a
stored run outlives its process and an interrupted one is marked rather
than lost. `pkg/ci/service_test.go` now exercises `MaxRunTime` too, which
the last plan listed as untouched.

**Not proved -- and this is the section's finding.** The two tests that
would settle it exist and nothing runs them.
`cmd/grain/ci_e2e_test.go` runs this repository's own
`.grain/workflows/tests.yml` to a verdict on a real backend, and
`cmd/grain/ci_hostile_test.go` runs a hostile workflow and asserts on
what its steps found -- the no-credential property the whole design rests
on, held from inside the sandbox rather than read off the wiring. Both
are gated on `GRAIN_TEST_CI_E2E=host` or `=kontur`, and that variable is
set in no workflow in `.github/`: `grep` finds it in the README and in
those two files, nowhere else. So on every commit, the property is
asserted by two tests that skip.

Three more, smaller:

* **`-ci` defaults to on** (`cmd/grain/daemon.go`) and `-max-ci-jobs`
  defaults to 1, taken out of `-max-workers`. A deployment that upgrades
  into this build reserves a sandbox for a feature nobody has switched on
  per repository yet. Nothing outside a unit test has measured what that
  costs a busy pool.
* the verdict is reported nowhere GitHub can see it -- no commit status,
  no check run -- so a pull request held by grain CI looks, on GitHub,
  like a pull request nobody is merging. That is a deliberate decision
  (`pkg/orchestrator/ci.go` says so), and it has never been read by a
  person who did not already know it.
* the kontur arm of both live tests has, as far as this repository
  records, never been run at all. The host arm at least runs on somebody's
  laptop; a job in a VM is where the checkout, the shell and the
  "no network" premise are all different.

**Hand run.** Now possible, which it was not a day ago. On a deployment
with a real backend: turn `grain-ci` on for one repository; `grain ci run
-watch` that repository's branch and confirm two sandboxes appear under
names that say which job they are; check the verdict against what
`.github/workflows/tests.yml` concluded about the same commit (with
`GRAIN_TEST_GITHUB_TOKEN` set, `ci_e2e_test.go` does that comparison
itself, and two CIs disagreeing about one commit is the finding worth
looking for); push a commit that fails one job and read the failure in
both `grain ci show` and the CI tab; then open a pull request for a task
holding the capability and confirm the merge queue holds it while the run
is red and releases it when it is green. Finally, run it once with a
dependency added to `go.mod` since the guest image was built, which the
workflow file itself predicts will fail there and pass on GitHub.

Filed: the live suites run without a person asking, and a hand run of the
whole path on a real deployment.

Shipped: `#970` one declared field taken round the whole loop in
`tests/e2e` -- state repo, dispatch, agent, back into the store; `#1019`

**Proved already.** `tests/e2e/custom_field_loop_test.go`'s
`TestASetValuedCustomFieldGoesFromTheStateRepoThroughARunAndBackIntoIt`
is the test the last plan filed, and it is the honest version of it: the

prompt, and the run writes it back. `pkg/ui/bulk_edit_test.go` covers the

`ui/e2e/fields.spec.js` now has data to run against.

it copies the vocabulary back exactly, or paraphrases it into a value the
declaration does not allow -- is measured by nothing, and the dropped
value is noted in the proposal body rather than failing anything. That is
a measurement rather than a test, and the live nightlies are where it
would live.

Filed: nothing new. It is a leg on the framework-nightly reading in
section 4.

## 3. The memory capability, and the agent that writes into every prompt

Shipped: `#989` a system schedule grain seeds for itself, at 03:00 on the
deployment's clock, that dispatches the nightly memory agent; `#990` the
two reading tools beside `update_memory`, so a run that can find a note
stale can replace it; `#999` what the prompt says about it; `#1054` the
memory pane and its listings; `#1059` the agent's template pinned to
`NetworkNone`; `#1063` what a `repo-case` merge does with a memory's
author; `#1066` the long documents it keeps; `#1072` how it is told a
document a person wrote by hand is different (main only).

**Proved already.** Unusually well, for something this new.
`pkg/orchestrator/systemschedule_internal_test.go` holds the seeding
asymmetry that makes the design safe -- seeded once on a fresh
deployment, never written over the deployment's own answers, nothing
seeded without a state repository -- plus the filed task's shape (no
target, the state repo to read, no network) and the pass's place in the
cycle. `pkg/mcp/memory_tool_test.go` covers every refusal the tools make
(too long to carry, no summary, past its own limit, a summary too long
for every prompt) and both deletions-by-empty-text.
`pkg/model/memory_document_test.go` covers the round trip per scope,
names that can be typed back, and the index marking what a person wrote.

**Not proved.** That it has ever run. This is a standing job, seeded
automatically on any deployment with a state repository, that dispatches
an agent holding a GRANT capability at three in the morning and writes
prose that is then repeated in **every prompt this deployment issues**
until somebody replaces it. The blast radius is every later run, the
feedback loop is a person noticing a prompt has gone strange, and
nothing in CI dispatches it. Specifically unmeasured:

* what the agent actually writes on a real day of history, and whether it
  is worth carrying in every prompt;
* whether a note it writes appears in a later dispatch's prompt, and
  whether the document index is rendered only for a task holding the
  grant, which is what `orchestrator.resolveMemory` claims;
* what happens when it runs on a deployment whose day was uneventful --
  whether it writes nothing, or writes something to justify the run;
* and the 03:00 default against a deployment that is busy at 03:00.

**Hand run.** On a deployment with a state repository and a day of real
history: confirm the schedule row was seeded and is exported; edit its
cadence and confirm the next reconcile leaves the edit alone; disable it
and confirm nothing re-enables it; then fire it by hand and read what it
files, end to end -- the task's prompt, the transcript, and what lands in
the memory pane. Then dispatch two ordinary tasks, one holding the memory
grant and one not, and diff their prompts: exactly one should carry the
document index. Finally, take one of the notes it wrote, make it wrong by
changing the tree under it, and confirm a later run holding the grant can
find and replace it.

Filed: that hand run.

## 4. Frameworks: retry in place, and three resume probes

Shipped: `#942` all three frameworks retrying in place, said in the
README; `#941` the honest record that the antigravity resume probe has
measured nothing so far; `#1013` claude measuring what a resume it cannot
serve does; `#1015` codex's probe pinned to the step that runs without a
credential; `#1003` the live nightly both now have; `#1023` a surface
capture for codex and agy; `#968` codex and agy able to be sat in front
of, not only claude; `#987` keeping what a provider said when no refusal
marker matched, in a store `grain failures` reads; `#1064`, `#1070` and
`#1076` (main only) the claude and codex API-retry measurements, and the
decision not to bound either.

**Proved already.** `pkg/agent/refusal_test.go` covers the bounded,
UTF-8-safe, single-line tail an unmatched failure keeps, and that the
loose matcher still recognises the refusals grain already knows.
Each framework's `retry_test.go` and `resume_test.go` cover the state
machine without a provider. `live-frameworks.yml` runs the live suites
nightly, with the no-credential probes separated from the credentialed
run so a missing secret is a skip rather than a false green.

**Not proved.** Three things, and they are all the same shape:

* the nightly has fired at most twice. The last plan's finding about
  `nightly.yml` -- a check designed to be red sometimes and to block
  nothing becomes wallpaper unless somebody reads it -- applies with more
  force here, because this one costs money every night.
* the antigravity resume probe still measures nothing (`#941` records
  exactly that), so of the three frameworks grain dispatches, one has no
  live evidence that a resumed conversation carries anything.
* the decision *not* to bound the frameworks' own API retry
  (`#1070`, `#1076`) is a decision about what happens during an outage.
  It was reached by measuring a stub. What a real multi-minute provider
  outage does to a run's deadline -- and to the sandbox it is holding
  while it waits -- has not been observed.

**Hand run.** A week of `live-frameworks` read against
`docs/nightly-test-review.md`, extended with the two questions that
prompt does not ask: what each night cost in provider credit, and whether
the run that spends it is asserting anything a cheaper test could. Plus,
in the same sitting, the section 2 measurement: give a live run a
set-valued custom field and see whether the value it writes back is one
the declaration allows.

Filed: that reading.

## 5. The merge queue's account of a check it cannot read

Shipped: `#943` waiting for a failing job's log instead of guessing why
there is none; `#946` bounding the check-run reads to the jobs whose logs
are already opened; `#1002` saying why a repair has no log rather than
filing it with none; `#1014` offering "Retry merge" only on tasks still
on the queue; `#1049`/`#1060` the decision that a cancelled check holds a
pull request, written down and told to agents; `#1048` hedging the
`github-sandbox` recommendation on the App being set up; `#957` a
concurrency group per merge, which is what stops one merge cancelling
another's checks in the first place.

**Proved already.** `pkg/mcp/failing_job_logs_test.go` covers the whole
awkward middle -- a log not served yet, a run still going, a startup
failure and a job that never started (neither of which is waited out), a
run whose Actions runs all finished clean, and the failed steps added to
a run with no served log. `pkg/orchestrator/mergequeue_retry_test.go`
covers a retried head getting another repair round and a retried stalled
head getting a whole deadline. `docs/hand-runs/2026-09-07-merge-queue.md`
is the previous plan's hand run, done: conflicted head, broken branch,
cancelled check.

**Not proved.** All of it against real GitHub. Every path above is
exercised through `pkg/github/githubsim`, and the changes in this batch
are precisely about the shapes GitHub returns when it is being unhelpful
-- a check run whose log is not written yet, a job that never started, a
run cancelled by a concurrency group. `githubsim` returns those shapes
because somebody taught it to; whether they are the shapes the API
actually returns is a claim about a simulator. The concurrency-group
change (`#957`) is the sharpest case: it changes what GitHub does to
*grain's own* checks, and nothing outside GitHub can rehearse it.

Filed: nothing new. This is a leg on the standing GitHub identity and
credentials pass, which already exists and which this batch gives three
more things to look for.

## 6. Target repos: the list moving under work already filed

Shipped: `#1065` parking every task about to be dispatched into a repo
`Config.TargetRepos` no longer names; `#998` re-checking the list when a
reply un-parks a task; `#992` a task's own repo no longer offered to it
as a read-only repo; `#1071` the same question asked of the first "Add
repo" (main only); `#991` what a repo edit during a run does, now that it
is only the next run.

**Proved already.** `pkg/orchestrator/targetrepos_test.go` covers the
five cases that matter: narrowing parks queued work rather than
dispatching it, the park lifts when the repo goes back on the list, an
unrestricted deployment parks nothing, a task with no repo is untouched,
and the park is written once rather than every tick. The last is the one
that would otherwise fill a timeline with a comment a second.

**Not proved.** The race the change is about. `reconcileTargetRepos` is
described as "this boundary's last look", and its value is entirely in
what it does to work that is *already moving*: a task whose sandbox is
being built as the setting is saved, a schedule firing into the same
tick, a suite pass mid-plan. The tests drive the reconciler directly with
a store the test wrote; nothing narrows the list while a real dispatch is
in flight.

**Hand run.** On a deployment with two target repos and real work: queue
several tasks against the second repo, start one of them, and remove that
repo from Settings while its sandbox is coming up. Then read, in order:
what the running task did (it should finish -- the proxy authorizes
against its live task's own target), what the queued ones say (parked,
with `model.OffAllowlistAtDispatchComment`, once each), what the schedule
that fires into that repo does on its next tick, and what a reply on a
parked task does. Put the repo back and confirm every park lifts. Then do
the destructive half: try to remove a repo whose tasks are still in play
and confirm the refusal (`#906`, last batch) still stands in front of all
of this.

Filed: that hand run.

## 8. Upgrade: what it costs before the button, and what it holds

Shipped: `#939` saying what an upgrade will cost before the button is
pressed, and the queue hold behind it; `#945` the upgrade check no longer
asking a run about a log it cannot read; `#964` the binary copy streamed
rather than read whole; `#965` schema upgrade; `#933` progress and
output; `#1024` saying when the pinned sandbox image is not the one this
build expects; `#1051` the record that `pkg/upgrade`'s two millisecond
bounds are not the flake somebody suspected.

**Proved already.** `pkg/orchestrator/upgradehold_test.go` is the good
one: an upgrade holds the queue and the next startup lets it go; an
upgrade that does not restart releases its own hold; a deployment
somebody had already paused is not disturbed; a pause taken *during* the
upgrade survives the release; and the next startup leaves the upgrade
check's own pause alone. Those five are the whole of the "who un-pauses
what" question, which is where this has gone wrong before.

**Not proved.** The cost estimate against a real upgrade. The number
shown before the button is an estimate of a download and a restart on
this machine, and the only way to find out whether it is worth showing is
to press the button on a provisioned deployment and time it. That is the
existing upgrade hand run (`docs/test-runs/2026-09-06-upgrade-pipeline.md`
covers the last one), which this batch gives two more things to check:
the estimate against the actual, and the pinned-image mismatch banner
(`#1024`) on a deployment whose image really is behind.

Filed: nothing new; two legs on the standing upgrade pass, which the last
plan already downgraded rather than closed.

## 13. Proxies, the store, and single facts

Shipped: `#1027` the Claude proxy reachable from inside a real guest,
then `#1028` all three; `#978` `credcheck` and the claude proxy's
capability; `#1011` the store at `synchronous=NORMAL`; `#988`/`#1046` an
Apache 2.0 licence and a NOTICE; `#952`/`#1007` `ghcr-prune` telling a
rate-limited prune from one whose token cannot delete, and saying what to

test; `#937` the sandbox directory given to main's new `BuildPrompt`

**Proved already.** `TestTheModelProxiesAreReachableFromInsideARealGuest`
runs in the `real KVM sandboxes` job on every pull request, which makes
the proxies one of the few things here proved on a real machine
automatically. `pkg/model/sqlite/open_test.go` checks the pragmas on
three pooled connections rather than on the first, which is the failure
mode that would otherwise be invisible. `cmd/ghcr-prune`'s suites cover
the plan and both refusals.

**Not proved.** What `synchronous=NORMAL` actually costs on a hard stop.
The reasoning in `sqlite.go` is careful and almost certainly right --
NORMAL cannot corrupt a WAL database, and it weakens neither the write
lock nor the isolation -- but the thing it does do is lose the last
commits when the machine dies, and "the last commits" of this store are
task states, observations and timeline entries that the state repository
export is *not* a backup of at that granularity. Nobody has measured the
window. It is one test: write continuously, `kill -9`, reopen, and count
what is missing.

Filed: that measurement.

## 14. What the suites themselves cost

**Proved already.** Each of these is a change to how tests run, so its
evidence is the numbers written where they were measured, and this batch
kept that habit.

**Not proved.** The same standing gap, now larger: six workflows in this
repository run on a schedule -- three live nightlies (`live-agent`,
`live-secrets-repo`, `live-frameworks`), a GCP smoke, the five-job
`nightly`, and the weekly package prune -- and all but the last are
designed to be red sometimes and to block nothing. The total that has
been read by a person is one night of one of them (`#985`, and `#1045`
saying why that reading was premature). The risk is not that any one of
them is wrong; it is that five schedules nobody reads cost money and
produce a green tick that means nothing.

Filed: the framework-nightly reading in section 4 is deliberately scoped
to *all* the live nightlies rather than to `live-frameworks` alone, so
this does not become a fifth unread schedule.
