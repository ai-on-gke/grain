## Branch situation & how follow-up tasks should handle it

Releases are cut from `main` by the continuous train (`.grain/settings.yml`, `scripts/release.conf`), and `v3.13.0` is `latest`. A `fix:` that a walkthrough lands on `main` ships with the next rc and needs **no backport task**. The exception is an operator asking for a patch to `release/v3.5.1` or `release/v3.1.1`: then fix `main` first and propose a backport with `writes: [{repo: "ai-on-gke/grain", base: "release/vX.Y.Z"}]` and `Backported-from: <sha>`.

Every follow-up walkthrough task filed from this plan targets `main` (`repo: "ai-on-gke/grain"`, `branch: "main"`) and depends on [Task #7014](/tasks/7014), so `docs/test-plans/2026-11-18.md` is on `main` when each walkthrough starts. Each proposal asks for unattended `auto_merge: true` once CI is green. Whoever approves the proposal decides whether to grant auto-merge on `main`.

The gate is **GitHub Actions**: `Tests` in `.github/workflows/tests.yml` (including `ui-ng e2e`), `plc-tests.yml` when `grain-plc/` is touched, `cla/google`, the workflow/hygiene scans, and the every-PR gating review. Inside a sandbox:

- Do not rely on the MCP `pull_request_status`, `base_branch_status` or `wait_for_checks` tools, and never chain `grain pr status` ahead of `grain ci wait`.

## §1. Capability server pages on `/next/` and start-failure reporting

### What changed
- **PR #1672 (`e39e69057`), "capability server pages with the schema-driven configure form":**
  - Settings → Capabilities on `/next/` opens each server on its own page, `/next/settings/capabilities/<encoded id>` (`ui-ng/src/app/settings/capability-server-page.component.ts`, route in `app.routes.ts`). The servers table links each id there; Stored secrets' "Used by" links go there too.
  - The page edits, renames and tests the connection, including Host placement (`run: host`, or `run: hostd` with a named host). It lists the server's secrets with Bind a secret and Replace value.
  - Server settings are drawn from the schema the server's `configure` tool declares (`capability-schema-form.component.ts`): write-only secret fields with set / missing / not set chips, Rotate for managed tokens, refusals shown on the field they name, gcp permission sets marked keyless (token) or service-account key, key-only fields following that choice. figma accounts get Test and Connect Figma with the OAuth callback.
  - Granted by lists every holder from `GET /api/capability-servers/usage`. When that read is refused or fails, the card and the Remove/Rename confirms say the holder list could not be read, not "Nothing grants it now" (`d33125287`).
  - New shared components: `g-info-popover` (click/Enter/Space, Escape, outside click, phone-bounded) and a confirm dialog that lists linked items.
- **PR #1471 (`d7aa452e1`), capability server start failures:**
  - Listener and runtime startup errors are marked `protocol.StartFailure`. The registry records them as **failed**, not needs-config: it keeps the config schema, does not set `ConfigRefused`, retries every `RetryInterval` so freeing the port needs no restart, and labels them "could not start: port 4254 in use" in `grain health`, daemon logs, `grain capability-servers` and server-down alerts.
  - A malformed or non-loopback `-listen` (`0.0.0.0:4254`, `127.0.0.1:abc`, `127.0.0.1:99999`, `127.0.0.1:`) stays a **configuration refusal**. The Settings probe no longer rewrites a bad port to `:0` and passes.
  - A drop alert raised for a server that never attached is cleared when the server settles into an unalerted needs-config (an unconfigured built-in after a transient exit, or config cleared back to `{}`).

### What CI proves
- `ui-ng/e2e/next-capability-server-page.spec.js` over `grain demo -secrets-store` (desktop, phone, dark), including the 500 usage read; vitest specs for the form round trip, schema field kinds, gcp mode rules, secret chips and holder links.
- `pkg/capability/servers`, `pkg/capability/intree`, `pkg/capability/protocol` unit tests for `StartFailure`, `-listen` validation and drop-alert clearing; `pkg/cli` health label tests.

### What is NOT proved
1. **The page against a real daemon's built-in servers** (git, host-script, gcp, figma, gchat) rather than demo fixtures: every schema field kind renders, a save round-trips through `GET /api/capability-servers`, a refused field shows its refusal on that field, and Rotate on a managed token changes the token a later probe uses.
2. **Host placement:** switching `run: host` → `run: hostd` with a named host that exists, one that does not, and back; the needs-host warning matches what `grain health` says.
3. **Destructive confirms with real holders:** a server granted by a template, a schedule and a task; Remove and Rename list all three with working links (tasks on classic `/tasks/<id>`); a role without the usage read sees "could not be read", never "Nothing grants it now"; Remove actually revokes the grant for a newly dispatched task.
4. **Secrets on the page:** Bind a secret, Replace value, Remove; Stored secrets' "Used by" links land on the right page; a secret value never appears in the DOM, network responses or the page's URL.
5. **Start failure vs refusal on a live daemon:** occupy port `4254` (`socat TCP-LISTEN:4254,fork -`) before start; the git server shows as failed with "could not start: port 4254 in use" in `grain health`, `grain capability-servers`, the alert and the `/next/` page, and **attaches by itself** within one retry interval after the port is freed. Then set `-listen` to each bad form above; each is a config refusal shown on Settings, the save is refused, no retry loop runs.
6. **Drop-alert lifecycle:** make a built-in exit at start once (bad config), then clear its config to `{}`; the server-down alert in `/next/inbox` clears and `grain health` reads clean. Check that a genuinely dropped attached server still alerts.
7. **Responsive and keyboard:** the page and info popovers at 1440/900/390 px, light and dark; popover focus return and Escape; the Remove confirm's linked list scrolls inside the dialog on a phone.

## §3. Review gates and review feedback

### What changed
- **PR #1760 (`1f5e09c54`), Accept findings on the targeted-review gate:**
  - `findingsGateCovers` and `questionsGate` map findings and open questions of triggers recorded under `LinkTargetedReviewTrigger` to the `targeted-review` gate (and their own `trigger:<name>`); templated triggers and pre-#1376 tasks stay on `review`.
  - `POST /api/tasks/{id}/accept-findings` and `grain accept-findings -gate targeted-review` accept it (previously 400). `MergeGate.Acceptable` is now true on the Targeted review gate in both UIs.
  - `ClearReviewFindingsForGate` follows `findingsGateCovers`, so clearing `review` cannot wipe targeted-review findings. Accepting an unrelated sibling trigger on a multi-trigger review no longer succeeds as a no-op. `reviewGatesSettled` checks `LinkMergePolicyWithdrawn`, `LinkQAHold` and `LinkBrokenRulesHold` before restoring AutoMerge.
- **PR #1808 (`097d82d3f`):** when GitHub refuses a review's draft review (422 "one pending review per pull request"), the reviewed task's owner still gets "Review needs your decision", their reply answers the questions (requeuing the task), and later reviews list them `[answered]`. The fallback returns the findings count, so a takeover review whose draft failed no longer records zero findings. `githubsim` gains `RefuseReviews`.
- **PR #1806 (`6a82a2336`):** "Earlier reviews of this pull request" spends its 2048-byte question cap on open questions newest review first, then answered ones newest first; each review gets a footer counting what was omitted by status.

### What CI proves
- `pkg/model` merge-gate tests for targeted-review mapping and isolation; `pkg/ui` accept-findings tests; `TestReviewWhoseDraftGitHubRefusedAsksTheOwnerAndTheirReplyAnswersIt`; `TestEarlierReviewsSpendQuestionCapOnOpenAndNewestFirst` and the 2 KB cap test.

### What is NOT proved
1. **Targeted review end to end:** a scratch repository with a template-less `.grain/triggers/` path trigger; a task touching that path gets a targeted review with findings; `/next/tasks/<id>` shows Accept findings on the Targeted review gate (and classic `/tasks/<id>`, which this PR also changed); accepting with a reason clears only that gate; AutoMerge is restored only when every other gate is settled. Repeat with two triggers and accept one: the other's findings and questions remain.
2. **Holds block restoration:** with a QA hold (`LinkQAHold`), a broken-rules hold and a withdrawn merge policy each in turn, accepting the last findings does **not** restore AutoMerge.
3. **CLI and authority:** `grain accept-findings -gate targeted-review` as owner, as an agent token (refused unless the docs say otherwise), and for a gate with no findings (clear error).
4. **422 fallback on a live daemon:** two reviews of the same head under one credential with the GitHub sim's `RefuseReviews`; the owner's Inbox on `/next/inbox` shows "Review needs your decision" with the closing sentence saying posting failed; the reply requeues; the next review's prompt lists the question `[answered]`.
5. **Question cap in a real prompt:** a PR with 4+ reviews (15 long answered questions, then open ones, then a force-push); read the next review's materialized prompt and check the order, footers and the 2048-byte total.
6. **Overlap:** `2026-11-16.md` §3 (review findings and gates) is still open; it covers Accept findings on `review`/`security-review`. Walk only `targeted-review`, the holds and the two feedback fixes here.

### Walkthrough & test procedures
1. Real daemon (SQLite and PostgreSQL) with the GitHub sim and fake agent CLI; reuse `docs/test-runs/2026-11-14-review-context/`.
2. Items 1–3 via `/next/tasks/<id>`, classic `/tasks/<id>` (the gate card only), the CLI and `curl`; items 4–5 by reading the review task's prompt file in its sandbox log.

## §4. Upgrades: cancel, cleanup and scheduled upgrades on PostgreSQL

### What changed
- **PR #1464 (`aea7b20ac`):**
  - `/next/settings/upgrade`'s "Upgrade in progress" Cancel upgrade now sends `DELETE /api/upgrade/current` with the reason (it used to call `DELETE /api/upgrade/scheduled` and claim success while the upgrade carried on).
  - A cancelled image upgrade removes its health check's container, found by the `grain.upgrade-check=<hash>` label; a custom `ImageConfig.RunCmd` must clean up its own (documented).
  - Report `docs/test-runs/2026-11-13-upgrade-cancel.md` lists **unfixed** findings F5 (a cancelled upgrade or rollback replaces the recorded rollback target with the running image), F6 (status offers a rollback that is refused for an unpinned previous image), F7 (cancel removes a target tag that was already on the host).
- **PR #1799 (`b3a0724e0`):** `Store.BusyRunCount` no longer coalesces a boolean with an integer, so `grain upgrade start -after-tasks-finish` starts on PostgreSQL (the default store for new installs) and `GET /api/upgrade` reports real `busyRuns`. `reconcileScheduledUpgrade` holds the queue before reporting a counting error and never starts on a count it could not read.

### What CI proves
- `pkg/upgrade` cancel/cleanup tests; the `/next/` settings spec asserting `DELETE /api/upgrade/current`; `TestBusyRunCountOnPostgres`, `TestAScheduledUpgradeHoldsTheQueueWhenItCannotCount`.

### What is NOT proved
1. **Scheduled upgrade on PostgreSQL end to end:** an image-mode daemon on PostgreSQL with two running fake-agent runs and one interactive session; `grain upgrade start -after-tasks-finish`; `GET /api/upgrade` shows `busyRuns: 2`; the queue is held (no new dispatch); the upgrade starts when both runs finish (the interactive session does not block it); `/next/settings/upgrade` shows each phase. ## §5. Secrets: deleting the `.migrated` plaintext copies

### What changed
- **PR #1512 (`87f78fa57`):** on each daemon start, before that start's own moves, every `<file>.migrated` copy left by `v3.5.0`'s move into the secrets store (GitHub credentials under `secrets/github`, the sandbox-access and package-cache CA bundles, the state and secrets repository tokens, the release-approval key) is checked against the store's own value (`secrets.enc`, or Secret Manager for the CA bundles when that is the backend), not a cache.
  - The store holds it (same value, or a superseding one after a rotation/renewal) → the copy is deleted and logged once.
  - The store holds nothing → the copy is kept and every start warns, saying how to re-import or drop it.
  - Copies moved during a start survive until the next start. Under `GRAIN_GITHUB_CREDENTIALS=files` nothing is deleted.
  - The relay token's copy (`secrets/relay/token.migrated`) is deleted unconditionally: the relay is gone.
  - Code: `gitproxy.RetireMigratedCopy`, `CredentialSet.DeleteMigratedCopies`, `daemon.deleteMigratedCopies` (`pkg/daemon/loose_credentials.go`, `ca_store.go`), `pkg/releaseapproval/keystore.go`; design `design/design/secrets-key-protection.design.md` §6.2.

### What CI proves
- Unit tests for each credential kind's retire path, the restart test (including the relay case with no `relay/token` secret), and the `files` mode skip.

### What is NOT proved
1. **A real upgrade path:** a data directory produced by a `v3.4.x` (pre-move) build, started once on `v3.13.0` (creates `.migrated` copies), then on `HEAD`. Every copy the store holds is gone after the `HEAD` start, the log names each once, and a second start logs nothing. GitHub pushes through the git proxy, sandbox CA trust and release approval keep working.
2. **Superseded and orphaned copies:** rotate the GitHub token in `/next/settings` between the two starts (copy deleted as superseded); delete one secret from the store before the `HEAD` start (copy kept, warning on every start, the re-import instruction actually works).
3. **`GRAIN_GITHUB_CREDENTIALS=files`:** nothing deleted; the daemon reads the plaintext files; switching back to the store and restarting deletes the copies.
4. **Downgrade:** after `HEAD` deleted the copies, the documented downgrade in `docs/host-setup.md` ("Downgrading to an earlier build") to `v3.13.0` still starts and authenticates.
5. **File safety:** a `.migrated` that is a symlink to a file outside the data directory, one with mode `0644`, and one the daemon cannot delete (read-only directory). The symlink target is never deleted or read through; failures are logged, not fatal.
6. **Secret Manager backend** is an external boundary: stub it only if no emulator is available, and say so.

## §7. Staging proxy credential stripping and stale-chunk Reload

### What changed
- **PR #1763 (`b3f3aa2ad`):**
  - `Server.handleStagingProxy` (`/staging/{name}/...` to a persistent sandbox, `pkg/ui/persistent_sandboxes.go`) now strips every controller credential before forwarding: `Authorization`, `Proxy-Authorization`, `X-Grain-Access-Code`, `X-Grain-Tunnel-Token`, `grain_*` cookies, signed proxy assertion headers (`X-Goog-IAP-JWT-Assertion`, `X-Grain-Hub-Assertion`, `X-Grain-Registry-Assertion`), every registered `IdentityVerifier.Headers()`, IAP session cookies (`GCP_IAP*`, `GCP_IAAP*`), root-origin `__Host-*` cookies, `X-Goog-IAP-*` / `X-Goog-Authenticated-User-*` edge headers, and hub/acting headers. The sandbox's `Set-Cookie` cannot plant those cookies either.
  - On `/next/`, a lazy route whose content-hashed chunk was replaced by a daemon upgrade (404 `no-store`) no longer leaves a blank screen: `staleChunkErrorHandler` keeps the loaded route and shows a snackbar with **Reload** to the requested destination; `@defer` chunk failures get the same action. `resolveReloadHref` rejects control characters and cross-origin resolutions (`/\t/evil.example.com`).
  - Save-Data skips the shell's idle `@defer` prefetch of the New task sheet as well as route preloading.

### What CI proves
- `pkg/ui` and `tests/security` tests pinning the stripped headers and cookies; ui-ng unit tests for `resolveReloadHref` and the error handler; the identity-sessions walkthrough's harness.

### What is NOT proved
1. **The boundary on a real persistent sandbox:** run a persistent sandbox whose app echoes request headers and cookies and sets hostile cookies (`Set-Cookie: grain_session=…; Path=/`, `__Host-x=…`, `GCP_IAP_UID=…`, a `Domain=` cookie). Reach it through `/staging/<name>/` behind the slow identity verifier harness from `docs/test-runs/2026-11-16-identity-sessions/`. No stripped name reaches the app, none of the planted cookies reach the browser, and the operator's own session survives.
2. **Encodings and case:** header names in mixed case, duplicated headers, a `Cookie` header split across lines, cookies with whitespace and quoted values, HTTP/2 and WebSocket upgrades through the proxy (credentials stripped on the upgrade request too).
3. **Stale chunk on a real upgrade:** open `/next/` on one build, replace the binary with another build (different chunk hashes) and restart; click an unpreloaded route (e.g. `/next/processes/quality`, `/next/settings/capabilities/...`). The snackbar appears, Reload lands on the requested page, the console has no unhandled rejection. Repeat for a `@defer` block. Check classic `/` does nothing worse than before.
4. **Open-redirect fuzz:** `resolveReloadHref` with `//evil.example.com`, `/\t/evil.example.com`, `/%09/evil.example.com`, `\\evil.example.com`, `javascript:…`, and a mount prefix (`/grain/next/`) behind a path-prefix proxy; only same-origin paths survive.
5. **Save-Data:** with `navigator.connection.saveData` true (Playwright CDP network emulation), no lazy chunk loads before navigation.

### Walkthrough & test procedures
1. Real daemon with the identity-sessions harness and a persistent sandbox (a tiny echo server is enough); `curl` and Playwright for items 1–2. Record the echoed headers verbatim with credential values redacted.
2. Item 3: build `HEAD` twice with a trivial `ui-ng` change between (or `HEAD~1`), swap and restart; Playwright at 1440 and 390 px.
3. Item 4 as table rows in the existing `resolveReloadHref` unit spec; item 2's gaps as `pkg/ui` or `tests/security` tests.
4. Write `docs/test-runs/2026-11-18-staging-proxy-stale-chunks.md`.
