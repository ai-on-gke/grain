## Branch situation & how follow-up tasks should handle it

Releases are cut from `main` by the continuous train (`.grain/settings.yml`, `scripts/release.conf`), and `v3.13.0` is `latest`. A `fix:` that a walkthrough lands on `main` ships with the next rc and needs **no backport task**. The exception is an operator asking for a patch to `release/v3.5.1` or `release/v3.1.1`: then fix `main` first and propose a backport with `writes: [{repo: "ai-on-gke/grain", base: "release/vX.Y.Z"}]` and `Backported-from: <sha>`.

Every follow-up walkthrough task filed from this plan targets `main` (`repo: "ai-on-gke/grain"`, `branch: "main"`) and depends on [Task #7543](/tasks/7543), so `docs/test-plans/2026-11-20.md` is on `main` when each walkthrough starts. Each proposal asks for unattended `auto_merge: true` once CI is green. Whoever approves the proposal decides whether to grant auto-merge on `main`.

The gate is **GitHub Actions**: `Tests` in `.github/workflows/tests.yml` (including `ui-ng e2e`), `plc-tests.yml` when `grain-plc/` is touched, `cla/google`, the workflow/hygiene scans, and the every-PR gating review. Inside a sandbox:
- Open the PR with `grain pr open` and wait on checks with `grain ci wait` (`timeout: 600000`, no `--jobs` flag).
- Do not rely on the MCP `pull_request_status`, `base_branch_status` or `wait_for_checks` tools, and never chain `grain pr status` ahead of `grain ci wait`.
- If a check is already red on `origin/main`, merge `origin/main` and report the unrelated base breakage rather than weakening the check.

## §1. `/next/` task action area and merge gates

### What changed
- **One action area per task (PR #1580, `b3674bbeb` and follow-ups):** the task page, the Inbox inspector and every pane that embeds a task (`shared/task-action-area.component.ts`) now share one area under the header: a "What's needed" sentence naming who must act; why auto-merge went off; the merge gates list (ported from classic `MergeGatesList` to `shared/merge-gates-list`) with each blocking gate's own actions; park cards; and every action the state allows, computed by `availableActions(task, viewer)` in `shared/task-actions.ts`. A Submit blocked by findings becomes **Send findings back** (posts findings to the thread and re-runs on the branch via run-now) and, for an unlimited role, **Accept findings…**. A Submit waiting on unreported CI is shown disabled with a reason. The header buttons, the More menu and the Changes tab's Submit/Retry merge/Force merge are **gone**. Follow-ups keep Run now on `awaiting_submit`, hide Accept findings from limited roles, and keep tabs and content reachable on phones and 1024×600 panes.
- **Retry merge as primary action (PR #1854)** on merge-failed tasks; **"Merge failed" instead of "Merging"** on `/next/tasks` rows and headers (PR #1836).
- **CI gate fed by GitHub checks (PR #1632, `df743edc4`):** on `ci_mode: github` repositories the CI merge gate now reads `github_ci_job` (task detail) or live head check runs (`GET /api/pull-requests/status`) and says passed / failing (naming checks) / running (naming unfinished ones), or "grain has no record of this pull request's checks". A stale trust-boundary classified head no longer pins the gate. Findings summaries always carry the count and the first finding's location and sentence, and `SyncHumanReviewHolds` backfills bare "review N left findings" records. The Changes tab's gate row shows the first finding / failing check instead of only on hover.

### What CI proves

2. **Removed controls left no hole:** every action the old header/More menu/Changes tab offered (Pause, Stop, Defer, Close, Reopen, Run now, Force merge, Retry merge, Edit) is still reachable from the area for each state where the API allows it. Compare with the classic task pane for the same task.
3. **CI gate on a GitHub-gated repo:** with the GitHub sim posting check runs via webhook: no checks yet → "no record"; one queued + one passed → running naming the queued one; one failed → failing naming it; all passed → passed. `GET /api/pull-requests/status` agrees with the task page. A grain-CI repository's gate is unchanged.
4. **Findings summaries:** a path-trigger review and a security review with three findings render "3 findings: `path:line` …" in the gate row, the Inbox and the task thread; a pre-existing bare record is backfilled after restart.
5. **Roles:** a limited role sees no Accept findings and no Force merge; a viewer sees the area's sentence but no actions; Send findings back is refused cleanly for a role without `tasks:write`.
6. **Inbox inspector and embedded panes** (`/next/inbox`, `/next/tasks` split, `/next/workstreams`, `/next/agents`) show the same area with the same actions; acting from the Inbox refreshes the row.
7. **Layout:** 390 px phone and 1024×600 pane with the longest area (blocked gates + park card + auto-merge-off note), light and dark; tabs reachable without scrolling the pane first; axe clean.

## §2. QA workflow engine: consolidated workflows, chips, S3 resolution and S3 bypass

### What changed
- **Three workflows (PR #1869):** the Software Workflow & QA catalog is now `standard-workflow` (default), `fast-baseline` and `gates-only`; legacy `v1`–`v4` and benchmark bundles leave the UI catalog but still resolve by alias. Tiered `propose_dag` workstream decomposition is the default for high-complexity root tasks on `standard-workflow` (children step down to `slice_plan`; Console Session / Director-filed roots keep `propose_dag`). `qaSummary` on `GET /api/tasks` and `GET /api/tasks/{id}` drives workflow/complexity/blast chips (`qaWorkflowChip`) with S0–S5 tooltips on Inbox, Tasks, Workstreams and task detail. S3/S4 shallow mirrors go through ephemeral git-proxy CI-read sessions (`NewQAMirrorResolver`).
- **Attachments (PR #1879):** bounded UTF-8 plain-text and Markdown task attachments feed complexity classification, S0/S1/S0b/S2 phases, S3/S5 check runs and `TaskQASummary`.
- **S3 and bypass (PR #1882, `fd1abda0f`):** S3's `baseSha` is resolved via `git ls-remote`/fetch/merge-base (deepening shallow history) with `checks.ErrBaseResolutionFailed` and a `qa:base-resolution` check run on failure; URL credentials are stripped/redacted. Rule severities are enforced (`strict-config-decoder`, `ui-budget-and-spec-floor`, `sibling-export-hazard` are `warn`; only `test-integrity-guard` blocks); `QAEngineRev` 7. The staging branch `grain-qa-stage/<id>` is used for CI/PR lookups while staging isolation is active. New **direct-human-only `POST /api/tasks/{id}/qa/bypass-s3`** (`merge:write`, plus `task.Writes` RBAC) with the `<g-bypass-s3-dialog>` modal: staging branch / pinned commit checks, held-PR safety, auto-merge withdrawal, S5 triage.

### What CI proves
- `pkg/qa/...`, `pkg/qa/checks` (severity, workspace), `pkg/model/qa_test.go`, `pkg/ui/qa_staging_ci_test.go`, `pkg/ui/qa_api.go` tests; `ui-ng/e2e/next-qa-bypass-s3.spec.ts`, `next-qa-workflow-studio.spec.js`, `next-qa-settings.spec.js`, `next-qa-engine.spec.js`, `puppeteer-workflow-verify.mjs` over `grain demo`.

2. **DAG default end to end:** on a real daemon, a high-complexity root task on `standard-workflow` proposes a DAG of child tasks; a child steps down to `slice_plan`; a Director-filed root keeps `propose_dag`. Chips on each show the right complexity/blast.
3. **`qaSummary` at scale and in chips:** `GET /api/tasks?limit=500` latency with and without QA rows (the O(1) batch claim); chips render on Inbox, Tasks list/Timeline, Workstreams and task detail at 390 px without overflow.
4. **Attachments:** a task with a Markdown spec attachment (and one oversized/binary attachment that must be skipped) gets a different complexity than the same task without it; nothing binary reaches a prompt.
5. **S3 base resolution against a real git remote:** shallow clone needing deepening, a deleted base branch (→ `qa:base-resolution` check run, not a root-commit fallback), and a remote URL with embedded credentials (never in argv, logs or check output).
6. **Staging CI refs:** while staging isolation is active, `grain ci wait`/`grain pr status` inside the run read `grain-qa-stage/<id>`; after promotion they fall back to the task branch.
7. **S3 bypass authority:** a person with `merge:write` and write on the repo can bypass; an agent token with `merge:write`, a person lacking `task.Writes`, and a viewer are refused (UI hides the control; API returns 403). A bypass on a held PR is refused; a successful bypass withdraws auto-merge and records who/why in the thread and audit log.

## §3. Shadow gate observations, second wave

### What changed
All of these remain **observation-only**: legacy lifecycle, goals, merges and waits keep sole authority, and every prediction is a nonrequired observation with empty work/actions.
- **CI checks (PR #1824):** current-attempt job membership, rerun handling, check-name identity fences, request-precision ordering.
- **Delivery/outcome predictions (PR #1816):** child success invalidated after reopen, canonical wire envelopes, unknown resource provenance, controller settlement across replay.
- **Base, nightly, publishing and pipeline health (PR #1825):** `base-green`, `nightly-green`, `pipeline-healthy` goals compared through legacy and current health profiles, with exact-tip pins and publication receipts.
- **QA stages and release qualification (PR #1830):** release breaking-change observations stay unknown without tag history.
- **Hardening:** independent shadow outcomes and no-work receipts (#1875); unsafe history and evaluator errors rejected (#1885); report/receipt observations scoped on implement tasks (#1904); fresh reads read-only and cached (#1905); all caller scopes intersected (#1903); history read budget sized to two 64-binding views (#1926); SQLite pipeline scan, Postgres finish truncation and heading order fixed (#1933).
- UI: shadow/provenance display on the task page (`ui-ng/e2e/next-gate-check-observations.spec.ts`, `next-gate-live-qualification.spec.ts`).

### What CI proves
- Extensive `pkg/model/gateobservationtest` matrices (checks, health, qualification, readonly), `pkg/gateobserve`, `pkg/gates`, `pkg/ui/gate_*_test.go` on SQLite and Postgres, race tests; the two ui-ng specs with persisted observations.

### What is NOT proved
`2026-11-19-shadow-gate-observations.md` walked the first wave (review/approval observations). Walk only the new observers:
1. **No authority leak, live:** on a real daemon over a day-shaped scenario (a PR with a failed-then-rerun job, a check renamed at the same head, a base going red then green, a nightly run, a release qualification), no task's state, goal, merge or wait differs from the same scenario with observation collection disabled. Diff the task tables.
2. **Rerun membership with the GitHub sim:** a failed job rerun at the same head flips the CI observation from failing to passing only once the rerun's job concludes; a sibling passing job cannot hide it.
3. **Health observations vs goals:** base-green/nightly-green/pipeline-healthy predictions agree with the legacy goal verdict at each step, and disagreements are labelled as such in the UI.
4. **Read path cost:** with 64+ bindings and 2,000 observation rows, opening a task page performs no writes (Postgres `pg_stat_statements` or SQLite trace) and stays within the 250 ms diagnostic budget; repeated opens hit the cache.
5. **Scope intersection:** a repo-limited role and an agent token see only observations for repositories all their scopes allow; a moved repository's history stays scoped.
6. **UI:** observation panels at 390 px and dark, keyboard inspection, heading order in standalone and split views; nothing offers an action.

## §4. Upgrades: schema-downgrade refusal and `grain db downgrade`

### What changed
- **Schema-downgrade refusal (PR #1505, `e2059bd2b`):** any upgrade, scheduled/automatic upgrade, explicit image override or rollback whose target build has a lower schema than the running store is refused across the container-image, Kubernetes and source-build pipelines, **before** any irreversible step. Release images carry `io.grain.schema-version` (stamped by `make image` and the train's promotion rebuild). `GET /api/upgrade/targets` marks such targets `allowed: false` with a reason; `POST /api/upgrade` returns 400; an `upgrade.schema-downgrade` Inbox notification is raised and cleared; scheduled/automatic upgrades drop refused targets and lift queue pauses. Startup still refuses `ErrSchemaTooNew` unless an operator-authored downgrade note (`operatorDowngrade: true`) exists, written by the new offline **`grain db downgrade -to N [-data-dir DIR]`** (refuses while a daemon is attached or `N` ≥ current). `/next/` greys out refused targets (`next-upgrade-downgrade-refused.spec.ts`).
- **Superseded scheduled upgrade cleared (PR #1872)** when an immediate upgrade starts, and the hold released on restart.
- **Host drain survival checked before extracting the upgrade image (PR #1888).**
- **`Store.BusyRunCount` on PostgreSQL (PR #1767)** no longer fails on COALESCE boolean/integer mismatch.
- Walkthrough fixes from `2026-11-18.md` §4 (already reported): #1851 (tag kept on cancel by image ID), #1878 (classic "why it waits" wording).

### What CI proves
- `pkg/upgrade/schema.go` tests (label probe, known tag schemas), daemon tests for the note and startup refusal, `next-upgrade-downgrade-refused.spec.ts`, `next-upgrade-status.spec.js`, CLI spec for `grain db downgrade`.

### What is NOT proved
1. **Real images in a local registry:** build two images with `make image` at schema 153 and one stamped 152 (or `v3.13.0`); push to `registry:2`. `/next/settings/upgrade` lists the 152 target greyed out with both build stamps and schemas; `POST /api/upgrade` to it returns 400; nothing in `image.env`, the schema-upgrade export or the service changed.
2. **Channel moving backwards:** auto-upgrade on a channel whose tag is repointed at an older-schema image is dropped cleanly, the Inbox notification is raised once and clears after a valid upgrade; queue pauses lift.
3. **Unlabelled image:** an image without the label falls back to the known release tag table or is treated as unknown (record which), never silently allowed when it is a downgrade.
4. **`grain db downgrade` disaster recovery:** stop the daemon, run `grain db downgrade -to 152`, start the older build: it opens; then follow `docs/host-setup.md` "Downgrading to an earlier build" to restore. Refusals: daemon running (names `systemctl stop`), `-to 153`/`-to 200`, wrong data dir. SQLite and PostgreSQL.
5. **Scheduled then immediate:** schedule an after-tasks-finish upgrade, then start an immediate one; the scheduled row is cleared, the banner disappears, a restart does not re-hold the queue.
6. **`BusyRunCount` on PostgreSQL:** a scheduled upgrade with running tasks on Postgres counts them and proceeds when they finish (no `countError`).
7. **Classic Settings → Upgrade** shows the same refusal (classic still serves upgrades today).

## §9. Forge and git-proxy resilience

### What changed
- **Login-page retries and parked finishes (PR #1913, `8f2810c4c`):** `CommandForgeTransport.RoundTrip` retries idempotent requests (GET/HEAD REST reads, `info/refs`, `git-upload-pack`) met with a `LoginRedirectError` after 2 s, 5 s and 15 s; pushes and REST writes are sent once; a source can disable retries via `CommandForge.RetryLogin`. In the finish stage, `salvagePushedBranch` is retried on a lapsed host login and, if it still fails, the run ends as `EnvironmentOutcome` and the task is parked on a comment naming the login to renew. A front end's redirect that the tool does not report as a login page is not waited out (`23d1ad181`).
- **Cut bodies (PR #1880):** a forge body the tool cut short after a 2xx fails (`ErrForgeBodyCut`) rather than reading as EOF; signed URLs kept out of errors; a lost/empty Actions job log is read from the run's logs zip once per run, only for finished jobs, bounded as a whole.
- **Hostile `.migrated` copies (PR #1846):** `RetireMigratedCopy` never follows a symlink, opens a FIFO or blocks.

### What CI proves
- `pkg/gitproxy` transport tests with fake tools (retry counts, idempotency), finish-stage tests, `pkg/ci`/`pkg/github` zip tests, daemon start test with hostile copies.

### What is NOT proved
1. **Lapsing login, live:** a fake forge tool (script on `PATH` used by the host git server) that returns a login page for the first N calls: a run's clone and REST reads succeed after retries; a push is attempted once and fails visibly; the daemon log shows the backoff.
2. **Finish parked:** a run that pushed, then whose finish hits a persistent login page, ends as environment outcome (not finish-failed), the task is parked with the renewal comment, and after "renewing" (tool stops returning the page) a resume opens the PR without re-running the agent.
3. **No stacked retries:** count tool invocations for one REST read under a lapsed login: exactly 4 (1 + 3 retries), not 16.
4. **Cut body:** the fake tool prints 200 + headers + half a JSON body then exits 1: the caller reports a cut body; `grain ci log` falls back to the run zip and gets the log; a still-running job does not trigger a zip download.
5. **No secrets in errors:** a signed log URL in the tool's stderr never reaches the task thread, daemon log or UI.

## §10. Authority and reconcilers

### What changed
- **Cross-task halting rail (PR #1398):** a run holding only `api:tasks:write` can no longer close, stop, pause, defer, resume, park-until, wait-on or set depends-on for a task wider than its own envelope (`agentSteeringRoutes`/`agentHaltingRoutes`).
- **Capability server retry (PR #1766):** a built-in server that had already attached under its current config/identity, or a zero-config host server, is retried when configure fails (e.g. after a host process recycle) instead of staying down.
- **In-place review credit (PR #1809):** an in-place security review is credited only with the commits it pushed through the git proxy.
- **Reconcilers at scale (PR #1941):** `reviews` and `notifications` reconcilers bounded at the 50,000-task shape (`reconciler_queries_test.go`).
- **Pipeline steward initialised (PR #1831)** when pipeline notifications are pending.

### What CI proves
- `pkg/ui` agent route tests and `TestRouteAuthorizationMatrix`; `pkg/capability/servers/configure_test.go`; security hold walkthrough e2e tests; reconciler query tests with seeded counts.

### What is NOT proved
1. **Halting rail through MCP/CLI inside a real run:** a task granted `api:tasks:write` scoped to repo A tries `grain api POST /api/tasks/<B>/close|stop|pause|park-until|wait-on|depends-on` on a task in repo B and on a task with a wider envelope: each refused with a clear error; the same on a narrower task in A succeeds.
2. **Capability retry on a real host:** attach a host capability server, kill its process, make the first re-configure fail (bad port), then fix: the server reattaches without operator action; the Inbox alert clears; `/next/settings/capabilities/<id>` shows the history.
3. **Reconciler timing at scale:** seed 50k tasks with the heavy-data seeder on PostgreSQL; `reviews` and `notifications` cycles stay under their budgets in the daemon's reconciler timing log; nothing is skipped (a new review is filed and a notification delivered during the run).
4. **Pipeline steward:** with a pending pipeline notification and no standing steward task, the six-hour wake files/initialises the steward rather than dropping as quiet.
5. **Review credit:** a person's push to the branch during an in-place review is not credited to the review (hold stays until the review pushes or passes).
