# Test plan: the 2026-09-05 batch

What landed on `main` between `e2bc8740` (the last merge of 2026-09-04)
and `fbba060c`, and what it would take to believe it works. Fifty-eight
pull requests: the day's own numbering, `grain/task-1` through
`grain/task-80`, plus the binaries rename (`#757`) and the kontur vendor
bump (`#802`, filed as `grain/task-392`). The last seven of them were
merged in the small hours of 2026-09-06; they are the same day's work and
are covered here.

This is a plan, not a report: nothing below has been run by hand for this
document. Each section says what the change already proves in CI, what it
does not, and what a person would have to do to find out. Where the
answer is "write a test", the task is named at the end of the section;
where it is "somebody has to try it on a real machine", the steps are
written out so the run is repeatable and its result means something.

## How to read the coverage claims

Six places tests run. The first four see every commit -- three of them on
pull requests as well as pushes, `build-artifacts.yml` on the push alone
-- and the last two run on a clock, so a change of theirs is at most a
day old rather than a pull request's own verdict:

| Where | What it runs | Trigger |
| --- | --- | --- |
| `tests.yml` `go` | `make fmt`, `make fmt-frontend`, `go build`, `go vet`, `go test -race ./...`, `npm test` | every PR and push to `main` |
| `tests.yml` `ui e2e` | `make test-e2e` -- Playwright against a real `pkg/ui.Server` (`grain demo`) | same |
| `tests.yml` `real KVM sandboxes` / `granule on a real VM` | `pkg/orchestrator` and `pkg/granule` against booted cloud-hypervisor guests (`GRAIN_REAL_VM_TESTS`) | same |
| `build-artifacts.yml` | builds the image, then `tests/container` (`GRAIN_TEST_IMAGE`) and `tests/installer` (`GRAIN_INSTALLER_E2E=1`, real `setup.sh` as root on the runner) | every branch push |
| `live-agent.yml` | `tests/e2e`'s live suite against the real `agy` binary and a real model credential | nightly, 07:37 |
| `gcp-smoke.yml` | the `gcp-key` capability's GCE and GKE lifecycle | nightly, 04:41 |

Three things follow, and every gap below is one of them:

* `go test ./...` reports `ok` for packages whose real tests skipped
  themselves (`tests/container`, `tests/installer`, the real-VM suites on
  a runner that does not set their variable). A green `go` job is not
  coverage of those.
* nothing in CI deploys grain the way an operator deploys it -- a GCE
  VM from `terraform/gcp`, `scripts/setup.sh` against a fresh machine, an
  image pulled from GHCR. `tests/installer` is the closest thing there
  is, and it runs `setup.sh` against an Ubuntu runner, not against the
  host shape a deployment actually has.
* nothing in CI touches real GitHub except through `pkg/github/githubsim`
  and the nightly live suite, so every new agent-facing GitHub surface
  below is proved against a simulator.

## 1. Host operations: power, root shell, suspend, tailnet

of it. `tests/installer` runs the real installer as root and then asks

`TestTheRootShellRunsACommandAsRoot` (a real path unit turning a written

(`systemctl is-enabled` on each sleep target reads `masked`, and the
logind drop-in exists). `tests/container`'s `TestThePowerButtonsWriteTheirControlFilesOnTheHost`
drives `POST /api/host/{reboot,shutdown,restart}` against the real image
and watches all three control files appear, and `TestAPathUnitTurnsThatControlFileIntoACommand`
pins the `PathModified` re-arm behaviour the shape depends on.
`tests/deploy` holds the file-level agreements (`TestSetupInstallsTheRootShellResponder`,
`TestTheInstallerRefusesHostModeNobodyAskedFor`, `TestTheTailnetOptionServesTheUIWithoutMovingIt`,
`TestTheTailnetOptionConvergesRatherThanFailingTheDeploy`). `pkg/rootshell`
and `pkg/ui/root_shell_test.go` cover the daemon's half against stubs;
`pkg/sysstat`'s nested-virt reading is checked against a real guest by
the `real KVM sandboxes` job.

**Not proved.**

* ~~`grain-shutdown.path` is enabled by `setup.sh` (line ~3151) but is
  not in `TestTheHostControlUnitsAreInstalledAndWatching`'s list, which
  names reboot, restart and shell only. The one power button whose
  failure mode is "the machine stays up and bills" is the one no test
  watches for.~~ Closed by `grain/task-118`: that test now asserts all
  four path units are active and reads each power unit's command back
  out of systemd with `systemctl cat`. It still never fires them -- see
  the bullet below, and the test's own comment.
* no test runs shutdown or reboot for real, for the obvious reason. The
  chain `Power tab -> POST /api/host/shutdown -> control file ->
  grain-shutdown.service -> systemctl poweroff` is proved link by link
  and never end to end.
* the root shell is proved as two halves that have never met: the UI pane
  to the daemon against a stub runner, and the responder from a direct
  file write. Nobody has typed a command into the pane on a deployed host.

  (`_AUTH_KEY`, `_HOSTNAME`, `_SERVE_PORT`, `_UP_ARGS`, `_REQUESTED`) are
  read by tests as *text in a script*. No run has ever brought up a
  tailnet, so `tailscale up` failing, `tailscale serve` binding the wrong
  port, or the "converge rather than fail the deploy" behaviour firing

* host mode (`GRAIN_HOST_SANDBOXES`) is asserted as an installer refusal

**Hand run.** On a throwaway GCE VM from `terraform/gcp`, one pass, in
this order (the destructive steps are last on purpose):

1. Deploy with `GRAIN_TAILSCALE_ENABLE=1`, a fresh auth key,
   `GRAIN_TAILSCALE_HOSTNAME` set to something recognisable. Expected: the
   deploy finishes, `tailscale status` on the host shows the node up, the
   UI answers on the tailnet name at `GRAIN_TAILSCALE_SERVE_PORT`, and it
   is *still* reachable at the address it was on before -- the option
   serves the UI without moving it.
2. Repeat the deploy with a deliberately invalid auth key. Expected: the
   deploy still completes and the UI is up on its original address; the
   tailnet leg logs its failure and converges.
3. Open System -> Root shell and run `id -un`, `systemctl is-active
   grain-daemon.service`, and something that fails (`false`). Expected:
   `root`, `active`, and a non-zero status reported as an answer rather
   than an error.
4. Open System -> Logs and confirm the kernel source is offered and has
   content; confirm the pane is titled System, not Debug.
5. Open the sandbox health pane. Expected: a nested-virtualization
   reading per sandbox, and it agrees with `ls /dev/kvm` inside a sandbox.
6. `systemctl suspend` from the root shell, or close the lid equivalent.
   Expected: refused; the host stays up.
7. Power tab -> Restart grain. Expected: the UI drops for a few seconds
   and comes back on the same data; running tasks are interrupted, not
   lost from the store.
8. Power tab -> Shut down host. Expected: the machine powers off and
   stays off. This is the step that proves `grain-shutdown.path`; do it
   last, and bring the VM back with `gcloud compute instances start`.

Filed: a test for the shutdown path unit, and this hand run.

been suspended, a posting account whose comment lands under a name the
operator did not expect, a 404 that is really a 403 with a
privacy-preserving response. `#786`'s "target repos no credential
covers" panel does not help with any of them, and it is worth being
clear about why: it is a pure local lookup against the ladder
(`ui.Client.targetReposMissingCredentials` -> `gitproxy.CredentialSet.Select`)
and never contacts GitHub, so a repo some ladder entry names reads as
covered whether or not the token behind that entry can actually reach

not the panel's. grain/task-194 settled that this is where the panel

now records -- and the pane says so above the ladder, so what a clean
panel does and does not claim is on screen for the hand run below to
read.

**Hand run.** On a deployment wired to a real GitHub account:

1. Settings -> GitHub, with no credential configured. Expected: every
   target repo listed as uncovered.
2. With two target repos configured, paste a token and then point an
   `owner/repo` ladder entry at it for the first of them, removing the
   `*` entry the first token of a deployment is given automatically
   (`handleSetGitHubToken`). Expected: the first repo covered, the
   second still listed as uncovered, by name. Pasting the token alone
   is not this test: it leaves the ladder at `{"*": "<name>"}`, which
   covers everything, so both repos read as covered however narrowly
   GitHub scopes the token -- which is what the caveat above the ladder
   says, and worth reading on screen while the deployment is in exactly
   that state.
3. Set the commit identity (author name and email) and run a task to a
   pull request. Expected: the commits on the branch carry that identity,
   and the pull request is opened by the posting account named in
   Settings -- check both, they come from different credentials.
4. Set the posting account to a second credential and repeat. Expected:
   the pull request and any comment grain leaves come from the second
   account, and the commits still carry the configured author.
5. Give a task a target repo the credential does not cover and let it
   push. Expected: the failure names which credential the request went
   out under, not just `404`.
6. Check the agent credential against its vendor from Settings ->
   Agents with a valid key, an expired key and a typo'd key. Expected:
   three distinguishable answers.

Filed: this pass, as one live task on a real deployment.

**Not proved.** The upgrade-moves-the-sandbox-image claim end to end: an

deployment. `sandboximage_test.go` proves the resolution happens per

one. This is the natural companion to section 2's hand run -- after step
3, dispatch a task and check the sandbox's image reference on the host.

Half closed by the 2026-09-06 hand run
(`docs/test-runs/2026-09-06-upgrade-pipeline.md`): on a deployment
installed against one sandbox reference and upgraded onto a build
stamped with another, every sandbox `konturctl` created afterwards came
from the *new* reference, with nothing on the host re-run or
re-configured -- visible both in the daemon's own start-up line and in

since a real sandbox image is 45 minutes of a KVM runner and the
published base it derives from was not reachable: the containers were
created from the right image and then failed to start. So "the
deployment reaches for the new image" is now observed on a real host,
and "a task runs inside a guest of the new image" still is not.

Filed: folded into the upgrade hand run.
