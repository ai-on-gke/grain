## 1. Remote Executor Pools, Rendezvous Relay Routing, and Agent Concurrency

Grain significantly advanced its remote execution architecture (`7938cd3b7`, PR #1971;
`115598dc6`, PR #1959; `660d0dfb8`, PR #1946; `216de1a24`, PR #1945; `ab7fb4975`, PR #1944;
`64c0f482e`, PR #1945; `3c5b77f3c`, PR #1937; `ab6b424e9`, PR #1939; `4dbbcff45`, PR #1931;
`078cef914`, PR #1940; `bddc44943`, PR #1935; `75a8872bc`, PR #1934; `32cae2b8f`, PR #1935;
`40168a878`, PR #1933; `1e9af43c6`, PR #1930; `a3d5ab08b`, PR #1925; `3b2ab31a5`, PR #1925;
`f0faf2582`, PR #1953; `91a73b423`, PR #1950; `12cf431d7`, PR #1928).
The remote execution subsystem now supports Cloud Run Rendezvous Relay routing (`pkg/relay`,
`cmd/grain/relay.go`), outbound reverse-tunnel client mode via `--relay-url`, multi-executor
pools with instance deduplication and least-loaded scheduling (`pkg/modelexec`), revocable
per-executor authentication tokens, UI token & concurrency management (`ExecutorsPanel.jsx`),
single-command bootstrap execution (`scripts/grain-remote-executor.sh`), full agent CLI
execution on remote hosts with native tool sandboxing, bidirectional half-close tunnel bridging,
and periodic control stream keepalives.

### Existing coverage
- In-memory mock transport unit tests in `pkg/modelexec/` and `pkg/relay/`.
- Concurrency and least-loaded pool scheduler tests in `pkg/modelexec/concurrency_test.go`.
- Multi-node lifecycle integration tests in `pkg/modelexec/remote_test.go` and `cmd/grain/executor_test.go`.
- UI component tests for `ExecutorsPanel.test.jsx`.

### Gaps and unproven behaviors
- Live execution of multiple remote executor daemons connecting outbound via Cloud Run Rendezvous Relay (`--relay-url`) with WebSocket upgrades and proxy header preservation.
- Proving least-loaded scheduling and instance deduplication when multiple executors share hostnames or reconnect with identical instance IDs.
- Concurrent execution of multiple agent tasks on a single remote executor host up to its configured concurrency limit, verifying agent isolation, credential file placement, and session directory cleanup.
- Revocation of an executor token from the UI and confirming immediate disconnection and rejection of reconnect attempts.
- Network resilience: verifying bidirectional half-close and keepalive ping recovery during transient network interruptions.

### Walkthrough & test procedure
1. Launch `grain demo` with relay service enabled (`grain relay --port=8090`).
2. Start two remote executor instances using `scripts/grain-remote-executor.sh --relay-url=http://localhost:8090` with concurrency set to 2.
3. Verify both executors register in the UI `ExecutorsPanel` with unique instance IDs and reported capacity.
4. Enqueue 4 concurrent agent tasks; assert that the scheduler distributes tasks evenly across both executor instances (least-loaded policy).
5. Verify in-flight task execution, live log streaming, native MCP tool execution, and session workspace isolation on the remote executor nodes.
6. Revoke one executor token via UI; assert the corresponding node is immediately disconnected and active runs failover or terminate cleanly.

## 2. Access & Accounts Management, Dynamic IAP IAM Policy Synchronization & System Administration

Grain introduced a comprehensive Access & Accounts management system (`85735b090`, PR #1977;
`ab0514bd9`, PR #1952; `e51f01309`, PR #1943; `3f45e4d51`, PR #1918; `a32dbb0b5`, PR #1919;
`b37dc8b9c`, PR #1948; `cb4916c73`, PR #1947).
This encompasses a new 'Access & Accounts' settings panel in the UI (`AccessPanel.jsx`,
`AccessView.vue`) under Administrator settings, backed by an account store (`pkg/access`),
CLI subcommands (`grain access add/remove/list`), and REST endpoints (`/api/access/accounts`).
It features real-time synchronization status tracking (Synced, Pending, Error), dynamic GCP IAP
IAM policy reconciliation (`pkg/iap`) targeting backend services, System Administrator accounts
with global configuration privileges, and username immutability under authenticated mode.

### Existing coverage
- Unit tests for `pkg/access/` store operations, JSON serialization, and account validation.
- Unit tests for `pkg/iap/` policy generation and reconciliation logic.
- UI component and API tests in `ui/src/api/access.test.js`, `AccessPanel.test.jsx`, and `SettingsOverlay.test.jsx`.

### Gaps and unproven behaviors
- End-to-end browser walkthrough adding, editing, and revoking user emails, service accounts, and security groups in `AccessPanel.jsx`.
- Live verification of IAP status chip transitions (`Pending` -> `Synced`) upon backend reconciler ticks.
- Dynamic reconciliation against Google Cloud IAM API (or mock IAP reconciler) verifying correct role bindings (`roles/iap.httpsResourceAccessor`).
- System admin privilege enforcement: verifying that system admin users can manage access accounts and system settings while standard team admins are restricted.
- Verifying username editing is disabled in UI when authenticated mode is active.

### Walkthrough & test procedure
1. Launch `grain demo` with authentication and access management enabled.
2. Navigate to Settings -> Administrator -> Access & Accounts.
3. Click '+ Add Account', add a user email (`developer@example.com`) and a service account (`sa-agent@project.iam.gserviceaccount.com`).
4. Verify accounts appear in the table with `Pending` status chips, transitioning to `Synced` once reconciliation completes.
5. Exercise filter, search, and sort controls across account types and sync statuses.
6. Revoke access for an account and confirm modal confirmation, status change, and IAM removal.
7. Attempt accessing `/api/access/accounts` with a non-admin user; assert `403 Forbidden`.

Filed: **Walkthrough: Access & accounts management, IAP policy sync, and system administration (docs/test-plans/2026-09-24.md §2)**

## 3. Advanced Team RBAC Roles, Self-Service Creation, Archival Lifecycle & Isolation

Team management capabilities expanded with self-service workflows, granular RBAC, and lifecycle
management (`574c9828e`, PR #1964; `5965968f8`, PR #1927; `d55722ed1`, PR #1926;
`1162b94ba`, PR #1922; `5c467af0b`, PR #1920; `1cfb45950`, PR #1921; `a92781b5e`, PR #1924;
`bdc55f4f1`, PR #1929; `e29be4405`, PR #1942; `7be9e67f9`, PR #1965; `062eb60a3`, PR #1949;
`a28f878e8`, PR #1932).
Key features include: any authenticated user can create a team and automatically become its admin;
three-tier team RBAC (`admin`, `member`, `viewer`) controlling mutations; team archival and soft-deletion
lifecycle; team-scoped default model configurations and secrets; team scoping to templates and suites;
strict team isolation across agent backends and remote executors; bulk team editing; and task details
overlay team reassignment.

### Existing coverage
- Model RBAC unit tests in `pkg/model/team_test.go` and `pkg/ui/teams_test.go`.
- Cross-team dependency and isolation assertions in `pkg/ui/team_isolation_test.go`.
- UI component tests in `ui/src/components/TeamsPanel.test.jsx`.
- Playwright specs in `ui/e2e/teams_walkthrough.spec.js`.

### Gaps and unproven behaviors
- End-to-end user journey: non-admin User X creates Team "Infra", verifies auto-assignment as admin, invites User Y as `member` and User Z as `viewer`.
- Proving role permission boundaries: User Y (member) can submit tasks but cannot edit team settings; User Z (viewer) can inspect tasks but cannot submit or mutate.
- Team archival lifecycle: archiving a team hides it from default views, disables new task submissions, while preserving historic runs and audit logs; subsequent unarchival restores full function.
- Multi-team agent execution verifying that team-scoped secrets and model backend configs do not leak across team boundaries.
- Live UI task details overlay: reassigning an existing task to another team and verifying queue migration.

### Walkthrough & test procedure
1. Launch `grain demo`.
2. As User A, create Team "data-eng"; assert User A is recorded as team admin.
3. Configure team-default model `claude-sonnet-5` and team secret `DATA_API_KEY`.
4. Add User B as `member` and User C as `viewer`.
5. Authenticate as User B: verify ability to launch tasks using team defaults, and verify inability to modify team settings.
6. Authenticate as User C: verify read-only access to tasks and logs.
7. Archive Team "data-eng": verify team disappears from active selectors and task intake is rejected.
8. Unarchive the team and verify full restoration of permissions and settings.

Filed: **Walkthrough: Team RBAC roles, self-service creation, archival lifecycle, and isolation (docs/test-plans/2026-09-24.md §3)**

## 4. MCP `propose_task` Full Parameter Expansion & Declarative Task Instantiation

The MCP `propose_task` tool was expanded with full declarative task configuration options
(`c5ce98122`, PR #1923; `ef02ecb96`, PR #1917; `10a1cc6e7`, PR #1915; `0bed25a13`, PR #1916;
`b6d90c3fd`, PR #1912).
Agents can now declare: `at_front` (queue front prioritization), `no_repo` (standalone task without
repository checkout), `template_id` & `template_fields` (instantiating tasks directly from templates),
`reads` & `writes` (cross-repository multi-repo permissions), `review_template_id` (attaching pre-merge
review templates), `sandbox_cpus`, `sandbox_memory_mb`, `sandbox_disk_gb` (custom VM sizing),
`network_access` (`open`, `restricted`, `none`), `model` and `agent_framework` overrides, and
`capabilities` (with automatic `grain-ci` capability granting on workflow repositories).

### Existing coverage
- Schema validation and argument parsing tests in `pkg/mcp/args.go` and `pkg/mcp/server_test.go`.
- MCP mock tool definitions in `pkg/mcp/mock_tools.go`.
- Task creation replay and template instantiation tests in `pkg/orchestrator/finish.go` and `pkg/ui/live_proposal_test.go`.

### Gaps and unproven behaviors
- Live agent execution invoking `propose_task` with all newly added parameters and validating correct task dispatch properties.
- Queue prioritization verification: proposing a task with `at_front: true` placing it ahead of existing queued tasks in the team backlog.
- Standalone execution of `no_repo: true` tasks verifying VM initialization without git checkout.
- Multi-repository read/write declarations (`reads`, `writes`) verifying sandbox credential mounting and git remote access.
- Template instantiation via `template_id` and `template_fields` validating parameter interpolation into task prompt bodies.

### Walkthrough & test procedure
1. Launch `grain demo`.
2. Dispatch a parent agent task that calls `propose_task` with:
   - `at_front: true`
   - `no_repo: true`
   - `sandbox_cpus: 4`, `sandbox_memory_mb: 8192`
   - `network_access: "restricted"`
   - `capabilities: ["grain-ci"]`
3. Propose a second task instantiating an existing template via `template_id: "system:workflow-review:nightly"` with `template_fields`.
4. Propose a third task declaring `reads: ["bwsalmon/kubernetes"]` and `writes: [{"repo": "bwsalmon/grain", "base": "main"}]`.
5. Verify that all three proposed tasks are created with exact declarative properties, correct queue positions, and proper repository mounts.

Filed: **Walkthrough: MCP propose_task declarative parameter expansion and templates (docs/test-plans/2026-09-24.md §4)**

## 5. Merge Queue Proactive Conflict Detection, Pre-PR Rebase Verification & Release Watchdog

Orchestrator merge queue mechanics and release monitoring were significantly hardened
(`942688654`, PR #1951; `3f1e51fbc`, PR #1969; `2258ac8ba`, PR #1955; `7317a2fd9`, PR #1936;
`c684f39ba`, PR #1970; `8892dd70b`, PR #1957).
Key improvements include: proactive mergeability evaluation of all queued pull requests immediately
when the base branch advances (dispatching parallel conflict repairs immediately rather than waiting
until a PR reaches the front of the queue); pre-PR base branch rebasing and mergeability checks
before opening pull requests; automated release failure triage with scheduled watchdog monitoring;
backlog partitioning by active team during dispatch evaluation; and graceful tolerance of external
Actions spending budget errors when Grain CI is authoritative.

### Existing coverage
- Merge queue conflict detection unit tests in `pkg/orchestrator/mergequeue_behind_test.go` and `mergequeue_test.go`.
- Pre-PR rebase verification tests in `pkg/orchestrator/ensure_pull_request_test.go`.
- Release watchdog and triage tests in `pkg/orchestrator/release_watchdog_test.go`.

### Gaps and unproven behaviors
- Live multi-PR merge queue simulation: enqueueing 3 dependent pull requests, landing PR 1, and verifying that PR 2 and PR 3 immediately evaluate mergeability in parallel.
- Verifying that when PR 2 develops a conflict against updated `main`, a repair task is dispatched proactively while PR 2 is still behind in the queue.
- Pre-PR rebase walkthrough: an agent finishes a task against an older base commit; orchestrator rebases cleanly onto latest base before opening the PR, avoiding redundant CI cycles.
- Scheduled watchdog execution detecting stalled release candidate branches and filing automated triage tasks.

### Walkthrough & test procedure
1. Launch `grain demo` with merge queue enabled.
2. Open PR A, PR B, and PR C touching related files in a test repository.
3. Merge PR A into `main`.
4. Assert that the orchestrator immediately evaluates mergeability for PR B and PR C on the advancement tick.
5. Introduce a deliberate conflict in PR C; verify the orchestrator marks PR C as conflicted and proactively dispatches a repair task without waiting for PR B to merge.
6. Verify clean rebase before PR opening when base branch has advanced.

Filed: **Walkthrough: Merge queue proactive conflict detection, pre-PR rebase, and release watchdog (docs/test-plans/2026-09-24.md §5)**
