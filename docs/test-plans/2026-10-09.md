## 1. Team Settings Git Connections List and Multi-Host Repositories

**Commits:** `b7e86f787`, `4d5ce3072`, `41d9df348` (backported from `main` `ffcca5a69`, `3c2753ba9`, `3e5f80417`)

### What changed
- **Team Git Connections List:** In Team Settings ▸ Git Identity (`ui/src/components/TeamGitPanel.jsx`), teams can now view, add, test, and delete multiple git connections backed by `Team.GitConnections`.
- **Connection Attributes:** Connections specify `Host` (e.g. `github.com`, `ghe.corp.example`), `Kind` (`github` or `git`), `Auth Type` (`pat` or `app`), and optional `Scope` (restricting credential usage to an org/user prefix).
- **Legacy Credential Migration:** Legacy `Team.GitCredential` configurations automatically render with a `legacy default` badge in the connections list.
- **Connection Verification:** Each connection row provides a "Test" button targeting `POST /api/teams/{team}/git-connections/check` (handled by `handleCheckTeamGitConnection` in `pkg/ui/team_git_connections.go`), verifying host reachability and credentials against the host's REST/GraphQL API or `git ls-remote`.
- **Read-Only Guards:** Commit `41d9df348` hides the "Test" button when the panel is viewed in read-only mode (e.g. for team readers without admin privileges).
- **Multi-Host Repo Parsing:** `RepoPicker.jsx` and `ui/src/state.js` (`looksLikeRepo` and `repoUrl`) now support multi-host repository references formatted as `host/owner/name` (e.g. `ghe.corp.example/acme/service`).
- **REST APIs:** Added `GET /api/teams/{team}/git-connections`, `POST /api/teams/{team}/git-connections`, `DELETE /api/teams/{team}/git-connections/{cred}`, and `POST /api/teams/{team}/git-connections/check`.

### What CI proves
- Unit tests in `pkg/ui/team_git_connections_test.go` test connection listing, creation with PAT/App, deletion, and validation error responses.
- Authorization tests in `tests/security/routes_test.go` verify that `/api/teams/{team}/git-connections` routes require team write/admin permissions.
- Vitest unit tests in `ui/src/components/TeamGitPanel.test.jsx` test rendering of connection tables, form submission, and badge displays.
- `ui/src/state.test.js` tests multi-host URL parsing in `repoUrl`.
- Initial walkthrough script in `docs/test-runs/2026-10-08-team-git-connections-ui.md` verified basic table rendering and adding mock PAT/App connections.

### What is NOT proved
- End-to-end task execution and proxying: cloning and pushing to a multi-host repo (`ghe.corp.example/org/repo`) through `gitproxy` using a non-default team connection.
- Host routing conflicts: behavior when multiple connections match overlapping hosts or scopes, verifying the most specific scope wins.
- Failure feedback in UI: error presentation when testing a connection with expired PATs, invalid GitHub App private keys, or unreachable internal hostnames.
- Interaction between RepoPicker multi-host selection in `NewTaskOverlay` and automatic team credential resolution during task dispatch.

### Walkthrough procedure
1. Launch `grain demo` with Playwright browser test harness.
2. Navigate to Team Settings ▸ Git identity for team `frontend`.
3. Add a secondary PAT connection for internal enterprise host `ghe.internal.acme` with scope `acme-org`.
4. Add a secondary GitHub App connection for `github.com` scoped to `partner-org`.
5. Click "Test" on each connection row and observe check status indicator; test with both valid credentials and deliberate invalid tokens to verify error toast/status rendering.
6. Switch to a non-admin viewer session; verify the "Test" button and "Add connection" form are completely hidden in read-only mode.
7. Open New Task modal; input a multi-host repo `ghe.internal.acme/acme-org/service-backend` into `RepoPicker`. Verify autocomplete and syntax acceptance without validation errors.
8. Queue a task targeting this multi-host repository; verify gitproxy resolves the scoped `ghe.internal.acme` credential and permits sandbox clone.

## 2. Release & Candidate Deletion Lifecycle

**Commits:** `ed99d7879` (backported from `main` `0a6562180`)

### What changed
- **Release Deletion API:** Added endpoint `DELETE /api/repos/{owner}/{name}/releases/{release}` in `pkg/ui/releases.go`.
- **Database Store Cleanup:** Implemented `DeleteRelease` across SQLite and PostgreSQL stores (`pkg/model/release_store.go`, `pkg/model/sqlite/release_store.go`, `pkg/model/postgres/release_store.go`). The deletion cascades to remove associated rows from `PendingReleases` and `PendingCandidates`.
- **Name Freeing:** Freeing deleted release names allows repository admins to re-create a release with the identical name immediately, clearing unprovisionable or stuck release states.
- **Authorization Enforcement:** Deleting a release strictly requires repository admin or team admin permissions (`pkg/ui/release_branch_authorization_test.go`).
- **UI Confirmation Control:** Added a confirm-guarded "Delete release" / "Remove release" button on release rows in `RepoReleases.jsx`.

### What CI proves
- Store tests in `pkg/model/sqlite/release_store_test.go` and `pkg/model/postgres/release_store_test.go` verify clean removal of release rows and associated candidates.
- Endpoint unit tests in `pkg/ui/releases_test.go` and route auth tests in `pkg/ui/release_branch_authorization_test.go` verify 204 NoContent on success and 403 Forbidden for non-admins.
- Playwright test `ui/e2e/release_delete_walkthrough.spec.js` exercises API creation, UI listing, confirmation prompt cancellation, confirmed deletion, and re-creation.

### What is NOT proved
- UI state synchronization when deleting a release while the release details overlay or candidate promotion modal is actively open in another tab or side pane.
- Concurrency and safety: attempting to delete a release while a candidate build or promotion pipeline is actively executing.
- Verifying audit trail or event logging when a release is deleted by a repo admin.
- Visual refresh behavior across Repo Releases and Overview tabs without manual page reload.

### Walkthrough procedure
1. Launch `grain demo`.
2. Navigate to Repositories ▸ `acme/widgets` ▸ Releases.
3. Create a candidate release `v2.5.0-abandoned` and cut an initial candidate `rc.1`.
4. Open the release card to inspect candidate rows.
5. Click "Remove release"; in the native confirmation prompt, click Cancel/Dismiss. Verify the release and candidate rows remain visible.
6. Click "Remove release" again; accept the confirmation prompt. Verify HTTP `DELETE` returns 204 and the release row immediately disappears from the UI without a full page refresh.
7. Attempt to create a new release named `v2.5.0-abandoned` immediately; verify creation succeeds with HTTP 201 Created.
8. Log in as a reader/contributor user without admin permissions; verify the "Remove release" button is disabled or absent, and a direct `DELETE` HTTP call returns 403 Forbidden.

## 3. Unsaved Changes Guard in Task Edit and Custom Fields

**Commits:** `131c8f003`, `8dd9070c8` (backported to `main` in `dd81e2299`, `d0be3a1d6`)

### What changed
- **Draft Dirty Tracking:** Lifts unsaved draft state from `EditTaskForm.jsx` and `CustomFieldsSection.jsx` into `DetailOverlay.jsx` via `editTaskUnsavedRef` and `customFieldsUnsavedRef`.
- **Navigation Interception:** `DetailOverlay` passes `isDirty` to `Overlay.jsx`, intercepting `Escape` key presses, clicking outside the overlay modal backdrop, clicking the internal `← Back` button, and triggering browser history Back (`window.onpopstate`).
- **Confirmation Dialog:** When `isDirty()` returns true, navigation attempts trigger a confirmation prompt (`"You have unsaved changes here. Leave and discard them?"`). Dismissing cancels the dismissal and retains modified field values; accepting discards the draft and closes the pane.
- **React Hook Order Bug Fix:** Commit `8dd9070c8` resolved a React invariant 310 violation in `CustomFieldsSection.jsx` by moving early-return guards (`if (declared.length === 0 && rows.length === 0) return null;`) below `useRef` and `useEffect` hook declarations.

### What CI proves
- Component unit tests in `CustomFieldsSection.test.jsx` and `EditTaskForm.test.jsx` test dirty check evaluation when form inputs change.
- `ui/e2e/deployment-operations-navigation.spec.js` verifies Escape, Back button, and browser Back prompt interactions when editing task titles or custom fields.

### What is NOT proved
- Edge cases with multi-tab or concurrent edits: opening both the Task Edit form and Custom Fields section simultaneously, modifying both, and verifying dirty flags combine correctly.
- Discarding changes after error responses: modifying fields, submitting invalid data resulting in an inline error/refusal banner, and then attempting to navigate away.
- Discarding drafts on keyboard shortcuts other than Escape (e.g. `g` hotkeys or tab switches).

### Walkthrough procedure
1. Launch `grain demo` with Playwright browser test.
2. Navigate to `/tasks/1` to open the task detail overlay.
3. Click "Edit" in the main task pane; change title and description.
4. Attempt to close by clicking the dimmed overlay backdrop; verify the discard confirmation dialog appears. Cancel dialog and confirm text inputs remain modified.
5. Expand "Edit fields" in CustomFieldsSection; modify custom dropdown/text attributes.
6. Press `Escape`; confirm dialog appears. Accept dialog; verify the overlay closes and subsequent reopening displays original unmodified values.
7. Open task details on a task with no custom fields declared or stored; verify no React console errors (invariant 310) are logged and the pane renders cleanly.
