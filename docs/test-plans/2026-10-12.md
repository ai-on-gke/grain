## 1. Team Credential Audit Log and Cross-Team Approval by the Target's Team

**Commits:** `3b66c0c9b` + `2a85c7ad4` (from `main` `2dc851411`), `99dc67d1e` (from `99455be77`), `c38fe4072`  
**Origin Task:** task 2861

### What changed
- The git proxy's audit log is wrapped by `gitproxy.TeamAuditLog`. Every entry still goes to `audit.log`.
  An entry made for a team's work (the live run on the sandbox, or a CI job sandbox's registered team) is
  also written to a new `credential_access_audit` table with task, run, repository, action, credential
  name and outcome. Free text goes through `model.RedactSecretMaterial` first.
- Capability grant resolution tags the secrets context with task and run as well as team. A resolution
  with no team is recorded against the default team.
- `GET /api/teams/{id}/audit-logs?limit=` (max 1000) merges the secret and credential trails, newest
  first. Only team admins and system admins can read it. Settings → Teams → audit panel reads it.
- `POST /api/tasks/{id}/approve-cross-team` now records the approval as the team that owns the target
  task. The target must be a depends-on link of the task, and a `targetTeam` that disagrees is refused.
  Before this, any team admin (every user administers their personal team) could clear the gate.

### What CI proves
- `pkg/gitproxy/teamaudit_test.go`, `pkg/model/credential_audit_test.go` (redaction, merge order).
- `tests/security/team_audit_logs_test.go` (role matrix and cross-team isolation),
  `tests/security/secret_audit_and_scoping_test.go` (approval by the dependent team's admin naming
  itself), `routes_test.go` lists the route as `teamAdmin`.
- `cross_team_dependency_confidentiality_test.go` and `cross_tenant_fair_share_test.go`.

### What is NOT proved
- A real git push or fetch through the demo's git proxy producing a row for the right team, task and
  run, and the row showing in the Settings → Teams audit panel in a browser.
- Redaction of a token that really appears in a proxy request (URL userinfo on a remote, an
  `Authorization` header), checked in the table, the API answer and the rendered panel.
- The panel and API as a plain member, viewer, another team's admin, and a system admin with and
  without Admin mode.
- The cross-team approval through the task pane: the approve control appears only for the target
  team's admins, an approval as the wrong team is refused with a readable error, and the dependent
  task dispatches once the right team approves.

### Walkthrough procedure
1. `grain demo` (add `-github-sim` so the git proxy has a forge) + Playwright. Create teams A and B,
   each with a git connection and a repo.
2. Start a task on team A that pushes a branch through the git proxy (a demo run, or a direct
   `git push` with a minted run token if the demo agent cannot push). Read
   `GET /api/teams/A/audit-logs`: one entry with task, run, repo, action `push`, outcome. Team B's log
   holds nothing for it.
3. Push once with a token embedded in the remote URL. Check the table row, the API and the panel for
   the token: it must be redacted in all three.
4. Open the audit panel as each role. Admins of A and system admins (Admin mode on) see it; members,
   viewers and B's admin get 403 and the panel says so rather than showing an empty list.
5. Make task A1 depend on B1 with `RequireCrossTeamApproval`. As A's admin, try to approve naming team
   A, then naming B: both refused. As B's admin, approve: A1 leaves the gate and dispatches. Repeat with
   a target that is not a depends-on link: refused.

## 3. Resource Bounds: MCP Exec Output and `read_file`, Git Proxy Pack Total

**Commits:** `b3c50afb4` (from `main` `8be925f06`), `8988fb6dd` (from `51df7aeed`)  
**Origin Task:** task 2801

### What changed
- Every exec runner in `pkg/mcp` (container, docker, kubectl, local) collects output into a
  `headTailBuffer`: the first and last 32 MiB of each stream with a marker in between.
- Remote `read_file`/`edit_file` refuse a path that is not a regular file. They read with
  `head -c <cap+1>` and a 2-minute timeout, and refuse a file over 32 MiB. Local `read_file`/`edit_file`
  do the same with `os.Stat` and an `io.LimitReader`, so a FIFO no longer blocks.
- `mcp.Serve` caps a request line at 64 MiB, answers an overlong line with `-32600` and keeps serving.
- The git proxy's `readPackCommits` refuses a pack once the commit data it holds passes 256 MiB.

### What CI proves
- `pkg/mcp/exec_output_test.go` (through `ContainerExecRunner` with a docker shim, heap checks), the
  local file tool tests, `pkg/gitproxy/pack_test.go`.

### What is NOT proved
- `read_file /dev/zero`, a FIFO, `/proc/self/...` and a 40 MiB file through a real sandbox's MCP
  server: daemon RSS stays bounded, each call answers with a readable refusal, and other runs and the UI
  keep working.
- `run_command` that writes 200 MiB to stdout: the answer carries the head, the marker and the tail,
  and the transcript and run pane render it.
- `edit_file` on a file just over and just under 32 MiB: the over-cap file is left byte-for-byte as it
  was.
- A crafted pack of deltas against a large commit pushed through the real proxy: the push is refused,
  the proxy's memory stays bounded, and an ordinary push right after succeeds.

### Walkthrough procedure
1. Run the daemon with a docker sandbox backend if the sandbox has docker. Otherwise drive the
   `mcp` server binary and `ContainerExecRunner` against a local container runtime, and say which in the
   report.
2. Through the MCP tool path, call `read_file` on `/dev/zero`, `/dev/urandom`, a FIFO, a directory,
   `/proc/self/environ` and a 40 MiB regular file. Watch daemon RSS (`ps -o rss`) before and after. Each
   call must return an error within the timeout.
3. `run_command "head -c 200000000 /dev/zero | tr '\\0' a"`: check the head/tail and marker, and that
   the run pane renders the result.
4. `edit_file` on 31 MiB and 33 MiB files; diff each file before and after.
5. Send one MCP request line over 64 MiB, then a normal call on the same connection: `-32600`, then a
   normal answer.
6. Build a pack with `git pack-objects` of many small deltas copying a 30 MiB commit message base and
   push it through `grain demo`'s git proxy with a run token. The push is refused, RSS stays bounded,
   and a normal push afterwards succeeds.

## 10. Per-Version Release Notes (`main`)

**Commits:** `be2088baa`, `94823af51`, `4276f0e35`  
**Origin Task:** task 3024

### What changed
- `docs/releases/vX.Y.0.md` are embedded (`docs/releases/releases.go`). `pkg/releasenotes` lists them
  newest first, with the date and commit parsed from each file. `grain release-notes [--from] [--to]
  [--json]` prints them; the JSON carries the binary's own version.
- `GET /api/release-notes/versions` and `/versions/{version}` (member level).
  `GET /api/upgrade/release-notes?branch=` (system admin) previews a target. On the container path it
  pulls, pins and verifies the image and runs `release-notes --json --from <running>`; on Kubernetes it
  runs a pod; on the source path it reads `docs/releases` from the fetched branch. A target without the
  subcommand or its own notes reads "release notes are not in this build". Previews are cached per
  branch for 5 minutes and run one at a time. Failures answer 422.
- Metrics → Release notes has Weekly and Versions sections. The upgrade pane previews a picked
  target's notes.

### What CI proves
- `pkg/releasenotes`, `cmd/grain/releasenotes_test.go`, `pkg/ui/releasenotes_versions_test.go`,
  `pkg/upgrade/releasenotes_test.go` (container, kube and source paths with fakes), Vitest.

### What is NOT proved

## 11. Non-Disruptive Upgrade Stages 0–1 (`main`)

**Commits:** `6e0b3c0e9`, `c045a170f`, `9dbc6a06d`, `b2a883e27`, tests `107e8d567`, `e47e425f6`  
**Origin Task:** task 2700, task 3024

### What changed
- Shutdown is a cancel cause of its own. A run live when the daemon stops finishes as
  `InterruptedOutcome` (no strike, `EndingInterrupted`). `RecoverOrphanedRuns` finishes leftovers the
  same way. Both leave a note on the task. The resumable session is recorded as soon as the agent CLI
  names it (claude `session_id`, codex `thread.started`, agy conversation id). Stop timeouts are 300s
  (docker), `TimeoutStopSec=330`, `terminationGracePeriodSeconds: 300`.
- The daemon HTTP client has a `RetryPolicy`: 2 minutes, exponential backoff with jitter. Refused dials
  and gateway 502/503 are retried for any method; resets, EOF and 504 only for idempotent ones; response
  timeouts never; grain's own JSON 502/503 is returned. On exhaustion it returns
  `DaemonUnavailableError`.
- `upgrade.GapRecorder` writes `state/restart-gap.json` (listener close and rebind times, deployment
  mode), logs each gap, and the post-upgrade check reports it.
- Model-proxy tokens persist to `secrets/modelproxy-<vendor>-tokens.json` (id, SHA-256 of the secret,
  owner, expiry; mode 0600; atomic rename). A corrupt file is reported and left alone.
- `GET /api/config` carries `restarting: true` while draining or during a restart-ending upgrade; the
  frontend shows "grain is restarting" instead of "cannot be reached".

### What CI proves
- `pkg/orchestrator/interrupted_test.go`, streak outcome tests, early-session tests per framework,
  `shutdown_budget_test.go`, `httpclient_retry_test.go`, `gap_test.go`, `tokens_persist_test.go`,
  `server_test.go`, `App.resilience.test.jsx`, and the container test restarting the daemon under an
  in-flight mcpserver call.

### What is NOT proved
- A real `grain demo` (or host daemon) stopped with SIGTERM while a demo run is live: the run ends
  `interrupted`, the task note appears, the streak is unchanged, and after restart the task resumes with
  its conversation.
- `kill -9` and restart: `RecoverOrphanedRuns` marks the run interrupted, not orphaned.
- The browser during the restart: "grain is restarting" (not "cannot be reached"), no error toasts,
  and the page recovering on its own.
- `state/restart-gap.json` contents after a real restart, and the journal lines.
- A model-proxy token minted before the restart still accepted after it, an expired one refused, and

## 12. Model Proxy: Concurrent Requests per Run Token (`main`)

**Commit:** `e4f399383`

### What changed
- `Proxy.ServeHTTP` counts open requests per token owner. Past `Proxy.MaxConcurrent` (default 16 per run
  per vendor, daemon flag `-model-proxy-max-concurrent`), it answers 429 in the vendor's own shape
  (Anthropic `rate_limit_error`, OpenAI `rate_limit_exceeded`, Google `RESOURCE_EXHAUSTED`) with
  `Retry-After`, audited as `too-many-requests`. The slot is taken after every other check and released
  once the response, stream included, has been copied.

### What CI proves
- `pkg/modelproxy/concurrency_test.go` (shapes per vendor, other runs unaffected, streaming holds the
  slot, refused requests take none), daemon help golden.

### What is NOT proved
- The flag wired through a real daemon, including `0` or negative values.
- Real vendor clients (Anthropic SDK, OpenAI SDK, `google-genai`) against the proxy with a slow stub
  upstream: they back off on the 429 and finish, rather than failing the run.
- The audit line in the daemon log and whatever surfaces refusals in the UI.
- A client that disconnects mid-stream releases its slot.

### Walkthrough procedure (target `main`)
1. Start the daemon (`grain demo` or a host daemon) with `-model-proxy-max-concurrent 2` and a local
   stub upstream that holds each request 5s. Mint a run token.
2. Fire 5 concurrent requests per vendor with curl: 2 succeed, 3 get 429 with the vendor body and
   `Retry-After`. A second token is unaffected.
3. Run each vendor's official client with retries on: all calls complete.
4. Start a streamed reply and kill the client mid-stream; the next request gets a slot.
5. Try `-model-proxy-max-concurrent 0` and `-1`; record the behaviour and whether it is documented.

## 13. Security Clearance Carried to Ports; Red Base Waits via Depends-On (`main`)

**Commits:** `d31c38f0e`, `acd860412`  
**Origin Task:** task 2935 (clearance)

### What changed
- `holdForTrustBoundary` tries `carryClearance` first. A clearance carries when every trust-boundary
  file's patch is the same (git patch-id style) in the cleared diff and the new head's diff. A port
  inherits its source's clearance if the source was cleared at its final head under the same list and
  repo-rules identity. The port keeps auto-merge, an earlier hold is released, and its review is
  closed (`LinkClearanceInheritedFrom`). A head that moves without touching a trust-boundary patch
  keeps its clearance.
- `heldForBrokenBase` and `waiting_base` are gone. Dispatch links each ready task on a confirmed-red
  branch to the branch's repair task (filing one if none) with `LinkDependsOn`. A second repair depends
  on the first, and loops are refused. The merge queue's all-inherited entries read `base_broken` naming
  the repair and are re-armed (base merged in, CI re-run) when the link clears. Repairs on a branch that
  turns green are closed as superseded.

### What CI proves
- `port_test.go`, `securityhold_test.go`, `securityhold_inherit_internal_test.go`;
  `baserepairlink_internal_test.go`, `inherited_failures_test.go`, `circuit_breaker_test.go`,
  `inherited_walkthrough_test.go`, `merge-queue-waiting-states.spec.js`.

### What is NOT proved
- A full port flow through the real orchestrator and queue: a trust-boundary change reviewed and
  cleared on `main`, merged, ported to `candidate` (mechanical and agent-made), merging without a second
  review, and the notice on the port's PR.
- The negative cases: the port's trust-boundary patch differs (conflict resolution), the source
  cleared at an earlier head, the trust-boundary list changed between them. Each must hold for review.
- A CI-repair commit on a held or cleared change: no new review filed.
- Red base end to end: tasks show "blocked on #N" in the UI, a merge-queue PR reads `base_broken`
  naming the repair, the repair turning the base green clears the links, and the entry is re-armed
  rather than dispatched. A manual depends-on loop is refused with a readable error.

### Walkthrough procedure (target `main`)
1. Extend the `tests/e2e` port and inherited-failure harnesses (real orchestrator and merge queue, fake
   forge) with a paired-branch repo that has a trust-boundary list.
2. Clearance: run each positive and negative case above and record holds, reviews filed and closed,
   links, and PR comments.
3. Red base: break the base's CI, queue three tasks and a PR with an inherited failure. Verify the links,
   `base_broken`, a single repair (a second one depends on it), then fix the base and watch the links
   clear, the entry re-arm and the repair close.
4. Load the resulting state in `grain demo` (or drive the same flow there) and check the task pane,
   Inbox and Repository overview wording in Playwright.
