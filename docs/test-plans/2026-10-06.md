## 1. The rendezvous relay is the only remote route

Commits:
- `96e40b25d` (`feat!`): removes `cmd/grain-tunnel-gateway`, `pkg/tunnel/connector`,
  `pkg/tunnel/gateway`, `cloudrun-proxy.tf` and the cloudrun-iap playbook.
  - A daemon given `-tunnel-gateway-url`, `-tunnel-token`, `GRAIN_TUNNEL_GATEWAY_URL` or
    `GRAIN_TUNNEL_TOKEN` refuses to start and points at `-relay-url`.
  - Terraform keeps `use_cloudrun_iap_proxy` only so that its validation fails with the same pointer.
  - `-ui-trust-tunnel` is renamed `-ui-trust-relay`, and the old name is still accepted.
  - The trust-boundary list moves to `trust-boundary/v5`.
- `d55f5a274`: relay settings are stored (`pkg/relaysettings`).
  - The settings are the URL, the IAP JWT audience (default URL + `/*`), the ID-token audience,
    the user IAP assertion audience, and a write-only token kept as secret `relay/token`.
  - Flags and environment variables override stored values. Every read says where each value came
    from.
  - A `relayManager` re-reads every 5 s (and at once after a UI save), restarts the client when the
    effective config changes, and writes `relay-status.json`.
  - Routes `GET/PUT /api/relay-settings` and `POST /api/relay-settings/test` are system-admin only.
    The Relay section on Admin → Access shows values, sources, connection state and last error,
    has a Test button, and warns when `-ui-trust-relay` is on with no user IAP audience.
  - `grain relay show|set|clear|test` edit `-data-dir` directly, so they work with the daemon down.
- `cc3d93137`: the relay verifies `X-Goog-IAP-JWT-Assertion` and requires the identity to be on
  `-daemon-allowed-emails` / `-executor-allowed-emails`, with `-iap-audience`.
  - `X-Goog-Authenticated-User-Email` is never read. A request with no assertion is refused.
  - With a daemon allow-list and an audience set, the daemon token becomes optional. A configured
    token is still required as well.
  - An allow-list without an audience refuses to start, and so does a relay with no
    authentication.
- `04175f2f2`: `relay_iap_mode = "cloud_run"` runs the relay on its `*.run.app` URL with Cloud
  Run's own IAP, and no load balancer. The provider moves to `~> 7.21`, and `moved` blocks
  keep a live load-balancer deployment's plan to moves.
- `ac6b5c067`: clients send `Upgrade: websocket` with a key, because an identity-aware front end before a
  `*.run.app` service passes only WebSocket upgrades. Relays still echo any upgrade token.
- `f52ad0f38`: a tunnel has a lifetime (`-relay-session-lifetime`, default 240 s, 0 never rotates).
  - At the lifetime the daemon dials a new tunnel, makes it current, and drains the old one.
  - Every ~20 s it asks `GET /relay/status`. If the serving instance has no session for it, it
    rotates at once, so a redeploy heals.
  - The relay replaces a held session only for the same `X-Grain-Relay-Client`. A true duplicate
    still gets 409.
- `7f03fa1ee`: `pkg/iapreconciler` manages an IAP web resource
  (`projects/N/iap_web/cloud_run-R/services/S`) as well as a backend service.
  - The resource is `-iap-resource`. When that is unset, it is derived from the relay's user IAP
    audience in Cloud Run form. `none` turns the derivation off.
  - The daemon always keeps its own relay identity on the policy, and refuses to write if it cannot
    find that identity.

## 3. The mechanical porter

Commits:
- `8c6fd129d`: `pkg/portpick` ports a merged change onto the other branch of a pair on grain's
  own host.
  - It takes the PR's commits that the target lacks, less any `git cherry` finds by patch id
    and any a `Backported-from` or `cherry picked from` footer names.
  - It cherry-picks each with `-x` and adds `Backported-from:`. On conflict it aborts, reports the
    commit and paths, and pushes nothing.
  - It pushes one new branch only: no `+`, no `--force`, and never a branch named like either side
    of the pair. The credential goes through `GIT_CONFIG_*`, and no host git config or hooks are
    read.
- `47e6ad845`: `filePorts` asks the porter first.
  - A clean pick files a port task that already owns its PR, completed through
    `finishWithPullRequest` and tagged `port-mechanical`.
  - A red grain CI goes to the merge queue's repair path. Nothing to port files nothing and notes
    the source.
  - A conflict or failed attempt files the agent port task, told why.
- `e698eee10`: `daemon.NewPorter` builds it over the git proxy.
  - Each attempt gets a token for its own `port-<random>` identity, with write to the one repo
    and, for a team's task, that team's credential. All of it is dropped at the end.
  - The merges metrics split landed ports into mechanical, agent and mechanical-but-repaired.
- `b56625fc1`: `--end-of-options` before every variable git argument.
- `e2e1d4aff`: the git proxy authorizes `info/refs?service=git-receive-pack` as a push. A sandbox
  with read scope only gets a readable refusal at the advertisement, not "RPC failed; HTTP 403".

### Walkthrough & test procedure
1. Base on `main`. Rebuild part 1's environment: the fake GCE served on loopback (part 1 used a
   25-line program; check whether `--fake-gce` works now and use it if so), silod bootstrapped
   on `127.0.0.0/8`, and `curl --interface` for origin identity. Record every stub.
2. Facade writes: through the `silo` CLI or `curl`, insert and delete an instance, a pd-balanced
   disk, an image, a snapshot, an instance template, and an instance from that template, plus one
   instance with a GPU and local SSD. After each step, read the ledger and assert the charge and
   its return. Make the fake fail one insert, and assert the charge comes back once silod sees the
   failed operation.
3. Leader: run two `silod serve` on one Postgres (Debian's `postgresql`, as part 1 installed).
   Start a slow fake operation, kill the leader, and assert the other takes the lease with a
   higher epoch and adopts the operation. Assert that a write stamped with the old epoch is
   refused.
4. Egress: `silod gateway --egress-listen`. Set a policy allowing `example.com:443` for silo A
   only. `curl -x` from A's and B's addresses to a local HTTPS target that the policy names by
   host. Assert allow and deny, and check that a child silo inherits.
5. Exports: silo A offers an http export to `/B`. B accepts it. `curl` through the gateway from
   B's address reaches A's target, and from C's address it is refused. Check the `proxy_protocol`
   header when it is set.
6. Front door: with fake keys, map a member and call `/compute/v1` through `silo proxy`. If
   `gcp-key` is present, repeat with a real ID token, read only.
7. Agents: create an agent through the fence API with `agents.Fake`, and assert the tool VM
   appears through the facade with its charge.
8. Write `docs/test-runs/<date>-silo-v1-part2.md` in the shape of part 1's report, with an SV-id
   table of what passed.

## Standing environment notes for the filed tasks

- **Branch.**
  - §1-§8 target `candidate`, which holds every commit they cover.
  - §9-§11 target `main`. If a cut lands before a task starts and the commits reach
    `candidate`, the task still runs on `main`, its own base, and says so in its report.
  - Each report names the tested commit and confirms it with `git branch -r --contains <sha>`.
  - `bwsalmon/grain` declares `port-branches: [main, candidate]`, so a fix merged on one branch is
    ported to the other, mechanically where it can be (§3). Do not cherry-pick by hand, and never
    merge `main` into `candidate` or the other way round.
- **Overlap.** Before filing a finding, check `docs/test-runs/` (in particular
  `2026-10-06-daily-exploratory-ui.md` and the `2026-10-05-*` reports) and the open tasks for the
  same finding. If it is there, link to it instead of fixing it twice.
- **CI authority.** Grain CI (`.grain/workflows`) is the only merge gate. GitHub Actions checks are
  informational.
- **Browser tests.**
  - Set `PLAYWRIGHT_BROWSERS_PATH=/var/cache/playwright`.
  - Build the UI (`cd ui && npm ci && npm run build`) so the run uses the production bundle in
    `pkg/ui/static`.
  - Run against the real `go run ./cmd/grain demo -addr 127.0.0.1:0 -open=false`.
  - Do not mock grain's own APIs or React. Stub only GitHub (githubsim / `-github-sim`), Google
    OAuth and IAP keys, live model sessions and providers, registries you cannot reach, and real
    cloud APIs. List each stub in the report.
  - Slowing or failing a real response with `page.route`, or wrapping a browser API such as
    `Notification` to record calls, is not mocking grain.
- **Formatting.** `npm run format` in `ui/` for UI changes, and `gofmt` for Go.
- **Security suite.** `make security` must stay green, and no `.grain/baselines/` count may rise.
- **Trust-boundary hold.** A fix touching a trust-boundary path is held for security review before
  it auto-merges, and that is expected. Examples: `pkg/gitproxy`, `pkg/relay`, `pkg/portpick`,
  `pkg/mcp`, `pkg/ci`, `pkg/orchestrator`, `pkg/ui` auth, `tests/security`, `.grain/triggers/**`
  and `.grain/merge-rules.yml`.
- **No live writes.** Read live state of this deployment, or of a GCP project, read only. Never
  write an IAP policy, a relay setting, or a release tag on a real remote.
- **Reports.** Each task writes `docs/test-runs/<date it runs>-<feature>.md`. The report covers the
  environment, tested commit, commands, outcomes, findings (each with a deterministic
  reproduction), stubs, fixes and the CI verdict.
- **Known flakes.** See the repository notes:
  - `RepoPage.test.jsx` "shows the inherited global value…";
  - `src/App.narrowing.test.jsx:89`;
  - `ui/e2e/team_declarations_ci_walkthrough.spec.js:229`.

  Record a recurrence. Do not chase it in a feature task.
