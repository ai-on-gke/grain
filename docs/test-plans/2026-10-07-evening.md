## 1. Admin mode: a system admin is a normal user until they switch it on

Commits:
- `5487e358e` (`main` `18b55304b`, task 2125/2144).
  - **Server.** `serveHTTP` (`pkg/ui/server.go`) attaches `model.WithoutSystemAdmin` to every
    request from a human principal that does not carry `X-Grain-Admin-Mode: on`.
    `Config.IsAdminIn` and `Store.IsAdmin` read that context. Those two reads reach:
    - `checkSystemAdmin`, and through it every admin-only route;
    - `authorizeRepo`, release workflows, `requireSystemAdminToName` and
      `canProvisionAccounts`;
    - `/api/config`'s `isAdmin`;
    - the console viewer check;
    - the team-store role queries, including the implicit default team;
    - `IsApprover(system-admins)` for sensitive-path holds.
  - **What is not affected.** `IsUserAllowed` alone reads the configured list, so an admin can
    still reach the server to switch the mode on. IAP membership sync and the first-account
    bootstrap are left alone. Requests with no principal (trusted loopback, trusted CIDRs, the
    local CLI token, in-process calls) are unchanged, and so are agent and automation principals
    and team admins.
  - **The CLI.** `HTTPClient` always sends the marker.
  - **Refusals.** A refusal that Admin mode alone causes ends "you are a system admin; turn on
    Admin mode to do this". `/api/config` and `/api/auth/user` report `isSystemAdmin` and
    `adminMode`.
  - **UI.** A sidebar "Admin mode" switch (`admin-mode-switch`) that starts off at every sign-in
    and is kept in `sessionStorage` (`grain.adminMode`). While it is on, `api()` sends the
    header, and a red chip and a banner are shown. Toggling it remounts the app.
    `actsAsSystemAdmin` hides the admin tabs in App, AdminOverlay and Team settings.
  - **Port.** The `candidate` port kept `IdentityNotAccepted` in `AuthUserResponse` beside the
    new fields.

## 2. How the caller authenticated, and no password controls for IAP users

Commits:
- `f45bfe28f` (`main` `ee4900cf7`, task 2125/2142).
  - `/api/auth/user` and `/api/config` report `authMethod` and `hasPassword`. `authMethod` is
    one of:
    - `iap`: a verified IAP or signing-proxy assertion;
    - `password`: a session for an account with a password;
    - `google`: a session for an identity with no password;
    - `header`: an opted-in plaintext identity header;
    - `trusted`: nobody signed in, from loopback, the local CLI token or a trusted CIDR.

    `extractPrincipal` (`pkg/ui/principal.go`) returns the method, and `serveHTTP` keeps it on
    the context. `GET /api/users` marks each account's `hasPassword`.
  - In Settings, an identity with no password account gets no "Change password" form. An IAP
    user sees "Signed in through IAP as <email>" in place of Log out.
  - The admin Users panel offers no "Change Password" for an account with no password.
  - The `candidate` port kept the combined header-trust check and its `logIgnoredIdentityHeader`
    call, returning `AuthMethodNone` there.

### Existing coverage

  and `ui.SetIAPAudience`.
- Vitest: `SettingsOverlay.test.jsx` and `UsersPanel.test.jsx`.
- No e2e spec, and no run with a real browser behind an assertion-signing proxy.

### Gaps
- **A real browser with an assertion.** Nobody has driven the Settings pane with a browser whose
  requests carry a verified `X-Goog-IAP-JWT-Assertion`. The unit test's key mechanism (or the
  `-iap-audience` test hooks) is enough to sign one locally.
- **A forged assertion beside a session.** A forged or expired assertion falls back to session

  show then. It should be the session's method, never `iap`.

- **Users panel and Admin mode together.** The admin Users panel now needs Admin mode (§1).
  Nobody has checked "Change Password" is offered only for password accounts when the mode is

- **What is exposed.** `GET /api/users` now marks `hasPassword` on every account. Check who may

## 3. Git hosts phase 1: credential host records, the wrong-host guard, team git connections and GitHub Apps on GHE

Commits:
- `6b08eaf95` (`main` `e3f81d2e7`, task 2320/2365). See `docs/git-hosts.md` for the design.
  - **Host records.** Every credential in `secrets/github/` may have `<name>.host.json` (`host`,
    `kind` `github`|`git`, optional `base_url`). A credential with no record is on the proxy's
    `ForwardHost`, otherwise on github.com. `BuildProxy` writes the default record down
    (`MigrateCredentialHosts`) when it forwards anywhere other than github.com.
  - **The wrong-host guard.** The proxy never sends a credential recorded for another host. The
    request is refused with `Credential.WrongHost`'s sentence, whichever rung of the ladder chose
    the credential.
  - **Apps on GHE.** App installation tokens are minted against the credential's own host API,
    `/api/v3/app/installations/<id>/access_tokens` on GHE (`RealTransport.PathPrefix`). The
    github.com-only refusal (`appsUnavailable`) is gone. An App on a `git`-kind host is refused.
  - **Team connections.** `Team.GitConnections` (`team.git_connections`, a JSON column with a
    migration, exported by the state repo) holds a credential, a host and an optional scope.
    `Store.TeamGitCredentialOn` resolves, in order:
    1. the repo override;
    2. the most specific connection on the host;
    3. the legacy `GitCredential` as the default host's default.

    No match is a `NoTeamGitCredentialError` naming the host.
  - **Port.** The `candidate` port left `anyone_may_propose` out of `teamColumns`.
  - **Not yet.** There is no API or UI for connections yet (phases 4 and 5). Nothing routes to a
    second host yet (phase 2).

### Existing coverage

  is forwarded; another host's credential is refused with nothing sent; an App on a git host is

## 4. A team's pull requests are opened, commented on and merged with the team's own token

Commits:
- `70d8287ba` (`main` `cf02705a1`).
  - Before this fix, a team that set its own PAT in Team settings → Git identity still saw the
    pull requests grain opened for its tasks posted as the deployment owner. The push used the
    team's token, but the REST client only ever used the deployment's ladder.
  - `credentialTokenSource` (`pkg/daemon/capabilities.go`) now asks first for the credential of
    the first custom team owning the repo: `Store.RepoTeams`, in `CiJobTeams` order, then
    `Store.TeamGitCredential`, so a per-repo override wins.
  - That answer is cached for 30 s per repo (`repoTeamCredentialTTL`). A repo no custom team
    owns, or whose team has no credential, stays on the ladder.
  - Both the daemon's client and the UI server's client use it.

### Existing coverage
- `pkg/daemon/team_token_source_test.go`
  (`TestCredentialTokenSourcePostsAsTheOwningTeam`): the selection, from a constructed store.
- No run has followed a team task from the push to its pull request through the real
  daemon/orchestrator with githubsim. So nobody has looked at which `Authorization` header the
  PR create, the comments, the review requests and the merge carried.

### Gaps
- **The whole journey.** Push, open the PR, comment (the progress comment and review comments),
  merge, and close or delete the branch: every REST call for one team task should carry the
  team's token. Nobody has checked that each call goes through this source and not through a
  client built elsewhere with the ladder.
- **Two teams owning one repo.** The first owner's token is used for the *other* team's task
  too. That may post team B's pull request as team A's identity, and needs A's token to have
  write access. Record what happens. If it is wrong, the task's own team should come first
  where it is known.
- **The 30 s cache.** A token a team admin has just changed or removed is used for up to 30 s.
  A removed credential (`credentials.Get` false) must fall back to the ladder, not fail. Nobody
  has checked either.
- **Reads.** The UI server's client now reads the repo (branches, checks, PR state) as the team.
  A team token with narrower access than the deployment's may make reads that used to work
  fail. Check what the repo page and the base-branch checks show then.
- **Hosts.** The team credential comes from the legacy `TeamGitCredential` (no host). On a
  GHE-default deployment it must agree with §3's host-aware answer.

   `pkg/daemon/capabilities.go` and how `tests/e2e` builds its githubsim-backed daemon.

   merge. Give githubsim a recorder for the `Authorization` header of every REST call. Assert

## 5. Settings import on PostgreSQL, and the state repo's other queries there

Commits:
- `f55660bd2` (`main` `908bc0a66`).
  - Before this fix, applying a merged settings change on PostgreSQL failed with
    `syntax error at or near "$2" (SQLSTATE 42601)`, and the daemon kept restarting. The cause
    was the withheld Google OAuth client secret being restored with `UPDATE … WHERE "id" IS ?`:
    SQLite accepts that, but Postgres does not.
  - `pkg/staterepo/withheld.go` and `resets.go`'s `rowKey` reset lookup now use
    `IS NOT DISTINCT FROM`.
  - `pkg/model/postgres/withheld_settings_test.go` covers the OAuth secret.

### Existing coverage
- The new Postgres test applies one settings change and checks that the secret survives.
- The `postgres` CI job (`.grain/workflows/tests.yml`) runs
  `./pkg/model/postgres/... ./pkg/model/` only. **`pkg/staterepo`'s own tests run on SQLite
  only.** So export, import, resets, withheld columns for every table, and the team columns
  added today (§3) have never run against PostgreSQL, except for this one test.

### Gaps
- **Every withheld column.** Only the OAuth secret is proven. `withheldColumns` lists the others;
  each needs an apply on Postgres.
- **Resets.** The reset path (`rowKey`) has no Postgres test. That includes a key column that is
  NULL.
- **Other SQL in `pkg/staterepo`.** Nobody has swept the package for other SQLite-only SQL:
  `IS ?`, `||` concatenation on non-text types, `INSERT OR REPLACE`, `GLOB`, `IFNULL`, boolean
  `0`/`1` literals and `rowid`. The Postgres adapter rewrites some of these (`adapter.go`'s
  `reParamIsNull`). The sweep must say which ones it rewrites.
- **A whole round trip.** Unchecked: export a populated Postgres store to the state repo, import
  it into an empty Postgres store, and diff the two. Also from SQLite to Postgres, which is the
  migration path an operator takes.
- **The daemon restart loop.** The failure mode was a daemon that restarted forever. Nobody has
  checked that a settings import that fails for any reason leaves the daemon serving and the
  failure visible (a log line, the settings sync status), rather than exiting.

### Walkthrough & test procedure
1. Base on `candidate`. Confirm `git branch -r --contains f55660bd2`. Install PostgreSQL as the
   `postgres` CI job does (`sudo apt-get install -y postgresql`, `postgrestest`), and run
   `go test ./pkg/model/postgres/ -run Withheld` to see the environment work.
2. **Withheld columns and resets (Go tests, kept, under `pkg/model/postgres/`).** For each entry
   in `withheldColumns`, apply a settings change that leaves the column withheld and assert the
   value survives. For resets, apply a reset whose key includes a NULL column and assert the row
   is matched and reset.
3. **SQL sweep.** `git grep -nE "IS \\?|OR REPLACE|GLOB|IFNULL|rowid|\\|\\|" pkg/staterepo`
   (and any SQL builder it calls). Classify each hit as portable, rewritten by the Postgres
   adapter (cite the rule) or broken. Write a failing Postgres test for each broken one, then
   fix it.
4. **Round trips.**
   - Populate a Postgres store through the store API: a config with OAuth, teams with §3's
     connections, schedules, templates, repo configs and users. Export it to a temp state repo,
     import that into an empty Postgres store, export again, and diff the two exports. They must
     be byte for byte the same.
   - Repeat with the first store on SQLite.
   - Add the test permanently.
5. **CI coverage.** If the tests from steps 2-4 live in `pkg/model/postgres/`, the `postgres` job
   runs them already. If any must live in `pkg/staterepo`, add that package to the job's
   `go test` line in `.grain/workflows/tests.yml`, and check that the job still finishes inside
   its timeout.
6. **Failure stays visible.** Feed the daemon's settings applier a state repo change that fails
   on purpose: a malformed row on a real Postgres store, run through the daemon's own apply
   loop or the function it calls. Assert the daemon keeps serving, and record where the failure
   is shown. A crash or a restart loop is a finding.
7. Report in `docs/test-runs/<date>-settings-import-postgres.md`.

## Standing environment notes for the filed tasks

- **Branch.** Every section targets `candidate`, which holds every commit it covers. Each report
  names the tested commit and confirms it with `git branch -r --contains <sha>`. `bwsalmon/grain`
  declares `port-branches: [main, candidate]`, so a fix merged on one branch is ported to the
  other, mechanically where it can be. Do not cherry-pick by hand, and never merge `main` into
  `candidate` or the other way round. §1-§3 cover ported code that was adapted for `candidate`.
  A fix there may not port back cleanly, so say so in the commit.
- **Overlap.** Before filing a finding, check `docs/test-runs/` and the open tasks for the same
  finding. Look in particular at the reports for 2026-10-06 §2 and §10 and 2026-10-07 §3, and
  the other `2026-10-07-*` reports. If the finding is already there, link to it instead of
  fixing it twice.
- **CI authority.** Grain CI (`.grain/workflows`) is the only merge gate. GitHub Actions checks are
  informational.
- **Browser tests.**
  - Set `PLAYWRIGHT_BROWSERS_PATH=/var/cache/playwright`.
  - Build the UI (`cd ui && npm ci && npm run build`) so the run uses the production bundle in
    `pkg/ui/static`.
  - Run against the real `go run ./cmd/grain demo -addr 127.0.0.1:0 -open=false`.
  - The Playwright suite sends `X-Grain-Admin-Mode: on` on every request by default
    (`playwright.config.js`). A spec about what a non-admin, or an admin with the mode off, sees
    must override it with `test.use({ extraHTTPHeaders: {} })`.

    cloud APIs. List each stub in the report.
