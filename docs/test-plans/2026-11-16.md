## §1. Identity-verified deployments: verifier sessions, exempt bundles, retries and preloading

### What changed
- **Verifier sessions (PR #1574, `5759e47eb`, `32a3e5e8f`):**
  - A slow `IdentityVerifier` paid a remote round trip on every request, and one `/next/` page load makes about 20 reads.
  - A verifier that implements `SessionBinder` (`SessionTTL` > 0, capped at 5m) now gets an HMAC-signed `__Host-grain_verified` cookie once a full Verify admits an identity. The cookie is HttpOnly, Secure and SameSite=Strict, and binds verifier, identity, Host and expiry. Its key is random per process.
  - A later request carrying the same header and a live cookie skips Verify when `LocalVerifier.VerifyLocal` accepts the header for the same principal.
  - `SessionGrace` lets an unreachable-backend verifier admit the session's own principal up to 5m past expiry. It is refused (401) on every verifier path unless a matching session exists, and grace never re-issues the cookie.
  - The staging proxy treats `__Host-`/`__Secure-` `grain_*` cookies as grain's own.
- **Exempt bundles (PR #1626, `4e355594b`…):** content-hashed `/next/<name>` and `/assets/<name>` bundles are served before `verifyCallerNow` under six exact-match conditions: GET/HEAD, not a hub tunnel request, no query, a canonical path, two segments, and a hashed file that exists. They carry `Cache-Control: private, max-age=31536000, immutable`, a cached gzip with a weak ETag, and ignore Range.
- **Cache headers (PR #1612, `50c7b4d84`):** `index.html` and unhashed files get `no-cache` plus a strong ETag (304 on `If-None-Match`). A missing asset-like path (`.js`, `.css`, `.map`, …) answers 404 `no-store` instead of the SPA fallback. Every refusal and error response is `no-store`. `/next/` awaits the access config before scope-gated initial loads (`7b3787f3d`).
- **`/next/` client (PR #1608, `65d2d3f6d`; PR #1539, `227d6f058`):**
  - `GrainApi` retries GET/HEAD on 503 `verifier_unavailable`, honouring `Retry-After` (default 2s, cap 10s, ±30% jitter, at most 3 retries or 20s). Concurrent reads share one recovery timer. Mutations, 401, 403 and other 503s are never retried.
  - The router preloads every lazy route 1.5s after boot (skipped under Save-Data). A thin `g-nav-progress` bar shows after 120 ms of pending navigation.
- PR #1567 classifies `pkg/ui/access_code_mode.go` under the auth-routes trust boundary.

### What CI proves
- `pkg/ui/verifier_session_test.go`: forged, tampered, expired, other-host and other-principal cookies, and grace refusals.
- Header and classification tests in `pkg/ui` (`TestIsContentHashedAsset`, `TestSpaHandler`, `TestRefusedAndErrorPathsCarryNoStoreNeverImmutable`, `TestServerStaticGzipETagRevalidation`, …), plus `tests/security`.
- `grain-api.service.spec.ts` retry unit tests.
- `ui-ng/e2e/next-task-page-stall.spec.js` (held reads plus a hanging chunk, with preload on and off).

### What is NOT proved
1. **A real browser behind a real slow verifier.** Nobody has run the daemon with a verifier implementing `SessionBinder`/`LocalVerifier` whose remote check takes 1–3s. In that setup:
   - a cold `/next/` load should do one full Verify, then cookie fast paths;
   - the cookie should be re-issued on each full verify and cleared on logout;
   - the cookie should never reach a staging environment through the staging proxy.
2. **Grace in practice:** backend down for < 5m after expiry admits the same principal; > 5m, or a different header principal, is refused; grace never extends itself across repeated requests.
3. **Bundle exemption from outside:** with a verifier that refuses everything, these must be served or refused correctly:
   - hashed bundles are served;
   - `index.html`, `/next/` routes, `.map` files, `?v=1`, `/next//chunk`, `%2e` paths and HEAD vs GET behave as specified;
   - the hub tunnel path is still verified.
4. **Browser caching end to end:** a second load serves bundles from the browser cache and revalidates `index.html` with a 304. The question to answer: does an upgrade (new bundle hashes) reach the browser on the next load without a hard refresh? Also check that missing chunks 404 cleanly (the stale-tab-after-upgrade case: does `/next/` show something useful?).
5. **Retry storm behaviour:** a burst of 503 `verifier_unavailable` with and without `Retry-After` should give no error banner during recovery, then one banner. A POST during the blip must surface at once.
6. **Navigation progress at phone width,** and that preloading does not fire under Save-Data.

### Walkthrough & test procedures
1. Write a small test verifier for the walkthrough (in a `docs/test-runs/2026-11-16-identity-sessions/` helper built under a build tag, or a `pkg/ui` test-only hook if one exists; read `design/design/authentication.design.md` first). It should be slow, count full verifies, and switch its backend off on command. Run a real daemon with it over SQLite.
2. Drive `/next/inbox`, `/next/tasks` and `/next/task/<id>` in Playwright. Log every request, the `Set-Cookie`/`Cookie` headers and the verifier's full-verify count for items 1, 2 and 5. Take a HAR of a cold and a warm load for item 4.
3. Probe item 3 with `curl` (a table of path → status, cache headers, whether Verify was called).
4. Simulate an upgrade for item 4: rebuild `ui-ng` with a changed bundle while the tab stays open, then navigate. Record what the user sees.
5. Add a `ui-ng/e2e/` scenario spec or `pkg/ui` test for any bug found. Write `docs/test-runs/2026-11-16-identity-sessions.md`.

## §2. Task list cost and the batch task summaries endpoint

### What changed
- **PR #1542 (`e32d05d66`, `4a50de3a8`, `43c3b0402`):**
  - `hydrateTasks` runs each child-table query once per list rather than once per task.
  - `ListOpenTasks` reads only open tasks for the live list and for `?state=` filters that cannot match a closed task.
  - The cache keeps a whole list only when it built one. Measured: a 6,000-task Postgres rebuild went from 6.5s to 45 ms.
  - `/next/` says "Could not read tasks" only when reads keep failing, and backs off while they do.
- **PR #1620 (`7bda5290d`, `dd537d292`, `58d07cd08`):**
  - New `GET /api/tasks/summaries?ids=…&comments_limit=&attempts_limit=`: up to 50 unique ids, limits clamped to 500, `{"tasks": {"<id>": TaskDetail}}`, ETag/304. Unauthorized and nonexistent ids are both silently omitted. `?repo=` is rejected.
  - Tasks, Agents, Workstreams and Inbox stores in `/next/` use chunked batches instead of per-task fan-out. `GET /api/tasks/{id}` stays for the task page.

### What CI proves
- `TestTaskListOnPostgresIsCheapAtSixThousandTasks`, and the open-only list checked against `?fields=full`.
- `pkg/ui` summary endpoint tests and the route authorization matrix.
- ui-ng store unit tests, and the e2e gating of the workstream root on `/api/tasks/summaries`.

### What is NOT proved
1. **Row parity on a big real store:** every open row's state, blockers, holds, grants, tags and custom fields are identical before (`?fields=full`) and after the open-only path. This needs PostgreSQL *and* SQLite with thousands of tasks, including deferred, awaiting-reply, rolled-over, repair and merge-queue rows.
2. **Cache correctness across transitions:** a task closing, reopening, or rolling over between an open-only build and a full build. Does `/next/tasks`' closed tab, or classic `/`, ever show a stale or missing row?
3. **Authorization of the batch endpoint on a live daemon:**
   - a repo-scoped role, an agent token with `tasks:read@repo`, and a CI API token (§10) asking for a mix of readable, unreadable and missing ids must get identical omission;
   - 51 ids answers 400; malformed ids answer 400;
   - ETag changes when any one task changes.
4. **Request counts on cold loads:** `/next/inbox`, `/next/agents`, `/next/tasks` (Workstreams view) with 200+ tasks issue a handful of summary calls, not dozens. Failures of one chunk keep cached data.
5. **Classic UI** still lists correctly (it polls the same `GET /api/tasks`).

### Walkthrough & test procedures
1. Real daemon over PostgreSQL then SQLite. Seed ~5,000 tasks (a bulk import into the state repository, or a seeding script under `docs/test-runs/2026-11-16-task-list-cost/`) with a realistic mix of states. Time `GET /api/tasks` (cold, after a write, 304) and diff open rows against `?fields=full` (items 1 and 2) while closing and reopening tasks in a loop.

## §4. `grain-agentd update`: signed owner-run self-update

### What changed (PR #1533, `362ccdde3`, `c6b23bdb5`, `72049c499`, `b02694b26`, `5fc43d276`)
- **`grain-agentd update`:**
  - fetches the signed manifest and binary for its platform from the controller (or `-from DIR`);
  - verifies against the release key **pinned at install** and the SHA-256;
  - refuses a downgrade or anything outside `update.pin`;
  - stages under `~/.local/lib/grain-agentd/versions/<v>/` and smoke-tests (`-build`, `-check`);
  - flips the `current` link and asks the running agent for an idle drain, so `systemd --user` restarts onto the new build;
  - rolls back if the new build has not said hello within five minutes.
- **Hosts list:** `GET /api/hostds` carries `update: {build, available, command}` for connected agents-only hosts that list `self_update`, whose `update.mode` is not off, on a platform a release is built for. Root-installed hosts never get one. `/next/settings/hosts` shows "Update available: <build> → <release>. On the host, run …".
- `docs/grain-agentd.md` gains "Updating it".

### What CI proves
- `tests/agentdcompat/update_linux_test.go` (`TestReleasedAgentdsUpdateToHead` for v3.2.0 and v3.8.0).
- Unit tests for signature, downgrade and pin refusal, and for the made-up platform.
- Settings → Hosts screenshot via the list fixture.

### What is NOT proved
1. **A real install, then update, on a VM-like user account with `systemd --user`,** following `docs/grain-agentd.md` verbatim. The update should wait for a running task to finish (idle cutover) and the run's spool should survive.
