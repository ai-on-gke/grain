## §1. Verified identities — `IdentityVerifier`, IAP principals, `-ui-allowed-principals`, CSRF, the signed-in badge and logout

### What changed (PR #395, `bb2c005d`, `4284622c`)
- **`IdentityVerifier` seam** (`pkg/ui/verifier.go`): `RegisterIdentityVerifier(v)` returns an unregister func; each verifier has an `AccessCodePrecedence`. IAP is the default first verifier when `-ui-iap-audience` is set (`-ui-iap-issuer`, `-ui-iap-keys-url` for the signing keys; `WithIAPValidator` replaces `IAPConfig.Validator`).
- **Admission without the access code** (`pkg/ui/single_tenant.go`): a caller with a valid signed assertion is let in by `singleTenantGate` without the access code. Any *invalid* signed header fails closed with 401 and a `logRefusedAssertion` line. Plaintext identity headers are ignored. A verifier whose precedence says so lets the access code win (a break-glass proxy).
- **Principals** (`pkg/ui/principal.go`): a verified email, lowercased in full, maps to `model.PrincipalHuman`, or to the new `model.PrincipalService` for `*.gserviceaccount.com`. v1 gives full operator access; there are no roles yet.
- **`-ui-allowed-principals`** (`pkg/ui/allowlist.go`, `pkg/daemon/ui_server.go` `CheckUIAllowedPrincipals`): entries `user:`, `serviceAccount:`, `group:`, `domain:`. The default is the deployment owner plus grain-provisioned service accounts. A `group:` entry is resolved through Cloud Identity lazily, cached, and only when no direct entry matched.
- **CSRF** (`pkg/ui/csrf.go`): state-changing requests from a verified browser must be same-origin.
- **UI**: the header rail shows the signed-in email badge and a menu (`PageHeader.jsx`); Settings → Access says how callers are admitted (`AccessSection.jsx`); logout under IAP goes to `/_gcp_iap/clear_login_cookie`.

### What CI proves
- `pkg/ui/verifier_allowlist_test.go` (841 lines): verifier ordering, fail-closed invalid assertions, plaintext headers ignored, precedence, every allowlist entry kind, lowercasing, service-account mapping, lazy group resolution, CSRF.
- `pkg/ui/auth_method_test.go`, `tests/security/identity_test.go`, `ui/e2e/iap-header-logout.spec.js` (badge, menu, logout redirect with a stubbed identity), `PageHeader.test.jsx`, `App.test.jsx`, `AccessSection.test.jsx`.

All of it uses an in-process validator or a stubbed identity. Nothing starts a real `grain daemon` with `-ui-iap-audience` and a keys URL and sends it signed JWTs.

### What is NOT proved
1. **The real flag path.** A `grain daemon` started with `-ui-iap-audience=<aud> -ui-iap-issuer=<iss> -ui-iap-keys-url=http://127.0.0.1:<p>/jwks` against a local JWKS server whose key you hold. Sign ES256 assertions yourself (`X-Goog-IAP-JWT-Assertion`). Check, each with `curl`: valid assertion and no access code → 200; expired, wrong audience, wrong issuer, unknown `kid`, bad signature → 401 and a `logRefusedAssertion` line naming why; no assertion → access code still required; a plaintext `X-Goog-Authenticated-User-Email` alone → not admitted.
2. **The allowlist, end to end.** Defaults (owner plus grain's service accounts) admit those and refuse another `user:`. Then `user:`, `domain:`, `serviceAccount:` entries, mixed case in the token and in the flag. A `group:` entry with no Cloud Identity reachable must refuse cleanly and say why, not hang or admit. A malformed flag value refuses to start the daemon with a message naming the entry.
3. **What a verified caller becomes.** A comment, a close and a settings save made by a verified human are attributed to that email (task thread, `task_event` from §5, audit log); a `*.gserviceaccount.com` caller shows as a service principal.
4. **CSRF in a real browser.** With Playwright sending the assertion header on every request (`extraHTTPHeaders`), a same-origin POST from the UI works. The same POST with a foreign `Origin`, or a cross-site form post, is refused. GETs are unaffected. The access-code path (no assertion) is not newly broken by the CSRF check.
5. **Badge, menu and logout** at 1440 and 390 px, light and dark: the email badge sits in the header rail without overflow on a long address, and Logout lands on `/_gcp_iap/clear_login_cookie`. With no verifier configured the badge is absent and the access-code login still works.
6. **Break-glass precedence.** A verifier registered with access-code precedence: a request carrying both a valid access code and an invalid assertion is admitted by the code, and only for that verifier.

2. Run the `curl` matrix of "not proved" 1, 2 and 6, recording status codes and log lines in a table.

## §2. The Director's writable grain/config checkout and `propose_config_change`

### What changed (PR #334, task 1595)
- **Writable checkout** (`f0e2ed5c`): a session holding grain/config in its Writes gets a pushable clone at `/home/debian/grain-state` with a git identity, and its prompt explains the edit-then-propose workflow. A session with read access only keeps the disabled push URL. The git proxy grants such a run its own proposal branches, `refs/heads/grain/config/<task-id>/*`; `main` and every other task's branches stay refused (`Store.GitConfigProposalPrefix`).
- **`propose_config_change`** (`8e7d7da7`, `pkg/mcp`): commits and force-pushes the session's edits to `grain/config/<task-id>/<slug>` and calls the internal `POST /api/tasks/{id}/config-change`. The `StateManager` diffs the branch against main and validates the merged tree (`staterepo.ValidateCandidateConfig`, with a conflict check). The result is stored as `Observation.PendingConfigChange` (schema 79), pinned to the pushed head. The finish posts a comment describing it and parks the task, as `request_secret` does; the in-process session loop stops on it too. Notification and standing-task wakes leave such a task alone.
- **Approve / reject** (`POST /api/tasks/{id}/config-change/approve|reject`): internal routes that refuse external agent tokens and any caller that is not a person. Approve checks `headSha` against the pending change and the live branch tip (409 if either moved), re-validates against today's main, merges exactly that commit, deletes the branch and runs `StateManager.Sync` before the session wakes. Reject deletes the branch. Both clear the pending change and post the decision as the person's comment, which wakes the session.
- **UI** (`4c7d2542`): `PendingConfigChange.jsx`, an inline approval card in `TaskChat` (interactive sessions such as the Director) and in `DetailOverlay` for any task.

### What CI proves
- `pkg/mcp/config_change_tool_test.go`, `pkg/daemon/config_change_test.go`, `pkg/ui/task_config_change_test.go`, `pkg/orchestrator/config_change_park_test.go`, `ui/src/components/detail/PendingConfigChange.test.jsx`: the tool's push and call, validation, parking, the person-only gate, the 409s, reject.

### What is NOT proved
1. **A real session's checkout through the real git proxy.** In a Director session on a `grain daemon` with an internal grain/config repository: `/home/debian/grain-state` exists, `git push` to `grain/config/<task-id>/x` works, and a push to `main`, to `grain/config/<other-task>/x` or to any other branch is refused with a message saying why. A session holding grain/config only in Reads cannot push at all.
2. **The whole loop in the browser.** The session edits a setting file (e.g. `settings/new-task-form.yml` or a schedule), calls `propose_config_change`, parks; the card appears in `TaskChat` and on the task page with the diff and validation result; a person approves; the change is applied (`grain settings` / the Settings page show it) before the session's next turn, which is told the decision.
3. **Every refusal a person can meet.** An invalid tree (bad YAML, an unknown key) is refused at propose time with the validator's message, not parked. Main moves between propose and approve in a way that conflicts → approve re-validates and refuses with a clear message. The session pushes again after proposing → approve returns 409 and the card says the head moved. Reject deletes the branch (`git ls-remote`) and the session is told.
4. **Who may approve.** The session itself, another run with `tasks:write`, and an external agent token calling approve/reject are all refused (403/validation error) and the task stays parked; only a person in the browser can approve.
5. **Parking.** A notification wake, a standing-task wake or an unrelated comment does not un-park the task while the change is pending; a daemon restart keeps the pending change and the card.
6. **The card's layout** at 1440 and 390 px, light and dark, with a long diff.

### Walkthrough & test procedures
1. Start a `grain daemon` with a data dir, an internal grain/config repository and a run host (shared step 3); open the Director (or a chat session granted grain/config in Writes). Use the stub framework if no agent credential exists, scripting the edit, the push and the tool call.
2. Do "not proved" 1–5 in order; record `git` transcripts, API status codes, `sqlite3 … 'select pending_config_change from task_observation where task_id=…'`, and the Settings page before and after.

## §4. Merge walk without ordering, Retry lifting an operator's stop, and the base-repair bypass confirm

### What changed
- **No ordering between pull requests** (PR #415, `1f869bc4`): `mergeWalk` has no heads, holds or passedOver. Every member that passes the merge predicate merges, up to `max_merges_per_repo` per lane per cycle; a hand-off to GitHub's own merge queue counts as a merge. A pull request is re-read before the second and later merges into a lane in one cycle. A lane closes only after a merge whose effect is unknown. Rows show each member's own blocker ("merges next cycle: this cycle's 1 merge into <repo> <base> is used (task N merged)"), UNKNOWN/PENDING rows say for how long (`waitclocks.go`), and nothing says "behind task N" any more. `docs/merge-queue-behind.md` explains it.
- **Retry on a stopped turn** (PR #416): Retry (API, UI and agent API) now resumes a turn an operator stopped; only a person's Retry may lift a stop (agents get a validation error). Retry on an operator-paused task names Resume. A stopped repair at the head of a queue no longer keeps its place and CI priority for the six-hour repair deadline. `grain task list` shows "(stopped by operator)", `--stalled` leaves it out, and the backlog counts stopped turns on their own line.
- **Confirm before base-repair PRs bypass human gates** (PR #356): turning the switch on (repo page's Merge queue tab and Settings → Repositories) asks first.

### What CI proves
- `pkg/orchestrator/mergewalk_test.go`, `mergerecheck_test.go`, the inverted ordering tests, `tests/e2e/mergequeue_lanes_walkthrough_test.go`, `TestRetryOfAStoppedTurnIsAPersonsToMake` and PR #416's tests, `ui/e2e/merge-on-green-base-repair-walkthrough.spec.js`.

### What is NOT proved
1. **The merge queue page as a person reads it** on `grain demo -github-sim -fake-ci`: three or more green PRs into one repo with `max_merges_per_repo=1` merge one per cycle, each row naming the cap; with `2`, two merge in one cycle and the second is re-read (watch the sim's request log). A PR whose mergeability is UNKNOWN, one with a check that never reports, and one conflicted, in front of green ones, hold only themselves and show "for Nm".
2. **Two merges that conflict with each other in one cycle**: the second, re-read against the moved base, is not merged and says why.
3. **Lane independence**: two repos (or two bases) each merge up to their own cap in the same cycle.
4. **Stop then Retry in the browser**: stop a running turn, see the task's state and its queue row say it waits on a person, press Retry; the task dispatches at once. Retry by an agent token is refused and the task stays stopped. A stopped base-repair at the queue's head is moved off and the next member merges well before the repair deadline.
5. **The confirm**: both switch locations ask, Cancel leaves it off (reload to check), OK turns it on, and turning it off does not ask.

1. `grain demo -github-sim -fake-ci -reconcile 2s`; build the PR set through the sim's `/api/e2e/github-sim/...` hooks and the demo API. For 4 use `consolerestserver` or a daemon with a run host (shared step 3).
2. Watch the repo page's Merge queue tab (`/repos/<owner>/<name>/settings/merge-queue`) and the task rows with Playwright at 1440 and 390 px; capture each row's note text per cycle.

4. Pin gaps as Go tests in `pkg/orchestrator` or Playwright specs.
5. Record in `docs/test-runs/2026-11-02-merge-walk-retry.md`.

## §5. Who closed or reopened a task — `task_event`, grain's own closes, and the timeline

### What changed
- **PR #242** (`b5175e84`, `4cd87097`, `cb4b569d`): `Client.setClosed` records each close and reopen that changes a task as a `model.TaskEvent` in the new `task_event` table: the actor (person, session/API grant acting as its task's agent, external agent token, or the deployment), time, optional `reason` (on the close/reopen bodies, or the agent API's `X-Grain-Acting-Reason`) and what the close cancelled. The timeline renders "Reopened" and a meta line ("by human bob · cycling in-flight tasks · cancelled run 1920-1 …"). `/api/pipeline/changes` includes closes; `grain get` and the MCP task views show them. Inferred requeues inside a closure are dropped.

Release-triage closes keep the triager's principal. Restarting or deleting a console session in the UI records the caller.

### What CI proves

## §6. New Task from a template, the board's form layer, and priority on every surface

### What changed
- **PR #410** (`f721e777`): a template's page has "New task from this template", opening the form on that template (and its bound repo). The form draws a Template picker whenever it was opened on a template or the deployment configures a `templates:` layer in `settings/new-task-form.yml`; switching re-applies the layer's defaults to untouched fields. ## §7. The sandbox `grain` CLI and namespace

### What changed
- **Strict flags** (PR #330): every sandbox command names the flags it reads; anything else, or a non-integer count, is `grain <cmd>: unknown flag --x (flags: ...)` with exit 2 before the proxy is asked. An unknown subcommand prints that command's sandbox help and exits 2; an unknown top-level command inside a sandbox gets the sandbox help. `--lines N`/`-n N` for the last N lines on `read`, `ci log`, `task prompt`, `task transcript`; `task transcript` reports the whole file's size on stderr.
- **Bytes** (PR #318): `--tail` counts bytes in `grain log`, `read` and `ci log`, and the help says so. `grain log` reads are audited as the reading task.
- **`deploy://pipeline-changes` paging** (PR #382): `grain read` takes `--cursor`/`--since` and `--page` for that URI only; the page ends with the exact next command. The tool-budget notice is worded per surface.
- **`src://core`** (PR #252): a daemon built on a module that requires core serves core's source under `src://core/...` and underneath the layer (union listings, layer wins); a miss names the core module@version and how to get it. Lookup order: `/usr/local/share/grain/core-src`, a local replace, the module cache.
- **`grain ci wait` follows a superseding run** (PR #335); **`grain task list` lists repo-granted siblings** (PR #371); **`resume_later`'s condition** is read back past grain's own notices (PR #248).

### What CI proves
- `pkg/sandboxcli/{flags,sandboxcli,task_list,actions}_test.go`, `TestTailHelpSaysBytes`, `TestSandboxGrainLogReadIsAuditedAsItsTask`, `pkg/namespace/{coresrc,namespace,stage2}_test.go`, `pkg/daemon/sandbox_namespace_test.go`, `pkg/gitproxy/cli_wait_ledger_test.go`, PR #248's `pkg/mcp` test.

### What is NOT proved
1. **The real in-sandbox binary** against a daemon's git proxy (`grain demo -git-proxy`, or a daemon with a run host — see `docs/test-runs/2026-10-31-sandbox-grain-cli/` for a harness to reuse): sweep every sandbox command with an unknown flag, a bad count, an unknown subcommand, and `--lines`/`--tail`; record exit codes and that no proxy request was made for a usage error.

3. **`src://core` in both builds**: on core's own `grain demo`, `src://core` behaves as documented for core itself; on a layer-like build (a scratch module that requires `github.com/ai-on-gke/grain` with a `replace` to the checkout), `grain ls src://pkg`, `grain ls src://core/pkg`, `grain grep` across both and a miss's message.
