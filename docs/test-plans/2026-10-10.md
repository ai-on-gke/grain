## 1. Multi-Host Forge API Clients and Plain-Git Host Refusal Handling

**Commits:** `607b5db86`, `b757cafbc` (ported from `main` `ea3b23a35`, `114b3ccc6`)  
**Design Document:** `docs/git-hosts.md` (Phase 3)  
**Origin Tasks:** task 2320, task 2365, task 2771

### What changed
- **Dynamic Forge API Clients and Transports per Host:**
  - In `pkg/daemon/mcpserver.go`, `repoTransport()` resolves repository host credentials via `credentials.SelectForRepoOn(host, owner, repo)`.
  - Determines forge API endpoints via `credHost.APIBase()`, dynamically routing GitHub Enterprise instances to `/api/v3` or github.com to `api.github.com`.
  - Respects `defaultHost` when a repository has no explicit host (`b757cafbc`).
  - Wire transport TLS settings adapt via `credHost.UseTLS()` and daemon `insecureHTTP`.
- **Clean Plain-Git Host Refusal Semantics:**
  - On plain git hosts (where `credHost.Kind == model.GitHostGit` or `APIBase()` reports no forge API):
    - MCP tools (`PullRequestReader`, `issueReader`, `githubDefaultBranchReader`) refuse requests with clear diagnostic explanations (e.g. `"repository ... is on a plain git host with no pull request or CI checks API"`).
    - `QueryMergeQueue` reports `mcp.MergeQueueReport` with `Paused: true` and diagnostic `PauseInfo` stating merge queue is unavailable for plain git hosts.
    - In `pkg/orchestrator/pullrequest.go`, `OpenPullRequestForTask` inspects `github.GitOnlySource` and cleanly refuses PR creation.
    - In `pkg/orchestrator/finish.go` (`salvagePushedBranch`), tasks whose pushed branches target plain git hosts finish cleanly without opening a pull request, recording an explanatory note on the task: `"Branch <branch> pushed to <repo>; no pull request opened because <host> is a plain git host."` and observing task completion.

### What CI proves
- Unit tests in `pkg/orchestrator/pullrequest_test.go` test PR creation refusal on git-only repositories.
- `pkg/daemon/team_token_source_test.go` exercises `repoTeamCredential` lookup with host parameter.
- `gitproxy` and `model` tests verify `NormalizeGitHost`, `SameGitHost`, and `HostOf`.

### What is NOT proved
- End-to-end task lifecycle on a plain git repository: dispatching an agent task targeted at a plain git host, pushing commits via `gitproxy`, and verifying that `salvagePushedBranch` completes the task cleanly with the explanatory note on the task card without throwing errors.
- MCP server tool responses in a running sandbox session targeting a plain git host: verifying that calls to `pull_request_status`, `wait_for_checks`, and `query_merge_queue` return the expected refusal sentences and paused merge queue status rather than unhandled panics or 500 errors.
- Default host fallback behavior when repositories omit the host component in mixed-host environments.

### Walkthrough procedure
1. Configure a mock plain git host in `gitproxy` or local test harness (kind `git`, no forge API base).
2. Create a test repository referencing the plain git host (e.g. `git.local.internal/test/repo`).
3. Exercise MCP server tools:
   - Call `PullRequestReader` against the plain git repo; verify error message indicates plain git host with no PR API.
   - Call `QueryMergeQueue`; verify report returns `Paused: true` with explanatory `PauseInfo`.
4. Create a task targeting the plain git repository.
5. In the task sandbox, make a commit and push to the task branch via `gitproxy`.
6. Conclude the task execution and trigger orchestrator branch salvage (`salvagePushedBranch`).
7. Verify the task state transitions to completed, no pull request is attempted, and the task detail card displays the note: `"Branch ... pushed to ...; no pull request opened because git.local.internal is a plain git host."`.

## 2. CLI `grain version` Subcommand and User Settings Version Display

**Commits:** `7f7564082` (ported from `main` `4c3c9e526`)  
**Origin Task:** task 2777, task 2811

### What changed
- **CLI `grain version` Subcommand:**
  - Added `version` subcommand in `cmd/grain/version.go` registered in `cmd/grain/main.go`.
  - Supports standard human-readable output (`release · revision[-dirty] · timestampZ`) or `dev (unstamped)`.
  - Supports `-json` flag outputting structured JSON with fields `release`, `revision`, `committedAt` (RFC 3339), and `modified` (boolean).
- **Settings Overlay Version Display:**
  - Added Version display section to user Settings dialog (`ui/src/components/SettingsOverlay.jsx`), tagged with `data-testid="settings-version-display"`.
  - Formats version from `config.version` matching CLI formatting rules, displaying either formatted stamp or `dev (unstamped)`.
  - Allows users to inspect deployment version directly from anywhere in the UI regardless of sidebar scroll position.

### What CI proves
- Unit tests in `cmd/grain/version_test.go` test unstamped, stamped, dirty, and release-only formatting, plus `-json` CLI output capture.
- Vitest tests in `ui/src/components/SettingsOverlay.test.jsx` test version rendering in settings dialog with stamped and unstamped configs.

### What is NOT proved
- Live CLI execution against built `grain` binary in a real Debian environment, testing exit codes, stdout, stderr, and invalid flag handling.
- End-to-end browser walkthrough: launching `grain demo`, opening user Settings overlay, verifying visual positioning, monospace typography, contrast, and consistency between `/api/config` and the UI display.
- Version consistency: verifying that the version displayed in the UI Settings dialog matches the output of `grain version -json` from the daemon host.

### Walkthrough procedure
1. Launch `grain demo -addr 127.0.0.1:0 -open=false`.
2. Build and run CLI:
   - Run `grain version`; verify output format matches `release · revision · time` or `dev (unstamped)`.
   - Run `grain version -json`; verify valid JSON structure parsing with `jq`.
   - Run `grain version -invalid`; verify non-zero exit code and usage information.
3. Launch Playwright browser session against `grain demo`.
4. Open the User Settings dialog via sidebar avatar/gear button.
5. Locate the Version section (`[data-testid="settings-version-display"]`).
6. Verify version text matches `/api/config` version payload and renders cleanly with monospace font.
7. Verify dialog close, escape key, and responsive layout across mobile and desktop viewport sizes.

## 3. Automated Version Upgrade Testing Harness

**Commits:** `6bbe8594a`, `ce3789180` (ported from `main` `1e0d3e0f2`, `3ccfcdef6`)  
**Origin Tasks:** task 2817, task 2821

### What changed
- **Version Upgrade Container Test Suite:**
  - Added `tests/container/version_upgrade_test.go` (`TestUpgradeFromPreviousVersion`) to verify daemon, database, task, and state-repo upgrades.
  - Automatically identifies previous release version tag via `resolvePreviousVersionTag()` (`git tag -l "v*"` excluding `-rc`, fallback `v1.7.0`).
  - Spins up daemon running previous baseline version image with populated tasks and comments.
  - Triggers upgrade via `POST /api/upgrade` to target test image (`GRAIN_TEST_IMAGE`).
  - Verifies upgrade phases: image pulling, digest pinning in `image.env`, restart signal creation in `control/restart`.
  - Restarts daemon on new image and verifies data integrity: existing tasks, comments, task listing, and health checks survive without regression.
  - Fix in `ce3789180`: queries `/api/sandboxes` for daemon health and sync verification instead of non-existent `/api/health`.
- **Nightly CI and Makefile Integration:**
  - Added `make test-upgrade` target in `Makefile`.
  - Added `upgrade-test` job in `.grain/workflows/nightly.yml` (4 CPUs, 16GB RAM, 60GB disk, 30-minute timeout).

### What CI proves
- Compilation and unit structure of `version_upgrade_test.go`.
- Makefile target invocation syntax.
- Endpoint validation: `/api/sandboxes` replaces 404 `/api/health`.

### What is NOT proved
- Execution in real multi-version environments where database migrations have occurred between major/minor schema versions.
- Clean rollback behavior if an upgrade image fails post-restart health checks.
- State-repo git three-way reconciliation across version upgrades with concurrent live tasks.

### Walkthrough procedure
1. Validate `make test-upgrade` prerequisites and flag validation in a local Docker test environment.
2. In a simulated upgrade scenario:
   - Initialize baseline SQLite store with known legacy task and team entities.
   - Execute upgrade sequence via `/api/upgrade`.
   - Verify `/data/control/restart` trigger file is created.
   - Start updated daemon binary against the existing SQLite directory.
   - Query `GET /api/sandboxes` and verify HTTP 200 OK with healthy daemon sync state.
   - Query `GET /api/tasks` and verify all legacy tasks and comments are preserved intact.
