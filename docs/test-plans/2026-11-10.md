## Branch situation & how follow-up tasks should handle it

Releases are cut from `main` by the continuous train (`.grain/settings.yml`, `scripts/release.conf`). From PR #1045 the train releases **at most once per Pacific calendar day** (`RELEASE_MAX_PER_DAY=1`, `RELEASE_DAY_TZ=America/Los_Angeles`) and keeps cutting `rc.N` of the next version from `main`'s newest known-good commit until one qualifies. There is no `release/vX.Y.Z` branch for the current line any more (`bb7836ba`). A `fix:` a walkthrough lands on `main` therefore ships with the next rc and needs **no backport task**. The only exception is a defect the operator asks to patch on an older line (`release/v3.1.1` still exists).

Every follow-up walkthrough task filed from this plan targets `main` (`repo: "ai-on-gke/grain"`, `branch: "main"`) and depends on [Task #3930](/tasks/3930), so `docs/test-plans/2026-11-10.md` is on `main` when each walkthrough begins. Each proposal asks for unattended `auto_merge: true` once CI is green. The operator who approves the proposal decides whether to grant auto-merge on `main`.

The gate is **GitHub Actions**: `Tests` in `.github/workflows/tests.yml`, `plc-tests.yml` when `grain-plc/` is touched, `cla/google` and the workflow/hygiene scans. Inside a sandbox, open the PR and wait on its checks with `grain pr open` and `grain ci wait` (with `timeout: 600000`, no `--jobs` flag). Do not rely on the MCP `pull_request_status`, `base_branch_status` or `wait_for_checks` tools on `hostd`/`runhost` sandboxes, and never chain `grain pr status` ahead of `grain ci wait`. If a check is already red on `origin/main` before your branch touches it, merge `origin/main` and report the breakage rather than weakening the check.

## §1. Token usage and budgets

### What changed
- **Recording** (`eecb480f`): each framework's CLI usage report is parsed into `agent.TokenUsage` on `agent.Result` (claude's `result` event with input/output/cache read/cache write and `total_cost_usd`; codex's `turn.completed`; agy's `result`), summed across re-execs and continued turns. Migration 130 adds `task_run_usage` (per run, keyed by connection, model, framework, host and task), `usage_capacity` (what a window had consumed when its provider refused it) and `usage_setting` (budgets, concurrency mode, retention).
- **Estimation** (`3b96af9a`, `pkg/usage`): a per-connection/model budget report gives usage in the window, remaining budget, reset, burn rate, run-out time and the workers the remainder sustains. A pause that opens records its window's consumption as that window's learned capacity. The mode is `advisory` by default, which changes nothing about dispatch. `auto` lowers the dispatch worker limit to the estimate within `[minWorkers, max_workers]`, and `off` disables the estimate.
- **API & CLI** (`159292a1`): `GET /api/usage`; `PUT /api/usage/settings` (mode, automatic-cap floor, retention, budgets; recorded in the config audit); `grain usage [-mode] [-min-workers] [-retention-days] [-budget conn[/model]=tokens/window]… [-clear-budgets] [-json]`. Task detail carries each attempt's usage and the task total.
- **UI** (`e07c18fa`, `612b77f8`): a Token usage and budgets card in Settings → Models (learned limits marked `~`), tokens per attempt on the task timeline and the task's total above it. `docs/connections-and-models.md` documents it, and the demo seeds figures.

## §2. Access administration by verified admins, access history, and limited roles' approval ceiling

### What changed
- **Verified admins manage other admins** (`f69f2e1f`): a signed-in person (IAP or another verifier) whose role holds every scope of an entry's current and new role may now assign, change and remove roles that hold a dangerous scope or deny scopes on other entries. Each such change needs a reason, recorded in `config_audit` (old role, new role, reason, who, when). The following are still refused:
  - agents and delegated requests;
  - widening, or adding or lifting a deny on, an entry that matches the caller (their `user:` entry or a `group:` they are in);
  - removing or narrowing the last `user:`/`group:` entry with a full role (`last_admin`, which names the access code as recovery).

  Narrowing a matching entry needs `confirmSelf` (`?confirmSelf=1` on DELETE). DELETE also takes `?reason=`.
- **CLI** (`c18be18e`): `grain access role` and `grain access deny` take `--reason` and `--confirm-self`.
- **History** (`8929db5a`): `GET /api/access/history` (`access:read`) lists the `config_audit` rows whose surface is `access`. Role choices say whether a role denies scopes.
- **UI** (`406d9924`): Settings → Access opens a reason panel (replacing `window.prompt`), shows the server's refusal on the panel, retries with `confirmSelf` on `confirm_self`, and gains an Access history card.
- **Hardening** (`7cdd1c8f`):
  - a POST on an entry matching the caller is refused (`self_escalation`), closing the DELETE-then-POST bypass;
  - group entries fail closed with no group checker;
  - agents get 403 even on an idempotent POST;
  - CR/LF in reasons are flattened.
- **Limited roles' approve/run-now** (`6875630e`, `48cb44f2`): approving, or running now an unapproved task, needs `tasks:admin` on its repository. It is held to the rules filing would apply: `autoMerge`, `keepRunning`, admission, each grant, the config-repo hold, network widening, reads/writes reach, and the task's **review template**, unless that is the repo's default review template.

## §3. Unified grants: canonical references, repository grants in GrantsPicker, held bare ids, proposal rails

### What changed
- **Canonical writes** (`4a0d3155`, slice 3 of `unified-grants.design.md`). Every grant writer (`pkg/model`, `pkg/repodecl`, `pkg/ui`, `pkg/cli`, `pkg/orchestrator`) now records:
  - `https://grain.dev/capabilities/api#<scope-or-preset>`, plus `={"repo":"<owner/name>"}` when it is repository-limited;
  - `https://grain.dev/capabilities/repo#read` and `#write`.

  These replace `api:<scope>[@repo]` and `repo-read:`/`repo-write:`. `model.CanonicalGrant` still reads the legacy spellings from unmigrated rows. `protocol.ValidMethod` accepts `.` and `/` segments, so slash-grouped scope sets like `ops/triage` list as methods. This reverses the previous plan's "storage is `api:`" expectation.
- **Policy & sync gaps** (`ce4a7094`): `CapabilityPolicy` is enforced on API grants at admission even with no pass-minting reference. Console session defaults, `DeclinedDefaults` and session-sync snapshots match by `CanonicalGrantKey`, so the spelling change never re-attaches a declined grant. Local daemon policy matches both spellings.
- **Repository grants in GrantsPicker** (`b5517814`, `aaf05ffc`, slice 5): reads and writes become lines of the Grants list on the New task overlay, the task pane's Access section, the template and schedule editors and the console session page. "Add grant…" → "Repository access" lets you read or write a repository. Held lines render as `owner/repo · read` and `owner/repo · <base> · write`. The task's own repo shows as a fixed `…/repo#target` line, and a template's `push:` refs are read-only. API bodies are unchanged.
- **Held bare ids** (`f4b4b649`): a bare capability id an object holds (e.g. `self-debug`) is now a removable line wherever `GrantsPicker` is shown. `CheckCapabilityGrants` reports `AliasOf`.
- **Proposal rails** (`d76d2791`, `2570f150`, `bac5ad1a`):
  - retired bare aliases are expanded on relayed proposals, default task grants and proposal seeding;
  - person-only non-reference grants (`api:self-upgrade`, `api:secrets:write`) are refused in `GrantsSubsetOf`, so an auto-merge parent cannot auto-submit a child asking for one;
  - escalation counts them regardless of `Via`, including on console sessions and the director.
- **`propose_task` argument validation** (`663e99ee`): undeclared arguments (`base`, `description`, `fields`, camelCase, typos, `writes[].branch`) are refused live and at run end, naming the nearest declared argument.
- **Declarations** (`d45aa842`): `repo#target`, and `repo#read`/`#write` carrying `base`, are refused at parse time. The whole sync fails and the previously synced declarations stay live, with `repo_declaration_sync.last_error` set.

## §4. Schedules on grain CI in a `ci_mode: github` repository, the weekly dead-code scan, and `nothing_needed` finishes

### What changed

## §9. Dispatch: Run now spent by a parking run, early wakes, and `grain ci test-history` on GitHub Actions

### What changed
- **Run now** (`ba4e06aa`, `c9951341`): a Run now request is given back only by suspensions that stopped the run before it could work: setup, restart, operator pause, OOM, usage limit, capacity, model and capability (`SuspensionKind.KeepsRunNow`). `requested` (resume_later), deadline, idle and context suspensions spend it, and a run withdraws any stamp no newer than its own start. `Store.Init` clears stale stamps left by older builds. The task pane keeps Run now enabled for a stale request (`runNowStale`), and its hint names the real hold.
- **Early wakes** (`4e47815f`): `SuspensionResumeAt` ignores the agent's own `SuspendRequested` suspension, so a `resume_later` with `{at, message: true}` (or `ci`, or a task) woken early by a message, CI verdict or Undefer is dispatched at once.
