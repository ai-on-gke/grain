## §1. Numeric task priorities — dispatch order, every filing surface, and the `priority` / `priorityDispatch` split

### What changed
- **Model and dispatch** (`98eb06ac`, PR #285): schema 73 adds `task.priority` and `template.priority`; `DefaultTaskPriority = 5`, and a higher number dispatches first. The orchestrator's queue and dispatch ordering use it, and sync and finish carry it onto follow-ups. It is wired through the REST API (`POST`/`PATCH /api/tasks`), MCP `propose_task`, the agent API, `grain task propose --priority` (host CLI and sandbox CLI, non-negative integers only), `.grain/templates/*.yml` (`repodecl`), `declschema` and composed work.
- **UI** (`98eb06ac`): New Task has a priority field; the detail pane, Edit task form and `Declared` show it; `TaskList` shows non-default priorities.
- **Hardening** (`42d25d37`): `tasksAdminTaskPatchBodyAllowed` fails closed on an empty or non-object `PATCH /api/tasks/{id}` body. `readJSONLimit`, `readAttachmentJSON` and `readOptionalJSON` reject trailing JSON after the first value, so a concatenated payload cannot smuggle fields past the agent gate. A refused repo-scoped grant names `tasks:admin`. Negative priorities are refused on templates and on declared templates.
- **Wire split** (`36e09cbd` PR #296, `a55ffd96` PR #297, `e9c423b8` PR #295): PR #273 and PR #285 both added `UpdateTaskRequest.Priority`, a `*bool` for priority-dispatch and a `*int` for numeric priority. Numeric is now `priority`. The capability toggle is `priorityDispatch` / `priority_dispatch`; a boolean `priority` is still accepted for it. A numeric edit is allowed under `api:tasks:admin`; a boolean toggle still needs `capabilities:admin` and human authority.

### What CI proves
- `pkg/ui/task_priority_test.go`, `pkg/dispatch/dispatch_test.go`, `pkg/orchestrator/sync_test.go`, the store tests in `pkg/model/{sqlite,postgres}/store_test.go`, `pkg/cli/list_test.go`, `pkg/mcp/mock_tools_test.go`, `pkg/repodecl/repodecl_test.go`: ordering, defaults, refusals, the JSON split, and trailing-JSON rejection.
- `NewTaskOverlay.test.jsx`, `EditTaskForm.test.jsx`, `TaskList.test.jsx`, `Declared.test.jsx`: rendering in jsdom.

### What is NOT proved
1. **Real dispatch order** on a daemon with a constrained sandbox budget: three queued tasks at priorities 1, 5 and 9 dispatch 9, then 5, then 1, and FIFO holds within one priority. Nobody has checked how this interacts with priority-dispatch (§5's `Budget.AdmitsPriority`), retry backoff and run-now.
2. **Every filing surface in a browser and a live CLI**: the New Task field, the Edit form, the list badge at 1440 and 390 px, `grain task propose --priority 8`, `propose_task` with `priority`, and a template declaring `priority: 7` filing a task that carries 7. Also unchecked: whether a follow-up proposal inherits its parent's priority or defaults to 5. Record which, and check it matches the commit's intent.
3. **The wire compatibility in practice**: an old client sending `{"priority": true}` toggles priority-dispatch rather than setting priority 1; `{"priority": 3}` from an `api:tasks:admin` agent token succeeds; `{"priorityDispatch": true}` from the same token is refused.
4. **Smuggling attempts against the live server**: `{"priority":3}{"approved":true}`, a JSON array body, and an empty body, all to `PATCH /api/tasks/{id}` under `api:tasks:admin`.
5. **Upgrade**: existing tasks read back as priority 5 after migration 73, and the board, filters and sort do not treat 5 as "unset".

## §2. Configurable New Task form — `settings/new-task-form.yml`, hidden defaults, and agent filings

### What changed
- **Server** (`71ca6b37`, PR #304): schema 77 adds `grain_config.new_task_form` (`model.NewTaskForm`). It holds per-field visibility (`shown` / `more` / `hidden`), order, label, help text, defaults and options, plus the capability picker's defaults, offered list, hidden list and display overrides. Layers merge in the order default → boards → repos → templates. `settings/new-task-form.yml` is parsed with unknown keys refused, projected onto the column the way `settings/capabilities.yml` is, and exported back. `GET /api/config` carries `newTaskForm`. `staterepo.Check` refuses unknown field IDs, a hidden title, a hidden repo without a valid default, and capability defaults or offers that the catalogue does not define, keeps CI-only, or denies.

Hidden fields are not drawn and file their resolved default. Changing the repo or template re-applies defaults only to fields nobody has touched (`formEdited`).

- **Neighbours**: `e12bb80b` names the repo picker's change-target switch generically. PR #224 (`373ff903`) stops New Task filing capability defaults the catalogue refuses. PR #233 (`82966917`) says which `/new?...` link field values were left out.

## §3. Who owns a setting — `settings_locked`, the shrunken Settings page, the Config Repo Browser, and declared settings

### What changed
- **`settings_locked`** (`17fcb581`, PR #275, schema 70): the internal grain/config write refusal from the 2026-10-30 plan's §2 is now **opt-in**. By default the UI and REST API write settings even with grain/config configured, and `SyncAfterWrite` exports them at once so the next reconcile keeps them. Settings → General gains "Lock settings in UI (require config repo PRs)", and a person can always unlock it. `configRepoOnly` is true exactly when there is an external config repo, or when `settings_locked` is on and the `directConfigWrites` opt-out is unset (`design/spec/settings/settings-mutability.spec.md` §1.3).
- **Settings shrink** (`3d26e211`, PR #234): Settings leads with Models & sandboxes, Secrets & access, Preferences and System / Operations. General, Git, Repositories, Tasks, Agents, Capabilities, CI and Memory move under "Managed in config repo". A bare `/settings` opens Models, and `/admin` still lands on General. While `configRepoOnly` is set, departing sections and a repo page's config tabs are read-only, with "View in config repo → <path>" links. The Config Repo Browser is at Settings → Config repo, `/config?path=` and `/settings/config-repo/<file>`.
- **Refusal follow-through** (`76881684` PR #319, `8667a0a3` PR #310, `ac4494d1` PR #237): the editor behind a refusal settles once its config PR opens; the UI says why a held config PR was not opened; a setting's refusal banner comes down once that setting saves.

- **Health → Settings links** (`2df36db6`, PR #290): pending-restart and unrunnable settings link to their Settings card. `ac366179` and `9a8bfe7b` fix anchor scroll and Enter in the Settings filter.
- **Validation** (PR #237 `cd108d81`, `d0ec2cb8`): Kubernetes ServiceAccount, Service, Deployment, container and proxy-host values Kubernetes cannot use are refused, and so is a built-in capability server setting its own configure would refuse.

## §4. Task branch names — the slug upgrade, `MaxBranchNameLen`, and refs git cannot push

### What changed
- **Slug upgrade** (`9f7044fe`, PR #282, schema 78): a stored `task_branch_template` of exactly `grain/{deployment}/task-{id}` is rewritten to `grain/{deployment}/task-{id}-{slug}`, and the pre-78 state-repo import normalises it the same way. Existing tasks keep their frozen branch names; custom and empty templates are left alone.
- **Length** (`ba2f7674`): `ValidBranchName` caps names at `MaxBranchNameLen = 244` bytes. `FormatTaskBranchName` trims or omits `{slug}` when a long custom template leaves under `MaxBranchSlugLen` (30) bytes of headroom. `UpdateSettings` validates the template against the longest deployment and task IDs. `cc92abf3` keeps the sample task ID in the refusal message, and `cb564cfd` caps fallback PR titles for very long task names.
- **git ref rules** (`dad9910e`, PR #236): a component that starts with `.` or ends in `.lock`, and a name ending in `.`, are refused, as `git check-ref-format` refuses them.

### What CI proves

## §5. Interactive and console sessions — warm sandboxes, in-process turns, `keep_running`, live grant edits, and admission

### What changed
- **Warm sessions** (`3630419d`, PR #198, schema 66): `SessionSandboxIdleTTL` (`session_sandbox_idle_ttl_ms`, default 30 m, set in Settings → Sandboxes, `grain settings -session-sandbox-idle-ttl`) keeps a session warm in two layers:
  - **In-process continuation** (`continueSessionTurns`): on a resumable framework, the turn's answer is relayed and the run waits for the next message.
  - **Warm-sandbox fallback** (`session_sandboxes.go`): the next dispatch reuses the same sandbox ID.
  - Fixes: reuse only for an unchanged task (`d720b5dd`); release once grants change (`c921280b`); tell turns who said what (`a8ab243b`).
- **Turn correctness** (`3e94b536`, PR #246): a message posted while the turn was writing its answer is no longer marked delivered. The idle wait polls at `CancelPollInterval` and wakes on `Store.CommentAdded`.
- **Latency** (`66fc9a7c`, PR #280): `GET /api/tasks/{id}/messages?after=N&wait_ms=M` long-polls (clamped at 5000 ms). An interactive task's creation, approval or comment wakes dispatch at once (`RunDispatchCycle`). Prepare skips the package cache and grain placement on reuse. `task_run_startup` records per-phase timestamps, exposed in `Attempt.Startup`, `GET /api/metrics` and `grain metrics`. Targets: < 45 s to the first turn, < 1 s for later turns. `5145f7de` puts the target-repo and pause gates back in front of the fast cycle, and commits comments atomically with their attachments.
- **`keep_running`** (`c6855867`, PR #287, schema 74): set on tasks, templates, schedules and console sessions. A run that finishes normally re-queues at 0 s with no failure-streak increment and keeps its warm sandbox. `6b80075c`: clearing it reclaims the warm sandbox. `sessionSandboxKey` includes Target, Base, Reads and Writes. System, template- and suite-backed schedules refuse keepRunning edits.
- **Live grant edits** (`45e1fb98`, PR #273): capabilities, reads, writes, model, network access, priority, keepRunning and proposal auto-approval can be changed on an active session, even with grain/config. The detail sidebar gains one-click Model and Network controls. PR #299 `7622acf3` keeps a removed default capability off; `270f6751` (PR #243) seeds sessions with the deployment's default capabilities at creation.
- **Admission** (`6fb018d5`, PR #307): a priority-dispatch sandbox (a console session, or a task holding priority-dispatch) is refused only by the host disk floor or by no schedulable node, never by the vCPU, memory or disk ceilings, the repair reserve or the CI gate. The admission refusal names its gate.
- **Tool budget** (`678881f4`, PR #245): a chat result that carries a person's reply restarts the per-wake tool budget.

### What CI proves
- `pkg/orchestrator/interactive_latency_test.go`, `tests/e2e/interactive_latency_test.go` (startup and turn latency with a stub framework), `pkg/orchestrator/consolesessions_test.go`, the session-sandbox tests, `pkg/dispatch` admission tests, `e2707d77`'s console-session admission e2e, and `ui/e2e/session-pending-grants.spec.js`.

### What is NOT proved
1. **A real framework in a real sandbox**: a chat session on the demo's real backend, or on a `grain daemon` with an agent backend if credentials exist. If not, use the stub framework and say so. Measure first-turn and later-turn latency from `Attempt.Startup`, and confirm that the second message within the TTL reuses the same sandbox ID and does not re-clone.
2. **TTL expiry and change**: shorten the TTL to 1 m. Check that the sandbox is released after it, and that the next message dispatches fresh. Change the TTL while a session is idle.
3. **Live grant edit mid-session**: remove a capability, narrow `writes` and change the model from the sidebar while the session is warm. The warm sandbox is released (`c921280b`, `6b80075c`); its token is revoked (verify with a stale-token call through the git proxy); the next turn runs with the new grants; a daemon restart and `reconcileConsoleSessions` do not re-add a removed default (`7622acf3`).
4. **`keep_running` end to end**: a task with it on restarts immediately after a normal finish, does not restart after a question or an operator stop, and does not accumulate a failure streak. Clearing it reclaims the sandbox. A system schedule refuses the edit.
5. **Admission under a full budget**: with CI or batch tasks filling the vCPU ceiling, a console session still starts, and the refused batch candidates' log lines name their gate.
6. **Message ordering**: a reply posted during the turn's last tool call is shown to the next turn; attachments are present the moment the message is.

### Walkthrough & test procedures
1. Start a `grain daemon` with a real sandbox pool (Granule or Docker run-host, as `tests/e2e` and `GRAIN_RUNHOST_DOCKER=1` use) and a sandbox budget of 2.
2. Open a director or chat session in the browser (1440 px; then the sidebar at 390 px). Send three messages; record `GET /api/tasks/<id>` `attempts[].startup` and the sandbox IDs.
3. Do steps "not proved" 2–6 in order, recording timestamps, sandbox IDs, `grain metrics` output and log lines.
4. Pin any deterministic gap as a Go e2e under `tests/e2e/` (stub framework) or a Playwright spec.
5. Record in `docs/test-runs/<date>-interactive-sessions-warm-keep-running.md`.

## §6. GitHub Actions as a repository's CI — the ported workflows, path filters, `github_workflow_run` schedules, and Grain CI standing down

### What is NOT proved

4. **`grain ci log` on a GitHub run** from a sandbox, and `grain ci wait` against the sim's check runs.

## §10. Review, merge and failure lifecycle fixes that change what a person sees

- **Security hold** (`22af36f8`, PR #218): keyed to the task's own pull request, so a task with two on-target PRs no longer flips clearance and re-files reviews.

- **Failure streak** (`166a83d7`, PR #241): a run cancelled by closing the task or stopping its turn does not count.
- **Change-target proposals** (`c1b15f3d`, PR #260): they never inherit auto-merge, and they stop looping on setup failure.
- **Empty CL** (`20c78bc3`, `ec2b1e72`, PR #253): an empty or deleted CL outside a run moves the task to awaiting_reply instead of awaiting_submit.
- **Holds** (`1341701a`, PR #221): grain's own end-of-run holds are no longer marked as the run's `hold_for_approval`.
- **Logs** (`9a6f43c6`, PR #295): duplicate gate-waiting logs are deduplicated and carry the job identity.

### What CI proves

3. **An errored overlap re-check** (sim with no workflow answering the merge-queue ref): one CI run, then the task is blocked with the error shown on the task page; a person's retry starts exactly one more.
4. **Close and reopen** a task with a live run: no backoff, and the task page shows no failure streak.
5. **A change-target proposal from an auto-merge parent**: filed without auto-merge, and it does not loop.
