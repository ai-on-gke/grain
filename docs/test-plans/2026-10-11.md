## 1. Per-Direction `port-types` Filter

**Commits:** `0a3426079`, `8f0b6c410` (from `main` `e4ae1bbaf`, `5d6df5ee5`)  
**Origin Task:** task 3024

### What changed
- Repository settings declaration (`.grain/settings.yml`) gains `port-types`: per `"<from>-><to>"`
  direction, the conventional-commit types a merge needs for grain to port it that way. An operator
  column holds the same setting (`RepoConfig.PortTypeFilter`); a repository's declaration can narrow
  only a pair it declared itself and can only widen an operator-configured list.
- `decidePort`/`portSkip` (`pkg/orchestrator/port.go`) read the PR's own commits: port if any non-port
  commit carries one of the types (`!` and scopes included; `Revert "..."` reads as `revert`) or a
  `Port: yes` footer. `Port: no` still wins. A direction with no entry ports everything. Skips are logged.
- This repository declares `main->candidate: [fix, revert]`. `scripts/backport-triage.sh` reads the
  same list (overridable via `PORT_TYPES`), logs features missing from `candidate` as skipped, and still
  reports every type missing from `main`.

### What CI proves
- `pkg/orchestrator/port_test.go`: type matching, `!`, scopes, revert, `Port: yes/no`.
- `pkg/model/repo_config_test.go`, `pkg/repodecl/settings_test.go`: parsing and the narrow/widen layering.
- `tests/deploy/release_workflows_test.go`: the triage script's reading of the settings file.

### What is NOT proved
- A real merge through grain's merge queue on a paired-branch repository producing (or not producing)
  a port task, end to end: declaration sync → `RepoConfig` → `decidePort` → port task filed/skipped with
  its log line.
- The layering against an operator-set column through the UI/API (Repo settings), including the
  narrow-is-refused case on an operator pair.
- A PR mixing a `feat:` and a `fix:` commit, a PR whose only matching commit is itself a port, a
  `Revert "..."` merge, and malformed declarations (`main-candidate`, unknown branch, empty list).
- `backport-triage.sh` run against a real local clone with a crafted history.

### Walkthrough procedure
1. Extend the `tests/e2e/port_mechanical_walkthrough_test.go` harness (real orchestrator and merge
   queue, fake forge) with a paired-branch repository declaring `.grain/settings.yml` `port-types: {main->candidate: [fix, revert]}`.
2. Merge, via the real queue, PRs on `main` with: only `feat:`; `feat:` + `fix(x):`; `feat:` with a
   `Port: yes` footer; `fix:` with `Port: no`; `Revert "feat: ..."`; `fix!:`. Record which produced a
   port task to `candidate` and the skip log line for each skip.
3. Merge a `feat:` PR on `candidate`; verify it is still ported to `main`.
4. Set an operator-level port-types list for the pair and verify the repo declaration can widen but
   not narrow it.
5. Run `scripts/backport-triage.sh` against the scratch clone with and without `PORT_TYPES`; compare
   its "missing" and "skipped" lists to the expected sets.

## 6. Shared-Fault Circuit Breaker, Base-Transition CI Cache Invalidation, Merge-Queue Telemetry

**Commits:** `3ea13cc05` (from `main` `c3f60b23d`), `faf82f23e` (from `main` `134749818`)

### What changed
- Single-flight incident lock: at most one automated repair task per broken base branch.
- While base CI is broken, dispatch of downstream tasks and merge-queue base rebases
  (`refreshStaleHead`) pause, recorded as `BranchWaitCapability` grant waits, until the lock clears.
- CI requests and cached job runs carry `BaseCommit`; cached failures are invalidated/purged when the
  base advances or goes green, leaving unaffected passes.
- Merge-queue telemetry (batch sizes, gate latency, queue wait, rebase/retest events) in the metrics
  API's merges section; `tuning_recommendation` table and allowlist validation in the tuning runner.

### What CI proves

  `pkg/metrics/merges_test.go`, `pkg/model/tuning_test.go`, `pkg/orchestrator/tuning_test.go`.

### What is NOT proved
- The whole loop on a real daemon with real grain CI: base goes red → one repair task, others held with
  a visible wait reason in the task pane → base fixed → holds clear, queue resumes, cached red for the
  old base no longer replayed.
- Telemetry values in `/api/metrics` after real merges, and the metrics UI rendering them.
- Tuning: a recommendation with a parameter outside the allowlist is refused before filing.

### Walkthrough procedure

   was merged.
5. Feed the tuning runner one allowlisted and one non-allowlisted parameter; verify the latter is

## 7. Non-Disruptive Upgrade Drain, `interrupted` Outcome, Client Retry

**Commit:** `b660114c6` (from `main` `6d4ef2740`)

### What changed
- `grain daemon -upgrade-drain-window` (0 = wait indefinitely): scheduled upgrades wait for active tasks
  and CI runs to drain, then proceed once the window expires.
- Runs cut short by daemon shutdown record outcome `interrupted` (`model.InterruptedOutcome`), keep
  suspended session checkpoints, and do not count toward failure streaks or retry backoff.
- `pkg/ui/httpclient.go` retries transient errors with bounded exponential backoff and jitter.
- UI timeline badge/label for interrupted runs.

### What CI proves
- `pkg/orchestrator/scheduledupgrade_test.go`, `pkg/model/sqlite/store_test.go`,
  `pkg/ui/httpclient_test.go`, daemon help golden.

### What is NOT proved
- A real daemon restart mid-run producing `interrupted` (not `failed`), the task's failure streak
  unchanged, the badge in the task timeline, and the task resuming afterwards.
- Drain behaviour with a short window on a real scheduled upgrade (logs, timing).
- CLI commands (`grain task ...`, `grain user list`) riding out a daemon restart via retry, and not
  retrying non-idempotent requests in a way that duplicates them.

### Walkthrough procedure
1. Run a daemon (demo or `grain daemon` with a stub agent) with a long-running task; SIGTERM the daemon.
   Restart; verify the run's outcome is `interrupted`, the failure streak/backoff is unchanged, and the
   Timeline shows the interrupted badge (Playwright).
2. Configure `-upgrade-drain-window 30s` and trigger a scheduled upgrade with an active run; record
   that it waits and then proceeds; repeat with 0 and a run that finishes.
3. While restarting the daemon, run a CLI read loop and a single `POST` (e.g. adding a comment); verify
   reads succeed after retry and the POST is applied exactly once.

## 11. Security Hardening

**Commits:** `348a146d1`, `07f95f71e`, `b706b7a27`, `c3a112ded`, `de3880a64`, `6bff86334`, `ed017ffbb`

### What changed
- Model proxy: Gemini forwards only `GET models`, `GET models/<name>`, and `POST models/<name>:<action>`
  for `generateContent`, `streamGenerateContent`, `countTokens`, `embedContent`, `batchEmbedContents`;
  OpenAI `/v1/responses/{id}/input_items` refused, retrieve/cancel/compact/input_tokens kept.
- Git proxy spools `git-receive-pack` bodies over 16 MiB to disk and deletes them; pack parsing bounds
  zlib output and delta destination sizes at 32 MiB.
- Sandboxnet server: `ReadHeaderTimeout` 10s, `IdleTimeout` 60s.
- `registry-push` defaults to admin teams; `registry-push` and `image-signing` are widenable in
  Settings → Capabilities.
- `golang.org/x/net` bump for GO-2026-6617; daemon-attached MCP tool roster held to grants.

### What CI proves
- `pkg/modelproxy/proxy_test.go` refusal cases; `pkg/gitproxy/{spool,pack,forward,local}_test.go`;
  `tests/security/capabilities_test.go`; `tests/security/mcp_tools_test.go`.

### What is NOT proved
- The model proxy as a running daemon serves it: a real sandbox token calling each refused route gets
  a refusal (and the allowed ones reach a stub upstream).
- A real `git push` of > 16 MiB through the proxy succeeds, leaves no temp files, and memory stays
  bounded; a crafted pack bomb is refused without the daemon dying.
- Slowloris against sandboxnet: a dripping client is cut off at ~10s while normal clients work.
- Settings → Capabilities shows `registry-push`/`image-signing` as widenable; a non-admin team has no
  `registry-push` until widened.

### Walkthrough procedure
1. Start the daemon's model proxy against a stub upstream; issue the refused and allowed requests with
   a run token; record status codes and what reached the stub.
2. Through the git proxy on a scratch repo, push a 40 MiB commit; watch `$TMPDIR` and RSS; push a
   crafted delta-bomb pack; verify refusal and daemon health (`GET /api/sandboxes`).
3. Open a raw TCP connection to the sandboxnet listener and send one header byte per second; verify
   the server closes it near 10s.
4. Playwright: Settings → Capabilities; widen `registry-push` to a non-admin team; verify the team's
   capability view before and after.
