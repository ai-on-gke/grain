## 1. Capability Servers: Configuration, Attach, API, CLI and Settings Card

**Commits (main only):** `146c07ef2`, `e7c5b7a09`, `357e5a904` (#4388, protocol), `388f488b6` (protocol review fixes), `7569392bd`, `3b3ce61b0` (in-tree servers), `0e6640377`, `af8edd8e3`, `7e8a1422e`, `0fc7d1b50` (#4425 and follow-ups; schema 29)

### What changed
- **Protocol (`pkg/capability/protocol`, `146c07ef2`):** Grain's side of the MCP capability protocol in `docs/capabilities-spec.md`:
  - capability references (`<capability_id>[#<method>]`);
  - grants in bare, object and CLI forms, with `with:` args validated against each method's JSON-schema;
  - the `mcpServers` entry shape (stdio `command/args/env` or HTTP `serverUrl/headers`), with `$secret:<name>` resolution;
  - a stdio and Streamable-HTTP MCP client, discovery of `mint_*`/`release_*` tools, mint-response validation, and the all-or-nothing admission pass;
  - `protocol.NewMethod`/`CapabilityServer` for writing servers in Go.
- **Review hardening (`388f488b6`):**
  - `ServeHTTP` answers 401 to everything when the token is missing or shorter than 32 bytes.
  - Unsupported JSON-schema keywords are refused rather than ignored. `allOf/anyOf/oneOf/not` and the bounds keywords are now enforced.
  - The HTTP client never follows redirects.
  - Placements may not land on `.claude.json`, shell start-up files, `.git-credentials`, `.gitconfig` or `.github-sandbox-token`.
- **In-tree servers (`7569392bd`):** `grain capability <gcp|self-debug|git|model-proxy|skill> [flags]` serves one server over stdio. Each reads its root credential only from its environment, and leases are revoked at deadline plus grace (`RunExpiry`) and on shutdown (`ReleaseAll`).
- **Storage and registry (`0e6640377`):**
  - `grain_config.mcp_servers` (schema 29) holds the deployment's servers. It is exported to `grain/config` as plain JSON, with secrets kept as `$secret:` references.
  - `pkg/capability/servers.Registry` attaches, refreshes (on reload and at least hourly) and detaches servers.
  - One bad entry is refused on its own and does not break the settings row.
- **Daemon, API and CLI (`af8edd8e3`):**
  - The daemon keeps the registry in step through `LiveConfig.Refresh`.
  - Relative stdio commands resolve under the `grain/config` checkout, and `$secret:` references resolve from the encrypted secrets store (audited as `capability-servers`). A stdio server's stderr is discarded.
  - Routes: `GET/PUT /api/capability-servers` and `POST /api/capability-servers/{remove,enable,disable,bind-secret}`. Each takes the `capability_id` in the JSON body and is trusted-only in `tests/security/routes_test.go`. Writes respect the external-config-repo write gate.
  - The `grain capability-servers` CLI reads secret values from stdin only.
  - `grain state check` warns about an entry the daemon would refuse, and about cleartext credential-looking env or headers.
- **UI (`7e8a1422e`):**
  - The "Capability servers" card in Settings → Credentials (`CapabilityServersPanel.jsx`) lists each server's attach state, error, discovered methods, env and headers as stored, and whether each referenced secret is set.
  - Each server has enable, disable and remove actions, and a per-server "Bind a secret" form opened on demand. An add-server form sits below the list.
  - The card is indexed for Settings search.

### What CI proves
- `pkg/capability/protocol/{protocol,e2e,dataplane}_test.go`: the protocol end to end over stdio and HTTP against in-process servers, plus the four review fixes.
- `pkg/capability/servers/servers_test.go`, `pkg/capability/intree/intree_test.go` and `pkg/cli/capability_serve_test.go`.
- `pkg/ui/capability_servers_test.go`, `tests/security/routes_test.go` (trusted level for the six routes), `pkg/staterepo/statecheck/statecheck_test.go`.
- Vitest `CapabilityServersPanel.test.jsx` (mocked API).

### What is NOT proved
- A **real daemon** attaching a **real `grain capability skill` (and `git`) stdio server** configured through the CLI and through the UI card, with its methods discovered and shown in the card.
- `$secret:` binding through the UI and CLI end to end:
  - the value lands only in the secrets store, never in `grain_config.mcp_servers`, the `grain/config` export, the API response, the daemon log or an attach error;
  - an unset secret yields an attach error that names the secret, not a value.
- Enable, disable and remove round-trips detaching a running stdio child (the process is gone), and re-enabling respawning it.
- A malformed entry committed to `grain/config` and pulled in: only that entry is refused, the rest attach, and `grain state check` reports it.

## 2. Capability-Reference Grants for Agent Task Runs

**Commits (main only):** `78838975e` (references accepted and minted at admission; `capability_policy`, schema 30), `3ee4a1627` (port relay), `422f795f2` (materialization), `905c24b38` (data-plane proxy), `cf6eb14f7` (CLI and prompt wiring), `92c354fd1` (remote executors), `111b16f93`

### What changed
- **Where references are accepted:** `capabilities:` lists everywhere accept references (`https://…[#method]`), bare or as `{capability, with}`. That covers `.grain` templates, schedules and workflows, Settings and repo defaults, `propose_task`, the API, and `-capability ref={json}`.
  - Each is normalized against its server's schema and recorded canonically as `<capability_id>#<method>={args}`.
  - `grain declarations check` validates syntax. Task creation and admission do full normalization.
- **Sub-task containment:** a child whose references the parent's recorded grants do not cover (`protocol.Uncovered`) is filed unapproved and without auto-merge.
- **Policy:** `grain_config.capability_policy` lists which repos, run kinds and events may hold which `<capability_id>#<method>`. Untrusted `pull_request` triggers are denied unless a rule sets `allowUntrusted`.
- **Materialization (`422f795f2`):** after the sandbox exists and before the agent starts:
  1. ports are forwarded through the capability port relay, which verifies with `/proc` that the far end belongs to the granting server's service;
  2. placements are written atomically with their modes;
  3. `setup_root` and `setup` run under `env -i`, with stdin closed and a 10-minute timeout.
  
  A failure aborts the attempt as setup-failed.
- **Endpoints:**
  - Each `mcp_endpoint` is proxied on a loopback listener at a random secret path. The proxy carries only POST, GET and DELETE, drops the client's `Authorization` and hop-by-hop headers, injects the server's headers, and never follows a redirect.
  - Grain handshakes through the proxy and names the servers (`AssignServerNames`).
  - The servers are registered for claude (`--mcp-config` plus `--allowedTools`), codex (`[mcp_servers.*]`), agy (`mcp_config.json` plus a hook allow) and custom backends.
  - `prompt_section` blocks are appended, each naming its grant.
- **Remote executors (`92c354fd1`):** the executor announces `capability_mcp_url` and carries connections back to grain on a `capability-mcp` multiplexed stream. An executor that predates this is refused with an upgrade message. A Kubernetes run pod is no longer handed loopback URLs (`SharesHostLoopback`).

### What CI proves
- `pkg/model/capability_ref_test.go`; `pkg/orchestrator/capability_{pass,materialize,endpoints}_internal_test.go`; `pkg/capability/portforward/portforward_test.go`; `pkg/capability/protocol/dataplane_test.go`.
- `pkg/agent/{,claude,codex,custom,antigravity}/capability_servers_test.go`; `pkg/modelexec/capabilitymcp_test.go`; `pkg/runhost/runhost_test.go`.

### What is NOT proved
- One **real task run in a real sandbox** (docker backend) that holds a reference grant, from start to finish:
  - the grant is minted at admission;
  - the port is forwarded and reachable inside the sandbox on `127.0.0.1:<sandbox_port>`, also under `network_access: none`;
  - the placement file exists with the right mode and owner;
  - setup ran;
  - the agent's CLI sees the capability's MCP tools and its prompt carries the `prompt_section`;
  - the pass is released when the run ends, on success and on cancel.
- The admission rollback when the second of two grants is refused: the first is released, and the task shows the server's reason as attributed untrusted text.
- A policy denial for an untrusted trigger, worded in grain's own words.
- A `propose_task` child asking for an uncovered reference is filed unapproved and without auto-merge.
- `recreate_sandbox` mid-run re-handshakes the endpoints.
- The port relay refusing a `host_port` whose listener is not owned by the granting server.
- `docs/capabilities.md` still says materialization is "not wired up yet" (doc drift).

### Walkthrough procedure

## 3. Capability-Reference Grants for grain CI Jobs and `git-repo` Write-Grant Hardening

**Commits (main only):** `7a32a1b51` (mint for CI jobs), `ec6bf7111` (materialize and write `mcp.json`), `e2533b216` (`git-repo` write grants: task branch only, fast-forward only, `-repo` required)

### What changed
- **Minting:** a `.grain/workflows` job naming a reference has it minted before its sandbox is built (`CiGrantReservations.Acquire`). The policy is checked as `CapabilitySubject{Kind: ci, Event, Untrusted}`, and attempt ids are `<deployment>-<ci run>-<job attempt>-<index>`.
- **Outcomes:**
  - A refusal errors the job, with the reason quoted.
  - `resource_exhausted` keeps the job queued as a grant wait until `retry_after` (capped at 1h).
  - A transient failure backs off from 30s and errors on the third in a row.
  - The pass is released however the job ends.
- **Repository CI list:** references a job declares no longer have to appear in the repo's CI capabilities list, and the policy decides. A reference the list names is not handed to a job that did not declare it.
- **Materialization (`ec6bf7111`):**
  - Ports and placements are applied and setup runs in the CI sandbox before any step.
  - Each endpoint proxy is forwarded into the sandbox on `127.0.0.1:38017+`, and `/home/debian/.grain/mcp.json` (0600) lists them.
  - The automatic retry reuses the same materialization without minting again.
  - Not covered: containers a step starts itself.
- **`git` server write grants (`e2533b216`):**
  - The branch must match `-push-branch` (by default anchored to `grain/…`) and must not be the base.
  - Updates are forwarded only when the pack proves a fast-forward (`gitproxy.PushShowsFastForward`).
  - `-repo` is required, and `with: {repo}` is an enum or pattern of them.

### What CI proves
- `pkg/orchestrator/capability_ci_internal_test.go`, `pkg/daemon/ci_capability_pass_internal_test.go`, `pkg/ci/requirements_test.go`, `pkg/capability/servers/servers_test.go` (git push-branch and fast-forward cases).

### What is NOT proved
- A real grain CI run of a workflow job declaring a reference, against the §2 demo server, where a step:
  - reads `~/.grain/mcp.json`;
  - calls the tool over the forwarded endpoint (`curl` with an MCP `tools/call`);
  - reads the placement;
  - reaches the port.
- The same job under `network_access: none`.
- The job's automatic retry (forced by a first-attempt failure) seeing the same `mcp.json` and tokens without a second `mint_` call.
- A `resource_exhausted` mint showing as a grant wait in the CI UI and the job starting after `retry_after`.
- A real `grain capability git` server refusing:
  - a push to `main` (the base);
  - a force-push to a `grain/…` branch;
  - a push to a branch outside `-push-branch`;
  - a `with: {repo}` outside `-repo`.
  
  It should accept a fast-forward push to `grain/x`.

### Walkthrough procedure
1. Check `git branch -r --contains 7a32a1b51 ec6bf7111 e2533b216` includes `origin/candidate`. Otherwise stop with `ask_question`.
2. Run a scratch daemon with grain CI enabled, pointed at a local `githubsim` or bare repo. Attach the §2 demo server (or a copy of it). Add a workflow job with `capabilities: [https://…#demo]` whose steps do `cat ~/.grain/mcp.json`, call `demo_echo` through the listed URL, and check the placement and port.
3. Push and run the workflow. Assert the steps pass, the mint and release are each called once, and the job log shows no secret header values.
4. Make the first attempt fail deliberately (a step that fails when a marker is absent, then creates it), so the automatic retry runs. Assert there is no second `mint_` and the same `mcp.json` URL works in the retry.
5. Set `network_access: none` on the job and repeat step 3.
6. Make `mint_demo` return `resource_exhausted` with `retry_after: 20` once. Assert the job shows a grant wait and then runs.
7. Start `grain capability git -repo owner/repo -upstream <local bare repo URL>` with `GIT_REPO_TOKEN` set. Mint a write grant and exercise the push cases listed above with `git push` through its proxy port. Assert each refusal message and that the fast-forward is accepted.
8. Record everything in `docs/test-runs/2026-10-23-capability-grants-ci-jobs.md`.

## 4. Agent CLI Run Locations, Per-Run Containers and Settings → Models Card

**Commits (main only):** `659283465`, `3f06a89bd`, `7c57dd176`, `89634062d`, `079b2975b`, `739e94f00` (security), `b86e9adf5`, `0dd0cf692`, `142891e8f`, `e132ad8d3`, `589b8d6e1`, `c4dbadfea` (schema 31; design in `docs/design/cli-run-location.md`)

### What changed
- **Run locations:**
  - Each agent CLI has a run location, `host`, `container` or `auto`.
  - Precedence: Settings (`grain_config.cli_run`), then the `-claude-run`/`-codex-run`/`-agy-run` flags, then the built-in default (`auto` for claude and codex, `host` for agy and custom commands).
  - The location is read live for each run.
  - `auto` runs on the host when `<cli> --version` works there, and in a container otherwise. When no image is available, `auto` stays on the host (`89634062d`).
- **Container runs:**
  - Each run is `docker run --rm --init` of the release image (`/etc/grain/image.env` or `-cli-image`), running as the daemon's uid on the host network.
  - Staged files, HOME, the working directory and symlink targets are bind-mounted at the same paths.
  - Credentials are passed as `--env NAME`, so they never appear in argv.
  - Cancelling a run kills its container, and leftover containers are reaped at start.
  - The MCP server stays on the host behind authenticated HTTP.
- **UI:** `GET/PUT /api/settings/cli-run` and a "Where each agent CLI runs" card in Settings → Models.
  - Each row shows the resolved location and why.
  - agy and custom commands are offered only the host. The custom-commands row now says a custom command runs as each connection's own command (`079b2975b`).
- **Installer:** `setup.sh` accepts `GRAIN_{CLAUDE,CODEX,AGY}_RUN`. `cloudtop-install.sh` defaults claude and codex to `container`. The readiness summary reports container CLIs, and the disk reclaimer keeps CLI images.
- **Security (`739e94f00`):**

## 5. `grain hostd`: Allowlisted Host Process Server, Host Runs and `run: host` Capability Servers

**Commits (main only):** `56da9b415` (hostd), `bed060a0a` (safepath, builds on every OS), `5ce7db0e7` (host runs only for CLIs hostd offers; agy on the Google track), `abdc97f52` (`run: host` stdio capability servers), `cfa8fa3f9` (per-CLI host-unavailable reason), `e81621946` (docs), `e83154a14` (security hardening from #5030's review)

### What changed
- **The server:**
  - `grain hostd` runs as the installing user, refuses root, and listens on a 0600 unix socket, checking each peer's uid with `SO_PEERCRED`.
  - It starts only the entries in a root-owned, non-writable `/etc/grain/hostd.yaml`, re-read on every request.
  - Each request's argv, env and cwd are checked against the entry (`paths_under`, accepted env names, `cwd_under`).
  - Children get a scrubbed environment, stdio is streamed, group signals are sent, deadlines are enforced, and refusals are logged.
- **Host runs:**
  - A container-mode daemon with `-hostd-socket` (or `/run/grain-hostd` mounted) runs `host` CLIs through hostd, and only when hostd's `Offers()` lists a `cli` entry of that name. Otherwise the run fails before staging, with the reason.
  - The Google build defaults agy to host behind hostd.
- **Capability servers:** a stdio capability server with `run: host` names a hostd capability entry and is started through hostd. Anywhere without hostd, the attach is refused.
- **Hardening (`e83154a14`):**
  - argv: any `..` component is refused; `--flag=value`, `name=value` and `-oVALUE` forms are split and checked; path-like values must be clean absolute paths under `paths_under`; `~` forms are refused; prompt text is no longer accepted in argv.
  - env: names the entry already sets are refused; `PATH/HOME/USER/LOGNAME/LANG/TZ/LD_*` are admitted only when named exactly; path-like values must be under `paths_under`.
  - stdin: a process 1024 frames behind no longer blocks cancel.
