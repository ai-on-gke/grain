# Nightly new features test plan: September 28, 2026

This plan covers all features and behavioral changes merged into `main` over the past
day (following `docs/test-plans/2026-09-25.md` and subsequent runs) through `29564f871`
(PR #2214). It encompasses over 40 merged pull requests and 100+ commits.

Key focus areas in this batch include:
1. **Autonomous Merge Queue, Demand-Driven Base CI, Batching & Bisection Engine**: Demand-driven base branch CI triggers, speculative PR batching, automated async conflict repair task dispatch with single-flight locks, and automated git bisection on batch failure.
2. **Team Settings Unpacking, Multi-Key GitHub Credential Management & Role Governance**: Unpacking Team settings into 4 dedicated inline panels (Team Profile, Members, Capacity, Git Identity), multi-key named GitHub tokens with glob pattern matching and interactive testing, role-based member management with last-admin safeguards, first-user admin bootstrapping, and team-scoped repository connections.
3. **System Settings Restructuring & Scoped Non-Admin Access**: Reorganizing Administrator settings into System Settings accessible to all users, with strict RBAC scoping granting non-administrators read-only visibility into Sandboxes and Caches while disabling cache flushes, and reserving full system configuration for administrators.
4. **UI Navigation Redesign, Bottom User Profile, Custom Pinned Items & Merged Task Dissolve**: Relocating user profile and settings to the bottom of the left sidebar rail, normalized navigation hierarchy, dedicated sidebar Merged list with smooth dissolve animations, custom icons and colors for pinned navigation, and real-time running CI output frame embedded in task detail view.
5. **Advanced CI Diagnostics, Flake Auto-Retry & Test Quarantining MCP Tools**: Test quarantine capability (`quarantine_test` MCP tool) with non-blocking CI pass and linked repair task creation, diagnostic MCP tools (`get_ci_log`, `retrigger_ci`, `query_test_history`, `run_ci_job`, `query_merge_queue`, `revert_task`), structured test failure reporting, and in-flight job retry.
6. **Two-Branch Release Candidate Cadence & Automated Symmetrical Backport Triage**: Streamlined two-branch release lifecycle (`main` and `candidate`) with semantic release tags (`v1.{X}.0-rc.{N}`, `v1.{X}.0`, `latest`), scheduled maintenance declarations on `candidate`, and symmetrical PR generation for backports/forward-ports with conflict markers and agent triage tasks.
7. **Access Control Accounts, RBAC Filtering & Granule Guest CA Cert Integration**: Access account filtering, sorting, and explicit account type normalization, coupled with Grain CA cert importing for Node/curl inside guest VMs and Playwright browser packaging.

Each section outlines what existing tests prove, the critical unproven gaps across real sandbox/browser environments, and concrete walkthrough steps.

## 1. Autonomous Merge Queue, Demand-Driven Base CI, Batching & Bisection Engine

`3c78b845d` (PR #2106, task-746), `360c58b8f` (PR #2050, task-662), and `ecd4612d2` (PR #2094, task-710) enhance Grain's autonomous merge pipeline with demand-driven base CI, speculative batching, and automated bisection.

Concretely:
- `pkg/orchestrator/basebranchci.go`: Implements demand-driven base branch CI triggering when unverified merges or pending merge tasks arrive on the queue, eliminating redundant polling while ensuring base health before batch merges.
- `pkg/orchestrator/repair.go`: Implements single-flight incident locking to prevent duplicate conflict repair tasks from being dispatched simultaneously for the same base branch breakage.
- `pkg/mcp/merge_queue_tool.go` and `pkg/mcp/revert_task_tool.go`: Introduce `query_merge_queue`, `revert_task`, and `revert_merge` MCP tools for inspecting merge queue batches, queued pull requests, and held gates, as well as generating clean revert commits linked to the origin task.
- `pkg/capability/pipelinecontrol/`: Provides `pause_pipeline` and `resume_pipeline` tools for emergency intervention.
- `ui/src/state.js` & `ui/src/components/TaskDetail.jsx`: Update merge queue UI status phrases to clearly distinguish states: "Waiting on Queue", "Resolving Conflicts", "Testing Batch", and "Merging".

### Existing coverage
- `pkg/orchestrator/basebranchci_test.go` verifies demand-driven trigger evaluation, base CI deduplication, and single-flight lock acquisition.
- `pkg/mcp/merge_queue_tool_test.go` and `pkg/mcp/revert_task_tool_test.go` test merge queue inspection payload formatting and git revert generation.
- `pkg/capability/pipelinecontrol/pipelinecontrol_test.go` tests pause and resume pipeline permissions and state toggling.
- `ui/src/state.test.js` verifies task state mapping for all merge queue statuses.

### Gaps and unproven behaviours
- **Multi-PR Batch Execution with Bisection in Real Environment**: No end-to-end test queues multiple concurrent pull requests where one PR contains a regression, verifying that the merge queue bisects the failing batch, identifies the culprit, merges the valid PRs, and dispatches a conflict repair task for the broken PR.
- **Dynamic Demand-Driven Base CI Execution**: Unproven whether an incoming PR correctly initiates base branch CI on a quiet repository and transitions from "Waiting on Queue" to "Testing Batch" smoothly without deadlocking.
- **MCP Merge Queue Inspection & Revert**: Verifying that an agent running in a sandbox can invoke `query_merge_queue` to inspect queue state, and successfully execute `revert_task` to revert a merged task with properly formatted attribution headers and git link relations.

### Walkthrough & test procedure
1. Launch `grain demo` with merge queue enabled on the test repository.
2. Create and push two independent task branches: Task A (clean, valid change) and Task B (introduces a failing CI test).
3. Queue both tasks for auto-merge.
4. Inspect the merge queue status in the UI, verifying transitions through "Waiting on Queue", "Testing Batch", and "Resolving Conflicts".
5. Verify via `query_merge_queue` that the batch failure triggers bisection: Task A merges cleanly into `main`, while Task B is rejected with a linked conflict repair task.
6. Dispatch an agent task with `pipeline-control` capability, execute `revert_task` against Task A, and assert that a clean revert commit is generated and pushed to the base branch.

## 6. Two-Branch Release Candidate Cadence & Automated Symmetrical Backport Triage

`8d8adfe77` (PR #2122, task-775), `a3a50ca03` (PR #2185, task-889), `38fe9ab1a` (PR #2072), `bf42a3133` (PR #2068), `c9302e36c` (PR #2069), `89339aed5` (PR #2067), `0666a1ffa` (PR #2058), `10736df5a` (PR #2057), `b7e90e54b` (PR #2056), `b5b301a24` (PR #2062), and `d6c3c137d` (PR #2115, task-757) establish a unified release candidate and backport automation architecture.

Concretely:
- `scripts/release-candidate-cut.sh` & `docs/release-candidate-management.md`: Eliminates versioned `rc/v*` branches in favor of a clean two-branch model: `main` (active development) and `candidate` (release stabilization), accompanied by immutable semantic release tags (`v1.{X}.0-rc.{N}`, `v1.{X}.0`, `latest`).
- Fast-forwards `candidate` directly from `origin/main` upon new candidate cuts and automatically tags `v1.{X}.0-rc.1`. Promotes stabilized candidates to `v1.{X}.0` directly from `candidate`.
- `.grain/schedules/`: Converts release-candidate cuts, staging cleanup, GKE smoke tests, and package pruning into agent-driven scheduled declarations targeting the `candidate` branch.
- Automated Backport Triage: Scheduled agent workflow creates symmetrical pull requests (`main -> candidate` backports and `candidate -> main` forward-ports). In the event of merge conflicts, commits conflict markers, files diagnostic draft PRs, and automatically triggers an agent review task with full triage context.

### Existing coverage
- `tests/deploy/release_workflows_test.go` tests candidate branch creation, tag naming, and promotion scripts.
- Unit tests in `pkg/orchestrator/` verify scheduled task dispatch against non-default base branches (`candidate`).
- Backport triage script unit tests verify symmetrical PR creation and conflict marker formatting.

### Gaps and unproven behaviours
- **End-to-End Two-Branch Release Cut & Promotion**: Unproven in a live git environment whether executing `release-candidate-cut.sh` cleanly updates `candidate`, cuts release tags, drafts GitHub release notes, and triggers the release build pipeline without manual git manipulation.
- **Automated Conflict Marker & Triage PR Generation**: Simulating a merge conflict between `main` and `candidate`, verifying that the backport workflow creates a diagnostic draft PR with conflict markers and dispatches an agent task to resolve it.
- **Scheduled Declarations on Candidate Branch**: Verifying that scheduled maintenance and smoke tasks correctly check out and execute against `candidate` rather than defaulting to `main`.

### Walkthrough & test procedure
1. Set up a local test repository with `main` and `candidate` branches.
2. Execute `scripts/release-candidate-cut.sh --dry-run` and verify branch targets, tag generation (`v1.X.0-rc.1`), and promotion logic.
3. Commit a feature commit to `main` and a conflicting commit to `candidate`.
4. Trigger the scheduled backport triage routine.
5. Verify that a draft backport PR is filed with conflict markers clearly delineated.
6. Verify an agent triage task is automatically dispatched with instructions to resolve the conflict and open a clean PR against `candidate`.
