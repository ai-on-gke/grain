# Nightly new features test plan: September 22, 2026

This plan covers the commits merged into `main` over the past day (following
the standing walkthrough and test batches) through `d825d3af6`. It evaluates
newly introduced features, configuration models, UI capabilities, and sandbox
infrastructure, identifying gaps between unit/contract assertions and live
end-to-end operation.

Each section details what existing tests prove, what remains unproven across real
environments, and the concrete walkthrough procedures required to validate the
behavior.

## 1. Multi-branch task configuration and cross-branch proposals

Tasks, templates, and schedules now support configuring multiple target base
branches across repositories, including multiple distinct base branches for the
same repository (`64cdcb932`, PR #1809). The composite primary key across
`task_write`, `schedule_write`, and `template_write` was updated to
`(task_id, owner, name, base)`. The MCP `propose_task` tool and the finish
orchestrator accept target base branches, resolve them against declared write
targets, and inherit auto-merge permissions accordingly.

### Existing coverage
- Schema and composite key migration unit tests in `pkg/model/schema.go` and `pkg/model/task_test.go`.
- Case normalization and repository key resolution in `pkg/model/sqlite/repo_case_test.go`.
- Finish orchestrator resolution of branch-specific write targets and auto-merge inheritance in `pkg/orchestrator/finish_test.go`.
- UI client write parsing validations in `pkg/ui/client_test.go`.

### Gaps and unproven behaviors
- End-to-end execution of a task with multiple branch targets proposing follow-up tasks targeting non-default branches.
- UI task creation and template editing forms allowing multiple branch entries for the same repository without validation collision.
- Verification that an auto-merged parent task proposing a child task for a declared non-default branch correctly inherits auto-merge, while a proposal for an undeclared branch is refused auto-merge and requires human review.

### Walkthrough procedure
1. Launch `grain demo` with local storage.
2. Create a task with multiple write targets declared for the same repository (e.g. `bwsalmon/grain` on branch `main` and `bwsalmon/grain` on branch `release/1.0`).
3. Run an agent session that invokes `propose_task` targeting both branches (`main` and `release/1.0`), as well as an undeclared branch.
4. Verify via API and database inspection that the child tasks are filed with the expected target base branches and appropriate auto-merge status.
5. In the UI Task detail view, verify that target branches are rendered clearly on each task card and in proposal reviews.

Filed: **Walkthrough: Multi-branch task configuration and cross-branch proposals (docs/test-plans/2026-09-22.md §1)**

## 2. Configurable auto-approval for task proposals from schedules and suites

Schedules, suites, and workflow reviews can now declare `auto_approve_proposals: true`
(`14b9533c9`, PR #1787; `c39daf99d`, PR #1808). This enables automated audits,
triage bots, and nightly test planning runs to file proposed follow-up tasks directly
into the active dispatch queue without requiring manual operator intervention in
the Inbox, while preserving safety bounds (depth limits and proposal caps).

### Existing coverage
- YAML parser tests in `pkg/repodecl/parse.go` and model compose tests in `pkg/model/compose_test.go`.
- Scheduled workflow synthesis and review handler tests in `pkg/orchestrator/scheduledworkflow_test.go`.
- SQLite persistence of `AutoApproveProposals` across schedules and suites.

### Gaps and unproven behaviors
- Live execution of a scheduled task with `auto_approve_proposals: true` calling `propose_task` in a running daemon, proving that the proposed task transitions directly to `approved` state in the database without lingering in Inbox proposals.
- Verification that exceeding proposal limits (depth or quantity caps) cleanly falls back to unapproved proposals with diagnostic logging rather than crashing or looping.
- Verification that scheduled tasks without `auto_approve_proposals: true` continue to leave proposals unapproved in the Inbox.

### Walkthrough procedure
1. Launch `grain demo`.
2. Define and trigger a scheduled task with `auto_approve_proposals: true` that executes a script proposing two follow-up tasks.
3. Observe the task finish lifecycle: assert both proposed tasks immediately appear in `approved` status ready for dispatch.
4. Define a second schedule without `auto_approve_proposals` and trigger it; assert its proposed tasks remain in `proposed` state in the Inbox.
5. Trigger a scheduled task that attempts to propose tasks beyond the allowed limit; verify that excess proposals are safely quarantined in `proposed` status with explanatory notices.

Filed: **Walkthrough: Configurable auto-approval of task proposals (docs/test-plans/2026-09-22.md §2)**

capabilities dropdown even when unselected, displaying readable names and readiness status.

5. Select a CI-only capability, save repository settings, and verify the successful toast notification.
6. Reload the page (direct URL navigation) and verify the selected CI capability remains active and persisted.
7. Verify that CI workflow generation for the repository includes the newly configured capability.

## 4. Granule sandbox guest network isolation and boot latency verification

The Granule sandbox VM networking was overhauled (`58964c664`, PR #1801) to allocate
inner dockerd subnets on `10.240.0.1/24` (pool `10.241.0.0/16`), preventing network collisions
with the host gateway proxy at `172.30.255.1` (which proxies git, package caches, and models).
Additionally, `ensureGuestDockerNetwork` dynamically repairs legacy guest daemon configs.
The suspend/resume device wait in initramfs was eliminated via `RESUME=none` and `noresume`
kernel arguments (`00994865d`, PR #1793; `f806af939`, PR #1807), dropping boot time by ~105 seconds.

### Existing coverage
- Granulefile build tests and initramfs configuration validation in `tests/deploy/deploy_test.go`.
- Granule VM spec kernel argument unit tests in `third_party/granule/pkg/vmspec/spec_test.go`.
- Unit tests for `ensureGuestDockerNetwork` in `pkg/orchestrator/granule_sandboxes.go`.

### Gaps and unproven behaviors
- End-to-end sandbox VM execution under live Granule backend verifying that a guest boots in under 15 seconds without hitting initramfs timeout stalls.
- Verification that running nested Docker commands inside the sandbox guest (e.g. `docker run`, `docker build`) does not conflict with host bridge proxies, and that `git clone` / package installs through `172.30.255.1` succeed cleanly during heavy guest container networking.

### Walkthrough procedure
1. Launch `grain daemon` with Granule sandbox backend enabled.
2. Dispatch a test task that boots a fresh Granule VM sandbox.
3. Measure the time from sandbox request to ready prompt; assert boot completes in < 20s.
4. Inside the sandbox, execute nested docker operations (`docker run --rm alpine ping -c 1 10.240.0.1`).
5. Concurrently perform git operations and package downloads routed through host proxy `172.30.255.1`.
6. Assert all network requests complete without `ECONNREFUSED` or routing loops.

Filed: **Walkthrough: Granule sandbox network isolation and boot performance (docs/test-plans/2026-09-22.md §4)**

## 5. Daemon backwards-compatible flag aliases for legacy Kontur configuration

The daemon CLI introduced flag aliases in `cmd/grain/daemon.go` (`08af259cb`, PR #1786)
mapping legacy `-kontur-*` flags (`-kontur-sandboxes`, `-kontur-workspace`, `-kontur-base-port`, etc.)
to their canonical `-granule-*` destinations with logged deprecation notices.

### Existing coverage
- Flag parsing unit tests in `cmd/grain/daemon_kontur_flag_alias_test.go`.

### Gaps and unproven behaviors
- Live CLI invocation of `grain daemon` with a complete suite of legacy `-kontur-*` flags to verify proper daemon bootstrap, log emission of deprecation warnings, and functional runtime binding without unexpected panic or fallback to host runners.

### Walkthrough procedure
1. In an isolated environment, invoke `grain daemon` with legacy flags:
   `grain daemon -kontur-sandboxes=true -kontur-workspace=/tmp/grain-kontur-test -kontur-base-port=9876 --dry-run` (or short-lived initialization).
2. Inspect daemon standard error output to verify deprecation notices are logged for each legacy flag.
3. Verify that the daemon initializes internal runners with the mapped granule paths and parameters.
4. Test mixed flag configurations (canonical `-granule-*` alongside unused `-kontur-*`) to ensure canonical flags take precedence.

Filed: **Walkthrough: Daemon legacy flag aliases and migration (docs/test-plans/2026-09-22.md §5)**

## 6. CI capability mounting and workflow execution

CI workflows were aligned to native capability paths (`8f0ecd817`, PR #1779; `e43cb5ea8`, PR #1777;
`534ca77be`, PR #1778). `gcp-key` mounts at `/home/debian/.gcp-service-account.json`, `github-sandbox`
mounts credentials at `/home/debian/.github-sandbox-repo` and `/home/debian/.github-sandbox-token`,
and `cmd/ghcr-prune` supports `GRAIN_CI_REPO` environment resolution.

### Existing coverage
- Unit tests for `cmd/ghcr-prune` in `pkg/grit` and `cmd/ghcr-prune`.
- Unit tests for capability credential mapping in `pkg/capability`.

### Gaps and unproven behaviors
- Execution of a native Grain CI workflow job declaring `gcp-key` and `github-sandbox` capabilities, verifying filesystem credential mount presence, correct file permissions (readable only by debian user), and successful execution of downstream tools (`ghcr-prune`, GCP SDK).

### Walkthrough procedure
1. Trigger a Grain CI test job specifying `capabilities: [gcp-key, github-sandbox]`.
2. Within the job step, verify that `/home/debian/.gcp-service-account.json` and `/home/debian/.github-sandbox-token` exist with non-empty contents and correct file mode.
3. Execute `cmd/ghcr-prune` with `GRAIN_CI_REPO` set; verify correct resolution of target repository and credential discovery.

Filed: **Walkthrough: CI capability credential mounting and ghcr-prune execution (docs/test-plans/2026-09-22.md §6)**
