# Test plan: the 2026-09-13 feature batch

This plan covers the 42 first-parent changes on `main` after `851c16288`
(the previous recent-feature test audit) through `5e960f048`. It is a plan,
not a record of a hand run. The batch also contains bug fixes, schema and CI
maintenance, and visual cleanup; those are mentioned only where they are part
of a newly added user flow.

The follow-up tasks below use the same rule: exercise a concrete workflow at
the highest practical level, add durable automated coverage where the flow is
not already represented, and fix any scoped bugs the run exposes. External
services may be simulated at their boundary, but the Grain server, persistence,
and browser or sandbox involved in the workflow should remain real.

## 1. Director can inspect a deployment and file durable work

The Director gained a read-only state checkout, bounded deployment diagnostics,
an explicit capability editor, immediate proposal persistence, and reliable
attachment to the open replacement task. Its page now uses the shared
conversation layout.

Focused tests cover grants, redaction, unavailable state, proposal replay and
replacement selection. They do not take an operator from granting the
capabilities through asking a diagnostic question, receiving a redacted answer,
filing a proposal, and continuing the conversation on the replacement task in
one running deployment.

Filed: **Exercise Director diagnostics through a durable proposal.**

## 2. Model configuration drives dispatch and recovers from incompatibility

The Models settings now configure modular backend entries rather than separate
legacy provider fields. Each framework gets its catalog, supported effort
choices, credentials, and custom overrides. Dispatch now pauses, without
spending an attempt, when Codex reports an incompatible model or account.

Component tests thoroughly cover the individual selectors and orchestrator
tests cover incompatibility classification. Missing is the seam between them:
save two backend entries, reload them, dispatch with the selected model and
effort, observe one incompatible backend pause while a healthy explicitly
configured backend remains eligible, then correct the setting and see the
paused task resume.

Filed: **Test model backend settings through dispatch and recovery.**

## 3. `grain/config` has a complete native change lifecycle

The controller-owned config repository now has the stable `grain/config`
identity, appears with ordinary repositories, is protected from removal, and
can be selected as a task's read or write target. Its repository page compares
native branches, and Grain now owns its pull request and merge lifecycle without
requiring GitHub or a configured mirror.

Route, API, and merge-queue tests cover the pieces, including an empty native
check list and comparison URLs after canonicalization. The remaining risk is
their composition. A browser flow should create a config-targeted task, push a
branch through the authenticated local alias, inspect the exact diff after a
reload and direct link, submit it, observe an immediate merge, and verify the
new config after restart. It should also prove that adding or replacing a
backup mirror does not change the alias.

Filed: **Take grain/config through a native pull request.**

## 4. Local Docker is a usable isolated sandbox backend

Grain can now execute each run in a local Docker container. The installer
chooses it when KVM is unavailable, pre-pulls the versioned image, and release
workflows publish both Docker and Kubernetes sandbox images.

Unit and installer-text tests cover backend methods, image selection, release
steps, and failure messages. No test installs the non-KVM path and then runs a
task whose checkout, shell command, MCP process, push, and teardown all happen
inside the container. That lifecycle is the proof that the fallback is an
isolated backend rather than merely accepted configuration.

Filed: **Run a task end to end in the local Docker sandbox backend.**

## 5. The daemon installer supports Trixie and operator Docker overrides

The setup path now installs Debian Trixie's split `docker-cli` package when
`docker.io` leaves no command, and the systemd service accepts
`GRAIN_EXTRA_DOCKER_RUN_ARGS` from `/etc/default/grain-daemon`. This is a
separate operator flow from running a task in the sandbox backend: it concerns
the outer daemon container and its host mounts.

The deployment suite checks generated shell and service text. A disposable
Trixie host/container run should install from the supported starting state,
mount a harmless host fixture with the environment override, restart the
service, read the fixture through the daemon container, and verify that a bad
override fails visibly without damaging the prior data directory.

Covered by `tests/installer/trixie`: it boots a clean Debian Trixie
userspace with systemd as PID 1, begins with no Docker command, and drives the
real setup script, service, and daemon container through both a working fixture
mount and a deliberately invalid override. The test is gated by
`GRAIN_INSTALLER_TRIXIE_E2E=1` because its faithful-container boundary needs a
privileged Linux container, a writable cgroup tree, package-network access, and
the host Docker socket. The hosted image jobs provide those capabilities;
ordinary unit runs and Grain's unprivileged native CI cannot safely provide
them.

Filed and covered: **Install Grain on Trixie with an extra daemon mount.**

## 6. Ambient-credential repositories survive a sandbox rebuild

Repositories outside GitHub may keep a custom clone URL while owner/name stays
their Grain identity. A sandbox clones such a remote with ambient SSH or Git
credentials, and recreation now looks up and restores the same URL rather than
falling back to the GitHub proxy.

Existing integration tests use local remotes and separately cover direct clone,
push, close-out, and recreation. The unproved boundary is the credential
mechanism itself. A scoped SSH remote should be added through the public UI or
CLI, used by a task without a GitHub credential, rebuilt via
`recreate_sandbox`, and used to commit and push again. The task should assert
that neither the remote nor secret material leaks into status, logs, or the
pull-request record.

Filed: **Recreate a task that uses an ambient-credential remote.**

## 7. Interactive tasks are visible when and where an operator asks

Live chats are now distinguished from background runs, use a purple active
mark, and are absent from ordinary default task lists. Explicit kind filters
can reveal them. Console sessions also received the shared full-height chat
layout and corrected single-message, typing-indicator, and separator styling.

Reducer and component tests cover each state and CSS hook. A real-browser flow
should start a Director or console exchange, confirm it is absent from the
ordinary list and CLI, reveal it with an explicit kind filter, and follow it
through list, board, timeline, detail, and the full-height chat at desktop and
phone widths. Closing it should leave a closed task, not stale merge activity.

Filed: **Follow an interactive task across filters and live surfaces.**

## 8. Deployment-defined task-list defaults behave like URL filters

The config row can now define the default task-list query, including no
defaults, while upgraded deployments retain historical closed-task behavior.
Explicit URL and CLI filters remain authoritative.

Codec and state tests prove parsing but not the operator workflow. A test should
apply defaults containing multiple supported conditions, open the web list and
CLI with no query, override each from the URL or command line, clear the
deployment default, and repeat after restart. Include an interactive-kind
default to prove the new built-in exclusion yields to deployment policy.

Filed: **Verify deployment task-list defaults in the web UI and CLI.**

## 9. Sandbox and CI activity is observable without opening each run

The sidebar now reports the cheap live sandbox count, sandbox sparklines label
their current values, and CI summaries and details distinguish cache hits.
Component tests render supplied snapshots, but they cannot prove that lifecycle
events produce those snapshots or that polling removes stale values.

One end-to-end observability flow should start an uncached CI job, watch the
sidebar and Sandboxes page gain and then lose its sandbox, repeat the same run,
and verify the cache-hit count and badge without a second live sandbox. Current
resource labels should update during the first run and remain correctly paired
with their series after another sandbox appears.

Filed: **Trace a CI cache hit through sandbox observability.**

## Changes that do not need another task

The standardized CI/Sandboxes page shell and chat color fixes are exercised by
the responsive browser flow above. Duplicate-submit prevention, closed-task
merge display, native comparison reloads, no-change schema upgrades, and
Debian package fallback all arrived with focused regression coverage; their
user-facing seams are included in the relevant tasks rather than filed again.
The v3 check-in suite, two-core CI request, schema-version bump, Kubernetes
pull policy, release workflow assertions, and test-fixture repairs change how
software is built or tested rather than adding another user flow.
