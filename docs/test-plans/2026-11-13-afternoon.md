## §3. Host `grain health` exit codes across live `FAILING`, `WARNING`, `ALERT` and in-sandbox checks

### What changed (PR #1442)
- **`grain health` exits `1` on `FAILING` checks** (`8bdaedcc1`, `pkg/cli/health.go`, `pkg/cli/main.go`, `design/spec/cli/host.spec.md`, `design/spec/external-cli/external-cli.spec.md`): host `grain health` (both text and `-json`) now returns a ` CLIExitError` with exit code `1` whenever any health section is `FAILING` — dispatch blocked, capability servers out of use, stale schedules with no run in more than twice their cadence, or repository `.grain/` declarations not read in full. In text mode it prints `grain: health: failing: <comma-joined summary>` on stderr; in `-json` mode it writes nothing extra so stdout stays valid JSON while exiting `1`.
- **Advisories and in-sandbox reads keep exit `0`:** `WARNING` and `ALERT` sections still exit `0`, and in-sandbox `grain health` (`pkg/sandboxcli`, reading `deploy://health`) still exits `0` so agents inspecting deployment health do not abort shell pipelines.

### What CI proves
- `pkg/cli/health_test.go` (`TestGrainHealthExitsOneWhenACheckIsFailing`) against an `httptest.Server` returning synthetic `HealthResponse` JSON structs.

### What is NOT proved
1. **Healthy and advisory-only states on a real daemon:** start a real `grain daemon -sandbox-port-base=0` (SQLite and PostgreSQL). Verify `grain health` and `grain health -json` exit `0` when clean (stderr empty, `-json | jq -e .` valid), and still exit `0` when the live daemon emits only `WARNING` or `ALERT` sections (for example, an raised warning/alert notification or unverified-mode advisory with no `FAILING` section).
2. **All four live `FAILING` triggers produced by the real daemon (not synthetic JSON):** induce each failing condition one by one and then two together on the running daemon:
   - **Dispatch blocked** (e.g. pause/hold dispatch or remove usable model connections while work is queued so `/api/health` reports dispatch blocked);
   - **Capability server out of use** (e.g. occupy built-in git capability port `4254` or register a failing capability server);
   - **Stale schedule** (a schedule enabled with a short cadence whose last run timestamp is older than twice its cadence with no run filed);
   - **Unread repository declarations** (commit a malformed `.grain/` YAML declaration on the `githubsim` default branch and reconcile).
   For each single failure and for a combined multi-failure state, verify:
   - `grain health` exits `1`, prints the human-readable `FAILING` section on stdout, and prints `grain: health: failing: …` on stderr;
   - `grain health -json` exits `1`, writes **empty stderr** (or never contaminates stdout), and pipes cleanly into `jq -e` with all failing arrays populated.
3. **In-sandbox `grain health` parity:** dispatch a sandboxed run (granting `https://grain.dev/capabilities/api#self-debug` or `deploy://health` access) while the daemon has at least one `FAILING` section active. Confirm the in-sandbox `grain health` (and `grain read deploy://health`) prints the failing report and exits `0`.

### What changed (PR #1444)
- **Upstream sync to `gke-labs/granule` `ccdbc4b`** (`002c34723`, `go.mod`, `third_party/granule/...`, `docs/granule-local-patches.md`): `third_party/granule` is byte-identical to `gke-labs/granule` at `ccdbc4b` (PRs #255–#256). In `third_party/granule/pkg/dockervm/docker.go`, `docker rm -f` and `docker stop` now treat Docker's `"removal of container … is already in progress"` as an active removal and poll `docker inspect` (up to 1 minute or `ctx.Done()`) until the container disappears before `granule vm delete` clears its saved VM state.
- **`pkg/granule/granule.go` (`Command.Delete` and `RemoveContainers`):** `Command.Delete` dropped its 30×2 s retry wrapper (`deleteInProgressAttempts`/`deleteInProgressInterval`) and is a direct pass-through to `granule vm delete` again. **Intentional behavioral change:** a removal that never settles within granule's 1-minute bound or before `ctx` expires now returns an error instead of silently returning `nil`. `RemovalInProgress` remains in `pkg/granule` for `RemoveContainers`, which invokes `docker rm -f` directly.

### What CI proves
- `pkg/granule/granule_test.go` and `third_party/granule/pkg/dockervm/docker_test.go`, both driving **`fakedocker`** (`GRANULE_DOCKER`), plus `TestCoreSaysNoGoogleTokens`. Neither CI job drives `granule vm delete` or `Command.Delete` against a real `dockerd` container teardown race.

### What is NOT proved
1. **Vendored tree integrity & test suites:** verify `third_party/granule` matches `go.mod`'s `ccdbc4b77525` commit (`docs/granule-local-patches.md`), build the vendored `granule` CLI from `./third_party/granule/cmd/granule`, and run both `go test -race ./pkg/granule/...` and `(cd third_party/granule && go test -race ./pkg/dockervm/... ./pkg/cli/...)`.
2. **Concurrent `vm delete` and `RemoveContainers` against real Docker Engine (`dockerd`):** using the sandbox's live Docker Engine, create real `dockervm`-shaped containers/VMs (including containers with non-trivial overlay filesystem data or a delayed stop/rm so concurrent `docker rm -f` calls overlap in `dockerd`) and race:
   - two concurrent `granule.Command.Delete` calls against the same VM name,
   - `docker rm -f <container>` racing `granule.Command.Delete` (simulating an orphan sweep racing run release), and
   - concurrent `granule.RemoveContainers` calls against `docker rm -f`.
   Confirm every racing caller that waits for completion returns `nil`, `docker inspect` confirms the container is gone, and the VM's state directory under `stateDir` has zero leftover state files.
3. **Timeout / `ctx` cancellation propagation (the changed error contract):** call `granule.Command.Delete` with a short `context.WithTimeout` (e.g. 50–100 ms) while container removal is genuinely still in progress (or over a thin wrapper delaying `dockerd`'s `inspect` disappearance while forwarding to real `docker`). Confirm `Command.Delete` now returns a non-nil error rather than silently returning `nil`, the saved VM state is **not** prematurely wiped while the container still exists, and a follow-up `Command.Delete` with an uncancelled context finishes cleaning up both container and saved state.
4. **Upstream-first rule:** if any defect is found inside `third_party/granule` itself, do **not** hand-patch `third_party/granule` on `ai-on-gke/grain` — document the exact reproduction in the report and propose the upstream fix against `repo: "gke-labs/granule"` first; fix any `pkg/granule` wrapper bug directly in `ai-on-gke/grain`.
