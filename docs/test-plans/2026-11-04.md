## §1. The release train, rebuilt — objective qualification, the continuous train, the task train's tag grant, `grain/rc-hold`, red-RC notifications

### What changed
- **Qualification instead of a staging soak** (#537, #536):
  - Stage 2's reconciler (`pkg/orchestrator/releasequalification.go`) finds every `vX.Y.Z-rc.N` that is neither `-discarded` nor promoted. Once that rc's Stage 1 (`nightly`) has succeeded, it starts the release-qualification suite at priority 8, always `until_clean`, max-passes 1 and no auto-merge.
  - Each item is judged objectively (`model.JudgeQualificationAttempt`): no PR, no follow-up outside its `qualification/<task-id>` scratch branch, a valid `Qualification-Verdict`/`Qualified-Tag`/`Qualified-Commit` footer, the scratch branch removed, and no live fixture tasks left behind.
  - The retry budget is `model.DecideReleaseQualification`: one product re-run, a third flaky item counts as systemic, and up to three infra re-runs before the candidate goes neutral.
  - The verdict is posted as the `grain/release-qualification` check run. Only grain's own App's check run counts (#622, #630, `CHECK_QUALIFICATION_APP`).
- **The continuous train on GitHub Actions** (#646):
  - `release-train.yml` is woken by finished release and nightly runs and by the qualification check run, with an hourly cron as a safety wake. The staging soak, `RELEASE_STAGING_URL` and the hard need for `GRAIN_API_URL` are gone.
  - `scripts/release-train-actions.sh` dispatches Stage 1, the one flake retry and the infra re-runs (as one `nightly.yml` run with `inputs.jobs`), and cancels a dropped rc's own runs.
  - A passing rc still stops at `vX.Y.0-pending`. The train never pushes `vX.Y.Z` or moves `latest`.
- **The train as a grain task** (#611, #665):
  - `.grain/templates/release-train.yml` has a `push:` list of exactly `v*-rc.*`, `v*-pending`, `v*-discarded`, `candidate` (force) and `release/v*` (create only). The git proxy refuses anything else (`TestTheReleaseTrainsGrantNeverReachesAPromotion`).
  - A change to any template's `push:` list is person-only (`trustboundary.TemplatePush`).
  - The task reads verdicts through the new `grain ci checks <sha> [--name] [--format github]` and `grain ci list --format github|github-jobs`, in GitHub's REST shapes.
  - Under `RELEASE_PUSH_GRANT=train`, `release-from-trunk.sh` refuses approve/reject/rollback.
- **`grain/rc-hold` and red candidates** (#638, #655, #671):
  - On a confirmed red rc, `releaseredrc.go` raises `pipeline.rc-failed:<rc_tag>` with the `<floor>..<rc_sha>` range. It raises `pipeline.release-escalated:<version>` after rc.3, `pipeline.release-infra-stalled:<rc_tag>` and `pipeline.flake-budget:<repo>:<item>`.
  - It keeps `grain/rc-hold` in progress on the red rc's commit while any open task title carries `[rc-blocker <rc_tag>]`.
  - Phase 2 of `release-from-trunk.sh` reads `grain/rc-hold` (only from `RELEASE_QUALIFICATION_APP`, which is now required) and emits `rc_held=` instead of cutting while it is held. It fails closed when the hold cannot be read.
  - The pipeline steward's prompt gains a red-RC triage section (`docs/pipeline-steward.md`).
- **Edges**:
  - #592: the train cuts only minor releases from `main`.
  - #619: every rc placeholder is filled, and `nothing_needed` is not offered.
  - #604: release-edition merges off GitHub, and "a release never starts" is reported.
  - #603: `release images` re-runs on checkout 5xx and VM death, and an unusable `working-directory` fails its step.
  - #608: the trust boundary narrows `release-promotion` to the approval path. The new `release-machinery` category is released by a clean security review.

### What CI proves
- `pkg/orchestrator/releasequalification_test.go`, `releaseredrc_test.go`, `releasestall_test.go` and `model`'s judge and decide tests cover each verdict rule and retry budget on synthetic task records.
- `scripts/release-from-trunk_test.sh` and `candidate-gate_test.sh` cover held, foreign-App, completed and absent `grain/rc-hold` cases on canned JSON.
- `tests/deploy/grain_workflows_test.go` (`TestTheReleaseTrainNeverPromotesARelease`) and `pkg/gitproxy/release_train_push_test.go` cover the promotion boundary.
- `pkg/trustboundary` tests cover the category split.

### What is NOT proved
1. **One rc through the whole loop over `githubsim`**:
   - A tag `v3.2.0-rc.1` lands, and Stage 1 is dispatched (or started by the tag push).
   - Stage 2 files the suite once Stage 1 is green, and the items close with valid footers.
   - `grain/release-qualification` is posted as grain's App, and `candidate-gate.sh` stages `v3.2.0-pending`.
   - Nobody else's check run with the same name is believed.

   Each step runs off the previous one's real output rather than canned JSON.
2. **The objective judge on real item tasks**:
   - An item that opens a PR fails.
   - One that proposes a follow-up on another branch fails.
   - One that leaves its scratch branch behind fails.
   - One whose footer names another commit fails.
   - One closed with an `INFRA` footer is re-run, not failed.
3. **Red rc → hold → rc.2**:
   - `pipeline.rc-failed` appears in the Inbox with the right range.
   - A task titled `[rc-blocker v3.2.0-rc.1] …` keeps `grain/rc-hold` in progress, and the next train run emits `rc_held` and cuts nothing.
   - Closing the blocker completes the hold, and the following run cuts rc.2.
   - At rc.3, `pipeline.release-escalated` is raised, and the steward does not cut.
4. **The task train's grant against the live proxy**:
   - Run the real `release-train.yml` template as a task against a scratch repo served by the scoped proxy.
   - It may push `-rc`, `-pending` and `candidate`, and is refused `vX.Y.Z`, `latest` and branch deletes.
   - A PR that edits the template's `push:` list is held for a person.
5. **`grain ci checks` / `--format github-jobs` fidelity**: in a sandbox task, compare the output with `githubsim`'s own REST answers for a commit with several attempts. Check that a run grain only knows from its job record is counted in `grain_note`, not invented.
6. **`release-train-actions.sh`** against `githubsim`: one combined re-run dispatch after Stage 1 finishes, and cancelling only the dropped rc's runs, never `main`'s.

## §2. Release approval, rollback and upgrades — Inbox Approve on GitHub Actions, the person-only rollback, upgrade on each release, retracted releases

### What changed
- **Approve from the Inbox on a `ci_mode: github` repo** (#607, #593, #590):
  - A new `release-pending` reconciler (`pkg/orchestrator/releasepending.go`) reads tags at most every 10 minutes. It raises `release.pending:vX.Y.Z` (Approve/Reject, the `-pending` tag message and `docs/releases/vX.Y.Z.md`) for each `-pending` without its release, and clears it when `vX.Y.Z` is tagged.
  - Approve, which only a person may do, signs a `pkg/releaseapproval` record (ECDSA P-256 key in the data dir, 15-minute expiry) and dispatches `.github/workflows/promote-release.yml` with it. A second press while the record is good is refused.
  - Patch releases (`vX.Y.Z` with Z > 0) get Approve/Reject too. `RELEASE_ALLOW_BREAKING` passes through for a person.
- **Rollback** (#664, #667):
  - `POST /api/releases/{version}/rollback` and `grain release rollback [-repo] [-to vA.B.C] [-reason] vX.Y.Z` are person-only.
  - On grain CI repos they start `promote-release.yml:rollback`. On Actions repos they sign a rollback record that binds the commit, `rollback_to` and the SHA-256 of the reason.
  - The workflow's `rollback` job refuses unless `GRAIN_CI_REQUESTED_BY_KIND=human`, and its inputs cannot be overridden by `env:`.
- **Upgrade on each release** (#605):
  - `grain_config.auto_upgrade_on = release` (schema 99). `reconcileReleaseUpgrade` watches the image channel's newest promoted release and never follows an `-rc.N`, `-discarded` or `-retracted` tag.
  - After a new release has stood for an hour, the reconciler schedules a drain-and-upgrade to `latest` or the exact tag.
  - A failure raises one `upgrade.failed:<release>` Inbox notification naming the stage. The failed release is not retried until a newer one is published.
  - Settings → General → Updates gains an "Upgrade automatically" picker: Off, "On each release (recommended)", or "Once a day".
- **Retracted releases** (#537, #610): `GET /api/upgrade[/targets]` reports `retractedRelease`. The Upgrade pane's `RetractedReleaseAlert` offers the fix-forward release and `latest`, and warns that going back is safe only without a schema change.
- #606: the upgrade e2e tests only upgrade from releases `latest` has promoted.

### What CI proves
- `pkg/orchestrator/releasepending_test.go` and `releaseupgrade_test.go` cover raise/clear and the settle hour on a fake clock.
- `pkg/releaseapproval` tests cover signing and verification.
- `tests/deploy/release_promotion_test.go` covers the person-only jobs and env isolation.
- Playwright `auto-upgrade-settings-layout.spec.js` and `upgrade-retracted-release.spec.js` cover layout over a stubbed `/api/upgrade`.

### What is NOT proved
1. **Approve end to end over `githubsim`**: the notification appears for a `-pending` tag. A person's Approve dispatches `promote-release.yml` once, with a record that verifies against the deployment's key. A second click is refused. An `api:*` token's approve is refused. Tagging `vX.Y.Z` clears the notification within one reconcile.
2. **Record tampering**: an expired record, a record for another commit and a record signed with another key are each refused by the verifier the workflow runs (`scripts/` helper or `pkg/releaseapproval` CLI).
3. **Rollback from the CLI and the UI as a person and as an agent**: the request body, the dispatched inputs, the reason's hash, and the refusal for a non-human caller (exit code and message). Do this on both a grain CI repo and an Actions repo.
4. **Upgrade-on-release with a real `grain daemon`** and a fake registry (`pkg/upgrade` test registry or a local OCI registry):
   - A new tag waits an hour (fake clock or a shortened setting), then drains and cuts over.
   - Two tags close together give one drain.
   - A failing health check raises `upgrade.failed` once and does not retry.
   - The next release clears it.
5. **Retracted release on a live upgrade pane**: with `<running>-retracted` in the registry, the alert's two buttons start the right upgrade.
6. **Settings UI** for the three modes at 1440/390 in light and dark, saved and reloaded, and the Inbox's patch-release row.

1. Shared steps 1–3, 6, 7 and 9. Scripts go in `docs/test-runs/2026-11-04-release-approval/`.
2. Items 1–3 against `-github-sim` with a seeded `vX.Y.Z-pending` tag, driven through Playwright (Inbox Approve/Reject) and `grain release approve|reject|rollback`. Capture every dispatch payload from `githubsim`.

## §3. Access and identity — the database allowlist, service accounts with a reason, `whoami` and principal labels, Settings → Audit

### What changed
- **Database allowlist** (#580, schema 98):
  - `-ui-allowed-principals` / `$GRAIN_ALLOWED_PRINCIPALS` is replaced by `allowed_principal` (`user:` and `group:`, with groups resolved through Cloud Identity), enforced live without a restart.
  - The flag is imported once when the table is empty and unmigrated, then ignored with a deprecation warning.
  - `GET/POST/DELETE /api/access/principals`, `grain access list|allow|deny`, and Settings → Access → Allowed users and groups.
  - `api:access:read` and the dangerous, person-only `api:access:write` need `X-Grain-Acting-Reason`, recorded in `config_audit`.
  - Verified allowlisted users hold operator privileges equal to an access-code session.
- **Service accounts back on, narrowly** (#652, schema 108):
  - `serviceAccount:<email>` entries are accepted for `*.gserviceaccount.com` only, and need a reason (`grain access allow --reason`).
  - Accounts whose keys grain hands to tasks (gcp-key pools, gcp permission-set accounts) are refused when added and at sign-in, even if planted in the table.
  - Settings → Access groups them as non-human callers with who, when and why.
- **Who am I** (#531): `GET /api/whoami` returns `{actor, onBehalfOf, source, verified, allowed}`. The sidebar user tile is back, opening Settings → Access.
  - Every actor surface carries `*Source`/`*Label`: task author and approver, comments, timeline transitions (including closes and reopens), pauses and the pipeline feed.
  - `GET /api/deployment/config-audit` is new.
  - `grain task read` and the MCP task views print labels.
- **Settings → Audit** (#635): three independently read cards: configuration changes (`settings:read`), credential access and secret resolutions (`secrets:read`). Each entry stacks as lines on a phone.
- **Edges**:
  - #633: an unavailable identity verifier answers 503, not 401.
  - #649: `$GRAIN_USER` is the default for `-as`.
  - #651: a rejected `-token` or env credential is reported accurately on 401.
  - #564: signing in with the access code returns to the deep link.
  - #587: Cloud Run direct-IAP qualification script `scripts/iap-e2e/run.sh`, already run live (`docs/test-runs/2026-11-04-iap-e2e-cloud-run*.md`).

4. **Labels everywhere**:

6. **The verifier down**: 503 on API calls, and a usable message in the browser.

## §4. External agents and the controller MCP — `gma_` owners, `X-Grain-Client`, owner-trust approval, `POST /api/mcp`, the workstation Director

### What changed
- **Owned external-agent tokens** (#629, schema 107):
  - `external_agent_token.owner` defaults to the issuer, may be named by an operator, and is locked to the caller for self-service minting and to an agent's own owner when an agent mints.
  - Requests run as `external:<name>` on behalf of the owner. Journal lines, audit notes, comments and filed tasks name the owner, and `POST /api/tasks` records the owner as requester.

## §5. The workstation CLI — global flags after the verb, exit codes, `grain fs`, external `grain ci` verbs, `grain merge-queue`, `grain health`

### What changed
- **Flags and exit codes** (#627):
  - Global flags (`-json`, `-server`, `-token`, `-audience`, `-as`, `-connect-timeout`, `-timeout`) are accepted after the verb with one or two dashes. Free-text verbs (`comment`, `broadcast`, `notify`) lift them only before the body. Stray positionals exit 2.
  - Exit codes: 0 success; 1 red CI or 5xx; 2 usage or 400/404/409/422; 3 401/403 or a sign-in page; 4 unreachable; 5 an explicit `-timeout` ran out.
- **`grain fs ls|cat|read|grep <uri>`** over the new `GET /api/fs/<scheme>/<path>` (#656):
  - Scopes per scheme: `ci:` → `ci:read`, `task:` → `tasks:read`, `deploy:` and `src:` → `deployment:read`, `config:` → `settings:read`, `memory:` → `memory:read`.
  - Repository-limited grants are held to the path's repo.
  - `src://` is refused to a `gma_` token without `deployment:src`.
  - It shares `pkg/nsclient` with the sandbox CLI (inline `?query` suffixes too). A grep cut short by the walk cap before any match exits 1.
- **External CI verbs** (#683):
  - `grain ci wait (<run-id> | -pr … | -ref … -repo …) [-jobs]` answers in the sandbox's wait shape plus faults. It exits 0/1/5. A wait for a job the run never had is not green.
  - `grain ci retrigger <run-id> [-jobs]`, `grain ci test-history <test>`.
  - `grain merge-queue [-repo] [-json]` over `deploy://merge-queue`. A `ci:read` caller sees only its repos, and `-repo` narrows but never widens.
- **`grain ci checks` and `--format github`** (#665), described in §1.
- **Actions logs** (#678, #543): job and step logs are read by bare run id, also on Enterprise-shaped hosts. Runs on non-default hosts are listed. A signed blob URL is kept out of transport errors.
- **`grain health`** (#634): prints layer counters (`ui.RegisterHealthCounters`) sorted by key, and the whole response with `-json`.
- #650: unknown `grain db` subcommands and stray `upgrade-postgres` arguments are refused.
- #602, #637: `design/spec/cli/*.spec.md` is generated from the code and kept true by `TestHostCLISpecCoversEveryCommandAndFlag`.

## §6. Agent access requests and console-session reach — `request_access`, Grant/Deny, sessions read every repo and CI

### What changed
- **`request_access`** (#648, schema 105): a turn-ending agent tool.
  - An agent can ask for another repository (read/write, with a base), a capability grant (in-process, `api:*` or a server method with `with:` arguments) or open network, with a reason.

## §7. Hostd — `install.sh`, park and reattach across disconnects, per-hostd capability servers, default hostds, sandbox budget edges

### What changed
- **`GET /api/hostd/install.sh`** (#541): sets up a remote `grain hostd` with `curl | sh`.
  - The script does not read itself as the token.
  - The daemon's release and image are told only to a caller with access.
  - Bearer guesses are rate-limited, and root staging is hardened.
  - On a single-tenant daemon the route stays open.
- **Disconnects** (#550):
  - A run on a hostd that drops is parked. `-hostd-reattach-timeout` (default 15m) re-attaches a detached CLI from its stdout/stderr cursor when the hostd reconnects, with nothing lost or repeated.
  - A reconnect wakes dispatch at once.
  - Past the timeout the run ends `interrupted` (`ErrHostdLost`) with no strike, and the process is cancelled once the hostd is back.
  - A CLI for a finished run is cancelled when its hostd connects.
- **Every hostd, not just the default** (#549):
  - Pinned runs start detached through their own hostd's `runhost.Hostd`, and adoption asks each hostd about its runs in `task_run_hostd`.
  - A pinned task's `run: host` capability servers (host scripts) start on its hostd, and the capability audit records that hostd.
- **Default hostds** (#551, #598, schemas 94, 102):
  - `template.hostd` and `repo_config.default_hostd`. Precedence: the filing, then the template, then the repository, then the default.
  - Both are settings-only keys, so a repo's own `.grain` files cannot route work onto somebody's hostd.
  - The task page gains a Hostd section (`PUT /api/tasks/{id}/hostd`, "Use default hostd"), and the repo Agents tab a Default hostd box.
  - A default naming a revoked hostd refuses the filing.
- **Edges**:
  - #626: a hostd setup failure is not read as a provider refusal burst.
  - #623: `-run-host-image` is refused with `-host-sandboxes`.
  - #663: `hostinit.CheckSandboxBudget`, `grain sandbox-budget` and `setup.sh` flag disks and budgets that cap concurrency far below `max_workers`.
  - #668: in-process builtin CI jobs (`grain-state-check`) skip the sandbox capacity gates.
  - #612: a mirror derived from `k8s_granule_image` is made explicit.
  - #206: removing a custom sandbox image reverts cleanly to the default.
  - #600: `setup.sh` pipelines are no longer killed by SIGPIPE.
  - #562 and #565: hostds are selected by registry labels only.

### What CI proves
- `pkg/runhost` and `pkg/hostd` tests cover reattach-from-cursor and lost-past-timeout on in-process fakes.
- `pkg/daemon` hostd tests (the reconnect/park test, `TestAPinnedHostdIsWaitedForAcrossADisconnect`) cover a pinned task through disconnect, park, reconnect and resume.

   - Twenty bad bearers are rate-limited.
