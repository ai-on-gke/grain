## Branch situation & how follow-up tasks should handle it

Releases are cut from `main` by the continuous train (`.grain/settings.yml`, `scripts/release.conf`). From PR #1154 every rc that passes Stage 1 is released, with no daily cap, and the next rc is cut in the same tick. There is no `release/vX.Y.Z` branch for the current line. A `fix:` a walkthrough lands on `main` therefore ships with the next rc and needs **no backport task**. The only exception is a defect the operator asks to patch on an older line (`release/v3.1.1` and the `v3.4.1` patch line).

Every follow-up walkthrough task filed from this plan targets `main` (`repo: "ai-on-gke/grain"`, `branch: "main"`) and depends on [Task #4297](/tasks/4297), so `docs/test-plans/2026-11-11.md` is on `main` when each walkthrough begins. Each proposal asks for unattended `auto_merge: true` once CI is green. The operator who approves the proposal decides whether to grant auto-merge on `main`.

The gate is **GitHub Actions**: `Tests` in `.github/workflows/tests.yml`, `plc-tests.yml` when `grain-plc/` is touched, `cla/google` and the workflow/hygiene scans. Inside a sandbox, open the PR and wait on its checks with `grain pr open` and `grain ci wait` (with `timeout: 600000`, no `--jobs` flag). From PR #1194 a task on a GitHub-CI repository holds `api:ci-read` on its own repository by default, so `grain ci list/log` and `grain pr status` now answer on this repository too; `grain ci wait` remains the way to block on checks. If a check is already red on `origin/main` before your branch touches it, merge `origin/main` and report the breakage rather than weakening the check.

## §1. Durable tasks: compaction, the current brief, stale handovers and rollover

### What changed
- **Compaction** (`f68eef4c`, schema 136): `task_context` holds a cursor. Comments at or before it are summarised by a fresh handover, and later prompts carry that handover plus only the newer comments, while every comment stays in the record. Agents compact with the new `compact_context` tool; the cursor stops at the last comment posted before the run started. People run `grain compact <id> [-handover-file f]` (and `grain brief` for the brief) or `POST /api/tasks/{id}/compact`: with a handover it compacts now, without one the next run is asked to compact first.
- **Versioned handovers** (`f68eef4c`): each new handover bumps `handover_version`, writing the same one again confirms it, and age is counted in runs and comments; past `HandoverStaleRuns`/`HandoverStaleComments` it is stale and the prompt says so.
- **Current brief** (`f68eef4c`, `272997a7`): `POST /api/tasks/{id}/brief` (reason required) replaces the description in the prompt; `task_brief_edit` keeps the history. The task page shows the brief in place of the description, an Edit brief editor, the original under a disclosure, and a Context panel (handover version/age, `stale` badge, cursor, standing request, **Compact** and **Write handover…**). Comments at or before the cursor collapse behind "Summarised by compaction".
- **Rollover** (`d6207420`, `a6efc80d`, `ec233660`, `261278d1`): `Store.Rollover` files a successor carrying the brief, last handover and settings and closes the predecessor as `rolled_over`, moving its PR, goal, subscriptions, open notifications, dependents and parks in one transaction. `grain rollover` / `POST /api/tasks/{id}/rollover` (`dispatch:write`) do it by hand; `reconcileRollover` does it by itself past 500 runs, 2,000 comments or a year, never mid-run. Non-durable tasks are refused. The task view carries `rolledOverFrom`/`rolledOverTo`.
- `2b13493a` reads a compacted task's conversation from its cursor.

### What CI proves
- `pkg/orchestrator/context_compaction_internal_test.go`, `rollover_internal_test.go`; `pkg/model/rollover_test.go`; `pkg/demo/demo_durable_test.go` (the seeded durable task).
- CLI spec and route scope tables (`pkg/ui/mutating_routes_test.go`) cover the new routes.

### What is NOT proved
1. **A real agent compacts through `compact_context`.** On a real daemon (SQLite **and** PostgreSQL) with a scriptable fake agent, file a durable task, post ~30 comments across several runs, then have a run call `compact_context` with a handover. Check:
   - the cursor equals the last comment posted **before** the run started, even when a person comments mid-run (that comment must appear in the next prompt verbatim);
   - the next prompt (read from the run's recorded prompt) carries the handover and only post-cursor comments, and is measurably shorter;
   - `/tasks/<id>#comment=<id>` of a summarised comment still opens it (disclosure expands, highlight lands).
2. **`grain compact` both ways.** `grain compact <id>` with no file sets a standing request the next run's prompt honours first; with `-handover-file` it compacts at once and bumps `handover_version`. Writing the identical handover again confirms it (version unchanged, age reset).
3. **Staleness.** Drive runs/comments past the thresholds and confirm the `stale` badge, the prompt's stale note and `GET /api/tasks/{id}/context` agree.
4. **Brief edits.** Edit the brief from the UI and API: empty reason → 400; a limited role without the task's scope → 403; history lists who/why; the original description remains under its disclosure; the next prompt uses the brief.
5. **Rollover end to end.** By hand (`grain rollover`) on a durable task holding an open PR, a goal, a subscriber, a dependent task and a task parked on it: confirm all move to the successor and nothing is left pointing at the predecessor; a non-durable task is refused; a running task is not rolled mid-run by the reconciler (lower the thresholds via a seeded store or `faketime`). The successor's first prompt carries the brief and handover.
6. **Upgrade 131 → 139.** Upgrade a store with a long-running durable task from `61668e58`; `grain state check`, a dump/import round trip and the task page all work, and the task has no brief until one is set (the description stands in).
7. **UI.** The durable task page, Context panel, collapsed summaries and Edit brief at 1440×900 and 390×844, light and dark.

## §2. Paged task detail, keyset cursors and comments delivered on reopen

### What changed
- `GET /api/tasks/{id}` takes `comments_limit`, `comments_before`, `attempts_limit`, `attempts_before` (1–500), answering `olderComments`/`olderAttempts` counts (`c4c24838`). Without them it answers what it always did.
- The detail is now **built from bounded store queries** rather than trimmed from a cached whole record, with the head page cached by change token (`bec18394`). The task page and console session view load 50 comments and 20 runs, keep earlier pages across conditional polls, offer "Show earlier", and fetch earlier pages when a `#comment=` deep link targets an older comment. `compactedThrough` collapses summarised comments without a separate context read.
- Handover writers read only the newest handover comment.
- Keyset cursors replace offsets on paged lists (`a4751f32`), and `grain mcp`'s `list_grain_tasks`, `grain_inbox` and `ci_runs` page (`4600724b`).
- A person's comment on a closed task is delivered when the task is reopened, and the reopen event says so (`f15e32e6`).

### What CI proves
- `pkg/model/comment_pages_test.go`, `pkg/ui/list_page_keyset_test.go`, `list_page_walkthrough_test.go`, `reopen_delivers_test.go`, `pkg/cli/mcp_external_paging_test.go`; `ui/e2e/closed-task-comment-box.spec.js`.

### What is NOT proved
1. **Big records.** Seed a task with ~2,500 comments and ~600 runs (SQL or API) on SQLite **and** PostgreSQL. Measure `GET /api/tasks/{id}` with and without limits (size, latency) and confirm the paged answer is bounded and `olderComments`/`olderAttempts` are exact.
2. **Paging correctness under writes.** Walk `comments_before` to the start while new comments and runs arrive: no duplicate or missing ids, and the head-page cache invalidates on each change token (a new comment shows on the next poll).
3. **Task page.** "Show earlier" fetches strictly older slices; a conditional poll does not drop loaded earlier pages; a deep link to comment #1 of 2,500 loads back to it and highlights it; a compacted task (§1) collapses correctly from `compactedThrough` alone.
4. **Pending question, failure streak and usage.** On a paged answer for an `awaiting_reply` task whose question is older than the page, the pending question, failure streak, session names and per-run usage totals are still correct (compare with the unpaged answer).
5. **Reopen delivery.** Close a task, comment as a person, reopen: the task is queued once, the next prompt carries the comment, the event text matches; a task with an open fixes PR (`AwaitsAck`) behaves as documented.
6. **`grain mcp` paging** through a real external MCP client (`grain mcp` over stdio) on a deployment with >200 tasks: each page stays under the tool cap and the cursor walks to the end.

## §3. Secrets store consolidation and the KMS-wrapped secrets key

### What changed
- **One `KeySource`** (`14036c3e`): the store loads its key once and reloads once when the file is sealed to a different key. `grain state key retired [list] | delete (-all | NAME...)` and Settings → State list and delete `secrets.key.replaced-*` archives (`46ac53f1`), refusing the live key and the archive the store is still sealed to.
- **Export** refuses an unencrypted bundle that carries the key unless `-plaintext` (`4103614f`).
- **Redaction** for `read_grain_log` is served by the daemon's `POST /api/secrets/redact` (internal route) instead of each mcpserver decrypting the store (`3eb70ff1`).
- **Credentials into the store** (`42737f62`, `92737323`, `4c6ff8eb`, `131a2a91`): GitHub PATs, App keys and SSH keys (`github-credential-<name>`), the state/secrets repo tokens, the sandbox-access and package-cache CAs, the release-approval key, `-hub-token-file` and the relay token are imported on start, verified by a fresh decrypt and their files renamed `*.migrated`. `GRAIN_GITHUB_CREDENTIALS=files` reverses it for a downgrade. `setup.sh` seeds through `grain secrets set -value-file`.
- **KMS-wrapped key** (`c86e4c98`, `c41cd662`, `523cd76f`, `2c03dfd9`): a `grain-secret-key-kms-v1:` key file is unwrapped once through Cloud KMS (`GRAIN_KMS_ENDPOINT` for the fake), retried with backoff when KMS refuses; `grain state key wrap -kms <key>` / `unwrap` via `POST /api/state-repo/secrets-key/{wrap,unwrap}` with an in-process fallback; Settings → State shows the protection, key name and last unwrap; terraform/gcp wraps by default.
- **Typed-in credentials** (`65b2e1bf`, `da3b70cf`): `grain state check -base REV` fails a literal credential a config change adds, warns on one the base held, and stored literals move into the secrets store.
- **`request_secret` refuses grain's own credentials** — model, minter, signing and App keys (`f6d4d52e`, `10da49b2`).

### What CI proves
- `pkg/secrets/{keysource,kms,kmsfake}_test.go`, `pkg/gitproxy/credstore_test.go`, `pkg/daemon/{ca_store,loose_credentials,mcpserver_redact,redact_files}_test.go`, `pkg/releaseapproval/keystore_test.go`, `pkg/cli/{state_retired,state_wrap}_test.go`, `pkg/ui/secrets_redact_test.go`, `pkg/staterepo/statecheck/literals_test.go`, `tests/security/credential_exposure_test.go`.

## §11. External config repository `require_verified` and column-scoped config changes

### What changed
- **`require_verified`** (`ecfc3dd0`, `23eaf02f`, `4458d2e7`): `PullExternal` walks first-parent history from the last applied commit and moves only across commits grain can vouch for — a PR merge/squash with required approvals on its final head, a merge by grain's forge account, a good SSH signature from `allowed_signers`, or a SHA an unlimited role accepted. The first unverifiable commit is held with everything after it; the State pane names it with an **Accept** button. Settings live in `<data-dir>/state-repo.json`, set via `POST /api/state-repo/remote`.
- **Columns** (`a6e33031`): a `tables/grain_config.json` change is judged by the columns it alters — plain settings need `settings:write`, `git_credential`/`git_connections` `secrets:write`, agent backends `connections:write`, everything else `capabilities:admin`.
- External state repo PRs are checked against the deployment's branch (`65568055`).

### What CI proves

Confirm the first three apply, the unsigned push and everything after are held, the journal logs once, the State pane names it, Accept (unlimited role only; a limited role and an agent are refused) applies it and the rest. A force-push rewrite is held.
2. **Approval on the final head only:** approval of an earlier head is not enough.
3. **Columns.** Config-change proposals altering only `max_workers`; `git_connections`; `mcp_servers`; and an unknown future column: each needs exactly the documented scope to approve.
