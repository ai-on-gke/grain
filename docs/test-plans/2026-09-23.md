## 1. PostgreSQL Storage Engine & SQLite-to-PostgreSQL Database Upgrade Pipeline

Grain now supports native PostgreSQL database storage alongside embedded SQLite
(`a7a6a714d`, PR #1845; `30d00cb2f`, PR #1830; `48a7ca82b`, PR #1875). The database
layer provides dialect abstraction (`pkg/model/dialect.go`), daemon startup flags
(`--db-driver=postgres`, `--db-dsn=...`), Unix domain socket and TCP integration
for Cloud SQL Auth Proxy (`c9582ba2f`, PR #1869), and an online/offline migration engine
(`grain db upgrade-sqlite-to-postgres` and `POST /api/settings/db/migrate-to-postgres`).

### Existing coverage
- Unit tests for PostgreSQL schema building and SQL dialect translation in `pkg/model/postgres/`.
- Conditional integration test suite in `pkg/model/postgres/postgres_test.go` (skipped when no PostgreSQL instance is running).
- Migration schema verification and type mapping tests in `pkg/model/schemaupgrade/`.

### Gaps and unproven behaviors
- Live execution of the SQLite-to-PostgreSQL upgrade pipeline on a populated database containing realistic datasets (teams, tasks, runs, custom attributes, schedules, CI step logs, and console sessions).
- Verification of zero data loss, foreign key consistency, sequence generator synchronization (`team_sequence`, `task_id`), and timestamp timezone fidelity across the migration.
- Dynamic daemon switchover and reconnection to PostgreSQL without state corruption or stale in-memory cached references.
- Cloud SQL Auth Proxy unix socket connection resilience under transient proxy restarts and network drops.

### Walkthrough & test procedure
1. Initialize a populated SQLite database in `grain demo` with multi-team records, active schedules, queued tasks, completed runs, and custom attributes.
2. Spin up a local PostgreSQL instance (or embedded test container).
3. Execute `grain db upgrade-sqlite-to-postgres` targeting the PostgreSQL instance; verify clean table migration and sequence synchronization.
4. Start `grain daemon --db-driver=postgres --db-dsn="postgres://..."` against the migrated database.
5. Verify all tasks, runs, teams, and schedules are readable and writable. Enqueue new tasks and execute agent cycles to verify transaction correctness and sequence increments.
6. Test failure recovery: simulate a interrupted migration and assert that SQLite remains unmodified and PostgreSQL tables rollback cleanly.

Filed: **Walkthrough: PostgreSQL backend and SQLite upgrade pipeline (docs/test-plans/2026-09-23.md §1)**

## 2. Chunked Append-Only Live CI Step Logs Storage & Streaming API

Grain introduced an append-only chunked storage model for live CI step logs
(`26981bd66`, PR #1890). `LiveCIChunkStore` in `pkg/model/chunked_log.go` partitions
continuous step output streams into indexed chunks by byte offset, allowing concurrent
writers (running CI steps) and readers (the UI live log stream and MCP `get_ci_log`)
to tail logs in real time without unbounded in-memory buffer allocations or SQLite write locks.

### Existing coverage
- Unit tests for chunk chunking, boundary slicing, and offset indexing in `pkg/model/chunked_log_test.go`.
- Concurrency tests for simultaneous write/read access on isolated in-memory chunk stores.

### Gaps and unproven behaviors
- Live CI job execution streaming multi-megabyte log outputs from active container sandboxes into `LiveCIChunkStore`.
- Verification of MCP `get_ci_log` pagination and tailing (`offset`, `tail`, `size`) while a job step is actively running and generating output.
- Log rollover and max storage retention policy enforcement under high volume step outputs.
- Verification that multiple concurrent readers tailing the same active step do not cause lock contention or dropped byte segments.

### Walkthrough & test procedure
1. Launch `grain demo` with live CI execution enabled.
2. Trigger a CI workflow containing a step that emits high-frequency output over 30 seconds (e.g. `for i in $(seq 1 1000); do echo "Log line $i - $(date)"; sleep 0.03; done`).
3. Concurrently invoke `get_ci_log` repeatedly with progressive `offset` values, verifying seamless log streaming with zero gaps or duplicated lines.
4. Verify tailing behavior with `tail: 1024` while the job is running, confirming that the latest output chunk is returned immediately.
5. Verify post-completion log finalization and persistence in the database once the CI run concludes.

Filed: **Walkthrough: Chunked live CI step logs and streaming API (docs/test-plans/2026-09-23.md §2)**

## 3. Release Candidate Branching, Promotion Pipelines & Commit Triage Workflows

New release management workflows were introduced (`d3c9f0e17`, PR #1868; `dcbfa0bd3`, PR #1837;
`e7acf9fef`, PR #1850). The system formalizes Release Candidate (RC) lifecycle management:
automated RC branch creation (`release/v*`), automated triage and cherry-picking of `fix:` commits
into active RC branches, Conventional Commits specification enforcement across repo prompts,
and release promotion pipelines with mandatory installer end-to-end testing.

### Existing coverage
- Workflow declaration parsing and YAML syntax checks in `.grain/workflows/`.
- Repository prompt Conventional Commits standards configuration.
- Installer end-to-end testing script in `scripts/installer-test-image.sh`.

### Gaps and unproven behaviors
- End-to-end execution of the backport triage workflow when a PR with `fix:` conventional commit messages merges into `main`.
- Automated cherry-picking into active `release/v*` branches, verifying correct merge commit creation, conflict detection, and diagnostic notification.
- Release candidate promotion workflow: tagging, building guest images, validating installer test suite, and updating release manifests.

### Walkthrough & test procedure
1. In a sandbox test repository, create a release branch `release/v1.0.0`.
2. Commit a bug fix on `main` with Conventional Commit message `fix(dispatch): correct queue ordering for front tasks`.
3. Trigger the backport triage workflow; assert that the commit is automatically identified and cherry-picked cleanly onto `release/v1.0.0`.
4. Create a conflicting commit on `main` and trigger triage; verify that backport conflict detection generates a human triage review task rather than failing silently.
5. Execute the release promotion pipeline with dry-run flags; verify that installer e2e tests run and pass before release artifacts are staged.

Filed: **Walkthrough: Release candidate branching, backport triage, and promotion workflows (docs/test-plans/2026-09-23.md §3)**

- UI component rendering tests for ownership status badges.

### Gaps and unproven behaviors

- Live CI workflow dispatch security verification: triggering an untrusted `pull_request` event and proving that write-scoped capabilities are safely refused while trusted `push` events receive full capability grants.
- Verification that team-scoped config repos enforce task submission boundaries across different teams.

### Walkthrough & test procedure
1. Launch `grain demo` and navigate to `/repo/bwsalmon/grain` in the UI.
2. Walk through repository ownership states: verify badge rendering and toggle repository between managed and read-only.
3. Attempt to trigger a task dispatch against a read-only repository; assert that the UI and API prevent modification.
4. Simulate a CI event trigger for an external pull request requesting `package-publish` capability; assert that the capability is stripped and the job runs in a sandboxed read-only context.
5. Verify that team-scoped config repo settings allow submissions only from authorized team members.

## 6. Multiple Teams: Dispatcher Concurrency Isolation, Scheduling & Queue Prioritization

The Multiple Teams architecture was fully integrated across Grain (`b8ca58c33`, PR #1860;
`c9aea035c`, PR #1861; `e78f3d52f`, PR #1862; `768612adc`, PR #1870; `aa9a4b1a2`, PR #1865;
`5b423b825`, PR #1874; `384d47da2`, PR #1877; `945538843`, PR #1878; `c970a3362`, PR #1880;
`7fb0fe71d`, PR #1885; `720cdac72`, PR #1887; `ccff85b56`, PR #1886; `f7a1fdfa9`, PR #1888;
`58d08a6ed`, PR #1889; `411e966d4`, PR #1892; `0c29cd761`, PR #1872).
Teams provide multi-tenant organizational structure: independent backlogs (`ReadyForTeam`),
per-team concurrency caps (`max_workers`, `max_mergers`, `max_ci_jobs`), targeted schedule
reconciliation, team user permissions, and proposal team inheritance.

### Existing coverage
- Model CRUD and state repository persistence tests in `pkg/model/team_test.go` and `pkg/staterepo/`.
- Dispatcher concurrency isolation unit tests in `pkg/dispatch/`.
- UI component unit tests in `ui/src/components/TeamsPanel.test.jsx`.
- Metadata scalability benchmarks in `tests/e2e/scalability_test.go`.

### Gaps and unproven behaviors
- End-to-end verification of dispatcher concurrency isolation under live workload: proving that when Team A hits its `max_workers` cap, the dispatcher continues evaluating candidate tasks and dispatches ready tasks for Team B without latency spikes or starvation.
- Multi-team schedule reconciliation under live orchestrator loops: verifying that schedules targeted at different teams fire independently and honor per-team overlap policies.
- Live agent execution proposal inheritance: verifying that an agent running on a Team "platform" task generates child proposals tagged with `team: "platform"`.

### Walkthrough & test procedure
1. Launch `grain demo`. Create Team "platform" (`max_workers: 1`) and Team "apps" (`max_workers: 3`).
2. Enqueue 5 tasks for Team "platform" and 5 tasks for Team "apps".
3. Trigger dispatcher cycles; assert that 1 task from "platform" and 3 tasks from "apps" are concurrently active.
4. Complete an "apps" task; assert the next "apps" task is immediately dispatched while "platform" remains capped at 1.
5. Execute a live agent task in Team "platform" that calls `propose_task`; assert that the resulting child task inherits `team: "platform"`.
6. Configure team-targeted schedules; verify orchestrator ticks trigger independent executions for each team.

Filed: **Walkthrough: Multiple teams dispatch isolation, schedules, and proposal inheritance (docs/test-plans/2026-09-23.md §6)**
