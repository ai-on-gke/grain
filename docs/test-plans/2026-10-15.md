## 1. Team Scope in the Shell: Creation Forms, Pins, Top Bar, Paths and Deep Links

**Commits:** `3b15d9f00`, `badd810ec`, `5311ed15f`, `bc629a157`, `e1cb14849`, `626f41b96`, `67d81b58d`,
`1ac5f4314`, `3995c35f3`, `bfb89b7c5`, `eaf91470b`

### What changed
- **Creation forms take the selected team** (`3b15d9f00`, then `badd810ec`). A new task, session,
  schedule, suite, template or CI run inherits the team from the route and `TeamContext`. The first
  commit removed the "Target team" selects outright. The second put part of them back:
  - New task keeps "Target team" whenever the caller has more than one team to file into
    (`teamChoices.length > 1`).
  - Schedule, suite and template forms show it only when editing an existing row (`!isNew`), so a move
    between teams stays possible.
  - New session and the CI page lost it.
- **Pins per team** (`5311ed15f`). Pinned sidebar items are stored under `grain.pinnedNav.<user>.<team>`.
  Switching team swaps the list. A legacy per-user list is split onto the per-team keys once the
  sessions and boards load. The Customize overlay offers only the current team's sessions and boards,
  and labels a pin from another team "Team: <id>".
- **Top bar** (`bc629a157`). Team home and Team settings sit in their own group at the far right, after
  the crumbs in the DOM, so Tab reaches them after the path. On a phone they wrap onto their own line.
- **Lower-case team paths** (`e1cb14849`). Page paths spell team ids in lower case.
- **Session deep links** (`626f41b96`). `/t/<other>/session/<id>` for a session of another team moves the
  shell to the session's team once, then lets the reader pick another team with the chat open.
- **Suite templates across teams** (`67d81b58d`). The suite form offers every readable template, the
  target team's first, each labelled "In team X" when the menu spans teams.
- **Viewer New task hold** (`1ac5f4314`). A viewer of the team the dialog opens in sees the server's
  refusal beside the team, and Create task is disabled with it as the accessible description. Picking
  one of the viewer's own teams lifts the hold.
- **Director capabilities** (`3995c35f3`). A new team's seeded Director gets only the capabilities that
  team may hold.
- `bfb89b7c5` keeps keyboard focus on the switcher through a pick. `eaf91470b` counts the team home's
  work the way the task list does.

### What CI proves
- Vitests: `TopBar.test.jsx`, `NewTaskOverlay.*.test.jsx`, `SchedulesList.test.jsx`,
  `SuitesList.test.jsx`, `NewSessionDialog.test.jsx`, `CIPage.test.jsx`, `PinnedNavContext` tests.
- e2e: `teams-walkthrough.spec.js`, `team-home-setup-checklist-walkthrough.spec.js`,
  `team_declarations_ci_walkthrough.spec.js`, `recurring-composed-walkthrough.spec.js`.
- `pkg/ui` tests for the Director's capabilities.

### What is NOT proved
- The two picker commits together in a browser. `1ac5f4314`'s "picking one of the viewer's own teams
  lifts the hold" needs the New task picker. Check that a viewer of team A who is a member of team B
  still gets the picker and can file into B. Also check what a viewer with exactly one writable team,
  opening New task under the team they only view, can do.
- Each creation form under `/t/alpha/...` actually POSTs `team: "alpha"`, read back from the API.
  This is especially important for New session and the CI page, which have no picker left.
- Moving an existing schedule, suite or template between teams still works from its edit pane.
- Pin migration from a real legacy `grain.pinnedNav.<user>` key in `localStorage`, across two teams. Also
  that Reset in one team leaves the other team's pins alone.
- The top bar's tab order and the 390x844 wrap.
- A mixed-case team id typed into a URL, and old links with an upper-case team.
- A cross-team suite saved with another team's template, and the run it files.
- The Director of a newly created non-admin team, read back from `GET /api/sessions`.

### Walkthrough procedure
1. Start `grain demo -addr 127.0.0.1:0 -open=false` and build the UI. Create teams `alpha` and `beta`.
   Create users: an admin of both; a member of `alpha` who is a viewer of `beta`; a viewer of `alpha`

2. As the admin under `/t/alpha`, create a task, session, schedule, suite, template and a CI run request.

3. Edit the schedule, suite and template and move each to `beta` with the edit pane's Target team.
4. As the alpha-member/beta-viewer, open New task under `/t/beta`. The refusal shows and Create task is

5. Pins: seed a legacy `grain.pinnedNav.<user>` list mixing an alpha session, a beta board and a view.
   Reload. The list splits per team as `5311ed15f` describes, and the legacy key is gone. Pin, reorder

## 3. Repository Page in Tabs; Standing Work Switch

**Commits:** `c612d0be4`, `a65c1ccf9`, `3ea563982`, `ab2b18c2f`, `c94ea34c6`, `72720d29a`, `417cbd8e7`,
`32aab9020`, `1faed8a1f`, `d81d94b01`, `b5d9ba5b8`, `9b0cf6b07` (`main` only)

### What changed
- The repository page is tabs: Overview (summary strip, batches in flight, recent CI runs), CI, Merge
  queue, Agents, Branches, Releases (work ownership and release workflows) and Advanced (declarations
  and Remove). The tab rides in the URL hash (`/repos/acme/widgets#ci`). Every panel stays mounted, so
  unsaved edits survive a look at another tab, and the CI tab carries a red dot while a base-branch gate
  is unjudged (`c612d0be4`, `a65c1ccf9`).
- **Standing work switch.** `model.WorkOwnership`'s repository default is drawn as one on/off switch
  (`3ea563982`) and every piece of standing work now reads it through `model.RunsWorkItem`, each under
  its own item so an override can turn one piece back on (`ab2b18c2f`). The items:
  - schedules (a skip is recorded, with no catch-up on return);
  - scheduled workflow runs;
  - the base-branch check and its retries;
  - post-merge jobs;
  - ports;
  - triage and repair tasks;
  - releases.

  Hand-filed tasks, their CI, the merge queue and their repairs keep running.
- The two release switches stay in step (`72720d29a`). Repo settings are drawn disabled for a member who
  is not a repo admin (`417cbd8e7`) and for read-only readers of the release pane (`32aab9020`). A
  by-hand base-branch run is refused while the check is off (`1faed8a1f`) or for a read-only reader
  (`d81d94b01`). Port pairs, filters and port-types warnings show on the page (`b5d9ba5b8`).
- `9b0cf6b07` (`main` only) describes each disabled control by the server's refusal.

### What CI proves

  task still dispatches and merges.
- A per-item override turning one item back on with the default off.
- Deep links to each tab (`#ci`, `#releases`, ...), Back/Forward between tabs, an unsaved edit kept
  across a tab change, and the CI tab's red dot while the gate is unjudged.

## 4. Stale-Copy Save Refusal; Skipped Firings; Memory Agent Retired

**Commits:** `9d55be291`, `f98d67b43`, `3112fd9a9`, `66e6f170b`, `9c86d191f`, `987eb8575`, `babea026e`

### What changed
- Schedule, suite and template PATCHes may carry a `revision` (a digest of the editable content). A
  PATCH from a stale copy gets 409 with code `stale`, checked before validation and again in the store's
  write. A PATCH without a revision applies as before (`9d55be291`).
- The three panes send the revision they opened on. On a stale refusal the pane stays open with its
  edits and offers Reload, which remounts it from the saved copy (`f98d67b43`).
- Every skipped firing gets one row in `scheduled_firing_skip`: why (open task, unfinished run, open
  review, standing work off, repo off the target list, paused, team archived), when, and what became of
  it (held, fired late as #N absorbing later occurrences, or dropped). The schedules page shows the
  newest skip once nothing suppresses it; the pane lists all (`3112fd9a9`, `66e6f170b`, `9c86d191f`).
- The deployment-wide memory agent (`system:memory-agent`) is retired and deleted on every cycle that
  finds it. Each team, `default` included, has its own `system:memory-agent:<team>` with its own
  general memory row (`987eb8575`, `babea026e`).

### What CI proves
- `pkg/ui` and `pkg/model` tests for the revision check, including the store-level race.
- Vitests for `StaleEdit.jsx`. An e2e covers two tabs on one schedule.
- Orchestrator tests for skip rows and their outcomes, and the schedules endpoint test.
- `reconcileSystemSchedules` tests for the retirement.

### What is NOT proved
- Two browser tabs on a suite and a template (the e2e covers a schedule). Reload keeps nothing from
  the stale copy.
- A skip's whole life on a running daemon: held by an open task, then fired late when it closes with a
  later occurrence absorbed; and dropped (team archived or schedule paused).
- The skip rows' fate through the `grain/config` export (runtime table, so not exported) and restart.
- A `system:memory-agent` row re-imported from an old `grain/config` dump is deleted before it fires, and
  `default`'s team memory agent writes `default`'s general row.

### Walkthrough procedure
1. Start `grain demo -reconcile 2s`. Open one suite in two browser contexts. Save a change in the first,
   then a different change in the second. The second pane stays open with its text, shows the refusal
   and Reload. Reload shows the first save's values. Repeat for a template.
2. PATCH with no revision through the API; it applies.
3. Run a real daemon with a schedule every minute whose template's task is left open. After three
   minutes, the pane lists one held skip that absorbed later occurrences. Close the task. The firing
   happens once and the skip reads "fired late as #N".
4. Pause the schedule, wait, and check the skip reads "dropped" or as documented in
   `docs/schedules.md`. Archive the team and check the reason.
5. Import a `grain/config` tree whose `tables/schedule.json` still lists `system:memory-agent`. After one
   cycle the row is gone and nothing fired. List the system schedules: one memory agent per team.

## 5. Install and First Sign-In: Port 4242, Installing User as Admin, Channels, CLI Timeouts

**Commits:** `cbda0719d`, `9f7b35185`, `ee19e6964`, `e2e05e675`, `705d77285`, `7dd44b4c7`, `ac735ab44`,
`8c2ab162c`, `4511f14be`, `0a82c4cda`, `7912eda5c`, `7a71d2656`, `da0a34cac`, `26169101c`

### What changed
- Every install path defaults the UI/API to `0.0.0.0:4242` and the CLI to `http://127.0.0.1:4242`.
  Re-runs keep the address an installed unit already uses. A unit an older `grain init` wrote is pinned to
  `127.0.0.1:8420` (`cbda0719d`).
- `setup.sh` writes `/etc/grain/cli.env` and makes `GRAIN_ADMIN_USER` (default `$SUDO_USER`) a system
  admin with a generated password in `<data-dir>/admin-password` (`grain user bootstrap-admin`).
  `grain init -admin-user` does the same. Re-runs never reset a password or remove an admin
  (`ee19e6964`, `e2e05e675`).
- `GET /api/config` tells an unauthenticated caller when no account has a password
  (`noPasswordAccounts`), and the sign-in dialog shows a hint as a note (`e2e05e675`, `705d77285`).
- The task CLI has `-connect-timeout` (5s) and `-timeout` (2m), and stops retrying after one budget
  (`8c2ab162c`, `4511f14be`).
- Upgrades default to the channel the deployment follows, read off the tag it runs; `GET /api/upgrade`
  reports `channel` and `/api/upgrade/targets` reports `default` (`0a82c4cda`). `setup.sh` installs
  `latest` by default and keeps a re-run's channel (`7912eda5c`). A previewed source branch that does not
  exist is reported (`7a71d2656`), and version names and notes are never mixed up (`da0a34cac`,
  `26169101c`).

### What CI proves
- `tests/installer` host-mode tests for `cli.env` and the admin (`ac735ab44`).
- `cmd/grain` tests for `-admin-user`, CLI timeouts and the README line.
- `pkg/upgrade` tests for `ChannelForRef`.
- Vitests for the sign-in hint and the Upgrade pane.

### What is NOT proved
- `grain init` run for real (as root in the sandbox, with systemd if available, otherwise its
  `-dry-run`/unit-writing path) on a fresh host and on a host with an older unit: the address chosen,
  the admin created, the password file's mode and owner, and a re-run changing nothing.
- The sign-in page of a fresh daemon in a browser: the hint shows, no account name leaks, and it goes
  away once a password exists.
- The CLI against a stopped daemon and a black-holed address: one readable line within the timeout.
