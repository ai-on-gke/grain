## §1. Interactive-session message delivery — final-tool-call addenda, `chat`'s pre-post poll, question parking and `RecordDelivered`

### What changed (PR #289)
- **Addenda acknowledgement deferred** (`5fa17498`, `pkg/mcp/addenda.go`, `pkg/mcp/registry.go`): a comment the addenda poller attaches to a run's tool result is acknowledged as delivered only at the next tool call that does not end the turn. Turn-ending tools (`comment_on_issue`, `ask_question`, `nothing_needed`, `resume_later`, …) do not consume new addenda. Before this, a comment that arrived on the final tool call was marked delivered although the agent never had a turn to answer it.
- **`chat` polls before it waits** (`5fa17498`, `pkg/daemon/mcpserver.go` `daemonChat.Chat`): it checks for comments past `deliveredCursor` at once, both before and after its own post, rather than only after the first ticker interval.
- **Wake a resting console session on the first reply** (`5fa17498`, `pkg/ui/client.go` `addAttributedComment`): `WakeOnMessage` now runs before `reopenAcknowledgeable`. A session parked by `ParkConsoleSessionTask`, which holds both `PendingQuestionCommentID` and a `{message: true}` deferral, wakes on the operator's first reply instead of staying deferred.
- **`ProcessResult` re-checks for waiting messages** (`5fa17498`, `4d275302`, `pkg/orchestrator/finish.go`): `interactiveMessageWaiting` is re-checked around `parkedOnAQuestion`, `restOnGoal` and `CompletedAt`, so a comment that lands while a result is processed leaves the task queued, not parked, deferred or completed. `hasComment` is set after `FinalText` is relayed on goal tasks, so that text is never relayed twice.
- **`RecordDelivered` guarded** (`4d275302`, `22b9637f`, `pkg/ui/messages.go`): advancing `DeliveredCommentID` and clearing `PendingQuestionCommentID` / `PendingSecret` happen in one atomic `ObserveField` transaction. The marker is cleared only when the mark moves past a **human** comment posted **after** the pending question. A run's own `POST /api/tasks/{id}/delivered` can no longer un-park its question with a comment that predates it.
- **`PostAgentMessage` does not park an already-answered question** (`a011eed4`, `8825f43f`): if an undelivered human comment is waiting when the run posts a chat message, the question is not parked, and any earlier question marker is cleared. This applies only on a task whose run keeps a delivered mark. A task with no mark parks as before, which keeps the Inbox notifications walkthrough's returning question working.
- **In-process session wait** (`d9b19ef1`, `pkg/orchestrator/consolesessions.go`): the question marker is set after the initial poll, not before.

### What CI proves
- `pkg/mcp/chat_tool_test.go`: `TestAddendaDeliveredOnFinalToolCallIsNotAckedUntilNextToolCall`, `TestTurnEndingToolsDoNotConsumeNewAddenda`.
- `pkg/daemon/mcpserver_test.go`: `TestDaemonChatReturnsCommentPostedBeforeChatStarts`, `…DuringWait`, `…BackToBackCommentsBeforeAndDuringChat`, `TestDaemonAddendaOnFinalToolCallLeavesCommentUndeliveredInStore`, `TestDaemonChatDeliversCommentAcrossDaemonRestartGap`.
- `pkg/ui/messages_test.go`: `TestRecordDeliveredOnlyClearsPendingQuestionOnNewHumanReply`, `TestRecordDeliveredKeepsAQuestionAskedAfterTheHumanComment`, `TestPostAgentMessageDoesNotParkOnAQuestionAlreadyAnswered`.
- `pkg/orchestrator/interactive_test.go`: `TestInteractiveMultiTurnConversationMixingChatAndPlainTextExits`, `TestInteractiveConcurrentCommentDuringProcessResultLeavesTaskQueued`.

All of these drive the daemon or store in-process, with the agent's tool calls scripted.

### What is NOT proved
1. **The real sandbox CLI path.** The agent's tool calls reach the daemon through the in-sandbox MCP server and `POST /api/tasks/{id}/delivered` over the run's token, not in-process. Nobody has checked that a comment posted while a real run's final tool call (`comment_on_issue`) is in flight reaches the next run's prompt and is not marked delivered in the store (`sqlite3 … 'select delivered_comment_id from task …'`).
2. **Every timing window, end to end.** A human comment posted (a) before the run calls `chat`, (b) during `chat`'s wait, (c) during the turn's last ordinary tool call, (d) during the final turn-ending call, and (e) while `ProcessResult` runs. Each must be answered exactly once, by the same run or the next one. Record the task's state after each: `queued`, never `awaiting_reply` with nobody left to answer, and never `completed`.
3. **Question parking as a person sees it.** The run asks a question and is parked, so the task shows in the Inbox. A comment that predates the question must not un-park it, but a reply after it must. A `PendingSecret` request behaves the same way. The Inbox count and the task row agree throughout.
4. **A resting console session wakes on the first reply.** Let a console session rest (`ParkConsoleSessionTask`; on `consolerestserver`, `POST /e2e/end-exchange`). A single operator reply in the browser must dispatch it at once (`RunDispatchCycle`), with no second message and no wait for the deferral.
5. **Goal tasks relay `FinalText` once**, even when a comment lands during the relay.
6. **A daemon restart between post and delivery** (`TestDaemonChatDeliversCommentAcrossDaemonRestartGap`, done for real): the comment is delivered exactly once after the restart.

1. Start `consolerestserver` or a `grain daemon` (see above). Create one chat/console session and one interactive goal task.
2. For each window in "not proved" 2, script the agent side so you control when its tool calls happen. Use the stub framework or `consolerestserver`'s provider hooks. With a real backend, prompt the agent to call a long `run_command` (`sleep 20`) before finishing. Post the human comment from the browser (1440 px) in that window. Record the comment ID, `delivered_comment_id`, `pending_question_comment_id` and the task state before and after, and the next run's assembled prompt (`GET /e2e/prompts` on `consolerestserver`).
3. Do "not proved" 3–6 in order, in the browser, and confirm the Inbox at 1440 and 390 px.
4. Pin any deterministic gap as a Go test (`pkg/daemon`, `pkg/orchestrator`, or `tests/e2e` with the stub framework) or a Playwright spec on `consolerestserver`.

## §2. Warm session sandboxes across a daemon restart — recorded isolation keys, fail-closed adoption, `recreate_sandbox`, and framework stickiness

### What changed (PR #289)
- **Adoption keeps warm sandboxes** (`5fa17498`, `pkg/orchestrator/adopt.go`, `pkg/runhost/adopt.go`): `Claim.Sandbox` is carried across run-host and `hostd` adoption, so a warm session sandbox is re-adopted by `SandboxName()`. `ResumeAdoptedRun` now parks an interactive run's sandbox warm when the run completes.
- **Recorded isolation keys** (`4d275302`, `4eec19be`): a new table, `task_run_sandbox_key` (`run_id`, `sandbox_key`, `grants_key`). `pkg/model/schema.go` creates it with `CREATE TABLE IF NOT EXISTS`, with **no schema version bump** (still 78). `finishRunTx` deletes it, and the Postgres adapter and state-repo table list know it. `runOne` records the dispatch-time `sessionSandboxKey` and `sessionGrantsKey` for each run (`Store.SetRunSandboxKeys`). On adoption, `ResumeAdoptedRun` parks the sandbox warm only under those recorded keys. A run with no recorded row (dispatched by an older daemon, or one whose `SetRunSandboxKeys` failed) **fails closed**: its sandbox is released. The earlier lease/pinned-target fallback and `Store.RunPinnedTarget` are gone.
- **Recreated sandboxes** (`4d275302`): an adopted sandbox is released, not parked, if a mid-run `recreate_sandbox` rebuild could not restore its capability placements or isolated VM shape.
- **Ledger** (`4d275302`): `parkWarmSessionInLedger` runs after `deps.Ledger.Release`. A first-attempt warm sandbox, whose sandbox name is the run ID, therefore stays tracked as idle and is not lost from the budget.
- **Framework/model stickiness** (`5fa17498`, `pkg/daemon/adoptable.go` `preferPrevious` / `preferredOnly`, `pkg/orchestrator/model_failover.go`): an unpinned interactive or resumable-session task's next run tries its previous attempt's framework and model first, so `--resume` keeps its CLI session. It falls back to the rotation when that connection is paused on a usage limit or does not support the model.

### What CI proves
- `pkg/orchestrator/interactive_test.go`: `TestResumeAdoptedRunEnforcesWarmSandboxIsolationAndLedgerPark` (including the narrowed-task-without-keys subtest), `TestInteractiveRunHostAdoptionMidChatWithRecreateSandboxAndSubsequentTurns`, `TestInteractiveFrameworkStickinessAndUsageLimitFallback`.
- `pkg/daemon/mcpserver_test.go`: `TestAgentPoolPrefersPreviousFrameworkAndModelAndFallsBackWhenPaused`.
- `pkg/staterepo/tables_internal_test.go` and `fidelity_test.go`: the new table is classified.

These use fake run hosts and an in-memory ledger.

### What is NOT proved
1. **A real restart with a real run host.** Start a chat session on a `grain daemon` with the Docker run host (or Granule), and stop the daemon mid-turn (`SIGTERM`, then start it again on the same data dir). The run is adopted, the turn finishes, and the sandbox is parked warm. The next message reuses **the same sandbox ID** without a re-clone. Check the sandbox ID in `GET /api/tasks/<id>` `attempts[]` and the run host's container or VM list.
2. **Narrowing during the restart gap.** While the daemon is down (edit the store with `sqlite3`) or just before it stops (from the sidebar), remove a capability, narrow `writes` or tighten network access. After adoption, the sandbox must be released, not parked. The next turn gets a fresh sandbox with the narrower grants, and the old sandbox's run token is refused by the git proxy.
3. **Fail closed for pre-upgrade runs.** Delete the run's `task_run_sandbox_key` row before the restart, to stand in for a run dispatched by an older daemon. The adopted sandbox is released and the next turn dispatches fresh, with no error shown to the person.
4. **Upgrade.** Open a data dir created by a build from before `20d79d0b`, at schema 78, with the new binary. `task_run_sandbox_key` exists afterwards although `SchemaVersion` did not change. `grain` state-repo export and import, and the Postgres store if available, carry the table or skip it as `tables_internal_test.go` says. A finished run leaves no row behind.
5. **The budget ledger.** After a first-attempt session parks warm, `GET /api/metrics` / Settings → Sandboxes shows it as idle and counted. When the idle TTL expires it is released and the count drops.
6. **`recreate_sandbox` then a restart.** The agent calls `recreate_sandbox` mid-turn on a task with a capability placement, then the daemon restarts. If placements could not be restored, the sandbox is released; otherwise it is parked.
7. **Stickiness with real connections.** Configure two agent connections on different frameworks in the rotation. A session's second run stays on the first run's framework and model. Pause that connection (simulate a usage-limit pause), and the next run falls back to the rotation without failing. Pinned tasks ignore the preference. If only one real credential exists, use stub backends and say so.

### Walkthrough & test procedures
1. Build `grain` from `main`, and also from `20d79d0b^1` for step 4. Start a `grain daemon` with a data dir, `-sandbox-port-base=0` and the Docker run host. `tests/e2e` and `tests/installer` show the flags.
2. Do "not proved" 1–7 in order. Record sandbox IDs, `sqlite3` reads of `task_run_sandbox_key` and `run_lease`, the log lines for adoption, park and release, and `grain metrics` output.
3. Pin any deterministic gap as a `tests/e2e` test (stub framework, Docker run host if CI has it) or a `pkg/orchestrator` test.
4. **Trust boundary:** `pkg/orchestrator/finish.go` and `pkg/runhost/*` are trust-boundary paths, so a fix there gets a security review before it merges. Say so in the commit message.
5. Record in `docs/test-runs/<date>-warm-sandbox-adoption.md`.

## §3. `TaskChat` in the browser — optimistic comments, serialised back-to-back sends, and out-of-order polls

### What changed (PR #289, `74e6396d`)
- `ui/src/components/TaskChat.jsx`: optimistic outgoing comments stay visible while the `POST` and task refreshes are in flight, across `running` → `awaiting_reply` → `queued` transitions. A second message typed while the first is in flight is queued on a promise chain, not dropped. `loadSessionTask` ignores a background poll that resolves after a newer one (`ui/src/App.jsx`).
- `ui/e2e/interactive-session-chat.spec.js` covers this against `consolerestserver`, which gained session hooks for it.
- Same PR, `1116754e`: `patchTouchesTaskGrants` (`pkg/ui/agent_api_gate.go`) treats the priority-dispatch toggle as a grant edit under every spelling: `priority` (boolean), `priorityDispatch` and `priority_dispatch`. An agent's `PATCH /api/tasks/{id}` that flips it therefore needs `capabilities:admin` and a reason. This finishes `2026-11-01.md` §1 "not proved" 3, and §3 below checks it live because it is the same session sidebar.

### What CI proves
- `TaskChat.test.jsx` (jsdom), `interactive-session-chat.spec.js` (one Chromium project against `consolerestserver`), and `pkg/ui/agent_api_internal_test.go` / `task_priority_test.go` for the gate.

### What is NOT proved
1. **Phone width and dark mode.** The spec runs one viewport. Optimistic bubbles, a "sending" state and the queued second message at 390 px in light and dark: no overlap with the composer, no layout jump when the server's copy replaces the optimistic one, and no duplicate bubble.
2. **A slow or failing `POST`.** Throttle the network (Playwright `route` with a delay; then a 500). The optimistic comment says it failed and can be retried, or is removed with a visible error. It must never sit as if sent. A failed first send must not block or drop the queued second one.
3. **Three or more messages in a burst**, including one with an attachment, keep their order in the UI and in the store (`GET /api/tasks/<id>/messages`).
4. **Out-of-order polls on a real daemon.** Two tabs on the same session, with one posting while the other polls. Neither tab regresses to an older message list.
5. **Keyboard and focus.** Enter sends, Shift+Enter makes a new line, focus stays in the composer after a send, and the queued state is announced to a screen reader (an `aria-live` region or the button state).
6. **The `priorityDispatch` gate live.** With an agent token holding `api:tasks:admin` but not `capabilities:admin`, `PATCH /api/tasks/{id}` with `{"priorityDispatch": true}`, `{"priority_dispatch": true}` and `{"priority": true}` is refused, each naming `capabilities:admin`. `{"priority": 3}` succeeds. With `capabilities:admin` and no reason, the toggle is refused for want of a reason.

### Walkthrough & test procedures
1. Run `consolerestserver` as `interactive-session-chat.spec.js` does, or a `grain daemon` with the stub framework.
2. Do "not proved" 1–5 in Playwright at 1440 and 390 px, in light and dark. Take `make ui-screenshots` of the session page before and after any fix, and assert layout with bounding boxes where it matters (the composer is not covered, and the bubbles are in order).
3. Do "not proved" 6 with `curl` against the daemon, using agent tokens minted as `tests/e2e` does.
4. Add Playwright cases for any gap to `ui/e2e/interactive-session-chat.spec.js`, or a sibling spec. Restore any `demoServer` state in `finally`.
5. Record in `docs/test-runs/<date>-task-chat-optimistic-sends.md`, naming the pages, widths and themes shot. Attach a small crop to the closing note.
