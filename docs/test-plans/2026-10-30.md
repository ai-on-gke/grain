## §1. GitHub issue importer — per-repository import settings, "Imported" tasks, and Import issues now

### What changed
- **Importer** (`e93fdcae`, PR #194): schema 64 adds five `repo_config` columns (`issue_import_enabled`, `_repo`, `_label`, `_approved`, `_interval_seconds`). An `issue-imports` reconciler polls the source repository's open issues (the repository itself or an upstream, optionally label-filtered; default every 10 min, minimum 60 s) and files one task per issue no task stands for (`Store.TaskForIssue`: `WorkOrigin "<source>#N"`, or `Task.Issue N` on a same-repository source, in any state, so a closed task's issue is never re-imported). Tasks carry origin reason `imported`, title `[#N] …` / `[owner/name#N] …`, a body with URL, author, labels, description and the first five comments. Default unapproved; `issue_import_approved` makes them queue at once. `Task.Issue` is set only for a same-repository source (so `Fixes #N` never names an unrelated issue in a fork). The work-tree reconciler posts no progress comment on an issue whose only tasks are unapproved imports. `PUT /api/repos/{o}/{n}/settings` takes the settings, `GET` returns `issueImport`, `POST /api/repos/{o}/{n}/import-issues` runs a pass now. The settings are **Authority** in `declschema` (a repo's `.grain/settings.yml` cannot set them). `imported` joins the kind vocabulary (`expect.kind`, `list_grain_tasks`).
- **UI** (`a0a64bde`): an unapproved import reads **Imported** rather than Proposed (row badge, detail pane, accessible label) with the same Approve; an `imported` chip on list rows and board cards (tooltip names the source issue) survives approval; "Imported issue" is an Origin filter value. Repo page → Agents gains a **GitHub issue import** section (switch, queue-without-approval with a trust sentence, source, label, interval, **Import issues now** reporting read/imported/skipped); Overview lists the importer's state.
- Demo seeds one imported task (`5b46752c`); `docs/github-issue-import.md` (`7130d12f`).

### What CI proves
- `pkg/orchestrator/issueimport_internal_test.go`, `pkg/model/sqlite/issue_import_store_test.go`, `pkg/ui/issue_import_test.go`: import once, label filter, upstream vs same-repo `Issue`, approval default, interval floor, the manual route.
- `RepoPage.test.jsx`, `state.test.js`, `ui/e2e/issue-import-layout.spec.js`: the seeded imported task's chip/badge layout and the settings section rendering.

### What is NOT proved
1. **The settings section driving a real import end to end in the browser**: switching the importer on for a repo, pressing *Import issues now* against `-github-sim` issues, the read/imported/skipped counts, a second press importing nothing, and the new tasks showing as *Imported* in `/`, `/inbox` and the board.
2. **Approval and dedup across states**: approving an import (chip stays, status leaves *Imported*), closing it, and confirming the next pass does not re-import it; an issue labelled after the fact with the configured label being picked up by the next pass; a pull request in the sim's issue list not being imported.
3. **Upstream source**: `issueImportRepo` set to another `owner/name` — titles carry `[owner/name#N]`, `Task.Issue` is unset, the eventual PR body does not say `Fixes #N`, and no progress comment is posted upstream while the task is unapproved.
4. **Declared settings refused**: a `.grain/settings.yml` in the repo declaring any of the five fields is refused/ignored as Authority, with the reason visible where declared-settings errors surface.
5. **Interaction with §2's write path**: on a daemon with a grain/config repository, saving the import section answers `config_managed_externally` with the patch; the UI must show the refusal (`ConfigRefusal.jsx`) rather than a silent failure, and the settings must arrive once that config PR is submitted.
6. **Approved-by-default mode**: with *queue at once* on, an import dispatches (demo `-fake-ci`) without a person; confirm the UI's trust sentence is shown before saving.

## §2. grain/config as the only API write path — refusals, validated held config pull requests, and the host-local opt-out

### What changed
- **Internal mode refuses too** (`d887dea9`, PR #145): `checkSettingsWritable`/`…Unrehearsed` now answer a non-bootstrap settings write from the HTTP API with the rehearsed `409 config_managed_externally` (with the patch) whenever the daemon has a controller-local grain/config, not only with an external config repo. The refusal says it is grain/config, marks itself internal and points at `POST /api/state-repo/pull-requests`. grain's own code and a UI with no config repository (`grain demo`) still write directly. Bootstrap routes (agent-backend PUT/DELETE, GCP keys, CLI run locations, capability-server secret binding) use `checkBootstrapWritable`, refused only by an external config repo. `PUT/POST /api/settings` and `PUT /api/deployment` are split: a request changing only Models/Sandboxes bootstrap fields is written; anything else is refused whole.
- **Pre-review validation** (`00acf020`): `staterepo.ValidateCandidateConfig` — `staterepo.Check` on a `VACUUM INTO` snapshot, `CheckDispatchLiveness` (refuses `max_parallel < 1`, every connection disabled, `default_model`/director model with no enabled connection, `console_sessions` without the director), and `RehearseApply`.
- **Held config pull requests from a refusal** (`fef0ec3d`): `POST /api/state-repo/pull-requests` (settings:write, people only) takes a refusal's `change` array (+ optional title/body), refuses unknown ops and unclean/non-exported paths, applies it to the base tree via `git archive`, validates (422 with the report on failure), commits to `grain/task-<id>` and files a completed, not-submitted task on grain/config awaiting a person's Submit.
- **Opt-out** (`8a658fea`): `state-repo.json` `directConfigWrites: true` makes internal mode write directly again (read on every guarded write, no restart); external mode still refuses.
- **Config ceiling widened** (`dd0cd0a5`, PR #166): `standing_sandbox*`, `persistent_sandbox`, `gcp_key`, `template_*`, `schedule_*` are under `NeverAutoMergePaths`; `ValidateConfigPolicy` refuses them in `auto_merge_paths`; `TestSettingsTablesAreHeldUnlessBenign` guards future tables.

### What CI proves
- `pkg/ui/config_internal_test.go`, `config_refusal_test.go`, `staterepo_test.go`: refusal shape, bootstrap split, opt-out.
- `pkg/staterepo/validate_pr_test.go`, `pkg/daemon/config_pull_requests_test.go`: validation suite and PR creation over a temp repo.
- `pkg/staterepo/settingstables_held_test.go`, `pkg/trustboundary/state_test.go`: the ceiling.
- `ConfigRefusal.test.jsx`: refusal rendering.

### What is NOT proved
1. **A person's journey in the browser on a real daemon**: changing an ordinary setting (e.g. Settings → Tasks max parallel, a repo's default grants, a template) and getting the refusal; whether the UI offers to open the config PR from it — **`ui/src` has no caller of `/api/state-repo/pull-requests` today**, so check whether a person can get from the refusal to a held PR without curl. If not, that is a gap to fix (scoped: a button on `ConfigRefusal` that posts the refusal's `change`) or to file.
2. **The held PR's life**: the grain/config task it files appears in `/inbox` as awaiting Submit, Submit merges it, the next sync applies it and the setting changes; validation failure (e.g. `max_parallel: 0`, disabling every connection) answers 422 with a readable report in the UI.
3. **Bootstrap writes still pass** in internal mode (Settings → Models connection edits, sandbox fields, GCP key, CLI run location), and a mixed `PUT /api/settings` is refused whole.
4. **Opt-out live**: flip `directConfigWrites` in `state-repo.json` on a running daemon and the next write goes through; flip back and it is refused; external mode ignores it.
5. **Ceiling over a real policy**: `settings/config-policy.yml` listing `tables/template_*.json` or `gcp_key` in `auto_merge_paths` is refused; an agent auto-merge config PR touching a template is held for a person.
6. **Agent route refusal**: an agent token on `POST /api/state-repo/pull-requests` gets 403.

### Walkthrough & test procedures
1. Build; start `grain daemon` with a temp data dir and a controller-local grain/config (as `tests/e2e/standalone_local_merge_test.go`, without its `directConfigWrites`), `-sandbox-port-base=0`, UI on a free port.
2. In Chromium at 1440/390: make each change in gap 1 and gap 3; screenshot each refusal. Try to reach a held PR from the UI.
3. `curl -X POST $GRAIN_SERVER/api/state-repo/pull-requests -d '{"change": <refusal.change>}'`; open the filed task in the UI; Submit; wait for sync; confirm the setting. Repeat with an invalid change for the 422.
4. Opt-out toggle (gap 4), ceiling (gap 5), agent token (gap 6).
5. If gap 1 is real and the fix is small and safe, add the button with a component test and a Playwright spec against a real daemon (`de52b8ee` shows how the real-daemon harness opts out of config PRs; this one should opt in). Otherwise propose it.
6. Record in `docs/test-runs/<date>-config-repo-write-path.md`.

## §4. CI across a daemon restart — step reattach over the dial-out channel, channel-lost re-runs, and 503 while CI starts

### What changed
- **Granule steps over dial-out** (`f76a2e17`, `45502012`, `87e93460`, `f35ccb06`, `fe90633b`, `001ca6f0`, PR #128): `sandboxaccess.Runner` runs k8s-granule commands, CI steps, file placements and port forwards over the dial-out channel with cursor-based reattach. New `-k8s-granule-access=dialout|kubectl` (default kubectl; dialout refused at startup outside a pod or without `-sandbox-access-addr`) and `-k8s-granule-reattach-timeout` (2m). A job ending on a lost channel concludes errored with `infra: sandbox channel lost` and is re-run once, uncached, on a task branch as soon as the run ends; a pass there is not a flake; `flake_recheck: false` is respected. When dial-out never connects, the wrapper container's log tail is read (`891415d8`, PR #162).
- **Reattach across restart** (`4b741c74`, PR #155): schema 64 `ci_step_attachment` (run, job, step, sandbox, exec id, cursor), checkpointed every 10 s; `daemon.AdoptCIRuns` resumes each in-flight step from its attachment; a lost sandbox ends the job channel-lost (errored, re-run) instead of interrupting the run; a run none of whose jobs got a sandbox is stamped interrupted and its branch re-run by the reconciler.
- **503, not 404, while CI starts** (`eab9750f`, `7b27ecf0`, PR #190): `ci.ErrNotUp`; `GET /api/ci/runs/{id}` and run starts answer 503 until `LiveCI` is published; `/cli/ci/wait` and `run-job` retry inside their slice. The CI API listener gets sandbox port offset 4 (9732 on the default block) (`f32fa609`), fixing api-grant CI jobs refused at capability resolution.

### What CI proves
- `pkg/sandboxaccess/runner_test.go`, `restart_test.go` (real acceptor restart), `pkg/daemon/ci_reattach_test.go` (shared sqlite across a restart), `pkg/orchestrator/channel_lost_ci_test.go`, `pkg/daemon/k8s_granule_access_flag_test.go`, `pkg/daemon/ci_gate_ready_test.go`, `pkg/mcp/grain_ci_wait_notup_test.go`, `pkg/ui/ci_notup_test.go`, the port-offset source test.

### What is NOT proved
1. **A real process restart mid-step on the default (non-GKE) backend**: the reattach path is GKE dial-out only; on the sandbox's own backend the old readoption path must still work after `RecoverUnattachable` replaced `RecoverInterrupted*`. Run a slow CI step, `SIGTERM` the daemon, restart, and check the run completes (or is stamped interrupted and re-run when nothing was attached).
2. **The waiter's view across that restart**: `grain ci wait` from a sandbox (or the git proxy `/cli/ci/wait` with a sandbox token) during the restart window sees `running`/503-retry, never a 404 "forgotten" error, and resumes with `resume_run_id`.
3. **UI during startup**: `/ci` and a task's CI panel while the daemon reports not-up — what the person sees (an error banner, an empty list, or a "starting" note).
4. **api-grant CI jobs on a daemon with `-sandbox-port-base`** now resolving `release-gate-read` (the port-offset fix) — a workflow job declaring an api grant runs.
5. **Dialout on a real cluster** (kind or GKE): out of reach of a task sandbox without a cluster; covered by unit tests over a real acceptor. Say so if no cluster is available.

### Walkthrough & test procedures
1. Build; start `grain daemon` with a temp data dir and a local repo whose `.grain/workflows` has a job that `sleep 60`s and a job with an `api:` grant; `-sandbox-port-base` on a free block (not 9728).
2. Push a branch; while the sleep step runs, `SIGTERM`; time the exit; restart; read `ci_step_attachment`, the run's jobs and `/ci` in Chromium. Repeat killing before any sandbox exists.
3. During the restart, poll `GET /api/ci/runs/<id>` and run a `grain ci wait --resume` through the git proxy; record status codes and messages.
4. Check the api-grant job resolved its grant.
5. If a kind cluster can be brought up in the sandbox, try `-k8s-granule-access=dialout`; otherwise record why not.
6. Coordinate with the 2026-10-29 §9 walker (shutdown under load) — if that report exists by the time this runs, reuse its harness and do not repeat its measurements.
7. Record in `docs/test-runs/<date>-ci-restart-reattach.md`.

## §5. The sandbox `grain` CLI everywhere — `grain-sandbox` carries the full CLI, setup places the daemon's build, and `grain log`/`grain metrics` filters

- (`f7dae2c4`) Sandbox setup places the daemon's own `grain-sandbox` (found beside the executable) at `/home/debian/.grain/bin/grain` unless identical bytes are already there or at `/usr/local/bin/grain`; failure is logged and the image's grain kept; `protocol.ReservedPath` keeps capability placements off that name.
- (`e11997b7`) `deploy://grain.log` and `deploy://metrics` pass query filters; `grain log` gains `--since/--until/--min-priority/--contains/--max-lines`, `grain metrics` gains `--window/--since/--until/--repo/--author`.
- (`7ee70a27`) Run prompts name `grain pr open` and the grain CLI.

### What CI proves
- `pkg/orchestrator/sandbox_grain_internal_test.go`, `pkg/capability/protocol/protocol_test.go`, `pkg/cli/sandboxcli_test.go`, `pkg/daemon/sandbox_namespace_test.go`, `pkg/namespace/stage2_test.go`, `TestGrainSourceCheckoutWalkthrough` (PR #192).

### What is NOT proved
1. **A stale image**: a sandbox whose `/usr/local/bin/grain` is an old host-script-only binary receives the daemon's build at `~/.grain/bin/grain`, and `run_command`'s PATH picks it first; a sandbox already carrying identical bytes gets nothing placed (check timing/log).

4. **Placement failure** (read-only home, no space) is logged and the run still starts.
5. **A placement capability named `grain`** is refused rather than overwriting the CLI.

### Walkthrough & test procedures

3. From inside a run's sandbox, run every command in gap 2 and gap 3; record outputs.
4. Gaps 4–5 with a Go test if not reproducible live.
5. Record in `docs/test-runs/<date>-sandbox-grain-cli.md`.

## §7. Task targeting and parking — fork head labels as a branch, retargeted pull requests, `resume_later` reasons and goal clean-up, infra-review proposals

### What changed
- **Fork head labels** (`8c9ab0c1`, `77aad99d`, `8d591d72`, PR #178): a task's branch may be `<fork-owner>:<branch>`; it resolves via `GET /repos/{o}/{r}/pulls?head=` to the open PR it heads, the task adopts it as `external-pr`, bases on the PR's base branch and is told to start its own grain branch from `refs/pull/<n>/head` (the git proxy never pushes to a fork). Malformed labels (`a:b:c`, empty side, bad login) and labels no open PR heads get specific errors. The new-task form explains a well-formed label and marks a malformed one invalid; with "Create a new branch" ticked the old behaviour applies.
- **Retargeted tasks** (`06f3d706`, PR #149): a `LinkFixes` PR in a repo that is neither the task's target nor its writes is off target, pruned on the next tick, ignored by readers; moving a task drops off-target links and their holds.
- **`resume_later` reasons and goals** (`fbf3a1ab`, PR #137): the agent's reason survives a park on tasks/wake time into the next run's suspension note; replacing/deleting a goal clears its `task.no-progress` notification and goal deferral; GoalSection distinguishes `on_limit: notify` from `hold`.
- **Infra-review proposals** (`69d0da3f`, `fa45477f`, PR #197): `system:infra-review` proposals that explicitly target a source repository the deployment works in are relayed as ordinary tasks; config/state/unknown repos still need a recognised `grain_config` parameter.

### What CI proves
- `pkg/model/forkhead_test.go`, `pkg/orchestrator/forkhead_internal_test.go`, `pkg/ui/forkhead_test.go`, new-task form tests; `sync_retarget_test.go`, `retarget_pullrequest_test.go`; `wait_for_task_test.go`, `wait_task_test.go`, `GoalSection.test.jsx`; orchestrator relay tests.

### What is NOT proved
1. **Fork label end to end over `-github-sim`**: create a fork PR in the sim, file a task with its label from the new-task form (desktop and phone), confirm the `external-pr` link, base branch, body guidance, and that a run's push goes to a grain branch in the task's repo and opens a follow-up PR; error copy for a closed PR's label and for `a:b:c`.
2. **Retarget in the UI**: edit a task with an open PR to another repo; the old PR chip disappears, holds are gone, the next PR links cleanly, and closing the old PR on the sim does not close the task.
3. **Park reason in a real run**: a run calling `resume_later` with a reason and a task target; the next run's prompt and the task conversation quote it.
4. **Goal clean-up in the UI**: replace and delete a goal that has raised `task.no-progress`; the notification clears in the bell/Inbox and the deferral is gone.

## §8. Health surfaces — hostd offers new built-in host entries on upgrade, and GitHub idle-poll backoff

### What changed
- **hostd built-ins** (`c59df948`, `afaa3068`, `c631576a`, PR #207): hostd offers its own build's capability entries (`intree.HostdBuiltins`) missing from the allowlist, running hostd's resolved `versions/<version>/grain`, only while that binary is a regular file writable only by the allowlist's owners; an operator's entry always wins. Health's missing-entry list (`HostExecutorStatus.OnlyNeeded`) counts only entries something would run (host-git, a built-in named by an enabled `run: host` server, a configured built-in). Also the dial-out reconnect backoff is capped at 5 s (`b0ce9495`, PR #172).
- **Idle-poll backoff** (`f023f448`, PR #133): `PollSchedule` metrics (`Tracked`, `BackedOff`, `BaseSeconds`, `CapSeconds`, `MedianSeconds`, `MaxSeconds`) in `/api/metrics`, `grain metrics` and the `/system/health` GitHub API budget panel; `grain demo -github-sim -reconcile` advances live spend and per-PR backoff; `-github-webhook-url` / `-github-webhook-addr` deliver webhooks that reset backed-off intervals.

### What CI proves
- `pkg/hostd/builtins_linux_test.go`, `pkg/daemon/hostexec_missing_test.go`; `pkg/github/poll_test.go`, `pkg/demo/demo_reconcile_test.go`, `GitHubBudgetPanel.test.jsx`, `ui/e2e/github-budget-panel.spec.js`.

### What is NOT proved
1. **Upgrade with an old allowlist on a real hostd** (`grain hostd` as in `zz_hostd_test.go`): an allowlist lacking `grain-gchat`; Health shows no error while gchat is unconfigured; configure gchat and the entry is offered and works; an operator-edited entry is not overwritten; a group-writable binary disables offering.
2. **Backoff over time in the demo**: watch `/system/health` for several reconcile cycles — backed-off count rising, median/max growing to the cap; send a webhook to `-github-webhook-addr` and see the PR's interval reset; numbers agree between UI, `/api/metrics` and `grain metrics`.

## §9. Security fixes from the 2026-10-28/29 reviews — live confirmation

### What changed
- **Event-gated CI capabilities withheld** from any non-person `workflow_dispatch`/release start (`62ce8160`, PR #180; `WithholdEventGated` on requests and persisted plans).
- **Git signing only for a sandbox that may push** (`0953a905`, PR #164): `POST /_grain/git-sign` refuses a no_repo or read-only sandbox, and no longer falls back to the primary ambient credential.
- **`GET /api/tasks` honours `?repo=`** (`af8a6180`, PR #171) so repo-scoped agent credentials see only their repo.
- Config ceiling (`dd0cd0a5`) is walked in §2.

### What CI proves
- Unit and route tests in `pkg/ui`, `pkg/gitproxy`, `pkg/workflows`, `tests/security/routes_test.go`.

### What is NOT proved
1. **From a real sandbox**: a read-only task's sandbox calling `git commit -S` (via the configured signing program) is refused; a writing task's sandbox gets a signature that verifies against the host owner's key.
2. **From an agent token**: `POST /api/ci/runs` with `event: workflow_dispatch` of a workflow declaring `repo-write`/`package-publish` runs without them (the job's resolved capabilities say so); the same from a person gets them; a persisted plan replayed after a daemon restart keeps the withholding.
3. **Repo-scoped `gma_` credential** on `GET /api/tasks`, `?repo=` of another repo, and with no `?repo=`: only its repo's tasks, ETag/caching not leaking across scopes (two credentials alternating).

### Walkthrough & test procedures
1. Real `grain daemon` (`-sandbox-port-base=0`) with an SSH signing key configured; run a no_repo task and a writing task; try signing from each.
2. Workflow with gated capabilities; start it via person and agent tokens; inspect run plan and job capabilities; restart and re-check.
3. Mint two repo-scoped external agent credentials (`docs/agent-api.md`) and alternate `GET /api/tasks`.
4. Any failure is a security bug: fix if scoped (with a regression test) and flag it in the report for security review; otherwise file it.
5. Record in `docs/test-runs/<date>-security-fixes-live.md`.
