# Nightly new features test plan: 2026-10-02

This plan covers what merged into `candidate` and `main` after `docs/test-plans/2026-10-01.md`, which
stopped at `main` `5ae6d177a` (2026-10-01 08:15 UTC). It runs through `main` at `5e4f4a3dc`
(2026-10-02 12:35 UTC) and `candidate` at `cf9d6156c` (PR #2609, 2026-10-02 08:02 UTC). That is 286
non-merge commits on `main`.

**Where the code is.** `candidate` is an ancestor of `main`: `git merge-base origin/main
origin/candidate` is `cf9d6156c`. Only 64 commits of this batch reached `candidate`. Nearly all of
them are UI fixes and specs from yesterday's walkthroughs, plus their reports (§8). Everything else
is only on `main`:

- the RBAC and authentication wave from the 2026-10-01 repo-wide review;
- security hold v2;
- per-team merge batch size;
- `propose_task not_before`;
- host-sandbox removal;
- granule sandbox addresses;
- the database and operations hardening;
- the CI and MCP fixes.

`0b3ca375c` moved releases to a single-day cycle, so tonight's 18:00 UTC cut should put all of this
on `candidate`. The tasks for §1-§7 are filed against **`main`** anyway: until the cut, a run based
on `candidate` would test code that does not have the feature. Their reports become the
qualification evidence for that release candidate. §8 is filed against `candidate`. Each report must
name the commit it tested (`git branch -r --contains <sha>`).

Focus areas:

1. **Role-based authorization of writes.** Member and admin roles on task writes. Team-scoped standing work: schedules, templates, suites, boards and memory. Console sessions, credential routes, repo admins, DB grants, trusted release runs. The caller is the signed-in principal, never a name in the request body.
2. **Authentication and registration.** Registration is closed by default (`OpenRegistration`) and privileged names are reserved. Identities are case-insensitive. Password login is refused for accounts with no password. The first-user bootstrap only runs on an empty deployment. Session cookies are hardened. Google sign-in needs a verified email.
3. **Security hold v2 and proposal auto-submit narrowing.** The hold is bound to the classified head (`LinkTrustBoundaryCleared`), and the path list is `trust-boundary/v2`. A child that widens `Reads` or `Writes` is never auto-submitted.
4. **Merge queue and proposal scheduling.** Per-team `mergeBatchSize`. A halved batch re-admits its members instead of adopting moved heads. `propose_task not_before` / `deferredUntil`.
5. **Sandbox backends.** Host sandboxes are removed (`feat!`). Granule changes: `-granule-command` for a remote granule, grain-assigned VM addresses (`pkg/sandboxaddr`), the allocated-address check, and the NetworkNone bridge-port filter. The standing-sandbox supervisor and lease give-back. macOS console sessions.
6. **Database, upgrade and operator tooling.** PostgreSQL store fixes, and a confirmation token in the daemon log before a database upgrade. `-upgrade-allowed-branches`. The `grain export/import` passphrase and key are read from a file or stdin, and `grain import` restores safe file modes. Deployment secrets move to GCP Secret Manager. Single-day release-candidate cadence.
7. **CI and MCP correctness.** The Actions cache is scoped by branch. `**/` globs match like GitHub's. Quarantine no longer excuses cancelled or errored steps. MCP wait credit is cumulative. `list_ci_runs` keeps a `reads` repo. GitHub rate limits apply per credential.
8. **On `candidate`: keyboard row opening and yesterday's walkthrough fixes.** Base-branch refusal on write. Dangling links are reported. Team model defaults. Schedule title cache. Release refusal and confirmation. Executor token team check. Render-throw containment.

`tests/security` (`make security`, also run by the `go` job) holds the route-authorization table.
That table is the floor for §1-§2. Several commits in this batch lowered its baselines
(`cf0e3f78a`). The table proves the HTTP status each route returns to each role. It does not prove
what a person sees in the browser, or that a refused write left nothing behind.

## 1. Role-based authorization of writes

Commits:

- `60c2041b2`: standing work and memory scoped by team.
- `b70f8878d`: console sessions limited to the caller's team, and privileges limited to admins.
- `1b0699355`: credential and state-repo routes need a system admin.
- `2ae042359`: repo admins in `RepoConfig.Admins` can edit settings, and refusals are 403.

- `cf949ee00`: tunnel and relay requests are not treated as in-process.
- `639b3bd79`: refused CI and release starts answer 400/403, not a redacted 500.

What changed: every mutating route now asks the request's verified principal for a role in the
object's team. Before, it checked only that the caller was allow-listed and could read the object.
An object in a team the caller cannot read is a 404. An object they can read but may not change is a
403. Before, many routes trusted a `user`, `creator` or `author` field in the JSON body.

### Existing coverage
- `tests/security/routes_test.go` is the route-authorization ratchet. It covers each route against anonymous, member and admin principals.
- Unit tests sit beside each handler: `pkg/ui/*_test.go`, the `registration_gate_test.go` family, and the console-session and DB-grant tests.
- `ui/e2e/rbac*.spec.js` (Director fixture now a system admin, `ef4a27780`) covers a subset in the browser.

### Gaps
- No one has signed in as a real **viewer**, **member**, **team admin**, **repo admin** and **system admin** in the browser and tried each write from the UI. Nobody has checked that the UI hides or disables what the server refuses, or that a refusal shows as a readable error and not a blank pane or spinner.
- No check that a refused write left no residue: no comment row, no state change, no schedule fired, no console session written into `Config.ConsoleSessions`.
- A cross-team schedule or template that fires tasks into another team has not been tried end to end, including a move of an existing schedule into a team the caller is not a member of.
- A repo admin who is in no team (`RepoConfig.Admins` only) editing repo settings, and the same person trying to change the admin list, have not been walked.
- A body-spoofed `user` on team update, credential copy and broadcast has not been sent from a real signed-in session (cookie plus CSRF token, not a test principal).
- `POST /api/repos/{o}/{n}/release-runs` from a repo admin naming an unreviewed `grain/task-*` branch or a pinned commit has not been tried.

### Walkthrough & test procedure

Create five users through a trusted (loopback) admin session: `viewer`, `member`, `teamadmin` (admin of team `alpha`), `repoadmin` (only in `RepoConfig.Admins` of a demo repo), and `sysadmin`. Create a second team `beta` that holds tasks, a schedule, a template, a board and a console session.

Each must be a 404 or 403 with nothing written. Then list schedules, templates, suites and boards as `member` and check that `beta`'s objects are absent.

5. As `member`, call the credential routes (agent key, GitHub token, state repo, Codex login) with a valid cookie and CSRF token. Expect 403 before any body is read. A deliberately malformed body must still get 403, not 400.
6. Send team update, credential copy, broadcast and task comment as `member` with `"user":"sysadmin"` in the body. Expect a refusal, or attribution to `member`, and never to `sysadmin`.
7. As `repoadmin`, save repo settings (expect success). Then change `admins` (expect 403). Then start a trusted release run on `grain/task-9999` and on a pinned SHA (expect 403 each).
