## §3. PostgreSQL id sequence resync after bulk imports and on startup

### What changed (PR #1502, [Task #5592](/tasks/5592))
- `f953f5c5c`: explicit-id bulk inserts (`staterepo.ImportMigrated` during schema-change rebuilds, `Import` for state-repo restores, `ImportTables` / live settings merges) left PostgreSQL serial sequences at 1, so the next `task_sequence`, `task_comment`, `task_event`, `config_audit`, `suite_item`… insert failed with SQLSTATE 23505. New shared `model.SyncPostgresSequences` (re-exported as `postgres.SyncSequences`) advances only sequences at or below `MAX(col)`, never rewinds. Called inside staterepo's `importInto`, `importSchemaUpgrade` and `UpgradeFromSQLite`, and checked on PostgreSQL daemon store open and after the state-repo startup load (logging what it resynchronized). Documented in `docs/database.md` and `docs/host-setup.md`.
- `a9d5912ab`: a resync write begins a read-write transaction and re-checks under grain's advisory writer lock and single-writer lease fence before `setval`, so a stale pool that lost its lease cannot move sequences and concurrent `OpenStore` callers cannot rewind past newer allocations; `pg_catalog` queried in `CURRENT_SCHEMA()`, `setval` arguments bound.

### What CI proves
- `pkg/daemon/schema_upgrade_postgres_sequences_test.go` (rebuild, startup check), `pkg/model/postgres/staterepo_roundtrip_test.go` (Import/ImportTables, fenced resync), `pkg/cli/stateprepare_postgres_test.go` — all **skip without PostgreSQL** in the runner unless it is installed.

### What is NOT proved
1. **A real schema-change rebuild** on a live PostgreSQL daemon: start the previous release (`v3.8.0`) on PostgreSQL, create tasks/comments/events/audit rows, start a `HEAD` build that forces a rebuild (or use `grain state prepare`/the upgrade path the tests exercise), then file a task, comment, save a setting, add a suite item — no 23505 anywhere, ids continue above the imported max.
2. **SQLite → PostgreSQL upgrade** (`UpgradeFromSQLite`) of a populated store followed by normal writes.
3. **State-repo restore** (`grain/config` import into PostgreSQL) and a live settings merge, followed by writes to every table with a serial id.
4. **Startup self-heal of an already-broken store:** a store whose sequences are behind (from a `v3.8.0` rebuild) is repaired on the first `HEAD` start, the log line names each resynchronized sequence, and nothing is rewound on a second start.
5. **Two daemons / lost lease:** a second daemon opening the same database (standby or stale pool) never moves sequences; the active one keeps allocating.
6. **Non-default schema** (`search_path` set to a custom schema) resyncs that schema only.

### Walkthrough & test procedures
1. Install `postgresql`; build `v3.8.0` and `HEAD`. Script items 1–6 under `docs/test-runs/2026-11-15-postgres-sequence-resync/`, recording `SELECT last_value FROM <seq>` vs `MAX(id)` for each serial table before and after each step.
2. Run the Postgres-backed packages with `GRAIN_REQUIRE_POSTGRES=1 go test ./pkg/daemon ./pkg/model/postgres ./pkg/cli ./pkg/staterepo` and record that they ran (not skipped).
3. Fix any bug with a Postgres-backed regression test; write `docs/test-runs/2026-11-15-postgres-sequence-resync.md`.
