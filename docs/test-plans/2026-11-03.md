## §1. The hostd registry — per-hostd tokens, owner-bound admission, `grain hostds`, Settings → Hostds

### What changed
- **Registry** (PR #473, schema 92; `pkg/model/hostd.go`, `pkg/daemon/hostd_registry.go`): a `hostd` table (name, owner, labels, created_by, revoked_at), with the co-located hostd seeded as `local`, and `hostd_token` (SHA-256 digests, a `LocalTable` that is never exported). Tokens rotate. Revoking a hostd revokes every token it has.
- **Hub** (`pkg/hostd/remote.go`): `hostd.Remote` holds any number of dialing-in hostds at once, keyed by token. `X-Grain-Hostd-Name` must name the token's hostd or the connection gets 403, and a connection replaces only its own hostd's live session. The shared `-hostd-token-file` is deprecated for one release as a single hostd named by `-hostd-token-name` (default `remote`), with `-hostd-token-owner` for its owner (#542).
- **Routes**: `GET /api/hostds` (`settings:read`), `POST /api/hostds`, `PATCH /api/hostds/{name}`, `POST …/rotate`, `POST …/revoke` (`capabilities:admin`). `local` has no token and cannot be revoked.
- **Owner-bound admission** (PR #542; `pkg/hostd/connect_identity.go`, `pkg/ui/hostd_connect.go`): through IAP or another `IdentityVerifier`, `/api/hostd/connect` needs both the token and a verified principal equal to the row's owner. A row with no owner, or a proxied request with no verified identity, is refused, and the refusal names both identities and says how to set the owner. A loopback hostd (no forwarding headers, no assertion) and any daemon with no verifier still admit by token alone.
- **CLI**: `grain hostds list|register|set-owner` (`register -owner -label -token-file`, with the token file narrowed to 0600). `grain hostd -server … -name`. `scripts/migrate-local-to-gke.sh --hostd-owner` refuses quote and backslash input.
- **Settings → Hostds** (under Secrets & access): list, register (token shown once), rotate, revoke, owner and labels, connection status.
- **Remote executors removed** (PR #411, migration 87): `grain hostd` is the only host agent. Settings → Executors, `ExecutorsPanel` and executor tokens are gone, and `docs/executors-removed.md` says what replaces them.
- **Edition hostd entries** (PR #474): `intree.RegisterHostdEntry` lets an edition register non-capability built-in allowlist entries that `grain hostd -ensure-builtins` adds on upgrade (with `max_duration`, `env`, `pass_env`). An operator's edited entry is kept and reported.

### What CI proves
`pkg/daemon/hostd_registry_test.go`, `pkg/hostd/registry_linux_test.go`, `pkg/ui/hostds_test.go` and `hostd_owner_test.go` (owner match, missing owner, unverified proxy, loopback), `pkg/model/{sqlite,postgres}/hostd_store_test.go`, `tests/security/routes_test.go` (route scopes), `ui/e2e/hostds-settings-layout.spec.js` (layout), `pkg/hostd/ensure_test.go` and `tests/deploy/hostd_builtins_test.go` (a fake edition entry), and `scripts/migrate-local-to-gke_test.sh`.

### What is NOT proved
1. **Three real hostds at once**: `local` plus two remote hostds dialing one daemon, each shown connected in Settings → Hostds and `grain hostds list`. Killing one raises `hostd-disconnected:<name>` and leaves the others connected. Restarting it clears the notification.
2. **Token lifecycle live**: rotate while connected (does the live session survive, and does a redial with the old token fail?), revoke while connected (the session is dropped and the redial refused), and a token presented under another hostd's `-name` (403, logged).
3. **Owner-bound admission behind a verifier**: run the daemon with the simulated IAP from `docs/test-runs/2026-11-02-iap-end-to-end.md`. A hostd whose assertion's email matches the owner is admitted, one with another email is refused with the message naming both, one with no owner set is refused, and `set-owner` followed by a redial admits it. Loopback without headers is still admitted by token.
4. **The deprecated shared token** with `-hostd-token-owner`, beside registry hostds. It logs deprecation and appears as `remote`.
5. **The UI flows**: register in Settings → Hostds (the token is shown once and gone on reload), edit owner and labels, rotate, revoke, at 1440 and 390 px. Check that `hostd_token` never appears in a state-repo export (`grain state export` / the grain-state checkout) and that `hostd` rows do.

7. **`-ensure-builtins`** on an allowlist with an operator-edited built-in entry: the entry is kept and reported, missing ones are added, and Health shows the drift.

## §2. Per-task hostd routing — name pins and labels, capacity, waiting, per-hostd pauses; remote staging and carry

### What changed
- **Routing** (PR #540; `pkg/daemon/hostd_route.go`, `pkg/daemon/agents.go`): a task can be pinned to one hostd by name or to any hostd carrying a set of labels (`task_hostd`; `hostd` on `POST /api/tasks`, `PUT /api/tasks/{id}/hostd`, and a Hostd field under New Task → Advanced options). With no pin, work goes to the default hostd as before. `SelectHostd` resolves the selector per run, and the run's agent CLI starts through that hostd's client.
- **No fallback**: a pinned hostd that is registered but not connected, or any hostd at its allowlist `capacity:`, holds the task in the queue with the reason (`waiting for hostd <name>`). An unknown, revoked or unmatched selector is refused outright.
- **Per-hostd pauses**: a usage limit on an ambient credential (a CLI login on that hostd's machine) pauses under a key scoped to the hostd. The default hostd keeps the bare key.
- **Records**: `task_run_hostd` stores each run's hostd, instance and owner, shown on the task's attempts (API and timeline). `task_run_capability_audit.hostd` (schema 93) names the hostd the grant's server ran through. That is still always the default hostd, since `run: host` capability servers and host scripts start once, at daemon start.
- **Known limits** (stated in PR #540): runs on a non-default hostd start attached, not detached, so they are not re-adopted after a daemon restart. Capability servers are not per-hostd. There is no template or repo default for the pin.
- **Remote session** (PR #469; `pkg/hostd/stage_linux.go`, `carry.go`, `pkg/agent/hostd_remote.go`): OpStage stages a run's files on the remote machine under `~/.grain/hostd-stage` (0700 directories, 0600 regular files, `O_NOFOLLOW`, FIFOs refused, symlinks only to the codex login). OpListen/OpCarry carry the run's MCP endpoint back over a loopback listener that refuses any `Origin` and any `Host` but its own. claude, codex and agy each run against the staged home.
- **Beside it**: the demo's `-host-executor hostd` reaches Capability servers (#495). Self-repair's `run_host_command` is served from the forked mcpserver (#503). A host script's audit record is written before its exit frame (#455).

### What CI proves
`pkg/daemon/hostd_route_test.go` (pin, labels, a disconnected pin waiting, capacity holding and releasing, pause keys, the audit's instance and owner, against real hostds), `pkg/model/*/hostd_run_store_test.go`, `pkg/ui/taskhostd_test.go`, `tests/security/hostd_routing_test.go`, `pkg/hostd/stage_linux_test.go` (symlink, FIFO, mode and temp-area confinement), `pkg/agent/antigravity/remote_sessions_test.go`, the New Task and Timeline vitest specs, `pkg/demo/demo_host_executor_test.go` with `ui/e2e/cli-run-locations-hostd.spec.js`, and `tests/e2e/host_exec_confirm_walkthrough_test.go`.

### What is NOT proved
1. **An actual run routed off the default hostd**: a task pinned to `ws-a` (one of §1's remote hostds, in its own `HOME`) runs its CLI there. Check with the stub framework writing `hostname`/`$HOME` into its report, and `ps` showing the process under `ws-a`'s hostd. The task page's attempt shows `ws-a`, its instance and owner.
2. **Labels**: a selector `{gpu: "yes"}` that matches two hostds goes to one of them, and one that matches none is refused at `POST /api/tasks` with a message (not queued forever).
3. **Waiting and capacity live**: stop `ws-a`, file a pinned task (the queue reason says `waiting for hostd ws-a` on the board, the task page and `grain task show`), restart `ws-a` (it starts within one cycle). Set `capacity: 1`, file two pinned tasks (one waits until the first finishes).
4. **Daemon restart with a run on a non-default hostd**: what happens to the attached run? Record it, whether it is lost, re-queued or reported. It is a stated limit, but the operator-facing outcome must be clear and not a silent hang.
5. **Staging on a real remote home**: the staged tree under `~/.grain/hostd-stage` has the documented modes. A FIFO or symlink planted in a persistent home is refused with a clear run failure. The loopback carry listener answers 403 to a `curl` with an `Origin` header or another `Host`.
6. **Per-hostd pause**: simulate a usage limit on `ws-a`'s ambient credential (stub framework emitting the limit text). Only `ws-a`'s key pauses, and Settings → Models shows it scoped. A task on `local` still runs.
7. **UI**: the Hostd field in New Task → Advanced options (pin by name and by labels, validation messages), the attempts list on `/tasks/<id>` at 1440/390, light/dark.

## §3. Operator attribution — principal sources, `config_audit`, the verified principal on every write, the "none" actions, sticky `auto_merge: false`

### What changed
- **Principal source** (PR #436, schema 91): `model.Principal.Source` (`iap`, `token`, `access-code`, `loopback`, `in-process`, `session`, `sandbox`, `external-token`, `internal`, or a verifier's name), stored as `<p>_source` beside every `<p>_kind`/`<p>_id` (task origin/approval/behalf, `task_comment`, `task_pause`, `pipeline_pause`, `scheduled_upgrade`, `memory`, `memory_document`, `release_note`, `task_event` incl. new `behalf_*`). `ui.RequestActor(ctx)` is now the single source of every write's actor.
- **Verified principal on every human write** (PR #518): an IAP or verifier write records `{human, <email>, <verifier>}`, and the fallback records `{human, operator, access-code|loopback|in-process}`. Every guarded config write (settings, repo settings, templates, schedules, sessions) appends a `config_audit` row. Memory and release-note writes no longer believe an author named in their body. Commit trailers carry the verified creator's and approver's email.
- **Settings saves** (PR #504): the log says `grain ui: settings saved by <who>: changed <fields>` (field names, never values), and the state-repo commit says `Update grain state after a write by <who>`.
- **The §3 "none" actions** (PR #530): withdraw-approval, submit, retry, defer, undefer, park-until, wait-on, depends-on, reorder and pending-secret set each append a `task_event` (`approval-withdrawn`, `submitted`, …, `secret-set`, which names the secret and never its value). They are kept out of the timeline's steps and listed in the pipeline change feed. Release-secret and external-agent-token writes are audited.
- **Sticky `auto_merge: false`** (PR #447): every write that changes `auto_merge` appends `auto-merge-on`/`auto-merge-off` with the principal and the Go function that wrote it. `propose_task`'s `auto_merge: false` and a PATCH to false add an `auto-merge-declined` link that only Submit, a releasing approval or a PATCH to true lifts. Holds and carried clearances record `auto-merge-kept-off`.
- **Re-closes** (PR #456): a standing closure keeps its stamp when a task is closed again.

### What CI proves

The task still reads `autoMerge: false` with `auto-merge-kept-off` events naming each writer. Then Submit merges it, recording `submitted` and `auto-merge-on` by the person.

## §5. The release pipeline — breaking-change notes and gate, short soaks, the patch-tag guard, nightly as RC qualification

### What changed
- **Release notes** (PR #526; `scripts/release-notes.sh`): a "## Breaking changes" section first (from `type!:` subjects and `BREAKING CHANGE:` trailers, on first-parent commits and every commit a merged PR brings). A `write` subcommand writes `docs/releases/<version>.md` and the GitHub Release body. `check-breaking` exits 3 unless the release is a major bump that `RELEASE_MAJOR` in `scripts/release.conf` asks for, or `RELEASE_ALLOW_BREAKING=<version>` overrides it.
- **Short soaks** (PR #515; `scripts/release-from-trunk.sh`): the `-pending` tag records the soak length and FORCE (`Soak-Seconds`, `Soak-Forced`, a SHORT SOAK warning), as do the notification and a `pending_soak=` output. `approve` refuses a soak under `RELEASE_SOAK_HOURS` minus slack (22 h) unless `RELEASE_SHORT_SOAK_OK=true`, which the `vX.Y.0` tag message then records.
- **grain's approve route** (PR #525): `POST /api/repos/{owner}/{name}/pending-releases/{version}/approve` takes `{"short_soak_ok": true}` (reject refuses it), and `grain release approve -short-soak-ok vX.Y.0` sends it. The route is person-only, and `GRAIN_CI_RELEASE_SHORT_SOAK_OK` cannot be set from any workflow `env:`.
- **Patch-tag guard** (PR #519; `scripts/patch-tag-guard.sh`, run first in `release.yml` and `promote.yml`, `.github/` and `.grain/`): a `vX.Y.Z` with Z ≥ 1 fails unless it was cut on `release/vX.Y.Z` from `vX.Y.<Z-1>` with only picked commits, or everything past `vX.Y.0` is `fix:`. `scripts/release-patch.sh <vX.Y.Z> <sha>...` does it the right way (refusing `feat:` picks unless `ALLOW_FEAT=1`).
- **Release workflow** (PR #546): the container e2e runs `TestUpgradeFromReleasedVersions` with `GRAIN_UPGRADE_RELEASE_IMAGE` set, and each baseline runs under a throwaway local tag so the image under test survives.
- **Nightly as Stage 1** (PR #529): `nightly.yml` runs on every pushed `vX.Y.Z-rc.N` tag (not `-discarded`/`-retracted`). RC runs are not cancelled by later ones, and a `stage-1` job fails unless all 14 hosted jobs succeeded.
- **Watchdog** (PR #513): `pipeline.nightly-missing:<repo>` when `nightly.yml` (or `gcp-smoke.yml`) has not run on `main` in 26 h. `.grain/schedules/nightly-ci-review.yml` files a workflow-review task for every red nightly run on `main`.
- **Playbook** (PR #544): one person action per release, which is approve.

### What CI proves
`scripts/release-notes_test.sh`, `release-from-trunk_test.sh`, `release-patch_test.sh`, `tests/deploy` checks on the workflows, `pkg/ui` tests for the approve route, and `pkg/ci` StepEnv refusal tests.

## §7. Merge queue and pull-request reconciliation — stalled external checks, every member's stall, a PR merged after its task closed

### What changed
- **External-check nudge** (PR #485; `pkg/forge/external_checks.go`, `pkg/orchestrator`): third-party app checks (such as `cla/google`) are classified apart from grain's and in-repo Actions. When they hold an eligible auto-merge PR's head pending for `DefaultExternalCheckStallThreshold` (30 min) with no change, grain nudges once per head. Behind the base, it merges the base in to make a new head. Up to date, it pushes nothing, re-requests the check suite or run where the forge allows it, and posts a short PR comment and task note. If re-requesting is unsupported, or the check is still pending past a second threshold, it raises `pipeline.merge-stalled:<task>` and keeps the PR unmerged. Queue rows name the check, its pending age and whether it was nudged.
- **Every member** (PR #444): stalled repairs, a CI that gave up on a head and stalled checks escalate for every lane member, not only the first read. Every ready member's CI is prioritised.
- **Closed-task PRs** (PR #535; `closedprs.go`): a read-only `syncClosedPullRequests` pass records a PR merged by hand after its task was closed (outcome, the blocked note cleared, and `until: merged` waits met).
- **GHES and command forges** (PR #534): node-ID GraphQL mutations (`resolveReviewThread`, `enqueuePullRequest`) go to the repository's own host.
- **Actions listings** (PR #490): GitHub Actions runs are paginated, with a `--workflow` filter on `grain ci list`.
- **Relay** (PR #496): `comment_on_issue`'s own body is relayed rather than a longer final text.

### What CI proves
`pkg/forge` classification and stall-window tests, `pkg/orchestrator` nudge, every-member and closed-PR tests, the `-github-sim` forgerouter test for node IDs, the pagination tests, and `effectiveCommentOnIssue` tests.

### What is NOT proved
1. **Nudge on `-github-sim`**: an auto-merge PR whose simulated `cla/google` stays pending. Lower the threshold with `SetExternalCheckStallThreshold` (or its flag, if one exists, otherwise a test hook in `consolerestserver`). Exactly one nudge per head, behind-base (a merge commit) and up-to-date (a re-request plus a PR comment) variants, then `pipeline.merge-stalled:<task>`, with the queue row and task page saying what grain did. A PR held for a person (Submit, review, paused) is never nudged.
2. **Two-member lane**: the second member's stall escalates while the first is green and merging.
3. **Hand-merge after close**: close a task whose PR is blocked, then merge the PR in the sim. Within a cycle the outcome reads merged, the blocked note is gone, and a task waiting `until: merged` on it resumes.
4. **Node-ID routing**: a repository on a second simulated host. `grain pr resolve` from a sandbox and the MCP `resolve_review_thread` both reach the right host (the sim's request log).
5. **Pagination**: seed more than 100 workflow runs in the sim. `grain ci list --provider github-actions --workflow nightly.yml --since 26h` lists the right ones, and the watchdog's §2b query (§5 item 6) agrees.
6. **Relay**: a scripted agent that calls `comment_on_issue` with a short report and then emits longer text. The task's closing note is the short report.

### Walkthrough & test procedures
1. `consolerestserver` or a real daemon with `-github-sim` (shared step 3). Read `docs/test-runs/2026-11-01-review-merge-lifecycle.md` and any `2026-11-02` merge-walk report that has landed first. Do not repeat their steps.
2. Script items 1–5 under `docs/test-runs/2026-11-03-merge-reconcile/`. Item 6 with the scripted provider.
3. Pin gaps as `pkg/orchestrator` or `tests/e2e` tests. Record in `docs/test-runs/2026-11-03-merge-reconcile.md`.

## §8. Sandboxes — Granule VM memory headroom, the open-network egress policy, `guestforward`, a persistent package-cache CA, codex isolation

### What changed
- **VM memory** (PRs #527, #532): a Granule VM's cgroup limit is guest memory + max(1024 MiB, 25%) (`orchestrator.GranuleMemoryLimitMB`, `model.VMMHeadroom`), capped at host memory (`-memory-limit-mb`) or the largest node's allocatable memory, and charged to capacity.
- **Egress NetworkPolicy** (PR #442; `deploy/kubernetes/networkpolicy.yaml` `grain-sandbox-egress`): open-network sandbox pods keep the internet but lose the metadata server, private, link-local and cluster CIDRs and in-cluster capability `serverUrl`s, while still reaching grain's pod and cluster DNS. `network: none` pods are deliberately not selected. `hostinit` re-applies the file on upgrade.
- **`guestforward`** (PR #524): Granule forwards into sandbox pods over `pkg/guestforward`.
- **Package-cache CA** (PR #483): the root CA persists at `<data-dir>/package-cache-ca.pem` (0600, rotating within 30 days of expiry), so adopted CI sandboxes keep trusting the cache across a restart.
- **codex** (PR #522): on codex-cli 0.166.0, `shell_tool`, `unified_exec`, `view_image` and `apply_patch` are switched off one by one. The pin is bumped. claude 2.1.316 and agy 1.4.12 are pinned too (#510).

### What CI proves
Unit tests for the memory arithmetic and capacity accounting, manifest-parsing tests for the policy, the granule job (`Tests / granule`), `pkg/pkgcache` CA persistence tests, and the live codex MCP-only test where it runs.

### What is NOT proved
1. **Memory on a real Granule VM** (needs KVM, `/dev/kvm`; skip with a note if absent): start a sandbox with 2 GiB and check the container cgroup's `memory.max` = 3 GiB. Run `dd` of a multi-GB file after filling the page cache, and the VMM survives. Health/capacity shows the headroom charged.
2. **Egress on kind + Calico** (the hosted job `cfba4672` added, run locally if Docker allows `kind`): an open sandbox pod can `curl https://example.com`, cannot reach `169.254.169.254`, a ClusterIP Service or another pod, and can reach grain's pod and DNS. A `network: none` pod still reaches nothing.
3. **CA across restart with adoption**: a Docker CI sandbox fetching through the package cache, a daemon restart, adoption, and the fetch still verifying. Delete the CA file and confirm it rotates and the next new sandbox trusts it.
4. **codex isolation**: with codex credentials only (skip otherwise), the MCP-only probe across profiles. Without them, check the written `config.toml`/`environments.toml` in a stub run's home.

### Walkthrough & test procedures
1. Check `/dev/kvm`, Docker and `kind` availability first and record them. Run what the sandbox allows and say plainly what was skipped and why.
2. Scripts under `docs/test-runs/2026-11-03-sandbox-resources/`.
