# Current gating → extensible MCP gates: migration coverage

**Source baseline:** `e253df886` (2026-11-16), including Task #50's merged action-binding design (PR #1703). Documentation audit only: no runtime, deployment, grants, forge rules or implementation tasks change. The repository's [contribution instructions](../design/playbook/contributions.playbook.md) and [specification](../design/spec/contributions/contributions.spec.md) apply.

The proposed model can represent the current families of decisions, but is **not ready to enforce them**. Compatibility requires importing actual predicates and exceptions, centralizing their decision writers, and establishing a credential/route boundary for protected effects. A gate result alone cannot prevent an agent from merging.

The authority is the [gate design](../design/design/mcp-gates.design.md), [MCP gate specification](../design/spec/mcp-gates/mcp-gates.spec.md), and Task #50's [action bindings and protected operations](../design/spec/mcp-gates/action-bindings.spec.md). Task #47's [snapshot/readiness transport, MGS-11](../design/spec/mcp-gates/mcp-gates.spec.md#MGS-11) and [transcripts](../design/spec/mcp-gates/examples/README.md) are available and remain unchanged. [Tracked resources](../design/spec/tracked-resources/tracked-resources.spec.md) supplies observations/identity, not decisions. This audit adds coverage, not another protocol or finalized evaluator API.

## Reading the mapping

**G** = guard on an operation; **O** = task outcome/completion obligation; **L** = Grain lifecycle/wait policy; **S** = scheduling/resource constraint; **P** = permission/admission control. One behavior can span these categories, but satisfying one never substitutes for another. Evaluator labels below describe responsibilities, not deployed tool names. `change.merge`/`change.submit` are Task #50's proposed registry examples, not existing endpoints.

**C** means preserve the stated legacy behavior on explicit import; **Δ** identifies a recommended or already-proposed intentional change requiring an explicit contract/admission decision. Unless stated otherwise, reevaluation follows relevant authoritative observations plus bounded polling/reconciliation, with freshness/head/policy changes invalidating prior results. Operator controls are server-authorized actions; UI badges, prompt instructions and free text confer no authority.

## Entry points and what can prevent bypass

The [Task #50 boundary requirements, AGB-5](../design/spec/mcp-gates/action-bindings.spec.md#AGB-5) are prerequisites, not current deployment guarantees. The following source routes must converge by **effect**, including taskless operations and guards attached by other tasks (AGB-2's inherited policy union and resource index).

| Caller/route traced | Current boundary and limit | Migration boundary |
|---|---|---|
| Agent terminal/MCP → sandbox tools; `grain` CLI → proxy → controller API; controller MCP → generated route → same handlers | [Proxy CLI actions](../pkg/gitproxy/cli_actions.go), [controller API bridge](../pkg/ui/agent_api.go), [API gate](../pkg/ui/agent_api_gate.go), [scope definitions](../pkg/model/agent_api.go) enforce grant/repo scopes, self-mutation rails and attribution. Sandbox CLI refuses dangerous/model-only scopes; controller MCP is a distinct authorized channel. Agents cannot enable auto-merge/Submit through those task APIs; limited roles cannot accept findings/force. These rails are not a universal forge mutation firewall. | Retain authentication/RBAC/reason/audit checks, then normalize all protected requests to executor bindings. Discovery or a `met` result grants nothing. Agent-selected task/tool aliases cannot select a weaker guard set. |
| Agent Git smart HTTP/SSH/command forge → credential proxy | [`Authorize`](../pkg/gitproxy/authorize.go), [`AuthorizeRefUpdates`](../pkg/gitproxy/refupdates.go), [protocol parser](../pkg/gitproxy/protocol.go), [command forge](../pkg/gitproxy/commandforge.go) restrict repository and default task-branch writes. Borrowed branches cannot be rewritten. **Exceptions:** template-declared pushes and `repo#write` grants can permit other refs, including base effects; config proposals have a separate path. | Base-ref writes/merge/auto-submit/queue effects must be executor-controlled or impossible with that identity. Preserve legitimate feature-branch edits; validate declared push/any-ref exceptions rather than treating all Git as safe. A generic authenticated tunnel is insufficient. |
| Person UI/CLI/API → Submit, acceptance, force, CL/config approval; automation → merge/release/queue | [Submit](../pkg/ui/client.go), [force/PR alias](../pkg/ui/merge_gates.go), [CL submit](../pkg/ui/change_submit.go), [config approval](../pkg/ui/task_config_change.go), [queue](../pkg/orchestrator/sync.go), [merge identity](../pkg/github/mergeidentity.go) have separate decision/effect paths today. Merge can fall back to push identity when no separate merge credential exists. | One executor for admitted protected effects, including automation and taskless operations. Approval evidence, override authority and ordinary execution permission remain separate. Fence old daemons/routes; no legacy queue left running beside an enforced adapter. |
| Credential placement/mint/refresh and external automation | [Sandbox proxy credentials](../pkg/mcp/git_credentials.go) are readable local proxy tokens, bounded server-side by live task/TTL/revocation; [refresh](../pkg/orchestrator/sandboxtoken.go) extends their lifetime. [Named Git credentials](../pkg/capability/githubtoken/githubtoken.go), [SSH](../pkg/mcp/ssh_git_credentials.go), [raw disposable GitHub token](../pkg/capability/githubsandbox/githubsandbox.go), [registry push](../pkg/capability/registrypush/registrypush.go), [package refresh](../pkg/capability/packagepublish/refresh.go), [GCP keys](../pkg/capability/gcpkey/gcpkey.go) and [release tools](../pkg/capability/release/release.go) are distinct authority paths. Signing/publishing capability mints retain CI-only event/repo restrictions, but capability admission does not guard every subsequent effect. | Inventory **effective rights**, issuance/refresh, ambient/CI credentials and alternate hosts/tools per resource/caller. Privileged credentials belong only to narrow executor adapters, or enforced protocol/ref/route restrictions must remove direct protected effects. Repo-scoped/no-admin GitHub contents-write is not proof of “cannot merge.” |

Prevention therefore requires exclusive control of the admitted agent/automation cohort's integration credentials/routes, canonical inherited policy resolution, current-context evaluation, fenced intent/lease/lock ownership and conditional side effects. GitHub's expected SHA rejects a changed head; it cannot freeze every external review, base or policy version. Forge rules/exclusion must close the remaining race for the promised guard, or AGB requires refusal (`boundary_unavailable`). Deferred forge queues need a protected **final execution**, not merely checked enrollment.

Independent people, PATs, apps, SSH identities, workflows or bots with outside write/merge rights can still integrate outside Grain unless separately constrained. Such integration is observed and attributed **external**, not described as guard-approved. No live credential/rules audit was performed here. With bypass credentials remaining, the proposed cohort must be refused/held or observation-only with **no Grain protected execution**, as AGB-5 specifies; this is a future admission rule, not a claim that today's legacy deployment has been stopped. Prompts, hidden buttons and `auto_merge=false` are not security enforcement.

Configuration deserves its own protected effect. [`pendingConfigChangeFor`](../pkg/ui/task_config_change.go) requires a human, the displayed proposal head, and every changed surface's scope from [`StateScopes`](../pkg/trustboundary/trustboundary.go). [`MergeConfigChange`](../pkg/daemon/config_change.go) rechecks proposal head/base, merged-candidate schema/liveness validation and clean checkout under its lock before local merge, then applies through state sync. Approval records a merged-but-not-yet-applied result if sync fails; merge and application are distinct facts. Reuse these validators/adapter; bind approval/application to exact proposal/head/base/config revision. Task #50 does not finalize the config-apply registry identity/conditional contract. Runtime settings/grant/policy edits must retain existing RBAC and cannot let an agent relax its own inherited protection. This deployment's configuration lives in `grain/config`, not this source repository.

## Representative end-to-end flows

These show the proposed migrated ownership; legacy differences are marked in the matrix, especially direct PR/CL closure and closure-only dependencies.

1. **Implementation → merge:** admit approved task and schedule resources; run produces H1/PR and report. Collect H1 CI, ordinary/security/path reviews and eligible Submit approvals. Review unmet → proposed executor blocks the agent's merge request without a forge call. Accepted current-H1 evidence + caller permission → locked/context-fenced merge intent and expected-H1 call; reconcile receipt. H2 invalidates H1 evidence. Completion consumes observed integration and still waits on required children/report/message disposition. Merge readiness is not integration.
2. **Review findings:** review delivery succeeds by reporting findings; parent merge guard stays unmet. Owner reply queues fix/re-review, not approval. Thread resolution is not acceptance. A clean relevant re-review, or authorized exact-review/gate/head acceptance, resolves that disposition; other reviews/CI/Submit remain. A force/repair exception can integrate before review finishes only with recorded continuing review ownership and legacy post-merge handling retained.
3. **Report acknowledgement:** no change, standalone report → delivered and needs receipt. Human reply means continue; acknowledgement/Close means receipt. Import child-report close-on-answer and configured nothing-needed ack separately. A pending question, unseen message or required outcome blocks new successful closure; receipt never approves code. Goal reports rest until goal/policy permits close.
4. **Required child fails:** ordinary legacy dependency still blocks while child is failed/open; if later canceled/closed it releases legacy dispatch/`tasks-closed until=closed`, without proving success. A migrated **success-required** child remains unmet after failure/cancellation. Parent may continue independent work and request authorized repair/replacement/waiver. A settled wait exposes failure; it cannot silently weaken the completion predicate or clear a merge guard.
5. **Repair goal:** reproduced base failure creates repair with base-green goal; own report/nothing-needed rests. Its own PR still needs required CI, even if eligible human-gate repair exception applies while base is red. New base confirmation/non-reproduction satisfies imported health predicate; optional publishing/nightly stays independently required. Missing release row counts only under explicit legacy import; unavailable required provider never counts. Settle run and revalidate before close/rest.
6. **Standing director:** person-closes policy survives ordinary turns and healthy periods. A new message wakes evaluation, which chooses useful work or a durable rest; explicitly required children hold that request's outcome, advisory children do not. Capacity/priority privileges grant no merge bypass. Authorized successful person-close requires processed messages, settled/transferred operations and remaining obligations met/waived; cancel records cancellation. Preserve rollover lineage and resting subscriptions.

## Reuse, authority handoff and ordering

Keep collectors: CI/check runs and confirmation, forge/CL observation, path/rule classification, review tasks/findings/questions, approvals, release/qualification/publication observations, notifications and message delivery. Feed immutable, scoped snapshot records into pinned read-only evaluators. MGS-11 requires complete declared domains, explicit unavailability, retained snapshot pages, final-only result/state acceptance and replayable readiness; `needs_data`, timeout or an expired page is not a readiness decision. Do not duplicate Task #47's wire schema. Action-profile 3.0 must be separately negotiated as specified by AGB-3 over that same transport.

Reuse action mechanics behind adapters (GitHub expected-head merge, CI start/retrigger, review/repair task creation, CL Submit/sync, config validation/application, release workflows). The executor supplies policy resolution, authorization, version fencing, durable intent/idempotency and uncertain-outcome reconciliation. Existing code is not evidence that every adapter already satisfies those requirements.

| Existing writer family | Handoff for migrated authority |
|---|---|
| Finish/report/nothing-needed/keep-running, `finishWithPullRequest`; review-task close; `recordPullRequestEvents`, landed detection, CL `RecordSubmitted`/wake | Record facts and request dispositions. Stop direct completion/close/requeue decisions for migrated tasks; integration receipt does not itself close. |
| `actOnGoal`, `meetGoal`, `reconcileMetGoalCloses`, base/nightly callbacks, goal limits and goal-rest wake | Import goal predicates and lifecycle policy; one central completion owner closes/rests against current evidence. No stored-met shortcut around new close fences. Current PR/CL direct closure can bypass this goal reconciler; it too must lose closure authority. |
| Security/path/QA hold settlement, review questions/feedback/clean-review clearing, Submit/acceptance/force and auto-merge restoration | Preserve attributed approval/disposition evidence; hand guard aggregation/exceptions and operation admission to action owner. No parallel “set AutoMerge true” permit. |
| Wake/suspension/dispatch, Run now/retry/defer/close/reopen, message acknowledgement and goal edits in UI/API; scheduled/repair/release producers | Route authorized policy/action requests and observation proposals to central owner. Disable direct lifecycle writes at handoff, including recovery paths; capacity arbitration remains Grain-owned. |
| Go [`StateOf`](../pkg/model/state.go), [SQLite](../pkg/model/schema.go)/[PostgreSQL](../pkg/model/postgres/schema.go) `task_state`; existing gate/UI projections | Select same authority epoch/precedence. Legacy fields are compatibility projections, never a second decision source. |

Recommended ordering, following [MGD-6](../design/design/mcp-gates.design.md#MGD-6) and [AGB-8](../design/spec/mcp-gates/action-bindings.spec.md#AGB-8):

1. Capture legacy decision fixtures, exceptions and evidence completeness; define storage/identity/permission ownership, snapshots and central projections. Resolve outcome/acceptance/QA/config adapter contracts below before claiming exact parity.
2. Shadow read-only evaluators against retained collectors; compare decisions without changing legacy lifecycle or mutation authority. Distinguish real incompatibilities from stale/missing evidence.
3. For each protected resource/effect, establish credential/route inventory, policy union/index and executor/adapter fencing/reconciliation. Migrate or hold **all** equivalent legacy mutation routes; negative bypass probes and external-race proof precede enforced admission. Resource guards may cover legacy-completion tasks too; lifecycle authority never exempts an action.
4. For each explicitly migrated task, settle/fence live work, import exact predicates/policies and transactionally switch authority while disabling **every** legacy lifecycle writer. Temporary legacy wake/dispatch adapters emit proposals to that owner only. Upgrade compatible readers first; an old daemon must hold, not fall back. Rollback requires explicit representable reverse handoff and retains action protection.
5. Move waits/dispatch to durable cursor/timer arbitration and API/UI projections, then remove legacy paths after the compatibility window. Validate closure/message races, failed children, head invalidation, outage/restart and uncertain-action recovery before expansion.

## Coverage and readiness assessment

The audited admission, lifecycle, change, recovery and authorization families have a proposed home; several remain **compatibility choices**, not interchangeable “gates.” Exact imports must retain closure-vs-success, report/ack provenance, ordinary-review missing/closed behavior, PR/CL direct closure despite concrete goals, CI none/empty/skip rules, repair bypass, missing release rows, nightly selection, broad pipeline quiet and standing-work exceptions. Stronger current-head proof, successful required children, fail-closed missing required evidence and transactional closure are intentional changes, not descriptions of present universal enforcement.

Unresolved blockers are concrete: no unified executor/binding/coverage index or central lifecycle owner is established by these designs; per-deployment credentials/external exclusion remain unverified; CL/promotion/publication/config/QA adapters need exact-version and reconciliation contracts; findings acceptance and legacy closure/landed outcomes need explicit import dispositions; provider/profile support, durable snapshots/journal/timers/leases and Go/SQL/UI parity must be implemented and validated. Task #47 settles the transport design, not runtime snapshot readiness. Task #50 specifies enforcement, not a deployed firewall. These gaps block implementation readiness claims, not this documentation audit. No implementation or automatic follow-up filing is proposed here.
