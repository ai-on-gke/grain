## Stubs

1. **Board rows were posted to `POST /api/boards`.** In the UI, "New board"
   files a task whose pull request against the team's config repository adds
   the row, and the demo cannot merge that pull request. The task itself was
   filed through the UI (step 8). The resulting board row was then posted
   straight to the API, as earlier walkthroughs and
   `e2e/team-board-off-team.spec.js` do.
2. **Some setup and verification calls went to grain's own API** from the same
   browser context. Reads: `GET /api/teams`, `/api/tasks`, `/api/tasks/:id`,
   `/api/schedules`, `/api/console-sessions` and `/api/boards`, to confirm
   what the UI had saved. Writes: on the second server, the `qa-infra` and
   `orphan-probe` teams were created with `POST /api/teams` before their
   Team Settings or deletion were walked through. No grain response was
   mocked.

Nothing else was stubbed. There was no GitHub and no live agent session; the
demo's own fake state stood in for them.

There were no page errors and no 5xx responses. The console errors were
"Failed to load resource" lines, each matching a 400 that the walkthrough

(`api.js`), so this is not a fault.

## Findings

### F1: Edit Team could not empty the Members field (fixed)
**Reproduction** (demo server, nothing stubbed):
1. Create a team with admins `admin, debian` and members `alice`.
2. Open **Edit Team**, set Admins to `debian`, clear Members, and click **Save**.

**Before:** the dialog closed with no error, and `GET /api/teams/<id>` still
listed `admin` (admin), `alice` and `debian` (admin). `TeamsPanel` sent
`users` only when Members was non-empty. `UpdateTeam` treats a missing
`users` as "unchanged", and treats `admins` as additive.

**Expected and now:** the two fields together are the team's membership. An
admin the Members field leaves out is sent as a user too, so the team is
`debian` (admin) alone. An edit that names nobody is still refused by the
client.

**Fix:** `ui/src/components/TeamsPanel.jsx` (the edit PUT sends Members plus
the Admins it lacks as `users`).

### F2: a config-repo task could not be moved to another team (fixed)
**Reproduction:**
1. Under team `qa-infra`, click **New board** and file the "Add a board" task.
   It targets `grain/config-qa-infra`.
2. Open the task, click **Edit**, set Target team to `admin (default)`, and
   click **Save**. Or tick it with other tasks, open **Bulk edit**, tick
   Team, pick the default team, and click **Apply**.

**Before:** 400 "only team "qa-infra" can submit to grain/config-qa-infra".
The Edit form has no repo field, and Bulk edit leaves the repo alone unless
its own row is ticked. So the task stayed on the team, and the team could
never be emptied for deletion.

**Expected and now:** like New task and the schedule form
(`followTeamConfigRepo`), a task aimed at the old team's config repo follows
the team to the new team's config repo. The Edit form says so under the
picker: "its config repo follows the team: saving moves it to
grain/config-default". Bulk edit does the same per task, unless its Repo row
is ticked. Tasks on any other repo are untouched.

**Fix:** `ui/src/components/detail/EditTaskForm.jsx` and
`ui/src/components/BulkEditOverlay.jsx`.

**Regression coverage (F1 and F2):**
- `ui/e2e/teams-edit-membership-config-repo.spec.js` (real demo server). It
  failed on the base commit and passes with the fix.
- Vitest:
  - `TeamsPanel.test.jsx` "sends the admins as the membership when the Members
    field is emptied" and "adds an admin the Members field leaves out…"
  - `detail/EditTaskForm.test.jsx` "moves a task on … to another team" (both
    a config repo and an ordinary repo)
  - `BulkEditOverlay.test.jsx` "moves a task on its old team's config repo to
    the new team's"

  All four new tests failed with the source files reverted to the base
  commit.

**Tests run:** vitest on the three test files (78 passed), and the new
Playwright spec (1 passed).

### Carried over: team deletion leaves its boards behind
F2 of the 2026-10-11 report still reproduces on this commit. I deleted a
clean team holding `board-5` through the UI. The board stays in `/api/boards`
as `team: "orphan-probe"`, while the team's console sessions are removed.
`model.Store.DeleteTeam` checks tasks and schedules but not boards,
templates or suites. That report filed it as a follow-up, which needs a
decision on deletion semantics, so it is not fixed here.
