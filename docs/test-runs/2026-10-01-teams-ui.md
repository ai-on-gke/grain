1. Fresh demo: `GET /api/teams` showed default team members `admin, alice, debian, operator, sysadmin`.
2. Created account `admin` in the Create account dialog. The dialog closed, a `grain_session` cookie was set, and a personal team `admin1` appeared.
3. The default team's membership was now just `[admin (admin)]`. Reproduced on a second fresh demo by registering `zed` via `POST /api/auth/register`: the default team became `[zed (admin)]`, and `zed` was also made system admin.

### 2. Settings > All Teams cards
- The default card shows name `admin`, ID `default`, description, Admins/Members, chips `Max Workers/Mergers/CI Jobs: Unlimited`, target repo `acme/widgets`, config repo `grain/config-default` with clone command, associated repo health, and the executor bootstrap command. - A team with limits 4/2/8 and default model `gemini-3.1-pro` shows `Max Workers: 4`, `Max Mergers: 2`, `Max CI Jobs: 8`, `Default Model: gemini-3.1-pro`, and members `admin (admin)`, `alice`, `bob (viewer)`.

The Team ID field is not offered in the edit dialog. Reloading `/admin` comes back on the **general & deployment** tab, not All Teams, because the tab is not in the URL (minor, not fixed).

### 5. Global team selector and persistence
- Picking `QA Infra` set `localStorage["grain.selectedTeam"]="qa-infra"`, showed 0 rows with the empty state "No tasks in this state.", and survived a reload.
- Deep links: `/?team=default` showed the default team's 10 rows without overwriting stored `qa-infra`. `/teams/qa-infra` selected QA Infra. `/?team=nonexistent-team` shows the raw ID with 0 rows and no "unknown team" hint (minor, not fixed).

### 6. Task intake, detail and bulk edit
1. `/new`: the **target team** MUI select was opened with the keyboard (focus, Enter). Its options are `name (id)`. Choosing `QA Infra (qa-infra)` added `grain/config-qa-infra` to the repo list and reset the repo to `—`, which disables **create task** until a repo is chosen. Chose `acme/widgets` and created task #13 (`team=qa-infra`, `queued`).
2. Clicking the row opened `/tasks/13`, showing `Team: QA Infra (qa-infra)`, `Model: Rotation` and `Creator: admin`. `Model: Rotation` is shown even though qa-infra's default model was `gemini-3.1-pro` (F4).
3. Edit → Team → `Security Operations (security-operations)` → save. After a reload the detail showed `Security Operations (security-operations)`.
4. In the backlog, ticked #1, #2 and #13, then **bulk edit…**. The Team row read "(mixed across the selection)". Ticked Team, chose `QA Infra (qa-infra)`, and clicked **apply to 3 tasks**. `/?team=qa-infra` then listed exactly #1, #2 and #13.

### 7. Deletion safeguards
- Delete on `qa-infra` showed a native confirm `Are you sure you want to delete team "qa-infra"?`. Accepting it returned 400 with an alert `cannot delete a team that still has tasks`, and the card stayed.
- Delete on `security-operations` (no tasks after the bulk move) removed the card, and it stayed gone after a reload.
- Delete on the `..` team called `DELETE /api/` → 404 `no such API endpoint: DELETE /api/`, and the card stayed (F2).

### 8. Schedules, sessions, CI, boards
- `/schedules` (all) listed 3 schedules. With `?team=qa-infra` it showed "No schedules yet." **+ new schedule** under qa-infra preselects target team `QA Infra (qa-infra)` and offers `grain/config-qa-infra` as a repo.
- `/sessions?team=qa-infra` lists one Director session for qa-infra. Every new team is given its own Director session (`/api/console-sessions` returns `director-N` with `team` set). The filter is correct.
- `/ci?team=qa-infra` reads "Not available: this deployment does not run grain CI" because demo runs with `-ci=false`. This is expected, so team scoping of CI runs could not be observed in demo.
- `/boards` shows 3 boards for all teams and an empty list for qa-infra.

### Console and network
The only errors seen were the expected 400s from rejected creates and deletes, plus `net::ERR_ABORTED` on `/api/tasks` polls that a navigation cancelled. There were no uncaught page errors.

## Findings

| # | Finding | Disposition |
|---|---|---|
| F1 | Registering the first password account rewrites the default team's membership to only that user (as admin) and makes them system admin. Existing `team_user` rows (`alice`, `operator`, …) are deleted. It is deliberate first-user bootstrap (ab3632f83), but "first" counts only the `user` table. | Security design question. **Follow-up proposed**, not changed here. |
| F2 | Team IDs `.`/`..` are accepted. Their Delete button calls `DELETE /api/` and 404s, so the team can never be removed. IDs with a leading `-` are accepted and show up as `--team -lead` in the bootstrap command. Unbounded length is accepted. | **Fixed**: new IDs must be ≤ 63 chars and start/end with a letter or digit (`model.ValidateNewTeamID`). Auto slugs are truncated to fit. |
| F3 | Team ID `all` (and `settings`, which `/teams/settings` treats as a route) are accepted. Selecting team `all` behaves as All teams. A team *named* "All" would auto-slug to `all`. | **Fixed**: both are reserved. Auto slugs skip them (`All` → `all-1`). |
| F4 | A team's `defaultModel`, `agentFramework` and `agentBackendID` are stored and shown on the card, but task creation and dispatch never read them. The detail view shows `Model: Rotation`. | Backend behaviour change. **Follow-up proposed.** Fixed in grain/task-1427: dispatch (`agentFrameworks` in `cmd/grain/daemon.go`) did already read the team's settings, which the grep missed. It now applies the team's framework, model and backend only to a task that named none of them, and treats a task with no team as the default team's. The detail view now shows e.g. `gemini-3.1-pro (team default)`. |
| F5 | The sidebar picker can't tell teams with the same name apart, and its search ignores IDs. | **Fixed**: shared names show the ID as secondary text, and search matches IDs. |
| — | `/admin` tab not in URL; unknown `?team=` gives no hint | Minor, noted only. |

Existing rows are still validated by the old `ValidateTeamID`, so a deployment that already stores a team under one of these IDs can still edit it.
