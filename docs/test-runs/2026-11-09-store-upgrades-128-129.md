## Findings

| # | Finding | Status |
|---|---|---|
| F1 | **`grain_submit_task` dropped `grants:`.** The tool built its `POST /api/tasks` body by copying the arguments it knew, and `grants` was not one of them. The control `grants: ["api:ci-read"]` filed task 14 holding **no** capabilities. Every refused shape was filed instead of refused, without its grants: tasks 8–11 in [`out/item3-intake.txt`](2026-11-09-store-upgrades-128-129/out/item3-intake.txt). One of them was `no_repo` + `repo#target`, which filed a no-repository task. | **Fixed** (`pkg/ui/mcp_endpoint.go`): `grants` is in the tool's schema and is forwarded as sent, so the route's own decoder files or refuses it. Regression: `TestControllerMCPSubmitTaskForwardsGrants` (it fails on the old code with `task filed with grants [api:ci-read] holds []`). `docs/agent-api.md` says so. Not on `release/v3.2.0`: its `POST /api/tasks` takes no `grants:` on create. |
| F2 | **Token-mode introspection answered an unrecognised token with `401 invalid_grant`.** `/runs/<attempt_id>/introspect` (`token_info_url`) answered that way for a token that was never minted, expired, released, or minted for another attempt. RFC 7662 §2.2 says such a token MUST be answered with `active: false`, and the plan asks for exactly that after the run ends. The unit test pinned the 401. | **Fixed** (`pkg/capability/intree/gcp_token.go`): it now answers `200 {"active": false}` and nothing more. The live-token answer and the token endpoint's `invalid_grant` refusals are unchanged. Regression: `TestGCPTokenModeIntrospectAndRealGcloud` (unknown token, another attempt's path, after release). It fails on the old code with `introspect(unknown) = 401 …`. **Touches `pkg/capability/*`, so the trust-boundary security review runs.** Not on `release/v3.2.0`, which has no introspection endpoint. |
| O1 | The operator learns about drops from the daemon log, plus a note on templates and schedules. Deployment and repository defaults and the catalogue defaults get **no** persistent note: only the log line says a grant left them. The task that held the grant keeps it (by design, `catalogueHold`), and the UI shows it as `github › read-issues`. | Recorded. The design says so (`MigrateCatalogueDisabledGrants` doc comment). |
| O2 | `propose_task` silently ignores an argument it does not declare. `base: "main"` + `repo#target` was recorded (`isError=False`) and filed as task 16 with the grant's target, because `propose_task` spells the base `branch`. With `branch`, the same request is refused. The `branch`/`no_repo` refusals read "…and the request's **repo** field both name the task's repository", naming a field the request did not send. | Follow-up proposed. |
| O3 | A `.grain/` template whose `capabilities:` names `repo#target={…}` passes `grain declarations check` as well-formed. It is kept as an ordinary grant, but `POST /api/tasks` refuses it (`unknown capability https://grain.dev/capabilities/repo#target=…`), so no task can ever be filed from that template. The refusal comes at filing time instead of at declaration time. It cannot retarget a task, because filing refuses it. | Follow-up proposed. |
| O4 | `EncodeCapabilityPolicy` writes an empty `"apiScopes": {}` into an upgraded policy the old build had written without it ([`out/s127-sqlite-old-vs-head-inplace.diff`](2026-11-09-store-upgrades-128-129/out/s127-sqlite-old-vs-head-inplace.diff)). This is cosmetic, and the round trip and `state check` are unaffected. On the v3.1.0 store, other migrations also add the `figma` server and drop `model-proxy` from `mcp_servers`. That is expected, and outside 128/129. | Recorded. |

## Items 1–2: real upgrades

### How the stores were made

[`walk.sh <name> <old-binary> <legacy|canonical> <sqlite|postgres>`](2026-11-09-store-upgrades-128-129/walk.sh) runs one cell. [`/tmp/matrix.sh`](#reproduce) runs all six. Each cell goes through these steps:

1. **Seed.** The old daemon starts (`-disable-native-sandboxes`). [`seed.sh`](2026-11-09-store-upgrades-128-129/seed.sh) makes, through its API, a stub GitHub token, `acme/widgets`, task 2, task 3 (approved), `template-1` and `sched-1`. The daemon is stopped, and the grants are written with SQL so that both stores get identical rows:
   - `in_process.read-issues` is **disabled** in the catalogue.
   - Its grant goes into `grain_config.default_capabilities`, catalogue `defaults.task`/`.ci`/`.repos[acme/widgets].task`/`.ci`, `repo_config` default and CI capabilities, `template_grant`, `schedule_grant` and task 2.
   - A control `api:test-quarantine` is written beside it everywhere.
   - Task 3 holds the sandbox-repo grant.
   - Both tasks get a `task_grant_wait` row under the retired `github-sandbox`.

   The canonical seed (127, rc) spells the grants as a 119/127 store does (`github#read-issues={}`, `github#sandbox-repo={}`), with JSON lists. The legacy seed (v3.1.0) spells them `read-issues` and `github-sandbox`, with comma lists. **Why SQL:** [`api-probe.sh`](2026-11-09-store-upgrades-128-129/api-probe.sh) ([`out/api-probe.txt`](2026-11-09-store-upgrades-128-129/out/api-probe.txt)) tried to make the shape through each old API:
   - The 127 build stores the grant in defaults, the repository, a template and a schedule, then **refuses** the `PUT /api/capability-policy` that disables it (`catalogue: defaults.task: capability … is disabled …`, task 3412's validation).
   - The rc build refuses the grant itself (`capability https://grain.dev/capabilities/github is not configured in mcpServers`), then accepts the disable.

   So these stores are the 2026-11-07 O1 ghost shape, written the way those were.
2. **In place.** HEAD starts on a copy. The walk captures its log, a full grant dump ([`dump.sh`](2026-11-09-store-upgrades-128-129/dump.sh)) and the API: `GET /api/settings`, `/api/capability-policy`, `/api/repos/acme/widgets/settings`, `/api/templates`, `/api/schedules`, `/api/tasks/3`. It then stops HEAD and runs `grain state sync` + `grain state check` on the store's own export.
3. **Dump route.** On a second copy: `grain state prepare-upgrade` (export the old rows, rehearse the import), then HEAD starts and imports. The resulting dump is diffed against the in-place route.
4. **Downgrade.** The old binary starts on the upgraded store, and the store is dumped before and after.

**Grant waits (migration 129).**
- Task 2's stale `github-sandbox` row reads `https://grain.dev/capabilities/github#sandbox-repo={} | github-app` after the upgrade, on every cell. Task 2 is proposed, so admission never re-probes it, and the row is exactly what migration 129 left.
- Task 3 (queued) was re-admitted by HEAD's first cycle under the canonical grant. - So the parked task resumes admission under the canonical name, not the retired one. Watching it go on to *dispatch* needs a configured GitHub App, which this walk did not have.

## Item 4: GCP token mode with a real gcloud

**Set-up:**
- A real HEAD daemon (`127.0.0.1:4242`, `-container-sandboxes -container-sandbox-image grain-sbx:walk -container-git-proxy-host 10.240.0.1 -github-host 127.0.0.1:4250 -github-insecure-http`), configured by 2026-11-04's [`setup-daemon.sh`](2026-11-04-capabilities/setup-daemon.sh): fake-agy connections, `acme/widgets`, a stub token.
- GitHub is [`simhost.go`](2026-11-04-capabilities/simhost.go).
- The gcp server is [`gcpwalk.go`](2026-11-08-gcp-token-mode-containers/gcpwalk.go): grain's own configurable gcp server over Streamable HTTP, built from this branch. Its admin connects to `gcpfake`'s in-memory IAM, which is the only stubbed boundary; the STS-style exchange and introspection are grain's own listener.
- It is registered as `https://grain.dev/capabilities/gcp` with the `org-deploy` set, `credential: token`.
- The sandbox image is `debian:bookworm-slim` with `cmd/grain-sandbox` and the host's gcloud SDK. The agent is [`fake-agy.sh`](2026-11-09-store-upgrades-128-129/fake-agy.sh) (2026-11-08's, with `--help` answered at once rather than run as a turn), which runs [`step.sh`](2026-11-09-store-upgrades-128-129/step.sh) while the run is live.

**What the run saw** (task 15; [`out/item3-4-run.txt`](2026-11-09-store-upgrades-128-129/out/item3-4-run.txt), [`out/item3-4-after-run.txt`](2026-11-09-store-upgrades-128-129/out/item3-4-after-run.txt)):
- `~/.gcp-service-account.json` is `external_account`, with `token_url` and `token_info_url` both on `http://127.0.0.1:4252/runs/grain-15-1-0/…`.
- `gcloud config list` shows `credential_file_override = /home/debian/.gcp-service-account.json` and `project = walk-proj`, both set by `activate.sh`.
- `gcloud auth print-access-token` printed a token for `deployer@walk-proj…`, minted through the listener. The gcp server's audit records two mints for the attempt.
- `gcloud auth list` reports `No credentialed accounts`. That is expected under `credential_file_override`, but it may surprise an agent.
- Inside the container, `POST token_info_url` with the live token answered `{"active":true,"exp":…,"username":"deployer@walk-proj.iam.gserviceaccount.com"}` with HTTP 200.
- The same token at `/runs/grain-999-1-0/introspect` (another attempt's path) answered `{"active":false}` with HTTP 200. Before F2, the 2026-11-08 walk recorded 401 here.
- After the run ended, from the host, the same token at its own `token_info_url` answered `{"active":false}` with HTTP 200 (before F2: 401). The token endpoint answers `401 invalid_grant: this grant's token is unknown or released`.
