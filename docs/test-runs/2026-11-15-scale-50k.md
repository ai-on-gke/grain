# Scale test: 100 running / 1,000 waiting / 50,000 total — 2026-11-15

Task 5994 asked what happens to grain at a busy deployment's shape: 100 runs
live, 1,000 tasks waiting, 50,000 tasks in all, on SQLite and on PostgreSQL.
This records how that was measured, what it found, and what is now gated
nightly and on every release candidate.

**Short answer:** at 50,000 tasks the store-wide O(N) paths dominate
everything.

- On SQLite a dispatch cycle takes **~50–65 s** and an orchestrator tick
  **1–2 min**. The task list endpoints take **~1m45s** to answer, or don't
  answer within 3 minutes when six of them are asked at once.
- On PostgreSQL readiness is cheap: the tick is 16 s, the dispatch cycle
  1.7 s, and 1,099 runs turned over in 2 minutes. But `Store.ListTasks`
  takes 43 s there, so no list endpoint answered at all, and RSS reached
  4.7 GB.

The cause isn't the 100 live runs or the 1,000 waiting tasks themselves. It
is work done once per ready candidate (`dispatch.Cycle`), once per task in
the store (`Store.ListTasks`, the `task_ready`/`task_blocked` views), or once
per request with no usable cache (`GET /api/tasks`, `/api/inbox`,
`/api/metrics`). On SQLite, writes from live runs queue behind all of that:
heartbeat p95 is **2.6 s** and max **7.5 s**.

Everything still *works*. There were no store errors, and every slot was
refilled: 200 runs (SQLite, 3 minutes) and 1,099 (PostgreSQL, 2 minutes)
completed and were replaced. It is slow, not broken, and each of the seven
follow-up tasks below targets one cost.

## Harness

`tests/e2e/scale_test.go` (new):

| Piece | What it does |
| --- | --- |
| Seed: history (48,900) | Each task gets a ~1.5–3.5 KB description, two custom fields, 1–5 runs (`StartRun`/`FinishRun`; 5 % failed out at `MaxConsecutiveFailures`), two comments, a `close` event via `ObserveClose`, and a `depends_on` edge on every fourth task. A third are merged (`fixes` link, `auto_merge`, `pr_merged_at`). Created-at is spread over 90 days. |
| Seed: waiting (1,000) | 40 % queued, 25 % proposed, 15 % `awaiting_reply` (pending question), 15 % blocked on an open `depends_on`, 5 % parked by `resume_later` (`Suspend`, `ResumeAt` +6 h, "waiting on CI"). Another 100 queued tasks fill the running slots. |
| Dispatcher | `dispatch.Cycle(…, Limits{Workers: 100})`, the selection and `StartRun` half of a real dispatch, every 100 ms. |
| Fake runs (100 live) | Each lives 4–12 s. Every 500 ms it writes `SetTaskActivity` (heartbeat) and `SetRunTranscript`. Every 2nd step it does a proxy read (`LiveRunCounts` + `GetTask`), and every 4th it posts a status comment. It then calls `FinishRun`, closes its task via `ObserveClose`, and files a replacement queued task, so the waiting queue stays at 1,000. No subprocess or VM: this measures grain, not the sandbox. |
| Orchestrator | `orchestrator.RunCycle` back to back, timed by its own `CycleTimes` ring (what `/api/metrics` serves). `MaxWorkers: 1` against 100 live runs, so it reconciles and decides but never starts a real sandbox. |
| HTTP API | `ui.NewServer` over the same store, with one client per endpoint: `GET /api/tasks` (default, `state=queued`, `state=running,awaiting_reply`, `q=`, `limit=100&cursor=`, `fields=summary&limit=50`), `/api/tasks/{id}`, `/api/tasks/{id}/messages`, `/api/metrics`, `/api/tasks/states`, `/api/inbox`. Plus 10 SSE subscribers on `/api/events?stream=1`. |
| Sampler | RSS (`/proc/self/status`), heap, goroutines, fds and GC pause every 500 ms. |
| Plans | `EXPLAIN QUERY PLAN` (SQLite) and timing (both backends) for `IsReady`, `Ready`, `States` and `ListTasks` on the seeded store. |

It fails on any store error, any non-2xx, a request still unanswered past its
budget when the run ends, a p95 over budget (tick, dispatch cycle, run writes,
each endpoint), or fewer than 100 runs completed and replaced.

- `TestScaleSmoke` runs it at 200 / 40 / 6 on both backends on every commit
  (about 5 s on SQLite and 13 s on PostgreSQL), ungated and judging no
  latency.
- `TestScale50k` runs it at full size, gated on `GRAIN_SCALE_TEST`
  (`make scale`).

Every dimension and budget is an env var: `GRAIN_SCALE_TOTAL`, `_WAITING`,
`_RUNNING`, `_REPOS`, `_DURATION`, `_RUN_LIFETIME`, `_API_CLIENTS`,
`_SSE_CLIENTS`, `_SEED_WORKERS`, `_MIN_COMPLETIONS`, `_TICK_P95`,
`_DISPATCH_P95`, `_API_P95`, `_WRITE_P95`, `_TICK_TIMEOUT`,
`_REQUEST_TIMEOUT`. `GRAIN_SCALE_BACKENDS` picks the stores,
`GRAIN_SCALE_REPORT_DIR` writes the per-backend reports, and
`GRAIN_SCALE_VERBOSE` keeps dispatch's per-candidate log lines.

Throughput: 200 dispatches and 200 completions in 3 min. All 100 slots were
refilled throughout (max live = 100), and there were no store errors. SQLite
reported no `SQLITE_BUSY`/`database is locked` errors: the slow writes are
queueing on the single writer (`busy_timeout`), not failing.

Runtime: max RSS **2.9 GB**, max heap **2.2 GB**, **20.9 GB allocated** in 3
minutes, GC pause total 0.65 s, max goroutines 511 (one per live run and
client), max fds 264. The allocation is almost all whole-store task lists
being rebuilt per request.

Plans (`EXPLAIN QUERY PLAN`):

- `task_ready` scans `task` and `task_link` (`SCAN l USING INDEX
  sqlite_autoindex_task_link_1`, `SCAN t`).
- `SELECT … FROM task_ready WHERE task_id = ?` still scans `task_link` whole,
  because `task_blocked` is a `GROUP BY` the predicate cannot push into.
- `task_state` is `SCAN t`, which is expected for all rows.
- Live runs, a task by id and a task's comments are indexed (`task_run_open_task`, primary keys).

### One client per endpoint (SQLite run 4)

Runs 1–3 drew endpoints at random from a shared pool of clients, so a
two-minute list request starved the other endpoints of samples. Run 4 gives
every endpoint its own client, which is now the harness default.

- Per-task endpoints are healthy at 50,000:
  - `GET /api/tasks/{id}`: p50 31 ms, p95 202 ms (2,886 requests);
  - `/api/tasks/{id}/messages`: p95 98 ms (9,208);
  - `/api/tasks/states`: p95 136 ms (4,726);
  - `/api/metrics`: p50 4.2 s, p95 5.5 s (41).
- **None of the six list-shaped endpoints answered once in 3 minutes**:
  - `GET /api/tasks` (default);
  - `?state=queued`, `?state=running,awaiting_reply`;
  - `?q=`, `?limit=100&cursor=`, `?fields=summary&limit=50`;
  - and `/api/inbox`.

  Six concurrent whole-store builds is more than the host clears in the run.
  The report now lists such requests under `api-unanswered/<endpoint>`, with
  how long they had waited.
- The tick (1m52s), the dispatch cycle (p50 66 s) and heartbeats (p95 5.0 s)
  are in line with run 3. It passed the ceilings.

## Where the limits are

1. **`dispatch.Cycle` is O(ready candidates) × (several queries + writes)
   every cycle, even with no free slot.** `pkg/dispatch/dispatch.go`, around
   the candidate loop at L938. For every one of the 550 ready candidates it
   does the following, *before* it learns there is no capacity:
   - `retryEligible`, a run-history read;
   - `setSuspensionWait`/`clearSuspensionWait`, a write;
   - `o.skip`;
   - `stillReady` → `Store.IsReady` (L1143, `pkg/model/store.go:4545`), at
     33 ms each on SQLite;
   - `recordSkipQuotaWait`/`clearQuotaWait`, a write.

   That is 50–65 s per cycle, and as the `dispatch` reconciler it is most of
   every tick. The per-candidate writes also take the SQLite writer away from
   live runs.
2. **`task_ready` / `task_blocked` cannot be evaluated for one task.**
   `pkg/model/schema.go:4711`–`4730`: `task_blocked` is `GROUP BY task_id`
   over every blocking link, LEFT JOINed into `task_ready`. One task's
   readiness is 33 ms and the whole ready set 175–260 ms at 50,000 tasks.
   Both grow with the size of the history, not the queue.
3. **`GET /api/tasks`, `/api/inbox` and the filtered lists rebuild a
   50,000-task list per request.**
   - The person-caller default list is `taskListCache.response`
     (`pkg/ui/task_list_cache.go:173`). It is keyed on the store's change
     token, which every heartbeat, transcript write and comment from 100
     live runs moves, so under load it effectively never hits.
   - The filtered and paged lists (`handleFilteredTaskList`,
     `pkg/ui/task_list_filter.go:285`) start from the same whole-store load
     (`Store.ListTasks`, `pkg/model/store.go:1538`: 9.6 s alone).
   - Even `?limit=100&cursor=` and `?q=` take ~1m45s, and `/api/inbox` the
     same.
   - This is also where the 2.9 GB RSS and 21 GB of allocation come from.
4. **`GET /api/metrics` takes 5–6 s at 50,000 tasks**
   (`pkg/ui/metrics.go:2202` → `Client.Metrics`). It recomputes from history
   per request.
5. **The `reviews` reconciler takes 13–15 s per tick and `notifications`
   3 s** (`pkg/orchestrator/review.go:69` `SyncReviews`:
   `OpenPullRequestLinks` joins the `task_state` view over every task, then
   `closeFinishedReviews`, `closeObsoleteReviews` and
   `releaseStaleReviewDependencies`). That is with the merged history
   settled (`pr_merged_at` set).
6. **Live-run writes queue behind all of the above on SQLite.** Heartbeat p95
   2.6 s and max 7.5 s; transcript max 6.7 s. Each heartbeat
   (`SetTaskActivity`, `pkg/model/store.go:3513`) is its own write
   transaction and also moves the change token that invalidates the list
   cache (item 3).
7. **PostgreSQL write throughput.** Seeding through the store's own write
   path runs at ~40 tasks/s with 8 writers on a 10-connection pool. That is
   about four times slower than SQLite.

Nothing here needed a fix just to let the test complete. Every path finished
inside generous timeouts, so this change lands only the harness and the gate,
and files each limit as its own follow-up.

## What is gated now

- `make test` / the `go e2e` job: `TestScaleSmoke`, on both backends where
  PostgreSQL is installed.
- `nightly.yml` `scale` (`deployment scale 50k`): a `sqlite`/`postgres`
  matrix, each leg running `make scale` with `GRAIN_REQUIRE_POSTGRES=1`
  (90-minute job, 70-minute `go test` timeout). The reports are uploaded as
  `scale-report-<backend>`.
  - It runs on the nightly schedule and on every `vX.Y.Z-rc.N`.
  - The `stage-1` verdict job `needs` it, and
    `tests/deploy/nightly_rc_qualification_test.go`,
    `scripts/candidate-gate.sh` (`CHECK_QUALIFICATION_JOBS`), its tests, the
    release-from-trunk fixtures, the playbook's Stage 1 table and
    `docs/github-actions-ci.md` all name it. Stage 1 now has 19 jobs.
  - `.grain/workflows/nightly.yml` mirrors it for grain CI.
- **Budgets are ceilings, not targets.** They sit at about three times what
  this host measured, sized for a 4-vCPU hosted runner:
  - tick p95 6 min, dispatch cycle p95 3 min;
  - each endpoint's p95 6 min, run writes p95 20 s;
  - timeouts 8 min;
  - at least 100 runs completed and replaced in the 3-minute run.

  At today's shape a healthy-deployment budget (a tick of a few seconds, a
  list under a second) would fail every night and block every RC on work not
  yet done. The ceilings instead catch a further regression, an endpoint that
  stops answering, a store error, or a slot that stops being refilled. Each
  follow-up below lowers the budget it moves.
- **Why Stage 1 and not Stage 2.** The shape is 50,000 rows the test writes
  into the store under test. On a throwaway runner that is a fixture. Stage 2
  (`.grain/suites/release-qualification.yml`) runs agent tasks against a live
  deployment, where the same check would leave 50,000 fake tasks in a real
  database, under every list, inbox and tick from then on. A read-only probe
  of a live deployment would measure whatever it holds that day, not a fixed
  shape, so it could not hold a budget either. The playbook and the suite
  file both say so.

## Follow-ups filed

Each one depends on this task, cites the measured number, and names the
budget it should lower once fixed.

1. `dispatch.Cycle`: stop paying per ready candidate when no slot is free,
   and batch or skip the unchanged wait-reason writes.
2. `task_ready` / `task_blocked`: make readiness evaluable per task
   (correlated `NOT EXISTS` and an index on blocking links by task).
3. `GET /api/tasks` / `/api/inbox`: page and filter in SQL, and stop
   live-run activity from invalidating the list cache.
4. `GET /api/metrics`: stop recomputing from all history per request.
5. `reviews` / `notifications` reconcilers: bound their per-tick work to
   what changed.
6. Live-run heartbeat/transcript writes: coalesce them, and keep them off
   the change token.
7. PostgreSQL write throughput and pool sizing under concurrent writers.
