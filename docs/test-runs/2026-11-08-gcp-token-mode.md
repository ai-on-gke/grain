The method's `permission_set` carried `"x-grain-person-granted": ["ext-deploy"]`, and the data-plane listener was up on `127.0.0.1:4252`.

## Outcome

| Item | Result |
|---|---|
| 1. An `external_account` config is placed, and the exchange at the forwarded listener succeeds from inside the container | **Pass.** `~/.gcp-service-account.json` (0600) is an `external_account` config whose `token_url` is `http://127.0.0.1:4252/runs/grain-21-1-0/token` and whose `credential_source.file` is the per-attempt token `~/.gcp-token/grain-21-1-0/ext-deploy.token` (0600, 64 bytes). There is no key: `grep -rl private_key ~` finds nothing. From inside the container, curl's RFC 8693 exchange and `adc-probe` both got `Bearer` tokens for `deployer@walk-proj…` living 3599 s. The placed `ext-deploy-id-token AUDIENCE` printed an ID token, and a wrong subject token got 401 `invalid_grant`. `activate.sh` ran as the grant's setup. |
| 2. Tokens refresh until the grant's deadline and not after | **Pass.** Every exchange minted a fresh token (`tok-7`, `tok-8`, `tok-9` …). With the server's clock moved to the deadline − 30 s, the exchange answered `expires_in: 30`, and `adc-probe` reported "expiring in 30s". At the deadline + 5 s, curl, `adc-probe` and the ID-token helper were all refused: `401 {"error":"invalid_grant","error_description":"permission set ext-deploy: the grant's deadline 2026-11-08T06:19:04Z has passed"}`. With the clock back, the exchange worked again, so the refusal is the deadline's and nothing else's. |
| 3. Release revokes | **Pass.** When the run ended, grain tore the container down and released the grant. The per-attempt token the step had saved, posted to the same listener from the host, got `401 {"error":"invalid_grant","error_description":"this grant's token is unknown or released"}`. |
| 4. An agent's `propose_task` cannot pass the person-granted set on | **Pass after two fixes (F2, F3).** The run, holding `ext-deploy`, called `propose_task` through its own grain MCP server, once with the set and once with no grant (the control). The proposal holding the set was filed `proposed/unapproved` ("awaiting a person"), while the control was queued `approvedBy: auto-submit` on the parent's permission. It was held for the right reason, but its note said the reverse of the truth (F2). Passing on `ext-logs`, a set any agent holding it may pass on, was held too (F3). After both fixes, `ext-deploy` is held with a note that says why, and `ext-logs` is queued and runs holding the set. |

## Findings

| # | Finding | Status |
|---|---|---|
| F1 | **Every stdio capability server's stderr was thrown away.** `startCapabilityServers` never set `servers.Options.Stderr`, so `protocol.Attach` discarded it. That included the gcp server's `gcp: audit: attempt … granted access tokens for … until <deadline>` and `minted an access token …` lines. `docs/capabilities.md` and `docs/gcp-key-permission-sets.md` give those lines as the record of every grant and token. The walk found the grant's deadline nowhere on the daemon: [`daemon-before-fix`](#f1-before-and-after) has the attach and nothing else. The capability audit of a gcp attempt is empty (the gcp method declares no `Audit`), so the log was the only record. | **Fixed** (`pkg/capability/servers/servers.go`, `pkg/daemon/capability_servers.go`). Each line a stdio server writes is the daemon's log line, `grain daemon: capability server <id>: <line>`, with the server's own timestamp dropped. The registry hands lines over whole and scrubbed of every secret the server was started with, on attach and on probe alike, so a server that prints its credential does not put it in the daemon's log. `TestAStdioServersStderrIsHandedOverInScrubbedLines` and `TestACapabilityServersStderrIsLoggedAsItsOwn`. Live: the audit lines in [`token-walk-items-1-3.txt`](2026-11-08-gcp-token-mode/token-walk-items-1-3.txt). |
| F2 | **A proposal passing on a person-granted set was held, but its note said the proposer did not hold the set.** Task 5 was filed by the person with `gcp#gcp-key={"permission_set":"ext-deploy"}` (recorded `…,"primary":true`). Its proposal of the same set read: "grain: this proposal asked for `…{"permission_set":"ext-deploy"}`, which task 5, which proposed it, does not hold itself." `protocol.Covers` never covers a person-granted grant, and that hold is right. But `model.CapabilityEscalationNote` worded every escalation as a grant the proposer lacks, so the person deciding was told something false, and the obvious response ("then give task 5 the set") changes nothing. | **Fixed** (`pkg/model/auto_submit.go`). A grant only a person may give (`model.IsPersonOnlyGrant`: person-granted sets and methods, dangerous api scopes) gets its own sentence: "…which only a person may grant: an agent cannot pass it on, whether or not task 15, which proposed it, holds it." Other escalations keep the old one. The test is `TestRelayedProposalOfAHeldPersonGrantedSetSaysWhyItWaits`. Live after the fix: proposal 16 in [`token-walk-item-4-after-fix-ext-deploy.txt`](2026-11-08-gcp-token-mode/token-walk-item-4-after-fix-ext-deploy.txt). |
| F3 | **A set the proposer held, written as an agent writes it, was held as an escalation.** Task 10 held `gcp#gcp-key={"permission_set":"ext-logs","primary":true}` (`ext-logs` is not person-granted; `primary: true` is the default the person's grant was recorded with). Its proposal of `{"permission_set":"ext-logs"}` was filed `proposed/unapproved` with "which task 10, which proposed it, does not hold itself" ([`token-walk-item-4-before-fix-ext-logs.txt`](2026-11-08-gcp-token-mode/token-walk-item-4-before-fix-ext-logs.txt), proposal 11). The end-of-run relay records a proposal's grants as the run typed them, and `protocol.Covers` compared them with `reflect.DeepEqual`. So a grant that left out an argument the parent's recorded form filled in was never covered, although minting fills the same default in. | **Fixed** (`pkg/capability/protocol/grant.go`, `server.go`). Discovery records each method's top-level argument defaults (`NoteArgDefaults`, beside `NotePersonGrantedArgs`), and `Covers` compares both grants with them filled in. A different value, a person-granted value and a method discovery has not seen are judged as before. The tests are `TestAnArgumentLeftOutIsCoveredAsItsDefault` and the `ext-logs`-shaped control in `TestRelayedProposalOfAHeldPersonGrantedSetSaysWhyItWaits`. Live after the fix: proposal 19 was queued `auto-submit` holding `{"permission_set":"ext-logs","primary":true}`, and its run was granted tokens for `log-reader@walk-proj…` ([`token-walk-item-4-after-fix-ext-logs.txt`](2026-11-08-gcp-token-mode/token-walk-item-4-after-fix-ext-logs.txt)). |
| O1 | A token minted near the deadline outlives it by up to a second and a half. `Manager.remaining` rounds the time left to the second and adds a second, so at the deadline − 30 s the token was minted `expiring 06:19:05Z` against a deadline of `06:19:04Z`. The exchange itself is refused from the deadline on. | Noted. It is far below GCP's own clock skew, and the next exchange is refused. |
| O2 | `grain daemon` reads a run's `propose_task` calls from the agent's own stream (`result.ToolCalls`, with the MCP server's records for their arguments), not from the MCP server. A tool call the agent CLI never reports is answered "Recorded (1 proposed task(s) so far this run)" and then never filed, and the run fails "the agent made no tool calls at all". The first item 4 attempt, whose probe called the tools out of band, filed nothing. A real agy reports every call, so this is the fake's gap, closed by the `fake-agy.sh` addition above, not grain's. | Noted. |
| O3 | Each fake-agy run is invoked twice: grain resumes the conversation (`--conversation fake-agy-walk`) after a first turn that made no tool call. The steps are armed once per walk for that reason. The runs of items 1–3 end `failed` ("the agent made no tool calls at all"): the probe looks in with `docker exec`, as 2026-11-04's did.
