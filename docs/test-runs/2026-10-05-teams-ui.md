# Teams management, task intake and multi-team UI walkthrough

**Date**: 2026-10-05
**Commit tested**: `72384b8ed` (candidate tip at the start of the run). The fix was re-verified on this branch's own build (`28d3358c5`), on a fresh demo store.
**Environment**: Debian sandbox, Linux x86_64, 4 vCPU / 7 GiB, Go 1.26.6, Node 20.19.0, Playwright with Chromium headless shell.
**Server**: `grain demo -addr 127.0.0.1:18080 -open=false` over its throwaway embedded SQLite store. It served the production frontend, built with `npm run build` into `pkg/ui/static` and embedded by `go build ./cmd/grain`.
**Browser**: Playwright library scripts drove visible controls at 1400×900. They were written for this run under `/tmp` and not committed; they are not the `ui/e2e` specs. Every `console` error and warning, `pageerror`, `requestfailed`, HTTP status ≥ 400, non-GET `/api/` request (with its body) and native dialog was logged.

This run follows [2026-10-04-teams-ui.md](2026-10-04-teams-ui.md). It covered that run's ground again, with different entry points where there are two: the sidebar's **new team** dialog (`NewTeamDialog`) rather than only Admin's, and Team settings > Capacity / Models / Team rather than only Admin's Edit dialog. It then looked at what happens to a schedule's or a task's team-bound settings when the item moves *back to the default team*. That is where the bug below was found.

## Stubs

None. The real server, frontend, browser and gestures were used throughout.

Non-UI calls:
- Reads: `GET /api/teams/:id`, `/api/config`, `/api/tasks/:id`, `/api/schedules` and `/api/console-sessions`, made from the Playwright request context (the same signed-in session) to confirm what the UI showed.
- No API writes were used for setup. Every team, task, schedule, session and board task was created through the UI.

`GET /api/repos/acme/widgets/github-branches` returns 404 in demo because there is no GitHub. That is an external boundary, and the base-branch field degrades to free text. No Gemini key was present at `/home/debian/.gemini-api-key`. None was needed, because nothing here dispatches an agent.

Setup: `npm ci`, `npm run build`, `go build -o /tmp/grain ./cmd/grain`, and `NODE_EXTRA_CA_CERTS=/etc/ssl/certs/ca-certificates.crt npx playwright install --with-deps chromium`. The first account (`admin`) was created through the demo's own **create account** form.

### Console and network
The only errors seen were:
- the expected 400s from refused creates, edits, deletes and the bulk edit's config-repo task;
- 404s on `github-branches` (no GitHub in demo).

The steady `net::ERR_ABORTED` on `GET /api/tasks` and `/api/tasks/:id` is not a failure. Counting responses showed each one is a `304` poll reply (`If-None-Match`, `pkg/ui/task_list_cache.go`), which Chromium reports as aborted because no body follows: over 12s, 4 responses were `304` and 4 requests "failed". There were no uncaught page errors and no 5xx.

## Findings

| # | Finding | Disposition |
|---|---|---|
| F1 | **A schedule could not be moved back to the default team.** `ScheduleOverlay` put `team` in its save body only when the chosen team was not `"default"`. `UpdateSchedule` reads an absent team as "leave it where it is", so the move saved 200 and left the schedule on its old team (F1b). On the old team's config repo, the repo had already followed to `grain/config-default`, so the same move was refused outright (F1a). The template and suite panes already always send their team. | **Fixed**: an edit now sends `team: "default"` whenever the saved schedule was on another team. |
| F2 | **Moving a task to another team keeps a model override the new team cannot serve, and hides it.** In Edit, `EditTaskForm` drops the model row when the new team's connections serve no model, and the `PATCH` sends only `team`. `UpdateTask` accepts it. The task keeps `model: gemini-2.5-pro` on a team with no connection for it, so it can wait indefinitely even after that team gains a connection for its own default. | **Follow-up proposed**: it needs a decision between clearing, refusing and flagging the override, and the same rule should hold in bulk edit. |
| — | The Models tab holds deployment-wide settings. The task URL stays under the old team after a move. The composition preview has no team. Partial bulk-edit failures leave the successful rows ticked. | Minor, already recorded or by design; noted only. |
