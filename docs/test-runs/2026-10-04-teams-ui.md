# Teams management, task intake and multi-team UI walkthrough

**Date**: 2026-10-04
**Commit tested**: `232c39294` (candidate tip at the start of the run). The fix was re-verified on this branch's own build (`9878e11b8`), on a fresh demo store.
**Environment**: Debian sandbox, Linux x86_64, Go (`/usr/local/bin/go`), Node 20.19.0, Playwright with Chromium headless shell (chromium-headless-shell-1234).
**Server**: `grain demo -addr 127.0.0.1:18080 -open=false` over its throwaway embedded SQLite store. It served the production frontend, built with `npm run build` into `pkg/ui/static` and embedded by `go build ./cmd/grain`.
**Browser**: Playwright library scripts drove visible controls at 1400×900. They were written for this run under `/tmp` and not committed; they are not the `ui/e2e` specs. Every `console` error and warning, `pageerror`, `requestfailed`, HTTP status ≥ 400, non-GET `/api/` request and native dialog was logged.

This run follows [2026-10-03-teams-ui.md](2026-10-03-teams-ui.md). It rechecked that run's ground and then went after something new: what happens to an item's **repo** when its **team** changes. That is where the bug below was found.

## Stubs

None. The real server, frontend, browser and gestures were used throughout.

Non-UI calls:
- Reads: `GET /api/teams`, `/api/tasks`, `/api/schedules` and `/api/console-sessions`. They were made from the Playwright request context (the same signed-in session) to confirm what the UI showed.
- Probes: `POST /api/tasks` and `DELETE /api/teams/default` were sent to check the server's answer directly.
- Setup: on the re-verification store only, the two teams were created with `POST /api/teams`. Team creation through the dialog had already been exercised on the first store.

`GET /api/repos/acme/widgets/github-branches` returns 404 in demo because there is no GitHub. That is an external boundary, and the branch field degrades to free text. No Gemini key was present at `/home/debian/.gemini-api-key`. None was needed, because nothing here dispatches an agent.

Setup: `npm ci`, `npm run build`, `go build -o /tmp/grain ./cmd/grain`, and `NODE_EXTRA_CA_CERTS=/etc/ssl/certs/ca-certificates.crt npx playwright install --with-deps chromium`. The first account (`admin`) was created through the demo's own **create account** form.

## Findings

| # | Finding | Disposition |
|---|---|---|
| F1 | **Switching a schedule's Target team left it on the old team's config repo.** `ScheduleOverlay`'s repo field is uncontrolled. Once the new team's options no longer held `grain/config-<old>`, a new schedule's select showed its first option while state, and the submit, kept the old repo; an edit fell back to the text box. `CreateSchedule` accepted the result, so a schedule was stored as `qa-infra` on `grain/config-platform-reliability`, a pairing `UpdateSchedule` refuses. `CreateTask` had the same gap for a request naming its team. | **Fixed**: the schedule form moves the repo with the team (`followTeamConfigRepo`, as New Task does). A new schedule whose pick the new team does not offer starts on that team's default, and the field is remounted so what it shows is what is sent. `CreateTask` and `CreateSchedule` now refuse a team config repo filed for another team (400 `only team "x" can submit to grain/config-x`). |
| — | Underscore IDs (`qa_infra`) sit beside hyphen IDs (`qa-infra`). Nonexistent usernames are accepted as admins. A deep link selects a team without persisting it. The task URL stays under the old team after a move. The Team dialog has no framework or backend fields. | Minor or by design, noted only. |
