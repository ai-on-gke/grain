# Deployment Operations Walkthrough — 2026-11-19

Task 7310 walked the observability and operator-control screens in a real
headless Chromium browser against real `grain demo` servers: System / Fleet
(Health, Logs, Sandboxes, Caches, Top, Pipeline, Metrics / Telemetry, Power),
Settings → Upgrade, the rail's CI page, the alerts bell and the standing
banners. Following "Two UIs" in `PROMPT.md`, every step ran on `/next/` where
`ui-ng/src/app/shell/nav.ts` and `ui-ng/src/app/app.routes.ts` provide a page,
and on classic `/` only where they do not yet.

Three real bugs on `/next/` were found and fixed in this branch, each with
Playwright E2E and Vitest unit regression coverage:

1. **F1 (`/next/ci` phone layout):** stacked standing banners plus an expanded
   shared-fault banner squeezed `.ci-split` to `0 px` height behind the phone
   bottom navigation bar, making every CI run invisible and untappable.
2. **F2 (`/next/settings/upgrade` loading & errors):** `upgradeControllable`
   defaulted to `true` before `GET /api/upgrade` answered, flashing an enabled
   `Start upgrade` form on unavailable and externally managed deployments, and
   both `GET /api/upgrade` 500 and `GET /api/upgrade/targets` 502 errors were
   silently swallowed.
3. **F3 (`/next/fleet?tab=logs` error handling):** a 500 from `GET /api/logs`
   was silently caught and reported as `"No log sources are configured on this
   deployment."`, and the Logs card's `Refresh` button became a permanent no-op.

## Findings and fixes

### F1 (fixed): `/next/ci` on a phone squeezed `.ci-split` to 0 px behind the bottom bar

- **Where:** `ui-ng/src/app/ci/ci-list.css`, `ui-ng/src/app/ci/ci-page.component.ts`.
- **Reproduction:** open `/next/ci` at 390×844 against Demo B (which carries the
  standing install notice, the global dispatch banner, and an expanded shared
  CI fault cluster). `.view-panel` was a fixed-height `overflow: hidden` flex
  column whose non-scrolling `.stage-header` (`273 px`) and `.ci-faults-banner`
  (`334 px`) plus the standing banners (`108 px` + `147 px`) pushed `.ci-split`
  to `y=924, height=0` below `.bottom-bar` (`y=752`) and `.compact-nav`
  (`y=788..844`). Tapping any CI run timed out because `.compact-nav`,
  `.bottom-bar` and `.ci-faults-banner` intercepted every pointer event. Even
  without standing banners, an expanded fault cluster left only `93 px` for the
  run list — less than one row (`123 px`).
- **Fix:** per `design/design/ui-design-book.design.md` §3 ("When a pane can
  get too short for its fixed header plus a whole item, scroll the header away
  with the content in that pane instead"), below `600 px` `.ci-view-panel`
  becomes one unified vertical scroller (`overflow-y: auto;
  overscroll-behavior: contain;`) while `.ci-split`, `.queue-pane`,
  `.ci-run-list`, and `.ci-inspector` expand in flow (`flex: none;
  overflow-y: visible`). When viewing a run on a phone (`.has-mobile-detail`),
  `.view-subtitle`, `.filter-strip`, `.ci-toolbar` and `.ci-faults-banner` hide
  while the single-row headline (`h1#ci-headline`) remains in place so the run
  inspector and its `← All runs` button appear immediately at the top of the
  screen with valid heading hierarchy (`h1` → `h2`), and `scrollTop` resets to
  `0` on open/close.
- **Verification (390×844 on Demo B):** `.ci-view-panel` occupies
  `y=307..752` (`clientH=445`, `scrollH=768`), `.ci-split` has full natural
  height (`123 px`), scrolling and tapping the first run opens
  `/next/ci/runs/…` immediately with `← All runs` at `y=398..430` cleanly above
  `.bottom-bar` (`y=752`), `← All runs` returns to `/next/ci` with the faults
  banner restored, and horizontal overflow is `0 px` in light and dark themes.
- **Regression coverage:** `CI on a phone scrolls its header, faults banner and
  runs together and opens detail cleanly @phone` in
  `ui-ng/e2e/next-deployment-operations.spec.js` (runs in both desktop and
  phone Playwright projects).

### F2 (fixed): `/next/settings/upgrade` flashed `Start upgrade` while loading and silently swallowed status & target errors

- **Where:** `ui-ng/src/app/settings/settings-instance.component.ts`.
- **Reproduction:**
  1. Delay `GET /api/upgrade` on a deployment with no upgrader (Demo A) or
     `-disable-self-upgrade` (Demo D), and open `/next/settings/upgrade`.
     Because `upgradeUnavailable` and `selfUpgradeDisabled` started `false`,
     `upgradeControllable()` was `true` before `GET /api/upgrade` answered: the
     page rendered no loading indicator and immediately flashed the target
     picker (`latest`), drain toggle, and an enabled `Start upgrade` button
     until the response arrived.
  2. Return HTTP 500 from `GET /api/upgrade`. `loadUpgrade()` caught and
     ignored the error, displayed no error alert, and left `Start upgrade`
     enabled with hardcoded `latest`/`main` fallback targets.
  3. Return HTTP 502 from `GET /api/upgrade/targets` on an enabled upgrader.
     `loadUpgrade()` silently discarded the error and left `Start upgrade`
     enabled against hardcoded `latest`/`main`.
- **Fix:** track `upgradeLoading`, `upgradeLoaded`, `upgradeError`,
  `upgradeTargetsLoading`, `upgradeTargetsError`, and a sequence guard
  `upgradeSeq`. `upgradeControllable()` now requires
  `upgradeLoaded() && !upgradeError() && !upgradeUnavailable() &&
  !selfUpgradeDisabled()`. While `GET /api/upgrade` is in flight on cold load,
  the card renders a `role="status"` loading banner (`Checking upgrade status…`,
  `data-testid="upgrade-loading"`) with no upgrade controls. Missing
  `GET /api/upgrade` access renders a `role="status"` notice
  (`data-testid="upgrade-denied"`). Status failures render a `role="alert"`
  error banner (`data-testid="upgrade-error"`) with a right-aligned `Retry`
  button and keep `Start upgrade` hidden. Target listing failures render a
  `role="alert"` banner (`data-testid="upgrade-targets-error"`) with `Retry`
  and disable the target picker and `Start upgrade` until targets load.
  `applyUpgradeStatus()` also reads `database` directly from `GET /api/upgrade`.
- **Regression coverage:** unit test `waits for upgrade status before offering
  Start upgrade, surfaces status and targets failures, and recovers on Retry`
  in `ui-ng/src/app/settings/settings-page.component.spec.ts`, and E2E test
  `Settings -> Upgrade shows loading before status arrives, surfaces status and
  targets errors, and retries cleanly` in
  `ui-ng/e2e/next-deployment-operations.spec.js`.

### F3 (fixed): `/next/fleet?tab=logs` reported `GET /api/logs` failures as "No log sources are configured" and left `Refresh` a no-op

- **Where:** `ui-ng/src/app/fleet/fleet-page.component.ts`.
- **Reproduction:** return HTTP 500 (`{"error":"log subsystem down"}`) from
  `GET /api/logs` and open `/next/fleet?tab=logs`. `loadLogSources()` caught
  and swallowed the error, leaving `logSources()` `null`, so the template hit
  `@if (!logSources()?.enabled)` and told the operator `"No log sources are
  configured on this deployment."`. Clicking `Refresh` called `loadLogLines()`,
  which returned immediately because `selectedLogSource()` was empty.
- **Fix:** store `logError` in `FleetPageComponent`, display it in a
  `role="alert"` banner (`data-testid="fleet-logs-error"`) while suppressing
  the false `"No log sources are configured"` message, and route the Logs
  card's `Refresh` button through `refreshLogs()` so it retries
  `loadLogSources()` when no source is loaded yet (and `loadLogLines()` once a
  source is selected).
- **Regression coverage:** unit test `surfaces GET /api/logs failures instead
  of claiming no log sources and recovers on Refresh` in
  `ui-ng/src/app/fleet/fleet-page.component.spec.ts`, and E2E test `Fleet
  Daemon Logs reports log-source errors and recovers on Refresh` in
  `ui-ng/e2e/next-deployment-operations.spec.js`.

## Three-angle review (Design, Functional, Adversarial)

- **Design:** all new markup uses existing design tokens (`.s-banner.readonly`,
  `.s-banner.error`, `.s-banner-text`, `.btn-tonal.s-btn-sm`,
  `.banner.banner-error`) with zero hardcoded colour literals; `ci-list.css` is
  6,045 B (well under the 8 kB component stylesheet cap); axe accessibility and
  contrast checks passed in `next-full-system.spec.js` across desktop/phone ×
  light/dark.
- **Functional:** verified all happy paths, error paths, retry/refresh
  recovery, cold load vs warm revisit, and phone list ↔ detail transitions on
  real rebuilt `grain demo` servers.
- **Adversarial:** checked stale-response races (`upgradeSeq`), missing
  `GET /api/upgrade` permissions (`upgrade-denied`), `scheduled-upgrade-banner`
  remaining visible and cancellable even when `GET /api/upgrade/targets` fails,
  and WCAG `h1` preservation when viewing CI run detail on a phone.
